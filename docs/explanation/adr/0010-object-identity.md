# ADR 0010: Objects are identified by hash, names are labels

Status: accepted (owner, 2026-11-17). Refines [ADR 0003](./0003-vault-and-store.md) (lookup tags), [ADR 0005](./0005-party-envelope-and-signing-policy.md) (party envelope) and [ADR 0008](./0008-capability-typed-ports.md) (which signer answers). Prepares [ADR 0011](./0011-key-custody-and-unlock.md).

## Amends

* [ADR 0004](./0004-data-classification.md), table of classes: a blinded handle (decision 5) is Structural, as a keyed hash; an object identity (a key hash, a content hash) stays Sensitive and is stored only sealed.
* [ADR 0008](./0008-capability-typed-ports.md), "One workflow": the sentence that whether a signature comes from the vault, a hardware wallet or a remote party "is decided by the signer that holds the key" stays. This record adds that neither the holder nor the owner's name is part of a key reference: `custody.KeyRef` becomes `{Role, Identity}` (decision 3), and a signer's answer is verified per operation. A signer announcement carries the device Profile (vendor and capabilities) of each announced handle, so the plan-time capability check of ADR 0008 runs for hardware keys attached to a remote own client (decision 3).
* [ADR 0005](./0005-party-envelope-and-signing-policy.md), "Which keys may sign remotely (M6)" and "Which refusals are sent": the cold-key rule is keyed on the most sensitive role ever recorded for the key identity, not on the role named in the demand, and it forbids answering a cold-role demand over a *network* transport. The file transport stays allowed, as ADR 0005 allows it, for the air-gap workflow. A refusal that rests on that recorded history depends on what the signer holds, so it moves from the refusals that are sent to the silent ones (decision 3). ADR 0005's M6 table refuses only the pool cold key over a network and allows hardware keys of other classes. This record is stricter: every cold role (pool cold and committee cold), vault-held or hardware-held, is refused over a network transport. The refusal of a committee-cold demand is new relative to the M6 table. A demand that itself names a cold role and arrives over a network is refused in the open; a demand that names another role for a key recorded with a cold role is refused silently. A silent refusal lets a plan pass and the demand go unanswered: it times out at the expiry of ADR 0005 and the plan reports it as unanswered (decision 3). ADR 0005's enrolment scope is unchanged; a co-signer of another operator is routed by party fingerprint and never by handle (decision 3).
* [ADR 0003](./0003-vault-and-store.md), "Records": the owner (the name and number of the artefact) in a record's associated data, in its sealed owner blob and in its lookup tag is replaced by the anchor identity of the owner, the kind and the number (decision 2). The associated data becomes the canonical CBOR encoding of `[format version, genesis nonce, record id, kind, anchor identity, number, class, record version, payload format]` (the genesis nonce is the value that ADR 0011 reads in place of ADR 0003's "workspace id"); the lookup tag is the HMAC under the index key over anchor identity, kind and number; the sealed owner blob, still padded to a fixed 160 bytes, holds the anchor identity, kind and number and no name. Names are held only by `label` records. The format version rises and the opener refuses a store of the old version (decision 4).

## Context

Today an object is found by the operator's name for its owner. `ports.Ref` is `{Name, Kind, Num}` (`spo/internal/ports/store.go`), the sealed store derives its lookup tag from name, kind and number ([ADR 0003](./0003-vault-and-store.md)), and the party-record and descriptor code resolve other objects by name. A key reference is `custody.KeyRef{Role, Holder, Owner, Device, Party}` (`spo/internal/domain/custody/custody.go`). `Holder` (vault, hardware, remote) is chosen by the command that creates the reference: `hw.holder()` in `spo/internal/adapters/cli/hardware.go`, `loadStoreKeys` in `party_signer.go`, and a `switch key.Holder` in `native/opcert.go` and `native/registry_signer.go`. By `grep` over `spo/`, 45 non-test lines contain `KeyRef{` (105 with test files), 39 of them setting `Holder`; 50 non-test lines contain `Holder:` (162 with test files), which also counts other structs that carry a holder (request types, `pool.Slot`).

Three consequences follow, and the owner's requirement R1 rules them out. A fourth is in the store itself: the associated data and the lookup tag of every sealed record bind the owner's *name* ([ADR 0003](./0003-vault-and-store.md), "Records"), so a name is not only a label at the edge but part of how each record is sealed.

1. A use case written against a name cannot run against a store it does not share. Two machines that call a wallet `alice` may mean different keys, and nothing detects it.
2. The holder is part of the reference, so "the same key, signed locally or over a network" is two different references.
3. Names are bound to keys by convention. The import work that is in progress found this three times: a pool descriptor whose `poolOwner[].ownerName` pointed at a wallet of the same name with different keys. The code now defends against it with a check of the final workspace (`internal/app/workspace/import_binding.go`, "Gate B", SPO-Xmulti-INV-007), which recomputes the binding from the key files. The check exists because the model lets the mistake happen.

R1 requires that a wallet plugged into this machine, and the same wallet attached to another machine reached over tailcat or direct Tailscale, are indistinguishable to a use case, and that the server knows which object is which, without learning chain identities (R4). A name cannot do that. An identity can, and a blinded handle of it (decision 5) lets the server tell objects apart.

## Decision

### 1. Every object has an identity that is a hash

| Object | Identity | Hash and encoding |
| --- | --- | --- |
| Payment, stake, pool cold, DRep, committee cold and hot, policy (verification-key) key | key hash | Blake2b-224 of the 32-byte Ed25519 verification key. This is the ledger's credential hash (`txbuild.KeyHash`, `domain/txbuild/witness.go`); the pool id is the cold key's hash; DRep and committee ids follow CIP-0129 (a header byte before the hash in the bech32 form only; the status of CIP-0129 is unconfirmed) |
| Native-script policy | script hash | Blake2b-224 of the tag byte `0x00` and the script CBOR, as the ledger defines it (unconfirmed against the ledger specification; the code computes the Plutus form in `txbuild/plutus.go`) |
| VRF key | VRF key hash | Blake2b-256 of the 32-byte VRF verification key, as in a pool registration certificate (unconfirmed against the ledger specification) |
| KES, BLS, Catalyst voting, Calidus key | key hash by project rule | Blake2b-224 of the verification key where the ledger or CIP defines a credential hash; otherwise Blake2b-256 of the raw verification key. The Calidus id of CIP-88 is unconfirmed. A KES key also has a number; the number is a property, not part of the identity |
| Transaction | transaction id | Blake2b-256 of the body CBOR exactly as built or received, never re-encoded (`txbuild/witness.go`); exempt from the canonical check below |
| Pool metadata file (`metadata.json`), extended and additional metadata, governance anchor documents (CIP-100, CIP-108, CIP-119) | hash of the file's bytes | Blake2b-256 of the exact bytes as received or published, with no domain tag. The on-chain value is the same hash over the raw file bytes (the metadata hash of a pool registration certificate, the anchor hash of a governance certificate or vote), so the identity equals it; the bytes are never parsed and re-serialised. Exempt from the canonical check below |
| Certificate, vote file, governance action file and witness file in cardano-cli text-envelope form | hash of the CBOR payload bytes as given | Blake2b-256 of the bytes the `cborHex` field decodes to, exactly as given, with no domain tag. The wrapper (`type`, `description`) is not part of the identity; the typed reference carries the kind. These bytes are what other tools and the ledger read and, for a witness, what a body hash was signed against; they are never re-encoded. Exempt from the canonical check below |
| Envelope (ADR 0005) | hash of the sealed bytes | Blake2b-256 of the bytes as received or sent, since signature and encryption are over those bytes. Exempt from the canonical check below |
| Pool descriptor, witness collection (a record of slots around transaction and witness bytes that keep their own identities), pending record, party identity document, audit event; every other object that `spo` itself defines | content hash | Blake2b-256 over the canonical CBOR encoding (RFC 8949 section 4.2) of the two-element array `[tag, value]`, where `tag` is a text string, a fixed label per object kind (`spo/obj/v1/pool-descriptor`, ...), and `value` is the object's canonical encoding. Equal bytes of two kinds therefore have two identities. A concatenation of tag and bytes is not used, because one tag is a prefix of another (`spo/obj/v1/pool-descriptor` and `spo/obj/v1/pool-descriptor/map1`) and the two could be made to produce the same input. For an object mapped from JSON the tag also carries the version of the JSON-to-CBOR mapping (`spo/obj/v1/pool-descriptor/map1`), so a change of mapping changes identities visibly |
| Party | fingerprint | unchanged: a hash over the two public keys ([ADR 0005](./0005-party-envelope-and-signing-policy.md)) |

**References are typed.** A reference from one object to another is `(kind, hash)`, never a bare hash, so a hash of one kind cannot be read as another and a resolver knows which table to consult.

**Canonical encoding** is RFC 8949 section 4.2 core deterministic CBOR, the mode `platform/seal` already uses for associated data (`seal.EncodeCanonical`, `seal.go`). Decoding an object that `spo` defines and that is to be hashed or stored rejects non-canonical input: the decoder re-encodes the decoded value and refuses unless the bytes are equal. The pool descriptor (`pool.json`), which upstream stores as JSON, is decoded, mapped to a typed value and encoded as CBOR for hashing; its JSON bytes are never the hashed form, because key order and whitespace would change the identity.

**Exemption: bytes whose hash is defined outside this project.** Every row of the table marked exempt is identified by a hash of the exact bytes and is never re-encoded: the transaction body, its auxiliary data and a script (the ledger hashes them as received); pool metadata JSON and the other metadata and anchor files (the hash on chain is over the raw file bytes, and a re-serialised file has another hash, so the registration certificate would no longer match the file the operator publishes); certificates, votes, actions and witnesses in text-envelope form (the CBOR payload as given); and envelopes. The ledger accepts encodings that are not core deterministic (indefinite-length items, other map key orders, as other wallets produce them), and a witness is over the hash of the body bytes, so re-encoding a body would give another transaction's id and every witness over it would fail. For these objects the exact bytes are the identity and the decoded form is for display and review only; a signer signs the hash of the bytes it was handed, never of a re-encoding. The rule does not extend to objects that `spo` itself defines (descriptors, records, audit events), which stay canonical. A test per exempt row pins it: a body in a non-canonical encoding, a metadata file with other key order and whitespace than a re-serialisation would give, and a certificate with indefinite-length items must each keep the identity of their input bytes.

A mutable object (a pool descriptor that changes) is a chain of immutable versions: each version has its own content hash and names its predecessor by hash. Decision 2 states which objects are mutable and how the newest version is found.

A key's identity does not contain its role. The same verification key can serve two roles; the role is a property of a use and is checked at the point of use (`custody.As`, ADR 0008). The workspace records every role a key identity has been used or imported in, per identity; the set only grows (decision 3 uses it). The role history is a workspace record (kind `role-history`, keyed by the key identity as its own anchor and number 0, decision 2), so it is the same on every client of the workspace.

### 2. An owner is an aggregate with an anchor identity; names are labels

**What a label points to.** A name groups many artefacts today (`ports/store.go`): a wallet has a payment key, a stake key, `addr`, `staking.addr` and certificates; a pool has a cold key, a VRF key, numbered KES keys, operational certificates, counters and a descriptor; a DRep, a committee member and a policy likewise. The unit a name points to is an **owner**, an aggregate identified by its **anchor identity**:

| Owner | Anchor identity |
| --- | --- |
| Pool | the pool cold key hash (the pool id) |
| Wallet | the payment key hash when the wallet has a payment key at creation or first import, otherwise its stake key hash |
| DRep | the DRep key hash |
| Committee member | the committee cold key hash |
| Policy | the policy id (the script hash) |

**The anchor rule is deterministic and stable.** The anchor is chosen once, when the owner is created or, for an owner that comes from an upstream directory, when it is first imported. It is fixed thereafter: it travels with the owner record on export and import between workspaces and is never recomputed. A wallet created payment-only keeps its payment key hash when it gains a stake key; a wallet created stake-only keeps its stake key hash when it gains a payment key. The store migration (decision 4) applies the same rule over the keys it finds.

**Residual case.** A wallet created stake-only that later gained a payment key has a stake-hash anchor, whereas the same keys imported elsewhere from a plain upstream directory get a payment-hash anchor. When the two meet (an import or an export into a workspace that holds the other), the membership check below detects that one identity would belong to two owners and refuses, showing both. The operator then resolves it explicitly with `merge`: two owners with identical member sets become one. One anchor is kept (by default the one already in the destination workspace); the other is recorded as an alias in the owner record, and a later import or export that carries the alias resolves to the kept anchor. Two owners whose member sets differ cannot be merged; the operator adds the missing member to one of them first.

**Membership is unique.** An identity is a member of at most one owner. A second claim (an import, a new owner or a manifest that lists an identity already listed under another owner) is refused with both owners shown, as a second label for one name is. The role history of an identity stays per identity (decision 1) and does not belong to an owner. The check of member identities against the owners runs on every open of the store, not only at migration.

**Labels, owner records and manifests.** A label maps `(kind of owner, name) -> anchor identity`, per workspace. It is stored as a sealed record of kind `label` (one per kind of owner and name) that the operator may change, and the set of `label` records is the **label index**. A `label` record holds only `(kind, name) -> anchor`. At most one label names an anchor in a workspace; a second label for the same anchor is refused. A `label` record is an ordinary record, enumerated as records are. The label records are the only place that holds a name. Renaming a wallet rewrites one `label` record and no other record.

Owner existence and membership never sit under a mutable name record. They are held by an **`owner` record**, keyed by `(anchor, kind owner, 0)`, which holds the hash of the owner's current owner manifest and the aliases of any merge.

**The owner manifest** is an immutable, content-hashed object (identity by the `[tag, value]` rule of decision 1) that lists the member identities of one owner by role (for a wallet `payment` and `stake`; for a pool `cold`, `vrf`, and the KES keys by number) and names the anchor it is bound to. Manifests are append-only: members may be added (a stake key, a new KES key), never replaced or removed; removing a member is a new owner. Adding a member writes a new manifest version that names its predecessor by hash, and the `owner` record is rewritten to point at it. A manifest whose anchor does not equal the anchor of the `owner` record that points to it is refused.

**References between objects hold identities, not anchors.** A pool descriptor lists its owners and its reward account by stake key hash, and its VRF key by VRF key hash. A stake key hash is a member identity and is the credential the chain itself uses for an owner and a reward account; it is not the anchor, which is a workspace-internal choice that may be a payment key hash. A reference resolves to the unique owner whose manifest lists that identity, which membership uniqueness makes unique.

**Records are keyed by `(anchor identity, kind, number)`.** ADR 0003 binds the owner *name* into a record's associated data and its lookup tag, so with that design a rename would change the lookup tag and the associated data of every record of the wallet, which means re-sealing them. Here the associated data binds the anchor identity, the lookup tag is derived from anchor identity, kind and number, and the sealed owner blob holds them. The number exists where the kind is numbered (a KES key, an operational certificate). Derived and unkeyed files (`addr`, `staking.addr`, `kes-expire.json`, pending updates, metadata files, descriptors) are records of their owner keyed the same way, and carry their own content hash as object identity where decision 1 gives one. A kind that has no owner (workspace settings, provider tokens) uses as its fixed anchor the hash of `[tag, ""]` under the rule of decision 1. A `label` record's anchor is the hash of `[tag, [kind of owner, name]]`, and its name is in the sealed payload, so the name never enters the associated data in clear. The text of ADR 0003 changes accordingly (see Amends).

**Ownerless and multi-owner objects.** Content-addressed records (transactions, party envelopes, witness collections, audit events) have no single owner: each is keyed with its own identity as anchor and number 0. A pending record names exactly one owning anchor.

**What is mutable.** Objects are immutable once written, with these exceptions, each a chain of versions and not an overwrite: the KES counters and operational-certificate counters (a counter is a record of the pool's owner, keyed by the anchor, its counter kind and the number of the key it counts, and its version only rises), the label index (the `label` records), the manifest pointer and aliases of each `owner` record, the role history of an identity (it only grows), and the deletion of pending records. A pool descriptor or any other object the operator edits is a new immutable object that names its predecessor, and the owner's record of that kind (keyed by its anchor, kind and number) is rewritten to name the newest version; that pointer is among the mutable exceptions.

Names remain at the adapter edge. Reading an upstream directory resolves each `ownerName` to an identity using the files of that directory, and refuses when the wallet found under that name does not hold the key the descriptor's witness or registration data names. Writing an upstream directory writes the label back. A name that two labels would claim is an error at import, with both identities shown. Consequently the Gate B check of the current import code becomes the resolver's own post-condition: after resolution there is nothing left to check by name.

### 3. A signing demand names an identity, and no holder

`custody.KeyRef` becomes `{Role, Identity}`: it loses `Holder`, `Owner` (the operator's name for a pool, wallet or DRep), `Device` and `Party`. Where a name is needed to show a key, the adapter at the edge resolves it from the `label` records; `KeyRef.String()` prints the role and the identity. What `Device` narrowed (a hardware vendor profile) is known to the hardware signer once its session is open and is not part of the reference. A demand is `(key identity, role, operation, payload)`. The payload is the full input of the operation, not a hash of it: for a transaction the body CBOR with its auxiliary data, for an operational certificate the KES key, counter and period, for a CIP-36, CIP-88 or CIP-8 message the message itself. The signer rebuilds the exact message to sign from the payload and the operation, and never signs a hash that was handed to it. ADR 0005's request already carries the body; this makes it the rule for every operation. The plan of ADR 0008 is built from the signers connected now.

**SignerDirectory.** Removing `Holder` from the reference requires something that says who can answer. That is `ports.SignerDirectory`, a port local to each client (it is not stored in the workspace and not shared): it maps a key identity to the signers currently able to answer for it, namely the local vault, each attached hardware device with its Profile, and each connected remote. `KeyRef{Role, Identity}` and the SignerDirectory ship in the same change; neither is built without the other.

**Two kinds of remote peer, kept apart.**

* **Own clients** are other machines of this operator that hold this workspace's master key. They are enrolled under [ADR 0005](./0005-party-envelope-and-signing-policy.md) as the operator's own clients, distinct from co-signers; how a server learns them is the subject of a later record. They alone can compute blinded handles (decision 5).
* **Co-signers** ([ADR 0005](./0005-party-envelope-and-signing-policy.md)) are other operators. They hold no master key of this workspace, so they cannot compute its handles, and they are never enrolled as own clients. They are *mailbox-only parties*: enrolled under ADR 0005, able to deliver and fetch envelopes addressed to them and nothing else. A signing demand for a key held by a co-signer is routed by the party fingerprint that ADR 0005's slot assignment records for that key, through the envelope; no handle is involved. The co-signer's answer is verified like any other (below). Blinded handles are used only inside one workspace, among clients that hold its master key.

The entries of the SignerDirectory are *connected signers*:

* the local vault (all its keys), each attached hardware device (the keys it has exported verification keys for), each own client reachable over a transport, and each co-signer party reachable through the envelope (for the keys ADR 0005's assignment gives it);
* An own client announces only the key handles (decision 5) inside its enrolment scope, never its whole inventory, which would defeat ADR 0005's rule that a signer does not disclose what it holds. Each announcement carries, for the handle, the Profile of the device that holds the key (vendor and capabilities, [ADR 0008](./0008-capability-typed-ports.md)), so that the plan-time capability check can run for a hardware key attached to a remote client. Each announced handle of a non-cold key carries proof of possession: a CIP-8 `COSE_Sign1` structure (CIP-8, message signing, RFC 9052) signed by the key with its own algorithm (EdDSA for Ed25519 keys). The signed message is the canonical encoding of the genesis nonce (ADR 0011, Amends), a context tag that no transaction or message can carry, a random value drawn by the verifier and a random value drawn by the signer, so that the verifier cannot choose the message and the proof can never serve as a CIP-8 signing oracle for a message of the verifier's choosing. Whether the CIP-8 protected header may carry the key hash in place of an address is unconfirmed; if not, the context tag goes in the payload. A key that has no COSE algorithm (KES, VRF) or a hardware key that cannot sign such a challenge is accepted on the first verified witness instead. **A key whose recorded roles include a cold role (pool cold, committee cold) never signs a proof-of-possession challenge**, because a signature over a challenge is the answer that the cold-key rule withholds from a network peer, and a peer could otherwise ask a cold key to sign a chosen message. Its presence is established only by a witness over a real operation that the planner demanded, verified as below, and until then the planner treats the client as possibly holding it. An announcement of a cold-role handle is a claim with no proof, and it never routes a demand over a network.
* `SignerFor(identity)` returns the connected signers that report holding it. With none, planning fails with the same error as today for an unavailable holder. With more than one, the operator's preference decides (a label attribute `prefer`), and the plan states which.
* Every witness is verified before use, and the verification is specific to the operation: the transaction id and the witness over it for a transaction, the operational certificate's signature and its fields for an opcert, the message form and signature for CIP-36, CIP-88 and CIP-8. The verification key's hash must equal the demanded identity. One function per operation in `custody` is the only verifier; the existing check in `pool.Collection.Fill` (M3) becomes one of them. A wrong signer, a wrong device account or a hostile remote cannot be accepted, and the use case cannot tell holders apart because it never sees one.
* The capabilities that [ADR 0008](./0008-capability-typed-ports.md) checks (the `Profile` of a signer) are those of the signers connected at planning time. Unplugging a Ledger before the plan makes its keys unavailable and a demand for them fails in the plan, not in the signing call.
* **The cold-key rule.** [ADR 0005](./0005-party-envelope-and-signing-policy.md) allows cold-key signing over the file transport, which is the air-gap workflow of the operator's own offline machine, and forbids it over a network transport. The rule here forbids answering a cold-role demand over a *network* transport; it does not forbid a remote signer as such, and an own client reached by carried file answers cold-role demands. It is keyed on the most sensitive role ever recorded for the key identity (decision 1), not on the role named in the demand: a key identity that was ever a pool cold key is never answered over a network transport, whatever role the demand names. The identity is the same, the policy decides whether that transport may answer. Because the refusal depends on the signer's private role history, it is *silent* under ADR 0005's non-disclosure rule: it sends no reply, and from outside it cannot be told from "no such key". The planner does not send such a demand over a network at all; the signer enforces the same rule again on receipt. A silent refusal lets a plan pass without being answered. Such a demand times out at the expiry of ADR 0005, and the plan reports it as unanswered, naming the demand, and never as refused.
* A remote signer, own client or co-signer, is a connected signer. The party envelope is the transport of its answers. A use case that today calls `RequestSignatures` for a slot with `HolderRemote` calls the same planning code as for a local key.

### 4. Migration from the name-keyed store

* The format version of the store is raised; the opener refuses a store of the old version and says which command migrates.
* Records keep their random ids. Because the associated data changes (see Amends), the migration re-seals every record under the same master key, in one transaction: the payload with a fresh nonce, the data key re-wrapped, the owner blob rewritten with the anchor identity and number in place of the name, and the lookup tag recomputed from anchor identity, kind and number. The master key is unchanged, so this is not a rekey and does not rotate data keys; it appends an audit row that records the migration.
* A new record kind, `label`, maps `(kind of owner, name)` to an anchor identity, and a new kind, `owner`, holds the owner's manifest pointer and aliases (decision 2). The migration reads each key record and derives its verification key hash. It determines the anchor of each name's owner by the rule of decision 2 applied to the keys present: the payment key hash of a wallet that has a payment key, otherwise its stake key hash; the cold key hash of a pool. It writes the owner manifest, the `owner` record and the `label`, and rewrites each descriptor's owner and reward references from names to stake key hashes. It refuses, with a list, when a name in a descriptor resolves to no key or to keys that disagree with the descriptor's own registration data, and when one identity would be a member of two owners. That is exactly the import defect, found once for existing stores. The explicit per-pool option `--quarantine` lets the migration proceed and leaves the named unresolved pool unusable until the operator fixes it.
* **Collisions when names stop being part of the key.** Two records of one owner that map to the same `(anchor identity, kind, number)` merge when their bytes are identical. When the bytes differ, the migration refuses for that owner and lists the colliding records; with `--quarantine` the owner is left unusable as above. An `UpstreamEncryptedSKey` has no identity of its own, because its key is encrypted under a password the migration does not have. Its identity is taken from the sibling verification key record of the same name. With no sibling verification key, the record is quarantined.
* `custody.KeyRef` becomes `{Role, Identity}` in one change across the code that constructs it (39 non-test `KeyRef{` lines that set `Holder`, 45 non-test lines with `KeyRef{` in all, by `grep`; `internal/app/{poolops,wallet,governance,stake,catalyst,poolkey,assets,poll,registry}` and `internal/adapters/{cli,hwcli}`); `hw.holder()` becomes a flag that says where a new key is generated, which is a command option and not a property of the reference afterwards.
* **The persisted witness slot.** `pool.Slot` (`spo/internal/domain/pool/witness.go`) carries `Holder` (vault, hardware, remote) and `Party`, which today holds a party *name*; both are written into the `regWitness` descriptor as JSON `holder` and `party`. Decision: `Holder` is dropped from the type and from the JSON, because who signs is decided by the signer directory at planning time (decision 3) and a stored holder would be a second source of truth; an old `holder` key is ignored on read. `Party` becomes `PartyFingerprint`, the ADR 0005 fingerprint of the party the slot is assigned to, written as the new JSON key `partyFingerprint` holding the fingerprint in hex. The key `party` is not reused, because a party name written in hex cannot be told from a fingerprint; `party` is read only by the migration, which resolves it as a name and never writes it back. The field is an assignment (a routing instruction for a co-signer), not a holder, and it must survive a rename of the party. Migration: for each stored collection the migration resolves each slot's party name through the party registry to its fingerprint; a name that no longer resolves leaves the slot unassigned, as `Collection.Unassign` leaves it, and the migration lists it. Display (`party_exchange.go`) prints the label of the fingerprint. `pool.Slot.Name` forms such as `<pool>.node` and `<owner>.staking` embed an owner's name; they are derived at export only, from the label, and are never stored as an identity. The stored slot names the key identity it needs.
* `ports.Ref` becomes `{Anchor, Kind, Num}`; a use case resolves a name to an anchor identity through the labels before it calls the store, and the store never sees a name.
* A migration check compares, for every record, the member identity that its owner manifest lists for it with the identity recomputed from the opened payload (for keys, the verification key hash; for content-hash kinds, the hash of the payload), and the anchor in its owner blob with the anchor of its owner, and refuses on a difference. It also runs the membership-uniqueness check of decision 2 over the migrated owners. The same check runs on every open of the store, not only at migration.

### 5. What the server learns: blinded handles

No server or sink sees a key hash, because a key hash links a network identity to a pool id and its funds. For each object it sees a **handle**: HMAC-SHA-256, under a handle key, over the domain tag and the object's identity. The handle key is derived from the master key by its own HKDF-SHA-256 label (`spo/handle/v1`), distinct from the label of ADR 0003's lookup-tag index key, so that a tag and a handle of the same name never coincide and one key's exposure does not give the other. Handles let the server tell objects apart, deduplicate, and route a signing request between *own clients* that announced the handle (decision 3), without learning a chain identity. Only clients that hold the master key can compute them; a co-signer cannot, and is routed by party fingerprint instead. Without the handle key a guessed identity cannot be tested against a handle, and the same identity has different handles in two workspaces.

What the server can still infer: how many distinct handles exist; which handles occur together in a commit or request; which authenticated own client announced which handle, and therefore which client holds which key; how often and when each is used; and the size of the sealed objects behind them. A rotation ([ADR 0011](./0011-key-custody-and-unlock.md) decision 6) replaces every handle at once, so the server can link each old handle to its new one by position in that commit and by identical size; rotation does not unlink an object from its history on the server. Handles are classed Structural in [ADR 0004](./0004-data-classification.md), as keyed hashes (see Amends).

### 6. Staging

Build now: ADR 0011 decisions 1-2 (plaintext paths removed, plain store test-only, release check, `key convert`); `ports.FactorSource` with a stand-in (with flags and factor id); the identity table with the `[tag, value]` rule, the canonical check and the per-operation witness verifiers; `KeyRef{Role, Identity}` together with the local SignerDirectory. After the owner approves 0010: owner records and manifests, label index, records keyed by anchor, the store migration. After the owner approves 0011: slot kinds and policies on disk, the cold-role sub-key, rotation. Server, object store and S3 wait for ADR 0012.

Handles (decision 5) and remote announcements (decision 3) are built with the server stage named above.

## Alternatives considered

* **One hash for every key, including role.** Rejected. It would make one verification key two identities and would break the ledger equality that makes a witness checkable by hash.
* **Blake2b-224 for every key.** The lead's rule says the ledger hash. The ledger does not use one length: VRF keys are hashed to 32 bytes, and a KES verification key has no ledger hash of its own. A single-length rule would collide with nothing but would not match what a registration certificate contains. The table keeps the ledger's choice where one exists.
* **Random ids as identity (as records have today).** Keeps names mutable and needs a mapping, but a random id cannot be recomputed by a second machine from the key, so two stores could not agree that they hold the same wallet. Records keep random ids as storage keys ([ADR 0004](./0004-data-classification.md) forbids deriving them from an address, a pool id or a name); identity is a separate, public-hash field.
* **Raw key hashes visible to the server.** Rejected for the reason in decision 5.
* **Content hash of JSON bytes.** Rejected for the reason in decision 1.

## Consequences

* A key's identity is public on chain once used, but ADR 0004 treats the link to this operator as Sensitive. An identity stored in the clear would leak that link; identities are therefore sealed inside records, and the server sees handles only. R1 and R4 are both met, with the inferences listed in decision 5.
* `spo` gains the same behaviour for a local vault, a hardware device and a remote client with no new use-case code: only a new `SignerDirectory` adapter and the removal of `Holder`.
* Import and export lose their name-binding defence as a special case; the resolver is the one place that binds names.
* A rename touches one `label` record. Records, lookup tags and associated data no longer contain a name.
* A descriptor edited by the operator is a new object each time. History is kept for free; storage growth is small.
* Every use case that builds a `KeyRef` changes. The compiler finds them all.
* An identity belongs to one owner, checked on every open; an operator who meets the residual anchor case of decision 2 resolves it with an explicit `merge`.

ADR 0012 (draft) builds on this record.

## Open questions

The owner accepted this record on 2026-11-17. The entries marked unconfirmed remain open.

* Whether the VRF, KES, BLS and Catalyst hash lengths above match the ledger and the CIPs; none was checked against a primary source here.
* The Calidus id derivation (CIP-88) and the CIP-0129 status are unconfirmed.
* Whether a mnemonic-derived software wallet that is later also attached on a hardware device (same key, two connected signers) should prefer the device, the vault or ask. The draft says "the operator's preference".
* Whether labels are per workspace or global per client. Per workspace is assumed, and `label` records live in the workspace's own records.
* Migration of a store whose descriptors do not resolve to keys. Recommended: refuse, with an explicit per-pool `--quarantine` that leaves the unresolved pool unusable; needs the owner's decision.

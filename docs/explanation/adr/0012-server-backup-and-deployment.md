# ADR 0012: Server, backup and deployment

Status: draft, revised after security review, 2026-11-17; not yet approved. The trust model (root, devices document and head chain) and the object layout need the formal model and a further review of decision 3 before approval (decision 13). Extends [ADR 0003](./0003-vault-and-store.md) (rollback and backup), [ADR 0005](./0005-party-envelope-and-signing-policy.md) (enrolment, envelope) and [ADR 0008](./0008-capability-typed-ports.md). Depends on [ADR 0010](./0010-object-identity.md) (identities, handles; accepted) and [ADR 0011](./0011-key-custody-and-unlock.md) (unlock, slot policy, rotation; accepted, 2026-11-17; its "Amendments" section is proposed, not accepted, and is cited here as "ADR 0011's proposed amendment"). Closes none of the numbered concerns; it supersedes the deferral in decision D9 ("a server API stays deferred") and meets S2 for several replicas.

## Changes in this revision

What moved after the security review (blockers B, then should-change items S). Each is marked again where it is decided.

* **Decisions 3 and 10, takeover and re-genesis (B1).** They no longer re-seal only the outer layer. Cold records are opened through their recovery wrap or old factor, and sealed again under the live factor and the live recovery public key; otherwise the operation is refused and the records are named. The unlock each needs is stated.
* **Decision 12, the client agent (B2).** Removed from this record. It needs its own record; the constraints it must meet are listed.
* **Decision 3, slot changes (B3).** A head whose slots hash differs from its predecessor's must carry a devices-role signature (namespace `spo/slots/v1`).
* **Decisions 2 and 4, object layout (B4).** Kind and class are sealed inside the object; the plaintext header holds only format and epoch; every class is padded to a power-of-two bucket; cold and hot records share an outer shape; clients fetch whole snapshots. The "what the server sees" table is rewritten. `meta` now has a home (the slots object).
* **Decisions 3, 9 and 10, freshness (B5).** The pin is (root version and hash, devices version, head sequence and hash); a signed `location` statement names the live store; a copy without it is read-only; `store promote` is added.
* **Decision 3, split view (B6).** A second head log in the backup sink under separate credentials; clients require agreement; creating a Secret-class record needs freshness corroborated within minutes. Witness cosigning is named as the later option.
* **Decision 11, Kubernetes (B7).** Block producers in Kubernetes are out of scope for v1; what a later design needs is recorded. The cluster runs the server only.
* **Decisions 2, 5, 7 and 8, handles (S1).** Preferred: no server-visible handle; the sealed ADR 0005 envelope is fanned out to the operator's own devices. The handle construction is specified as the fallback, with its leaks.
* **Decision 3 (S2, S3, S8).** The devices-role credential is on a different authenticator from every daily slot; the note text is shown before signing; the server verifies a head before appending it; a workspace with no pool gets a devices-role operator attestation as its corroboration source. The undefined signature type `0x22` is removed.
* **Decisions 4 and 9 (S4, S11).** Short-lived federated credentials for S3 only; bucket policy; separate account with Object Lock; the built restore refusals are kept for the layout.
* **Decision 5 (S5, S6).** Ports split so none has an unsupported half; every object-store or mailbox envelope is `NetworkTransport`. `sealedstore` must re-implement more than the draft said.
* **Decisions 6 and 10 (S9).** One canonical store per workspace id; `store convert` retires the SQLite file; a `hardware` SQLite backup is verified through factors.
* **Decisions 3 and 4 (S10).** The home-made protocol pieces are modelled with test vectors before the format is frozen; multi-writer direct-bucket mode is dropped from v1.
* **Decision 7 (S7, S12).** Remote answers from own clients go through the full ADR 0005 signer path; the multi-tenant server has an allow-list, per-workspace prefix and quota, and an audit log.
* **Decision 13.** Staging replaced; "after the owner approves 0010/0011" replaced by what is built.
* **Open questions for the owner** added as a numbered section.

## Amends

* [ADR 0003](./0003-vault-and-store.md), "Rollback": for the sealed object store, the unauthenticated head file is replaced by the signed head chain of decision 3. The SQLite file keeps its head file until it is demoted to a cache (decision 6).
* ADR 0003, "Backup and recovery", `restore`: for the sealed object store, `--allow-older` opens an older head **read-only**; it is not a way to write over a newer workspace (decisions 9 and 10). The SQLite `restore` is unchanged until demoted.
* ADR 0003, associated data: the "workspace id" bound in slot and record associated data is the genesis nonce (amendment stated in [ADR 0011](./0011-key-custody-and-unlock.md), Amends; decision 3 here uses it). The workspace id of this record is the hash of root version 1 and is not bound there.
* ADR 0003, "What the file reveals without the passphrase": for the sealed object store the exact length of Sensitive payloads, the kind and the record version are no longer visible; decision 4 replaces the list.
* [ADR 0004](./0004-data-classification.md), table of classes: the **root documents**, the **devices documents**, the **location statements** and the **slots object** (decision 3 and 4), which list root public keys, the keys of the devices role, device public keys, party fingerprints and their cross-signatures, the slot table and policy, are Structural and stored in plaintext. ADR 0004 classes a link between an operator and a public-on-chain value as Sensitive; a device key and a party fingerprint are not public on chain, but they identify the operator's machines and co-signers. What an observer of the bucket or server learns from them: how many machines the operator enrols and how many co-signers they have, the fingerprints and public keys of each, when each was enrolled or removed, which device signed which head, when the root, the devices document or the slots changed, and commit timing. It does not learn a name, a pool, a key hash or what a co-signer signs. Each workspace enrols its own device key (decision 3), but the cross-signed party fingerprint is the same in every workspace the machine joins, so an observer of two buckets can link an operator's machines across workspaces by that fingerprint (open questions).
* [ADR 0010](./0010-object-identity.md), decision 5 (blinded handles, accepted but not built): if the owner accepts the envelope fan-out of decision 7 (owner question 4), the server never sees a handle and decision 5 of ADR 0010 is not used for the server stage; its handle construction survives only as the fallback specified in decision 7.
* [ADR 0005](./0005-party-envelope-and-signing-policy.md), enrolment: a party is enrolled either as one of this operator's head-signing **devices** or as a **mailbox-only party**, both listed in the devices document (decisions 3 and 7); this is how a server learns the own clients that ADR 0010 leaves open. ADR 0005's ceremony is reused, and an enrolment carries the pin (decision 3). ADR 0005's approval gate is amended in ADR 0011. ADR 0005, "The transport kind": every envelope that comes from a `Mailbox` or an object-store adapter is `NetworkTransport` (decision 5).
* [ADR 0008](./0008-capability-typed-ports.md): the new ports are split by capability (decision 5).
* [ADR 0002](./0002-architecture-and-dependencies.md), "Layout" and "Third-party modules", in addition to the amendment of [ADR 0011](./0011-key-custody-and-unlock.md): `adapters/sealedstore` (the `Store` and `Vault` over an object store and a head log), `adapters/objstore/{dir,s3,gcs}` (the object and head back ends) and the server adapters of this record are added. Modules: `golang.org/x/mod/sumdb/note` for the signed-note framing, if adopted (confined to `adapters/sealedstore`; unconfirmed, open questions); `golang.org/x/crypto/ssh` for the SSHSIG signatures (decision 3; in `go.mod` as an indirect module today, unconfirmed); the S3 and Google Cloud Storage clients (`adapters/objstore`); `ssh-keygen` as a pinned external tool for root signing. Each enters the `confined` table of `spo/internal/archtest/arch_test.go`.

## Context

Requirements R1, R4, R6 and R7 of the owner: any client, local or reached over tailcat or Tailscale, acts on committed objects without a difference; on a highly available Kubernetes deployment too; the server cannot decrypt; backups go to a sink such as S3 or a directory and can be re-imported; the same design runs as a Kubernetes deployment and as a local deployment that uses the backup artefact directly.

The owner's requirements, as the security bar of this record: securables like cold keys must be encrypted at rest and no insecure mechanism is tolerated; unlock is more than a password (FIDO2, passkeys, Vault backends); the server has no way to decrypt on its own; standard, well-adopted processes are used (age, HPKE RFC 9180, SSHSIG, C2SP signed notes, RFC 9421, TUF's rules, S3 Object Lock); backups go to a sink and re-import; the application runs as a Kubernetes deployment and as a local deployment that references the backup artefact entirely.

**What exists today** (handoff, store format 3). One SQLite file per workspace, opened by one process that holds the unlocked keys ([ADR 0003](./0003-vault-and-store.md)). The file carries a slot table with a policy (`standard`, `hardware` or `strict`) and the recovery public key hash bound in every slot's associated data; cold-role records are sealed in the cold form (sub-key plus an HPKE recovery wrap); `workspace rotate` re-seals every record, presenting the recovery composite where a cold record needs its wrap; `--unlock recovery-composite` is limited to `workspace rotate`, `workspace policy set` and `store slots`; `store restore` refuses a weaker policy unless told, restores through factors and takes the larger operational-certificate and KES counters; `node export` writes age ciphertext and the separate `spo-node-keys` helper is the only plaintext writer. The head file records the newest audit sequence and MAC and is unauthenticated: someone who replaces the file and its head together with an older pair is not detected (`spo/internal/adapters/sqlitestore/head.go`, "WHAT THIS DOES NOT DO"). Backup is `VACUUM INTO` plus a verification (`sqlitestore/backup.go`, `Restore*`). A multi-party coordinator today is a process with the unlocked store: tailcat serves it and the party registry is a sealed record in the same store (`adapters/tailcat/server.go`, `adapters/partystore`). The workspace file lives on a local disk because advisory locks are unreliable on network file systems (ADR 0003).

Two consequences for this record. A server that cannot decrypt cannot read the sealed party registry, so it cannot use ADR 0005's `Admit` for authentication; it needs an access list of its own (decision 7). And ADR 0004 classes anything public on chain as Sensitive, so the server holds *no plaintext object at all* except the structural ones named below: "public objects" in the working notes do not exist.

## Decision

### 1. Roles

* **Server**: stores sealed objects, a signed head log and sealed envelopes in transit; verifies and orders commits (decision 7); authenticates clients by device key. It is stateless over the object store, so any number of replicas serve.
* **Client**: any `spo` process the operator unlocked. It decrypts, runs every use case, signs with vault-held keys, drives hardware wallets attached to it, queries the chain and submits.
* **Local deployment**: a client with no server, opening a directory of the same layout directly (decision 10). A bucket opened directly has a **single writer** (one device); there is no multi-writer direct-bucket mode in v1 (decision 4).

Two sets of parties are kept apart. **Devices** are this operator's own clients: they hold the workspace's master key and can commit heads with their device key for as long as the current devices document lists them (decision 3). A device cannot change the root, the devices document or the slot table, and so cannot add or remove devices; the devices document and every slot change are signed by the operator's own FIDO2 credentials, the `devices` role that the root delegates. **Mailbox-only parties** are co-signers under ADR 0005, other operators who hold no master key of this workspace: they can deliver envelopes to, and fetch envelopes addressed to, themselves and nothing else.

The server never holds an unlock factor, a master key, a data key or a plaintext secret, and never signs with a vault-held key. Hardware keys sign on the device attached to a client. A key held by a client that is not connected cannot sign; nothing in the server can stand in. There is no other long-lived holder of the master key in this record: a client agent is not part of it (decision 12).

### 2. What the server sees, and what a compromised one can do

*Changed in this revision (B4, S1).* The table covers the sealed object store layout of decision 4, not the SQLite file.

| The server sees | From |
| --- | --- |
| For each object: its hash (the name), its stored size, one of a small set of power-of-two sizes (decision 4), its creation time, and a plaintext header of format byte and key epoch | the layout of decision 4 |
| For each commit: the set of objects written together, the head that references them, and the time. Not the kind of any object: a cold record, a hot record, an audit row and a manifest have one outer shape | commits |
| **Not visible:** the record kind, the class, the record version, the record id, the exact payload length, whether a record is in the cold form, a FIDO2 credential id or salt of a cold record, a handle | sealed inside the object |
| The slots object, readable before unlock and necessarily plaintext: slot count and kinds (`passphrase`, `recovery`, `fido2-hmac`, `composite`), the `bound`, `rec_hash` and `factors` columns, KDF parameters, the credential ids of FIDO2 slots and the relying-party id, the **policy** (`standard`, `hardware`, `strict`), the key epoch and the recovery public key hash | the slots object (decision 4) |
| Root public keys, thresholds and expiry; the keys of the devices role; device public keys, fingerprints and cross-signatures; mailbox-only party fingerprints and public keys; root and devices versions; location statements; which device signed which head; when a head changed the slots; commit rate and timing | the root documents, the devices documents, the location statements and the head log |
| For envelopes: recipient and sender party fingerprints needed to route, a padded size, time | decision 8 |
| The client's network address or Tailscale identity | transport |

*What the hardening removes.* In the draft the server saw each record's kind and version, the exact length of Sensitive payloads and the visible cold form with its credential id. Those identify a pool: the public length of a pool's metadata and certificate payloads, the opcert counter rewrite when a block producer is issued a certificate, and a cold record's credential id all appear in the plaintext of a design that exposed them. Now only a bucket size, a creation time and a header are visible per object.

*What remains (the residual leak).* **Commit timing** and the number and bucket sizes of the objects of a commit. An opcert counter bump or a KES period change is a commit at a predictable time and of a predictable shape, so an observer who knows the operator runs a pool can still guess when a certificate is issued. Padding hides what an object is, not when a commit happens. A device may commit `refresh` heads on a fixed schedule so that commits are not only caused by use; this reduces the signal and is not a guarantee. A client fetches the whole snapshot (decision 4), so the server does not learn which record is read.

R1 and R4 are met without handles by the fan-out of decision 7: the server routes between the operator's own devices by party fingerprint and never sees a key hash, a pool id, a name, a descriptor, a balance, run history, audit event text, a `label` record, the party registry or a handle. Requests to co-signers are routed by party fingerprint and carry no handle. If the owner instead keeps server-visible handles (decision 7, fallback), the server can infer the number of distinct handles, which occur together, which device announced which, and how often each is used, and a rotation lets it link old to new.

A *compromised* server can: refuse service; withhold or delay objects and envelopes; serve an older head (detected by a client that persists the newest pin it verified, decision 3); withhold newer heads (detected as a freeze when the newest head has expired, and, within minutes, by the second head log of decision 3); show two clients different histories (detected by the second head log and by comparison, decision 3); delete objects (detected as a missing hash; recovered by re-publication or restore, decision 4); learn timing, bucket sizes and the structural data above. If it can write to the bucket it can squat `heads/n+1`, or write garbage at higher numbers; clients ignore any head that is not part of the valid chain and skip it by the gap rule (decision 3). This is denial of service that is detected and recoverable, never a forgery. It cannot read any payload; forge a head, a root, a devices document or a slot change (it lacks every device key, the root keys and the devices role keys); add or alter a slot (it lacks the master key, and a slots change needs a devices-role signature); change the device set or the root keys; or make a client accept an object whose hash does not match. It can keep a client from learning a newer root or devices document until the client is shown it by another device, by the second head log or by the operator's pin (decision 3).

**Deployment precondition: the `hardware` policy.** Under the `standard` policy of [ADR 0011](./0011-key-custody-and-unlock.md) the passphrase slot can be guessed offline by whoever holds the bucket or the server's storage, bounded only by the Argon2id parameters. A server or bucket deployment therefore requires the `hardware` policy (or `strict`): the sealed object store refuses a bucket or server back end for a workspace whose slots object says `standard`. A `standard` workspace is local-only; the existing filesystem backup of it keeps the warning that states the offline-guessing exposure, and an S3 backup of it is refused (owner question 8).

### 3. Integrity with an untrusted server: a signed root, a signed devices document, and a signed, hash-chained head

**Model.** Trust is anchored in a **root** document held by the operator, not in anything derived from the master key. The roles, thresholds, rotation, rollback and freeze rules are those of The Update Framework (TUF specification, version 1.0.37 of 8 October 2026; the roles in section 2.1, root key rotation in section 6.1, the client's root update procedure in section 5.3, the attacks in section 1.5.2; the version and section numbers were read from the published specification). The mapping:

| Here | TUF |
| --- | --- |
| Root document (versioned; root keys and threshold; the keys and threshold of the delegated `devices` role) | Root role, section 2.1.1 |
| `devices` role and its document: the operator's own FIDO2 credentials sign a versioned document that lists the device keys, and sign every slot change | A delegation of signing authority from the root; the closest TUF notion is the keys the root names for the snapshot and timestamp roles, but TUF has no signed list of committing keys with a void rule, so the mapping is loose |
| Head: sequence number, expiry, previous-head hash, the root and devices versions it was made under | The snapshot and timestamp roles, sections 2.1.3 and 2.1.4: consistency of the set of objects, and freshness |
| Manifest (sealed list of records) | Takes the place of the targets role; it is sealed, so a locked client cannot read it |

**What TUF does not give.** TUF is designed for software update metadata: a repository of target files that many clients download and verify. This record adopts its role, threshold, rotation, rollback and freeze rules and not its file layout (its JSON metadata, consistent snapshots, delegations and mirrors). TUF's freshness rules limit but do not remove a split view; the second head log (below) is this record's answer. It does not protect a client that never learns of a newer root or devices document, beyond the expiry of what it was shown and the second head log. The loss of the root threshold is unrecoverable (below).

**Formal model (S10, changed in this revision).** The pieces of this decision that are home-made, not taken from TUF or the signed-note format, are the **gap rule** with `skips` (rule 7), the **`void-after`** rule (rule 6), the exact-lines rule, the slot-change authorisation, the promote statement and the second-log agreement rule. Before the format is frozen they are modelled in **TLA+** (clients and a hostile server over write-once heads; safety properties: no client builds on a void head after it has learned the removal, no two clients accept different valid chains past an agreed pin unless the split-view alarm fires, a skippable head is never one a locked client cannot judge) and the signature framing of the three note kinds is checked in **Tamarin** or an equivalent symbolic tool for domain separation; and a set of **test vectors** (valid and invalid notes of every kind) is committed and run against the Go implementation. Format freeze waits for both (decision 13, stage 5).

**Notes and signature types.** The root, the devices document, the location statements and every head are written in the C2SP signed-note format (c2sp.org/signed-note), the framing used by the Go checksum database and by Sigstore's transparency-log checkpoints. A note is UTF-8 text ending in a newline, an empty line, then signature lines of the form em dash, space, key name, space, base64 of a 4-byte key id followed by the signature. Signature type `0x01` is Ed25519 (RFC 8032), the key id is the first four bytes of SHA-256 over the key name, a newline, the type byte and the public key, and a key name must contain no space or plus sign. A raw Ed25519 signature over the note text cannot come from the keys this record recommends for roots: a FIDO2 authenticator signs `authenticatorData ‖ clientDataHash` and not arbitrary bytes, and a Cardano hardware wallet signs transactions or CIP-8 structures only. Root and devices-role signatures therefore use two further signature types, each a distinct note signature type with the same key-id derivation (the type byte values `0x20` and `0x21` are proposed here and are unconfirmed against the signed-note type registry; the draft named a third, `0x22`, that was never defined, and it is removed):

* **`0x20`, OpenSSH SSHSIG with a FIDO2-backed key** (`sk-ssh-ed25519@openssh.com` or `sk-ecdsa-sha2-nistp256@openssh.com`). The message is the note text (or, for a slots authorisation, the statement of "Authorised changes"). The signature is the SSHSIG blob of OpenSSH's `PROTOCOL.sshsig` (confirmed from that document: the preamble `SSHSIG`, version 1, public key, namespace, reserved, hash algorithm `sha256` or `sha512`, signature; the signed data is the preamble, namespace, reserved, hash algorithm and the hash of the message, and the namespace must not be empty). The namespace is fixed by the statement kind: `spo/root/v1` for a root, `spo/devices/v1` for a devices document, `spo/slots/v1` for a slot change, `spo/location/v1` for a location or promote statement, `spo/attest/v1` for an operator attestation; the hash algorithm is `sha512`. The key id covers the SSH wire-format public key. `golang.org/x/crypto/ssh` exports `KeyAlgoSKED25519` and `KeyAlgoSKECDSA256` and parses SSH public keys; that its `PublicKey.Verify` verifies the security-key signature form (the flags byte and counter that the authenticator signs) is expected but unconfirmed here, and that the package has no SSHSIG support is likewise unconfirmed. A verifier therefore implements the SSHSIG framing itself and checks the signature with `ssh.PublicKey.Verify`, and a test against signatures made by `ssh-keygen -Y sign` pins it. The signature must carry the user-presence flag and the user-verification flag (per the security-key signature format of OpenSSH's `PROTOCOL.u2f`; unconfirmed from the source here); a root key is created with the `verify-required` option, and the application string is fixed at `ssh:spo` (unconfirmed that `ssh-keygen` accepts it for sk keys; the option is `-O application=`). Signing is done by `ssh-keygen -Y sign`, driven through `execx` as a pinned tool; whether a given authenticator supports Ed25519 is unconfirmed, and the ECDSA P-256 form is the one every FIDO2 authenticator supports.
* **`0x21`, CIP-8 `COSE_Sign1`** for a hardware-wallet key (CIP-8 message signing, RFC 9052). The payload is the note text, the protected header carries the EdDSA algorithm and the key's hash (the header form that Cardano hardware wallets accept for message signing is unconfirmed), the key hash of the signer is the root key's identity, and the verifier checks the Ed25519 signature over the `Sig_structure` of RFC 9052. Whether `cardano-hw-cli` or the device firmware signs an arbitrary payload in this form for a Ledger or Trezor is unconfirmed.
* **`0x01`, a software Ed25519 key,** is allowed only for a workspace under the `standard` policy of ADR 0011 that is local (no server, no bucket). Under `hardware` or `strict`, falling back to a software root key kept on disk is refused: the workspace does not accept a note signed with type `0x01` as a root, devices, slots, location or attestation signature, and `store init` refuses to create a root whose keys include one. Device heads use `0x01` always (the device key, below).

A note carries signature lines that match the keys of its role and nothing else (the exact-lines rule below applies to every note kind of this record).

**The root document.** The text of a root is:

```
spo/root/v1
<version, decimal>
<"nonce:<hex>" in version 1; the workspace id in hex in later versions>
<expires, RFC 3339 UTC>
threshold root <n>
rootkey <signature type> <public key hex>          one line per root key
role devices <m>
devkey <signature type> <public key hex>           one line per key of the devices role
```

The first line is the domain tag. The hash of a root is Blake2b-256 over the note text only, never over the signature lines (a signature line can be re-encoded without invalidating the signatures, so a hash over them would give one root many names). **The workspace id is the hash of root version 1**; version 1 carries the genesis nonce (16 random bytes), which the slot and record associated data of ADR 0003 bind (ADR 0011, Amends), the cold sub-key HKDF takes as its salt and the HPKE recovery wrap binds in its `info` (ADR 0011's proposed amendment); two workspaces never share an id even if they share keys. **The nonce is therefore a property of the workspace: no operation changes it in place, and re-genesis, which makes a new nonce, re-seals every cold record (decision 3, "Loss of the root threshold and re-genesis").** Roots are stored as `roots/<version>`, write-once.

* **Root keys** are held by the operator and are offline-capable: FIDO2 authenticators (signature type `0x20`) or hardware-wallet keys (type `0x21`). They are never derived from the master key and never held in a device's file. **The root changes only root keys and role delegations** (the keys and threshold of the `devices` role); it does not list devices. Recommended: 2 of 3, with the keys kept apart (owner question 7).
* **A new root version** is signed by a threshold of the keys of the **previous** root and a threshold of the keys of the **new** root (TUF section 5.3). Its version is exactly the previous version plus one. A key present in both may sign once and counts for both. A root note carries no signature line from a key that is in neither root, none repeated and none that fails to verify; otherwise it is refused.
* **Expiry.** A root has an `expires` time that the operator sets (recommended one year). A client does not commit under an expired newest root and reports it; renewing it is a new root version.

**The devices role and the devices document.** Enrolling a device at the root threshold would need the root keys for every new laptop, which is unworkable for one operator. The root therefore delegates a `devices` role: its own keys (the operator's FIDO2 credentials) and its own threshold (1 by default). The role signs a **devices document**, versioned, stored as `devices/<version>`, write-once:

```
spo/devices/v1
<version, decimal>
<workspace id in hex>
<root version> <root hash>                             the root it is made under
threshold heads <k>                                    device signatures a head needs (1 by default)
device <fingerprint hex> <public key hex> <cross-signature hex>    one line per device
mailbox <fingerprint hex> <public key hex>             one line per mailbox-only party
removed <fingerprint hex> void-after <seq, decimal> <head hash>    one line per removed device
```

A devices document is valid when its version is the previous one plus one, the root it names is verified, and it carries signature lines by exactly the threshold of `devkey` keys of that root and no others. A device cannot sign it, so **one unlocked device cannot add or remove devices**, and a thief of one device key cannot either. The `removed` line is the void rule of "Revoking a device". When a root changes the `devices` role keys, the next devices document is signed under the new root. Mailbox-only parties are listed here because the server's access list reads them in plaintext (decision 7).

**One touch, many meanings (S2, changed in this revision).** The devices role signs devices documents, slot changes, location and promote statements and attestations: each is a FIDO2 touch, and a touch alone does not say what was signed. Three rules. (a) **A different authenticator.** The credential of a `devkey` of the devices role is on a different authenticator from every credential of every daily slot (`fido2-hmac` and `composite` slots) of the workspace. This is checked by credential id when the `devkey` is enrolled and when a slot is added (a slot whose credential id is a `devkey`'s is refused); the check sees credential ids, not the physical token, so two credentials on one token are not detected and the rule is also an operator procedure. (b) **The text is shown before signing.** The client prints a decoded, human-readable form of what it asks the role to sign (devices added and removed with fingerprints, the slot kinds and policy that change, the location, the counters of an attestation) and signs only after the operator confirms; the signature covers the bytes shown. (c) **A display hardware wallet** as the devices-role key (type `0x21`) is an option where the device shows the payload; whether current firmware displays a CIP-8 payload and not only a hash is unconfirmed, and the plain FIDO2 key shows nothing.

**The head.** Each commit appends one **head**, written in the same signed-note framing. The text of a head is:

```
spo/head/v1
<kind: genesis | normal | refresh | rotation | takeover>
<workspace id in hex, or "nonce:<hex>" in the genesis head>
<seq, decimal>
<previous head hash, hex; empty in the genesis head>
<root version> <root hash>
<devices version> <devices hash>
<manifest hash> <slots hash>
<committing device fingerprint>
<expires, RFC 3339 UTC>
recovery-key <hash of the recovery public key, ADR 0011 decision 6>
[slots-auth <key id hex> <signature base64>   one line per signer of the devices role; present exactly when the slots hash differs from the predecessor's, and in the genesis head]
[skips: "skips <seq>:<note hash> ..." listing the sequence numbers and the note hashes of the heads skipped by the gap rule]
[takeover only: "restored-from <head hash of the backup the content came from>"]
```

The first line is the domain tag, so a signature over a head cannot be taken for another kind of statement. A head has an **expiry**: the committing client sets it, by default the commit time plus **14 days**, and at most a cap of 90 days for a planned absence of the operator (both are proposals, owner question 9). A `refresh` head repeats the manifest and slots hashes of its predecessor with a new sequence number and expiry; any device may commit one, as a client does when the newest head has passed half its validity, but never on top of an expired head (rule 4). The `recovery-key` line is the same in every head unless a rotation that presented the recovery composite changes it. In an object store the hash of the recovery public key is carried in each head as well as in the associated data of every slot ([ADR 0011](./0011-key-custody-and-unlock.md) decision 6); the client compares both.

**The head hash is over the note text only,** for the reason given for roots (it includes the `slots-auth` lines, which are text). A head carries **exactly** the signature lines expected: one by each of the committing devices (as many as the devices document requires of a head, one by default, each listed in the devices document the head names), in order of fingerprint, and no other. A note with any other signature line, a repeated one, a missing one, an unparsable line, or text that does not match the layout above is refused. The signed-note format lets a verifier ignore unknown signature lines; this record does not. The tlog-checkpoint body of the same project (origin, tree size, Merkle root) is not used: there is no Merkle tree here, and putting a sequence number and a hash in the tree-size and root-hash lines would make monitors read a log that is not one. Go's `golang.org/x/mod/sumdb/note` implements the framing for key type `0x01`; adding it as a dependency is unconfirmed, and its verifier ignores unknown signature lines and unknown signature types, so the exact-lines rule and the types of this record are applied by code of this record in front of it.

**Authorised changes.** The root authorises only a change of root keys or of the `devices` role. A rotation of the master key ([ADR 0011](./0011-key-custody-and-unlock.md) decision 6) and the revocation of a device are authorised by the devices role: the devices document changes **first** (a new version signed by the role; it may leave the device set unchanged when only the master key rotates), and then the `rotation` head commits under it: a `rotation` head names a devices version higher than its predecessor's, and its committing device is listed in that new document. Nothing else rotates the master key in the chain.

*Changed in this revision (B3): slot changes.* In the draft any holder of the master key could change the slot table by an ordinary head, adding a slot (an attacker's authenticator) or lowering the policy, and the slots hash in the head only bound what had been committed. **A head whose slots hash differs from its predecessor's must carry a devices-role signature over the statement**

```
spo/slots/v1
<workspace id in hex>
<new slots hash>
<predecessor head hash>                 empty in the genesis head
```

by exactly the threshold of the `devkey` keys of the root the head names, as SSHSIG (type `0x20`, namespace `spo/slots/v1`) or CIP-8 (type `0x21`), carried in `slots-auth` lines of the head. A head that changes the slots hash without them, with signatures that do not verify, or whose statement names another predecessor, is **failing** under rule 5 (a locked client can check this: the slots object is structural and the statement is plaintext). Because the statement names the predecessor, an authorisation cannot be replayed on another head. A rotation head always changes the slots hash, so it carries `slots-auth` in addition to the devices document that preceded it. When a client moves past a head that changed the slots (at fresh start, on a pin walk or after `store verify`), it **prints the change**: slot kinds and credential ids added and removed, the policy before and after, whether the recovery public key hash changed, and which devices-role keys signed; an unlocked client asks for confirmation before it commits on top of it for the first time. A thief of the master key alone can therefore still read, but can no longer add a slot that other clients accept.

**Device key.** The device key is a separate Ed25519 key per workspace, cross-signed by the machine's ADR 0005 party identity: the party identity signs the device public key and the device key signs the party fingerprint, each under its own domain tag; the cross-signature is in the device's line of the devices document. The device key signs the head signature line (`spo/head/v1`) and request authentication (decision 7, tag `spo-request-v1`). **Domain tags.** A key signs under more than one context only where each context has its own domain tag, which is the rule here, and the tags are: the device key, `spo/head/v1` (the first line of the note) and `spo-request-v1` (the RFC 9421 `tag` parameter); a root key, `spo/root/v1` only; a key of the devices role, `spo/devices/v1`, `spo/slots/v1`, `spo/location/v1` and `spo/attest/v1` (SSHSIG namespaces; the statement's first line repeats the tag); the party identity key, which signs the ADR 0005 envelopes and rotation statements under ADR 0005's domain strings, the device cross-signature under `spo/device-cross/v1`, and, for a mailbox-only party, requests under `spo-request-v1`. When a party identity rotates (ADR 0005), a new cross-signature is carried by a new devices version.

**Device key at rest, before unlock.** The device key is needed before the workspace is unlocked, to authenticate to a server, so it cannot depend on the master key. Chosen: it lives in a file that is sealed (XChaCha20-Poly1305) under a key from a device-local factor. Under the `hardware` and `strict` policies, which every server and bucket deployment requires (decision 2), the device-local factor must be a TPM-bound `systemd-creds` credential (on Linux where a TPM 2.0 exists) or a FIDO2 `hmac-secret` output; the Argon2id key from a device passphrase is **refused** there and is allowed only under `standard`, which is local-only. This is a device-local factor for the device key file, not a slot of the workspace: whether a TPM-bound slot may open the workspace under `hardware` is owner question 10 (recommended: no). The key is opened into guarded memory for a session and never exported. A non-exportable signing key in a FIDO2 authenticator or the TPM was considered and is deferred: whether a given authenticator or TPM supports Ed25519 is unconfirmed, and a P-256 key would change the head signature suite.

**Client rules** (TUF section 5.3 for the root, and the rollback and freeze checks of its later steps, here applied to heads).

1. **Roots and devices documents first.** Before trusting any head, a client walks root versions from the newest it has verified (at the start, the pinned one): it fetches `roots/<v+1>`, verifies it as above, and repeats until there is none; then it does the same for `devices/<v+1>` under the newest root, and reads the newest location statement. A document that is absent is unavailable and is retried; a document that fails is ignored. A newest root or devices document that is older than one the client has already verified is refused (rollback).
2. **Heads.** A head is **valid** against the verified chain up to its predecessor, where the predecessor is the last valid head, when: the framing and the exact signature lines hold; the root version it names exists, verifies, is not lower than its predecessor's, and is not lower than the newest root the client knows when the head extends the chain beyond the client's last verified head; likewise for the devices version it names; each committing device is listed in the devices document the head names and is **not void** (rule 6); the previous-head hash equals the hash of the predecessor; the sequence number is one above the predecessor's plus the number of heads it skips (rule 7); a `rotation` head names a higher devices version than its predecessor; the `recovery-key` line equals the predecessor's unless the head is a `rotation` head; **its slots hash equals its predecessor's or the head carries the devices-role slots authorisation above**; and the slots hash the head references equals the hash of the bytes stored under that name (and, for the newest head, the manifest). Expiry is not a validity check: an expired head is valid and old.
3. **Rollback.** A client persists its **pin** (below) and refuses a head with a lower sequence number or a head that names a lower root or devices version than it knows. Two different heads at one sequence number that both pass the checks are a fatal alarm: the client that sees both stops writing and reports them.
4. **Freeze.** When the newest head a client can obtain has expired, the client treats it as a freeze alarm and **refuses to commit** on top of it. It is not a click-through: the client continues only when the freshness is corroborated by a source independent of the server, either
   * **the second head log** (below), when it holds a head at least as new and agrees; or
   * **another enrolled device's last-seen head**, exchanged over ADR 0005's transport in a signed answer to a challenge the client draws: a head with a sequence number at least as high as the client's newest, reported by a device that is not the one committing, within the time of the exchange. This proves that, as of the exchange, an independent device had seen no newer head than the one the client holds or had seen a head the client can fetch; it does not prove that no newer head exists, because a device and the client can both be kept from the same later head by the server; or
   * for a **pool workspace**, the operational-certificate counter on chain compared with the counter recorded in the store: the on-chain counter of the pool's cold key (read from a chain provider the client already trusts for submission) must be no higher than the store's. This proves that the store has not fallen behind the last block-producing use of the pool's certificate; it proves nothing about commits that did not touch a counter; or
   * for a workspace **with no pool** (S8, changed in this revision), where neither another device nor a chain counter exists, a **devices-role operator attestation**: a statement `spo/attest/v1`, workspace id, head sequence and hash, the time and the words "I have seen no later commit of this workspace", signed by the devices role (one touch, text shown). It proves only the operator's say-so, and the record says so; it is the only corroboration a single-device workspace can have.

   The committer may set a head's expiry up to the cap (90 days), so a planned absence does not trip the freeze. A restore of an old backup reports the expiry of its newest head and is not refused for it.
5. **Failing.** A head is **failing** only if it fails a check of rule 2 that a locked client can make, and that check can be decided from bytes the client holds or can fetch. **Nothing else makes a head failing or void.** A head whose manifest names an unknown key epoch, whose manifest does not open under the master key, or whose slots object does not open, passes the locked checks and is not failing: the client cannot judge it locked, and it means *re-unlock*. A referenced object, root or devices document that is *absent* is unavailable, and the client waits and retries, because a hostile or lagging store can hide an object and must not be able to make a valid head look skippable. What a locked client **cannot** verify: what the manifest lists, that the manifest's sealed sequence number and predecessor match the head, and that the manifest is the genuine one for that point. It can check that the manifest's plaintext epoch equals the epoch of the slots object the head references; a mismatch is a refusal that stops the client and is reported, not a ground for a skip. A credential-free restore (decision 9) is therefore a check of the chain and the objects, and `store verify --deep` after unlocking is the full check.
6. **Void heads.** A devices document that carries `removed <fingerprint> void-after <seq> <head hash>` makes **void**, for every client that knows that document, every head signed by that device with a sequence number greater than `<seq>`, whatever root or devices version the head names. The head hash in the line is the head at `<seq>`, so a client that holds a different head at that number rejects the document as inconsistent with its chain. A void head is skipped by rule 7, and a client does not move its state for it.
7. **The gap rule.** Heads are write-once (decision 4), so a failing or void head can never be replaced. The chain continues past it: the next valid head names as its predecessor the **last valid head**, carries the sequence number after the skipped one or ones, and carries an explicit `skips` line listing each skipped sequence number with the note hash of the head stored there. A client accepts a skip only for a head it can itself judge: failing by rule 5 or void by rule 6. A head that is merely unavailable or that cannot be judged locked is never skippable, so a hostile writer cannot make a good head look skippable by hiding an object. A `skips` line that lists a sequence number the client judges valid, or that omits a failing or void head standing between the predecessor and the new head, makes the new head invalid.
8. **Agreement with the second head log** (B6, below). Before it builds on a head, a client compares what it holds with the second log, and refuses on a difference.

**The manifest** is a sealed object that lists every live record id with its version and object hash. Labels and owner records ([ADR 0010](./0010-object-identity.md) decision 2) are records of kinds `label` and `owner` and are listed like any other record; there is no separate label index object. The manifest also contains, inside the seal, the sequence number and the previous head hash, and it carries its key epoch in the plaintext header of decision 4. **Only an unlocked client can verify the sequence number and the previous-head hash inside the sealed manifest**, because they are inside the seal. A listed device key that signs head n+1 pointing at an old genuine manifest is a valid head for a locked client; an unlocked client then finds another sequence number or predecessor in the manifest and stops.

**The slots object** is immutable, hashed from the head, readable before unlock, and carries the slot table **and `meta`** (decision 4). The devices document is plaintext, because the server's access list must read it.

**What a stolen device key can and cannot do.** A device key, opened with its local factor, lets its thief authenticate to the server and commit heads until the operator removes the device. It cannot change the root, the devices document or the slots, so it cannot add a device, remove one, add a slot or rotate the master key. It does not hold the master key, so it cannot produce a manifest or slots object that an unlocked client can open; a head it commits is valid for a locked client and unusable for an unlocked one, which stops and reports (rule 5). Once the device is removed with a `void-after` sequence (below), **nothing the thief commits after that sequence is accepted** by a client that knows the new devices document: those heads are void and are skipped. A client that has not yet learned the document can be kept from it by a hostile server until the freshness rule (rule 4), the second head log or another device tells it. The thief cannot make a client accept a head, a manifest or content it chose.

**Revoking a device, and the split view during revocation (B6, changed in this revision).** A revoked device still knows the master key, and the data keys of everything it opened. Revocation is a devices document followed by the **rotation** of ADR 0011 decision 6. The operator's procedure, in this order:

1. Find the last head that is known to be legitimate: the newest head committed by the device before the loss, taken from another enrolled device's last-seen head, from the second head log or from the operator's record of the last commit made on the device itself. Heads after that one that were signed by the lost device are the thief's. Choosing a number too low voids honest heads from that device and costs only a skip; choosing it too high leaves the thief's heads valid.
2. Commit a new devices document, signed by the devices role (one FIDO2 touch), that removes the device with `void-after <that sequence> <that head hash>`.
3. Commit the next head under it from a remaining device. It names the last valid head as predecessor and carries a `skips` line for every head of the removed device after `void-after` (rule 7).
4. Commit the rotation head of ADR 0011 under a higher devices version, with `slots-auth`: a new master key, fresh data keys, every payload re-encrypted, new slots, in one head signed by a remaining device.
5. In server mode the access list follows the devices document, so the revoked device loses authentication at the server as soon as the server sees the document. There are no per-device bucket write credentials (no multi-writer direct-bucket mode, decision 4).

A revoked device cannot produce a head that a client which knows the new devices document accepts: its heads after `void-after` are void, and a head naming the new document does not list it. **What the draft left open:** a server can keep a client on the pre-rotation branch until that branch's head expires (14 days by default), and during that time the client seals new secrets under the revoked epoch, which the revoked device can read. Two rules close most of it. **A second, independent head log** records every head: the committing client appends each head note to the backup sink (decision 9) under credentials that are separate from those it uses for the server or the live bucket, on a bucket with Object Lock, as `headlog/<seq>`, create-if-absent. A client **requires agreement** before building on a head (rule 8): it reads the sink's log (a bucket listing and the newest notes); if the sink holds a head the server does not show, the server is withholding, and the client stops with a split-view alarm; if the two differ at a sequence number, fatal alarm; if the sink lags by one head, any client that holds the newer head verifies it and appends it, and then goes on. A hostile server therefore has to compromise the sink's separate credentials and account too. **Creating any Secret-class record** (a signing key, a mnemonic, a token) requires that the client has corroborated freshness within minutes (recommended: 5): a read of the second log that agrees with the newest head it holds, or an answer from another own device; otherwise it refuses and says why, because a Secret sealed under a revoked epoch is what the attack gives away. Other commits are not held to this bound and are limited by head expiry. The revoked device can still read what it could read before; the operator rotates any key material it could read (ADR 0011). **Cosigning of heads by independent witnesses** (the C2SP tlog-witness protocol, c2sp.org/tlog-witness; not read here, unconfirmed) is the later option for a stronger split-view defence; it needs a checkpoint-shaped statement, and the head of this record is deliberately not one. It is not designed here (owner question 6). The second log does not defeat a server and a sink both controlled by one attacker, and the operator's own bucket lifecycle must not let the sink log expire.

**Pins and location (B5, changed in this revision).** In the draft a client starting from a backup had no freshness anchor and no write path.

* **The pin** is the tuple (root version and root hash, devices version, head sequence and head hash). It is **printed after each commit and after each backup** (and by `store verify`), and the operator keeps it outside the sink it protects (a note, a password manager entry, a printout); a pin kept only beside the backup protects against nothing the sink's writer controls. A **fresh client and a restore refuse anything below the pin**: a root, devices document or head chain that does not reach the pinned versions and sequence with the pinned hashes. A client with no pin is refused. Enrolled devices exchange their pins in the ADR 0005 envelope and compare.
* **The `location` statement** names the live store: a note signed by the devices role (SSHSIG, `spo/location/v1`) that carries the workspace id, a sequence number, the location (the server URL, the bucket URL or the directory, as the operator names it), the head sequence and hash it was made at, and a time. It is stored as `locations/<seq>`, write-once, beside the roots; the newest valid one wins. **A store whose location is not the newest statement's, or which carries no such statement for the place it is opened at, opens read-only.** A backup copy is therefore read-only without a rule that depends on how the copy was made.
* **`store promote`** makes a copy the live store: a **devices-role-signed statement** "continue from head H at location L" (`spo/location/v1`, kind `promote`), where H is a head the copy holds and L is the copy's location. Rules: the statement names the counters it takes, which are the **maximum** of the copy's, the old live store's (if it can be read) and **the chain's**; for a **pool workspace the on-chain corroboration of the opcert counter is mandatory** (the chain counter must not exceed the counter the new chain records, else the promote names the counter and is refused); for a workspace with no pool, the operator attestation of rule 4 stands in. Heads after H in the old chain are **abandoned** and listed in the statement; any client that learns the promote and held abandoned heads is told which commits were lost. The old location is retired by the operator (credentials revoked); a client that sees heads at the old location after the promote statement ignores them, and two valid chains from H, one at each location, are a split-view alarm, not a fork that clients follow. The first commit at L after the promote is an ordinary head by a listed device after a fresh unlock.

**Loss of the root threshold and re-genesis (B1, changed in this revision).** If fewer root keys than the threshold survive, no new root version can be made, and the workspace cannot change its root keys or the keys of its `devices` role. Devices can still be changed while the `devices` role keys survive. This is unrecoverable by design: nothing else can authorise a root change without making the root meaningless. The way out is **re-genesis**: an operator who can still open a copy of the workspace creates a **new workspace id**, that is, a new root version 1 with new root keys and a **new genesis nonce**, and a genesis head whose manifest holds the content of the chosen head, re-sealed under a fresh master key.

In the draft this re-sealed only the outer layer. That is wrong for cold records: the nonce is the HKDF salt of the cold sub-key and is bound in the HPKE `info` of the recovery wrap, so a cold record cannot be carried by its old wrap, and a record whose inner wrap and recovery wrap were left as they were would open with a removed authenticator or the old recovery credential. **Re-genesis treats cold records exactly as the built rotation does.** For every record in the copy: a non-cold record is opened with the master key of the copy and re-sealed under the new master key and nonce. For a **cold-role record**: it is opened through its **recovery wrap**, using the current recovery credential (the recovery composite under `hardware`; the recovery key under `standard`), and the recovered signing key must derive the record's stored identity before it is re-sealed (the identity check, ADR 0011's proposed amendment), or, where no wrap exists (a record migrated from format 2, an upstream-encrypted key), through its **old factor** (the cold passphrase or the cold `hmac-secret` assertion, presented once per record before any write). It is then sealed again with a fresh data key under the **new** sub-key factor and the **new** recovery public key, with new associated data under the new nonce. A record that can be opened in neither way **refuses the whole operation and is named**; the operator may name it in `--leave-unreachable`, which leaves it out of the new workspace (ADR 0011's proposed amendment: nothing is skipped silently). Every record is re-sealed; there is never a second copy of a cold record that the old cold passphrase or authenticator still opens in the new workspace. The new workspace gets a new recovery composite and new slots (the recovery key pair is bound to the nonce's slot associated data); the old recovery credential then opens only the old chain.

**Which unlock is allowed.** Opening cold records through the wrap needs the recovery composite, and the built scope of `--unlock recovery-composite` is `workspace rotate`, `workspace policy set` and `store slots`, with the rule that **no cold record is created or re-bound through a handle opened by the recovery slot** (ADR 0011's proposed amendment). So re-genesis (and the takeover of decision 10 in the case that needs a wrap) runs as the **rotation-class operation**, `workspace rotate --from-backup <copy>`: the recovery composite is presented once, before the write transaction, for the unwrapping, and the new cold records are sealed by the rotation under the new factors, not by the recovery handle. This **extends the scope of the recovery composite by that one command**, which is a change to ADR 0011's proposed amendment and needs the owner's confirmation (owner question 7); nothing else may take the recovery composite, and no daily operation does. A record that opens through the current cold factor needs only a daily unlock. The operational-certificate and KES counters of the new workspace are the larger of the live and the backup values, never lower (decision 10). Nothing in the old chain authorises the new one, so no client follows it by itself: every device is enrolled again and the operator prints and distributes the new pin. The old workspace id is retired by the operator, who revokes the old bucket credentials and writes a retiring `location` statement if the devices role still exists; its chain remains and can still be read by whoever holds its factors.

What this catches: rollback of a client that has seen newer or has the pin; a forged head, root, devices document or slot change; a replayed old manifest; heads of a revoked device after the new devices document is known; set tampering; a split view that includes the sink's log. What it does not: a split view when the server and the sink are controlled together, and a client that is kept from the newest documents and has no other source.

**Compared with a transparency log** (RFC 9162, Certificate Transparency 2.0): a Merkle tree head with consistency and inclusion proofs serves many clients that cannot fetch the whole log and need monitors. Here the history is one operator's and clients fetch the whole manifest; consistency proofs would add machinery and the split-view problem would remain, because it needs gossip either way. Recommendation: the root document, the devices document and the hash-chained signed head in signed-note framing, with the second head log.

### 4. Layout, the latest head, and retention

*Changed in this revision (B4, S4, S10).*

```
workspace/
  objects/<aa>/<hash>   immutable: every sealed object (records, audit rows,
                        manifests), one outer shape; and the slots objects
  roots/<version, 20 digits>      signed root documents, write-once
  devices/<version, 20 digits>    signed devices documents, write-once
  locations/<seq, 20 digits>      signed location and promote statements, write-once
  heads/<seq, 20 digits>          signed heads, write-once
```

**Object shape.** An object's name is the Blake2b-256 of its stored bytes, so any client or the sink can verify it without a key. A **sealed object** is

```
header (plaintext):  format byte || key epoch (8 bytes)
body   (AEAD):       wrap area || sealed header || payload ... padded
```

and nothing else is plaintext: **the kind, the class, the record version, the record id, the anchor identity and the payload length are inside the seal**, with the associated data of ADR 0003 (store format 2 and later; the kind and class remain in the associated data, which both sides compute, not in a stored plaintext column). **Every object is padded to a power-of-two bucket of at least 4 KiB** (**power-of-two buckets**, chosen over Padmé: Padmé's finer granularity leaves many distinct lengths, and the point here is that public lengths such as a pool's metadata and certificate payloads fall into the same few buckets; the cost is at most twice the size, which is acceptable for objects of this size; a payload larger than the largest bucket is split into chunks of that bucket). Padding is inside the seal: the AEAD tag covers it, and a client checks it is zeros after opening. **Cold and hot records share the outer shape.** The wrap area has the size of the cold form (record-wrapping key wrap, inner sub-key wrap, HPKE recovery wrap, salts and credential id) for every record: a hot record fills the unused part with random bytes and the sealed header says which parts are in use. The credential id and the per-use salts of a cold record are inside the seal, readable only after the outer key opens them, as they are in the built cold form (`[label, header, outer, recovery wrap]`). Audit rows and manifests have the same shape. **Clients fetch whole snapshots**: a client lists the heads, fetches the manifest and every object it does not yet hold, in a fixed order, and never fetches or queries by record or by handle; the SQLite cache of decision 6 is built from them. The server learns the objects written by a commit and nothing about which are read.

**The slots object** is the one plaintext-structured object: the slot table of ADR 0003 and ADR 0011 (kinds, `bound`, `rec_hash`, `factors`, KDF parameters, credential ids) and **`meta`** (workspace id, store format, policy, key epoch and the recovery public key hash). It is the layout's home of `meta`, which the draft omitted. It has the same header (format and epoch), is padded to a bucket, is referenced by hash from the head and is distinguished only by that reference; there is no mutable `slots` file. The sealed record and audit-row formats are ADR 0003's with the changes above (the audit MAC chain stays, and is checked by unlocked clients; the signed head is what an untrusted server cannot forge).

**Heads, roots, devices documents and locations are write-once everywhere.** Nothing in this layout is ever overwritten. A commit is: write the new objects (idempotent, harmless if the commit fails), and only after every object the head references has been written, then create `heads/<n+1>` **only if it does not exist**, using each back end's own precondition (a root, `roots/<v+1>`, a devices document and a location statement are created the same way):

| Adapter | Create-if-absent |
| --- | --- |
| Local directory | write a temporary file, `fsync`, then `link(2)` it to the final name (fails if it exists), or `open` with `O_EXCL`; `fsync` the directory. Not on a network file system (ADR 0003) |
| S3-compatible | `PutObject` with `If-None-Match: *`; a second writer gets 412. AWS documents this for `PutObject`, `CopyObject` and `CompleteMultipartUpload`; support by other S3-compatible stores (MinIO, Ceph, R2) varies and is unconfirmed here |
| Google Cloud Storage | an upload with `ifGenerationMatch=0` |
| Server (several replicas) | the server calls the adapter beneath it; the replica that loses gets a conflict, which the client treats as below |

A probe at first use shows that a store accepts the precondition; it does not prove the operation is atomic, so the adapter documents the store it was tested against and refuses an unknown one unless told. Listing is strongly consistent on S3 (stated by AWS since 2020; the date is from memory).

**Who writes (S10, changed in this revision).** The bucket has exactly one writer: the server (which is the only writer and refuses overwrites itself), or one local device in a local deployment. **Multi-writer direct-bucket mode, where several devices write to a bucket with their own credentials, is dropped from v1** (owner question 5): its safety rests on bucket policy that cannot be fully verified by a probe, its revocation needs per-device bucket credentials, and the formal model of decision 3 does not cover it.

**The bucket (S4, changed in this revision).** For a bucket used directly or by the server, and for the backup sink (decision 9): credentials are **short-lived and federated**: SSO, AWS IAM Roles Anywhere, or IRSA or Workload Identity for the server in a cluster; **no static access keys in a configuration file, an environment variable or a Kubernetes Secret**, and `spo` refuses a configuration that has them. The **bucket policy** denies delete to every device principal, requires conditional writes (`If-None-Match`) and denies overwrite on `heads/`, `roots/`, `devices/`, `locations/` and `objects/`; only a separate `gc` role may delete, and only under the grace period below. The **backup bucket** is in a **separate account** from the live store and the server, with **S3 Object Lock in compliance mode**, versioning, and SSE-KMS as defence in depth only (the objects are already sealed; KMS adds a key policy, not confidentiality that this design relies on). **Access logs are another observer**: they show who read or wrote which object and when, which is the same metadata as the server sees, and go to a bucket the operator controls with its own retention. Setup writes a probe object under a scratch prefix with the same policy and attempts an overwrite and a delete, and refuses to create the workspace unless both are refused; what the probe can show for a given store is unconfirmed, and where it cannot be shown the store is not accepted.

**The latest head is not the highest number.** Anyone who can write to the bucket can put garbage at `heads/n+1`, or at `heads/n+5`. The latest head is the highest head of the **valid chain from the client's last verified head**: the client reads `heads/n+1`, verifies it with the locked-client checks of decision 3 (framing and exact signature lines, the named root and devices versions and the listing of the committing device in them, previous hash, sequence, the slot-change authorisation, referenced objects matching their hashes) and, if unlocked, the sealed binding, then `n+2`, and so on. A head that is failing or void is **skipped by the gap rule** (decision 3, rule 7): the client does not stop at it, but looks for the next valid head, which must name the last valid head as predecessor, carry the next sequence number after the skipped ones and list them in a `skips` line, which the client checks against what it holds. A garbage head beyond a gap that no valid head's `skips` line accounts for is never reached. A head that fails verification does not count and does not move the client's state. A head that is valid but cannot be judged by this client, whether its manifest has an unknown key epoch or does not open, is not skippable; the client stops and says *re-unlock* (it may be a rotation or a head written by a device it has not met). A head or root with an absent referenced object is unavailable; the client waits and retries.

**Squatting.** A writer who is not a listed device can write only failing heads; they can squat sequence numbers, which the gap rule skips at the cost of one `skips` line, and they can only deny service. A listed device that is stolen writes void heads after its removal (decision 3, "Revoking a device"). In both cases the damage is detected by every client that verifies and is never a forgery, and nothing is overwritten. A client that holds a verified copy of an object that has been deleted from the store re-publishes it (`Put` is idempotent: the name is the hash). Where the bucket is versioned, deleted versions remain for inspection.

A conflict on a valid head (someone committed `n+1`) means the client fetches the new state, re-runs its `Update` function against it (ADR 0003's version-checked update) and retries, as `ports.ErrConflict` does today. **A client whose commit loses the create-if-absent race to a rotation head discards its plan and retries from scratch after re-unlocking**: the rotation changed the master key, the key epoch and every purpose key, so a plan built on the old state, and the objects written for it (harmless, unreferenced), cannot be carried over.

**Retention.** Heads, roots, devices documents, location statements and slots objects are **kept**: they are small, and they are what verifies the chain from genesis. Records and manifests that the newest head no longer references may be garbage-collected by `store gc` under the rules below; an older head whose manifest has been collected stays valid as a link of the chain.

**Liveness: deleting an object a valid head references must be recoverable.**

* `store gc` has a **grace period** (recommended 30 days, and never shorter than the head validity plus the longest expected offline time of a device). It never deletes an object that any head made within the grace period references, and never deletes an object younger than the grace period, as the store clock reports its creation.
* A commit writes its objects before its head. An object that a commit has written and its head does not yet reference is younger than the grace period, so `gc` cannot take it; and `gc` re-reads the list of heads immediately before each deletion, so a head that appears meanwhile protects what it references. With the grace period much longer than a commit, `gc` and a commit cannot race.
* A client or a backup that holds an object with the hash a valid head references, and finds it absent from the store, **re-publishes** it. A restore from a backup does the same for what the live store lacks.
* A deletion is a conditional request that the server checks itself (decision 7); devices do not delete objects, only a separate `gc` credential does.

A rotation (ADR 0011) is one head commit; its old records and manifests become unreferenced and are collected after the grace period where the sink allows (not from backups, object versions or object lock, as ADR 0011 says). A head whose manifest's plaintext epoch differs from the epoch of the slots object it references is refused by the client (decision 3: a refusal, not a ground for a skip): a manifest from before a rotation cannot be committed under the slots of after it, nor the reverse.

### 5. Ports and adapters

*Changed in this revision (S5, S6).* New, in `spo/internal/ports`, **split by capability so that no port has an unsupported half** (ADR 0008): an adapter implements only the ports it can honour, and wiring takes the ports it needs.

* `ObjectWriter`: `Put(hash, bytes)`, idempotent.
* `ObjectReader`: `Get(hash)`, `Has`.
* `ObjectLister`: `List(prefix)`.
* `ObjectDeleter`: a conditional delete (decision 7); implemented only by the `gc` credential's adapter.
* `HeadAppender`: `Append(note)`, create-if-absent; returns the existing note on conflict. There is no replace operation. It covers heads, roots, devices documents and location statements.
* `HeadReader`: `Latest`, `Since(seq)`, `Get(seq)`.
* `AccessList`: enrolled device public keys and mailbox-only parties, read from the newest verified devices document, readable by the server (decision 7).
* `Mailbox`: `Deliver(recipient, envelope)`, `Fetch(recipient)`, `Ack`. It extends the existing `ports.Transport` envelope senders and receivers (`ports/party.go`) with store-and-forward.

A backup sink (decision 9) is an `ObjectWriter` and `HeadAppender` for the writing side and an `ObjectReader`, `ObjectLister` and `HeadReader` for the restoring side; a sink that is write-only for devices gives the device the writer ports only. There is no combined `ObjectStore` or `HeadLog` port.

**Transport kind.** Every envelope that comes from a `Mailbox` or from any object-store adapter, the **directory adapter included**, is **`NetworkTransport`** in the sense of ADR 0005 ("The transport kind"). A mounted bucket or a synced folder never counts as the file transport, so the cold-key rule (a pool cold key is not signed over a network transport) cannot be satisfied by putting the envelope in a bucket. `FileTransport` stays the adapter of a carried file only.

The existing `ports.Store` and `ports.Vault` stay as they are. A new adapter `adapters/sealedstore` implements them over the ports above. **What it must re-implement from `sqlitestore`** (the draft said "verification, conflict, audit", which is not enough; the SQLite file today does all of the following and the layout must keep each): the slot table and the **policy check** on every open (`unlock.Check`; the opener refuses a table that breaks its policy); the **cold session and the cold source** (the sub-key factor presented per signing session with the per-use salt rotation and the previous-wrap fallback); the **recovery presentation** and the **rotation** (including the cold re-seal through the recovery wrap, the identity check, `--leave-unreachable`, and that recovery material lives for one operation); **restore through factors** and the **weaker-policy check** (decision 9); the **migrations** (format 1 and 2 refusals, `workspace migrate`); the **previous-wrap and heal logic** for cold records; the recovery-wrap backfill of a rekey, passphrase change or rotation; the audit chain and its checks; conflict handling; and the per-operation counters. Every use case runs unchanged, because it sees `Store`, `Vault` and the `SignerDirectory` of ADR 0010 and nothing else; whether the objects are in a directory, a bucket or behind a server is wiring. `Signer` entries for an own remote client are reached by the party envelope over `Transport` or `Mailbox`; a co-signer's by party fingerprint (decision 8); a use case cannot tell. Chain access, submission and hardware stay client-side. The differential test of decision 6 runs the same operation script, including the rotation, recovery and restore scenarios of the handoff's real-device table, over both stores.

### 6. The SQLite file

Decision: the layout is the canonical, portable format for backup, local deployment and the server's content once the sealed object store has had equal review depth to the SQLite file. Until then the SQLite file stays canonical for a solo operator and the existing SQLite backup artefact is the backup (decision 13, stages 1 and 2). Afterwards it becomes a **local cache** of sealed objects of a remote or bucket store, rebuilt from the layout and never authoritative. Reasons: the file has seven reviews and its verification is what makes the opcert and KES counters trustworthy (ADR 0003); Verify time grows with the chain (about 200 ms at 50,000 audit rows), so a client caches the verified prefix; migrating the whole store at once gives up a reviewed component for a rewrite. Cost: while both exist, two stores have to keep their invariants; a differential test runs the same operation script over both.

**One canonical store per workspace id (S9, changed in this revision).** A workspace id has exactly one canonical store, recorded in the signed location statement (decision 3). `store convert` of a SQLite file to the layout writes the first location statement for the new layout and **retires the SQLite file for that id**: it is renamed with a `.retired` suffix, its head file is replaced by a retired marker naming the layout, and `spo` refuses to open a retired file for writing (read-only inspection needs `--allow-retired`). A SQLite file and a layout for the same id are never both writable. **`store convert` of a `hardware` SQLite backup verifies through factors**: the backup is opened with a factor of its own slot table (the daily authenticator or the recovery composite where the operation allows it), not with a passphrase, because under `hardware` and `strict` no passphrase opens a store; a conversion that needs a factor the operator cannot present is refused. Cold records are converted by the rules of decision 3 (re-sealed through their wrap or old factor; otherwise refused and named).

### 7. Client authentication, handles, and the multi-tenant server

Over Tailscale or tailcat the transport already authenticates a node. ADR 0005 binds the node key to a party identity in its `Hello`; that registry is sealed. The server therefore keeps an **access list**: the device keys and the mailbox-only parties of the newest verified devices document, exposed as `AccessList` (public keys and fingerprints only).

**Every request is authenticated, reads included.** Each request carries an HTTP Message Signature (RFC 9421, February 2024) by a device key: signed components `@method`, `@target-uri` and `content-digest` (RFC 9530, not read here), with the parameters `keyid` (the device fingerprint), `created`, `expires`, `alg` (`ed25519`) and `tag` (`spo-request-v1`), and is refused unless the key is in the list and the time check passes. The `tag` is the domain separation of this signature. A mailbox-only party signs the same way with its ADR 0005 party identity key, and the server lets it reach the mailbox endpoints for its own fingerprint and nothing else: no object, no head, no list. There is **no unauthenticated read path**. Backups are read from the sink with the sink's own access, never through the server, so a read path for them is not needed.

**The server verifies a head before it appends it (S3, changed in this revision).** A head is accepted for `Append` only if: the framing and the exact signature lines are right; each signer is listed in the devices document the head names and is not void; the sequence number and the previous-head hash match the newest head the server holds (or its `skips` line accounts for the gap); and, when the slots hash changes, the `slots-auth` lines verify. The server needs no key for this: it holds only public keys. This is a defence of availability and quality, it keeps garbage out of the log; clients verify everything themselves and never trust the server's check.

**Handles (S1, changed in this revision).** *Preferred (owner question 4): no handle is visible to the server.* The signing demand between the operator's own devices is **the sealed ADR 0005 envelope, fanned out to all of the operator's own devices** by party fingerprint through the mailbox, with the key identity (not a handle) inside the seal. Each device that receives it answers, with a refusal of a fixed padded size if it does not hold the key ("not held" and a real refusal look alike), so the server learns neither which device holds which key nor which key was asked for. Cost: every device handles every demand; the number of devices is small. *Fallback, if the owner keeps server-visible handles:* handle = HMAC-SHA-256(`K_h`, canonical CBOR `["spo/handle/v1", kind, hash]`), with `K_h` = HKDF-SHA-256(IKM = master key, salt = genesis nonce, info = "spo/handle/v1"). The leaks, stated: **equality** (the server sees that two handles are equal, so that one key is used in two requests or two commits); **linkage across rotation** (a rotation replaces `K_h`; the server links old to new by position in the commit and identical size, so rotation does not unlink an object from its history); and **a revoked device computes handles until the rotation**, because it still holds the old master key, so it can test guessed identities against what the server saw before the rotation. The handle is Structural in ADR 0004.

**Replay protection without server state.** A nonce that the server remembers needs state shared between replicas, which the stateless design (decision 1) does not have. Chosen instead: a **bounded time window**. The signed `created` must be within 60 seconds of the server's clock (either side) and `expires` at most 60 seconds after `created`; a request outside that is refused. **The real replay window** is longer than a minute when clocks differ: a device whose clock runs 60 seconds ahead produces `created` up to 60 seconds in the future with `expires` 60 seconds after that, so a captured request can be replayed for up to about 120 seconds of the server's time, and replicas whose clocks differ from each other add that difference. This needs the clocks of devices and replicas to agree (NTP; a device whose clock is wrong is refused with a message that says so). A per-device monotonic counter stored in the object store was considered and rejected: it makes every request, reads included, a conditional write to a shared object contended by all replicas, which gives up statelessness for a protection that the properties below already provide. The `nonce` parameter is therefore not used.

Inside the window a replay can repeat only what the request already did, because every operation is either idempotent or made safe by a precondition:

* **Idempotent:** reads return the same sealed bytes; `Put` of an object is keyed by the hash of its bytes; a mailbox delivery is keyed by the envelope's message id, which the recipient's replay log (ADR 0005) already refuses a second time; an acknowledgement.
* **Safe by a precondition:** a head append is create-if-absent for one sequence number with one fixed content, so a replay is a conflict and changes nothing; **a delete is conditional and checked by the server**: the request names the object and the head sequence number its decision was made at, and the server refuses it unless that is still the newest head, the grace period has passed and no head within it references the object (decision 4, Retention). A replayed delete after success finds nothing to delete and is a no-op; a replayed delete after a newer head is refused.

The remaining exposure is a repeated read by someone who captured the request inside the tunnel, who learns what the sealed response holds (sealed objects and structural data) and nothing that the capture did not already contain.

Enrolment of a device reuses ADR 0005's ceremony: fingerprints compared out of band, scope and roles per party; the new devices version that adds the key is signed by the `devices` role (decision 3; one FIDO2 touch by default, no root keys), and the enrolment carries the pin (decision 3). Enrolment of a mailbox-only party is the same ceremony and adds a `mailbox` line to the devices document only, so it cannot sign a head. What ADR 0005 does not provide and this record adds: a way for a server to learn enrolments without the registry.

**A multi-tenant server (S12, changed in this revision).** A server that serves several workspaces needs rules that a single-workspace one does not. **Who may create a workspace:** an **allow-list of root key ids** in the server's configuration; a request to create a workspace presents root version 1 and is accepted only when a root key of that note is on the list (the server can check the signatures; it cannot judge anything else). **Per-workspace prefix and quota:** each workspace id has its own prefix in the bucket, a byte and object quota, and a rate limit on commits, so one workspace cannot exhaust another's. **A minimal audit log** of the server's own: workspace creation and deletion, access-list changes seen, quota refusals and rejected heads, with the workspace id, the device fingerprint, the time and the network identity; no payload and no object names beyond the hash. Retention is stated in the configuration (recommended 90 days), and the log is itself an observer of the metadata of decision 2.

### 8. Envelopes and the mailbox

An envelope is already sealed to the recipient with `age` and signed by the sender (ADR 0005), so a server may hold one without reading it. The mailbox is keyed by the recipient's party fingerprint, which the server sees. A signing demand for a key held by another operator is routed by the party fingerprint that ADR 0005's slot assignment records, through the mailbox or a direct transport; a co-signer cannot compute this workspace's handles (if any exist) and the demand carries none. The ADR 0005 rules that a signer's refusals depend on private checks, and the cold-key rule (keyed on the most sensitive role ever recorded for the key, ADR 0010), are enforced at the clients, unchanged. A signer offline for a day receives the request when it connects; the request's expiry (ADR 0005) bounds that.

**Every envelope from a `Mailbox` is `NetworkTransport`** (decision 5), so a pool cold key is never signed through the mailbox; a cold-role demand is answered only over the carried-file transport of ADR 0005.

**Remote answers go through the full ADR 0005 signer path (S7, changed in this revision).** An answer from the operator's own client to a demand, whether over `Mailbox`, tailcat or an object-store adapter, is produced by `Signer.Handle` with the approval gate of ADR 0005 (the transaction view, the policy checks, the per-demand refusal rules) **and a fresh presentation** of the factor the policy requires for that key (ADR 0011 decision 8: a touch, a PIN for the key's class). A cached unlock, an existing session, or a reply produced by a background process does not satisfy a demand. Nothing answers a signing demand without that gate, and the server has no way to produce an answer.

### 9. Backup and restore

*Changed in this revision (B5, S4, S11).* **Stage 1 uses the existing sealed SQLite backup artefact** with no new cryptography (decision 13); the text below describes backup of the layout (stage 3) and what both share.

A backup is a copy of `objects/`, `roots/`, `devices/`, `locations/` and `heads/` to a sink (a directory, an S3-compatible bucket; a `standard` workspace is local-only and may be backed up to a filesystem directory only, with the warning of decision 2; owner question 8), taken by listing the heads and copying everything reachable from the newest valid head, the heads being the last to be written so the copy is a valid prefix. It needs no further encryption because objects are sealed. The sink learns the metadata of decision 2 and that this is a backup of a workspace. The sink is on a bucket with the properties of decision 4 ("The bucket"): its own account, Object Lock in compliance mode, versioning, federated short-lived credentials, and its own prefix; the sink also holds the second head log of decision 3. Object lock and versions keep old slot tables and ciphertext permanently, which is why ADR 0011 makes factor removal a master-key rotation. A backup keeps every root, devices document, location statement, head and slots object, and the records and manifests the newest head references; it does not rely on what the live store has garbage-collected. **After each backup the client prints the pin** (decision 3).

Restore verifies without any credential, **against the pin the operator supplies** (root version and hash, devices version, head sequence and hash; from `store verify`, from the print after the last commit or backup, or from a device enrolment record): every object's hash equals its name; the roots walk from version 1, whose hash is the workspace id, through every version to the newest, with each version signed by a threshold of the previous and of its own root keys, and the newest version is at or after the pinned one with the pinned hash at the pinned version; the devices documents walk from version 1 under the roots they name, each signed by the `devices` role of that root; the heads verify from the genesis head to the newest, each with exactly the expected signature lines by devices listed in the devices document it names and not void, any gap accounted for by a `skips` line, every slots change carrying its devices-role authorisation, and the slots and devices hashes match. **The restore refuses a head chain that ends below the pinned head**; a copy that carries no location statement naming it opens read-only (decision 10). A backup whose newest head has expired is reported, not refused (decision 3, rule 4). **The built restore refusals are kept** (S11): a restore of a copy whose slot table's policy is **weaker** than the live workspace's is refused unless `--allow-weaker-policy` is given with the recovery material presented on the current store first; a restore **opens the store through factors**, never by a passphrase under `hardware` or `strict`; and a restore **never lowers the operational-certificate or KES counters** of a live workspace: for each, it takes the larger of the live and the backup value, or refuses and names the counter. What this does not check is what only an unlocked client can (decision 3): an operator who needs more unlocks and runs `store verify --deep`. It refuses a backup of another workspace id, and a head older than the destination's unless told with `--allow-older`. A restore without a pin is refused. **`--allow-older` is read-only inspection of an older head**: the result can be opened and verified, never written, and it is never a second way to fork the store; writing the content of a backup into the live workspace needs the takeover of decision 10, which extends the live chain, and making a copy the live store needs `store promote`. Existing SQLite backups import through `store convert` (decision 6).

### 10. Local deployment from the artefact, takeover, and promote

`spo -C <directory-or-s3-url>` opens the layout with the `sealedstore` adapter over the directory or bucket adapter and no server: the copy *is* the store.

**How "a simple local deployment referencing the backup artefact entirely" is met (changed in this revision).** A directory or bucket copy of the layout, with the pin the operator printed, is enough to open the workspace on a machine that has none of the original infrastructure: no server, no cluster, no other device. Opened that way the copy is **read-only**: the client verifies the chain against the pin, unlocks through a factor of the slots object (a daily authenticator, or the recovery composite where the operation allows), and reads, verifies and signs offline with what the copy holds. To **write** from the copy (commit heads, create records, rotate), the operator runs **`store promote`** (decision 3): a devices-role-signed statement "continue from head H at location L" that makes the copy the live store, with on-chain corroboration of the counters for a pool workspace (the operator attestation otherwise). After the promote the copy accepts commits from a listed device, and the old location is retired. The device and the devices-role authenticator are the only things needed beside the artefact and the pin; nothing in a deployment's server or cluster is.

**Takeover (B1, changed in this revision).** `heads/<seq>` is write-once, so there is no second branch to write on: the one way to put the content of a backup into the live workspace is a `takeover` head that **extends the live chain**. Its rules:

* **Where it sits.** Its sequence number is the **pinned live head's sequence plus one** and its previous-head hash is that pinned head's hash. The operator pins the live head and the root (decision 3, Pins); a takeover is refused without the pins. The destination must hold the heads of the live chain up to the pinned head; heads are small and self-verifying, so they are copied from any device or sink that has them. If the live chain's newest heads cannot be obtained at all, there is no takeover.
* **What it keeps.** It keeps the live head's slots object, devices document, key epoch and root version, and changes none of them (when it runs as a rotation, below, it does so by the rotation's own rules). **A takeover from a backup can therefore never bring back a removed factor or a revoked device: the slots of the live chain and the devices of the live devices document are the only ones the head can name.**
* **How records come across.** The draft re-sealed the backup's records only under the live master key, which leaves a cold record with its old inner (sub-key) wrap and its old recovery wrap, so that a removed authenticator or the old recovery credential would still open it. Now: the backup is opened through a factor of its own slot table (restore through factors, decision 9). Each non-cold record is re-sealed under the live master key at the live epoch. **Each cold-role record is opened through its recovery wrap using the current recovery credential (identity check), or through its old factor, and is sealed again with a fresh data key under the live cold factor and the live recovery public key**, exactly as the built rotation does; a backup that binds a different recovery public key hash from the live one opens its cold records only through the old factor or the old recovery credential, which are then presented and not retained. A record that can be opened in neither way **refuses the takeover and is named**; `--leave-unreachable` leaves a named record out, only as in ADR 0011's proposed amendment. Nothing in the takeover head carries an inner or recovery wrap of the backup.
* **Which unlock.** A takeover whose cold records all open through the current cold factor needs a **fresh daily unlock** of the live chain's epoch and that factor, by a device listed in the live chain's devices document. A takeover that needs the recovery wrap needs the recovery composite, whose scope is `workspace rotate`, `workspace policy set` and `store slots` only, and **no cold record is created through the recovery slot**; it therefore runs as the **rotation-class operation** `workspace rotate --from-backup <copy>` (decision 3, "Which unlock is allowed"): a `rotation` head (devices document first, `slots-auth`, new master key) carrying `restored-from`. This extends the recovery composite's scope by that command and needs the owner's confirmation. A device that the current devices document does not list, a revoked device included, cannot sign it.
* **Counters.** **A takeover never lowers the operational-certificate or KES counters:** for each counter it takes the larger of the live and the backup value, or refuses and names the counter, because a lowered counter would let a block producer sign a certificate or a KES period that the chain has already seen. For a pool workspace it also compares the on-chain counter.
* **If the live epoch cannot be unlocked.** If the operator cannot unlock the live chain's epoch because its factors are lost, that is the recovery path of ADR 0011 (the recovery composite, then a rotation), not a takeover.
* **Who accepts it.** Every client that has the pinned head sees the takeover as an ordinary extension of its chain: it passes the locked-client checks and the sealed binding. No client is asked to accept a fork.

Two different heads at one sequence number that both pass the locked-client checks are a fatal alarm (decision 3). `--allow-older` (decision 9) never produces a head.

### 11. Kubernetes

*Changed in this revision (B7).* **Scope: the server only.** A `Deployment` of replicas behind a `Service` runs the server of decisions 1, 5, 7 and 8: ordering and verification of heads, object storage and the mailbox. The bucket is the only state (a `StatefulSet` and a persistent volume are not needed). The head conflict of decision 4 is the only contended write. A disruption budget and a rolling update need no coordination. **No use case runs in the cluster**: it holds no unlock factor, no master key, no Vault token for the workspace's transit key and no signing key; its service account reaches the bucket through IRSA or Workload Identity (decision 4) and nothing in Vault or KMS (checked in review of the manifests, which are not in this repository yet). Scope: Tailscale only for the first version; an ingress later requires TLS 1.3 and the request signatures of decision 7. The multi-tenant rules of decision 7 apply.

**Block producers in Kubernetes are out of scope for v1.** The built delivery cannot run in a pod: `spo-node-keys` reads its age identity only from the systemd credentials directory, requires ramfs or `noswap` tmpfs, relies on a TPM-bound host identity that a pod does not have, does no sender authentication, and keeps no monotonic state (handoff and ADR 0011's proposed amendment). Block producers are systemd hosts. What an honest later design needs, recorded here and designed in its own record (decision 13, stage 7):

* an **identity** that does not depend on a TPM in the pod: rooted in a cloud KMS key reached through workload identity, with the labelled trust that the cluster's IAM (and so whoever administers it) can use that key, or a vTPM with attestation of the node and workload;
* **signed node exports** under the tag `spo/node-export/v1`, so the producer authenticates the sender (the built export is age ciphertext with no sender authentication);
* a **monotonic guard**: the helper refuses a set that is not above its recorded KES period and certificate counter, which needs state that survives a restart;
* a **no-swap check on the node** for the memory-backed directory (the `noswap` check of the built helper, or a verified equivalent for the node's runtime).

### 12. Unattended automation under R4, and the client agent

*Changed in this revision (B2): the client agent is removed from this record.* The draft's agent cached the master key for up to 12 hours, could add a slot, could be unlocked by a "passphrase, or Vault identity" (contradicting the `hardware` precondition of decision 2 and ADR 0011 decision 6), and had as its one named job a scheduled KES rotation that needs the pool cold key, which no agent may hold. **A client agent needs its own record**; this record does not define one, and nothing here depends on it.

Impossible by design in this record: anything that needs a vault-held key, a decrypted object or an unlock factor with no client present, such as a scheduled KES rotation or opcert renewal run by a server job. Hardware-held keys cannot sign without the device either. The server may *remind* (an envelope that says "KES period ends in 3 days") because that needs no secret. Hot keys on a block producer are delivered to it under ADR 0011's node-delivery exception, not decrypted by the server.

**Constraints on any future agent** (recorded so that the later record starts from them):

* **It never holds the master key.** It holds **scoped grants**: HPKE (RFC 9180) wraps of the **data keys of named hot records** to an agent key, nothing for a cold-role record (ADR 0011 decision 6) and no record not named.
* **The agent key is TPM-sealed**, created under a **devices-role signature** and **listed, with its scope, in the devices document**; a grant not listed there is void like a removed device.
* **It cannot change slots**, the devices document, the root or a policy; it commits no head that changes the slots hash (decision 3), and a head it signs is an ordinary head.
* **It is never on the cluster that hosts the server**, nor on any machine that holds the server's bucket credentials.
* Unlock of the agent's own state follows the `hardware` precondition; no passphrase or Vault-only unlock.

## Consequences

* The server holds only ciphertext of one outer shape and padded sizes, the structural slots objects, the root, devices and location documents, and no handle if fan-out is chosen; it is replaceable; a lost server loses no data when a bucket survives.
* Chain and object verification no longer need the passphrase, which makes a backup checkable by a third party who holds a pin. What the sealed manifest binds is checked only by an unlocked client.
* Every commit costs one device signature (more if `threshold heads` is raised), a slot change or rotation costs devices-role touches, and a client must refresh the head before it expires. A bucket gets many small objects of a few bucket sizes, up to twice the payload size; `store gc` and prefix sharding (`<aa>/`) are needed. Heads, roots, location statements and the structural objects are never collected.
* The access list gives the server the set of device keys, the root keys, the keys of the devices role, the mailbox-only party fingerprints and commit timing. Commit timing and commit shape are the residual metadata leak.
* Enrolling or removing a device, changing a slot or promoting a copy needs the operator's FIDO2 credentials (one touch each), not the root keys, on an authenticator separate from the daily one; losing the root threshold stops changes of the root keys and the `devices` role, and is unrecoverable except by re-genesis into a new workspace id, which re-seals every cold record.
* Revoking a device is a devices document with a `void-after` sequence, a head that skips the thief's heads, and a rotation: it costs devices-role signatures and a re-encryption of the whole workspace, and binds clients that have learned the new document; the second head log and the freshness bound on Secret-class records limit what a split view can give away.
* Two stores coexist for several stages; the cost is the differential test; each workspace id has one canonical store.
* A split-view attack by a malicious server on two clients is detected by the second head log unless the attacker also controls the sink. A backup copy cannot be used as a working store until it is promoted by a devices-role statement; its content reaches the live workspace by a takeover that extends the live chain, with every cold record re-sealed.
* Write access to the bucket allows denial of service by squatting heads; clients detect it and skip failing heads by the gap rule, and nothing is overwritten. A stolen device key cannot change the root, the devices document or the slots, add a device or rotate, and after its removal nothing it commits past `void-after` is accepted; until then it can commit heads that an unlocked client cannot open.
* Server and bucket deployments need the `hardware` policy, root and devices-role keys that are FIDO2 or hardware-wallet keys (a software key is refused), and hardware-bound or TPM-bound device keys; a `standard` workspace stays local.
* Kubernetes runs the server only; block producers stay on systemd hosts; there is no client agent in this record.

## Open questions for the owner

Each has a recommendation and the trade-off. Items 1 to 3 shape scope; 4 to 7 the trust model.

1. **What the Kubernetes deployment does.** Recommended: ordering, storage and the mailbox only; no use case runs in the cluster (decision 11). Trade-off: the cluster never holds a factor, a key or a plaintext, at the price that every operation that needs a key stays on an operator machine.
2. **Whether there is a client agent.** Recommended: not in this ADR; a separate record that meets the constraints of decision 12. Trade-off: no scheduled key-using jobs now, but no long-lived holder of unlocked material and no contradiction with the `hardware` policy.
3. **Block producers in Kubernetes.** Recommended: out of scope for v1; systemd hosts only (decision 11). Trade-off: no pod-based producer until an identity, sender authentication and monotonic state exist, in exchange for not weakening the delivery the helper enforces.
4. **Server-visible handles or envelope fan-out.** Recommended: fan-out (decision 7). Trade-off: every own device receives and answers every demand and the server learns nothing, against handles that save that traffic but leak equality, linkage across rotation and a revoked device's ability to compute them.
5. **Multi-writer direct-bucket mode in v1.** Recommended: no; one writer, the server or one local device (decision 4). Trade-off: devices cannot write to a bucket themselves, which removes per-device bucket credentials and the part of the model that a bucket policy could not verify.
6. **Split-view defence.** Recommended: the backup sink as a second head log now, C2SP witness cosigning later (decision 3). Trade-off: the sink log costs one object per commit and defeats a lone hostile server, but not an attacker who holds both the server and the sink; witnesses would cost a checkpoint-shaped statement and third parties.
7. **Root and devices-role keys.** Recommended: FIDO2 SSHSIG root keys, 2 of 3, kept apart; the devices role on a separate authenticator from every daily slot (decision 3, S2); and confirmation of the one-command extension of the recovery composite's scope (`workspace rotate --from-backup`, decision 3). Trade-off: three authenticators for the root plus two for daily use and the devices role, against a root that one lost token cannot freeze or one stolen token cannot move.
8. **`standard` workspaces backed up to S3.** Recommended: keep the refusal; filesystem backups only (decision 2). Trade-off: a `standard` operator cannot use a bucket as a sink, but a bucket holder cannot guess the passphrase offline.
9. **Pin format and lifetimes.** Recommended: the pin includes a head (decision 3); 14-day head validity (90-day cap), 30-day gc grace. Trade-off: a pin that includes a head must be re-printed after each commit or backup and kept outside the sink, in exchange for refusing a rolled-back restore; shorter validity trips the freeze more often.
10. **TPM-bound device slots under `hardware`.** Recommended: no; a TPM-bound factor protects only the device key file (decision 3). Trade-off: a stolen laptop with its TPM cannot unlock the workspace, but a workspace cannot be unlocked unattended by a TPM either.

## Open questions

Technical points, unconfirmed or to be read before the format is frozen.

* Whether S3-compatible stores other than AWS S3 (which documents `If-None-Match` on `PutObject`) support it, and object lock or deny-overwrite policies, with what guarantees.
* Whether `golang.org/x/mod/sumdb/note` is adopted for the signed-note framing or the format is implemented directly: unconfirmed; its verifier ignores unknown signature lines, so the exact-lines rule needs a wrapper either way. RFC 9530 (`content-digest`) was not read. The 60-second window of decision 7 is a proposal.
* Device key. Recommended: a separate key per workspace cross-signed by the party identity, sealed at rest under a TPM-bound or FIDO2 factor, with the Argon2id passphrase fallback only under `standard` (decision 3). Whether a FIDO2 authenticator or TPM can hold a non-exportable Ed25519 head-signing key: unconfirmed.
* Unconfirmed: the signature type byte values `0x20` and `0x21`; that `golang.org/x/crypto/ssh` verifies security-key signatures and has no SSHSIG support; the `ssh-keygen` options for the application string and `verify-required`; which authenticators support Ed25519 for `sk-ssh-ed25519`; the CIP-8 header form and arbitrary-payload signing on Ledger and Trezor; whether any display hardware wallet shows a CIP-8 payload.
* The `devices` role: whether a lost devices-role credential should be replaceable without a root version (it cannot be, as designed).
* How an operator finds the last legitimate head when no other device is enrolled (the proposals: the second head log, or the operator's own record of the last commit).
* The grace period of `store gc`, the head validity, the cap on expiry, the half-validity refresh rule, the five-minute freshness bound of decision 3 and the freshness sources of rule 4 are proposals.
* C2SP tlog-witness (unconfirmed) as the later split-view defence.
* TUF: the version (1.0.37) and the section numbers of decision 3 were read from the published specification; the step numbers inside sections 5.3 to 5.6 for the rollback and freeze checks are to be read against the text before the format is frozen.
* Padding: power-of-two buckets with a 4 KiB floor are proposed; the floor and the chunking above the largest bucket are to be set with the layout.
* Plaintext root and devices documents let an observer who sees two workspaces' access lists link an operator's machines across them by the party fingerprint, which is the same in every workspace. Whether the fingerprint is replaced in the root by a per-workspace value is open.
* Whether the sink may be a read-write live store of another workspace (a backup of a backup).
* The node-delivery exception of ADR 0011 and any later scheduled KES rotation are for the record that defines an agent.

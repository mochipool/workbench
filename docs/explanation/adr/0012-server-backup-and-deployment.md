# ADR 0012: Server, backup and deployment

Status: draft — not ready for approval; the trust model (root, devices document and head chain) needs a further security review. Extends [ADR 0003](./0003-vault-and-store.md) (rollback and backup), [ADR 0005](./0005-party-envelope-and-signing-policy.md) (enrolment, envelope) and [ADR 0008](./0008-capability-typed-ports.md). Depends on [ADR 0010](./0010-object-identity.md) (identities, handles) and [ADR 0011](./0011-key-custody-and-unlock.md) (unlock, slot policy, rotation). Closes none of the numbered concerns; it supersedes the deferral in decision D9 ("a server API stays deferred") and meets S2 for several replicas.

## Amends

* [ADR 0003](./0003-vault-and-store.md), "Rollback": for the sealed object store, the unauthenticated head file is replaced by the signed head chain of decision 3. The SQLite file keeps its head file until it is demoted to a cache (decision 6).
* ADR 0003, "Backup and recovery", `restore`: for the sealed object store, `--allow-older` opens an older head **read-only**; it is not a way to write over a newer workspace (decisions 9 and 10). The SQLite `restore` is unchanged until demoted.
* ADR 0003, associated data: the "workspace id" bound in slot and record associated data is the genesis nonce (amendment stated in [ADR 0011](./0011-key-custody-and-unlock.md), Amends; decision 3 here uses it). The workspace id of this record is the hash of root version 1 and is not bound there.
* [ADR 0004](./0004-data-classification.md), table of classes: the **root documents** and the **devices documents** (decision 3), which list root public keys, the keys of the devices role, device public keys, party fingerprints and their cross-signatures, are reclassified from Sensitive to Structural and stored in plaintext. ADR 0004 classes a link between an operator and a public-on-chain value as Sensitive; a device key and a party fingerprint are not public on chain, but they identify the operator's machines and co-signers. What an observer of the bucket or server learns from them: how many machines the operator enrols and how many co-signers they have, the fingerprints and public keys of each, when each was enrolled or removed (the devices version or head that changed it), which device signed which head, when the root or the devices document changed, and commit timing. It does not learn a name, a pool, a key hash or what a co-signer signs. Each workspace enrols its own device key (decision 3), but the cross-signed party fingerprint is the same in every workspace the machine joins, so an observer of two buckets can link an operator's machines across workspaces by that fingerprint (open questions).
* [ADR 0005](./0005-party-envelope-and-signing-policy.md), enrolment: a party is enrolled either as one of this operator's head-signing **devices** or as a **mailbox-only party**, both listed in the devices document (decisions 3 and 7); this is how a server learns the own clients that ADR 0010 leaves open. ADR 0005's ceremony is reused, and an enrolment carries the pin (a root version and its hash). ADR 0005's approval gate is amended in ADR 0011.
* [ADR 0002](./0002-architecture-and-dependencies.md), "Layout" and "Third-party modules", in addition to the amendment of [ADR 0011](./0011-key-custody-and-unlock.md): `adapters/sealedstore` (the `Store` and `Vault` over an object store and a head log), `adapters/objstore/{dir,s3,gcs}` (the `ObjectStore` and `HeadLog` back ends) and the server adapters of this record are added. Modules: `golang.org/x/mod/sumdb/note` for the signed-note framing, if adopted (confined to `adapters/sealedstore`; unconfirmed, open questions); `golang.org/x/crypto/ssh` for the SSHSIG root signatures (decision 3; in `go.mod` as an indirect module today, unconfirmed); the S3 and Google Cloud Storage clients (`adapters/objstore`); `ssh-keygen` as a pinned external tool for root signing. Each enters the `confined` table of `spo/internal/archtest/arch_test.go`.

## Context

Requirements R1, R4, R6 and R7 of the owner: any client, local or reached over tailcat or Tailscale, acts on committed objects without a difference; on a highly available Kubernetes deployment too; the server cannot decrypt; backups go to a sink such as S3 or a directory and can be re-imported; the same design runs as a Kubernetes deployment and as a local deployment that uses the backup artefact directly.

**What exists today.** One SQLite file per workspace, opened by one process that holds the unlocked keys ([ADR 0003](./0003-vault-and-store.md)). Its head file records the newest audit sequence and MAC and is unauthenticated: someone who replaces the file and its head together with an older pair is not detected (`spo/internal/adapters/sqlitestore/head.go`, "WHAT THIS DOES NOT DO"). Backup is `VACUUM INTO` plus a verification; the copy has no head file of its own, and restore opens it with the passphrase or recovery key to verify it (`sqlitestore/backup.go`, `Restore*`). A multi-party coordinator today is a process with the unlocked store: tailcat serves it and the party registry is a sealed record in the same store (`adapters/tailcat/server.go`, `adapters/partystore`). The workspace file lives on a local disk because advisory locks are unreliable on network file systems (ADR 0003).

Two consequences for this record. A server that cannot decrypt cannot read the sealed party registry, so it cannot use ADR 0005's `Admit` for authentication; it needs an access list of its own (decision 7). And ADR 0004 classes anything public on chain as Sensitive, so the server holds *no plaintext object at all* except the structural ones named below: "public objects" in the working notes do not exist.

## Decision

### 1. Roles

* **Server**: stores sealed objects, a signed head log and sealed envelopes in transit; orders commits; authenticates clients by device key. It is stateless over the object store, so any number of replicas serve.
* **Client**: any `spo` process the operator unlocked. It decrypts, runs every use case, signs with vault-held keys, drives hardware wallets attached to it, queries the chain and submits.
* **Local deployment**: a client with no server, opening a directory or bucket of the same layout directly.

Two sets of parties are kept apart. **Devices** are this operator's own clients: they hold the workspace's master key, can commit heads with their device key for as long as the current devices document lists them (decision 3), and can compute blinded handles. A device cannot change the root or the devices document, and so cannot add or remove devices; the devices document is signed by the operator's own FIDO2 credentials, the `devices` role that the root delegates. A device cannot change the root keys either. **Mailbox-only parties** are co-signers under ADR 0005, other operators who hold no master key of this workspace: they can deliver envelopes to, and fetch envelopes addressed to, themselves and nothing else.

The server never holds an unlock factor, a master key, a data key or a plaintext secret, and never signs with a vault-held key. Hardware keys sign on the device attached to a client. A key held by a client that is not connected cannot sign; nothing in the server can stand in.

### 2. What the server sees, and what a compromised one can do

| The server sees | From |
| --- | --- |
| Object hashes, exact sizes of sealed objects, creation times | the layout of decision 4 |
| Per object: a blinded handle (HMAC of its identity under the workspace handle key, [ADR 0010](./0010-object-identity.md) decision 5) | commits and signing requests between devices |
| Per record: random id, kind, version, time of write; the exact length of Sensitive payloads, the size bucket of Secret ones | ADR 0003, "What the file reveals" |
| Slot count, kinds, policy, KDF parameters, credential ids of FIDO2 slots and the relying-party id | the slots object is readable before unlock |
| Root public keys, thresholds and expiry; the keys of the devices role; device public keys, fingerprints and cross-signatures; mailbox-only party fingerprints and public keys; root and devices versions; which device signed which head; commit rate and timing | the root documents, the devices documents and the head log |
| For envelopes: recipient and sender party fingerprints needed to route, size, time | decision 8 |
| The client's network address or Tailscale identity | transport |

R1 and R4 are met together by the handles among devices: the server tells objects apart, deduplicates and routes a signing request between devices to the one that announced the handle, and does not see a key hash, a pool id, a name, a descriptor, a balance, run history, audit event text, a `label` record or the party registry. It can still infer the number of distinct handles, which handles occur together, which device announced which handle (so which device holds which key), and how often each is used; a rotation replaces every handle in one commit, which lets it link old to new ([ADR 0010](./0010-object-identity.md) decision 5). Requests to co-signers are routed by party fingerprint and carry no handle.

A *compromised* server can: refuse service; withhold or delay objects and envelopes; serve an older head (detected by a client that persists the newest head and root and devices versions it verified, decision 3); withhold newer heads (detected as a freeze when the newest head it can show has expired); show two clients different histories (detected only when they compare heads); delete objects (detected as a missing hash; recovered by re-publication or restore, decision 4); learn timing and sizes. If it can write to the bucket it can squat `heads/n+1`, or write garbage at higher numbers; clients ignore any head that is not part of the valid chain and skip it by the gap rule (decision 3). This is denial of service that is detected and recoverable, never a forgery. It cannot read any payload; forge a head, a root or a devices document (it lacks every device key, the root keys and the devices role keys); add or alter a slot (it lacks the master key, and the slots hash is in the signed head); change the device set or the root keys (that needs a new devices document signed by the devices role, or a new root version signed by a threshold of the old and of the new root keys); or make a client accept an object whose hash does not match. It can keep a client from learning a newer root or devices document until the client is shown it by another device or by the operator's pin (decision 3).

**Deployment precondition: the `hardware` policy.** Under the `standard` policy of [ADR 0011](./0011-key-custody-and-unlock.md) the passphrase slot can be guessed offline by whoever holds the bucket or the server's storage, bounded only by the Argon2id parameters. A server or bucket deployment therefore requires the `hardware` policy (or `strict`): the sealed object store refuses a bucket or server back end for a workspace whose slots object says `standard`. A `standard` workspace is local-only, and a filesystem backup of it prints a warning that states the offline-guessing exposure.

### 3. Integrity with an untrusted server: a signed root, a signed devices document, and a signed, hash-chained head

**Model.** Trust is anchored in a **root** document held by the operator, not in anything derived from the master key. The roles, thresholds, rotation, rollback and freeze rules are those of The Update Framework (TUF specification, version 1.0.37 of 8 October 2026; the roles in section 2.1, root key rotation in section 6.1, the client's root update procedure in section 5.3, the attacks in section 1.5.2; the version and section numbers were read from the published specification). The mapping:

| Here | TUF |
| --- | --- |
| Root document (versioned; root keys and threshold; the keys and threshold of the delegated `devices` role) | Root role, section 2.1.1 |
| `devices` role and its document: the operator's own FIDO2 credentials sign a versioned document that lists the device keys | A delegation of signing authority from the root; the closest TUF notion is the keys the root names for the snapshot and timestamp roles, but TUF has no signed list of committing keys with a void rule, so the mapping is loose |
| Head: sequence number, expiry, previous-head hash, the root and devices versions it was made under | The snapshot and timestamp roles, sections 2.1.3 and 2.1.4: consistency of the set of objects, and freshness |
| Manifest (sealed list of records) | Takes the place of the targets role; it is sealed, so a locked client cannot read it |

**What TUF does not give.** TUF is designed for software update metadata: a repository of target files that many clients download and verify. This record adopts its role, threshold, rotation, rollback and freeze rules and not its file layout (its JSON metadata, consistent snapshots, delegations and mirrors). TUF's freshness rules limit but do not remove a split view: a server can show two clients two different, individually valid histories until they compare. It does not protect a client that never learns of a newer root or devices document, beyond the expiry of what it was shown ("Revoking a device", below). The loss of the root threshold is unrecoverable (below). Cosigning of heads by independent witnesses (the C2SP tlog-witness protocol, c2sp.org/tlog-witness; its details were not read here and are unconfirmed) would add a defence against a split view. It is a later measure and is not designed here: it needs a checkpoint-shaped statement, and the head of this record is deliberately not one (below).

**Notes and signature types.** The root, the devices document and every head are written in the C2SP signed-note format (c2sp.org/signed-note), the framing used by the Go checksum database and by Sigstore's transparency-log checkpoints. A note is UTF-8 text ending in a newline, an empty line, then signature lines of the form em dash, space, key name, space, base64 of a 4-byte key id followed by the signature. Signature type `0x01` is Ed25519 (RFC 8032), the key id is the first four bytes of SHA-256 over the key name, a newline, the type byte and the public key, and a key name must contain no space or plus sign. A raw Ed25519 signature over the note text cannot come from the keys this record recommends for roots: a FIDO2 authenticator signs `authenticatorData ‖ clientDataHash` and not arbitrary bytes, and a Cardano hardware wallet signs transactions or CIP-8 structures only. Root and devices-role signatures therefore use these signature types, each a distinct note signature type with the same key-id derivation (the type byte values `0x20`, `0x21`, `0x22` are proposed here and are unconfirmed against the signed-note type registry):

* **`0x20`, OpenSSH SSHSIG with a FIDO2-backed key** (`sk-ssh-ed25519@openssh.com` or `sk-ecdsa-sha2-nistp256@openssh.com`). The message is the note text. The signature is the SSHSIG blob of OpenSSH's `PROTOCOL.sshsig` (confirmed from that document: the preamble `SSHSIG`, version 1, public key, namespace, reserved, hash algorithm `sha256` or `sha512`, signature; the signed data is the preamble, namespace, reserved, hash algorithm and the hash of the message, and the namespace must not be empty). The namespace is fixed by the note kind: `spo/root/v1` for a root and `spo/devices/v1` for a devices document, and the hash algorithm is `sha512`. The key id covers the SSH wire-format public key. `golang.org/x/crypto/ssh` exports `KeyAlgoSKED25519` and `KeyAlgoSKECDSA256` and parses SSH public keys; that its `PublicKey.Verify` verifies the security-key signature form (the flags byte and counter that the authenticator signs) is expected but unconfirmed here, and that the package has no SSHSIG support is likewise unconfirmed. A verifier therefore implements the SSHSIG framing itself and checks the signature with `ssh.PublicKey.Verify`, and a test against signatures made by `ssh-keygen -Y sign` pins it. The signature must carry the user-presence flag and the user-verification flag (per the security-key signature format of OpenSSH's `PROTOCOL.u2f`; unconfirmed from the source here); a root key is created with the `verify-required` option, and the application string is fixed at `ssh:spo` (unconfirmed that `ssh-keygen` accepts it for sk keys; the option is `-O application=`). Signing is done by `ssh-keygen -Y sign`, driven through `execx` as a pinned tool; whether a given authenticator supports Ed25519 is unconfirmed, and the ECDSA P-256 form is the one every FIDO2 authenticator supports.
* **`0x21`, CIP-8 `COSE_Sign1`** for a hardware-wallet key (CIP-8 message signing, RFC 9052). The payload is the note text, the protected header carries the EdDSA algorithm and the key's hash (the header form that Cardano hardware wallets accept for message signing is unconfirmed), the key hash of the signer is the root key's identity, and the verifier checks the Ed25519 signature over the `Sig_structure` of RFC 9052. Whether `cardano-hw-cli` or the device firmware signs an arbitrary payload in this form for a Ledger or Trezor is unconfirmed.
* **`0x01`, a software Ed25519 key,** is allowed only for a workspace under the `standard` policy of ADR 0011 that is local (no server, no bucket). Under `hardware` or `strict`, falling back to a software root key kept on disk is refused: the workspace does not accept a note signed with type `0x01` as a root or devices signature, and `store init` refuses to create a root whose keys include one.

A note carries signature lines that match the keys of its role and nothing else (the exact-lines rule below applies to every note kind of this record).

**The root document.** The text of a root is:

```
spo/root/v1
<version, decimal>
<"nonce:<hex>" in version 1; the workspace id in hex in later versions>
<expires, RFC 3339 UTC>
threshold root <n>
rootkey <signature type> <public key hex>          one line per root key
role devices <m>
devkey <signature type> <public key hex>           one line per key of the devices role
```

The first line is the domain tag. The hash of a root is Blake2b-256 over the note text only, never over the signature lines (a signature line can be re-encoded without invalidating the signatures, so a hash over them would give one root many names). **The workspace id is the hash of root version 1**; version 1 carries the genesis nonce (16 random bytes), which the slot and record associated data of ADR 0003 bind (ADR 0011, Amends), so two workspaces never share an id even if they share keys. Roots are stored as `roots/<version>`, write-once.

* **Root keys** are held by the operator and are offline-capable: FIDO2 authenticators (signature type `0x20`) or hardware-wallet keys (type `0x21`). They are never derived from the master key and never held in a device's file. **The root changes only root keys and role delegations** (the keys and threshold of the `devices` role); it does not list devices. Recommended: 1 of 2 or 2 of 3, with the keys kept apart (two places).
* **A new root version** is signed by a threshold of the keys of the **previous** root and a threshold of the keys of the **new** root (TUF section 5.3). Its version is exactly the previous version plus one. A key present in both may sign once and counts for both. A root note carries no signature line from a key that is in neither root, none repeated and none that fails to verify; otherwise it is refused.
* **Expiry.** A root has an `expires` time that the operator sets (recommended one year). A client does not commit under an expired newest root and reports it; renewing it is a new root version.

**The devices role and the devices document.** Enrolling a device at the root threshold would need the root keys for every new laptop, which is unworkable for one operator. The root therefore delegates a `devices` role: its own keys (the operator's FIDO2 credentials, which are in the operator's pocket in daily use) and its own threshold (1 by default). The role signs a **devices document**, versioned, stored as `devices/<version>`, write-once:

```
spo/devices/v1
<version, decimal>
<workspace id in hex>
<root version> <root hash>                             the root it is made under
threshold heads <k>                                    device signatures a head needs (1 by default)
device <fingerprint hex> <public key hex> <cross-signature hex>    one line per device
mailbox <fingerprint hex> <public key hex>             one line per mailbox-only party
removed <fingerprint hex> void-after <seq, decimal> <head hash>    one line per removed device
```

A devices document is valid when its version is the previous one plus one, the root it names is verified, and it carries signature lines by exactly the threshold of `devkey` keys of that root and no others. A device cannot sign it, so **one unlocked device cannot add or remove devices**, and a thief of one device key cannot either. The `removed` line is the void rule of "Revoking a device". When a root changes the `devices` role keys, the next devices document is signed under the new root. Mailbox-only parties are listed here because the server's access list reads them in plaintext (decision 7).

**The head.** Each commit appends one **head**, written in the same signed-note framing. The text of a head is:

```
spo/head/v1
<kind: genesis | normal | refresh | rotation | takeover>
<workspace id in hex, or "nonce:<hex>" in the genesis head>
<seq, decimal>
<previous head hash, hex; empty in the genesis head>
<root version> <root hash>
<devices version> <devices hash>
<manifest hash> <slots hash>
<committing device fingerprint>
<expires, RFC 3339 UTC>
recovery-key <hash of the recovery public key, ADR 0011 decision 6>
[skips: "skips <seq>:<note hash> ..." listing the sequence numbers and the note hashes of the heads skipped by the gap rule]
[takeover only: "restored-from <head hash of the backup the content came from>"]
```

The first line is the domain tag, so a signature over a head cannot be taken for another kind of statement. A head has an **expiry**: the committing client sets it, by default the commit time plus 14 days, and at most a cap of 90 days for a planned absence of the operator (both are proposals). A `refresh` head repeats the manifest and slots hashes of its predecessor with a new sequence number and expiry; an unlocked agent (decision 12) or any device may commit one, as a client does when the newest head has passed half its validity, but never on top of an expired head (rule 4). The `recovery-key` line is the same in every head unless a rotation that presented the recovery composite changes it. In an object store the hash of the recovery public key is carried in each head as well as in the associated data of every slot ([ADR 0011](./0011-key-custody-and-unlock.md) decision 6); the client compares both.

**The head hash is over the note text only,** for the reason given for roots. A head carries **exactly** the signature lines expected: one by each of the committing devices (as many as the devices document requires of a head, one by default, each listed in the devices document the head names), in order of fingerprint, and no other. A note with any other signature line, a repeated one, a missing one, an unparsable line, or text that does not match the layout above is refused. The signed-note format lets a verifier ignore unknown signature lines; this record does not. The tlog-checkpoint body of the same project (origin, tree size, Merkle root) is not used: there is no Merkle tree here, and putting a sequence number and a hash in the tree-size and root-hash lines would make monitors read a log that is not one. Go's `golang.org/x/mod/sumdb/note` implements the framing for key type `0x01`; adding it as a dependency is unconfirmed, and its verifier ignores unknown signature lines and unknown signature types, so the exact-lines rule and the types of this record are applied by code of this record in front of it.

**Authorised changes.** The root authorises only a change of root keys or of the `devices` role. A rotation of the master key ([ADR 0011](./0011-key-custody-and-unlock.md) decision 6) and the revocation of a device are authorised by the devices role: the devices document changes **first** (a new version signed by the role; it may leave the device set unchanged when only the master key rotates), and then the `rotation` head commits under it: a `rotation` head names a devices version higher than its predecessor's, and its committing device is listed in that new document. Nothing else rotates the master key in the chain.

**Device key.** The device key is a separate Ed25519 key per workspace, cross-signed by the machine's ADR 0005 party identity: the party identity signs the device public key and the device key signs the party fingerprint, each under its own domain tag; the cross-signature is in the device's line of the devices document. The device key signs the head signature line (`spo/head/v1`) and request authentication (decision 7, tag `spo-request-v1`). **Domain tags.** A key signs under more than one context only where each context has its own domain tag, which is the rule here, and the tags are: the device key, `spo/head/v1` (the first line of the note) and `spo-request-v1` (the RFC 9421 `tag` parameter); a root key, `spo/root/v1` only; a key of the devices role, `spo/devices/v1` only; the party identity key, which signs the ADR 0005 envelopes and rotation statements under ADR 0005's domain strings, the device cross-signature under `spo/device-cross/v1`, and, for a mailbox-only party, requests under `spo-request-v1`. When a party identity rotates (ADR 0005), a new cross-signature is carried by a new devices version.

**Device key at rest, before unlock.** The device key is needed before the workspace is unlocked, to authenticate to a server, so it cannot depend on the master key. Chosen: it lives in a file that is sealed (XChaCha20-Poly1305) under a key from a device-local factor. Under the `hardware` and `strict` policies, which every server and bucket deployment requires (decision 2), the device-local factor must be a TPM-bound `systemd-creds` credential (on Linux where a TPM 2.0 exists) or a FIDO2 `hmac-secret` output; the Argon2id key from a device passphrase is **refused** there and is allowed only under `standard`, which is local-only. The key is opened into guarded memory for a session and never exported. A non-exportable signing key in a FIDO2 authenticator or the TPM was considered and is deferred: whether a given authenticator or TPM supports Ed25519 is unconfirmed, and a P-256 key would change the head signature suite.

**Client rules** (TUF section 5.3 for the root, and the rollback and freeze checks of its later steps, here applied to heads).

1. **Roots and devices documents first.** Before trusting any head, a client walks root versions from the newest it has verified (at the start, the pinned one): it fetches `roots/<v+1>`, verifies it as above, and repeats until there is none; then it does the same for `devices/<v+1>` under the newest root. A document that is absent is unavailable and is retried; a document that fails is ignored. A newest root or devices document that is older than one the client has already verified is refused (rollback).
2. **Heads.** A head is **valid** against the verified chain up to its predecessor, where the predecessor is the last valid head, when: the framing and the exact signature lines hold; the root version it names exists, verifies, is not lower than its predecessor's, and is not lower than the newest root the client knows when the head extends the chain beyond the client's last verified head; likewise for the devices version it names; each committing device is listed in the devices document the head names and is **not void** (rule 6); the previous-head hash equals the hash of the predecessor; the sequence number is one above the predecessor's plus the number of heads it skips (rule 7); a `rotation` head names a higher devices version than its predecessor; the `recovery-key` line equals the predecessor's unless the head is a `rotation` head; and the slots hash the head references equals the hash of the bytes stored under that name (and, for the newest head, the manifest). Expiry is not a validity check: an expired head is valid and old.
3. **Rollback.** A client persists the newest head, root version and devices version it has verified, and refuses a head with a lower sequence number or a head that names a lower root or devices version than it knows. Two different heads at one sequence number that both pass the checks are a fatal alarm: the client that sees both stops writing and reports them.
4. **Freeze.** When the newest head a client can obtain has expired, the client treats it as a freeze alarm and **refuses to commit** on top of it. It is not a click-through: the client continues only when the freshness is corroborated by a source independent of the server, either
   * **another enrolled device's last-seen head**, exchanged over ADR 0005's transport in a signed answer to a challenge the client draws: a head with a sequence number at least as high as the client's newest, reported by a device that is not the one committing, within the time of the exchange. This proves that, as of the exchange, an independent device had seen no newer head than the one the client holds or had seen a head the client can fetch; it does not prove that no newer head exists, because a device and the client can both be kept from the same later head by the server; or
   * for a **pool workspace**, the operational-certificate counter on chain compared with the counter recorded in the store: the on-chain counter of the pool's cold key (read from a chain provider the client already trusts for submission) must be no higher than the store's. This proves that the store has not fallen behind the last block-producing use of the pool's certificate; it proves nothing about commits that did not touch a counter.

   The committer may set a head's expiry up to the cap (90 days), so a planned absence does not trip the freeze; an unlocked agent may commit `refresh` heads while the newest head is unexpired. A restore of an old backup reports the expiry of its newest head and is not refused for it.
5. **Failing.** A head is **failing** only if it fails a check of rule 2 that a locked client can make, and that check can be decided from bytes the client holds or can fetch. **Nothing else makes a head failing or void.** A head whose manifest names an unknown key epoch, whose manifest does not open under the master key, or whose slots object does not open, passes the locked checks and is not failing: the client cannot judge it locked, and it means *re-unlock*. A referenced object, root or devices document that is *absent* is unavailable, and the client waits and retries, because a hostile or lagging store can hide an object and must not be able to make a valid head look skippable. What a locked client **cannot** verify: what the manifest lists, that the manifest's sealed sequence number and predecessor match the head, and that the manifest is the genuine one for that point. It can check that the manifest's plaintext epoch equals the epoch of the slots object the head references; a mismatch is a refusal that stops the client and is reported, not a ground for a skip. A credential-free restore (decision 9) is therefore a check of the chain and the objects, and `store verify --deep` after unlocking is the full check.
6. **Void heads.** A devices document that carries `removed <fingerprint> void-after <seq> <head hash>` makes **void**, for every client that knows that document, every head signed by that device with a sequence number greater than `<seq>`, whatever root or devices version the head names. The head hash in the line is the head at `<seq>`, so a client that holds a different head at that number rejects the document as inconsistent with its chain. A void head is skipped by rule 7, and a client does not move its state for it.
7. **The gap rule.** Heads are write-once (decision 4), so a failing or void head can never be replaced. The chain continues past it: the next valid head names as its predecessor the **last valid head**, carries the sequence number after the skipped one or ones, and carries an explicit `skips` line listing each skipped sequence number with the note hash of the head stored there. A client accepts a skip only for a head it can itself judge: failing by rule 5 or void by rule 6. A head that is merely unavailable or that cannot be judged locked is never skippable, so a hostile writer cannot make a good head look skippable by hiding an object. A `skips` line that lists a sequence number the client judges valid, or that omits a failing or void head standing between the predecessor and the new head, makes the new head invalid.

**The manifest** is a sealed object that lists every live record id with its version and object hash. Labels and owner records ([ADR 0010](./0010-object-identity.md) decision 2) are records of kinds `label` and `owner` and are listed like any other record; there is no separate label index object. The manifest also contains, inside the seal, the sequence number and the previous head hash, and it carries its key epoch in a plaintext header. **Only an unlocked client can verify the sequence number and the previous-head hash inside the sealed manifest**, because they are inside the seal. A listed device key that signs head n+1 pointing at an old genuine manifest is a valid head for a locked client; an unlocked client then finds another sequence number or predecessor in the manifest and stops.

**The slots object** is immutable and hashed from the head, and is readable before unlock. The devices document is plaintext, because the server's access list must read it.

**What a stolen device key can and cannot do.** A device key, opened with its local factor, lets its thief authenticate to the server and commit heads until the operator removes the device. It cannot change the root or the devices document, so it cannot add a device, remove one or rotate the master key. It does not hold the master key, so it cannot produce a manifest or slots object that an unlocked client can open; a head it commits is valid for a locked client and unusable for an unlocked one, which stops and reports (rule 5). Once the device is removed with a `void-after` sequence (below), **nothing the thief commits after that sequence is accepted** by a client that knows the new devices document: those heads are void and are skipped. A client that has not yet learned the document can be kept from it by a hostile server until the freshness rule (rule 4) or another device tells it. The thief cannot make a client accept a head, a manifest or content it chose.

**Revoking a device.** A revoked device still knows the master key, and the data keys of everything it opened. Revocation is a devices document followed by the **rotation** of ADR 0011 decision 6. The operator's procedure, in this order:

1. In a direct-bucket deployment, where devices write to the bucket with their own credentials, revoke the device's bucket write credential (and its read credential). Write credentials are per device for this reason (decision 4).
2. Find the last head that is known to be legitimate: the newest head committed by the device before the loss, taken from another enrolled device's last-seen head or from the operator's record of the last commit made on the device itself. Heads after that one that were signed by the lost device are the thief's. Choosing a number too low voids honest heads from that device and costs only a skip; choosing it too high leaves the thief's heads valid.
3. Commit a new devices document, signed by the devices role (one FIDO2 touch), that removes the device with `void-after <that sequence> <that head hash>`.
4. Commit the next head under it from a remaining device. It names the last valid head as predecessor and carries a `skips` line for every head of the removed device after `void-after` (rule 7). The heads of the removed device that already exist are listed by their sequence numbers and note hashes.
5. Commit the rotation head of ADR 0011 under a higher devices version: a new master key, fresh data keys, every payload re-encrypted, new slots, new handles, in one head signed by a remaining device.

A revoked device cannot produce a head that a client which knows the new devices document accepts: its heads after `void-after` are void, and a head naming the new document does not list it. A client that does not yet know the new document learns it by walking devices versions before it trusts any head (rule 1). A client that the server keeps from the new document, because the server withheld it or because the client was offline, still accepts the revoked device's heads, until those heads expire (rule 4) or the client is shown the new document by another device or the pin of the operator. The revoked device can still read what it could read before. The operator rotates any key material the revoked device could read (ADR 0011).

**Pins.** The operator's pin is a root version and the hash of its text. It is printed at creation and on every root change, and `store verify` prints it. A fresh client, and a restore, require a pin at or after the newest root version the operator knows; with an older pin the walk of rule 1 would start from a root the operator has since replaced. A fresh client starts from the pin and the root documents and devices documents that follow it, then takes the newest valid head under them; it walks previous-head links back to the first head made under the pinned root version or to genesis (`store verify --full` walks all). Enrolled devices exchange their last-seen head, root version and devices version in the ADR 0005 envelope and compare. A fresh client without a pin is refused, because a server could otherwise show it an old but genuine root and chain.

**Loss of the root threshold and re-genesis.** If fewer root keys than the threshold survive, no new root version can be made, and the workspace cannot change its root keys or the keys of its `devices` role. Devices can still be changed while the `devices` role keys survive. This is unrecoverable by design: nothing else can authorise a root change without making the root meaningless. The way out is **re-genesis**: an operator who can still unlock a copy of the workspace (the slots, or the recovery composite) creates a **new workspace id**, that is, a new root version 1 with new root keys and a new genesis nonce, and a genesis head whose manifest holds the content of the chosen head, re-sealed under a fresh master key. The operational-certificate and KES counters of the new workspace are the larger of the live and the backup values, never lower (decision 10). Nothing in the old chain authorises the new one, so no client follows it by itself: every device is enrolled again and the operator prints and distributes the new pin. The old workspace id is retired by the operator, who revokes the old bucket credentials; its chain remains and can still be read by whoever holds its factors.

What this catches: rollback of a client that has seen newer; a forged head, root or devices document; a replayed old manifest; heads of a revoked device after the new devices document is known; set tampering. What it does not: a split view between clients, which stays detectable only by comparison, and a client that is kept from the newest documents.

**Compared with a transparency log** (RFC 9162, Certificate Transparency 2.0): a Merkle tree head with consistency and inclusion proofs serves many clients that cannot fetch the whole log and need monitors. Here the history is one operator's and clients fetch the whole manifest; consistency proofs would add machinery and the split-view problem would remain, because it needs gossip either way. Recommendation: the root document, the devices document and the hash-chained signed head in signed-note framing.

### 4. Layout, the latest head, and retention

```
workspace/
  objects/<aa>/<hash>   immutable: sealed records, audit rows, manifests,
                        the slots objects
  roots/<version, 20 digits>      signed root documents, write-once
  devices/<version, 20 digits>    signed devices documents, write-once
  heads/<seq, 20 digits>          signed heads, write-once
```

An object's name is the Blake2b-256 of its stored bytes, so any client or the sink can verify it without a key. The sealed record and audit-row formats are ADR 0003's unchanged (the audit MAC chain stays, and is checked by unlocked clients; the signed head is what an untrusted server cannot forge). The slot table of ADR 0003 and ADR 0011 is the `slots` object, referenced by hash from the head; there is no mutable `slots` file.

**Heads and roots are write-once everywhere.** Nothing in this layout is ever overwritten: not a head, not a root, not a devices document. A commit is: write the new objects (idempotent, harmless if the commit fails), and only after every object the head references has been written, then create `heads/<n+1>` **only if it does not exist**, using each back end's own precondition (a root, `roots/<v+1>`, and a devices document are created the same way):

| Adapter | Create-if-absent |
| --- | --- |
| Local directory | write a temporary file, `fsync`, then `link(2)` it to the final name (fails if it exists), or `open` with `O_EXCL`; `fsync` the directory. Not on a network file system (ADR 0003) |
| S3-compatible | `PutObject` with `If-None-Match: *`; a second writer gets 412. AWS documents this for `PutObject`, `CopyObject` and `CompleteMultipartUpload`; support by other S3-compatible stores (MinIO, Ceph, R2) varies and is unconfirmed here |
| Google Cloud Storage | an upload with `ifGenerationMatch=0` |
| Server (several replicas) | the server calls the adapter beneath it; the replica that loses gets a conflict, which the client treats as below |

A probe at first use shows that a store accepts the precondition; it does not prove the operation is atomic, so the adapter documents the store it was tested against and refuses an unknown one unless told. Listing is strongly consistent on S3 (stated by AWS since 2020; the date is from memory).

**In direct-bucket mode the bucket must refuse overwrite.** A condition on create does not stop a writer who holds a write credential from overwriting an existing key. A direct-bucket deployment therefore requires **object lock** (retention in compliance or governance mode on `heads/`, `roots/` and `devices/`) or a **bucket policy that denies overwrite and delete** of those prefixes, and setup verifies it: it writes a probe object under a scratch prefix with the same policy, attempts to overwrite it, and refuses to create the workspace unless the overwrite is refused. What the probe can show for a given store is unconfirmed; where it cannot be shown, the store is not accepted. With a server, the server is the only writer and refuses overwrites itself. Overwritten or deleted objects are not a recovery path in this record: nothing is ever replaced, so clients never need to.

**The latest head is not the highest number.** Anyone who can write to the bucket can put garbage at `heads/n+1`, or at `heads/n+5`. The latest head is the highest head of the **valid chain from the client's last verified head**: the client reads `heads/n+1`, verifies it with the locked-client checks of decision 3 (framing and exact signature lines, the named root and devices versions and the listing of the committing device in them, previous hash, sequence, referenced objects matching their hashes) and, if unlocked, the sealed binding, then `n+2`, and so on. A head that is failing or void is **skipped by the gap rule** (decision 3, rule 7): the client does not stop at it, but looks for the next valid head, which must name the last valid head as predecessor, carry the next sequence number after the skipped ones and list them in a `skips` line, which the client checks against what it holds. A garbage head beyond a gap that no valid head's `skips` line accounts for is never reached. A head that fails verification does not count and does not move the client's state. A head that is valid but cannot be judged by this client, whether its manifest has an unknown key epoch or does not open, is not skippable; the client stops and says *re-unlock* (it may be a rotation or a head written by a device it has not met). A head or root with an absent referenced object is unavailable; the client waits and retries.

**Squatting.** A writer who is not a listed device can write only failing heads; they can squat sequence numbers, which the gap rule skips at the cost of one `skips` line, and they can only deny service. A listed device that is stolen writes void heads after its removal (decision 3, "Revoking a device"). In both cases the damage is detected by every client that verifies and is never a forgery, and nothing is overwritten. A client that holds a verified copy of an object that has been deleted from the store re-publishes it (`Put` is idempotent: the name is the hash). Where the bucket is versioned, deleted versions remain for inspection.

A conflict on a valid head (someone committed `n+1`) means the client fetches the new state, re-runs its `Update` function against it (ADR 0003's version-checked update) and retries, as `ports.ErrConflict` does today. **A client whose commit loses the create-if-absent race to a rotation head discards its plan and retries from scratch after re-unlocking**: the rotation changed the master key, the key epoch, every purpose key and every handle, so a plan built on the old state, and the objects written for it (harmless, unreferenced), cannot be carried over.

**Retention.** Heads, roots, devices documents and slots objects are **kept**: they are small, and they are what verifies the chain from genesis. Records and manifests that the newest head no longer references may be garbage-collected by `store gc` under the rules below; an older head whose manifest has been collected stays valid as a link of the chain.

**Liveness: deleting an object a valid head references must be recoverable.**

* `store gc` has a **grace period** (recommended 30 days, and never shorter than the head validity plus the longest expected offline time of a device). It never deletes an object that any head made within the grace period references, and never deletes an object younger than the grace period, as the store clock reports its creation.
* A commit writes its objects before its head (decision 4). An object that a commit has written and its head does not yet reference is younger than the grace period, so `gc` cannot take it; and `gc` re-reads the list of heads immediately before each deletion, so a head that appears meanwhile protects what it references. With the grace period much longer than a commit, `gc` and a commit cannot race.
* A client or a backup that holds an object with the hash a valid head references, and finds it absent from the store, **re-publishes** it (`Put` is idempotent: the name is the hash). A restore from a backup does the same for what the live store lacks.
* A deletion is a conditional request that the server checks itself (decision 7); devices do not delete objects in a direct-bucket deployment, only a separate `gc` credential does.

A rotation (ADR 0011) is one head commit; its old records and manifests become unreferenced and are collected after the grace period where the sink allows (not from backups, object versions or object lock, as ADR 0011 says). A head whose manifest's plaintext epoch differs from the epoch of the slots object it references is refused by the client (decision 3: a refusal, not a ground for a skip): a manifest from before a rotation cannot be committed under the slots of after it, nor the reverse.

### 5. Ports and adapters

New, in `spo/internal/ports`:

* `ObjectStore`: `Put(hash, bytes)`, `Get(hash)`, `Has`, `List(prefix)`. Adapters: directory, S3-compatible, remote server client.
* `HeadLog`: `Latest`, `Since(seq)`, `Append(head)` (create-if-absent; returns the existing head on conflict). There is no replace operation: heads are write-once.
* `BackupSink`: the same three, write side only for a sink that is not read-write.
* `AccessList`: enrolled device public keys and mailbox-only parties, read from the newest verified devices document, readable by the server (decision 7).
* `Mailbox`: `Deliver(recipient, envelope)`, `Fetch(recipient)`, `Ack`. It extends the existing `ports.Transport` envelope senders and receivers (`ports/party.go`) with store-and-forward.

The existing `ports.Store` and `ports.Vault` stay as they are. A new adapter `adapters/sealedstore` implements them over `ObjectStore` and `HeadLog` with the logic now in `sqlitestore` (verification, conflict, audit). Every use case runs unchanged, because it sees `Store`, `Vault` and the `SignerDirectory` of ADR 0010 and nothing else; whether the objects are in a directory, a bucket or behind a server is wiring. `Signer` entries for an own remote client are reached by the party envelope over `Transport` or `Mailbox`; a co-signer's by party fingerprint (decision 8); a use case cannot tell. Chain access, submission and hardware stay client-side.

### 6. The SQLite file

Decision: the layout is the canonical, portable format for backup, local deployment and the server's content once the sealed object store has had equal review depth to the SQLite file. Until then the SQLite file stays canonical for a solo operator and is converted to the layout for backup and server use. Afterwards it becomes a **local cache** of sealed objects of a remote or bucket store, rebuilt from the layout and never authoritative. Reasons: the file has seven reviews and its verification is what makes the opcert and KES counters trustworthy (ADR 0003); Verify time grows with the chain (about 200 ms at 50,000 audit rows), so a client caches the verified prefix; migrating the whole store at once gives up a reviewed component for a rewrite. Cost: while both exist, two stores have to keep their invariants; a differential test runs the same operation script over both.

### 7. Client authentication

Over Tailscale or tailcat the transport already authenticates a node. ADR 0005 binds the node key to a party identity in its `Hello`; that registry is sealed. The server therefore keeps an **access list**: the device keys and the mailbox-only parties of the newest verified devices document, exposed as `AccessList` (public keys and fingerprints only).

**Every request is authenticated, reads included.** Each request carries an HTTP Message Signature (RFC 9421, February 2024) by a device key: signed components `@method`, `@target-uri` and `content-digest` (RFC 9530, not read here), with the parameters `keyid` (the device fingerprint), `created`, `expires`, `alg` (`ed25519`) and `tag` (`spo-request-v1`), and is refused unless the key is in the list and the time check passes. The `tag` is the domain separation of this signature. A mailbox-only party signs the same way with its ADR 0005 party identity key, and the server lets it reach the mailbox endpoints for its own fingerprint and nothing else: no object, no head, no list. There is **no unauthenticated read path**. Backups are read from the sink with the sink's own access, never through the server, so a read path for them is not needed.

**Replay protection without server state.** A nonce that the server remembers needs state shared between replicas, which the stateless design (decision 1) does not have. Chosen instead: a **bounded time window**. The signed `created` must be within 60 seconds of the server's clock (either side) and `expires` at most 60 seconds after `created`; a request outside that is refused. **The real replay window** is longer than a minute when clocks differ: a device whose clock runs 60 seconds ahead produces `created` up to 60 seconds in the future with `expires` 60 seconds after that, so a captured request can be replayed for up to about 120 seconds of the server's time, and replicas whose clocks differ from each other add that difference. This needs the clocks of devices and replicas to agree (NTP; a device whose clock is wrong is refused with a message that says so). A per-device monotonic counter stored in the object store was considered and rejected: it makes every request, reads included, a conditional write to a shared object contended by all replicas, which gives up statelessness for a protection that the properties below already provide. The `nonce` parameter is therefore not used.

Inside the window a replay can repeat only what the request already did, because every operation is either idempotent or made safe by a precondition:

* **Idempotent:** reads return the same sealed bytes; `Put` of an object is keyed by the hash of its bytes; a mailbox delivery is keyed by the envelope's message id, which the recipient's replay log (ADR 0005) already refuses a second time; an acknowledgement.
* **Safe by a precondition:** a head append is create-if-absent for one sequence number with one fixed content, so a replay is a conflict and changes nothing; **a delete is conditional and checked by the server**: the request names the object and the head sequence number its decision was made at, and the server refuses it unless that is still the newest head, the grace period has passed and no head within it references the object (decision 4, Retention). A replayed delete after success finds nothing to delete and is a no-op; a replayed delete after a newer head is refused.

The remaining exposure is a repeated read by someone who captured the request inside the tunnel, who learns what the sealed response holds (sealed objects and structural data) and nothing that the capture did not already contain.

Enrolment of a device reuses ADR 0005's ceremony: fingerprints compared out of band, scope and roles per party; the new devices version that adds the key is signed by the `devices` role (decision 3; one FIDO2 touch by default, no root keys), and the enrolment carries the pin (decision 3). Enrolment of a mailbox-only party is the same ceremony and adds a `mailbox` line to the devices document only, so it cannot sign a head. What ADR 0005 does not provide and this record adds: a way for a server to learn enrolments without the registry.

### 8. Envelopes and the mailbox

An envelope is already sealed to the recipient with `age` and signed by the sender (ADR 0005), so a server may hold one without reading it. The mailbox is keyed by the recipient's party fingerprint, which the server sees. A signing demand for a key held by another operator is routed by the party fingerprint that ADR 0005's slot assignment records, through the mailbox or a direct transport; a co-signer cannot compute this workspace's blinded handles and the demand carries none. Blinded handles are used only among devices of one workspace. The ADR 0005 rules that a signer's refusals depend on private checks, and the cold-key rule (keyed on the most sensitive role ever recorded for the key, ADR 0010), are enforced at the clients, unchanged. A signer offline for a day receives the request when it connects; the request's expiry (ADR 0005) bounds that.

### 9. Backup and restore

A backup is a copy of `objects/`, `roots/`, `devices/` and `heads/` to a sink (a directory, an S3-compatible bucket; a `standard` workspace is local-only and may be backed up to a filesystem directory only, with the warning of decision 2), taken by listing the heads and copying everything reachable from the newest valid head, the heads being the last to be written so the copy is a valid prefix. It needs no further encryption because objects are sealed. The sink learns the metadata of decision 2 and that this is a backup of a workspace. A sink must not be given write access to the live store's bucket path; use its own prefix and, on S3, object lock or versioning against deletion. Object lock and versions keep old slot tables and ciphertext permanently, which is why ADR 0011 makes factor removal a master-key rotation. A backup keeps every root, devices document, head and slots object, and the records and manifests the newest head references; it does not rely on what the live store has garbage-collected.

Restore verifies without any credential, **against a pin the operator supplies**, a root version and its hash (taken from `store verify` output, from the print at the last root change or from a device enrolment record): every object's hash equals its name; the roots walk from version 1, whose hash is the workspace id, through every version to the newest, with each version signed by a threshold of the previous and of its own root keys, and the newest version is at or after the pinned one with the pinned hash at the pinned version; the devices documents walk from version 1 under the roots they name, each signed by the `devices` role of that root; the heads verify from the genesis head to the newest, each with exactly the expected signature lines by devices listed in the devices document it names and not void, any gap accounted for by a `skips` line, and the slots and devices hashes match. A backup whose newest head has expired is reported, not refused (decision 3, rule 4). A restore never lowers the operational-certificate or KES counters of a live workspace: for each, it takes the larger of the live and the backup value, or refuses and names the counter. What this does not check is what only an unlocked client can (decision 3): an operator who needs more unlocks and runs `store verify --deep`. It refuses a backup of another workspace id, and a head older than the destination's unless told with `--allow-older`. A restore without a pin is refused. **`--allow-older` is read-only inspection of an older head**: the result can be opened and verified, never written, and it is never a second way to fork the store; writing the content of a backup into the live workspace needs the takeover of decision 10, which extends the live chain. Existing SQLite backups import through `store convert`.

### 10. Local deployment from the artefact, and takeover

`spo -C <directory-or-s3-url>` opens the layout with the `sealedstore` adapter over the directory or bucket adapter and no server: the copy *is* the store. Single-writer rules are those of decision 4. **A backup copy is read-only.** Writing to it as if it were the live store would fork the store into two validly signed chains, each extending the same head.

**Takeover.** `heads/<seq>` is write-once, so there is no second branch to write on: the one way to put the content of a backup into the live workspace is a `takeover` head that **extends the live chain**. Its rules:

* **Where it sits.** Its sequence number is the **pinned live head's sequence plus one** and its previous-head hash is that pinned head's hash. The operator pins the live head (from `store verify`, another device or an enrolment record) and the root (decision 3, Pins); a takeover is refused without the pins. The destination must hold the heads of the live chain up to the pinned head; heads are small and self-verifying, so they are copied from any device or sink that has them. If the live chain's newest heads cannot be obtained at all, there is no takeover.
* **What it keeps.** It keeps the live head's slots object, devices document, key epoch and root version, and changes none of them. The takeover head references a new manifest whose records come from the backup **re-sealed under the live master key** at the live epoch. A takeover from a backup can therefore never bring back a removed factor or a revoked device: the slots of the live chain and the devices of the live devices document are the only ones the head can name, and anything in the backup that was sealed under an older epoch is re-sealed or dropped. **A takeover never lowers the operational-certificate or KES counters:** for each counter it takes the larger of the live and the backup value, or refuses and names the counter, because a lowered counter would let a block producer sign a certificate or a KES period that the chain has already seen.
* **Who signs.** A device listed in the live chain's current devices document, after a **fresh unlock** of the live chain's epoch (a fresh presentation of a factor the workspace policy accepts, [ADR 0011](./0011-key-custody-and-unlock.md)). A device that the current devices document does not list, a revoked device included, cannot sign it. The head carries `restored-from <head hash>`, the head of the backup the content came from, as a record of what was done.
* **If the live epoch cannot be unlocked.** If the operator cannot unlock the live chain's epoch because its factors are lost, that is the recovery path of ADR 0011 (the recovery slot or composite, then a rotation), not a takeover; a takeover needs the live master key to re-seal.
* **Who accepts it.** Every client that has the pinned head sees the takeover as an ordinary extension of its chain: it passes the locked-client checks and the sealed binding. No client is asked to accept a fork.

Two different heads at one sequence number that both pass the locked-client checks are a fatal alarm (decision 3). `--allow-older` (decision 9) never produces a head.

### 11. Kubernetes

Replicas are stateless: a `Deployment` behind a `Service`, with the bucket as the only state (`StatefulSet` and a persistent volume are not needed). The head conflict of decision 4 is the only contended write. A disruption budget and a rolling update need no coordination. The pod holds no unlock factor and no Vault token for the workspace's transit key; its service account can reach the bucket and nothing in Vault or KMS (checked in review of the manifests, which are not in this repository yet). Scope: Tailscale only for the first version; an ingress later requires TLS 1.3 and the request signatures of decision 7.

### 12. Unattended automation under R4, and the client agent

Impossible by design: anything that needs a vault-held key, a decrypted object or an unlock factor with no client present, such as a scheduled KES rotation or opcert renewal run by a server job. Hardware-held keys cannot sign without the device either. Supported pattern: a **client agent** on an operator-controlled machine, unlocked by the operator (FIDO2 touch, passphrase, or Vault identity of that client), that holds unlocked material in guarded memory and serves the scheduled jobs. Its rules: an idle timeout and a hard cap of about 12 hours; it locks on suspend; it listens on a Unix socket and checks the peer credentials; it disables core dumps and ptrace; it never exports the master key; and it keeps no TPM-sealed state unless that is a slot kind counted by the policy of ADR 0011.

**Cold-role keys are not held by an unlocked agent.** A "fresh touch" required before using a cold key is only a user-interface gate if the key is already decryptable in the agent's memory, so that is not the design. Vault-held cold-role keys (pool cold and committee cold, and any role the operator marks) are sealed under a **per-record sub-key** in addition to the record-wrapping key, derived by HKDF-SHA-256 from a fresh factor presentation per signing session, with a per-use salt that is rotated on each use; the derivation, the factor for each policy, and the recovery wrap are in [ADR 0011](./0011-key-custody-and-unlock.md) decision 6 and are not repeated here. The agent can open the master key and every record that is not cold-role, but cannot decrypt a cold-role key without that presentation. The decrypted key is held for the signing session only and is zeroised when the signing completes. **The agent caches only what the policy allows**: the master key and derived keys, hot-role keys (KES, VRF and others the operator permits the agent to hold for scheduled jobs), and non-secret records; never a cold-role key beyond a session. This changes the sealed record format of cold-role records and so belongs to the group of changes that need a further review (decision 13); until then no agent holds a cold-role key at all. Cold-key, slot and device operations always need the fresh presentation. The server may *remind* (an envelope that says "KES period ends in 3 days") because that needs no secret. Hot keys on a block producer are delivered to it under ADR 0011's node-delivery exception, not decrypted by the server.

3. SQLite demoted to cache once the criterion of decision 6 is met.
4. Kubernetes manifests, a chart, and the unattended agent with the cold-role sub-keys.

Out of scope: threshold or multi-operator custody, a Merkle transparency log, end-to-end search over sealed data, multi-writer offline merge, any change to chain access ([ADR 0006](./0006-chain-access-providers.md)).

## Consequences

* The server holds only ciphertext, the structural slots objects, the root and devices documents, and handles; it is replaceable; a lost server loses no data when a bucket survives.
* Chain and object verification no longer need the passphrase, which makes a backup checkable by a third party who holds a pinned head. What the sealed manifest binds is checked only by an unlocked client.
* Every commit costs one device signature (more if `threshold heads` is raised), and a client must refresh the head before it expires. A bucket gets many small objects; `store gc` and prefix sharding (`<aa>/`) are needed. Heads, roots and the structural objects are never collected.
* The access list gives the server the set of device keys, the root keys, the keys of the devices role, the mailbox-only party fingerprints and commit timing.
* Enrolling or removing a device needs a new devices document, signed by the operator's FIDO2 credentials (one touch by default), not the root keys; losing the root threshold stops changes of the root keys and the `devices` role, and is unrecoverable except by re-genesis into a new workspace id.
* Revoking a device is a devices document with a `void-after` sequence, a head that skips the thief's heads, and a rotation: it costs one devices-role signature and a re-encryption of the whole workspace, and binds only clients that have learned the new document.
* Two stores coexist for several stages; the cost is the differential test.
* A split-view attack by a malicious server on two clients is detected late and only by comparison. A backup copy cannot be used as a working store; its content reaches the live workspace only by a takeover that extends the live chain.
* Write access to the bucket allows denial of service by squatting heads; clients detect it and skip failing heads by the gap rule, and nothing is overwritten. A direct-bucket deployment requires object lock or a deny-overwrite policy, verified at setup. A stolen device key cannot change the root or the devices document, add a device or rotate, and after its removal nothing it commits past `void-after` is accepted; until then it can commit heads that an unlocked client cannot open.
* Server and bucket deployments need the `hardware` policy, root keys that are FIDO2 or hardware-wallet keys (a software root key is refused), and hardware-bound or TPM-bound device keys; a `standard` workspace stays local.

## Open questions

* Whether S3-compatible stores other than AWS S3 (which documents `If-None-Match` on `PutObject`) support it, and object lock or deny-overwrite policies, with what guarantees.
* Whether `golang.org/x/mod/sumdb/note` is adopted for the signed-note framing or the format is implemented directly: unconfirmed; its verifier ignores unknown signature lines, so the exact-lines rule needs a wrapper either way. RFC 9530 (`content-digest`) was not read. The 60-second window of decision 7 is a proposal.
* Device key. Recommended: a separate key per workspace cross-signed by the party identity, sealed at rest under a TPM-bound or FIDO2 factor, with the Argon2id passphrase fallback only under `standard` (decision 3); needs the owner's decision. Whether a FIDO2 authenticator or TPM can hold a non-exportable Ed25519 head-signing key: unconfirmed.
* Root keys. Recommended: 1 of 2 or 2 of 3, FIDO2 authenticators (SSHSIG) or hardware-wallet keys (CIP-8), kept apart; root expiry one year, head validity 14 days with a cap of 90; needs the owner's decision. Unconfirmed: the signature type byte values; that `golang.org/x/crypto/ssh` verifies security-key signatures and has no SSHSIG support; the `ssh-keygen` options for the application string and `verify-required`; which authenticators support Ed25519 for `sk-ssh-ed25519`; the CIP-8 header form and arbitrary-payload signing on Ledger and Trezor.
* The `devices` role. Recommended: the operator's FIDO2 credentials with threshold 1 by default, separate from the root keys; whether a lost devices-role credential should be replaceable without a root version (it cannot be, as designed); needs the owner's decision.
* Discarding heads committed by a stolen device key: designed in decision 3 (`void-after`, rules 6 and 7). Open: how an operator finds the last legitimate head when no other device is enrolled (the proposal is the operator's own record of the last commit); needs the owner's decision.
* The grace period of `store gc` (30 days proposed), the head validity (14 days proposed), the cap on expiry (90 days proposed), the half-validity refresh rule and the freshness sources of rule 4 are proposals.
* Optional cosigning of heads by independent witnesses (C2SP tlog-witness, unconfirmed) as a later defence against a split view.
* TUF: the version (1.0.37) and the section numbers of decision 3 were read from the published specification; the step numbers inside sections 5.3 to 5.6 for the rollback and freeze checks are to be read against the text before the format is frozen.
* SQLite store. Recommended: it stays canonical until the sealed object store has had equal review depth, then becomes a local cache; needs the owner's decision.
* Client agent. Recommended: the rules of decision 12, with cold-role sub-keys; needs the owner's decision.
* Kubernetes scope. Recommended: Tailscale only for the first version; an ingress later requires TLS 1.3 and request signatures; needs the owner's decision.
* Plaintext root and devices documents let an observer who sees two workspaces' access lists link an operator's machines across them by the party fingerprint, which is the same in every workspace. Whether the fingerprint is replaced in the root by a per-workspace value is open.
* Whether the sink may be a read-write live store of another workspace (a backup of a backup).
* The node-delivery exception of ADR 0011 interacts with unattended KES rotation.

# ADR 0009: The TUI is a second driver of the same command tree

Status: accepted, 2026-11-16. Refines [ADR 0002](./0002-architecture-and-dependencies.md) and [ADR 0008](./0008-capability-typed-ports.md). Closes concerns U1 and U2 by design (decision D9).

## Context

The CLI adapter holds about a hundred commands. Each one states what it needs (`Env`, `Cap`, `Require`, `withEnv`), refuses before it asks for anything, confirms with its own text and default, writes its own audit record, and talks to the operator only through three ports of `cli.Deps`: `Terminal` (`ReadSecret`, `ReadLine`), `Out` and `Err`.

A TUI that offered "workflows" would restate every one of them: which questions to ask, in which order, with which default. Each restatement is a place where a refusal, a confirmation or an audit record can be missed (concern U1). A screen that redraws, keeps scrollback and may be recorded is also a place where a secret can be left behind (concern U2).

## Decision

### A second driver of the same tree

The TUI walks the cobra tree the CLI builds (`cli.NewRoot(deps)`) and presents it as menus (groups, then commands). For the chosen command it renders a form generated from the command's metadata, then runs the command's own `RunE` in-process, with `Deps` whose `Terminal` and `Out` the TUI implements. Every refusal, needs check, confirmation default and audit record is the command's. A command added to the CLI appears in the TUI with no TUI code.

### Wiring: the TUI imports no other adapter

`cmd/spo` builds the root command and gives the TUI a factory, `func(terminal, out, err) (*cobra.Command, error)`. The TUI calls it once to learn the tree and once per command it runs, so every run has its own state, and a command's progress lines reach the TUI and never the real terminal. `adapters/tui` imports cobra and its own library, not `adapters/cli`; the arch test fails otherwise, and fails when anything but `cmd/` imports `adapters/tui`.

`spo tui` starts it. Bare `spo` is unchanged. The global flags (`-C DIR`, `--upstream-layout`, `--accept-rollback`) are fixed for the session and put before every command's arguments.

### Forms from metadata

* Positional arguments come from the `Use` line: `<name>` required, `[name]` optional, `...` repeatable. Bracketed flag groups, `(a | b)` alternatives and the value placeholder after a flag are not positionals.
* Flags come from their pflag definitions: bool is a switch, string and number a text field with the default as a hint, `stringArray` and `stringSlice` a list. The usage text is shown under the focused field.
* Only what the operator changed is passed, as `--name=value`, and the command line the form stands for is shown under it. The command's own defaults apply to the rest.
* The form runs the command through cobra (`SetArgs`, `ExecuteContext`), so argument validation, required flags and flag parsing are cobra's, not a copy.

### Hints: names, paths and flag groups

A command tells an interactive driver what an argument or flag holds through annotations, never through code the driver imports. The vocabulary is in `platform/uihint`:

* `Names(class)` marks a value that names a workspace object. The classes are wallet, pool, stake, policy, asset, drep, committee-cold, committee-hot, voting-key, calidus and party.
* `File(exts...)`, `NewFile(exts...)` and `Dir()` mark a path: an existing file, a file to write, a directory, with an optional extension filter.
* Cobra's own flag groups (`MarkFlagsMutuallyExclusive`, `MarkFlagsRequiredTogether`, `MarkFlagsOneRequired`) are read from the annotations cobra stores (`uihint.Groups`; a test fails if a cobra upgrade renames them). A command that documents an exclusion declares it to cobra, so the form can show it before the run and the CLI enforces it the same way.

A flag carries its hint as a pflag annotation; a positional argument carries it as a command annotation keyed by its label in the usage line. Bare upper-case words in a usage line (`FILE`, `POOL`, `FILE|DIR...`) are positionals, as `<name>` is. The hints are registered from one table (`cli/uihints_table.go`, keyed by command path and label or flag) by `cli.MarkForUI`, so a command file carries none; a test (`TestUIHintTableMatchesTheTree`) fails when an entry names an argument or flag that does not exist.

The TUI asks for candidates through one function the composition root gives it (`tui.NameLister`). It returns names by class and nothing else; it is the CLI's own listing of the store (`cli.WorkspaceNames`), so names come from the same records the commands read, never their contents. Called without a passphrase it opens nothing and reports that the workspace is sealed, and completion is off until the operator asks (`ctrl+n`) and types the passphrase once. The same hints feed cobra's shell completion (`cli.AttachCompletion`): there, with no way to prompt, names are offered for the upstream layout only.

The file picker is in the TUI and lists directory entries only (names, kinds, link targets). It follows a symbolic link only after showing its target and a second confirmation.

### Secrets

* Passphrases and confirmations are the command's own prompts. A `ReadSecret` becomes a masked modal showing the command's text verbatim; a `ReadLine` (every `[y/N]`) becomes a text modal with the same text. Nothing typed into a masked field is drawn or logged.
* A flag that names a descriptor carrying a secret in (`--password-fd`, `--mnemonic-in-fd`, `--token-fd`, `--message-passphrase-fd`, `--protection-key-fd`, `--new-passphrase-fd`, `--recovery-key-in-fd`) is annotated in `cli` (`uihint.SecretFD`). The form shows it as a masked field. The value goes into a private pipe made for the run and its descriptor number is passed as the flag; the pipe is closed when the command returns. Leaving it empty leaves the command's own prompt. A descriptor number is never a form field.
* A flag that names a descriptor the command writes a secret to (`--recovery-key-fd`) is not offered. Without it the command shows the secret itself, once, and the command is annotated `uihint.SensitiveOutput`.
* Typed secrets live in a slice of fixed capacity, as in the CLI's terminal, and move into `platform/secret` buffers (which wipe the slice) when handed on. The form wipes its secret fields when the command starts, when the operator leaves the form and when the program ends.
* The output of a command marked sensitive is zeroed when the operator leaves it. All output is zeroed when the run is dropped.
* The TUI runs on the alternate screen, enables neither mouse reporting nor bubbletea's debug log, and restores the terminal on exit, a panic included.

### One command at a time, cancelled by its context

A command runs in its own goroutine under a context. Its prompts are messages to the program; the operator's answer goes back on a channel. Esc or Ctrl-C at a prompt, or while it runs, cancels the context: the prompt returns the context's error and the command leaves what the same cancel leaves in the CLI. A second Ctrl-C quits.

### Untrusted text

Commands already quote what a peer or the chain supplied. The TUI also cleans everything it draws (output, prompts, menu text, field values): escape sequences (CSI, OSC, DCS and the other forms, including the C1 forms), carriage returns, other control characters, bidirectional controls and invisible format characters. Output cannot move the cursor, restyle the screen or reorder what the operator reads.

### Reachability is checked

A test walks the CLI's command tree independently of the TUI and fails when a runnable, non-hidden command is missing from the TUI's menu or the menu has one the tree lacks (concern U1). Another fails when a `-fd` flag is not classified as a secret in or a secret out, so a new descriptor flag cannot reach the TUI as a number.

## Alternatives considered

1. **Hand-written screens per workflow.** The best screens, and the worst for U1: every workflow exists twice. Rejected.
2. **A TUI over a new `UI` port, with the CLI as a second implementation.** The cleanest on paper. The CLI's commands already are that port: they read their input through `Terminal` and flags and write to `Out`. Extracting a port now would move code without removing duplication. Rejected.
3. **Run the binary as a subprocess for each command and drive a pty.** Reuses the CLI exactly, but puts passphrases on a pty, loses structured cancellation and cannot show a modal over the command's own prompt. Rejected.
4. **`cli` imports a TUI package, or the TUI imports `cli`.** Two driving adapters would depend on each other, which ADR 0002 forbids, and the TUI could call unexported helpers. Rejected for the factory above.
5. **A generic form generator library.** Forms that edit a Go struct need a struct per command. Rejected: the metadata is cobra's.
6. **tview or tcell directly.** Larger, and a widget toolkit where a small model-update-view loop is enough. tview also stores typed text in widget state this adapter cannot wipe.
7. **bubbletea v1.** Tried first and rejected: v1.3.10 queries the terminal's background colour from a package `init`, so every `spo` invocation on a terminal, not only `spo tui`, sent an escape query and could block on standard input (seen hanging under `script(1)`). The v2 line (`charm.land/bubbletea/v2` v2.1.1, `charm.land/lipgloss/v2` v2.1.1) has no such `init`; `spo version` emits no query. `bubbles` is not used: the input and scroll code is our own.

## Consequences

* The TUI is as small as its form generator and its modal plumbing. It cannot disagree with the CLI about what a command does.
* Names the workspace holds are completed from a read-only listing through a function `cmd/` supplies. For a sealed workspace that costs one passphrase entry per session (until a command is run), asked only on request; the names are kept in memory only.
* The TUI is tested on a real pseudo-terminal (`cmd/spo/tui_pty_test.go`); a build environment without one skips those tests.
* A command that prints a lot is read in a scrolling pane, not paged by the command.
* The CLI's `Err` stream and prompts appear in the same pane as `Out`, in order. Tests compare the `Out` stream, which is what the CLI prints on stdout.
* The library adds a set of pure Go dependencies (bubbletea v2, lipgloss v2, go-runewidth and their helpers), about 2.3 MB in the static binary. The arch test confines them to `adapters/tui`.
* Mnemonics are never shown by any command today, so the only secret the TUI can show is the recovery key a command displays once. If an audited display or export command is added that shows a key, it must carry `uihint.SensitiveOutput`.

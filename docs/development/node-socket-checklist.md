# Node socket: what only a real node can confirm

Online mode reads the chain through a cardano-node socket (`spo/internal/adapters/native/n2c`, wired in `spo/cmd/spo/online.go`, [ADR 0006](../explanation/adr/0006-chain-access-providers.md)). The adapter was built from the gouroboros library's documentation and the ledger CDDL, and is tested against an in-process fake node (`n2c/n2ctest`) that serves the server side of the same library on a UNIX socket. The fake answers with bytes the tests give it: hand-written from the CDDL, or encoded by the library, which proves little. **Only one reply was ever sent by a real node**: `GetDRepState`, copied from the gouroboros tests, which say it came from cardano-cli 11.0.0.0 on a devnet. Per query, `spo/internal/adapters/native/n2c/README.md` lists which bytes are which.

**Nothing here has run against a cardano-node.** Each item below is an assumption to confirm on the preview network, with throw-away keys and a preview node that is synced and reachable through its socket. Do not run it on mainnet, and do not sign for a pool that matters in online mode until it has been done. Record the result next to the item together with the cardano-node and cardano-cli versions and the node-to-client version the handshake negotiated; where reality differs, fix `n2c` with the node's bytes as a new test fixture (capture them, for example, by logging the reply at the adapter's `do` call in a scratch build), or write the difference into the README of `n2c` as a known difference.

Setup, once: `spo init --network preview --mode online`, `spo provider set node /path/to/node.socket`, then `spo capabilities`, which must list the node socket as the provider of `tip`, `sync-check`, `utxo`, `opcert-counter` and the governance readers. For the cross-checks add Koios (`spo provider set koios`, then `spo provider order node koios`). The right-hand column says what a difference most likely means; "Unknown" is the adapter's answer to a reply it cannot decode, and it never becomes a wrong value.

| # | Check and what to expect | How | A difference means |
| --- | --- | --- | --- |
| 1 | **Handshake.** `spo address ADDR` for any preview address connects and prints `[node socket preview]`. The adapter offers the node-to-client versions of gouroboros v0.219.0 with network magic 2. | Run it against the node; also with the wrong network (a mainnet node socket in a preview workspace) and expect `handshake with the node failed (is the network magic 2 right?)`. | If a preview node refuses: the library's version range does not meet the node's (the library is too old or too new for this cardano-node), or the socket is not a node-to-client socket. Record the node version and the negotiated version. |
| 2 | **Address forms.** A socket path, `unix:/path`, and a TCP forward on loopback (`socat TCP-LISTEN:3001,bind=127.0.0.1,fork UNIX-CONNECT:/path/node.socket`, or `ssh -L`) give the same answer. A `tcp://` address on a non-loopback host prints the plain-TCP warning exactly once per command. | Run `spo address` with each form; bind socat to a LAN address once for the warning. | A form that fails is a parsing difference in `parseAddress`. A warning printed twice or not at all is in `cmd/spo/online.go`. |
| 3 | **Tip and epoch.** `spo pool opcert check --opcert-file F` prints `KES period now N`; N equals the slot of `cardano-cli query tip` divided by 129600 (preview), within one block's age. | Run both within a second of each other; use a certificate file with the current period. | `GetChainPoint` or `GetEpochNo` is decoded wrongly, or the era history (item 5) converts slots wrongly. |
| 4 | **Genesis from the node.** Without `--shelley-genesis` (and without a bundled genesis) the command takes the KES period length, the evolutions and the system start from the node. The output of `pool opcert check` is identical with and without `--shelley-genesis` set to preview's `shelley-genesis.json` (`slotsPerKESPeriod` 129600, `maxKESEvolutions` 62, `epochLength` 86400, `slotLength` 1). | Run the same check twice. | `GetGenesisConfig` is decoded wrongly (its layout is the library's), or the era-history units of item 5 are wrong. With a bundled genesis the node's values are never used: compare them anyway. |
| 5 | **Era-history units.** The adapter reads the slot length as milliseconds and the era bounds as picoseconds, and the tests encode them that way themselves. A synced preview node is reported synced (`spo address` does not refuse); a node whose tip is more than two minutes old is refused with `not synced`. | Run `spo address` on the synced node. Then run it on a node that has been stopped for ten minutes and restarted (or a fresh node still catching up; `cardano-cli query tip` shows `syncProgress` below 100). With `cardano-cli query slot-number 2026-01-01T00:00:00Z` (any date after the era's start) compare the slot with the one `spo` derives (it does not print it; use the KES period of item 3 for a date a known number of periods away). | A healthy node refused as unsynced, or a stale one accepted, means the picosecond or millisecond reading of the era summary is wrong (a factor of 1000 is the likely error), or `GetSystemStart` is read as the wrong year or day. Fix `EraHistory` and add the node's bytes as the fixture. |
| 6 | **Sync gate.** On an unsynced node, `spo address`, `spo wallet send`, `spo pool opcert check` and every command that reads UTxOs, accounts, pools, DReps or governance state refuse with `not synced`, before building anything; the tip, the parameters and the submission are not gated. | Item 5's stale node: run `wallet send ... --yes` with a throw-away wallet and expect the refusal, no prompt and nothing submitted. | A command that goes on against an unsynced node reads a stale ledger: report the command; its reads must pass the gate in `online.go`. |
| 7 | **Protocol parameters (Conway).** `wallet send` computes a fee equal to `cardano-cli conway transaction calculate-min-fee` for the same body with `cardano-cli conway query protocol-parameters`. The node accepts the transaction. The fields the commands use (`txFeePerByte` 44, `txFeeFixed` 155381, `utxoCostPerByte` 4310, the deposits, `maxTxSize`, `minFeeRefScriptCostPerByte`) match the node's. | Build a send with `--yes` on a funded throw-away wallet, then compute the fee with cardano-cli on the same transaction (the fee is in the summary `wallet send` prints; `--yes` still prints it after signing). | A wrong or missing field means the library's Conway parameter structure differs from the node's (new fields appear in each hard fork). `ErrUnsupportedEra` means the node is not in Conway. |
| 8 | **UTxOs.** `spo address ADDR` lists the same outputs as `cardano-cli query utxo --address ADDR`: transaction id, index, lovelace, native assets with their names, and the datum hash, inline datum and reference script flags. Use an address with a multi-asset output, one with a datum hash, one with an inline datum and a script address with a reference script. | Compare the two listings; the adapter sorts by id then index. | A difference in assets or flags is a decoding difference of the Babbage-and-later map form of an output. An error naming a decode failure means the reply is shaped differently than the hand-written bytes assumed. An address with no outputs must print none, not an error. |
| 9 | **Submission and rejection.** `wallet send` is accepted: `Submitted transaction ID through node socket preview`, and ID equals `cardano-cli conway transaction txid`. Submitting the same transaction again, or one that spends a spent input, is refused with a reason from the node and `spo` does not say it was submitted. | Send, then re-submit the same signed transaction through a second `offline execute` or by repeating the build with a stale UTxO. | The era id sent with the transaction comes from `GetCurrentEra`; a rejection naming an era is a mismatch of that index. A rejection printed as hex only means `RejectedError` should decode more of the node's failure; record the bytes. A timeout after sending is `outcome unknown`: check with `cardano-cli query utxo` before retrying. |
| 10 | **Reward account.** `spo stake status NAME` for a registered, delegated stake address with rewards and a DRep delegation shows the rewards, the pool, the vote delegation and the deposit equal to `cardano-cli conway query stake-address-info`. An unregistered address is `not registered`, never `unknown`. | Compare for a registered address, one with no delegation, and one never registered. | `unknown` for a registered address means a query the node's negotiated version lacks (`GetStakeDelegDeposits`, `GetFilteredVoteDelegatees`, `GetProposals`) or a decoding difference; the deposit a refund rests on is then unstated and `stake deregister` refuses. A deposit or balance that differs is a wrong field. |
| 11 | **Pool state.** `spo pool status POOL` for a registered pool shows pledge, cost, margin, reward address, owners, relays and metadata equal to `cardano-cli conway query pool-params`; for a retiring pool `retiring` with the epoch; for an unregistered id `not registered`. | Compare for a registered pool, a retiring one (register and retire a throw-away pool on preview) and a random id. | A swapped field is the layout of the pool-params record; `unknown` for everything is the `GetPoolState` reply shape (its result is four maps). A retired pool shown as registered is the future-pool-params map read in place of the current one. |
| 12 | **The opcert counter, against the node's own tool.** `spo pool opcert counter POOL-ID` for a pool that has made blocks shows the number `cardano-cli conway query kes-period-info --op-cert-file F` calls the counter in the chain state; for a pool that never made a block, `none: the pool has made no block yet`. `pool opcert check --next` accepts a certificate with that number plus one. | Use a preview pool with blocks and a certificate file of its current opcert, and a pool with no blocks. | `unknown` with `not the layout`: the Praos `DebugChainDepState` reply differs from the library's documentation (a pre-Babbage layout, or an extra wrapper). A number that differs means the adapter reads the wrong map (the counters of another structure). An unknown pool is `none` only if the node's map has no entry: confirm a pool with blocks never shows `none`. |
| 13 | **The opcert counter, against Koios.** With `[provider] order = "node,koios"`, `pool opcert counter POOL-ID` and `pool opcert check` show `node socket preview and koios preview` and the same number. Right after the pool made a block with a newer certificate Koios may be one behind: the command refuses with `the two sources differ by one: the indexer may lag the node by a block; retry in a few minutes` (not overridable), and succeeds when the numbers are equal; a larger difference refuses with `the providers disagree`. The rule is that only equal readings agree (the ledger accepts n when m <= n <= m+1, so a reading one ahead could produce m+2); record how long a lag lasts in practice. With one provider `pool opcert issue` needs `--single-source`. | Compare for several pools over a day; watch one pool across a certificate rotation. | A pool where the two settle on different numbers for hours: the node's counter and the last block's counter mean different things after all (for example the node keeps counters of blocks that were later rolled back, or prunes entries). Then the rule must change; `pool opcert issue` would refuse where it should not, or accept where it should not. Also check that after `--single-source` runs the audit log holds a `single-source-read` record (`spo store verify`, or `.spo-workspace-audit.json` for an upstream-layout directory), and that a node and Koios on one host are refused unless `[provider] same_host_ok = true`. |
| 14 | **Pool info for import.** `spo pool import NAME POOL-ID` needs `pool-info` (the node) and `pool-updates` (the node cannot say when a pool last updated, so Koios must be configured and named in the order). The registration, owners, relays and the opcert counter it takes from the node equal Koios's `pool_info` for the same pool. | Compare with Koios, and with `cardano-cli query pool-params`; without Koios in the order the command must refuse before any prompt naming `pool-updates`. | A relay of a type the reader does not know (IPv6, SRV) is dropped or garbled; record the pool. |
| 15 | **DRep state.** `spo drep status DREP-ID` shows deposit, expiry epoch, anchor and delegated stake equal to `cardano-cli conway query drep-state --drep-key-hash H` and `query drep-stake-distribution`. This is the one reply the tests have from a real node, for the state; the stake distribution reply is hand-written. | Compare for a registered DRep with stake, one without, and an unregistered id (`not registered`). | A mismatch in the stake is the `GetDRepStakeDistr` shape (hand-written). A mismatch in the state means the captured bytes were from a devnet with another layout than preview's node. |
| 16 | **Committee members state: may come back Unknown.** The library decodes `GetCommitteeMembersState` as a bare structure where the other queries are decoded from the one-element array a node wraps results in. `spo committee status` for a hot or cold key of a member shows the status, the expiry and the hot key equal to `cardano-cli conway query committee-state`. If the node wraps the reply, the read is `unknown` (a test pins that) and no committee check can be made. | Run it for a member with a hot key authorised, a member with none, and a resigned one. | `unknown` for all: the node wraps this reply. Fix by unwrapping in `gov.go` and recording the bytes. A wrong status with a value is worse than unknown: report it at once. |
| 17 | **Constitution: may come back Unknown.** Same question for `GetConstitution`. A treasury withdrawal or parameter change reads the constitution's guardrails script hash; `spo action create treasury-withdrawal ...` or `parameter-change ...` must show the anchor URL, the anchor hash and the script hash equal to `cardano-cli conway query constitution`. | Run an `action create` that needs the constitution on preview, which has a guardrails script. | `unknown`: as item 16. A script hash shown where the constitution has none, or none where it has one, is a decoding difference of the optional script field. |
| 18 | **Ratify state and the previous action ids: may come back Unknown, and the order is recalled, not checked.** `GetRatifyState` is decoded by the library as a bare structure. The previous-action-id layout (four optional ids in the order parameter update, hard fork, committee, constitution) is from the ledger source, not checked. `spo action create parameter-change|hard-fork|update-committee|new-constitution` must propose against the previous id that `cardano-cli conway query gov-state` prints under `prevGovActionIds` for that purpose. | Read the four ids with cardano-cli, then run each `action create` and compare the previous id it records. Use a preview with at least one enacted action of two purposes so that two ids are non-null and a swap is visible. | `unknown`: the wrapper, as 16. A previous id that is another purpose's: the four ids are in another order than recalled; the ledger would reject the proposal as `InvalidPrevGovActionId` at submission, with the deposit still held in the transaction. A null where cardano-cli shows an id is a misread of the optional id. |
| 19 | **Governance actions.** `spo vote create` (for DRep, committee hot key or pool) lists the open actions with the same ids, kinds, deposits, return addresses, anchors and the expiry epoch as `cardano-cli conway query gov-state`; `spo vote tally` shows the votes the node holds. A parameter change shows the parameter names and the security group (the names come from the key table of the library's `ConwayProtocolParameterUpdate` and CIP-1694). | Compare on preview with several open actions of different kinds. | A key without a name leaves the security group `unknown`: add the missing key to the table. A wrong kind or deposit is the proposal-procedure layout. |
| 20 | **Stake distributions for the tally.** `spo vote tally` percentages computed from the DRep distribution, the SPO distribution, the default pool votes and the committee equal those of the governance tools for the same action (cardano-cli's `query drep-stake-distribution`, `query spo-stake-distribution` and the ledger's own ratification). | Compare for one action each of a DRep-voted, an SPO-voted and a committee-voted kind. | A difference in the DRep percentage is the treatment of `AlwaysAbstain` and `AlwaysNoConfidence` and of expired DReps; this is the least verified of the governance reads. |
| 21 | **Unreachable and silent nodes.** With the node stopped, `spo address ADDR` fails at once naming the socket and the reason; with a socket that accepts and never answers (for example `nc -l -U /tmp/x.sock`) it fails after `timeout_seconds` and no longer. The reading is `unknown`, never `none`: `pool opcert counter` never prints `none: the pool has made no block yet` in this case. | Both, with `timeout_seconds = 2`. | A hang is a missing deadline on a protocol step; record which command. |
| 22 | **The connection is per command and is closed.** Each command makes one connection when it first reads the chain and none when it reads nothing; after the command returns the node shows no `spo` connection (`ss -xp`, or the node's `cardano-node` log of N2C clients). | Run `spo capabilities` (no connection), `spo address` (one), then look at the node's socket connections. | A leaked connection holds one of the node's N2C slots; the node limits them. |
| 23 | **Cross-check of the reward account and the pool.** With the node and Koios both named in the order, `spo stake deregister` for an address with no rewards goes on with both sources named in the summary; for an address Koios reports with rewards the node does not (a stale Koios) it refuses naming both answers. | Run `stake deregister` on a throw-away registered address; compare the summary with `stake status` under each provider alone. | A refusal where both are right: a field the two providers state differently (the deposit, the vote delegation text). Record which and normalise it in `compareAccounts`. |
| 24 | **Another era.** If the preview node is in an era after Conway, parameters give `ErrUnsupportedEra` and submission uses the node's era index. Today the node is Conway; run this when a hard fork is scheduled. | Watch a hard fork on preview. | A hard fork that the adapter cannot follow stops every chain command in online mode; the fix is a new decoder in `chain.go`. |
| 25 | **Transaction status and `--wait`.** Submit a small payment on preview with `spo wallet send ... --wait --wait-confirmations 2` and, in another terminal, `spo tx status TXID` before and after the block. After inclusion the node answers `in a block, depth not stated` (an unspent output of the transaction); in the pool of pending transactions it may answer `in the mempool` (local tx monitor). For a bare id it must never print `has not seen it`. `--wait` with the node and a web provider ends `confirmed` once the web provider states 2 confirmations; the node alone states no depth, so `--wait-confirmations 2` on the node alone times out (exit 20) by design. `expired` (exit 21) needs a transaction whose validity bound has passed while every provider says not seen: the node says so only from an input of the transaction that is still unspent. | Compare `tx status` with `cardano-cli conway query tx-mempool tx-exists TXID` and `query utxo --tx-in TXID#0`. Compare Koios' `num_confirmations` and Blockfrost's depth for the same transaction with the block heights (does Koios count the block that holds it?). | `unknown` for a transaction that is in a block: the by-reference UTxO reply shape, or an output index that was not probed (more than 8 outputs and a bare id). `in the mempool` after inclusion: the tx-monitor snapshot is stale. `has not seen it` for an included transaction is a misread and a bug: report it at once, since it could license a rebuild. |

## What the wiring does that no test with a fake can show

* The adapter negotiates a node-to-client version with the node (item 1). The fake negotiates with the same library, so a version the library offers and no real node supports is invisible to the tests.
* The node's replies carry era-dependent encodings (items 7, 8, 11, 12): the fake serves whichever the test wrote.
* Concurrency: the adapter runs one operation at a time on one connection. A real node may answer slowly under load; the per-operation timeout (default 30 seconds) closes the connection when it fires (the protocol state is then unknown) and every later read of the command is `unknown`. Check that a slow answer (a busy mainnet-sized preview node) is not mistaken for a dead one: raise `timeout_seconds` before reading anything into a timeout.

## What is not in online mode

The node cannot answer asset holders (so ADA Handles), transaction metadata (so polls and Calidus registrations), the time of a pool's last update, a tally or script evaluation; `spo capabilities` lists each absent with its remedy, and a command that needs one fails before any prompt. There is no era reader for the air-gap commands, and the node states no block height or depth for `spo tx status` and `--wait` (see item 25). A Koios or Blockfrost section supplies these only if `[provider] order` names it: confirm with the network log (or a firewall rule) that a configured but unnamed Koios receives no request in online mode.

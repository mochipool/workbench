# Handoff: state of the workbench

Read this before changing `orchestrator/`, `tools/workbench.nix` or `docs/`. It records what exists, how to prove it still works, what is unfinished, and what we learned about the upstream scripts that the code relies on. The longer-term direction is in [Roadmap: native port](./roadmap-native-port.md).

## Verify the current state

Every one of these must pass before and after your change:

```sh
nix flake check --accept-flake-config                     # includes workbench-tests (52 unit tests)
nix build --accept-flake-config -o result-workbench .#workbench
cd orchestrator && SPO_WB_E2E_WORKBENCH=$PWD/../result-workbench/bin/workbench \
  nix shell --impure --expr '(import (builtins.getFlake "nixpkgs") {}).python3.withPackages (p: [p.pytest])' \
  -c sh -c 'PYTHONPATH=src python -m pytest -q -p no:cacheprovider'   # 52 unit + 1 real-script e2e
```

The e2e test (`tests/test_e2e_real_scripts.py`) drives the real pinned scripts and cardano-cli in offline mode on preview. It needs network access for one light-mode `01_workOffline.sh new`. The tutorial `docs/tutorials/rotate-kes-on-preview.md` was executed verbatim and ends `[DONE]`. Re-run it after changing `kes-rotate`.

Unit tests use stand-ins (`tests/fake_scripts.py`) that reproduce the upstream file contract. When you learn something new about upstream behaviour, encode it in the stand-in first, so the unit tests cannot drift from reality again (this happened once; see Gotchas).

## Go reference implementation (`spo/`)

Started 2026-11-16. Read [Go reference implementation: concerns](./go-reference-implementation-concerns.md) and the [ADRs](../explanation/adr/README.md) before touching it. The concerns page has a *Status* table that says what is closed.

State: 68 of 68 specs are implemented (`spo/spec-coverage.toml`; the waived ids carry their reasons, and `python3 spec/tools/specctl.py coverage --tests spo --config spo/spec-coverage.toml` is the proof). The sealed store is the default (ADR 0003): `spo init` creates a workspace (`workspace.spo`, its head file and `spo.toml`), every command opens it with a passphrase from the terminal or `--passphrase-fd`, a rekey always revokes the old recovery key, and a rolled-back file is refused unless `--accept-rollback`. The release binary cannot write a signing key or any other secret unprotected (see *No secret is written unprotected* below): a plain upstream-layout directory is only the source of `workspace import`. Offline mode (clock, transfer file) and light mode (Koios, light-mode parameters file) are wired. Provider API tokens are stored in the sealed store. See [spo CLI](../reference/spo-cli.md) and [spo.toml](../reference/spo-toml.md).

Built, by area (the table below says where):

* Keys and pool: KES, VRF and cold keys, opcert issue and check, the pool descriptor, certificates, registration and retirement with witness collections, and the import of a pool from the chain or an info file (`pool import`, `pool export-info`).
* Money: `wallet send`, `claim-rewards`, `send-assets`, the stake commands, the offline transfer file (`offline ...`), native policies, mint, burn and settle, and the token-registry entry (`asset meta generate` and `check`; the registry needs light mode with a server, so a test network needs `[registry] url`).
* Governance: DReps, committee, votes and actions (`info`, `no-confidence`, `update-committee`, `new-constitution`, `hard-fork`, `treasury-withdrawal`, `parameter-change`), with the checks the commands can make. `parameter-change` checks a cost model's length against the current model and refuses when that model cannot be read as an array (a provider that serves the models keyed by name) unless `--allow-cost-model-length-change`, which then prints "cost model length not checked". `action submit` carries the guardrails script when the constitution has one, with the execution units from a provider (see "Not built"); its parameter-change and guardrails parts are compared with cardano-cli in `test/parity` (`gov_params_oracle_test.go`, `gov_plutus_oracle_test.go`) but never ran on a network.
* Other: Calidus (`new`, `register-metadata`, `status` in light mode, `sign`) and Catalyst (`key new`, `key qrcode`, `register`) registration (signed metadata records, with a pool cold key, a voting key and a stake key on a device where the profile says so), ADA Handles, SPO polls, BLS keys.
* Hardware wallets: the adapter over `cardano-hw-cli` is built and tested against a stand-in tool only. **Untested on devices**: work through [the device checklist](./hardware-device-checklist.md) before relying on it.
* Multi-party signing (file and tailcat transports, ADR 0005): the `spo party ...` commands and the signing and review flows (`cli/party*.go`, `cmd/spo/party.go`) are wired. The library stack and the wiring were cleared by review (nine Opus passes in all; the last lists no required change) with the operating conditions in the "Multi-party signing" section of [the command reference](../reference/spo-cli.md). The pre-signature summary (`cli/party_summary.go`) and the rule that `approve` refuses when any certificate, vote, withdrawal or required-signer line was folded are the parts reviews kept finding gaps in: change them only with a regression test and a review. Since the ninth review: the review body quotes a peer's relay hosts, metadata URL and anchor URLs, `approve` re-reads the terminal size just before it asks, `review` ends with a warning when it folded an authority section, and `foldedError` names every foldable category from one table (`authorityCategories` in `cli/party_review.go`; a test fails when a line of the authority region belongs to no row). Identity rotation (`party rotate`, `party rotation list|accept|reject`, SPO-Xparty-IF-008 and INV-030 to INV-033, PR-006) and the collection-closed notice (INV-035 to INV-037) are built and have **not** been through a review pass: treat `app/multisig/rotation.go`, `domain/party/rotation.go` and the closing-notice changes in `signer.go` as new, security-relevant code. Not built: nothing in the party stack is known to be missing.
* TUI (`spo tui`, ADR 0009, [reference](../reference/spo-tui.md)): a second driver that walks the same command tree, so a new command is in it with no TUI code. The parity test is `TestU1...` in `cmd/spo`; a new `*-fd` flag must be classified in `cli/uihints.go` (`TestU2...`). Name completion, the file picker and the flag-group display are driven by hints registered in `cli/uihints_table.go` (command path and argument label or flag name to a `uihint` value); a new command that takes a wallet, pool, file and so on adds a line there, and `TestUIHintTableMatchesTheTree` (`cli`) fails when a label no longer exists. Flags that exclude each other are declared with cobra's `MarkFlags...` so the form shows them. The pty tests (`cmd/spo/tui_pty_test.go`, `TestPTY...`) run `spo tui` on a real pseudo-terminal and skip, saying "no pseudo-terminal", where there is none (a Nix sandbox).

* Selective import from several folders (`spo workspace import DIR... --depth --only --rename --all --dry-run --manifest`, [Xmulti](../../spec/extensions/Xmulti.md), [how-to](../how-to/import-multi-folder-layout.md)): `app/workspace` `import_select.go` (discovery, selection, rename, collisions), `import_paths.go` (descriptor path fields, resolved lexically against the discovered owners, byte-preserving rewrite), `cli/workspace_import.go` (flags, manifest, table and `--format json` plan), `tui/import_flow.go` (guided flow on `ctrl+g` of the command's form; it runs the command with `--dry-run --format json` and builds its flags, no import logic). Atomicity: the plain form keeps one store update per owner; the selective form stores the whole run in one update ([Xmulti](../../spec/extensions/Xmulti.md) INV-008). The snapshot (`List`, whole reads) and both gates run before it because the store cannot list or open a secret from inside an update (`ErrReentrant` on sqlitestore), and a decryption is slow; the update first re-reads what the decisions rested on (`verifySnapshot`: snapshot artefacts and contents, the plan's destinations and the probe set of each name) and returns `ports.ErrConflict` if it moved. The port has no store head or version, so an artefact of another kind added to an unprobed owner, or a new pool naming a replaced wallet, is not seen; a version in the port would close that. Descriptor names are read by the domain accessors (`Owners`, `Text`, `pool.RegistrationNames`) in Gate B and the oracle; repeated or case-variant keys are refused. A merge into a workspace owner needs an identity anchor (OUT-019). A name collision among selected owners stops the run before any write. Limits: owners beyond the folders and depth are workspace-only; pool records are tied to owners only through key bytes, cold-key references, key hashes, pool ids and descriptor names. `ports.SourceTree` (`Subdirs`) is the only new port. The manifest is a small TOML subset parsed in `cli` (the module has no TOML library; `adapters/config` has its own parser for `spo.toml`). Unverified: behaviour on a source tree shared over NFS or with unusual names beyond the tests, and descriptor fields added by upstream versions after the pinned tag.
* Import planning (`app/workspace` `import.go`, `import_select.go`, `import_paths.go`, `import_snapshot.go`, `import_leftovers.go`, `import_binding.go`): the run is split into a plan and an execution. The plan reads the workspace once into a snapshot (`wsSnapshot`), decides every selected owner in dependency order (an owner a pool names is decided first; two pools naming each other are refused as a reference cycle) and writes nothing; execution writes the planned owners and refuses a pool whose owner was not written. A dry run is the same plan without the writes. Every name a descriptor holds that refers to an owner goes through one function, `resolver.resolveRef`: `poolOwner[].ownerName`, legacy `poolOwner`, `poolRewards`, and each name inside `regWitness` (`regPayName`, the slot keys `<pool>.node`, `<owner>.staking`, `<pay>`, and the pool name inside `metadataFilesList`), which `openRegistration` enumerates and then requires to map to the name it already has. Never add a field with a resolution of its own. The property the planner must keep ([Xmulti](../../spec/extensions/Xmulti.md) INV-006): every name a stored descriptor carries is a wallet this run stored from the source owner the layout names, or one the workspace holds with byte-equal stake and payment verification keys, or one only the workspace has (noted by stake key hash); otherwise the pool is refused; and no owner holds another owner's key material. Four reviews in a row broke INV-006 through four different paths, each patched where it broke, so the property is now enforced on the planned END STATE by two gates that every path must pass; the path logic (which makes the messages) is kept in front of them. **Gate A** (`checkCoherence` in `import_leftovers.go`, OUT-016; the only implementation, no second copy): whenever the stored name of an owner is a name the workspace already holds, with or without `--overwrite`, the result (existing artefacts plus incoming, incoming winning) must be provably one owner: same kind, every key pair matched (a pair whose halves come from both sides and cannot be derived refuses), addresses and certificates derivable from the result's keys, payment and stake keys together only through a base address or a common origin, every operational certificate decoded (`pool.ParseOpCert`) and naming the result's cold key and the KES key of its number, counters consistent; anything unverifiable refuses. **Gate B** (`checkBinding` in `import_binding.go`, INV-007): after the plan and before any write, every stored pool's final descriptor names (enumerated by `refFields` and `registrationRefs`, the same functions the rewrite uses) must be wallets of the end state (`endState`) that have a stake key and the keys of the source owner the layout names; it does not call `bindSelected` or `resolveRef`. A new path or field must pass both; do not weaken them to fit a path. Tests: `multi(t, tr, dst)` registers `assertINV006` (`import_inv_test.go`) at the end of every selective-form test, an oracle that recomputes the property from the stored files and the source tree; `import_gates_test.go` has the probes, and unit tests that feed Gate B a hand-written plan. Disable a gate or a path fix temporarily and the oracle shows what leaks. What no gate can see: a failure of the write itself (the execution-time dependency check stays). The plain form (one folder, no selection flag) keeps its old outcomes and only gains notes. Probe new import changes with a descriptor that names an unselected owner with other keys in the workspace, and with `--overwrite --rename` onto a hardware or payment-only workspace wallet.
* Transaction status and waiting (`spo tx status`, `--wait` on every submitting command; [Xconfirm](../../spec/extensions/Xconfirm.md), ADR 0006 addendum): `ports.TxStatusReader` on Koios, Blockfrost and the node, `app/txconfirm`, `cmd/spo/txwatch.go` (per-call freshness and sync guards), `cli/txwait.go` (the submit recorder, the wait, the exit codes). Built and tested against loopback stand-ins and the fake node only: the Koios and Blockfrost shapes are from public documentation, never a live service, and the node's answers are the fake's. **Local state is still applied on an accepted submission, not on confirmation**: the asset record update of `asset mint`/`burn` (`app/assets/mint.go`, `ApplyChange` when `res.Submitted`) and of a queued one (`UpdateHook`, `SettlingSubmitter`/`Settle` in `app/assets/record.go`); the offline queue entry's removal, the addresses marked used and the history line (`airgap.ExecuteTx`, `Bundle.CompleteSubmit`); the pool descriptor's registration and retirement records (`RecordRegistration`, `RecordRetirement`) and the `.multisig.submitted` record of a pool registration (`poolops/register_pool.go`); and the party collection's close (`multisig.Coordinator.CompleteNow` sends `CollectionClosed` with outcome submitted). Whether any of these should wait for a confirmation is undecided.
* Pending records (hazard H9, [Xconfirm](../../spec/extensions/Xconfirm.md) PR, ADR 0006 addendum): the asset record of a mint or burn and the registration and retirement records of a pool descriptor are applied when the transaction is **confirmed**, not when it is accepted. `assets.Pending` (domain; carries a kind and the validity bound) is stored as `<txid>.pending` (`ports.PendingUpdate`; `<txid>.asset-pending` is still read); `app/assets` has the one apply path (`Settle.Apply`, one store commit with the removal, so a crash cannot apply twice), `SettleFromBundle` (offline machine; applies only on a history entry `spoConfirmed`, `--accept-submitted` trusts the submit) and `UpdateHook`; `poolops.ApplyRegistration`/`ApplyRetirement` are the pool appliers, plugged in by `cli/txsettle.go` (`settleAppliers`); `app/txsettle` is the provider settle (`spo tx settle`) and `RecordInTransferFile` (writes `spoConfirmed`/`spoExpired` history entries on the online machine); `txconfirm.Waiter.Probe` makes a settle cost one poll. A command that leaves a pending record sets `envSpec.settles` (wait by default, `--no-wait`, `addSettleFlags`); `offline execute` sets `settlesIfPending` and decides after the submit (`executeSettling`). `txflow.Input.Stage` is where the retirement writes its pending update before the transaction leaves. Choices a reader should know: the carrying fields keep their first names (`spoAssetPending`, `spoAssetSubmitted`) and now hold any kind, because the parity tests and old files use them; confirmation is recorded in the file by `spo tx settle` on the online machine (not by re-running `offline execute`, whose queue is empty after the submit); a registration's witness collection and certificate are consumed when the transaction is sent while `regEpoch`/`regSubmitted` wait; the multi-party coordinator's "submitted" notice takes a pending registration for the body as proof. Not done: a retirement or registration whose submission outcome is unknown after a crash that lost the process before the pending record was written (the record is written before the transaction leaves, so only a failed write of the record itself, which stops the command first, would lose it); `UpdateHook` still applies a carried asset update to a local copy of the record when no pending record is found, as the first version did (a repeat on the queuing machine would apply it again to its own record); it now first checks the update against the confirmed transaction (id, and the mint field's policy, name and amount; PR-027). The transfer file is unauthenticated (E7): `SettleFromBundle` applies an outcome only for a transaction recorded as submitted and gone from the queue, discards on an expiry only when the stored bound equals the queued one, and `RecordInTransferFile` takes the id and bound from the transaction stored in the history entry (`spoTxCbor`), so a file written before that key existed cannot be settled from. A submission whose provider answered another id is an unknown outcome (`chain.IDMismatchError`) and keeps the pending record; the status rule for web providers is `chain.SubmitStatusRefuses` (PR-008). `spo tx settle` settles every item and exits 1 if one failed (PR-016). Not tested: `test/parity` `settlePending` now asserts the pending record exists, but the parity tests skip without the toolchain and were only vetted here.
* Chain access (ADR 0006): Koios, Blockfrost (second provider), the offline snapshot and the node socket (online mode; **never run against a real node**, see below) are wired. Reads of the harmful-if-false class (reward balance, pool registration, DRep registration, opcert counter, pool import data) need two agreeing sources or `--single-source`; the acknowledgement is recorded in the audit log by a `ports.SingleSourceHook` that each use case calls at the point where it accepts the single source, before anything is signed, submitted, queued or written (a use case told to accept one without a hook refuses). One record per accepted read: `stake deregister` writes two. `pool import` reads the chain once (`ImportPoolFromChain.Fetch`) and every later step uses that answer. A web provider needs a tip under ten minutes old as the first or the second source; two sources on one host need `same_host_ok`, and the summary says when that was relied on. Every string a chain, provider, peer or file chose is written through `platform/textsafe` (`shown` in `cli`, `ports.IsPlainText` in the use cases); `cmd/spo` prints every command error through `cli.SafeMessage`.
* Multi-party: `enqueue` has no exemption by item type; only `enqueueRotation`, called by `RotateIdentity`, queues announcements sealed by the identity they replace, and marks them (`OutItem.Rotation`) so the outbox sweep keeps them. An outbox written before that mark existed would have its undelivered rotation announcements dropped by the sweep.

* Key references and the signer directory ([Xidentity](../../spec/extensions/Xidentity.md) IF-001, IF-002, INV-015, INV-016, PRE-004, PRE-005, SEC-005, SEC-006; ADR 0010 decision 3, local part): `custody.KeyRef` is `{Role, Identity}`; the holder, owner name, device and party are gone from it, and a hardware flag on a command is `custody.Placement` (where a NEW key is generated). `ports.SignerDirectory` has `Connected(key)` (the signers connected now, in preference order) and `SignerFor(key)`; `adapters/native.Signers` is the one directory: the vault (found by identity through `ports.KeyIndex`, here `labels.Index` over the owner manifests of the identity-keyed store), the attached device (`hwcli.Lazy`, with its own Profile, so a device unplugged before the plan fails in the plan) and `Remotes` (co-signer parties by fingerprint, answers deferred, `Network` says whether the demand travels over a network). Order is hardware, vault, remote (vault first for an operational certificate: `ports.SignerForOperation`); an operator's assignment (`txflow.Slot.Party`/`External`) wins over the directory; `Signers.Prefer` is the one hook for the operator preference that has no label attribute yet. Use cases resolve a name to a reference once, at their edge, with `app/keyring` (`Resolve`, `ResolveHeld`, `Held`), which read through `ports.NamedReader`; the label resolver (`ports/labels`) maps the name to an anchor. Use cases ask a signer for a capability, not a place: `hwkeys.IsHardware(signer)` (it takes the options of a device witness) and `hwkeys.OnDevice(directory, key)`; `internal/archtest/keyref_test.go` fails on any `Holder`-named identifier under `internal/app`. The cold-key rule is keyed on `ports.RoleHistoryOf` (the stored `role-history` record of the identity): the directory does not offer a network remote for such a key, `Coordinator.History` does not create the request, `Signer.History` refuses it again on receipt. The persisted slot has `partyFingerprint` and no holder (INV-015); `ResolveLegacyParties` turns an old `party` name into a fingerprint on open, and `Coordinator.OnRotate` moves open slots when a party rotates. The vault signer derives the transaction id from the bytes it is handed and checks that the key it opened is the demanded one. Not built: own-client remotes, announcements, proof of possession and blinded handles (later, per ADR 0010 decision 6); the token-registry attestation signer still takes 32-byte messages, not the entry; a remote co-signer is not wired into `cmd/spo` as a directory entry (a slot assigned to a party is still opened through the coordinator, outside `Signers.SignerFor`); `ports.RoleHistoryOf` is read before a store transaction opens, never inside one (the sealed store's gate is not re-entrant, which hung `TestTailcatTwoOwnerRegistrationEndToEnd`).
* Object identity and witness verifiers ([Xidentity](../../spec/extensions/Xidentity.md), ADR 0010 decision 1 and the verifier part of decision 3): `domain/identity` has the typed identity `Ref` (kind and hash; text and one-length-byte binary forms), one constructor per row of the ADR's table, one kind per spo-defined object kind bound to its tag, the `[tag, value]` content hash with its tag registry (a JSON-mapped kind has only its `/map1` tag), a library-free canonical CBOR encoder and strict decoder (`DecodeCanonical` is the canonical check; the exact-bytes rows never go through it), the fixed anchors, and the owner manifest (immutable, append-only, content-hashed, with a fixed role vocabulary per owner kind and the anchor rule checked). `domain/custody` has `RoleHistory` (with `Extends` for the store to call on every write) and the verifiers `VerifyTxWitness`, `VerifyOpCert`, `VerifyCip36`, `VerifyCip88`, `VerifyMessage`, `VerifyRegistryAttestation`: `pool.Collection.Fill`, `party.VerifyWitness`, `txbuild.VerifyWitness` (now a thin call) the hardware adapter, the Catalyst and Calidus registration, the operational certificate and the token-registry use cases use them and hold no check of their own (`hwcli/noverify_test.go` fails on an `ed25519.Verify` there). Rows the ADR marks unconfirmed (script hash, VRF hash, KES, BLS, Catalyst and Calidus hashes) are marked in the code and the spec: a test shows agreement with the code that already computed the value, not with the ledger specification or a CIP. `domain/identity` and `platform/seal` each have a canonical CBOR encoder (the domain takes no CBOR library and the platform may not import the domain); `internal/archtest/canon_agree_test.go` (a random loop and a fuzz target) pins that they agree; `seal` still emits invalid UTF-8 as given, the domain encoder refuses it. **Nothing is wired yet:** `ports.Ref` still holds a name, `custody.KeyRef` still has `Holder`, `Owner`, `Device` and `Party`, there is no `ports.SignerDirectory`, no `owner` or `label` record, no role-history record, no store migration and no blinded handles. The stored witness slot (`pool.Slot`) still carries `Holder` and a party name. A later change builds those on this package.

**Not built:**

* Unlock factors on disk (ADR 0011), what is not built: the Vault and KMS clients; TUI flows beyond the generated forms; a `Rekey` that "re-creates the slots the policy allows" under `hardware` and `strict` (ADR 0011 Amends, ADR 0003 "Rekey" step 3): it is refused there with a message that names `spo workspace rotate` (deviation, by design: rotation is the path). The cold-role sub-key and the HPKE recovery wrap are built (see "Cold-role sub-keys and the HPKE recovery wrap" below). Built: the commands `workspace slot list|add-fido2|remove`, `workspace policy show|set`, `workspace rotate`, `workspace init --policy`, `--unlock`, `--fido2-device`, `--fido2-pin-fd`, `--recovery-pin-fd`, `--recovery-key-in-fd`, `--old-recovery-pin-fd`, `--keep-copy`, `--allow-weaker-policy`, `--old-passphrase-fd`, `--remove-unfinished`, `node export` and the helper `spo-node-keys` (see below); the store (format 3, migration, the opener's policy check, unlock through `fido2-hmac` and `composite` slots, `AddFactorSlot`, `Rotate` with its recovery presentation, `RemoveSlotByRotation`, `Reauthenticate`, `VerifyFileFactors`, `RestoreWithFactors`, the restore policy check); the touch-probe result stored with the factor and listed. e2e over `fakefido` in `cmd/spo/unlock_e2e_test.go`, `unlock_custody_e2e_test.go`, `node_export_e2e_test.go`.
* Not built: converting a kept-encrypted BLS key (no verification key can be derived; import it again with `--password-fd`), and encrypting or decrypting a key file in place in a plain directory (the upstream script `01_protectKey.sh` does that). A kept-encrypted KES or VRF key can now be converted, because the native deriver derives both (the same derivation as the delivery check).

**Node delivery (ADR 0011 decision 2), built, never run on a real host.** `spo node export` (`app/nodekeys`, `cli/nodeexport.go`) seals the three hot files to an age X25519 recipient (`adapters/nodeage`) after the checks of SPO-Xcustody-PRE-007 to PRE-011; the KES and VRF derivations are `ports.HotVKeyDeriver`, implemented in `adapters/native/hotkeys.go` (the only home of the Blink Labs libraries), and the exact form of each kind is `domain/pool/hot.go` (`ValidateHot`, the one table of kinds). The start-up helper is the separate program `cmd/spo-node-keys` (`spo-node-keys deliver --from DIR --to DIR`), logic in `adapters/nodefiles` (`Deliver`, `Dir`): directories opened with `O_DIRECTORY|O_NOFOLLOW` and checked on the descriptor, files created with one `openat(O_CREAT|O_EXCL|O_NOFOLLOW)`, ramfs only. Choices made where the ADR is silent (each is the most restrictive reading; the owner may relax them): the helper reads the age identity only from the systemd credential `spo-node-age-identity` in `$CREDENTIALS_DIRECTORY` (not a flag, not a path), which must be a plain file with no group or other bits, on ramfs; the helper refuses to run as root (its files are owned by the user it runs as, no `chown`); the output directory must exist and be on ramfs (the credentials directory too: whether systemd's is ramfs or tmpfs is unconfirmed, so on a tmpfs one the helper refuses); the helper never replaces a file; `node export` takes the recipient as a file (`--recipient FILE`), refuses `age` recipients other than X25519, names its files `<plain name>.age`, and records the recipient by an 8-byte identifier of its SHA-256. The ADR says `node export` "records that the host has no TPM-bound identity": it cannot see the host, so it records `not verified` by default and `none` with `--no-tpm-identity`.

How a command gets what it needs, and how to add one:

* One `Env` carries every capability, each typed by its narrow port (`adapters/cli/env.go`). `cmd/spo/env.go` builds it with `Deps.Wire(store, WireOptions)` from the workspace config, the effective mode, the genesis overrides, the provider token and the transfer-file path. A chain capability is nil when the mode or provider cannot supply it, and the wiring records why (`Env.Absent`). `spo capabilities` prints the same Env.
* A command is one file in `spo/internal/adapters/cli` with a `*cobra.Command`, registered in `root.go`. It calls `a.withEnv(cmd, envSpec{needs: ...}, fn)`. The needs (`Cap` constants, `OneOf(...)`) are checked on an Env built before the store is opened, so a command that cannot run here fails before any prompt, with one error listing every missing capability and why. Inside `fn`, use the `Env` fields; never nil-check a field. Chain commands add `addChainFlags` (`--offline`, genesis flags, optionally `--transfer-file`).
* Nothing changes in `cmd/spo` when you add a command. It changes only when you introduce a new adapter, or a new capability: add a field and a `Cap` in `env.go`, give `Env.has` its case, and wire it in `cmd/spo/env.go` for each mode (or record why it is absent).
* Errors from the store are sentinels in `cli/deps.go`; `explain.go` turns each into one sentence with the remedy, for every command.
* Tests: fakes in `adapters/cli` (a fake `Deps.Wire`; see `wallet_test.go` for a fixture around the real native ledger), the real adapters in `cmd/spo` on a sealed workspace (`e2e_test.go`; Argon2 runs at its floor, so one workspace is created and copied).

Things that will bite:

* **No secret is written unprotected** (the owner's rule; ADR 0011 (proposed); [Xcustody](../../spec/extensions/Xcustody.md)). The release binary must be unable to write a signing key or any other secret unencrypted. The plain upstream-layout directory is not a workspace: `--upstream-layout`, `key protect`, `key unprotect` and `workspace export --plaintext` are gone. What enforces it: `adapters/upstreamdir` is the read-only reader (no write method; `ports.ReadStore`), `adapters/exportdir` is the only writer of the layout and refuses every secret that is not a signing key in upstream's encrypted form, and the writable plain store lives in `spo/test/plainstore`, which `internal/archtest` keeps out of every non-test file except `cmd/spo/wiring_plain.go` (built only with `-tags plainlayout`, not a release). `tools/spo.nix` proves absence in the release build: `go list -deps` has no `spo/test/` package, and the installed binary's help names no `--upstream-layout`, `--plaintext` or `unprotect`. Tests that need a plain directory (`cmd/spo` e2e, the CLI fixtures, `test/parity`, `test/world`) import `plainstore` directly or call `usePlainLayout(t)` in `cmd/spo`; `spo-parity` also runs with the tag. Imported keys that stay in upstream's password-encrypted form (`--keep-encrypted`) are sealed records that cannot sign and are never exported: `spo key convert` decrypts one, checks it against its verification key and stores it as a normal sealed key (ed25519 key types only; KES, VRF and BLS are re-imported with `--password-fd`).

  Inventory of what could write secret material outside the sealed store, as of this change:

  | Path | What it writes | Decision |
  | --- | --- | --- |
  | `--upstream-layout` plain store (`fsstore`, `cli/root.go`, `cmd/spo/wiring.go`) | every secret kind in clear (signing keys, mnemonics, QR code, party keys), mode 0400 | removed from the release; the writer moved to `test/plainstore` (refuses mainnet); the reader that stays is read-only |
  | `key unprotect` and its `.spo-workspace-audit.json` | a decrypted signing key in clear, in place | removed; an existing audit file is ignored by import |
  | `key protect` | an encrypted key in place, in a plain directory | removed (only meaningful in a plain directory) |
  | `workspace export --plaintext` | signing keys and mnemonics in clear | removed; the flag, `--yes` and the confirmation word are gone |
  | `workspace export --password-fd` / `--generate-password` | signing keys encrypted in upstream's gpg form (pinned `--s2k-mode 3 --s2k-digest-algo SHA512 --s2k-count 65011712 --cipher-algo AES256 --force-mdc`), non-secret files | kept as a transport form (gpg's S2K is not memory-hard); password at least 20 characters or generated; destination `exportdir` checks the OpenPGP packets and refuses anything else; mnemonics, QR codes, kept keys are skipped |
  | `workspace export` of a kept-encrypted record | the encrypted key text, back out | removed (INV-003); `key convert` first |
  | `catalyst key qrcode` | the voting key as a QR code under a 4-digit PIN (Catalyst's format) | the PNG writer is removed from the release; the code is drawn on a terminal only (alternate screen, cleared on Enter), after a stated 10,000-guess warning and a confirmation, and the display is audited; see item (3) below |
  | `init`, `store rekey`, `store recover` recovery key (`deliverRecoveryKey`) | the new recovery key: shown once on the terminal with a typed confirmation, or written to `--recovery-key-fd N` | kept; see item list below |
  | `hwcli` scratch directory (`hwcli/exec.go`) | hardware signing files, transaction bodies and witnesses, 0600 in a 0700 temp dir removed after the call | kept: none is a secret by ADR 0004 (no key material) |
  | `party export`, `party` snapshot copy (`privateCopy`), witness files, the offline transfer file | public identity document, chain-view snapshot, witnesses, transactions | kept: not secret (ADR 0004); party private keys stay sealed |
  | mnemonics (`wallet new --mnemonic`, `drep`, `committee`, `calidus`) | stored sealed; never displayed or written | kept as is |
  | crash dumps and logs | none: `secret.HardenProcess` sets RLIMIT_CORE 0 and no ptrace; secrets are in locked guarded buffers; no logger is configured | kept |

  Legitimate secret outputs that stay, with their guards and a recommendation (nothing was changed silently): (1) the recovery key on the terminal: shown once, the operator must type back its last group, a hard refusal without a terminal unless `--recovery-key-fd` is given; recommendation: keep, it is the only copy. (2) `--recovery-key-fd N` and `--password-out-fd N` write a secret to a descriptor the operator opened; `internal/platform/secretfd` accepts only a pipe or a Unix socket open for writing and refuses a regular file, directory, device or terminal, descriptors 0, 1 and 2, and a closed descriptor, before any effect ([Xcustody](../../spec/extensions/Xcustody.md) OUT-005, PRE-006); the check is driven by the same table (`secretFDFlags`) that classifies the flags for the TUI, so a new secret-output flag is checked as soon as it is classified. The export delivers its generated password before it writes any file. (3) The Catalyst QR code: the payload is encrypted with a 4-digit PIN, which does not resist an offline guess, so it is written to no file. The drawing on a terminal is the one named, audited, non-persistent output of this secret ([Xcustody](../../spec/extensions/Xcustody.md) INV-001, OUT-004): a tty is required, the risk is stated first, the default answer is no, `--yes` works on a tty only, and the display is recorded in the audit log before the payload is built. (4) `workspace export` of keys encrypted with a gpg symmetric password: the parameters are pinned, the password must be at least 20 characters besides upstream's strength rule, or is generated (160 bits); gpg's S2K is not memory-hard, so the export is a transport form to be deleted after use ([Xcustody](../../spec/extensions/Xcustody.md) SEC-003). (5) The `spo-parity` derivation is built with the `plainlayout` tag and installs no executable (a log and a marker only); the check `spo-tagged-no-binary` fails when a tagged derivation has any runnable file.

* **Hardware wallets are untested on real devices.** The adapter is built and tested against a stand-in tool. Before relying on it, work through [the device checklist](./hardware-device-checklist.md).

* **The multi-party stack passed its fifth security review** with operating conditions (ADR 0005, `spec/extensions/Xparty.md`). Four fix rounds preceded it and two of them left a fail-open edge, so any change to `domain/party`, `app/multisig` or the transports needs a regression test that fails without the change, and an Opus review. The wiring obligations a command must meet are listed in ADR 0005 (address inspector always set; resolver only through `OwnProvider`/`OwnSnapshot`; `Received` only from a transport; a real approval gate).
* **The sealed store passed its seventh security review** with operating conditions (ADR 0003). Its history matters: each of the first five fix rounds introduced a new defect, mostly around rekeying, locking and SQLite's side files. Change `spo/internal/adapters/sqlitestore` only with a regression test per change and an Opus review afterwards. The multi-party library stack is cleared; the wiring of its commands is pending review (see the *Status* table in the concerns page).
* **Parity tests that need cardano-signer skip inside the Nix sandbox.** The signer is a prebuilt binary whose interpreter path cannot be patched, so it does not run there. Run them in the development loop: `source <scratch>/env.sh` style variables as described in `spo/test/parity/parity_test.go`, then `go test ./test/parity/`. The Nix check allows exactly that skip and fails on any other.
* **Tailcat adds about 18 MB** to the binary and a large test-only dependency set (concern T8).

* **Nix does not see files jj has not told git about.** After creating files, run `git add -N <paths>` before `nix build`, or the flake fails with "not tracked by Git".
* **`vendorHash`.** After any change to `spo/go.mod` or `spo/go.sum`, set `vendorHash` in `tools/spo.nix` to the all-`A` placeholder, build, and paste the hash Nix reports.
* **Go version.** `spo` needs Go 1.27 (tailcat). It is built with the `nixpkgs-go` flake input, which is locked separately from the release set's `nixpkgs`.
* **Check [Go library coverage](./go-library-coverage.md) before writing an adapter.** It says which library function to use, what has only been read and not run, and what we write ourselves.
* **Capability-typed ports (ADR 0008).** One small interface per capability; no method whose honest implementation is "unsupported". Signatures go through a `custody.Plan`, built before any effect. Do not write a hardware variant of a use case.
* **Native first (ADR 0007).** New key, signing and ledger operations go in `spo/internal/adapters/native` on Blink Labs' libraries, each with a parity test against the pinned cardano-cli in `spo/test/parity`. Do not add a cardano-cli adapter for something `bursa` or `gouroboros` covers. cardano-cli 11.2.3.0 cannot write KES or VRF keys to a pipe, which is one reason.

How to port a use case (the pattern `GenerateKesKey` sets):

1. Read its specs. Put state rules in `domain/<context>`, the sequence in `app/<context>`, and add only the port operations it needs.
2. Unit-test the use case with fakes, citing ids in `// spec:` comments. Record each upstream-quirk decision in the test that cites the id.
3. Add a differential test in `spo/test/parity` that runs the upstream script through `workbench exec` and compares state.
4. Add the spec code to `implemented` in `spo/spec-coverage.toml`; waive what is deliberately not ported, with a reason.
5. Fold anything the real tools taught you back into the spec.

Where to go next: the **Not built** list above. Running the node-socket checklist against a preview node comes first, then a recorded Koios `/ogmios` answer and a local Plutus evaluator.

## Backup sink (ADR 0012 stage 1)

`spo store backup --sink URL`, `spo store backups --sink URL` and `spo store restore --sink URL --pin PIN` move the existing sealed backup file to and from a directory (`dir:/abs/path`) or an S3 bucket (`s3://bucket/prefix`). No new cryptography. Code: ports `spo/internal/ports/objects.go`; use case `spo/internal/app/backupsink` (no `os`: scratch space is `ports.Scratch`, adapter `spo/internal/adapters/scratchdir`); adapters `spo/internal/adapters/objstore/{dir,s3}`; commands `spo/internal/adapters/cli/store_sink.go`; wiring `openSink` in `spo/cmd/spo/wiring.go`; the S3 fake with fault injection `spo/test/fakes3`. Spec [Xbackup](../../spec/extensions/Xbackup.md); how-to [Back up to a sink](../how-to/back-up-to-a-sink.md); design choices in "Implementation notes, stage 1" at the end of ADR 0012.

**Nothing was run against a real bucket.** The S3 adapter was tested only against the in-process fake, including dropped connections, a lost response, a stalled download, a corrupted body, expired credentials and credentials from the SDK's real chain (a `credential_process` with an expiry, and environment keys, which are refused). Real Object Lock behaviour, the SDK's `CanExpire` for SSO, Roles Anywhere and web identity, and any S3-compatible store are unconfirmed (concern S6). The AWS modules entered `go.mod` (the `tailscale.com` dependency already pulled the SDK in indirectly) and `go get` raised a few of their versions; both `vendorHash` values in `tools/spo.nix` were updated.

Known gap, not built: **`store restore --allow-older` can lower the operational-certificate and KES counters** (`checkReplace` returns early on `AllowOlder`; restore has no counter rule). ADR 0012 decision 9 says restore keeps the larger value; the code does not (concern S5). `store restore --sink` therefore refuses `--allow-older`. No earlier sentence in this page claimed otherwise.

Restore install crash window (fixed in the stage-1 fix round): the restore writes `<file>.head.next` before the swap and removes it after the head file; an open adopts it when it names the file's own verified head (notice on stderr), and ignores and reports one that does not. Tests build the crashed states for an older and a newer backup and a forged sidecar (`TestRestoreCrashAdoptsTheSidecarForOlderAndNewerBackups`, `TestRestoreCrashForgedSidecarDoesNotSuppressTheRollbackError`). `store restore --sink` still refuses `--allow-older` (concern S5).

## Owners, labels and the identity-keyed store (ADR 0010 decisions 2 and 4)

Read [Xidentity](../../spec/extensions/Xidentity.md), "Owners, labels and the identity-keyed store" (INV-017 to INV-026, IF-003 to IF-005, PRE-006), and [how to migrate a workspace](../how-to/migrate-a-workspace.md). The shape:

* `ports.Ref` is `{Anchor, Kind, Num}`; the store (`sqlitestore`, and `test/plainstore` behind its directory mapping) never sees a name. The use cases are written against `ports.NamedStore`/`NamedReader`/`NamedWriter`/`NamedVault`/`NamedRef`; `ports/labels` (`labels.Named(store)`) is the one resolver and also keeps the `label`, `owner`, `owner-manifest` and `role-history` records. A name that is the text form of an identity (`key-hash:<hex>`) names the owner that lists it, so a descriptor that holds identities still works with the use cases. Signers and the key index work at the anchor level (`ports.Store`, `ports.Vault`, `ports.KeyHome`); a command gets both from its session (`session.Store` by name, `session.Anchored`).
* An owner is created by the first key that anchors it; an owner with no anchoring key yet is provisional (its records sit under a derived anchor until the key arrives and the records move). Named records (transaction ids, transfer file names, `state`, provider tokens, Calidus and voting key families) are keyed by a derived anchor with a label in the group of their kind. Store format 2; `seal.RecordFormat`, `LegacyRecordFormat`; `Reseal` converts one record.
* `labels.Derive` is the resolver of a name-level source: the stems of a directory (the plain store, `workspace import`, `<kind> merge --from`) or of an old store (`labels.PlanMigration`, `sqlitestore.Migrate`). The committed fixtures of format 1 are `internal/adapters/sqlitestore/testdata/legacy-v1/*.db` (built by `legacyfixture_gen_test.go` with the code of format 1; the generator no longer compiles against the current code and is kept as the record of what the fixtures hold). A change to the format needs a new migration that steps from format 2 by itself: the opener already refuses by format number and `Migrate` is written for one step.

## Slot table and policy on disk (ADR 0011, store format 3)

* Format 3 (`seal.StoreFormat`) is schema version 2 of `adapters/sqlitestore`. `keyslots` has the kinds `passphrase`, `recovery`, `fido2-hmac` and `composite` and the columns `bound`, `rec_hash` and `factors`; `meta.policy` holds `standard`, `hardware` or `strict` (`table.go`, `schema.go` migration 2). The record encoding is still format 2, so a migration re-seals nothing; the genesis nonce is the workspace id.
* The opener (`open` in `store.go`) refuses format 1 and format 2 before it derives a key (`ErrLegacyFormat`, `ErrFormat2`, both naming `spo workspace migrate`), then runs `unlock.Check` on the table (`table.check`), then unlocks. A table that breaks its policy is `ErrPolicyViolated` wrapped in `ErrVerify`, and no key is derived and no authenticator is asked.
* Every slot of format 3 binds the policy and the recovery public key hash in its associated data (`seal.SlotBinding`, `SlotSpec.Policy`; labels `spo/slot-ad/pr` and `spo/slot-ad/2`; the committed vectors of the older encodings still pass). The recovery key pair is X25519 derived by HKDF from the recovery key (`seal/recovery_pub.go`); the ADR names no derivation, so this one is the implementation's.
* Legacy slots: format 2 slots cannot be rewrapped by a migration (it has no credentials), so they stay as they are, with the older associated data, and `unlock.Slot.Legacy` exempts them from the two hash rules under `standard`. Until a rekey replaces them, a FIDO2 slot cannot be added (no recovery public key to bind) and a recovery slot may be added; in format 3 proper a second recovery slot is refused (`ErrUseRekey`).
* Consequence to know: a stray or old slot row in the file now makes the open fail with a policy refusal (before, such a row was skipped with a notice and the right credential still opened). That is the required behaviour of an opener that refuses a table that breaks its policy; an operator removes the row or restores a backup.
* `Rotate` (`rotate.go`): new master key, fresh data key and payload nonce for every record, the plan's table and policy, no copy of the file (a copy opens with the credentials the rotation revokes; `RotatePlan.KeepCopy`, `--keep-copy`, is the explicit opt-in and is removed on a failed rotation), one transaction, a rollover row and a `rotate` row. A rotation of a workspace that has a recovery path needs a `RecoveryProof` (`PresentRecovery`: the recovery key and, under hardware, the recovery authenticator, checked against the bound recovery public key hash), refused with `ErrRecoveryNotPresented` otherwise; a strict workspace needs none and is not loosened (`ErrRotateWeakens`; ADR 0011 does not say how). Gap: `Rekey` is not covered by the proof rule (standard only). `Rekey` shares its core and is bound by the same table check, so it is refused under `hardware` and `strict`. Under `hardware` the recovery key pair derives from the slot key of the recovery composite (info `spo/recovery-hpke-x25519/hardware`), so the recovery key alone cannot reproduce the bound hash.
* Key separation (review N1) was **not** changed: the slot key of the new kinds is the AEAD key of the wrap and the HMAC key of the commitment, and ADR 0011 decision 3 says "the slot wraps the master key with XChaCha20-Poly1305, stores the commitment, and binds its own parameters in associated data, exactly as the two existing kinds do" and "The commitment (an HMAC under the slot key, checked before the AEAD, ...)"; splitting the key by HKDF-Expand labels would contradict those sentences. Under `hardware` the recovery key pair is already derived from the slot key by a separate HKDF with its own label.
* Tests: `adapters/sqlitestore/format3_test.go` (opener, migration, fake authenticator, tamper cases), `platform/seal` (`TestSlotPolicyIsBoundInAssociatedData`), `domain/unlock` (`TestLegacySlotsAreStandardOnly`), `cmd/spo` (`TestMigrateCommandOnAFormat2Workspace`). The format 2 fixture `testdata/legacy-v2/store.db` was made by the format 1 to 2 conversion code (`format2fixture_gen_test.go`, build tag `format2fixture`) after the format 3 code existed, not by a freshly made format 2 `Init`.

### Cold-role sub-keys and the HPKE recovery wrap (ADR 0011 decision 6), built

Built: a signing key whose identity has a cold role (pool cold, committee cold) is sealed in the cold form (`platform/seal/cold.go`: `[label, header, outer, recovery wrap]` in the wrapped-key column, class `secret-cold` in every associated data, no schema change for the records), so the master key alone opens only the outer layer. The store classifies at put time (`ports/labels/keyclass.go`: the verification key stored beside the signing key gives the identity, the role history says cold or not; a key with neither is refused), re-seals a stored key in the transaction that gives its identity a cold role (`coldPrepare`), and opens a cold record through `Store.Open` in a write transaction that rotates the salt (`openCold`; the secret is released after the commit). The factor is `sqlitestore.ColdSource` (`SetColdSource`): under standard a sub-key passphrase (Argon2id, per-record salt), under hardware and strict one two-salt assertion of the credential in the header. The CLI wires it (`cli/cold.go`: `--cold-passphrase-fd`, `--new-cold-passphrase-fd`, prompts; `ColdFactors`, `ColdVerifier`). Rotation re-seals cold records under the new table's factor (`RotatePlan.ColdNew`; the old factor is the handle's source, or the recovery credential through the wrap); a rekey that keeps the recovery key re-wraps only the outer layer; a rekey with a new recovery key moves the wraps using the presented recovery key; `Migrate3` seals cold keys under a sub-key passphrase. The recovery wrap is RFC 9180 base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 (`crypto/hpke`), info and AAD as the ADR 0011 amendment says; the recovery public key is `meta.recovery_pub` (new column in the format 3 migration text), checked against the hash the slots bind. Verification without the factor authenticates the outer layer and checks the class against the role history; `store verify --deep --with-cold-factor` opens the payloads.

What remains, and what to read first:

* The sub-key factor of a hardware record is bound to ONE credential (the one of the slot the handle unlocked through when the record was made or last rotated). A second holder's authenticator does not open it. Open: whether each daily slot should get its own sub-key wrap.
* Under standard nothing checks that the sub-key passphrase typed for a second cold key is the one used for the first; a different one makes two records with two passphrases. Open: try the offered passphrase against an existing cold record at creation.
* A cold record is opened through the vault only. `txn.OpenSecret` (used by the label layer to move a provisional owner's records) refuses a cold record (`ErrColdInTransaction`); a signing key stored under a provisional anchor in an earlier transaction than its verification key cannot be stored at all (the store needs the verification key to classify).
* A key kind that is not the signing key of a role (BLS, ITN, mnemonics, provider tokens, party and tailcat keys) is not classified and stays hot; the mnemonic of a cold role (`cc-cold.mnemonics`) is classified and sealed as cold (see the cold-key section).
* A verification key replaced after its signing key was classified is not re-classified (the store reads it at the next put or open).
* The recovery path checks the recovered key with `ports.VerificationKeyDeriver`; a key of a kind it cannot derive (KES, VRF) is refused, which is right for cold keys and means a cold role on a VRF or KES identity cannot be recovered.
* Real device: rows 28 to 31 of the table above. Nothing here has touched an authenticator.

## Gotchas: the upstream contract the code depends on

All verified against `gitmachtl/scripts` `Update-2026-04`. If a bump to `spo-scripts` changes any of these, the probes or validation that cite it break.

* **Scripts print signing keys.** `04c` prints the new KES `.skey` `cborHex` to stdout. Never capture, log or tee script output. `ScriptRunner` inherits the terminal and, under `--json`, sends script stdout to stderr.
* **Prompts read the terminal.** `ask()` reads from `$(tty)`, else `/dev/tty`. A prompt without a default loops forever without a terminal. `ENV_SKIP_PROMPT=YES` skips only the final transaction confirmation.
* **Config precedence.** `00_common.sh` sources `<scriptDir>/common.inc`, then `~/.common.inc`, then `./common.inc`. The workbench owns `./common.inc` (first line `# managed-by: spo-workbench`).
* **Offline mode needs an online-made transfer file.** In offline mode every `01_workOffline.sh` action, `attach` included, calls `readOfflineFile`, which exits unless `offlineTransfer.json` exists with non-empty `.protocol.parameters`. The engine's `_handoff_problems` checks this. The stand-ins originally missed it; the e2e test caught it.
* **KES counters.** `04c` writes `kes.counter-next` if absent, exits 2 when `kes.counter == kes.counter-next`, and sets `kes.counter` to N. `04d` requires them equal, issues `node-N.opcert`, increments `node.counter`, and sets `kes.counter-next` to N+1. **Every `04d` run increments the cold counter**, hence non-repeatable.
* **`offlineTransfer.json` shape.**
  * `.address` is keyed by the bech32 string (the `.addr` file content).
  * `.transactions[]` entries carry `txJSON`; `execute <n>` (1-based) deletes the entry on success.
  * `.files."<name>".base64` holds attachments.
  * `new` discards everything.
* **`04e ... next`** in light mode for a pool with no blocks expects counter 0 and exits 0.
* **File locking** is `chmod 400` (`file_lock`) / `600` (`file_unlock`).
* **Variants.** Mainnet and testnet script directories differ: the testnet one adds `04f_genBLSKeys.sh`, `13a_spoPoll.sh`, `13b_sendSpoPoll.sh` and example `common.inc` files; only mainnet ships `sha256sum_sposcripts.txt`.

## Conventions

* VCS: jj colocated with git. Develop on a change on top of `main`, `jj bookmark create <topic> -r @`, then `jj new main <topic> -m "merge: ..."` and `jj bookmark set main -r @`. Commit; leave pushing to the user.
* Runtime code is Python standard library only; `pytest` exists only in the test derivation. Adding a runtime dependency is a decision to record in [Orchestrator design](../explanation/orchestrator-design.md).
* Docs follow Diataxis; keep facts in one place. `docs/reference/` is the single source for CLI, config, workflow and state formats. Update it in the same change as the code.
* Subagents: pass an explicit `model` on every dispatch: `sonnet` for work, `opus` for review.

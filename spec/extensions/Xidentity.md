# Xidentity: object identity and per-operation witness verification

This spec is not upstream behaviour. It specifies [ADR 0010](../../docs/explanation/adr/0010-object-identity.md), decision 1 (every object has an identity that is a hash, and references are typed), the verifier part of decision 3 (a signer's answer is verified by one function per operation, against the identity that was demanded) and, in the sections "Key references and the signer directory" and "Directory rules", the local part of decision 3: `custody.KeyRef` is `{Role, Identity}` and `ports.SignerDirectory` says which connected signer answers. It is code in `spo/internal/domain/identity`, `spo/internal/domain/custody`, `spo/internal/ports` (`keyindex.go`), `spo/internal/app/keyring` and the directory in `spo/internal/adapters/native`. The store is keyed by anchor identity (decisions 2 and 4, in the section "Owners, labels and the identity-keyed store" below): `ports.Ref` is `{Anchor, Kind, Num}`, a name is a label, `ports.NamedStore` is the name-level view the use cases are written against, and `ports/labels` is the one resolver; `ports.KeyIndex` finds a key's records through the owner manifests.

Terms: an **identity** is a typed pair (kind, hash). An **spo-defined object** is one that `spo` itself defines (descriptors, records, audit events, manifests). An **exempt row** is bytes whose hash is defined outside this project (a transaction body, a metadata file, a text-envelope payload, a party envelope): their identity is the hash of the exact input bytes and they are never re-encoded.

Rows that the ADR marks unconfirmed are unconfirmed here too. None of them was checked against the ledger specification or a CIP text; the tests prove only that the new constructor agrees with the value the repository already computes. They are INV-004, INV-005 and the Calidus part of INV-005.

## Inputs

- **SPO-Xidentity-IN-001** An identity is read from its text form `<kind>:<lowercase hex>` (`ParseRef`; uppercase hexadecimal is refused) or from its binary form (`UnmarshalRef`, `ReadBinary`). An unknown kind, a hash of the wrong length for its kind, a non-hexadecimal hash, a length byte that disagrees with the bytes present and trailing bytes are refused.
- **SPO-Xidentity-IN-002** A key constructor takes a raw verification key of exactly the length of its key type (32 bytes; a BLS key 48 or 96) and refuses any other length.

## Refusals

- **SPO-Xidentity-PRE-001** `ContentOf` refuses a tag that is not in the registry (INV-008), including the bare tag of a kind that is mapped from JSON.
- **SPO-Xidentity-PRE-002** A role history refuses an unknown role, a non-key identity and an empty role set. A manifest refuses an unknown kind of owner, a missing anchor, an anchor that is not the member its owner kind's anchor rule names, a role outside the vocabulary of its owner kind, a number on an unnumbered role (so a second payment key at another number), a member of the wrong identity kind, a role and number listed twice. An identity may be listed under more than one role of one owner (INV-028).
- **SPO-Xidentity-PRE-003** `WalletAnchor` refuses a wallet with neither a payment nor a stake key, and every anchor function refuses an identity of the wrong kind.

## Invariants

- **SPO-Xidentity-INV-001** A reference is typed: an identity carries its kind, and two identities of different kinds are never equal even with equal hash bytes. A function that needs a kind (`Require`) refuses another. Identities are comparable with `==` and ordered by `Compare` (kind code, then hash bytes). There is one kind per spo-defined object kind (pool descriptor 12, witness collection 14, pending record 15, party identity document 16, audit event 17, owner manifest 18, role history 19, label 20, owner record 21, workspace settings 22, provider token 23), so a reference names the table a resolver consults. Kind codes are part of the binary form and are never reused or renumbered.
- **SPO-Xidentity-INV-002** The key-hash identity is Blake2b-224 of the 32-byte Ed25519 verification key, the credential hash of the ledger. It equals `txbuild.HashKey` and the pool id of `chain.PoolIDOf`.
- **SPO-Xidentity-INV-003** The native-script identity is Blake2b-224 of the tag byte `0x00` and the script CBOR as given (unconfirmed against the ledger specification). It equals the policy id the policy code computes (`native.scriptHash`).
- **SPO-Xidentity-INV-004** The VRF identity is Blake2b-256 of the 32-byte VRF verification key (unconfirmed against the ledger specification). It equals `pool.VrfHash`, the value of a pool registration certificate.
- **SPO-Xidentity-INV-005** KES, BLS and Catalyst voting keys are identified by Blake2b-256 of the raw verification key, a Calidus key by Blake2b-224 of it, by the project rule of ADR 0010 (all unconfirmed against the ledger and the CIPs). A Calidus identity equals the hash `cose.CalidusIDBytes` carries after its header byte. The number of a KES key is not part of its identity.
- **SPO-Xidentity-INV-006** The exact-bytes rows are Blake2b-256 of the input bytes with no tag and no re-encoding: a transaction id (of the transaction body bytes as built or received), a metadata or anchor file, the CBOR payload of a text envelope (`cborHex`, without the wrapper) and a sealed party envelope. A transaction body in a non-canonical encoding (an indefinite-length map), a metadata file with another key order and whitespace than a re-serialisation would give, and a certificate payload with indefinite-length items each keep the identity of their input bytes, and refuse the canonical check of INV-009 if they were put through it. The transaction id taken from a whole transaction is that of the exact bytes of its first element.
- **SPO-Xidentity-INV-007** The content hash of an spo-defined object is Blake2b-256 over the canonical CBOR (RFC 8949 section 4.2.1, core deterministic encoding) of the two-element array `[tag, value]`. It is the only way a content identity is derived, and the kind of the result is the kind bound to the tag. Equal values under two tags have two identities.
- **SPO-Xidentity-INV-008** Tags are fixed labels from one registry, bound one-to-one to a content kind (`spo/obj/v1/pool-descriptor/map1`, `.../witness-collection`, `.../pending-record`, `.../party-identity-document`, `.../audit-event`, `.../owner-manifest`, `.../role-history`, `.../owner-record`, `.../label`, `.../workspace-settings`, `.../provider-token`). A kind mapped from JSON has only the tag with the mapping version (`.../pool-descriptor/map1`); its bare tag is not registered, so one descriptor has one identity. A tag that is a prefix of another gives different identities for inputs constructed to collide under concatenation of tag and bytes (tested with a registered pair).
- **SPO-Xidentity-INV-009** The canonical check: decoding an spo-defined object re-encodes the decoded value and refuses (`ErrNotCanonical`) unless the bytes are equal. A longer integer head than needed, an indefinite length, map keys out of order, a duplicate map key, trailing bytes and a truncated item are refused. Items outside the model (floats, tags, simple values other than booleans and null) are refused as unsupported. Nesting is limited to 65 levels, and a value at that limit can still be hashed (the `[tag, value]` wrapper sits one level above). A head that claims a count larger than the bytes left, or than half of them for a map, is refused, and nothing is allocated from a claimed length beyond a small constant, so decoding allocates in proportion to the input. Text must be valid UTF-8: the domain encoder and decoder refuse it. `platform/seal` keeps its own library-backed encoder for associated data, which emits invalid UTF-8 as given; it is not changed (that could alter existing associated data), so the domain encoder is the stricter of the two and no spo-defined object can contain such a string. A differential test in `internal/archtest` (a deterministic random loop and a Go fuzz target) pins that the two encoders produce the same bytes for the shared value model and that `DecodeCanonical` accepts and rejects exactly what the library's strictest decoder plus a re-encode accepts and rejects, with the same value.
- **SPO-Xidentity-INV-010** The binary form of an identity is one length byte (the number of bytes that follow), the kind code and the hash. Its length is fixed per kind (1 + hash length), so a reader can check it and can skip an identity of a kind it does not know. The zero identity has no binary form.
- **SPO-Xidentity-INV-011** The fixed anchors that are pure functions: the anchor of a kind that has no owner is the content hash of `[tag, ""]`; the anchor of a label record is the content hash of `[label tag, [kind of owner, name]]`; the anchor of a pool, DRep and committee member is its key hash and that of a policy is its script hash. A wallet's anchor is its payment key hash when it has a payment key at creation or first import, otherwise its stake key hash.
- **SPO-Xidentity-INV-012** A role history holds the roles one key identity was ever used or imported in. The set only grows (`With`, `Merge`; there is no removal), and `Extends` checks that a history to be written is a superset of the stored one for the same identity (`ErrRoleHistoryShrunk`), for the store to call on every write. It reports its most sensitive role and whether it has a cold role (pool cold or committee cold). Its canonical encoding is `[identity, [role...]]` with the roles sorted, and decoding refuses non-canonical, unsorted, duplicate and unknown roles. The sensitivity order beyond "cold roles first" is a project choice.
- **SPO-Xidentity-INV-013** An owner manifest is immutable and content-hashed (INV-007 with the manifest tag, so its identity has the owner-manifest kind). It states its kind of owner, lists members by role and number, names its anchor and, from the second version on, its predecessor by hash, which must be of the owner-manifest kind. The role vocabulary is fixed per kind of owner, with a required identity kind per role: wallet `payment` and `stake` (key hash); pool `cold` (key hash), `vrf` (VRF key hash) and `kes` (KES key hash, the only numbered role); DRep `drep`; committee member `cold` and `hot`; policy `script` (script hash). The anchor must be the member of the anchor role: pool `cold`, DRep `drep`, committee `cold`, policy `script`, wallet `payment` when its first version has one and otherwise `stake`; it is the same anchor in every later version, so a stake-only wallet that gains a payment key keeps its stake anchor. `Add` returns the next version and refuses replacing a listed role and number (`ErrManifestAppend`); a removal is not expressible. `Extends` verifies that a version is the legitimate successor of another: same kind of owner and anchor, the predecessor's hash, every earlier member unchanged.
- **SPO-Xidentity-INV-014** `CheckAnchor` refuses a manifest whose anchor is not the one expected (`ErrAnchorMismatch`).

## Verifiers

- **SPO-Xidentity-SEC-001** A returned transaction witness is accepted only by `custody.VerifyTxWitness`: the verification key's Blake2b-224 hash must equal the demanded key-hash identity (else `ErrWitnessKey`) and the Ed25519 signature must verify over the transaction id (else `ErrWitnessSignature`). `VerifyTxWitnessOverTx` derives the id from the exact body bytes and refuses a claimed id that differs from them. `pool.Collection.Fill`, `party.VerifyWitness` and `txbuild.VerifyWitness` call it and hold no check of their own. A claimed id that differs from the body bytes is refused with its own error (`ErrTxIDMismatch`).
- **SPO-Xidentity-SEC-002** An operational certificate is accepted only by `custody.VerifyOpCert`: it is over the KES key, counter and period that were asked for, its cold key's hash is the demanded identity, and the cold signature verifies over KES key, counter and period. The operational certificate use case (`poolops`) verifies what the vault or the device returned this way against the stored cold key and the KES key, counter and period it asked for, before anything is stored.
- **SPO-Xidentity-SEC-003** CIP-36, CIP-88 and CIP-8 messages are accepted only by `custody.VerifyCip36`, `VerifyCip88` and `VerifyMessage`: the message is well formed and its signature verifies as `domain/cose` defines, and the key that signed it hashes to the demanded identity (the stake key, the pool id, the COSE key respectively), else `ErrMessageKey`. The Catalyst registration and the Calidus registration use cases verify the signer's answer this way against the demanded stake key and pool id: a valid registration made by another key is refused. A token-registry attestation that a signer returns to the registry use case is accepted only by `custody.VerifyRegistryAttestation`, against the policy's verification key when the workspace holds it, otherwise against the key hashes of the policy script's signature leaves; verifying entries read from a registry stays in `tokenmeta`, because no demand of `spo` stands behind them.
- **SPO-Xidentity-SEC-004** The hardware adapter verifies every witness, operational certificate, CIP-36 registration and CIP-88 registration its device returns through these functions and calls `ed25519.Verify` for none of them. A witness whose signing file carries no public key cannot be checked against the demanded key and is refused.

## Key references and the signer directory

- **SPO-Xidentity-IF-001** A key reference is `custody.KeyRef{Role, Identity}`: it carries no holder, owner name, device or party, and `String()` prints the role and the identity. `ports.SignerDirectory` maps a key reference to the signers connected now that report holding the key (`Connected`) and to the preferred one (`SignerFor`): the local vault (the keys it holds, found by identity), each attached hardware device with its own Profile (the keys it has stored hardware signing files for) and each co-signer party reachable through the envelope (the keys the slot assignment of ADR 0005 gives it, routed by fingerprint; its answer is deferred). No connected signer is `ports.ErrNoSignerFor`, or `ports.ErrNoHardwareSigner` when the stored records say the key is on a device and none is connected, the error users saw for an unavailable holder. A use case states a demand (key identity, role, operation, payload) and builds its plan from `Connected`; it asks for a capability of the signer returned (`hwkeys.IsHardware`: the signer takes the options of a device witness), never for where the key sits. Own-client remotes, announcements, proof of possession and blinded handles are not built here: they are one more kind of remote entry of the directory when the server stage comes.
- **SPO-Xidentity-IF-002** A use case turns today's (owner name, role) into a key identity once, at its edge, with `keyring.Resolve`: it reads the stored verification key of the name and applies the identity constructor of the role (key hash; VRF, KES, Catalyst and Calidus by their own rule), and refuses a name with no verification key (`ports.ErrNoVerificationKey`). `keyring.ResolveHeld` also says whether a signing key or a hardware signing file is stored under the name. Placement is not a property of a reference: `hw.holder()` is now `custody.Placement` (`PlaceVault`, `PlaceHardware`), the command option that says where a NEW key is generated (`custody.PlanGeneration(place, roles...)`).

## Directory rules

- **SPO-Xidentity-INV-015** The persisted witness slot (`pool.Slot`, the `regWitness` of a pool descriptor) carries the key it needs (role and key hash) and no holder. Its party is a fingerprint: JSON `partyFingerprint`, 40 hexadecimal digits, written only for an assigned slot. An old `holder` key is ignored on read. An old `party` key is read as a name and resolved through the party registry to a fingerprint when an existing collection is opened (`Collection.ResolveLegacyParties`); a name that no longer resolves leaves the slot unassigned and is reported by the use case; `party` is never written. `Slot.Name` forms such as `<pool>.node` are for display and export only, and the display prints the label of the fingerprint. A rotation of a co-signer's identity moves the unfilled slots of the coordinator's open collections to the new fingerprint (`Coordinator.OnRotate`).
- **SPO-Xidentity-INV-016** An operator's assignment is a routing instruction and wins over the directory: a slot assigned to a co-signer by fingerprint, or left to another signer by the descriptor (`ownerWitness` is not `local`, SPO-05c-INV-005), is not signed here even when its key is also in this workspace; with `AllowPending` it is left open, without it the plan refuses it. The directory chooses only among slots with no assignment. When several connected signers hold one key identity the default order follows the upstream corpus: hardware, then vault, then remote (SPO-Pfiles-INV-002, SPO-15-INV-002: with both a signing key and a hardware file the hardware wins, and with no device connected the plan refuses rather than falling back to the signing key); for an operational certificate the vault comes first (SPO-04d-INV-004) (`ports.SignerForOperation`). One hook (`Signers.Prefer`) is where an operator preference will act (there is no label attribute yet). With `AllowPending` a slot on a device is left for the operator's later run, as before. One verification key is a member of one owner (INV-019), so a key never answers through another name. No package under `internal/app` names a holder type, a holder constant or a holder field (an architecture test reads the sources).
- **SPO-Xidentity-PRE-004** The cold-key rule is keyed on the roles recorded for the key identity, whatever role the demand names, and fails closed: a key identity that was ever recorded in a cold role (pool cold, committee cold), or whose history cannot be read for certain (a verification key record that cannot be read), is not demanded of a network remote. The coordinator does not create a request for a network transport (the refusal is the open one for a cold role demanded, `ErrColdKeyOverNetwork`) and the signer refuses again on receipt with the silent refusal of ADR 0005; a carried file may answer. The directory withholds a network remote for such a key too (`ports.ErrColdOverNetwork`), but no `cmd/spo` wiring has a remote directory entry yet, so in this build the coordinator is the sending-side check and that branch is exercised by tests only. The history is the stored `role-history` record of the identity (INV-020, `ports.RoleHistoryOf` reads it through the key index); a record that cannot be read fails the rule closed. It is read before a store transaction opens, never inside one.
- **SPO-Xidentity-PRE-005** A device that is not connected when the plan is made offers an empty Profile naming the cause, so a demand for its keys fails in the plan, before the device is asked anything and before the operator is. A hardware signing file that holds another account's public key is refused at the same point (`ports.ErrWrongHardwareFile`) and again before any tool call that would use it.

## More verifiers

- **SPO-Xidentity-SEC-005** An answer is verified against the demanded identity, whoever made it: a hardware answer made with a signing file whose public key is another account's is refused (`hwcli.ErrWrongKey`), and a remote answer made by another key than the slot's is refused by `Collection.Fill` and `party.VerifyWitness`. A key the vault finds for an identity is checked to be that key before anything is signed.
- **SPO-Xidentity-SEC-006** A demand carries the full input of the operation: the vault signer is handed the transaction (body and auxiliary data), derives the transaction id from the bytes it was given (`identity.TxIDOfTx`) and refuses a claimed id that is not the id of those bytes; it signs the id it derived, never a hash handed to it. An operational certificate is made from the KES key, counter and period of the demand; CIP-36, CIP-88 and CIP-8 signers take the registration or the message itself. The answers the use cases themselves check, besides the transaction witness and the registrations, are the pool witness file (`pool witness sign`, `VerifyTxWitnessOverTx`) and a Calidus text signature (`custody.VerifyText`). One signer still takes a hash: the token-registry attestation (`SignRegistryMessages`) signs 32-byte messages that the registry use case derives; handing it the entry to rebuild them from remains to be done.
- **SPO-Xidentity-SEC-007** The generic CIP-8 message-signing paths refuse a payload that starts with `spo-` or `spo/` (`relaybind.IsReserved`; `relaybind.ErrReservedPayload`), on the payload before any hashing, so that only the typed relay statement methods of ADR 0014 (SPO-Xrelaybind-SEC-016, SEC-017) can produce one. The paths are `native.VaultSignatures.SignMessage`, `hwcli.Session.SignMessage` and `hwcli.Lazy.SignMessage` (the lazy path refuses before the device is opened). The guard is the first check, before the role, the address and the key. An ordinary message, and a near miss of the prefix (`spo`, `Spo-`, ` spo-`), still signs. The registrations that sign a digest of their own (`hwcli.Session.SignCip88`) use the unguarded internal path: a Blake2b digest has no meaning as text, and a refusal of one that began with the prefix would be a one-in-four-billion failure of an honest registration. **Corrected after the security review:** this list was incomplete. A fourth route signs caller-chosen bytes with a key that is also a wallet key and is not a COSE message path at all: the Calidus `sign` (`app/poolkey.SignWithCalidusKey`, `native.VaultSignatures.SignText`, `pool calidus sign`), a raw Ed25519 signature over the text, with a key that is the payment key 0/0 of its mnemonic. The reserved-prefix guard does not cover it (a signature over a `Sig_structure` does not start with `spo-`); SPO-Xidentity-SEC-008 does.
- **SPO-Xidentity-SEC-008** The Calidus `sign` signs a text only and refuses the signing input of a relay statement (extension of SPO-15-IF-006 and SPO-15-EXT-006, which define the input as a text: upstream passes it to `cardano-signer sign --data-text`, and a byte string that is not UTF-8 is not a text there; no requirement of the upstream corpus is changed for any text). `ports.CheckSignableText` refuses data that is not valid UTF-8 (`ports.ErrNotText`; a COSE Sig_structure starts with `0x84` or `0x85`, never a UTF-8 lead byte) and, as defence in depth, data for which `relaybind.LooksLikeSignedStatementInput` is true (`relaybind.ErrRawStatementInput`; SPO-Xrelaybind-SEC-018). It is applied in the adapter (`native.VaultSignatures.SignText`, before any key is opened), in the use case (`SignWithCalidusKey.Run`, before the store is read and before a signer is asked) and in the command (`pool calidus sign`, before the workspace is unlocked); each has its own test. Reason: a raw signature over the Sig_structure of a binding, made by the Calidus key of a mnemonic (its payment key 0/0), wrapped by anyone into a `COSE_Sign1`, verifies at the relay as a binding of the operator's payment key hash to an attacker's device. The routes that sign a digest or a typed body only (the registrations, the registry messages, the transaction witness, the device key's own arrays) carry no caller-chosen bytes; the table is in ADR 0014.

## Owners, labels and the identity-keyed store

This section specifies ADR 0010 decisions 2 and 4: owners are aggregates with an anchor identity, names are labels, records are keyed by `(anchor, kind, number)`, and a store of the name-keyed format is migrated. The code is `spo/internal/ports` (`store.go`, `keyindex.go`), `spo/internal/ports/labels` (the resolver, the records of the identity layer, the migration plan), `spo/internal/platform/seal` (format 2 of a record), `spo/internal/adapters/sqlitestore` (the store, `migrate.go`), `spo/test/plainstore` (the test-only directory store, name-based on disk) and `spo/internal/adapters/cli` (`rename.go`, `workspace migrate`).

Terms: a **label** names an owner (a kind of owner and a name) or a named record; an **owner record** points at the newest **manifest** of an owner; a **provisional owner** is an owner whose anchoring key does not exist yet; a **named record** is a record keyed by a string the use case or the protocol chooses (a transaction id, a transfer file name, `state`) and owned by no one.

- **SPO-Xidentity-INV-017** A record is keyed by `(anchor identity, kind, number)`: `ports.Ref` is `{Anchor, Kind, Num}` and the store never sees a name. A use case holds a `ports.NamedRef` and `ports/labels` resolves it to a `Ref` through the label records before the store is called; the directory stores (`upstreamdir`, `exportdir`) and the test-only plain store handle names at their own edge. The sealed record of format 2 binds the anchor identity (binary form) and the number into its associated data, the canonical CBOR `[format version 2, genesis nonce, record id, kind, anchor, number, class, record version, payload format]`; its sealed owner blob, padded to 160 bytes, holds the canonical CBOR `[anchor, kind, number]`; its lookup tag is the HMAC under the index key over the anchor, the kind and the number (namespace `record-ref/v2`). No name is in the associated data, the owner blob or the tag. The audit rows keep the encoding of format 1 (`seal.LegacyRecordFormat`); the key slots, the audit chain and the key epoch are unchanged.
- **SPO-Xidentity-INV-018** A `label` record maps `(group, name)` to an anchor; its own anchor is the content hash of `[label tag, [group, name]]`, so the name is only in the sealed payload, and the group is a kind of owner or, for a named record, a store kind. A second label for a name, or for an owner's anchor, is refused showing both. The set of `label` records is the label index; a label is an ordinary record. A wallet's label also records whether its payment account is kept under `<name>.payment` (a wallet made by 03a) or under `<name>` (a key-only address made by 02): the one trace of the upstream layout, kept so that a listing, an export and the plain directory store give the files the names the scripts expect.
- **SPO-Xidentity-INV-019** An owner exists as an `owner` record keyed `(anchor, owner kind, 0)` that holds the hash of its newest manifest and the aliases of any merge. The first verification key that anchors an owner (a pool's cold key, a wallet's payment key or its stake key, a DRep's key, a committee member's cold key, a policy's id) creates the owner, its first manifest and its label by the anchor rule (INV-011); a further key (a stake key, a KES key by number, a VRF key, a policy's key) writes a new manifest version that names its predecessor and rewrites the owner record. A manifest never replaces or removes a member (`ErrManifestAppend`). An identity is a member of one owner: a second claim, in a write or in an import, is refused with both owners shown (`ErrMembership`), also when a role of one owner would take an identity another owner has. A record of an owner whose anchoring key does not exist yet (a pool descriptor written before the cold key, a wallet's address file, a VRF key generated first) is kept under a provisional anchor (a derived named anchor) with the label; the anchoring key moves the records to the real anchor in the same transaction, and the verification keys kept meanwhile join the manifest. A verification key record that does not parse is kept as a record of its owner and lists no identity. Policy owners list the key hash (`key`) beside the script id so that the signer finds a policy key by identity; a Calidus key and a Catalyst voting key belong to no owner and are found by reading their verification key records.
- **SPO-Xidentity-INV-020** The role history of a key identity is a `role-history` record keyed by the identity as its own anchor and number 0. Creating or importing a key records its role; every write goes through `RoleHistory.Extends`, so the set only grows. `ports.RoleHistoryOf` reads the record. Recording a role when a key is used in a role at planning time is not built.
- **SPO-Xidentity-INV-021** A rename replaces one `label` record and no other record: the sealed bytes (payload, wrapped key, owner blob, lookup tag, version) of every other record, the owner record and the manifests are unchanged. A name that another owner of the kind has is refused. The plain directory store moves the files of the owner.
- **SPO-Xidentity-INV-022** A named record is keyed by the content hash of `[named-record tag, [group, name]]` as its anchor, with its label in the group of its kind (a Calidus key's records and a voting key's records share the family group of their name, so their verification key, signing key and hardware signing file have one anchor). Deleting the last record of a name deletes its label. A provider token is a named record. An upstream-encrypted signing key is keyed by the identity of the verification key it pairs with; with no verification key it is quarantined, a named record that no signer can use. Deviations from ADR 0010: the fixed ownerless anchor of provider tokens and settings is not used (a token is a named record), and a record keyed by its own content identity (transactions, envelopes, collections, audit events) is not built: the strings the use cases and protocols choose key the records, and a pending record names its pool inside its payload.
- **SPO-Xidentity-INV-023** The integrity check runs at migration and on every open of the store (`labels.Check`): each owner record parses and names a stored manifest that hashes to the id it names, is bound to the anchor of the owner record and has its predecessors; membership is unique across owners and aliases; each label is keyed by its own group and name and at most one label names an anchor; every owner has a label; and for every member of every manifest the verification key stored for it hashes to the identity the manifest lists. A failure refuses the open, naming both owners where two are involved. `OpenOptions.SkipVerify` skips it, as it skips the verification of the chain.
- **SPO-Xidentity-INV-024** Migration (`spo workspace migrate`, `sqlitestore.Migrate`) converts a store of format 1 in one transaction. The opener refuses a store of format 1 before it derives a key, with `ErrLegacyFormat`, which names the command. Records keep their random ids; each is opened under its old associated data and sealed again under the same master key with a fresh payload nonce, its data key re-wrapped, its owner blob rewritten from the anchor and number and its lookup tag recomputed, at the next record version (the audit chain wants each change to be the next version); the master key and the data keys do not change. Owners and anchors come from the keys present by the anchor rule (`labels.Derive` over the stems of the old store; a stem `<w>.payment` and a stem `<w>` are one wallet), and the `label`, `owner`, manifest and role-history records are written. Two records that map to one reference merge when their bytes are identical and are refused otherwise. An upstream-encrypted signing key takes its identity from the sibling verification key or is quarantined. Each pool descriptor's owners, reward account and open-registration payer are rewritten from names to key hashes (`pool.Descriptor.MapRefs`) and the slots of its witness collection take the fingerprint of their party from the registry; a party that no longer resolves leaves the slot unassigned and is listed. One audit row records the migration. Before the transaction the file is copied beside it (`<file>.pre-migrate-v1`, mode 0600) and the report says where; a failure anywhere leaves the original untouched (tested with an injected failure), and a refused plan changes nothing and makes no copy. The plan's identity layer is checked as INV-023 checks it before anything is written. A pool descriptor still holds names in its pending-record and slot-name text; the identity references are the three above.
- **SPO-Xidentity-PRE-006** A migration refuses, with the list of every problem and without changing anything: a name in a pool descriptor that resolves to no wallet or to a wallet without the key the reference needs; a descriptor whose pool id is not the hash of the cold key under its name; an identity that would be a member of two owners; two records that map to one reference and differ; a key record that does not parse; a record of a kind the version does not know. `--quarantine <pool>` lets it go on for a pool whose own problems those are: the pool's descriptor keeps the names it had and the problems are listed as quarantined; a colliding pool's records are kept apart as named records. A problem of a wallet is never quarantined.
- **SPO-Xidentity-INV-025** The report of a migration lists the backup, the number of records converted, merged and added, the owners, the descriptors rewritten, the quarantined pools and the unassigned slots.
- **SPO-Xidentity-INV-026** An export writes the labels back: a reference in a pool descriptor that is an identity (an owner, the reward account, the payer, as `MapRefs` names them) is replaced by the label of the owner that lists it, `<label>.payment` for the payer when the wallet keeps its payment account so. A reference whose owner has no label is left. Reading an upstream directory resolves each name to an identity from the directory's files (`labels.Derive`), and a name that would resolve to a stake key another name resolved to, a pool id that is not the hash of the cold key and a witness slot whose recorded key hash is not that of the wallet's stake key are refused (Xmulti INV-007).
- **SPO-Xidentity-IF-003** `spo <kind> rename <old> <new>` for `wallet`, `pool`, `drep`, `committee` and `policy` rewrites one label (INV-021). It asks for the workspace passphrase and nothing else.
- **SPO-Xidentity-IF-004** `spo <kind> merge <name> --from DIR [--as NAME]` records the anchor of the owner `NAME` of an upstream directory as an alias of the owner `<name>` of the workspace, when the two have identical member sets (differing sets cannot merge: add the missing member first). The kept anchor does not change, and an import that carries the alias resolves to the kept owner. The owners are the residual case of the wallet anchor rule (INV-011): a wallet made stake-only that gained a payment key is anchored by its stake key, the directory's wallet by its payment key.
- **SPO-Xidentity-IF-005** `spo workspace migrate [--quarantine POOL]...` converts a workspace of the old format (INV-024) and says where the copy is; every other command on such a workspace refuses with `ErrLegacyFormat`.
- **SPO-Xidentity-INV-027** A label name is plain: it follows the rules of `ports.NamedRef` (letters, digits, `-`, `_`, single dots; no path, shell or control characters; at most 128 bytes) and is never the text form of an identity (`<kind>:<lowercase hex>`, as `identity.ParseRef` reads it), because such a name resolves through membership to an owner. One validator (`labels.CheckLabelName`) is called by every write of a label (rename, create, provisional owner, named record, migration plan, import), and the check of every open reports a stored label whose name has that form.
- **SPO-Xidentity-INV-028** One key may be a member under more than one role of one owner's manifest (a wallet whose payment and stake keys are one key: the anchor is the payment key when the wallet has one, and the key index returns a home per role); one key is never a member of two owners (INV-019). The role history of the key holds every role.
- **SPO-Xidentity-INV-029** For every manifest member that has a role, a role history that contains the role must be stored; the check of every open refuses a store where it is missing. The key index fails closed for a member of an owner that has no stored history (`ErrCorrupt`), so the cold-key rule on the signing and request paths refuses such a key (the signer also refuses a held key whose history is unknown); the migration plan refuses when a role history cannot be built.
- **SPO-Xidentity-PRE-007** An owner that has records but no anchoring key (a provisional owner) cannot be renamed: the refusal says to add its key first. A rename never moves an anchor.
- **SPO-Xidentity-INV-030** A handle opened for the migration (`OpenLegacy`) can only migrate: `View`, `Update`, `Open` and every write that changes the file (a rekey, a slot change) return `ErrLegacyFormat`; `Migrate` and the read-only planning it needs are the only users. A migration chooses, of records that collide on one reference, the one whose stem sorts first, not the one with the lowest record id; identical ones merge into it, differing ones refuse, and only wallets collide (`<w>` and `<w>.payment`), so that refusal is not quarantinable.
- **SPO-Xidentity-INV-031** Verification of the file (`store verify`, `VerifyFile`, `VerifyFilePayloads`) runs the check of the identity layer of INV-023 after the verification of the chain, and a failure is an `ErrVerify` that wraps `labels.ErrCorrupt`; a store that every open refuses cannot pass verification. A row of format 1 put into a migrated store is refused by open and by verification.

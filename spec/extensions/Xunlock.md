# Xunlock: unlock factors, slot-key derivation and unlock policy

This spec is not upstream behaviour. It specifies the parts of [ADR 0011](../../docs/explanation/adr/0011-key-custody-and-unlock.md) decisions 3, 4, 6, 8 and 9 that do not touch the store file: the factor port, the adapter that drives the libfido2 command-line tools, the slot-key and sub-key derivations, and the policy check of a slot table. It also specifies the Vault and KMS backend factor of decision 5 (`ports.KeyWrapBackend`, `adapters/vaultkms`, the backend composite slot and its commands). The cold-role sub-key use and rotation are specified in [Xcustody](Xcustody.md). The backend clients were tested against in-process stand-ins only, never against a real Vault, OpenBao or AWS account.

Terms: a **factor** is a secret a person holds or a device reproduces; a **factor output** is its 32 bytes. A **factor id** names a factor inside a slot (for FIDO2, `ports.FactorIDOf` of the credential id). A **slot** wraps the master key under a key derived from factor outputs. A **table** is the slots of a workspace with its policy (`standard`, `hardware`, `strict`). The **libfido2 tools** are `fido2-token`, `fido2-cred` and `fido2-assert`, pinned in the toolchain manifest; the behaviour below is read from their man pages and source at libfido2 1.16.0 (the version the flake pins; 1.17.0 was read as well) and has not been run against a device.

## Interface

- **SPO-Xunlock-IF-001** `ports.FactorSource` has `Profile`, `Enrol` and `Assert`. `Enrol` takes a relying-party id, an optional device and an optional PIN (user verification is always required), and returns the credential id, the credProtect level the authenticator confirmed, the `getInfo` version strings, the factor id and the result of the touch probe. `Assert` takes a credential id, a relying-party id, a current 32-byte salt, an optional next 32-byte salt, a presence flag and an optional device and PIN (user verification is always required and cannot be switched off), and returns the output for each salt together with the UP and UV flags.
- **SPO-Xunlock-IF-002** A source reports a `FactorProfile` read from the device (for the libfido2 tools, `fido2-token -I`: the extension, version and option lines): hmac-secret, two salts, credProtect, CTAP 2.1, a PIN set, built-in verification. `Enrol` and `Assert` check it with `ports.CheckFactorProfile` before `fido2-cred` or `fido2-assert` runs. `ports.CheckFactorProfile` names every capability an operation needs that the profile lacks, and the caller runs it before it asks for a PIN or a touch.
- **SPO-Xunlock-IF-003** The adapter `adapters/fido2cli` runs `fido2-token -L` (device choice), `fido2-token -I` (getInfo), `fido2-cred -M` (enrolment) and `fido2-assert -G` (assertion) through `platform/execx`, from the paths of the toolchain manifest. With no device given it uses the one device `fido2-token -L` lists and refuses none or several.
- **SPO-Xunlock-IF-004** The unlock policies are `standard`, `hardware` and `strict`; any other value is refused.
- **SPO-Xunlock-IF-006** `ports.PINChecker` is the optional capability to check an authenticator PIN without making a credential or asking for a touch: `fido2cli.Source.CheckPIN` runs an assertion with `-t up=false` and the PIN for a credential id that cannot exist; a wrong PIN is `ErrFactorPIN`, and `ErrFactorNoCredential` means the PIN was right. `sqlitestore.PreflightFactors` uses it, after the capability check of every authenticator, to verify every PIN a rotation will use before any credential is made. The order (the PIN token is obtained before the credential lookup) is the CTAP 2.1 flow as libfido2 implements it and is not confirmed on a device.
- **SPO-Xunlock-IF-005** `unlock.Check` checks a whole slot table against its policy and returns every violated rule, each with a rule code and the slot it concerns. It is the one check that slot add, policy change, rekey and the opener use.
- **SPO-Xunlock-IF-007** `ports.KeyWrapBackend` has `Ref`, `Wrap` and `Unwrap`. `Wrap` takes the 32-byte secret B in guarded memory and a `ports.WrapContext` (the 16-byte genesis nonce and the 16-byte slot id) and returns a wrapped blob of at most 4096 bytes; `Unwrap` takes the blob and the context and returns exactly 32 bytes in guarded memory. Every backend passes the contract suite `porttest.KeyWrapContract`: a wrap opens under its own context only (another nonce, another slot id, the two swapped and a short id are refused), a changed, truncated, extended, empty or oversized blob is refused, a B that is not 32 bytes is not wrapped, and no error contains B or the credential. `Ref` is the backend's public reference (kind `vault-transit` or `aws-kms`, address, Vault namespace, key), with no credential.
- **SPO-Xunlock-IF-008** `vaultkms.Vault` is a Vault Transit client on the standard library (no Vault SDK). It reads the key's configuration (`GET /v1/<mount>/keys/<key>`) once per client, then wraps with `POST /v1/<mount>/encrypt/<key>` and unwraps with `POST /v1/<mount>/decrypt/<key>`, sending B as `plaintext` and the context as `associated_data` (never `context`). It sends the token in `X-Vault-Token` and, when the reference has one, the namespace in `X-Vault-Namespace`. Before the token is used for anything else it is looked up once per client (`GET /v1/auth/token/lookup-self`, SPO-Xunlock-PRE-049).
- **SPO-Xunlock-IF-009** The Vault token is the client's: `VAULT_TOKEN`, else the token helper file (`token_file`, default `$HOME/.vault-token`, read as SPO-Xunlock-PRE-048 says, at most 16 KiB), or with `auth = "jwt"` a login at `POST /v1/auth/<jwt_mount>/login` with `role` and the JWT read from `jwt_file` (read the same way). A token is printable ASCII without spaces, at most 4096 bytes. It is held in guarded memory for the life of the client and destroyed when the client is closed.
- **SPO-Xunlock-IF-010** `vaultkms.KMS` is an AWS KMS client on the standard library (no AWS SDK). It calls `TrentService.Encrypt` and `TrentService.Decrypt` (JSON 1.1) with the key ARN as `KeyId` and the encryption context, and signs every request with Signature Version 4 written by hand (host, `content-type`, `x-amz-date`, `x-amz-security-token` and `x-amz-target` signed). The signer reproduces the published SigV4 examples (the `get-vanilla` case of the AWS test suite, the IAM `ListUsers` example and the signing-key example, recalled from memory) and agrees with a second signer written in the test, which the stand-in KMS uses to check every request.
- **SPO-Xunlock-IF-011** Short-lived AWS credentials come from a web identity token (`web_identity_token_file` and `role_arn`, or `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN`) exchanged at STS `AssumeRoleWithWebIdentity` (an unsigned form POST, `DurationSeconds=900`), or from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` in the environment. The STS endpoint is the public one of the key ARN's partition and region unless `private_sts_endpoint` is set (SPO-Xunlock-PRE-046). In the XML answer, `SecretAccessKey` and `SessionToken` must each occur exactly once as plain text (no markup, entity or CDATA) and are copied from the answer's bytes into guarded memory; the structure (root element, nesting, `AccessKeyId`, `Expiration`, and that the two texts are the ones inside `Credentials`) is decoded strictly, with no entities, from a copy in which those two texts are blanked. The STS credentials are kept until a minute before they expire.
- **SPO-Xunlock-IF-012** `spo.toml` has the optional sections `[vault]` (`address`, `namespace`, `mount` default `transit`, `key`, `ca_file`, `auth` `token` or `jwt`, `token_file`, `jwt_mount`, `jwt_role`, `jwt_file`, `timeout_seconds` 1 to 600, `allow_loopback_http` true or false) and `[kms]` (`key_arn`, `private_endpoint`, `private_ca_file`, `private_sts_endpoint`, `private_sts_ca_file`, `role_arn`, `web_identity_token_file`, `role_session_name`, `timeout_seconds`, `allow_loopback_http`). Neither has a key for a token or an access key; an unknown key (the earlier `endpoint`, `sts_endpoint` and shared `ca_file` of `[kms]` included) is refused, and a `private_*ca_file` without its `private_*endpoint` is refused. `[vault]` address, namespace, mount and key and `[kms]` key ARN and endpoint (the public endpoint of the ARN's region, or `private_endpoint`) are read when a slot is added, and they are the authority at every unlock: the reference a slot stores is a claim, checked against them before it is used (SPO-Xunlock-PRE-045). The sections are kept when the file is rewritten.

## Inputs

- **SPO-Xunlock-IN-001** A salt is 32 bytes. An assertion with a next salt sends both to the authenticator as one 64-byte value (the current salt first), which libfido2 passes as the two salts of the hmac-secret extension, and splits the 64-byte answer into the output for the current salt and the output for the next. An assertion with one salt sends 32 bytes and gets 32.
- **SPO-Xunlock-IN-002** The factor id of a FIDO2 credential is SHA-256 over the label `spo/factor-id/fido2-credential`, a zero byte and the credential id: 32 bytes, the same wherever the credential id is known.
- **SPO-Xunlock-IN-004** The wrap context of a backend factor is the genesis nonce and the slot id (ADR 0011 decision 5). For Vault it is sent as `associated_data`, the base64 of the canonical CBOR of `[nonce, slot id]` (35 bytes: `0x82 0x50 nonce 0x50 slot id`); for KMS it is the encryption context `{"spo-genesis": <nonce hex>, "spo-slot": <slot id hex>}`, lower-case hex. Ids of another length are refused.
- **SPO-Xunlock-IN-003** The inputs of a slot key are factor outputs of exactly 32 bytes each, given in the canonical order: ascending by factor kind code (passphrase 1, recovery 2, fido2 3, backend 4), then by factor id bytes, with no repeat. Another length, another order or a repeated factor is refused.

## Outputs

- **SPO-Xunlock-OUT-001** The key of a `fido2-hmac` or `composite` slot is HKDF-SHA-256 (RFC 5869) with IKM the concatenation, in order, of `uint32_be(len) || output`; salt the 16-byte genesis nonce; info the canonical CBOR of `["spo/slot-key", format version, slot id, slot kind, [[factor kind, factor id], ...]]`. A `fido2-hmac` slot is the one-factor case. The derivation matches fixed vectors computed in Python by a second implementation.
- **SPO-Xunlock-OUT-002** The associated data of such a slot is the canonical CBOR of `["spo/slot-ad", format version, genesis nonce, slot id, slot kind, [[factor kind, factor id, params], ...], hash of the recovery public key, commitment]`, where the params are the Argon2id parameters and salt of a passphrase factor, the credential id, relying-party id, hmac-secret salt and touch-probe result of a FIDO2 factor, and the backend kind, address, namespace, key reference and wrapped secret of a backend factor (SPO-Xunlock-OUT-018). The commitment is the HMAC-SHA-256 of the slot key over the slot-commit label, as for the older kinds, and is compared before the AEAD. A change of any bound value makes the slot fail to open.
- **SPO-Xunlock-OUT-003** The cold-role sub-key is HKDF-SHA-256 with IKM one 32-byte factor output, salt the genesis nonce, info `uint32_be(format version) || "cold-subkey" || len(identity) as one byte || identity`, where the record identity is 28 or 32 bytes. It matches a fixed vector computed in Python.
- **SPO-Xunlock-OUT-004** `Enrol` returns the credential id read from `fido2-cred -M`, the credProtect level read from the extension map of its authenticator data, the version strings read from `fido2-token -I`, `ports.FactorIDOf` of the credential id, and the touch-probe result.
- **SPO-Xunlock-OUT-006** The touch probe records "touch not enforced" for an answer that returns an output, whatever its flags; "touch enforced" only for a named refusal of the request (`FIDO_ERR_UP_REQUIRED`, `FIDO_ERR_OPERATION_DENIED`); a PIN error or a missing device ends the enrolment; any other failure (a deadline, a usage error, malformed output) records "touch enforcement not confirmed", which a listing shows as not confirmed enforced. The probe runs whether the PIN is the caller's, the tool prompts for it, or the authenticator verifies the user itself; its result is stored with the factor (`seal.FactorParams.Touch`), bound in the slot's associated data (OUT-002) and shown by `workspace slot list`.
- **SPO-Xunlock-OUT-007** The cold-role sub-key under a Vault or KMS composite is HKDF-SHA-256 with IKM the ordered factor outputs each as `uint32_be(len) || output`, salt the genesis nonce and the info of OUT-003, the factors in canonical order and distinct; it matches a fixed vector computed in Python.
- **SPO-Xunlock-OUT-008** A store of format 2 is converted to format 3 by one transaction: the slot table is rebuilt with the kinds `passphrase`, `recovery`, `fido2-hmac` and `composite` and the columns `bound`, `rec_hash` and `factors`, `meta.policy` is `standard`, no record is re-sealed (the record encoding stays format 2 and the genesis nonce is the existing workspace id), the passphrase and recovery slots are carried over unchanged as legacy slots (the associated data they were made with), one audit row records the migration and the slot-set hash, and a copy of the sealed file named `<file>.pre-migrate-v2` (mode 0600, created exclusively) is made first.
- **SPO-Xunlock-OUT-009** Opening through a `fido2-hmac` or `composite` slot asserts every factor of a slot the caller can present, in the slot's order, checks the source's profile before it asks for a PIN, derives the slot key as in SPO-Xunlock-OUT-001 and accepts a master key only of the current key epoch. A slot whose authenticator does not hold the credential is skipped; a wrong PIN ends the open.
- **SPO-Xunlock-OUT-010** A rotation draws a new master key and a fresh data key for every record, re-encrypts every payload, writes the table of its plan with its policy and a recovery key (none under `strict`), appends a rollover row and a `rotate` row, and commits in one transaction. It makes no copy of the file: a copy opens with the credentials the rotation revokes. `RotatePlan.KeepCopy` (`workspace rotate --keep-copy FILE`) asks for one explicitly (created exclusively, mode 0600, removed again when the rotation fails, and the command says that it opens with the OLD credentials and is to be destroyed once the new factors are confirmed).
- **SPO-Xunlock-OUT-011** In store format 3 a slot's associated data binds the workspace policy: `["spo/slot-ad/2", format version, genesis nonce, slot id, slot kind, factor entries, recovery public key hash, policy, commitment]` for the two new kinds, and `["spo/slot-ad/pr", 3, workspace id, slot id, kind, kdf, policy, recovery public key hash, commitment]` for a bound passphrase or recovery slot. The slot-set hash of an audit row is `["spo/slotset/3", policy, rows]`.
- **SPO-Xunlock-OUT-012** The recovery key pair is X25519 with the private scalar HKDF-SHA-256 (no salt) of the recovery key under info `spo/recovery-hpke-x25519` for `standard`, and of the slot key of the recovery composite under info `spo/recovery-hpke-x25519/hardware` for `hardware`; so under `hardware` the recovery key alone derives another key and cannot reproduce the hash bound in the slots. The recovery factor of a hardware composite has the id SHA-256 of a label and the composite's slot id (the hash cannot be its id, because it derives from the slot key).
- **SPO-Xunlock-OUT-013** `spo workspace rotate --policy standard|hardware|strict` enrols the authenticators it needs (`--fido2-device` for the daily one, `--recovery-device` for the recovery composite under `hardware`, which must differ), presents the current recovery credential first (`--recovery-key-in-fd` or a prompt, and under a hardware workspace the recovery authenticator `--current-recovery-device` with its PIN), checks the PIN of every authenticator it will enrol before it makes any credential (the daily one from `--fido2-pin-fd`, the recovery one from `--recovery-pin-fd` or a prompt that names the device, never the daily PIN for it), rotates as SPO-Xunlock-OUT-010 says, and delivers the new recovery key as `store passphrase change` does (none under `strict`, which needs `--yes-strict`). `workspace slot list` and `workspace policy show` read the table without any key. `workspace slot add-fido2` enrols an authenticator and adds a `fido2-hmac` slot. `workspace policy set --policy ...` is the same operation. "Two different authenticators" is checked by device path and credential only: one token unplugged and plugged again as the second would pass, and the documentation says so.
- **SPO-Xunlock-OUT-014** `store backup` of a workspace under the `standard` policy prints, after the verified copy, a warning that whoever holds the copy can guess the passphrase offline, bounded only by the Argon2id cost (ADR 0011 decision 6); under `hardware` and `strict` it prints none. A backup of a workspace that unlocks through FIDO2 factors is verified through those factors.
- **SPO-Xunlock-OUT-015** `workspace init --policy hardware|strict` creates the workspace under that policy in one command: no passphrase is asked, the workspace is first made with a random passphrase and recovery key that exist only in the process and are destroyed, and the rotation of OUT-013 replaces every slot; any failure removes the files the run created.
- **SPO-Xunlock-OUT-017** A rotation (`Rotate`) writes, in the audit row of its slots, one event `["slot-removed", kind, slot id]` for each slot of the old table whose id the new table does not carry: a strict rotation by one daily factor therefore names every slot of the other holders that it removed. `workspace slot remove` writes the same event for the one slot it removes. The events are sealed in the audit chain with the rest of the row and are read back by opening the workspace (`openEvent`); they hold slot kinds and ids, never a factor.
- **SPO-Xunlock-OUT-016** `workspace slot remove <id>` removes a slot by a rotation that re-creates every other slot with its factors present (the passphrase, the authenticators, the recovery key and composite; a recovery slot or composite that stays gets a new recovery key), after presenting the current recovery credential. The table that would remain is checked with `unlock.Check` before any authenticator is asked: the last passphrase or recovery slot of `standard`, and under `hardware` and `strict` the last slot besides the recovery composite (rule `daily-slot`), cannot be removed. The audit chain records a `slot-removed` event beside the `rotate` row. A FIDO2 slot that stays is re-created with a fresh hmac-secret salt (one two-salt assertion proves the old and yields the new output), so an output captured earlier does not survive.
- **SPO-Xunlock-OUT-005** `Assert` returns the UP and UV flags read from the authenticator data of the assertion, not the flags asked for.
- **SPO-Xunlock-OUT-018** A backend factor's params in the slot are `[backend kind, address, namespace, key reference, wrapped B]` (printable fields without spaces; the blob 1 to 4096 bytes); the stored factor list round-trips exactly, and a slot whose stored kind, address, namespace, key or blob was changed does not open. The factor id is SHA-256 over `spo/factor-id/backend`, a zero byte and the canonical CBOR of `[kind, address, namespace, key]`.
- **SPO-Xunlock-OUT-019** `Store.AddBackendSlot` draws a slot id and 32 random bytes B, wraps B at the backend under `[genesis nonce, slot id]`, unwraps the blob once and compares the answer with B in constant time, then unwraps it once more under a fresh slot id of the same workspace and requires the backend's refusal (`ErrBackendRefused`; an answer means the backend ignores the context, `ErrBackendConfig`; any other error fails the enrolment), and only then writes a composite slot of the backend factor and the caller's other factors in one transaction with its audit row. A backend that does not give B back, ignores the context, or fails, adds nothing.
- **SPO-Xunlock-OUT-020** Opening through a composite with a backend factor (`FactorInputs.Backend`) first checks, for each slot and before any factor of it is asked for, that every factor can be presented (a slot that needs one the inputs lack is skipped with no prompt) and that every backend factor's reference passes `FactorInputs.BackendCheck` (SPO-Xunlock-PRE-045); then it asks the caller's client for the backend the slot names (the client's reference must equal the slot's), prints "asking <kind> at <address>", unwraps the slot's blob under the slot's own genesis nonce and slot id, and uses B as that factor's output in the derivation of SPO-Xunlock-OUT-001. Inputs without a backend client skip such a slot; any backend error ends the open (fail closed: `ErrBackendFactor`, naming the slot id, the backend kind and address, wrapping the port's error kind, and saying that the other ways in, `--unlock passphrase`, `fido2` or `recovery-composite`, are not affected). `workspace slot list` and `Describe` show the backend's public reference and nothing secret.
- **SPO-Xunlock-OUT-021** A backend slot is removed by `workspace slot remove` (a rotation that re-creates the other slots). A rotation never creates a backend slot (the plan is refused), and a removal that would keep a backend slot is refused with an error that says so, because the wrap at the backend is bound to the old slot id; the operator removes the backend slot first and adds it again after.
- **SPO-Xunlock-OUT-022** `spo workspace slot add-backend --backend vault|kms --with passphrase|fido2` opens the workspace with its current factors, takes the backend from `[vault]` or `[kms]` of `spo.toml`, makes the other factor (a new passphrase for this slot only, asked twice or `--new-passphrase-fd`; or a new FIDO2 credential on `--fido2-device`) and adds the composite. `--unlock backend` opens a workspace through such a slot (the composite's passphrase from a prompt or `--passphrase-fd`, read once per run and given as a copy to every open of the run, or the authenticator), and `store verify` verifies through it.

## External tools

- **SPO-Xunlock-EXT-001** Enrolment runs `fido2-cred -M -h -c 3 [-v -q] -i /dev/fd/N <device> es256`: hmac-secret and credProtect 3 requested, the parameters (client data hash, relying-party id, user name, user id) on a pipe, and the answer on standard output (a credential id and authenticator data hold no secret). The verification path follows `getInfo`: with a PIN, no `-v` is passed, because with `-v` the tool asks for built-in verification first and prompts for a PIN only when the authenticator answers PIN_REQUIRED, which a PIN-only authenticator does not do for a request carrying uv=true; the PIN is on the tool's standard input. An authenticator with built-in verification and no PIN is enrolled with `-v -q`. A PIN-only authenticator with no PIN given is refused unless the tool may prompt on the terminal.
- **SPO-Xunlock-EXT-002** An assertion runs `fido2-assert -G -h [-p] <verify> -i /dev/fd/N -o /dev/fd/M <device>`: the parameters (client data hash, relying-party id, credential id, salt) on a pipe, the answer (client data hash, relying-party id, authenticator data, signature, hmac secret, one base64 line each) on a pipe read into guarded memory. `-p` asks for user presence. `<verify>` is always present: `-v` with a PIN on standard input, or `-t uv=true -t pin=false` for built-in verification, or `-v` with the tool's own terminal prompt.
- **SPO-Xunlock-EXT-003** `fido2-token -I <device>` is read for the lines `version strings:` and `extension strings:`.
- **SPO-Xunlock-EXT-004** The touch probe is an assertion with `-t up=false -v` and the PIN on standard input. It runs for every enrolment: with the PIN on standard input, with the tool prompting for the PIN itself, or with the authenticator's built-in verification.
- **SPO-Xunlock-EXT-005** The authenticator data the tools print is a CBOR byte string around the raw data: 32 bytes of relying-party hash, a flags byte (bit 0 UP, bit 2 UV, bit 6 attested credential data, bit 7 extension data), a 4-byte counter, then for an enrolment the attested credential data and an extension map. The adapter decodes it strictly and refuses any other shape.

## Refusals

- **SPO-Xunlock-PRE-001** Enrolment refuses an authenticator whose makeCredential output does not confirm credProtect 3, whatever versions it reports.
- **SPO-Xunlock-PRE-002** Enrolment refuses an authenticator whose `getInfo` versions list neither `FIDO_2_1` nor `FIDO_2_1_PRE`, or whose extensions lack `hmac-secret`, or whose credential does not report hmac-secret.
- **SPO-Xunlock-PRE-003** An assertion without the UV flag when verification is required, or without the UP flag when presence is required, is refused by `Assertion.Require`, which destroys the outputs. The adapter applies it before it returns.
- **SPO-Xunlock-PRE-004** An answer with no hmac-secret line, with an output of the wrong length, with two equal outputs for two different salts, or with authenticator data that does not decode is refused as malformed.
- **SPO-Xunlock-PRE-005** An assertion for a credential the authenticator does not hold is `ErrFactorNoCredential`; an expired touch is `ErrFactorTimeout`; a wrong PIN is `ErrFactorPIN`; a blocked PIN is `ErrFactorPINBlocked`; none of them carries the tool's output.
- **SPO-Xunlock-PRE-006** `Check` refuses an empty table, an unknown policy, a slot with no id, a repeated slot id and a slot whose factors do not fit its kind.
- **SPO-Xunlock-PRE-007** `Check` refuses a `standard` table without a passphrase slot or without a recovery slot.
- **SPO-Xunlock-PRE-008** `Check` refuses, under `hardware` and `strict`, a slot that a passphrase alone opens.
- **SPO-Xunlock-PRE-009** `Check` refuses, under `hardware` and `strict`, a slot that the recovery key alone opens.
- **SPO-Xunlock-PRE-010** `Check` refuses, under `hardware`, a recovery composite that is not the recovery key and a hardware factor, or whose hardware factor also has a standalone slot (by factor id).
- **SPO-Xunlock-PRE-011** `Check` refuses a Vault or KMS factor in a slot with no other factor, in every policy, and under `hardware` and `strict` a slot with such a factor and no FIDO2 factor.
- **SPO-Xunlock-PRE-012** `Check` refuses a composite slot with a factor that is also a standalone slot, matched by factor id for recovery, FIDO2 and backend factors. Passphrases are not compared.
- **SPO-Xunlock-PRE-013** `Check` refuses a recovery slot under `strict`.
- **SPO-Xunlock-PRE-014** `Check` refuses a table whose slots bind different recovery public key hashes.
- **SPO-Xunlock-PRE-015** `Check` refuses, under `hardware` and `strict`, a slot that has no FIDO2 factor.
- **SPO-Xunlock-PRE-017** Enrolment refuses a credential whose authenticator data has the UV flag clear, an authenticator that can neither verify with a PIN nor with built-in verification, a PIN given to an authenticator with none set, and no PIN where one is needed and the tool may not prompt; each before `fido2-cred` runs where `getInfo` shows it.
- **SPO-Xunlock-PRE-018** `Check` refuses a `hardware` table with no recovery composite (a table with no recovery path is `strict`).
- **SPO-Xunlock-PRE-019** `Check` refuses a `hardware` recovery composite whose FIDO2 credential also appears in any other slot, standalone or inside another composite.
- **SPO-Xunlock-PRE-020** `Check` refuses a table with more than one distinct recovery factor.
- **SPO-Xunlock-PRE-021** `Check` refuses a slot with no recovery public key hash under `standard` and `hardware`, and a slot with one under `strict`, whose slots bind none.
- **SPO-Xunlock-PRE-022** The opener refuses a workspace of format 2 with an error that names `spo workspace migrate`, before any key is derived and without changing the file.
- **SPO-Xunlock-PRE-023** Under `hardware`, a passphrase alone and the recovery key alone open nothing; the daily authenticator and the recovery composite (the recovery key and the second authenticator) open the workspace, and the second authenticator alone opens nothing.
- **SPO-Xunlock-PRE-024** Slot add, rekey and rotation run `Check` on the table they would write and refuse a table that breaks the policy, leaving the file unchanged. A rekey makes a passphrase and a recovery slot, so it is refused under `hardware` and `strict`; a second recovery slot is refused in format 3 (the recovery key is bound in every slot).
- **SPO-Xunlock-PRE-025** `Check` accepts a legacy slot (a passphrase or recovery slot sealed before format 3, which binds no recovery public key hash) under `standard` only, and refuses a legacy slot that claims a hash.
- **SPO-Xunlock-PRE-026** A command opens a workspace that has no passphrase slot through its FIDO2 factors without asking for a passphrase; `--unlock passphrase` on it is refused, naming the policy; `--unlock recovery-composite` opens through the recovery composite (the recovery key typed at a prompt and the second authenticator); a binary with no factor source wired refuses before it prompts or runs a tool; an authenticator of another seed, or one that does not set the user-presence flag, opens nothing.
- **SPO-Xunlock-PRE-027** A rotation of a workspace that has a recovery path (`standard` or `hardware`) is refused with `ErrRecoveryNotPresented`, before anything is written, unless the handle holds a `RecoveryProof`: `Store.PresentRecovery` checked the recovery key (and under `hardware` the recovery composite's authenticator) against the recovery public key hash bound in the slots, on that handle and in the current key epoch. A daily-credential-only handle cannot rotate. A `strict` workspace has no recovery path and needs no proof, and a rotation of it to `hardware` or `standard` is refused with `ErrRotateWeakens`: ADR 0011 does not say how a strict workspace may be loosened. A `Rekey` is not covered by this rule (it is refused under `hardware` and `strict`, and under `standard` the recovery key it makes is the passphrase holder's).
- **SPO-Xunlock-PRE-028** The PIN of an authenticator is held per role (daily, recovery, current recovery), read from its own descriptor (`--fido2-pin-fd`, `--recovery-pin-fd`, `--old-recovery-pin-fd`) or its own prompt that names the role and the device, and never offered to another role; a rotation verifies every PIN (`PreflightFactors`) before it enrols, so a wrong recovery PIN leaves no credential on the daily token.
- **SPO-Xunlock-PRE-029** A session unlocked through FIDO2 factors has no passphrase (`session.Pass` is nil, `session.factorSession` is true). The approval gate asks the authenticator again (`Store.Reauthenticate`: a fresh assertion with PIN and touch, checked against the master key of the handle), fails closed when there is no factor source, and signs nothing on a refused presentation; `store backup` and `store verify` verify through the factors.
- **SPO-Xunlock-PRE-030** `unlock.Check` refuses, under `hardware` and `strict`, a table whose only slots are recovery composites (rule `daily-slot`), so the last slot that opens the workspace without the recovery path cannot be removed.
- **SPO-Xunlock-PRE-031** Under `standard`, `RekeyKeepRecovery` keeps only the recovery key that was presented (its public key hash must be the one bound in the slots, `ErrWrongRecovery`), and the presentation (`viaRecovery`, a proof) ends with the rekey or rotation it authorised, so a second one needs a new presentation. A rekey (`Rekey`, `ChangePassphraseRekey`, `RekeyKeepRecovery`) is refused with `ErrRecoveryNotPresented` unless the handle was unlocked with the recovery credential or `PresentRecovery` succeeded on it in the current epoch; a handle opened through a passphrase or a FIDO2 convenience slot only cannot replace the recovery path. `store passphrase change` presents the recovery key and keeps it (the bound hash is unchanged, no new key is made); `store recovery-key new` presents the current key first; in a FIDO2 session a passphrase change is refused. `PresentRecovery` skips a recovery slot that does not bind the hash the table binds.
- **SPO-Xunlock-PRE-032** A rotation of a `strict` workspace names every slot it removes and needs `--yes-remove <slot id>` for each; the store re-checks the confirmed ids against the table that is there inside its transaction (`ErrRemovalNotConfirmed`), so a slot added after the confirmation is not removed unseen. Whether a factor of each removed slot should be required instead is an open owner decision.
- **SPO-Xunlock-PRE-033** `store restore` (`sqlitestore.Restore*`) refuses a backup whose unlock policy ranks weaker (`unlock.Weakens`) than the policy of the workspace it would replace, with or without `--force` and `--allow-older` (`ErrRestoreWeakens`, checked from the two slot tables without a key, before the destination is locked). `--allow-weaker-policy` (with `--force`) allows it only when the current workspace's recovery credential is presented and checked with `PresentRecovery` on the current file: under `standard` the recovery key opens the file and is checked against the bound hash; under `hardware` the recovery key and the second authenticator (`--recovery-key-in-fd` or a prompt, `--current-recovery-device`, `--recovery-pin-fd`). A wrong credential changes nothing. A `strict` workspace has no recovery credential and is never replaced by a weaker backup (`ErrNoRecoveryPath`). The same or a stronger policy needs none of this.
- **SPO-Xunlock-PRE-034** A backup of a workspace under `hardware` or `strict` is restored through its factors: `store restore` reads the backup's policy without a key and verifies the copy with its FIDO2 slots (`RestoreWithFactors`, the verification `store backup` makes), asking the daily authenticator as at unlock. A passphrase cannot verify it, and a binary with no factor source refuses before it asks for anything. A wrong PIN installs nothing.
- **SPO-Xunlock-PRE-035** `init --policy hardware|strict` marks the workspace as unfinished with the file `workspace.spo.init-pending` (mode 0600, created exclusively before anything else is made, holding the policy and the time, no secret) until the rotation has committed. The marker is removed after the commit and after every failure that removes the files. When the rotation's outcome is unknown (`ErrOutcomeUnknown`), the policy of the file is read without a key: the policy reached means it committed (the recovery key is delivered, the marker removed); the file still `standard` means it did not (the new recovery key is destroyed, the files and the marker are removed, and the error says the rotation did not take effect); a file that cannot be read means nothing is removed, the new recovery key is delivered marked as valid only if the rotation took effect, and the marker stays. A later `init` that finds the marker beside a `standard` file recognises an interrupted init (an unopenable file whose random passphrase is gone) and removes the leftover files only after an explicit confirmation (`--remove-unfinished`, or `y` at a prompt, default No; with no terminal and no flag nothing is removed). A file that already has another policy is a finished workspace: only the stale marker is removed.
- **SPO-Xunlock-PRE-036** `store passphrase change` needs the OLD passphrase typed again, in addition to the recovery key: a prompt of its own (`Old passphrase (type it again)`) or `--old-passphrase-fd`, apart from the session's passphrase, which is not reused. A typing that differs from the one the session was opened with, or no way to ask, refuses before the recovery key is presented, the new passphrase is asked or anything is written.
- **SPO-Xunlock-PRE-037** A slot removal (`RemoveSlotByRotation`) re-creates each kept FIDO2 slot only from an authenticator that is the slot's: the existing slot is opened with the old-salt outputs of ALL its factors (the recovery key too, for a recovery composite) and must give this handle's master key; only then is the output for the fresh salt used. An impostor or wrong-secret authenticator, which answers any request, gives `ErrWrongCredential` and nothing is written.
- **SPO-Xunlock-PRE-038** The Vault client refuses a Transit key whose type is not `aes128-gcm96`, `aes256-gcm96` or `chacha20-poly1305` (the types that take associated data) and a key whose `derived` field is true, missing or not a boolean, before it encrypts or decrypts anything.
- **SPO-Xunlock-PRE-039** A backend address (and the STS endpoint) is `scheme://host[:port]` with no credentials, path, query or fragment, and `https`. Plain `http` is accepted only to a loopback IP address (`localhost` and other names are not accepted) and only when `allow_loopback_http = true` is set in the section of `spo.toml` (default false: TLS always); a slot row can never turn it on. A server certificate that the system roots or the CA file of that endpoint do not trust fails the call. A CA file that holds no PEM certificate is refused. No proxy from the environment is used.
- **SPO-Xunlock-PRE-040** Static AWS access keys are refused before any request, with a message that names the remedy (a session token, or a web identity): credentials in the environment without `AWS_SESSION_TOKEN`, and any key id that is not a temporary one (an allow-list: only `ASIA` is accepted, so `AKIA`, `AIDA`, `AROA` and anything else are refused). STS credentials that are not temporary (`ASIA`), lack a secret or session token, or are expired are refused. A web identity needs both the token file and the role ARN.
- **SPO-Xunlock-PRE-041** The KMS key is a key ARN (`arn:aws|aws-cn|aws-us-gov:kms:<region>:<12 digits>:key/<id>`); an alias or a bare key id is refused. Every answer must name exactly that ARN as `KeyId` and `SYMMETRIC_DEFAULT` as `EncryptionAlgorithm`, or it is refused.
- **SPO-Xunlock-PRE-042** An unwrap answer that is not exactly 32 bytes is refused (`ErrBackendResponse`) before any key is derived.
- **SPO-Xunlock-PRE-043** `AddBackendSlot` runs `unlock.Check` on the table with the new slot before the backend is asked: a backend with no other factor is refused, under `hardware` and `strict` a backend without a FIDO2 factor (a passphrase beside it is not `hardware`), a FIDO2 credential that is already a standalone slot, and a recovery credential as the other factor. The other factor is a passphrase or a FIDO2 credential only.
- **SPO-Xunlock-PRE-044** `workspace slot add-backend` refuses before it opens the workspace or asks for anything: no backend client in the binary, a missing `--with`, an unknown `--backend`, a `spo.toml` without the section it names, `--with fido2` without a factor source, and `--with passphrase` on a workspace whose policy is not `standard`. After the workspace is opened, every refusal of the store (`Store.CheckBackendSlot`: a read-only handle, `ErrSlotViaRecovery`, `ErrUseRekey`, the policy with the new slot, an invalid reference) runs before the authenticator is asked anything or makes a credential (`--with fido2`) and before the backend is called, so a refused slot leaves no credential on the authenticator. `--unlock backend` refuses before any prompt when the binary has no backend client or no slot of the table has a backend factor.
- **SPO-Xunlock-PRE-045** The backend reference a slot stores is a claim: the slot row is not authenticated until the slot opens, and anyone who can write the workspace file or a backup (a backup-sink operator included) can change it. Every path that would contact a backend (open, `store verify`, `store backup`'s verification, `store restore`, the layout export, the approval gate) checks each backend factor of a slot against `[vault]` or `[kms]` of `spo.toml` (`FactorInputs.BackendCheck`, `ports.CheckBackendClaim`) before any credential is loaded, any other factor of the slot is asked for, any notice is printed or any call is made. A slot whose kind, address, namespace or key is not byte-equal to what `spo.toml` names, or whose kind has no section, ends the open with `ErrBackendMismatch` and an error that shows both references and says the workspace file may have been altered. Inputs with a backend client and no check fail closed the same way, and the resolver of the command layer checks again before it builds a client.
- **SPO-Xunlock-PRE-046** The KMS endpoint and the STS endpoint are the public ones of the key ARN's partition and region (`kms.<region>.amazonaws.com`, `sts.<region>.amazonaws.com`, `.amazonaws.com.cn` for `aws-cn`), with the system roots. A slot address other than the public KMS endpoint is accepted only when it equals `private_endpoint`; `private_ca_file` is the CA of that endpoint only. The web identity token goes to another STS endpoint only with `private_sts_endpoint`, whose CA is `private_sts_ca_file` only. These opt-ins are for private (VPC) endpoints; a CA file without its endpoint is refused, and a plain-http private endpoint needs `allow_loopback_http` and a loopback IP address.
- **SPO-Xunlock-PRE-047** A Vault encrypt or decrypt answer that carries warnings (a list that is not empty) is refused (`ErrBackendResponse`): Vault lists there a parameter it ignored, such as `associated_data` on a server that does not support it. A server that ignores the associated data without a warning is caught at enrolment (SPO-Xunlock-OUT-019).
- **SPO-Xunlock-PRE-048** A credential file (the token helper file, `jwt_file`, `web_identity_token_file`) and a CA file are opened with `O_NOFOLLOW` and `O_NONBLOCK` and checked on the open descriptor: a symbolic link, a FIFO, a device or a directory is refused without blocking; the file must be a regular file of at most its bound (16 KiB for a credential, 1 MiB for a CA file), read into one buffer of its stated size that is not grown. A credential file must be owned by the user running spo and readable by its owner only (no group or other permission bits). A CA file must be owned by that user or root and not writable by group or others.
- **SPO-Xunlock-PRE-049** A Vault token (from `VAULT_TOKEN`, the token helper file or a JWT login) is looked up (`GET /v1/auth/token/lookup-self`) before it is used for anything else. A token whose `ttl` is 0 (it never expires) or whose `policies` include `root` is refused (`ErrBackendCredential`) with a remedy (a token with a TTL, or a JWT login). The answer is hostile input: `data.ttl` must be a whole number of at most ten digits, `data.policies` an array of at most 64 strings without escapes, each at most 256 bytes; anything else is `ErrBackendResponse`.
- **SPO-Xunlock-PRE-016** `Derive` and the slot functions refuse a slot with the wrong factor count for its kind, a salt or credential of the wrong size, and parameters of another factor kind.

## Invariants

- **SPO-Xunlock-SEC-007** The authenticator PIN is held in guarded memory owned by the command and destroyed when it ends, on success and on failure, and every hmac-secret output (the daily and recovery plans of a rotation, an assertion's output and next output) is destroyed on every path; no guarded buffer is alive after the command.
- **SPO-Xunlock-INV-006** No identifier of a test-only switch (a name ending `ForTest` or `ForTests`, or containing `TestOnly` or `GuardOff`, in any case) is declared or used in a non-test file under `internal/` or `cmd/` (`internal/archtest`). A guard that tests must skip is skipped by presenting what it asks for (`PresentRecovery`), never by a variable the production code carries.
- **SPO-Xunlock-INV-001** A slot key changes with the order of its factors, a factor id, the slot id, the slot kind, the genesis nonce, the format version and any factor output. Two factor outputs cannot be shifted into one another.
- **SPO-Xunlock-INV-002** The `passphrase` and `recovery` slot derivations are unchanged: the committed vectors of the seal package still pass.
- **SPO-Xunlock-INV-003** A refused assertion holds no secret afterwards, and a source that cannot do what an operation needs is refused by `CheckFactorProfile` before any prompt.
- **SPO-Xunlock-INV-004** A new workspace is format 3 under `standard` with one passphrase slot and one recovery slot, both binding the same recovery public key hash.
- **SPO-Xunlock-INV-005** A rotation that fails part way (an error after some records were re-encrypted) changes nothing: the old credentials open the file, every record is as it was and the file verifies.

## Security

- **SPO-Xunlock-SEC-001** No factor output, PIN or salt-derived secret is in an argument vector, in the environment, in a file or in a log line. A PIN reaches the tools on standard input through a pipe; the outputs come back through a pipe into guarded memory; the parameters go through a pipe.
- **SPO-Xunlock-SEC-002** A tool that is given a PIN on standard input is started without a controlling terminal, because libfido2's PIN prompt reads `/dev/tty` first. Without a PIN, the tool prompts on the terminal itself and the process never sees the PIN.
- **SPO-Xunlock-SEC-003** The error of a failed tool call carries a typed reason and the exit status, never the tool's output.
- **SPO-Xunlock-SEC-005** What a tool writes back is bounded: the captured standard output and standard error of a call, and each secret pipe, have a maximum (64 KiB and 8 KiB for the libfido2 calls; 128 MiB and 16 MiB by default for any other tool), and a tool that exceeds it is stopped and the call fails.
- **SPO-Xunlock-SEC-006** The opener runs `Check` on the slot table before it derives a key or asks an authenticator. A file edited to flip the policy, drop a factor from a composite, swap a slot row from another workspace, replace the recovery key hash or roll slots back opens with no weaker factor set: it is refused, or no slot opens, because the policy, the factor entries and the recovery key hash are bound in the associated data of every slot.
- **SPO-Xunlock-SEC-008** B, the Vault token and the AWS secret key and session token are held in guarded memory. What this package zeroes: each request body that carries B, the JWT or the web identity token (built in one buffer of its final size, never grown, escaped by hand); each answer (read into one buffer of the bound or of the declared length, never grown); a credential file's bytes; the fixed array B's base64 is decoded through. The secrets of an answer (B in a decrypt answer, the token of a login, the STS secret key and session token) are located by a scanner of this package and copied from the answer's own bytes into guarded memory: no decoder holds them, and no Go string of them is made. Copies that remain and cannot be zeroed: the Vault token and the AWS session token as Go strings in the request headers (`net/http` takes header values as strings), the Authorization header string, and the copies `net/http` and `crypto/tls` make of headers and bodies in their own buffers (the bufio writer and reader, the TLS record buffers, an HTTP/2 frame); the environment strings `VAULT_TOKEN`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` as the process received them; the base64 of B in the request body as `net/http` copies it; the SigV4 secret as the HMAC key inside `crypto/hmac`. No error of a backend carries B, the credential, or text the backend sent: errors carry a kind (`ports.ErrBackendRefused`, `ErrBackendCredential`, `ErrBackendConfig`, `ErrBackendUnavailable`, `ErrBackendResponse`, `ErrBackendMismatch`), a status code, an exception name or public parameters (addresses, key names).
- **SPO-Xunlock-SEC-009** The backend credential exists only in the client process: it is never written to the workspace or `spo.toml` (neither has a place for it), never passed on the command line (there is no flag for it), and never given to a child process (the tools run through `platform/execx` get a complete environment of their own and inherit nothing). A refused token or credential is reported without its value.
- **SPO-Xunlock-SEC-010** Every backend answer is hostile input: an answer whose declared length is over 64 KiB is refused before it is read, a longer body is cut at 64 KiB + 1 and refused (what the client allocates for a 4 MiB body stays under 1 MiB), response headers are bounded at 32 KiB, a redirect is never followed (the token never reaches another host), every call (connection and TLS handshake included) has a deadline, compression is off, and wrong JSON types, trailing data, a duplicate key in any object, an escape in a key, nesting deeper than 16 or more than 4096 keys, escapes in a secret or in a field that is compared, a ciphertext that is not the backend's form, another key id, and a secret of the wrong length are refused. The JSON answers are read by a scanner of the package rather than `platform/strictjson`, because strictjson refuses the many keys a Vault or KMS answer has that the client does not read, and because a standard decoder copies the secrets into memory that cannot be zeroed; the scanner accepts only what `encoding/json` accepts as one object. The response parsers and the scanner are fuzzed.
- **SPO-Xunlock-SEC-011** A backend composite opens with all its factors only: the backend alone (B without the other factor), the other factor alone (the file and the passphrase without the backend), and a backend that answers a B of its own choosing open nothing; a chosen B fails the commitment of the slot key, so it cannot make the slot accept another key.
- **SPO-Xunlock-SEC-012** A wrapped blob moved to another slot or another workspace does not open it: the backend refuses it under the other context, and a backend that ignored its context would still not open the other slot, because that slot's associated data binds its own blob.
- **SPO-Xunlock-SEC-013** `adapters/vaultkms` imports the port, `platform/secret` and an allow-list of standard packages only (no process start, no logging, no third-party module; `syscall` for SPO-Xunlock-PRE-048), only `cmd/spo` imports it, and the relay binary and its assembly do not reach it (`internal/archtest`).
- **SPO-Xunlock-SEC-014** The approval gate of a session opened with `--unlock backend` presents the composite again (`Store.Reauthenticate`): the backend is asked again and the composite's passphrase is read from the terminal, every time, never from `--passphrase-fd` (a descriptor given at start does not satisfy a fresh presentation, as with the passphrase and FIDO2 gates); with no terminal nothing is signed. A backend-plus-passphrase session needs no FIDO2 factor source to sign.
- **SPO-Xunlock-SEC-004** An authenticator that returns an output to an assertion with user presence off is recorded as "touch not enforced" in the enrolment; the touch requirement of the cold-role sub-key is then a stated residual risk, not a guarantee.

# Xsnapshot: raw snapshot of the sealed store

This spec is not upstream behaviour. It specifies work package 2 of stage 3 of [ADR 0012](../../docs/explanation/adr/0012-server-backup-and-deployment.md): a lossless reader and writer for the encrypted SQLite store. It moves rows, sealed as they are stored, into a plain data value and back into a new store file. It is the base of a later conversion between the SQLite file and a sealed object layout. No record is decrypted and no new cryptography is added. There is no command in this stage.

Terms: a **snapshot** is the four tables of the store (`meta`, `keyslots`, `records`, `audit`) and the schema version, every column of every row, in a defined order. A **sealed field** is a column that holds sealed or MAC'd bytes; a snapshot holds it as an opaque byte slice. **Verification** is the existing full verification of a file through a credential (the one `store verify` and a restore use, without `--deep`). A **transient column** is a column that describes the file and not the workspace.

## Interface

- **SPO-Xsnapshot-IF-001** `ReadSnapshot(ctx, path, credential)` returns the snapshot of a file and its facts. `WriteSnapshotFile(ctx, path, snapshot, credential)` creates a new store file. The credential has exactly one of three fields set: a passphrase, the printed recovery key, or FIDO2 factor inputs; none or more than one is refused. The credential is the one the file's policy takes: a hardware or strict workspace is opened through its factor slots.
- **SPO-Xsnapshot-IF-002** A snapshot is plain data: `Meta` (every column of the one `meta` row and the schema version), `Slots` (every column of every `keyslots` row), `Records` (every column of every `records` row) and `Audit` (every column of every `audit` row). Sealed fields are byte slices. A NULL of a nullable column is a nil slice or nil pointer; an empty value is not nil. Rows are in a defined order: slots and records by id (bytewise), audit by sequence number, which is strictly increasing. `Validate` checks the bounds of OUT-004 and that order, and nothing else.
- **SPO-Xsnapshot-IF-003** `ReadSnapshot` returns, with the snapshot, facts computed by the store package: the workspace id, the head of the audit chain, the slot set hash that `slots` and `rollover` audit rows record, for each record the hash that the `touched` lists of audit rows record for it, and the notices of the verification (a cold record healed from its previous wrap, cold records without a recovery wrap, a checkpoint key record) together with one notice when the original has no head file. `FactsOf` computes the same from a snapshot alone. The slot set hash and the record hash functions are not exported.

## Outputs

- **SPO-Xsnapshot-OUT-001** The snapshot read from the file `WriteSnapshotFile` wrote equals the snapshot it was given in every column of every table, except the transient column of OUT-002. This holds for a standard workspace with records of every class, a cold-role record under the standard, hardware and strict policies (with a previous wrap, healed), a workspace after a rotation, a policy change, a slot added and removed, a passphrase change and a rekey, a workspace migrated from format 2 and from the legacy format, one holding a checkpoint key record, and one holding operational-certificate and KES counter records. The written workspace verifies (plain and deep) and opens with the same credential, and lists the same records, gives the same non-secret record values and the same cold status, policy, slots and audit head.
- **SPO-Xsnapshot-OUT-002** The one transient column is `meta.cleanup_pending`: 1 from the commit of a rekey until its VACUUM and WAL truncation have succeeded. `ReadSnapshot` reports its value. `WriteSnapshotFile` writes 0 whatever the snapshot says, because the new file has had no rekey. No other column is transient.
- **SPO-Xsnapshot-OUT-003** `WriteSnapshotFile` builds the file under a private temporary name in the destination's directory (mode 0600) from the schema the migrations produce, inserts every row as given, and links it into place with a call that cannot replace anything. The head file is written after the link, by the atomic head-file writer, and the head file's announcement (`<path>.head.next`) is made before the link and removed after the head file is written. The file has mode 0600.
- **SPO-Xsnapshot-OUT-004** Limits, enforced by `Validate` on a snapshot and, before any row is loaded, by `ReadSnapshot` on the counts and total size of a file: at most 100000 records, 500000 audit rows and 64 key slots; at most 4 MiB in one byte field; at most 256 MiB in all byte fields and kind strings; a kind of at most 64 bytes. A snapshot beyond a limit is refused as `ports.ErrSnapshot` before a file is created.

## Preconditions and failures

- **SPO-Xsnapshot-PRE-001** A snapshot is taken only from a file that verifies through the credential presented, and what is verified is what is read. The original is locked exclusively (refused while any handle has it open) and copied through the locked descriptor into a private temporary file in its directory (mode 0600, random name, removed on every path). The copy is verified through the credential, its rows are read read-only, and it is checked to be the same file before and after the read; the original's path is not read again for content, so a file renamed over the path meanwhile changes nothing. The copy's audit chain must contain the head recorded in the original's head file (a rolled-back original is refused as an open refuses it, a head file of another workspace is refused); a missing head file is a notice. A file that fails verification, a wrong credential, and a workspace that fails the cold-record checks of verification (for example a cold record left under its old factor on request) give no snapshot. Residual: a process that writes to the locked inode itself while ignoring the lock, during the copy, can make the copy differ from every state the workspace had; the copy then fails verification unless that process can also forge the audit chain, which needs the workspace key. The same holds for a process that replaces the temporary copy in the window between verifying it and reading it, which the same-file check narrows to a race between two descriptors it already holds.
- **SPO-Xsnapshot-PRE-002** `ReadSnapshot` refuses: a file that is not of the current store format (a file of format 1 or 2 must be migrated first); a file whose mode is not owner-only, that is not a regular file of the current user, or that is a symbolic link; a file with a rollback journal or a non-empty WAL beside it; a file that another handle has open; and a file whose schema differs from the allow-list (a trigger, view, extra table, extra index or changed column).
- **SPO-Xsnapshot-PRE-003** `WriteSnapshotFile` links a file into place only after the built file passed the schema allow-list, a check that the recovery public key of the meta row is the one the slots bind (and that a table whose slots bind none has none), the full verification through the credential presented, and a read-back that equals the snapshot given (except OUT-002).
- **SPO-Xsnapshot-PRE-004** `WriteSnapshotFile` never overwrites. An existing file, `.head`, `.head.next`, `.head.lock`, `-wal` or `-journal` at the destination is refused as `ErrExists`; `WriteSnapshotFile` is not a way to replace a workspace, and an import over an existing workspace must install the written file with the restore (`RestoreWithFactors`), which applies the policy, rollback and counter rules; a file that appears between the build and the link is not replaced, and is left as it is.
- **SPO-Xsnapshot-PRE-005** A snapshot with a duplicate record id, lookup tag, slot id or sequence number, rows out of order, a sequence number below 1 or a gap in the audit chain, an unknown slot kind, an empty id, an unknown policy or schema version, an oversized field or kind, or more rows than OUT-004 allows, is refused and nothing is written.

- **SPO-Xsnapshot-PRE-006** On a platform without file locking (the build of `lock_other.go`) `ReadSnapshot` and `WriteSnapshotFile` refuse with `ErrSnapshotPlatform`: the exclusive lock of PRE-001 is not available there. The package builds for Windows (`GOOS=windows go vet`); the refusal is not run on that platform by the tests.

## Invariants

- **SPO-Xsnapshot-INV-001** A failed `WriteSnapshotFile` leaves no file, no temporary file, no head file, no announcement and no head lock file that it made. A destination that existed is untouched.
- **SPO-Xsnapshot-INV-002** A process that dies between the build and the link leaves only a temporary file named `.snapshot-*` in the directory, and nothing at the destination. A process that dies between the link and the head file leaves the complete file, the announcement and no head file; the next open of the file makes the head file and removes the announcement, as for a restore that died in the same place. The write does not leave a file with another file's head file beside it.
- **SPO-Xsnapshot-INV-003** Changing one value of any column of any table of a snapshot makes `WriteSnapshotFile` fail, with nothing left behind, except for the columns that nothing the store verifies binds. These are `meta.created_at` and `records.updated_at`: they are written as given and read back as given, and the file verifies. `meta.cleanup_pending` is the transient column of OUT-002.

## Security

- **SPO-Xsnapshot-SEC-001** Nothing is decrypted. No record payload is opened, and no cold-role factor is asked for. A snapshot holds integers, strings and byte slices only and no key, passphrase or factor output; the bytes of a snapshot contain none of the test keys, passphrases, recovery keys or authenticator secrets. Reading a snapshot asks the authenticator exactly as often as the verification alone, and leaves no secret buffer live.
- **SPO-Xsnapshot-SEC-002** A hardware or strict workspace is read and written through its factors. A passphrase, an empty passphrase or the printed recovery key alone is not accepted for it, for the read or for the verification of the write, and the failed write leaves nothing. The second authenticator does not open a strict workspace.

# Xcustody: no secret is written unprotected

This spec is not upstream behaviour. Upstream keeps every signing key as a plain file (mode `0400`, [Pfiles](../upstream/patterns/Pfiles.md) SEC-002) and offers `01_protectKey` to encrypt or decrypt one file in place. The port's owner rule is stricter: **securables such as cold keys are encrypted at rest, the application tolerates no insecure mechanism, and the release binary must be unable to write a signing key or any other secret unencrypted.** What counts as a secret is the class of [ADR 0004](../../docs/explanation/adr/0004-data-classification.md): signing keys of every kind, mnemonics, the Catalyst QR code (the voting key under a four-digit PIN), provider tokens, party identity private keys, tailcat keys. The decision is recorded as ADR 0011 (proposed).

The rule is carried by types and by the architecture test (`internal/archtest`), not by convention: the release contains a directory reader with no write method, the one writable plain-directory store is a test-only package that production code cannot import, the one writer of the upstream layout the release has refuses every secret that is not a signing key in upstream's encrypted form, and the one secret the release only displays, the Catalyst QR code, is drawn on a terminal and written to no file. The one named exception is the delivery of a pool's hot keys to its block producer (ADR 0011 decision 2): `spo node export` writes only `age` ciphertext, and the producer's start-up helper, a separate program that cannot open a workspace, is the only writer of a signing key in clear.

Terms: an **upstream-layout directory** is a directory of the file names of [Pfiles](../upstream/patterns/Pfiles.md). A **kept key** is a signing key that an import of an older release (`--keep-encrypted`, removed) stored still in upstream's password-encrypted form (an `UpstreamEncryptedSKey` record); no import creates one now. The **plain store** is `spo/test/plainstore`, the writable store of that layout, used only by tests and by a build with the `plainlayout` tag.

## Interface

- **SPO-Xcustody-IF-001** The release command tree has no way to write a signing key unprotected: no global flag `--upstream-layout` (a plain directory is not a workspace), no `key protect` and no `key unprotect` (they changed a key file of such a directory in place), no `--plaintext` or `--yes` on `workspace export`, and no confirmation word that writes a key in clear. `workspace export <dir>` with `--password-fd N` or `--generate-password` is the only way a signing key leaves the sealed workspace, and it is encrypted.
- **SPO-Xcustody-IF-003** `workspace export` takes its password in exactly one of two ways, and the two are mutually exclusive: `--password-fd N` (a password the operator chose), or `--generate-password`, which draws 160 random bits and writes them as eight hyphen-separated groups of four base32 characters, alternately lower and upper case (39 characters; it meets the strength rule of PRE-001 and the length rule of PRE-003). The generated password is shown once on the terminal (standard output must be a terminal, else the command is refused before anything is read) or written to the descriptor `--password-out-fd N`, which must be a pipe or a Unix socket (OUT-005); it is never stored, logged or put in an argument. `--password-out-fd` goes with `--generate-password` only.
- **SPO-Xcustody-IF-004** `spo catalyst key qrcode <name> [--pin-fd N] [--yes]` has no file output: it has no `--out` and no `--show` (the terminal display is the only mode), and it writes no `<name>.catalyst-qrcode.png`. It requires standard output to be a terminal and refuses a pipe or a redirect before anything is asked, with or without `--yes`.
- **SPO-Xcustody-IF-005** `spo node export <pool> --recipient FILE --out DIR [--kes N] [--no-tpm-identity] [--reason TEXT]` reads the pool's KES signing key, VRF signing key and operational certificate from the sealed workspace and writes only `age` ciphertext, sealed to the one recipient named by `--recipient`, into `DIR`, which must not exist or must be empty: `kes.skey.age`, `vrf.skey.age` and `node.cert.age`, each created exclusively, mode 0600. It has no option that writes a plaintext file, and nothing but ciphertext leaves it (OUT-006). `--kes N` names the KES key; without it the newest key that has a certificate is taken (the KES counters say which). It needs the sealed workspace, not `--upstream-layout`. Its refusals come before any prompt or write where they need no workspace (PRE-011).
- **SPO-Xcustody-IF-006** `spo-node-keys deliver --from DIR --to DIR` is the block producer's start-up helper, a separate program (INV-007). It takes the producer's age identity from the systemd credential `spo-node-age-identity` in `$CREDENTIALS_DIRECTORY` (PR-002), decrypts the three ciphertext files of `--from`, and writes `kes.skey`, `vrf.skey` and `node.cert` into `--to`, which must already exist (MODE-001, PRE-014). It prints the three paths and has no other command, no flag that names an identity file or a key, and no way to open a workspace.
- **SPO-Xcustody-IF-008** `spo workspace import` has `--defer-encrypted` and no `--keep-encrypted`: with it no upstream-encrypted key file is imported, each is reported as left in the source, its owner is not imported, and no password is asked for. `--keep-encrypted` is refused with a message that names `--defer-encrypted`. No `UpstreamEncryptedSKey` record is created (decision 2 of ADR 0011).
- **SPO-Xcustody-IF-002** `spo key convert <key> [--password-fd N]` turns a kept key into an ordinary sealed signing key. `<key>` is the key file's stem with or without `.skey` (`mypool.node`, `mywallet.payment.skey`). The upstream password is read from the descriptor, else asked for without echo.
- **SPO-Xcustody-IF-007** The sealed store takes the factor of the cold sub-key (decision 6 of ADR 0011) through `Store.SetColdSource(ColdSource{Passphrase, Factors, Deriver})`; a store with no source refuses every operation that needs the factor (PRE-018). The command layer wires it as `cli.ColdOpen`: the sub-key passphrase from `--cold-passphrase-fd` or a prompt (asked twice when a sub-key is made), the daily authenticator named by `--fido2-device` for the hardware and strict policies, and `--new-cold-passphrase-fd` for the table a rotation writes. `spo store verify --deep --with-cold-factor` opens every cold-role payload read-only (INV-015).
- **SPO-Xcustody-IF-009** `spo store slots` prints, after the slots, the line "N cold records without a recovery wrap" and the command that adds the wraps, and `spo store verify` prints the same fact as a note, whenever N is not zero and the policy is not `strict` (where there is no wrap by design). It needs the workspace key and no cold factor: the wrap, or its absence, is in the wrapped-key column and is authenticated by the outer layer (OUT-009), which the workspace key opens; a record whose outer layer does not authenticate is a verification failure, not a count.

## Inputs

- **SPO-Xcustody-IN-001** An upstream-layout directory is only ever read: it is the source of `spo workspace import`, opened through a type that has no write method (`ports.ReadStore`; the reader's method set is `View`, `Open`, `List`, `Subdirs`). No code path of the release opens such a directory for writing except the export destination of OUT-003.
- **SPO-Xcustody-IN-002** An audit log that an earlier version left in an upstream-layout directory (`.spo-workspace-audit.json`) is listed by an import as an ignored file, with no warning; it is never read as a record and never written.

- **SPO-Xcustody-IN-003** The recipient file of `node export` holds exactly one `age` X25519 public key (`age1...`); blank lines and `#` comment lines are allowed. A file with a secret key (`AGE-SECRET-KEY-`), with more than one recipient, with none, or with a recipient of another kind (a passphrase, a plugin, a post-quantum key) is refused before the workspace is opened. The file is at most 8 KiB.
- **SPO-Xcustody-IN-004** The factor of a cold sub-key is, under the standard policy, a passphrase that opens no standalone `passphrase` slot (PRE-020), and under hardware and strict one hmac-secret assertion of the credential named in the record's header, with user presence and user verification, from an authenticator whose profile has two-salt assertions (MODE-004). The factor is presented fresh for every cold record an operation touches; nothing is cached across commands, and the passphrase is kept in guarded memory for one operation only.

## Refusals

- **SPO-Xcustody-PRE-001** `workspace export` without a password is refused before anything is read, written or audited, and a password that is not strong in upstream's sense ([Ckey](../upstream/common/Ckey.md) INV-001) is refused the same way.
- **SPO-Xcustody-PRE-002** `key convert` changes nothing, and says why, when: no kept key has the name; the password does not open it (tried once; no retry); the workspace holds no verification key to check the decrypted key against; the key is of a type that has no derivable verification key here (BLS: import such a key again from its directory with `--password-fd`; a KES or VRF key is derived as PRE-009 says and must be of the exact form of PRE-010); the decrypted key does not belong to the verification key in the workspace; a sealed key of that name already exists.

- **SPO-Xcustody-PRE-003** `workspace export` refuses, before anything is read, written or audited, a password of fewer than 20 characters (counted as upstream's prompt reads it, [Ckey](../upstream/common/Ckey.md) SEC-001), in addition to the strength rule of PRE-001. gpg's key derivation is not memory-hard (SEC-003), so the length carries the protection.
- **SPO-Xcustody-PRE-004** `offline attach` refuses a file that is a secret, naming the reason: a name ending `.skey`, `.hwsfile` or `.mnemonics`; a cardano-cli text envelope of a signing key type, or any JSON envelope whose type names a signing key; a hardware signing file; upstream's encrypted-key envelope; a JSON array or nested object that holds any of those envelopes; a bech32 private key (CIP-5: `ed25519_sk`, `ed25519e_sk`, `ed25519_seed`, `xprv`, and every human-readable part ending `_sk`, `_xsk` or `_seed`, such as `root_xsk`, `acct_xsk`, `addr_xsk`, `stake_xsk`, `pool_sk`, `kes_sk`, `vrf_sk`, `drep_sk`, `drep_xsk`, `cc_cold_sk`, `cc_hot_sk` and the `_shared_xsk` forms) anywhere in the text, in either case; a file that is only 64 or 128 hexadecimal characters; a list of 12, 15, 18, 21 or 24 words of 3 to 8 letters in either case, numbered or not, separated by spaces, commas or line breaks (also as a JSON array of strings); a UTF-8 byte order mark is ignored, a UTF-16 file is refused. Verification keys, certificates, transactions, witnesses and metadata JSON pass. The transfer file travels in clear. The check is a guard against a slip, not a proof: a file disguised on purpose passes. It applies to the file's own name and to the name it is stored under.
- **SPO-Xcustody-PRE-006** A descriptor given to receive a secret (OUT-005) is checked before any effect: before a key is read, a file or directory is created, the audit log is written or the store is changed. A descriptor that is not a pipe or a socket, such as `--password-out-fd 5 5>file`, `--password-out-fd 1`, or a descriptor number that is not open (`--password-out-fd 57`), is refused with the reason and what to use instead.
- **SPO-Xcustody-PRE-007** `node export` refuses unless the role history of the KES key and of the VRF key each contains the hot role of its kind (`kes`, `vrf`) and no cold role (`pool-cold`, `committee-cold`). A key with no stored history is refused (fail closed: it cannot be told that the key was never cold), and so is a history that cannot be read. Nothing is sealed, written or audited.
- **SPO-Xcustody-PRE-008** `node export` refuses when the operational certificate of the KES number does not name this KES key: its KES verification key is not the stored one of that number. It also refuses when the KES verification key, the VRF verification key or the certificate of the number is missing.
- **SPO-Xcustody-PRE-009** `node export` derives the verification key of each signing key and refuses when it is not the stored one: for a KES key the Sum6 root verification key, for a VRF key the public key of its seed, which must also be the public half the key carries. The KES derivation checks the whole Sum6 structure of the 608 bytes against the seeds the blob actually holds: at each level the active child's public key must equal the stored left key (right seed present) or the stored right key (right seed erased, the key being in the right subtree), a present right seed must regenerate the stored right key, and a leaf is the Ed25519 public key of its seed; the root is the hash of the two stored keys, so a blob whose seeds were overwritten is refused and the key returned is derived from secrets that are there. A period-0 key of cardano-cli 11.2.3.0 is the known-answer fixture (`adapters/native/testdata/kes-oracle`); evolved keys (spent seeds erased) are covered only through the library's own `Update`, whose erasure the check handles as above. The derivation is behind `ports.HotVKeyDeriver`, implemented in `adapters/native/hotkeys`. An import of a KES or VRF signing key by stem and `key convert` apply the same derivation.
- **SPO-Xcustody-PRE-010** A file of a hot kind is accepted only in its exact form: the three members `type`, `description` and `cborHex`, each once and no other; the envelope type of the kind; a `cborHex` that is a CBOR byte string of exactly 608 bytes (KES key) or 64 bytes (VRF key), or, for the certificate, the structure `[[kesVKey, counter, period, signature], coldVKey]` with nothing after it. A file that has the envelope type of a hot kind and other key material is refused by `node export`, by the import by stem (as a key that cannot be derived), by the helper and by the writer.
- **SPO-Xcustody-PRE-011** A refused `node export` creates no directory and no file, records no audit event and returns no ciphertext, whatever refused it. The refusals that need no workspace (the recipient, a non-empty or non-directory `--out`, `--out` equal to the workspace directory) come before the workspace passphrase is asked for.
- **SPO-Xcustody-PRE-012** The helper writes nothing when any of the three ciphertext files is missing, is larger than 64 KiB, does not open with its identity (sealed to another recipient, or changed after sealing), decrypts to more than 4 KiB, or decrypts to a file that is not, in the exact form of PRE-010, the kind of its file name (the VRF key sealed under the name of the KES key, a cold key, a certificate for another KES key). All three are decrypted and checked, and the KES key is checked against the certificate (the verification key derived from it is the one the certificate names), before the first file is created.
- **SPO-Xcustody-PRE-013** The helper refuses without writing anything when it runs as root; when `$CREDENTIALS_DIRECTORY` is not set or does not hold the credential; when the credential is a symbolic link, not a plain file, owned by neither the user it runs as nor root, larger than 1 KiB, accessible by others, writable or executable by its group, or readable by a group that is not the helper's own primary group (a credential 0400 or 0440 of the user's own group passes; 0440 root:root does not unless the helper's group is root's); when it is not exactly one `AGE-SECRET-KEY-` identity; or when the credentials directory is not on the file system the rule accepts (PRE-014), so the identity is never read from a disk. How systemd really makes these files is unverified on a real host.
- **SPO-Xcustody-PRE-014** The helper opens each directory with `O_DIRECTORY|O_NOFOLLOW` and checks the open descriptor, not the path: `fstat` says it is a directory owned by the user the helper runs as (or by root, for the ciphertext and credentials directories) and writable by neither group nor others, and, for the output and credentials directories, `fstatfs` says the file system is `ramfs` (`RAMFS_MAGIC`), or `tmpfs` whose mount has the `noswap` option: the mount carrying the descriptor is found in `/proc/self/mountinfo` by the device id of `fstat`, every mount of that device must be a tmpfs with `noswap` in its mount or super-block options, and no match refuses. Every other file system is refused, a `tmpfs` without `noswap` (its pages can be swapped) included. A directory that is a symbolic link as its last component is refused. The output directory must exist: the helper creates none.
- **SPO-Xcustody-PRE-015** The helper refuses, writing nothing, a delivery file with no valid magic and header, a header whose kind is not the kind of its file name, and three files whose pool id, KES number or certificate counter differ.
- **SPO-Xcustody-PRE-016** `node export` refuses a certificate whose cold signature does not verify over the KES verification key, the counter and the period, whose cold verification key is not the pool's stored cold verification key (and the issue counter's), whose KES period is not below 2^20, or whose counter is not the newest one the pool's issue counter has made (`counter + 1` is the counter file's next value: an older certificate is a rollback). The helper repeats the signature check and checks that the certificate carries the pool id and counter of the headers; it has no pool record.
- **SPO-Xcustody-PRE-017** `node export` refuses when the Ed25519 identity (the key hash) of the VRF public key or of the KES leaf public key has any role history, or is a member of an owner in a role other than `kes` or `vrf`: an Ed25519 key, a cold key included, relabelled as a hot key. `workspace import` applies the same check to a VRF or KES verification key it reads by stem (the declared public key's Ed25519 identity), and refuses the pool with that reason; a key with no such history imports as before.
- **SPO-Xcustody-PRE-005** `catalyst key qrcode` asks for confirmation before it builds the payload (default no; `--yes` answers it, on a terminal only) after stating that anyone who photographs, records or shares the screen can recover the key with at most 10,000 guesses, and it is refused, with nothing built, when the display cannot be recorded in the audit log (OUT-004) or the voting key has no signing key (a hardware key).
- **SPO-Xcustody-PRE-018** When the handle has no cold source, or its source lacks what the policy needs (no passphrase callback under standard; no authenticator source, or a profile without two-salt assertions, under hardware or strict), every operation on a cold-role record fails with `ErrColdFactorRequired` or the capability error before any prompt, any PIN callback or any assertion, and writes nothing.
- **SPO-Xcustody-PRE-019** A signing key whose verification key is not stored beside it, or whose key identity has no role history, is refused at put (`labels.ErrNoKeyIdentity`, `labels.ErrNoRoleHistory`): the store never seals such a key as a hot key.
- **SPO-Xcustody-PRE-020** A new sub-key passphrase that opens a standalone `passphrase` slot of the workspace is refused (`ErrColdPassphraseReuse`) and nothing is written. A passphrase that is a factor inside a composite slot cannot be tested; for it the rule is advice.
- **SPO-Xcustody-PRE-030** With a recovery credential present, a rotation, and a recovery rekey that is given a new cold factor (`store recover`: `RekeyCold`), open each cold record that has a recovery wrap through the wrap (PRE-021), whatever cold source the handle has wired: the old factor is never consulted for it, so a lost cold passphrase, a lost daily authenticator or a recovery authenticator wired as the cold source does not stop a recovery. The cold mnemonic is such a record (PRE-033). The wrap is opened and the identity checked in the gather, before the file lock and with only the recovery private key; a record whose identity check fails falls back to the OLD cold factor (a record that opens with it is accepted and sealed again under the new one; one that does not is named in the refusal, which also wraps `ErrRecoveredIdentity` with the record's name). The old factor is used for a record with no wrap, one that cannot be checked against its identity (an upstream-encrypted key, or a mnemonic when no mnemonic deriver is wired), and one whose identity check failed. EVERY record the old factor opened is sealed again under the new factor, so the workspace never ends with two cold passphrases. When the old factor cannot be presented for a record, the change is refused before anything is written and names the record as `kind/label` (`ErrColdWouldStrand`); only PRE-031 leaves it. A cold row that appeared after the factors were gathered fails the change with `ErrColdWrapRaced`. After `store recover` every re-established record opens with the NEW cold factor (the new cold passphrase, `--new-cold-passphrase-fd` or two prompts, asked once, only if a record needs it, before the lock) and not with the lost one. A factor that was wrong, absent or refused is reported as that (`ErrColdFactorWrong`, `ErrColdFactorRequired`, `ports.ErrFactor*`), never as corruption, and only such an error lets the gather treat a record as unreachable: corruption, a cancelled context and a memory error abort, and `ErrRecoveredIdentity` is reported as tampering, not as a factor error. A `--unlock recovery-composite` session does not wire the recovery authenticator as the cold source.
- **SPO-Xcustody-PRE-031** A rotation or recovery leaves a cold record under its old cold factor only when the operator names the record (`--leave-unreachable kind/label`, `ColdSource.LeaveUnreachable`) and the recovery credential was presented; a name that matches no cold record, or a name given without the recovery credential, is refused (`ErrColdLeaveUnknown`) with nothing written. The transaction that leaves it writes a `cold-left` audit event naming the record id and sets a left mark in the record's cold form (PRE-034). A cold record is opened with the factor its own header names (a passphrase header in a hardware workspace opens with the passphrase, and the reverse), so a left record still opens and can be re-established by a later rotation. Leaving a record does not strand the others: the workspace's cold passphrase is compared only across records not marked left.
- **SPO-Xcustody-PRE-032** No slot is created on a handle unlocked through a slot that holds the recovery factor (the recovery key, or the recovery composite): `AddFactorSlot`, `AddPassphraseSlot` and `AddRecoverySlot` refuse with `ErrSlotViaRecovery`; the way to recover is a rotation. A FIDO2 credential that belongs to a recovery composite (of the table now or of the plan) is refused as a daily factor, in a slot added or in a rotation (`ErrRecoveryCredentialAsDaily`). `workspace rotate` takes the new daily authenticator as `--new-fido2-device` (its PIN `--new-fido2-pin-fd`), distinct from `--fido2-device`; in a `--unlock recovery-composite` session `--fido2-device` is the current recovery authenticator, `--new-fido2-device` is required and may not be that device, and the recovery key typed to open the session is presented again as the proof. `store recover` refuses on a hardware or strict workspace and names that procedure.
- **SPO-Xcustody-PRE-033** A committee cold mnemonic made by the tool with `--account` or `--index` other than 0 records that path in its record: the stored file is the words, a newline and a line `derivation <account> <index>`, written only when the path is not 0, 0. The store releases the words only (`ports.StripDerivation`) to a reader; the derivation line stays in the sealed record. `ports.ColdMnemonicVKeyDeriver` derives the committee cold verification key at the recorded path (0, 0 for a record without one), and the recovery check compares its identity with that of the signing key beside it, so a routine rotation and a recovery re-establish such a mnemonic through its wrap. A legacy record without the line made at another path mismatches, falls back to the old cold factor (PRE-030), and is otherwise named and refused unless left (PRE-031). A file import has no account or index to record (it takes none).
- **SPO-Xcustody-PRE-034** A cold record left on request (PRE-031) carries a left mark in its cold form: outside the inner wrap, so it can be set without the sub-key, and inside the associated data of the outer layer, so only a holder of the workspace key changes it. It is kept by every rekey, rotation and open of the record, and dropped only when the record is sealed again under the current factor. `store verify` fails, and `store slots` lists the record, for as long as the mark is set, under every policy and without any factor; the mark is encoded only when set.
- **SPO-Xcustody-PRE-035** `--unlock recovery-composite` is accepted only by `workspace rotate`, `workspace policy set` and `store slots`; any other command refuses it before it asks for anything and names those commands. The recovery key typed to open a recovery session is kept only by `workspace rotate`, is used once as the proof and destroyed there; every command, however it ends, destroys the PINs, cold-key passphrases and recovery text it read (a guarded-buffer count returns to its baseline). `workspace rotate` takes the new workspace passphrase of a standard table from `--new-passphrase-fd` and the recovery key of a recovery session from `--recovery-key-in-fd`, so both flows script without a terminal.
- **SPO-Xcustody-PRE-021** A cold record is re-established through its recovery wrap only if the decrypted signing key derives the key identity stored for the record (`ErrRecoveredIdentity`); otherwise the whole rotation is refused and nothing changes. Without a verification-key deriver the recovery path is refused. The wrap is made with only the public key, so this check is what stops a planted record.
- **SPO-Xcustody-PRE-022** A rotation of a workspace that holds cold-role records is refused, before anything is written, unless it is given the sub-key factor of the new table (`RotatePlan.ColdNew`) and either the sub-key factor of the old table (the handle's source) or the current recovery credential (`RecoveryProof`). A rekey that makes a new recovery key needs the recovery credential presented, and moves the recovery wraps to the new key without any sub-key factor.
- **SPO-Xcustody-PRE-023** A cold record is never wrapped to a recovery public key that does not hash to the value the slots bind (`ErrRecoveryKeyMismatch`), nor when the slots bind different values.

- **SPO-Xcustody-PRE-024** The recovery credential authorises one operation. Whatever the outcome of the rekey, rotation or slot removal it was presented for, the handle then holds no recovery proof, no recovery secret (not the one of an unlock through the recovery credential either) and does not count as unlocked through it; a second guarded operation needs a new presentation (`ErrRecoveryNotPresented`).
- **SPO-Xcustody-PRE-025** A kept key whose stem is a cold kind is sealed in the cold form through the verification key beside it, so reading it (`key convert` does that first) needs the cold factor; one with no verification key beside it cannot be written and is refused (`ErrColdNoSibling`). A mnemonic of a cold role (`cc-cold.mnemonics`) is sealed in the cold form bound to the identity of the verification key beside it, and refused when there is none.
- **SPO-Xcustody-PRE-026** A signing-key envelope whose type belongs to a cold role (pool cold, committee cold) is refused by `put` and by import under any other record kind (`ErrEnvelopeKind`), so it is never sealed hot.
- **SPO-Xcustody-PRE-027** Under `standard` a cold record created while another passphrase-sealed cold record exists is sealed only under the sub-key passphrase that opens the existing one (`ErrColdPassphraseDiffers`): a workspace has one cold passphrase, changed by rotation. The check tries EVERY passphrase-sealed cold record; a passphrase that opens some and not others means the workspace is already split, and the creation is refused with `ErrColdSplit`, which names `store verify` (INV-023). A row of the cold form that does not authenticate (or whose owner blob does not open, or whose class disagrees with its role history) is skipped, and is never a reason for the check to pass: the check finds a genuine record if there is one, and when cold rows exist and none can be used the creation is refused (`ErrCorrupt`) with nothing written (INV-022).
- **SPO-Xcustody-PRE-029** A rekey or passphrase change that makes the table bind a recovery public key adds a recovery wrap to every cold record that has none (a record migrated from format 2, whose legacy slots bound none). It needs the cold sub-key factor once per such record, presented before the file lock is upgraded and before the write transaction begins (INV-021); with no source it is refused with `ErrColdFactorRequired` before anything is asked, with a wrong factor with `ErrColdFactorWrong`, and in both cases nothing is written. A record changed while the factor was being presented makes the rekey fail with `ErrColdWrapRaced` and nothing changes. A rekey whose new table binds no recovery key (`strict`) leaves records without a wrap as they are.
- **SPO-Xcustody-PRE-028** A handle unlocked through a slot that holds the recovery factor creates no cold record and re-binds none to the recovery authenticator (`ErrColdViaRecovery`).

## Invariants

- **SPO-Xcustody-INV-001** The release binary is unable to write a signing key or any other secret unencrypted to a file or pipe it has opened for that purpose. (a) A plain upstream-layout directory is not a workspace: the release has no opener for it. (b) The writable plain store lives under `spo/test/`; only `_test.go` files, packages under `spo/test/` and `cmd/spo/wiring_plain.go` (built only with the `plainlayout` tag) may import it, and the default build contains none of it. (c) The export destination refuses any secret that is not a signing key envelope in upstream's encrypted form, whatever the caller asks. (d) The plain store opens a directory only when its `spo.toml` exists, parses and names a network that is not mainnet (SEC-002). (e) The Catalyst QR code is written to no file: the renderer and its port have no method that takes a path and no image encoder; the terminal display of OUT-004 is the one named, audited, non-persistent output of this secret, and it is drawn on the terminal's alternate screen and cleared afterwards.
- **SPO-Xcustody-INV-002** The release build proves the absence: the dependency set of `cmd/spo` built with no tags has no package under `spo/test/`, and the installed binary has no `--upstream-layout`, no `key unprotect` and no `--plaintext` (`internal/archtest`, and the install check of `tools/spo.nix`). A build with the `plainlayout` tag is not a release, and no derivation built with it installs an executable: the `spo-parity` output holds a log and a marker, and the check `spo-tagged-no-binary` of `tools/spo.nix` fails when a tagged derivation has any file that can be run.
- **SPO-Xcustody-INV-004** The OpenPGP check of the export destination accepts one message form only, the one the pinned gpg command (EXT-001) emits: one packet of tag 3 that is version 4, with cipher AES-256, S2K mode 3, hash algorithm 10 (SHA-512), an encoded count that decodes to at least 65011712 and no encrypted session key (the body is exactly 13 octets); then one packet of tag 18 whose first octet is 1 and whose body is at least 49 octets, which is 1 (version) + 18 (random prefix of the 16-octet block and its 2 repeated octets) + 8 (the shortest literal data packet: 2 header, 1 format, 1 name length, 4 date) + 22 (the MDC packet: tag, length, 20 hash octets); and nothing else. Version 5 session key packets, the AEAD packet (tag 20), MD5 or SHA-1 or SHA-256 S2Ks, a count below the pinned one, and every other packet are refused. **Limit:** ciphertext cannot be told from plaintext by inspection, so a body of plausible length that is plaintext passes. The check proves that the envelope has the form of a password-encrypted message. That the content IS encrypted rests on the producers: the only writers of such an envelope are the gpg adapter, which encrypts with the pinned options and verifies the result decrypts, and an upstream-encrypted record kept verbatim from an import, which `workspace export` never writes (INV-003).
- **SPO-Xcustody-INV-005** An envelope in upstream's encrypted form has exactly the members `type`, `description` and `encrHex` ([Pfiles](../upstream/patterns/Pfiles.md) OUT-003), each once. A member of any other name, or a repeated member, makes it malformed: it is refused on export and at import, so a kept-encrypted record (`UpstreamEncryptedSKey`) is stored only with that field set, and an envelope cannot carry a plaintext secret beside the ciphertext.
- **SPO-Xcustody-INV-006** The workspace-opening binary contains no writer of a signing key in clear. `adapters/nodefiles`, the writer of the start-up helper (three kinds, exact form of each, descriptor-based directory checks, ramfs, mode 0400, `O_EXCL`), is imported by no non-test package but `cmd/spo-node-keys`, and is in the dependency set of `cmd/spo` neither in the release build nor in the `plainlayout` build (`internal/archtest`; `go list -deps` in the install check of `tools/spo.nix`). The `node export` side (`adapters/nodeage`) can only seal: it has no method that writes a file.
- **SPO-Xcustody-INV-007** The start-up helper cannot open a workspace: the dependency set of `cmd/spo-node-keys` holds no sealed store (`adapters/sqlitestore`), no slot or key-wrapping code (`platform/seal`, `domain/unlock`), no factor source (`adapters/fido2cli`), no command tree, no multi-party store, no SQLite driver and not `adapters/native` itself: it imports only the small `adapters/native/hotkeys` package, a confined home of the Blink Labs libraries. The helper is its own Nix package (`spo-node-keys`), installable without `spo`. `internal/archtest` and the check phase of `tools/spo.nix` prove it from the import graph, and also that the helper still contains the writer, so the proof cannot pass by the helper losing it.
- **SPO-Xcustody-INV-008** The writer's table of kinds is pinned: exactly `HotKES` (`kes.skey`, `KesSigningKey_ed25519_kes_2^6`), `HotVRF` (`vrf.skey`, `VrfSigningKey_PraosVRF`) and `HotOpCert` (`node.cert`, `NodeOperationalCertificate`); the writer creates a file in exactly one place, one `openat` with `O_CREAT|O_EXCL|O_NOFOLLOW`, and no other file-creating call of `os`, `syscall`, `x/sys/unix` or `io/ioutil` exists in the package, through any import alias or a dot import (`internal/archtest`). A new kind or a second way to create a file fails the test and needs the review ADR 0011 asks for.
- **SPO-Xcustody-INV-003** A kept key never leaves the workspace and cannot sign. It is written nowhere by `workspace export`, which names `key convert` as the way to make it exportable.
- **SPO-Xcustody-INV-009** The ordinary data key, that is the master key's record-wrapping key, does not open the payload of a cold-role record: it opens the outer layer, which holds the data key wrapped under the cold sub-key. The sub-key is derived by `seal.DeriveColdSubKey` from the factor output, the genesis nonce, the format version and the key identity.
- **SPO-Xcustody-INV-010** The class of a record (`secret-cold` against `secret`) is in the associated data of the payload and of both layers of the data key, together with the record id, kind, owner, number and version. A cold record cut to the hot form, or a hot record given the cold form, fails to open; a hot record written for a cold identity by a holder of the master key is refused on read (`ErrColdClassMismatch`), against the role history.
- **SPO-Xcustody-INV-011** The header of a cold record (the Argon2id salt and parameters, or the credential id and the current and next hmac-secret salts) is canonical CBOR, validated against the floors and ceilings of ADR 0003 and the lengths of CTAP 2.1, and authenticated by the outer and the inner layer.
- **SPO-Xcustody-INV-012** A rekey that keeps the recovery key re-wraps only the outer layer of a cold record (`RewrapCold`): header, inner layer, recovery wrap, payload and its nonce are unchanged and no sub-key is needed.
- **SPO-Xcustody-INV-013** The recovery wrap is RFC 9180 base mode with DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 and ChaCha20-Poly1305, single message; its open path reproduces the RFC 9180 Appendix A.2 vector.
- **SPO-Xcustody-INV-014** The `info` of the recovery wrap is the canonical CBOR of ["spo/cold-recovery-wrap/1", cold record format, genesis nonce, recovery public key hash, record identity] and its AAD is the record's associated data (version and class included); the key epoch is not bound. A wrap of another record, of an older version, of another workspace or of another recovery key does not open; the SHA-256 of the wrap is in the associated data of the outer layer.
- **SPO-Xcustody-INV-015** `Verify`, `VerifyPayloads`, backup, restore, `labels.Check` on open, listing and a rekey that keeps the recovery key need no sub-key factor. Deep verification opens a cold record's outer layer, so it authenticates class, header, recovery wrap and associated data and checks the sealed class against the role history, but it cannot say that the payload decrypts or that the key in it belongs to its identity; it reports how many records it could not open. `VerifyColdPayloads` (`store verify --deep --with-cold-factor`) presents the factor, opens each payload read-only, and still does not derive the key identity.
- **SPO-Xcustody-INV-016** One signing operation that uses a cold key makes one assertion (two salts in the same assertion) or asks the sub-key passphrase once; creating a cold record makes one assertion per record; a refused or impostor presentation changes nothing.
- **SPO-Xcustody-INV-018** The sub-key and the recovery wrap bind the version of the cold record form (`seal.ColdRecordFormat`, "spo/cold-record/1"), not the store format.
- **SPO-Xcustody-INV-017** A rotation that fails part way, cold-role records included, changes nothing: the file is as it was, the old factor opens every record and the file verifies.

## Outputs

- **SPO-Xcustody-OUT-001** `key convert` stores the sealed key and removes the kept record in one transaction: both happen, or the workspace is as it was. The decrypted key is in guarded memory only and is written nowhere in clear. The destination key, the kept record and the verification key the check used are read again inside that transaction: a sealed key that has appeared, a kept record that has gone or a changed verification key stops the conversion with nothing changed (`ports.ErrConflict` or the refusal of PRE-002).
- **SPO-Xcustody-OUT-002** `key convert` prints the name of the converted key and nothing of its content.
- **SPO-Xcustody-OUT-003** `workspace export` writes the non-secret artefacts as [Pfiles](../upstream/patterns/Pfiles.md) names them, and each signing key in upstream's encrypted form with the given password, verified to decrypt again before it is written. Mnemonics, the Catalyst QR code, kept keys and this program's own records are never written; each skipped artefact is in the report with the reason. The export is audited before the first key is written. The destination checks what it is given: the ciphertext in each envelope must be exactly what the pinned gpg command emits (INV-004), or the key is refused; the shape of the envelope alone is not enough. The envelope has exactly the members `type`, `description` and `encrHex` (INV-005).
- **SPO-Xcustody-OUT-004** `catalyst key qrcode` draws the QR code of the voting key on the terminal and in no file. In order: it states the risk (PRE-005), asks, reads the PIN, records the display in the audit log (operation `catalyst-qr-display`, the key's name, no key material; the display is not made when the record cannot be written), builds the payload, draws the code on the alternate screen and clears that screen when the operator presses Enter. A terminal log, a recording or a shared screen can still hold it.

- **SPO-Xcustody-OUT-005** A secret that a command writes to a descriptor (a flag classified as secret output in `internal/adapters/cli/uihints.go`: `--password-out-fd` of `workspace export`, `--recovery-key-fd` of `init` and of the `store` commands) goes only to a pipe or a Unix socket that is open for writing, through the one helper `internal/platform/secretfd`, which `fstat`s the descriptor and refuses a regular file, a directory, a block or character device (a terminal is one: a secret shown on a terminal goes through the interactive display, not the flag), descriptors 0, 1 and 2, a closed descriptor and a read-only one. The refusal says that a secret is never written to a file and names a pipe to a password manager or to the consuming process. The check is applied from the same table that classifies the flags, so a flag cannot be classified secret-output without being checked. `workspace export` generates the password and writes it to the descriptor before it reads any key, creates the directory or records the audit event, and writes the export files only after that write succeeded: a failed delivery leaves no encrypted file, and a successful delivery followed by a failed export leaves only a password that opens nothing. `init` removes the workspace files it created when the recovery key could not be written. A socket must be a Unix-domain socket; a network socket is refused. The check covers the descriptor only: what the process at the other end of the pipe does with the secret (for example a shell redirect that copies it to a file) is outside the binary's knowledge and is the operator's responsibility.

- **SPO-Xcustody-OUT-006** `node export` seals each of the three files to the recipient with `age` (X25519, one recipient) and writes nothing else: no plaintext, no temporary plaintext. All three files are checked (PRE-007 to PRE-010, PRE-016, PRE-017) and sealed in memory. The ciphertext is then written under temporary names in `DIR` (`.<name>.tmp`, exclusive, mode 0600, synced), the delivery is recorded in the workspace's audit log (operation `node-export`, the pool name, the KES number, an identifier of the recipient, the three file names and the statement of OUT-007), and only then are the files renamed to their names. When the record cannot be made the temporary files are removed and no named file exists; there is no audit row without files and no named file without a row, except in a crash between the record and the renames (a row, the files under their temporary names), which is documented.
- **SPO-Xcustody-OUT-008** The sealed payload of each file is a magic line, a canonical header line and the envelope. The header (compact JSON, fixed field order) holds the format (1), the pool id (the hash of the certificate's cold key), the file's kind, the KES number, the certificate counter and the export time. The helper requires the kind of each header to be the kind of its file name, the pool id, KES number and counter to be the same in the three files and the certificate to carry that pool id and counter, and refuses a mixed set (PRE-015). The header is not a signature: age gives no sender authentication, so whoever can write the delivery directory can choose which complete set, genuine or self-made, the node runs. The helper keeps no state between runs, so it cannot refuse an older complete set; that is an owner decision recorded in the handoff.
- **SPO-Xcustody-OUT-007** The audit event and the report of `node export` say what the command cannot check: that the producer's identity is held as a TPM-bound `systemd-creds` credential and not as a file on a disk. The event records `tpm-identity=not verified` by default and `tpm-identity=none` when `--no-tpm-identity` states it is not TPM-bound, and the report warns that anyone who can read that host's disk can decrypt the files. The recipient is recorded by an identifier (the first 8 bytes of the SHA-256 of its text, in hexadecimal), not in full.
- **SPO-Xcustody-OUT-009** A cold-role record has the wrapped-key column `["spo/cold-record/1", header, outer, recovery wrap]` (canonical CBOR): `outer` is the XChaCha20-Poly1305 sealing, under the record-wrapping key, of `inner`, which is the data key sealed under the sub-key, followed, for an hmac-secret record whose header names a previous salt, by the previous inner wrap (the same data key under the sub-key of that salt, associated data `["spo/cold-prev/1", record AD, header, previous salt]`). The header of an hmac-secret record is `[kind, credential, salt, next, previous salt or empty, fallbacks]`. The previous wrap is inside the outer layer, so it is authenticated by the workspace key and by the header and the recovery wrap hash in the outer associated data; a file editor can neither drop nor swap either wrap, and a master-key holder who grafts the previous wrap of another record or of another version of this record gets a wrap that does not open (INV-020). The payload, the owner blob and the lookup tag are as for a hot record. The schema does not change.
- **SPO-Xcustody-OUT-010** Opening a cold record through the vault writes it again, in the transaction of the open and before the secret is released: a new record version, a new payload nonce, the header's salt rotated (a fresh Argon2id salt under standard; under hardware the stored next salt becomes the current one and a fresh next salt is drawn, the data key being wrapped under the output for the old next salt, which the same assertion returned). Under hardware the data key is sealed again under the output for the stored next salt, which nothing has verified, and the wrap proved good in this open (the one under the salt just used) is kept as the previous wrap, replacing the older one: only an open that succeeded with the current wrap replaces the previous one. If the factor is wrong or the commit fails nothing is released.
- **SPO-Xcustody-OUT-011** A cold record under a table that binds a recovery public key carries the HPKE wrap of its data key to it (`meta.recovery_pub`, checked against the bound hash); the wrap is rewritten whenever the record's version changes and whenever a rotation or rekey changes the recovery key. A record made before a workspace bound a recovery key (a migration from format 2), or under strict, carries no wrap. A migrated record gains one in the first rekey that binds a recovery key (PRE-029), not at its next open; until then the recovery key does not reach it (IF-009).

- **SPO-Xcustody-INV-020** A hmac-secret cold record keeps at most one previous inner wrap beside the current one. An open tries the current wrap, then, only if it fails to authenticate, the previous one (a second assertion with the previous salt); so a faulty authenticator that answered the next salt wrongly leaves the record openable, under `hardware` and `strict` alike. The previous wrap is replaced only by an open that succeeded with the current wrap. When the previous wrap had to be used, the new current answer is verified before it is sealed under: the new salt is asserted a second time and the two answers compared in constant time (one extra touch, only in this case). If they agree the record is healed (a fresh current salt, no previous wrap, the header's fallback counter incremented; `store verify` prints the count for each record as a note); if not, nothing is rewritten, the secret is still released from the previous wrap, and a warning ("the authenticator returned an inconsistent answer; the record was not rotated") is given at every such open, so a persistent fault cannot pin the previous salt silently. Under `standard` the next salt is derived from the passphrase in process, so no previous wrap is kept. The cost: an output captured for the previous salt opens the record until the next open that succeeds with the current wrap (one rotation longer than before).
- **SPO-Xcustody-INV-021** The cold factor of a NEW cold record (a pool cold key, a cold key import, a key that gains a cold role, the migration) is never asked for while a write transaction or the exclusive file lock is held. An `Update` first runs its function in a transaction that counts the cold records it would create, seals them under throwaway sub-keys and is rolled back; the factor is then presented once for each record (the passphrase once under standard, one assertion per record under hardware and strict) with nothing held, and the function runs again in a transaction that only consumes the material, held in guarded memory and destroyed at the end. A write that needs more than was gathered fails with `ErrColdNotGathered` and asks nothing. The migration gathers in the same way before its lock. A rotation, and a recovery rekey that re-establishes records, gather their factors (the old factor where PRE-030 needs it, the new one for every record sealed again) before the file lock and the write transaction too (`coldPre`), each bound to the version and hash of the row it was made for, so a concurrent change is refused (`ErrColdWrapRaced`); `store verify --with-cold-factor` lists the records in a read transaction that is closed before it asks.
- **SPO-Xcustody-INV-023** `store verify` (and `store slots`, as a list) counts and names by `kind/label` the cold records that the workspace key alone shows to be out of step: a header kind that does not match the policy, a FIDO2 credential that belongs to no current daily slot, and a record named by a `cold-left` event since the last rekey; `store verify` fails (`ErrVerify`) while there is one, and fails when the cold status cannot be read. That two records are sealed under different cold passphrases cannot be seen without the passphrase and is not reported; creating a cold record in such a workspace is refused with `ErrColdSplit`, which names `store verify`.
- **SPO-Xcustody-INV-022** The same-passphrase check (PRE-027) never passes because a cold row failed to authenticate; see PRE-027.

## Modes

Here a mode is the file mode and the user a file is made for, not a work mode.

- **SPO-Xcustody-MODE-001** Every file the helper writes is created with one `openat` relative to the checked directory descriptor, `O_CREAT|O_EXCL|O_NOFOLLOW|O_WRONLY|O_CLOEXEC`, mode 0400, and is checked on its descriptor to be a plain file of the user the helper runs as with one link. A file that exists is never replaced (the helper refuses and the files of that run are removed again).
- **SPO-Xcustody-MODE-002** The helper runs as the node's own user, never root, so that the files are owned by the user whose node reads them and nobody else needs a `chown`. When a write fails part way, the files that the run created are removed and the directory is left as it was.
- **SPO-Xcustody-MODE-003** Under standard the sub-key factor output is Argon2id over the sub-key passphrase with a 16-byte per-record salt and the parameters of a new slot (stored in the header).
- **SPO-Xcustody-MODE-004** Under hardware and strict the factor output is the hmac-secret output of the credential of the slot the handle unlocked through (stored in the header), for a 32-byte per-use salt, with user presence and user verification; a source whose profile lacks two-salt assertions is refused before the PIN. Every salt a new cold record or a rotation seals under is asserted twice and the two outputs compared in constant time before anything is sealed (one extra touch per record at creation and at rotation, so two touches per record in all); a mismatch refuses with `ErrColdAnswerInconsistent` and writes nothing. The answer for the NEXT salt at an open cannot be checked in the same session; INV-020 covers it.
- **SPO-Xcustody-MODE-005** Under strict there is no recovery public key, no wrap and no recovery path: a lost factor loses the record.

## External tools

- **SPO-Xcustody-EXT-002** `age` (`filippo.io/age`, no external tool) seals and opens the delivery, in `adapters/nodeage` only: X25519 recipients and identities, one stanza. `node export` refuses a recipient that is not one, and the helper refuses an identity that is not exactly one X25519 secret key.
- **SPO-Xcustody-EXT-001** The export's gpg command pins the parameters of the encrypted form explicitly, so they do not rest on gpg's defaults or a configuration file: `--cipher-algo AES256 --s2k-mode 3 --s2k-digest-algo SHA512 --s2k-count 65011712 --force-mdc` (gpg 2.4 accepts all of them), in a private empty gpg home. Decryption by upstream's scripts or by `gpg --decrypt` needs no option, because gpg reads the parameters from the message ([Ckey](../upstream/common/Ckey.md) INV-003).
- **SPO-Xcustody-EXT-003** The recovery wrap uses `crypto/hpke` of the Go standard library (RFC 9180), in `internal/platform/seal` only; there is no new module.

## Procedure

- **SPO-Xcustody-PR-002** The helper's procedure: read the identity from the credential (PRE-013), open and check the ciphertext directory, decrypt and check all three files (PRE-012), check the KES key against the certificate, open and check the output directory (PRE-014), and only then write the three files (MODE-001). It asks nothing and prints only the paths.
- **SPO-Xcustody-PR-001** `key convert` decrypts the kept key with the password (as typed and as upstream's prompt stored it, [Ckey](../upstream/common/Ckey.md) PRE-007), derives the verification key from the result and compares it with the one in the workspace, and only then stores the sealed key and removes the record (OUT-001).
- **SPO-Xcustody-PR-003** At put the store classifies each signing-key record from the role history of the key identity its verification key hashes to (the verification key stored with the same anchor, number and role): cold roles are pool cold and committee cold; the sub-key applies by identity, whatever role the record was made for. Calidus and Catalyst voting verification keys, which belong to no owner, and the verification keys of an owner with no anchoring key yet, record their role history when they are written.
- **SPO-Xcustody-PR-004** A transaction that writes a role history gaining a cold role re-seals, in the same transaction, every stored signing key of that identity in the cold form; if the factor is not present the transaction is refused and nothing changes. A role history only grows, so a cold record is never rewritten hot.
- **SPO-Xcustody-PR-005** The migration of a store of format 2 to format 3 seals in the cold form every signing key whose identity has a cold role, under a sub-key passphrase given through the handle's cold source (the standard policy it creates); with none the migration is refused, naming the kinds, and the file is unchanged. The passphrase is asked before the exclusive file lock and the write transaction (INV-021), by a dry run in a transaction that is rolled back. The migrated slots bind no recovery key, so the sealed keys carry no recovery wrap, and `spo workspace migrate` ends its output with a warning that says so and names `spo store passphrase change` (and `spo store recovery-key new`) as the commands that add the wraps (PR-009).
- **SPO-Xcustody-PR-009** The rekey that adds the wraps (PRE-029) presents the cold factor once per cold record without a wrap, outside any transaction, derives the data key of each, and in the rekey's transaction seals the HPKE wrap to the new recovery public key from that data key, without opening anything else; afterwards `store slots` and `store verify` report none, and the recovery key re-establishes each record (PRE-021). On a `hardware` workspace every record carries its wrap from creation, so no such step arises.

## Security

- **SPO-Xcustody-SEC-004** The delivery is the one place where a signing key is in clear, by necessity: the KES key, the VRF key and the certificate on the producer's ramfs for as long as the service runs, and in the node's memory; the age identity in the helper's memory while it decrypts, and on the credentials ramfs of its service. Nothing is in clear on a disk. The cold key, the workspace key and every other secret never reach the host. The protection of the identity is the host's: a TPM-bound credential protects it against a copy of the disk, a key file of the host protects it against nothing that can read the disk (OUT-007), and a process that runs as the node's user can read the three files, as the node does. The headers of OUT-008 bind a set together but authenticate no sender, and the helper keeps no rollback state. The helper, the files and the decrypted bytes are hardened as the rest of the release is (no core dump, locked memory).
- **SPO-Xcustody-SEC-001** An import never changes the source directory: its files, modes and contents are as they were.
- **SPO-Xcustody-SEC-002** The plain store refuses mainnet unconditionally. It opens a directory only when the directory's `spo.toml` exists, parses and names a network that is not mainnet; a missing `spo.toml`, one that cannot be read (the network is then unknown) and one that names mainnet are all refused, and so is the mainnet network magic. There is one constructor, and the composition root of the `plainlayout` build uses it.
- **SPO-Xcustody-SEC-003** An export is protected by gpg's iterated-and-salted S2K, which is not memory-hard, so it is weaker against offline guessing than the sealed workspace (Argon2id). It is a transport form: move it, use it, and delete the directory and the password after use. The 20-character minimum (PRE-003) and the generated password (IF-003) are what make it hold; a password the operator chose is only as good as its length.
- **SPO-Xcustody-SEC-005** The sub-key, the factor outputs, the PIN and the sub-key passphrase are held in guarded buffers and destroyed right after the operation, on success and on failure (a cold open that loses a race with another writer, or fails to commit, leaves no plaintext key in guarded memory); a signing key opened for a cold record is returned to the caller only after the transaction that rotates its salt has committed.

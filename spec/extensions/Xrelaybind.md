# Xrelaybind: binding and revoke statements, pure rules

This spec is not upstream behaviour. It specifies work package 1 of [ADR 0014](../../docs/explanation/adr/0014-wallet-key-identity-for-the-relay.md) (status: accepted in outline): the pure domain of the wallet-key identity at the relay. The package is `internal/domain/relaybind`. It does no I/O, holds no state and imports only the standard library, `internal/domain/cose` (Blake2b and the CIP-8 `Sig_structure`), `internal/domain/party` and `internal/domain/identity` (the canonical CBOR helper). The relay binary links it, so nothing in its import closure may open an envelope.

Terms: **K** is the wallet key hash, Blake2b-224 of the 32-byte Ed25519 verification key. A **statement** is a CIP-8 `COSE_Sign1` signed by that key whose payload is a binding or a revoke line. The **strict parser** is this package's own; the lenient parser of `internal/domain/cose` is unchanged (CIP-88 and cardano-signer outputs need it).

The vectors of this package are written with a fixed **software** test key and are **provisional**: ADR 0014 freezes them only after one real-device check (payment and stake message signing, un-hashed, on Ledger and Trezor, with the protected header bytes `cardano-hw-cli` writes). Where the ADR leaves room this spec takes the stricter reading; the choices are listed in "Choices that go beyond the ADR text".

## Outputs

- **SPO-Xrelaybind-OUT-001** The binding payload is one line of lower-case ASCII with single spaces, no line feed and no leading or trailing space, at most 120 bytes: `spo-relay-binding-v1 device <40 hex> from <unix seconds> until <unix seconds>`. It is 101 bytes with 10-digit times. `device` is the party fingerprint as 40 lower-case hex digits. Times are decimal digits without sign or leading zero (`0` itself is valid) and at most 12 digits. `Binding{Device, From, Until}.Render()` writes it and refuses what the parser refuses (a time outside 0 to `MaxTime`, a lifetime outside the bounds).
- **SPO-Xrelaybind-OUT-002** `ParseBinding` accepts only the byte-exact canonical rendering: it parses, re-renders the parsed values and requires equal bytes (the canonical rule of ADR 0010). It also requires `0 <= from < until <= MaxTime` and a lifetime `until - from` of at least `MinLifetimeSeconds` (1 hour) and at most `MaxLifetimeSeconds` (180 days). A payload that is not canonical is `ErrPayloadNotCanonical`; a canonical one with a lifetime out of range, including `until <= from`, is `ErrLifetime`.
- **SPO-Xrelaybind-OUT-003** The revoke payload is `spo-relay-revoke-v1 device <40 hex or all> not-before <unix seconds>`, with the same text rules as the binding (89 bytes with a 10-digit time and a device). `Revoke{All, Device, NotBefore}` renders and `ParseRevoke` parses it by the same re-render rule; `all` is lower-case and carries no device; `not-before` is 0 to `MaxTime`. The wallet-signed revoke is a `COSE_Sign1` by K over this payload, with the same strict parse and key checks as a binding.
- **SPO-Xrelaybind-OUT-004** The device-signed revoke is an Ed25519 signature over the canonical CBOR array `["spo/relay-revoke-device/v1", device fingerprint (20 bytes), not-before]`, the label inside the array as the mailbox auth bytes have it (`DeviceRevokeBytes`). It starts with the byte 0x83, which no ASCII payload does. `VerifyDeviceRevoke(ed25519, x25519, notBefore, signature, now, policy)` validates the `Policy` (only its skew is used), refuses a small-order or non-canonical Ed25519 key (`ErrWeakKey`), recomputes the fingerprint from the two keys, refuses a not-before beyond `now + skew`, and verifies the signature; it returns the revoked device and the not-before as a `VerifiedDeviceRevoke`, a type with unexported fields that only this function makes (the registry accepts a device-signed revoke only as that type: SPO-Xmailbox-SEC-062); a refusal returns the zero value. Its tombstone has scope `ScopeDevice` (OUT-014).
- **SPO-Xrelaybind-OUT-005** The strict parser accepts exactly this `COSE_Sign1`: an array of 4, untagged; a protected byte string holding the map `{1: -8, "address": bstr}` in either key order and nothing else, the address being exactly 28, 29 or 57 bytes (PRE-014); the unprotected header exactly `{"hashed": false}`; an embedded payload byte string; a 64-byte signature byte string; nothing after it. It is the encoding `cose.Sign1.Encode` writes for the software signing path. `ParseStatement` returns a `Statement` whose accessors return copies.
- **SPO-Xrelaybind-OUT-006** `Statement.Canonical()` is the relay's own encoding: the protected bytes as signed, the unprotected header written as `{"hashed": false}`, definite lengths and shortest heads. `Statement.FullHash()` is Blake2b-256 of `Canonical()`, signature included; it is the **binding hash of the version 2 auth bytes** (the commitment of one authentication to the exact bytes presented), and `VerifiedBinding.FullHash()` returns it. It is NOT the registry's de-duplication key (OUT-013): a key holder can produce many valid signatures over one statement, each with its own full hash. Two different statements (another payload, another signature bit, another address form, another signer) have different full hashes. Because the strict parser admits one encoding, `Canonical()` of every accepted input equals the input.
- **SPO-Xrelaybind-OUT-007** `ParseCOSEKey` reads the `COSE_Key` that travels with a statement: at most 128 bytes, a 32-byte Ed25519 key, and exactly the bytes `cose.EncodeKey` writes (no extra pair, no other order, no non-shortest head). A key that is a small-order point, in any encoding, or is not a canonical point encoding is `ErrWeakKey` (SEC-008).
- **SPO-Xrelaybind-OUT-008** Test vectors are committed (`internal/domain/relaybind/testdata/vectors.json`) and regenerated and compared by a test: bindings (a key-hash address and a Shelley base address; the shortest and the longest lifetime; `until` at `MaxTime`), wallet-signed revokes (one device and all), device-signed revokes with the signing bytes, and near-miss payloads. They are marked as software-key vectors, not frozen for hardware. `testdata/check_vectors.py` recomputes the payloads, protected headers, `Sig_structure`, `COSE_Sign1` bytes, full hashes, statement identities, key hashes, fingerprints and device-revoke arrays with its own CBOR encoder, **verifies every Ed25519 signature with a hand-written RFC 8032 verifier** (standard library only; its "signatures verified" count counts successes only), shows with its own point arithmetic that every listed refused verification key (`rejected_public_keys`) is small-order or non-canonical, and checks that no near miss matches the canonical grammar. A Go test runs it when `python3` is on `PATH`; `SPO_REQUIRE_PYTHON=1` makes a missing interpreter a failure, and `tools/spo.nix` adds `python3` to `nativeCheckInputs` and sets it, so `nix flake check` always runs the check (the same variable runs the check of `internal/domain/mailbox`).
- **SPO-Xrelaybind-OUT-009** The client rule for `from` is `ChooseFrom(now, lastNotBefore) = max(now - 60 s, lastNotBefore + 1 s)`, where `lastNotBefore` is the latest tombstone time the client holds for the device (`NoTombstone`, -1, if none), clamped at 0. A `now` outside 0 to `MaxTime`, a tombstone outside -1 to `MaxTime`, and a result that leaves less than `MinLifetimeSeconds` before `MaxTime` are `ErrRange`.
- **SPO-Xrelaybind-OUT-010** The tombstone rule is a pure function. A binding is blocked when its `from` is not later than some applicable tombstone not-before (`NoTombstone` is skipped); the three tombstones that apply are `Tombstones{Pair, All, Device}` (OUT-014). `MergeTombstone(current, incoming)` is the maximum, so a stored tombstone is never lowered, and `Tombstones.Merge(scope, notBefore)` applies it to one scope. `TombstoneExpired(notBefore, now)` is true only once `now > notBefore + MaxLifetimeSeconds`: a binding with `from = notBefore` and `until = from + MaxLifetimeSeconds` still verifies at `now == until` (`now <= until`), so the tombstone is kept through that second. There is no variadic "allowed" function: a call with no tombstones must not mean "allowed" (revision after the package review).
- **SPO-Xrelaybind-OUT-011** `IsReserved(payload)` is true for a payload whose first bytes are `spo-` or `spo/` (lower-case, from the first byte). The generic message-signing path will refuse such a payload, before any hashing (ADR 0014 decision 3, work package 3); every statement payload of this package is reserved.
- **SPO-Xrelaybind-OUT-012** The relay's invalidation predicate (revision of ADR 0014 decision 7 after the package review): `Invalidated(stored Binding, merged Tombstones)` is true exactly when the stored binding's `from` is not later than some applicable tombstone. On a verified revoke the relay ALWAYS records the tombstone (the maximum, OUT-010), and deletes the binding, closes the device's sessions and deletes its queued mail ONLY when `Invalidated` is true for the binding it stores. A revoke older than the stored binding changes nothing but the tombstone: after "forget this device" and a re-login with `from = not-before + 1`, the client's own re-sent revoke (ADR decision 8: re-sent on every connection) or anyone replaying the revoke bytes (a revoke names no relay) cannot wipe the newer binding or its mail. A revoke whose not-before is at or after the stored `from` does invalidate it.
- **SPO-Xrelaybind-OUT-013** Two distinct identifiers, named by use. `Statement.FullHash()` / `VerifiedBinding.FullHash()` (OUT-006) includes the signature and is the **commitment in the v2 auth bytes**. `VerifiedBinding.StatementID()` (and `VerifiedRevoke.StatementID()`) is Blake2b-256 of the canonical CBOR array `["spo/relay-statement-id/v1", K (28 bytes), payload]`: the wallet key hash and the exact payload, **no signature and no header bytes**; it is the key of the registry's de-duplication and of "one binding per device". Two valid signatures by one key over one statement (different nonces, which a key holder can always make) have different full hashes and one statement identity; another payload or another signer has another identity; another address form or protected-header key order of the same key and payload has the same identity and another full hash.
- **SPO-Xrelaybind-OUT-014** Three tombstone scopes (revision of ADR 0014 decisions 7 and 8). `ScopePair`: `(K, device)`, from a wallet-signed revoke of one device. `ScopeAll`: `(K, all)`, from a wallet-signed revoke of "all". `ScopeDevice`: the device under ANY key, from a device-signed revoke, which carries no wallet key and so cannot be stored under `(K, device)` when the device is not bound where it arrives; without this scope the device's old binding could be presented again. `VerifiedRevoke.Scope()` gives `ScopePair` or `ScopeAll`; a verified device revoke is `ScopeDevice`. `Admit(vb, Tombstones{Pair, All, Device}, now, policy)` is the relay's one admission function and takes all three; `NoTombstones()` is the value with none (the zero value is not "none": 0 is a valid not-before, so it fails closed for a `from` of 0).
- **SPO-Xrelaybind-OUT-015** The client waiting rule: `PlanFrom(now, lastNotBefore, skew)` returns the earliest `from` (`ChooseFrom`, OUT-009) and `wait = max(0, from - skew - now)` seconds before the relay will accept it, that is, it waits exactly when `last + 1 - skew > now`; the wait is at most `skew + 1` seconds, so the client waits and does not ask the wallet to sign again. On a binding refusal that the rule does not explain, the client backs off (a growing delay, a small limit on tries) and tells the operator; it does not ask the wallet to sign a new binding, because a relay that refuses for a reason the client cannot see will refuse the next signature too. `skew` outside 0 to `SkewSeconds` is `ErrRange`.

## Preconditions and failures

- **SPO-Xrelaybind-PRE-001** Sizes are checked before work and before any allocation: the whole `COSE_Sign1` is at most `MaxSign1Bytes` (512, checked before the parse), the protected header at most 128 bytes, the payload at most `MaxPayloadBytes` (120), the address at most 57 bytes (and exactly 28, 29 or 57, PRE-014), the signature exactly 64, the `COSE_Key` at most `MaxKeyBytes` (128). An input that claims a length of 2^32 or 2^64 - 1 is refused after its head, with less than 1 KiB allocated.
- **SPO-Xrelaybind-PRE-002** A non-shortest integer or length head is refused (`ErrNotShortest`), at every position of the structure.
- **SPO-Xrelaybind-PRE-003** An indefinite length is refused (`ErrIndefinite`), at every position.
- **SPO-Xrelaybind-PRE-004** A tag is refused (`ErrTagged`), at every position, including tag 18 on the whole array.
- **SPO-Xrelaybind-PRE-005** A duplicate map key is refused (`ErrDuplicateKey`), in the protected header and in the unprotected one.
- **SPO-Xrelaybind-PRE-006** Any protected-header key other than the integer 1 and the text `address` is refused (`ErrProtectedKey`).
- **SPO-Xrelaybind-PRE-007** A `hashed` key in the protected header is refused (`ErrHashedInProtected`), whatever its value.
- **SPO-Xrelaybind-PRE-008** An unprotected header other than the map `{"hashed": false}` is refused (`ErrUnprotected`): a bare integer, an empty map, `true`, another key, an extra pair, null, and any other item.
- **SPO-Xrelaybind-PRE-009** A payload that is not an embedded byte string is refused: absent (null, detached) is `ErrDetached`, over 120 bytes is `ErrPayloadSize`.
- **SPO-Xrelaybind-PRE-010** A signature that is not a 64-byte byte string is refused (`ErrSignatureSize`).
- **SPO-Xrelaybind-PRE-011** A byte after the structure, or after the protected map inside its byte string, is refused (`ErrTrailing`).
- **SPO-Xrelaybind-PRE-012** A text string that is not UTF-8 is refused (`ErrNotUTF8`).
- **SPO-Xrelaybind-PRE-013** The protected algorithm must be present and equal -8 (EdDSA); anything else is `ErrAlgorithm`.
- **SPO-Xrelaybind-PRE-014** The protected address is a byte string of exactly 28, 29 or 57 bytes (`ErrAddress` otherwise, at parse). Verification accepts only these forms (revision after the package review; `cose.KeyBelongsToAddress` is not used because it checks neither the credential type, the length nor the structure): (a) the 28 bytes equal K; (b) 29 bytes, header type 6 (enterprise, key hash) or 14 (reward, key hash), credential equal to K; (c) 57 bytes, header type 0 or 2 (base address with a key-hash payment credential), where K equals the PAYMENT credential; K as only the stake credential is not a match, and header type 1 (script payment credential) is not an accepted form (owner decision, 2026-11-18: a wallet signing for a base address signs with the payment key, and one signing with the stake key presents the reward address). The network id (low nibble of the header) must be 0 or 1. A form not accepted (a script credential type, a pointer address, any other type, a network id above 1, a length that does not fit its header) is `ErrAddressForm`; an accepted form that names no key credential equal to K, including K in a script slot, is `ErrWrongKey`. `VerifiedBinding.AddressPart()` says which part matched (`PartKeyHash`, `PartEnterprise`, `PartReward`, `PartBasePayment`). The stake credential of a base address is not looked at, and may be anyone's: **callers display and log only the key hash K, never the address bytes**. Where a hardware tool and the vault path write the key-hash form by default (ADR 0014), the raw forms exist for an external CIP-30 `signData`.
- **SPO-Xrelaybind-PRE-015** A near-miss binding payload is `ErrPayloadNotCanonical`: another case, a leading, trailing or double space, a tab, a line feed or carriage return, a NUL or non-ASCII byte, a leading zero, a plus or minus sign, a hex, exponent or decimal number, an empty or 13-digit number, an upper-case or short or long or non-hex device, swapped or missing or extra fields, another label, a length over 120 bytes, `until` above `MaxTime`. Changing any one byte of a valid payload gives a refusal or a payload that re-renders to exactly those bytes.
- **SPO-Xrelaybind-PRE-016** The time bounds: `MaxTime` equals `mailbox.MaxTime` (253402300799, the end of year 9999; a test pins them, as this package cannot import the mailbox domain); a lifetime of exactly 1 hour and exactly 180 days pass, one second less and one second more are `ErrLifetime`; `from` of 0 is valid; `until` above `MaxTime` is refused.
- **SPO-Xrelaybind-PRE-017** A near-miss revoke payload is `ErrPayloadNotCanonical`: `ALL` or `All`, `all` with a device or with extra spaces, upper-case or short or long hex, a leading zero, a sign, an empty or 13-digit or over-`MaxTime` time, another label, a missing or misspelled `not-before`, an extra field, a binding payload.

## Security

- **SPO-Xrelaybind-SEC-001** `VerifyBinding(statement, verification key, authenticated device, relay time, policy)` runs the checks of ADR 0014 decision 3 in this order and each failure is its own sentinel: the verification key is not a small-order or non-canonical point (`ErrWeakKey`, SEC-008); the signature over `cose.SigStructure(protected as signed, payload)` (`ErrBadSignature`); the protected address is one of the accepted forms (`ErrAddressForm`) and names K, the Blake2b-224 of the verification key (`ErrWrongKey`, PRE-014); the payload parses and re-renders equal (`ErrPayloadNotCanonical`); the device in the payload equals the authenticated device (`ErrDeviceMismatch`); the lifetime is within the ADR's bounds (`ErrLifetime`) and within the policy (`ErrLifetimePolicy`, which is also `ErrLifetime`; SEC-011); `from - skew <= now` (`ErrNotYetValid`) and `now <= until` (`ErrExpired`). It returns a `VerifiedBinding` (SEC-010). `VerifyRevoke` runs the same key, signature and address checks, then a canonical revoke payload, then `not-before <= now + skew` (`ErrRevokeFuture`); a binding is not a revoke and a revoke is not a binding. **The device argument** is `party.FingerprintOf` of the Ed25519 and X25519 keys the client presented, and those keys must be the ones whose signature authenticated the session (the mailbox `VerifyAuth` signs the fingerprint): the caller computes it from the presented keys and never takes it from a frame field or from the statement being verified. With one computed value, ADR 0014 rule 6 (the payload's device equals the fingerprint of the presented keys and of the session) is one check. The identity is the hash of the verification key, never the header alone.
- **SPO-Xrelaybind-SEC-002** Nothing mutated verifies: for a valid statement every single-bit flip, every byte deletion, every byte insertion and every truncation is refused; so are the structured mutations (non-shortest heads, a duplicated key, a `hashed` key moved into the protected header, an extra protected key, a bare integer unprotected header, a tag added, a trailing byte, a payload upper-cased, with an extra space, a leading zero or a line feed, a payload for another device). The unprotected header is the only unsigned part; the strict parser admits one form of it, so no malleable variant is accepted.
- **SPO-Xrelaybind-SEC-003** The full hash is stable and exact: it depends on the statement alone, it is Blake2b-256 of the canonical bytes, and it differs for every different statement, including two valid signatures by one key over one statement. Signatures are unforgeable by anyone who does not hold the key but NOT unique (the holder can pick another nonce); uniqueness belongs to the statement identity (OUT-013), which excludes the signature.
- **SPO-Xrelaybind-SEC-004** Time arithmetic cannot overflow: times of a parsed statement are 0 to `MaxTime`; the comparisons are `now < from - skew`, `now > until` and `notBefore - skew > now`, never `now + skew`; a relay time anywhere in int64 gives a refusal or an acceptance, never a wrapped value; `ChooseFrom` checks its inputs before it computes.
- **SPO-Xrelaybind-SEC-005** Every length read from the input is checked against its bound before anything is allocated or sliced for it; a test runs hostile heads (2^32 and 2^64 - 1 byte strings, arrays and maps; an over-long input) and asserts under 1 KiB of allocation per parse. The skip of the unprotected header preallocates nothing from a claimed pair count and keeps no key list (a duplicate is found by walking the map again, quadratic in the pairs of one map and bounded by the 512 input bytes); the test asserts under 1 KiB per parse for a 512-byte input that claims 233 pairs and for maps of 100 and 160 real pairs. (A first version preallocated the key list: that input allocated about 6.3 KB.)
- **SPO-Xrelaybind-SEC-006** A statement cannot be confused with another signature: its payload starts with ASCII `spo-`, so it is reserved (OUT-011); the device-signed revoke is a CBOR array starting 0x83, as the v2 auth bytes are an array; a `Sig_structure` is an array starting 0x84 `Signature1` and is longer than the 32-byte transaction hash a witness signs; a binding does not verify as a revoke and a revoke does not verify as a binding.
- **SPO-Xrelaybind-SEC-007** A `Policy` may only tighten: the skew is 0 to `SkewSeconds` (300, `party.MaxHelloLifetime`) and the maximum lifetime `MinLifetimeSeconds` to `MaxLifetimeSeconds`; any other value (including the zero `Policy`) is `ErrRange` in `VerifyBinding`, `VerifyRevoke`, `VerifyDeviceRevoke`, `Admit` and `Policy.Validate`. `DefaultPolicy()` is the ADR's.
- **SPO-Xrelaybind-SEC-008** Small-order and non-canonical verification keys are refused (`ErrWeakKey`), in `ParseCOSEKey` and, before the signature check, in `VerifyBinding`, `VerifyRevoke` and `VerifyDeviceRevoke`. A point is small-order exactly when its y coordinate is 0 (two points of order 4), 1 (the identity), p-1 (order 2), or one of the two y values of the four points of order 8; the sign bit of x does not change y, so every encoding of the eight points is refused, including the non-canonical ones that set the sign bit with x = 0. A y of p or more (up to 2^255 - 1) is not canonical and is refused. Reason: with the identity point, R = identity and S = 0 verify for every message, so a statement "signed" by nobody verifies under the hash of that key. The check compares 32 bytes and allocates nothing. Vectors list the refused encodings and the Python check derives their order with its own arithmetic.
- **SPO-Xrelaybind-SEC-009** A binding is never accepted, registered or held before it is valid. `VerifyBinding` refuses `from - skew > now` (`ErrNotYetValid`), which is exactly "`from` is later than relay time plus the skew"; `Admit` repeats the window at the time of registration (`ErrNotYetValid`, `ErrExpired`). A binding dated years ahead therefore cannot be presented, so it cannot stay latent and occupy a device slot (a revoke's not-before is capped at relay time plus the skew, so such a binding could not be revoked in advance). A stored binding that is re-verified at registry load is valid, expired, or over a tightened lifetime policy (dropped), or, when the relay's clock was stepped back below its `from - skew`, not yet valid: it is then kept on disk and not served until the clock reaches it, never quarantined (SPO-Xmailbox-OUT-080, SEC-060; revised after the registry review: the first reading said "never not yet valid", which a board with no battery clock breaks).
- **SPO-Xrelaybind-SEC-010** `VerifiedBinding` and `VerifiedRevoke` have unexported fields only and are filled only by `VerifyBinding` and `VerifyRevoke`; they are read through accessors (`Key`, `Binding` or `Revoke`, `FullHash`, `StatementID`, `AddressPart`). Another package cannot build one (a composite literal that names or lists a field does not compile); a test asserts by reflection that no field is exported. `Admit` is the relay's one admission function: it refuses, in this order, a value no verification produced, the zero value (`ErrUnverified`); a `Policy` outside the ADR's (`ErrRange`); a binding not yet valid or expired at `now` (`ErrNotYetValid`, `ErrExpired`); and a `from` not later than every one of the three tombstones (`ErrRevoked`).
- **SPO-Xrelaybind-SEC-011** A relay with a tightened maximum lifetime answers a binding whose lifetime is within the ADR's bounds but over that maximum with `ErrLifetimePolicy` (which also is `ErrLifetime`), a class distinct from a malformed or out-of-bounds lifetime (plain `ErrLifetime`). Intended mapping for the relay session: the wire error code is still `7 binding`; the client, which knows the class from the relay's later announcement of its maximum, signs ONE new binding no longer than that maximum and never loops (OUT-015 back-off).

## Invariants

- **SPO-Xrelaybind-INV-001** `internal/domain/relaybind` imports only the standard library (no `os`, `net`, process, unsafe, `time/tzdata` or random-source package), `domain/cose`, `domain/party`, `domain/identity` and Blake2b (a test parses the imports of its own source files, and `internal/archtest` checks that the package's whole import closure holds nothing the relay may not link, such as `age`).
- **SPO-Xrelaybind-INV-002** Whatever `ParseStatement`, `ParseBinding`, `ParseRevoke` or `ParseCOSEKey` accepts is its own canonical form (re-rendering or re-encoding gives the input bytes), and no input makes a parser or a verifier panic (fuzz targets seeded with valid and hostile inputs; every seed is small).
- **SPO-Xrelaybind-INV-003** The lenient parser of `internal/domain/cose` is unchanged: a test shows it still accepts a non-shortest head, a bare integer unprotected header, an extra protected key, a `hashed` key in the protected header and a duplicate key, each of which the strict parser here refuses.

## Choices that go beyond the ADR text

- **Untagged only.** The ADR does not say whether a tag 18 is allowed. `cose.Sign1.Encode` (the software path) and CIP-30 `signData` write no tag, so a tagged `COSE_Sign1` is refused. If the device check shows that a hardware tool writes the tag, allow it then: the canonical form drops it.
- **Either protected key order.** The ADR names the protected header `{1: -8, "address": K}`. The protected bytes are signed, so another key order is not malleable; it is accepted and has its own hash. Duplicates and any other key are refused.
- **A single unprotected form.** The strict parser accepts only the bytes of `{"hashed": false}`. The ADR has the relay re-encode the unprotected header; since every other form is refused (the ADR lists them), `Canonical()` of an accepted input equals the input, and it is still computed from the parts.
- **Address forms (revised after the package review).** The first build accepted 28 to 64 bytes and trusted `cose.KeyBelongsToAddress`, which checks neither the credential type, the length nor the structure: a script credential address with K in the hash slot, trailing junk, a truncated base address and a base address with someone else's payment part all verified. The ADR requires the raw forms only for an external CIP-30 `signData`, so exactly the forms of PRE-014 are accepted: the key hash, a 29-byte enterprise or reward address with a key-hash credential, a 57-byte base address whose key-hash payment credential equals K. Pointer addresses and network ids above 1 are refused. This is the strictest set the ADR permits that still serves CIP-30; it is not looser than "the 28-byte key hash only" by anything but those raw forms. A base address that carries K only as its stake part is refused (owner decision, 2026-11-18): no honest wallet writes it, and it would show another party's payment address beside K. A stake key identifies itself by the key hash or the reward address; a wallet without a staking part uses its payment key.
- **Lifetime is part of `ParseBinding`, and `VerifyBinding` takes a `Policy`.** The brief and the ADR list the lifetime as a payload rule (rule 7); `VerifyBinding` evaluates it after the device check, in the ADR's order. A relay "may tighten the maximum, never raise it", so the maximum and the skew are the fields of a validated `Policy`.
- **The device argument.** The ADR's step 6 compares the payload's device with the fingerprint of the presented keys and of the session. The caller computes one fingerprint (`party.FingerprintOf`) and passes it.
- **The device-signed revoke** is specified in full by the ADR (array, label inside); no choice was needed beyond the typed bounds (not-before 0 to `MaxTime`, skew 0 to `SkewSeconds`).
- **Small-order and non-canonical keys are refused; signatures are not unique (revised after the package review).** The first build said that `crypto/ed25519.Verify` makes a signature unique and that a small-order key is harmless. Both were wrong. `Verify` refuses a non-canonical `s` but the holder of an ordinary key can make many valid signatures over one statement (different nonces); and with the identity point as the key, R = identity and S = 0 verify for any message. So small-order and non-canonical keys are refused (SEC-008), and the registry de-duplicates by `StatementID` (OUT-013), not by the hash that includes the signature (OUT-006).
- **A far-future `from` is refused at presentation (decision taken after the package review).** A revoke's not-before is capped at relay time plus the skew, so a binding dated beyond that cannot be revoked in advance. The existing rule `from - skew <= now` is exactly "from is not later than now plus skew"; it is kept, repeated by `Admit`, and stated as "a binding is never stored before it is valid" (SEC-009).
- **`Admit` takes a struct of tombstones** (`Tombstones{Pair, All, Device}`) instead of three positional integers, so that the (K, device), (K, all) and device-only values cannot be swapped by mistake, and it takes relay time and the `Policy` so that registration repeats the window.

## The software signing path (ADR 0014, work package 3)

Work package 3 builds the signing side for software keys: `internal/domain/relaywallet` (the wallet key type), the typed methods of `ports.RelayStatementSigner` (implemented by `native.VaultSignatures`; the hardware adapter answers "not supported"), `relayport.DeviceRevokeSigner` (implemented by `envelope.Local`), the use case `internal/app/relaybinding`, and the reserved-prefix guard on the generic message paths (SPO-Xidentity-SEC-007). `relaywallet` is a separate domain package so that `domain/relaybind`, which the relay binary links, stays free of custody types (INV-001). Hardware signing is work package 4 and is gated on the real-device check; no hardware capability row is added here. The command line (`bind`, `revoke`, `forget`, print and import for external wallets) and the storage of results are later packages.

- **SPO-Xrelaybind-OUT-016** `relaywallet.WalletKey` is a closed sum type: a value is made only by `FromPayment(custody.Key[custody.Payment])`, `FromStake(custody.Key[custody.Stake])` or the default-deny `FromRef(custody.KeyRef)`, never from raw key bytes, and its field is unexported. A `custody.Key` of any other role does not compile into the call. The typed constructors also refuse the zero `Key` (anyone can write `custody.Key[custody.Payment]{}`) and a reference whose identity is not a 28-byte key hash (a script, Calidus or Catalyst hash of the same size is refused). `KeyHash()` is the hash in the identity, K; it is the only name of the signer to display or log. The zero `WalletKey` is not a wallet key (`IsZero`).
- **SPO-Xrelaybind-SEC-012** A pool cold key, a committee cold key and every other role are refused at construction (`relaywallet.ErrRole`): `FromRef` accepts exactly the payment and the stake role and refuses an unknown role. A test enumerates `custody.Roles()`, so a role added later is refused until the constructor and the test are changed on purpose; it also names the cold roles and fails if one stops being cold. A test reads the parameter types of `FromPayment` and `FromStake`.
- **SPO-Xrelaybind-SEC-013** A key whose role history holds a cold role (`custody.RoleHistory.HasColdRole`) is refused at use (`relaywallet.ErrColdHistory`), even when the reference is labelled payment or stake; a history that cannot be read, or that belongs to another identity, is refused (`ErrHistoryUnreadable`: the cold-key rule fails closed); a use case built with no history source signs nothing (`relaybinding.ErrNoHistory`). The use case checks it before the signer is asked, and the vault signer checks it again before it opens the key. The history only grows, so a key once recorded cold never passes again. Revised after the security review: a key with NO known history is now refused too (SEC-020), and any role outside payment and stake is refused (SEC-019); the first build let both pass. What is not enforceable: a payment-labelled reference to a cold key that lives only on a device cannot be told apart here, which ADR 0014 decision 4 items 2 and 3 cover on the hardware path (work package 4). A key hash carries no role, and the relay cannot tell a pool id from a payment key hash.
- **SPO-Xrelaybind-IF-001** `relaybinding.Service.SignBinding(ctx, walletKey, device, lifetime, lastNotBefore)` builds the binding with `PlanFrom` on its injected clock (`from = max(now - 60 s, lastNotBefore + 1 s)`, OUT-009), `until = from + lifetime` (a lifetime of 0 is 90 days, or the policy's maximum when that is shorter), has the signer sign it with the protected-header address equal to the bare 28-byte key hash and the payload embedded and not hashed, then parses and verifies its own result (SEC-014) and returns the statement bytes, the COSE key bytes, K, the `Binding`, `StatementID` and `FullHash`. The results are copies. The use case stores nothing; a later package persists, per relay and device, the binding it holds (statement and COSE key), its pending revokes (kept until the revoked binding's `until`, ADR 0014 decision 8) and the latest tombstone not-before (the next call's `lastNotBefore`).
- **SPO-Xrelaybind-IF-002** `SignWalletRevoke(ctx, walletKey, target, notBefore)` builds the revoke of one device or of all the devices of the key, has it signed as IF-001, and verifies it with `VerifyRevoke` (SEC-015). The role and the history are checked first. A not-before later than now plus the skew, a negative one, one past `MaxTime`, and "all" with a device are `ErrPolicy` and nothing is asked of the signer.
- **SPO-Xrelaybind-IF-003** The device-signed revoke is made through a typed method, `relayport.DeviceRevokeSigner.SignRelayDeviceRevoke(notBefore) ([64]byte, error)`, never a callback over bytes: the implementation (`envelope.Local`) builds `DeviceRevokeBytes(own fingerprint, notBefore)` itself, so it can sign only that labelled array for its own fingerprint (INV-005). `SignDeviceRevoke(ctx, device, notBefore)` verifies the signature with `VerifyDeviceRevoke` and returns what the Revoke frame carries (fingerprint, both public keys, not-before, signature).
- **SPO-Xrelaybind-PRE-018** Policy bounds, checked before the signer is asked, each as `ErrPolicy` together with the reason: a lifetime is a whole number of seconds from one hour (`MinLifetimeSeconds`) to the policy's maximum (`ErrLifetime`, and `ErrLifetimePolicy` when only the policy's tightened maximum is exceeded); a `Policy` outside the ADR's (skew 0 to 300 s, maximum one hour to 180 days) is `ErrRange` inside `ErrPolicy`; a tombstone time outside -1 to `MaxTime` is refused; a not-before as above (IF-002). The zero `Policy` means `DefaultPolicy()`.
- **SPO-Xrelaybind-PRE-019** The wait rule is `PlanFrom` (OUT-015) on the injected clock: when `from - skew > now` the answer is a `*relaybinding.WaitError` (`errors.Is(err, ErrWait)`) with the wait duration and the `from` the binding will have; the signer is not asked, the use case does not sleep, and the wallet is not asked to sign a later binding. At a tombstone of now + skew the wait is one second; at now + skew - 1 there is none.
- **SPO-Xrelaybind-PRE-020** A clock before 1970, past year 9999, or within a binding's minimum lifetime of the largest time is `ErrClock`; so is a `from + lifetime` past `MaxTime`. A clock out of range is `ErrClock` for the revokes as well. Nothing is asked of the signer.
- **SPO-Xrelaybind-PRE-021** The hardware adapters (`hwcli.Session` and `hwcli.Lazy`) do NOT implement `ports.RelayStatementSigner` (revised after the security review: the first build implemented stub methods that answered `ports.ErrRelayStatementUnsupported`, which put the methods on every `MessageSigner`; SEC-022): there is no hardware signing until the real-device check of ADR 0014 work package 4, which adds a real hardware implementation of the narrow port. A test asserts that neither type implements it, by type assertion and by reflection on the method sets. The profile has no payment or stake `OpSignMessage` row on any vendor. `ports.ErrRelayStatementUnsupported` is kept, distinct from `ErrNotSupported` and from a refusal, for that implementation.
- **SPO-Xrelaybind-SEC-014** Self-verification of a binding: whatever the signer returns is parsed with `ParseStatement` and `ParseCOSEKey` and verified with `VerifyBinding` (for the device, the time and the policy of the call), and is then compared with what was asked for. A signer that returns anything else is `ErrSelfVerify` (never `ErrSigner`), and nothing is returned. The comparisons: signed by the requested wallet key (K); the protected-header address is the bare 28-byte key hash (the verifier also accepts an enterprise, reward and base address, which this signing path never writes); the payload is the one rendered; the binding parsed is the one asked for; the bytes are the canonical encoding. Cases a test feeds from a scripted signer: another key's signature under the wallet key, another key signing everything, a different binding or lifetime or device, a revoke instead of a binding, an extra protected-header key, a `hashed` key in the protected header, a tagged envelope, a hashed payload, a detached payload, a non-shortest or indefinite head, a trailing byte, an enterprise, base and script-credential address, another unprotected header, a small-order, foreign, unparseable or missing COSE key, a flipped bit, an empty or truncated statement.
- **SPO-Xrelaybind-SEC-015** Self-verification of a wallet-signed revoke is the same with `VerifyRevoke` and the revoke asked for (all against one device, another device, another not-before, a binding instead of a revoke are refused). A device-signed revoke is verified with `VerifyDeviceRevoke` against the signer's own identity: a signature by another key, for another not-before or another device, the zero signature, a signature over the bytes without the label, and an identity whose Ed25519 key is a small-order point are `ErrSelfVerify`.
- **SPO-Xrelaybind-SEC-016** The reserved-prefix guard (ADR 0014 decision 3). Every generic message-signing path refuses a payload for which `IsReserved` is true (`ErrReservedPayload`), on the data before any hashing, so a `Hashed` request is refused too, and before anything else is looked at. The paths found are `native.VaultSignatures.SignMessage`, `hwcli.Session.SignMessage` and `hwcli.Lazy.SignMessage` (before the session is opened). **Corrected after the security review:** the first text said that no use case or command signs an arbitrary message with a wallet key. That was wrong: the Calidus `sign` (`app/poolkey` `SignWithCalidusKey`, `native.VaultSignatures.SignText`, the command `pool calidus sign`) signs caller-chosen bytes with a raw Ed25519 signature and no COSE structure, with a key that is the payment key 0/0 of its mnemonic; the guard of this requirement does not cover it, and SEC-018 does. See SPO-Xidentity-SEC-007 and SPO-Xidentity-SEC-008.
- **SPO-Xrelaybind-SEC-017** The typed methods `SignRelayBinding` and `SignRelayRevoke` (`ports.RelayStatementSigner`) are the only way to produce a reserved payload. They render the payload themselves from the typed statement (so a statement the relay would refuse, such as a lifetime over 180 days, is refused before the key is opened), take the 28-byte key hash of the key they opened as the protected-header address, embed the payload un-hashed and sign the CIP-8 `Sig_structure`. For the software key of the committed vectors the vault produces exactly the bytes of `testdata/vectors.json` (the whole `COSE_Sign1`, the `COSE_Key`, and through the use case the full hash and the statement identity): Ed25519 is deterministic and the vault adds nothing.
- **SPO-Xrelaybind-INV-004** The guard does not change the other message uses: the ordinary CIP-8 message, the CIP-88 and CIP-36 registrations and the Calidus registration sign as before (their tests run unchanged), and the guard reads the payload, not a digest of it.
- **SPO-Xrelaybind-INV-005** `envelope.Local.SignRelayDeviceRevoke` signs exactly `DeviceRevokeBytes(its own fingerprint, notBefore)`: the signature equals an independent Ed25519 signature of those bytes, verifies with `VerifyDeviceRevoke`, does not verify for another not-before, another fingerprint, or bytes without the label, and a not-before outside 0 to `MaxTime` is refused with no signature. See INV-006 for the bound.

## Review fixes and print and import (ADR 0014 work package 3, security review)

- **SPO-Xrelaybind-SEC-018** No route that signs caller-chosen bytes raw (Ed25519 over the bytes, no COSE structure of its own) with a key that could also be a wallet key can produce a signature that verifies as a relay statement. The Calidus `sign` is such a route: a Calidus key made from a mnemonic is the payment key 0/0 of that mnemonic, so a raw signature over the bytes `cose.SigStructure(cose.ProtectedHeader(K), binding payload)`, wrapped by anyone into a `COSE_Sign1`, is accepted by `ParseStatement`, `ParseCOSEKey` and `VerifyBinding` as a binding of K to the attacker's device (proved by a test over the real use case and vault before the fix). The predicate `relaybind.LooksLikeSignedStatementInput(data)` is true for a COSE Sig_structure prefix (the array head `0x84`, `0x85` or `0x9f` followed by the text head and one of the context strings `Signature1`, `Signature`, `CounterSignature`, `CounterSignature0`, `CounterSignatureV2`) and for any data for which `IsReserved` is true; it is pure and allocates nothing. `ports.CheckSignableText` adds the rule of SPO-Xidentity-SEC-008 (valid UTF-8) and returns `relaybind.ErrRawStatementInput` for the predicate. The adapter (`native.VaultSignatures.SignText`, before any key is opened), the use case (`SignWithCalidusKey.Run`, before the store is read) and the command (`pool calidus sign`, before the workspace is unlocked) all apply it, so that a layer added or changed without one of them is still closed by the others. The other raw routes need no guard because they sign only a digest or a typed body: the registration digests (CIP-36, 32 bytes) and the registry messages (32 bytes) are shorter than any Sig_structure (a test), the CIP-88 registration signs a Sig_structure of a hash with a pool cold key that is never a wallet key, the transaction witness signs the id derived from the body bytes, and the device key signs only the typed array of its auth and its revoke. The full table is in ADR 0014.
- **SPO-Xrelaybind-SEC-019** The role-history rule is default-deny. `relaywallet.WalletKey.CheckHistory` refuses a history that holds any role outside payment and stake: a cold role is `ErrColdHistory` and every other role (drep, committee hot, policy, KES, VRF, Calidus, Catalyst vote, and any role added to custody later) is `ErrOtherRoleHistory`. A test enumerates `custody.Roles()` for both starting roles, so a role added later is refused until the rule and the test are changed on purpose. Reason: a policy key shares the payment signing-key envelope, and a drep or hot key is a key whose use is not a wallet's.
- **SPO-Xrelaybind-SEC-020** A key with no known role history is refused (`relaywallet.ErrNoHistory`; first build: it passed). The vault signer (`signStatement`) checks it with the store's own index (`labels.Index.RoleHistory`, the stored record that `labels.RecordRole` writes; the plain test store derives the same record from its key files, as `porttest` derives it from the homes), so a key the store has no history of is refused before it is opened. Over the real encrypted store a test records roles with `labels.RecordRole` and shows that a key with a cold role or another role, and a key with none, are refused and that a payment-only and a payment-and-stake history sign. The use case passes a history-less key only behind the option `Service.AllowUnknownHistory`, which nothing sets: it is reserved for device-only keys in work package 4, whose safety rests on the derivation-path check. A known history is always checked in full, with or without the option.
- **SPO-Xrelaybind-SEC-021** Self-verification pins the protected-header bytes on the software path: the statement's protected header must equal `cose.ProtectedHeader(K)` byte for byte (`ErrSelfVerify`). The verifier accepts the two keys in either order (the bytes are signed), but the vault never writes the other order, so a signer that does is not the signer asked for.
- **SPO-Xrelaybind-SEC-022** The narrow signing ports are not reachable from the broad ones. `ports.RelayStatementSigner` is its own interface and `ports.MessageSigner` does not embed it (a reflection test over both method sets), so a holder of a `MessageSigner`, or of one found through a signer directory, cannot sign a binding. Only the software vault adapter implements it (the hardware adapters do not, PRE-021). An archtest scans the identifiers of the non-test files of the module: `RelayStatementSigner` is named only by `ports/signatures.go`, `app/relaybinding`, `adapters/native` and `cmd/spo`; `relayport.DeviceRevokeSigner` only by `ports/relayport/devicerevoke.go`, `app/relaybinding`, `adapters/envelope` and `cmd/spo`.
- **SPO-Xrelaybind-SEC-023** Import verification (IF-004). A wallet answer is accepted only if all of these hold, each with its own test: the prepared request is intact, unexpired and of the right kind (`ErrPrepared`, `ErrPreparedExpired`); the bytes parse strictly and verify with `VerifyBinding` (for the prepared device and the clock) or `VerifyRevoke`; the payload is byte-equal to the prepared rendering; the signing key hash is the prepared one; the binding or revoke is the prepared one; the bytes are the canonical encoding; the role history of K, when the store knows the key, holds only payment and stake. A failure of any is `ErrImport` (a hashed payload, a tagged or non-canonical envelope, an address form `relaybind` refuses, a signature over another payload, device or time, another key). The bare-key-hash rule of the software path (SEC-014) is relaxed here only to the exact address forms `relaybind` accepts; the result reports which (`AddressPart`) and whether the store knows the key.
- **SPO-Xrelaybind-IF-004** Print and import for an external wallet (use-case half; the command flags are work package 8). `Service.PrepareBinding(ctx, ExternalWallet{KeyHash | Address}, device, lifetime, lastNotBefore)` and `PrepareRevoke(ctx, wallet, target, notBefore)` return a `Prepared`: the exact payload (text and hex), the address to sign for (the address given, in one of the exact forms of `relaybind.KeyOfAddress`, or the bare key hash), `Hashed` false (do not hash), the time prepared and the expiry ten minutes later (`PreparedLifetime`, on the injected clock), and `ID`, the Blake2b-256 of the canonical array `["spo/relay-prepared/v1", kind, K, address, payload, prepared at, expires at]`, which binds every other field so an import cannot be matched to a different request. Planning is SignBinding's (`planBinding`: zero device, lifetime, tombstone, clock, wait rule), so the refusals of PRE-018 to PRE-023 hold. A key the store knows with a history outside payment and stake is refused at prepare too; a key it does not know is allowed (it lives in the wallet). `ImportBinding` and `ImportRevoke` verify as SEC-023 says. Nothing is signed or stored by the use case; the caller keeps the `Prepared` between the two commands. **Remaining for work package 8:** the flags `--print` and `--import` of `spo party relay bind` and `forget`, reading and writing the hex, and persisting the `Prepared`.
- **SPO-Xrelaybind-PRE-022** A tombstone time more than skew + 1 s ahead of the clock is `ErrPolicy`, not a wait (a relay refuses a revoke dated beyond relay time plus the skew, so a tombstone can never legitimately be further ahead). At skew + 1 the answer is a two-second `WaitError`; at skew + 2 it is refused. The duration arithmetic of the wait is clamped (`waitDuration`: negative is 0, more than a Duration holds is the largest Duration), because the unchecked product of about 2.5e11 seconds wrapped to a negative Duration and a caller that sleeps and retries would have busy-looped.
- **SPO-Xrelaybind-PRE-023** The zero fingerprint is no device: a wallet-signed revoke that is not "all" and names it, and a binding to it, are `ErrPolicy` before any signer is asked.
- **SPO-Xrelaybind-INV-006** `relayport.DeviceRevokeSigner.SignRelayDeviceRevoke(notBefore, notBeforeBound)` takes the largest not-before the caller accepts, because the method has no clock; `envelope.Local` refuses a not-before above it (`ErrRevokeFuture`) and signs nothing, as for a value outside 0 to `MaxTime`. The use case passes relay time plus the policy's skew, the same bound it checks itself, so a bare identity cannot be asked for a revoke dated beyond what a relay accepts (such a tombstone would be a lasting denial of service against the device's own later bindings).

# Xmulti: selective import from one or more folders

This spec is not upstream behaviour. Upstream keeps one flat directory per working set; many operators instead keep pools and wallets in separate folders and write the pool descriptor's `ownerName` and `poolRewards` as relative paths (`../wallets/owner`). [Pfiles](../upstream/patterns/Pfiles.md) defines the file names an import recognises; this spec defines how an import reads several folders (and sub-folders to a bounded depth), lets the operator choose which owners to bring in and under which name, and makes the pool descriptors that name other owners by path usable in the flat workspace. The use case is `workspace.ImportWorkspace.Import`; the CLI is `spo workspace import`, the TUI flow drives the same command.

Terms: an **owner** is what `OwnerOf` groups (a pool, a wallet or another kind) in one folder; it is identified by its kind, name and folder. The **stored name** is the name it has in the workspace. A **source root** is a folder the operator gave; a **found folder** is a root or a sub-folder read below it.

## Interface

- **SPO-Xmulti-IF-001** `spo workspace import <dir>...` takes one or more folders and the options `--depth N`, `--only KIND:NAME[@DIR]` (repeatable), `--rename KIND:NAME[@DIR]=NEW` (repeatable), `--all`, `--dry-run`, `--format table|json` (json only with `--dry-run`), `--manifest FILE`, `--print-manifest` and `--manifest-out FILE`. `--owner NAME`, `--password-fd`, `--keep-encrypted` and `--overwrite` keep their meaning. KIND is `pool`, `wallet` or `other`; `@DIR` names the folder when the same name is in two.
- **SPO-Xmulti-IF-002** A manifest is a TOML file of keys `sources` (array of folders), `depth`, `all`, `only` and `rename` (arrays of the strings the flags take), nothing else: a key it does not define is refused, so is an array with no comma between two strings, and a comment may stand after a value or inside a multi-line array. A relative folder in it is relative to the manifest's own folder. `--print-manifest` writes the manifest the given flags stand for to standard output and `--manifest-out FILE` to a new file (never replacing one); neither imports anything. Reading a manifest and printing it again gives the same manifest.
- **SPO-Xmulti-IF-003** The TUI offers an import flow: the operator chooses one or more folders (picker restricted to folders, or a typed path), sees the owners found per folder with their would-import or would-refuse status, toggles the owners to import, is asked for a new name when two selected owners would collide, sees every descriptor rewrite before confirming, and confirms on a summary that shows the equivalent `spo workspace import ...` command line and can save it as a manifest. The TUI holds no import logic: it runs the command with the arguments it builds, first with `--dry-run --format json`, then without `--dry-run`.

## Discovery and selection

- **SPO-Xmulti-IN-001** Discovery lists, for each found folder, each owner with its kind, name, folder, the artefacts found and the outcome of the checks of [Pfiles](../upstream/patterns/Pfiles.md) (would import, or would be refused and why). It stores nothing and writes nothing to the sources.
- **SPO-Xmulti-IN-002** The depth is 0 by default (the given folder only), at most 4. A folder reached twice is read once. Discovery refuses, naming the bound, when it would read more than 200 directories or 20000 files in all.
- **SPO-Xmulti-IN-003** With a selection (`--only`, `--owner`, `--all`) only the selected owners are imported; nothing is imported merely because it was found. One folder at depth 0 with no selection imports everything found, as the import always did (the plain form, see PRE-009). Several folders, or a depth above 0, with no selection is refused, naming `--only` and `--all`.
- **SPO-Xmulti-IN-004** `--rename SEL=NEW` stores the selected owner under NEW; `NEW` must be a valid workspace name. Every artefact of the owner is stored under it, with the rest of the artefact's name kept (`.payment`, the numbers of KES keys and operational certificates, the counters, the key stem of an upstream-encrypted key).

## Refusals

- **SPO-Xmulti-PRE-001** A selector that matches no owner, or owners in more than one folder, is refused before anything is read further; the message names the folders.
- **SPO-Xmulti-PRE-002** A rename of an owner that is not selected, a second rename of one owner, a new name that is not a valid workspace name, and a new name that is the name (in any case) of an owner that was found and is not selected are refused before anything is written: a pool that names the unselected owner would otherwise be bound to the keys of the renamed one. A new name that is the name of a selected owner is valid when that owner is itself renamed away in the same run (a swap, a chain); otherwise it is the collision of OUT-002.
- **SPO-Xmulti-PRE-003** `--manifest` together with folders, `--depth`, `--only`, `--rename`, `--all` or `--owner` is refused; the manifest alone declares what is imported. The options that do not select (`--dry-run`, `--password-fd`, `--keep-encrypted`, `--overwrite`, `--format`) combine with it.
- **SPO-Xmulti-PRE-004** A pool whose `ownerName`, `poolOwner` (legacy string) or `poolRewards` resolves to an owner that was found but is not selected is refused, naming the owner to add, unless the workspace already holds a wallet of that name whose stake verification key, and payment verification key where either wallet has one, are byte-equal to the source owner's; with other keys the pool is refused, naming the workspace wallet and the source owner.
- **SPO-Xmulti-PRE-005** A pool whose reference that holds a path resolves to no owner found, and to no wallet the workspace holds under the last name of the path, is refused. In the plain form a bare name that is not found is kept as it is, as before: the workspace is expected to hold it; in the selective form it is refused (PRE-013). When a reference resolves to no source owner and the workspace holds a wallet of that name, the pool is accepted and a note on the descriptor row says it was bound to that wallet, with its stake key hash or stake address.
- **SPO-Xmulti-PRE-006** A reference that is an absolute path (leading `/` or a drive letter) or whose `..` leaves every source root is refused; it is never followed.
- **SPO-Xmulti-PRE-007** Any spelling of a reference that resolves to the same owner (`owner`, `./owner`, `../pool/owner`) gives the same stored name; an owner that several pools name is imported once.
- **SPO-Xmulti-PRE-008** A bare name in a descriptor is looked up first in the descriptor's own folder. Upstream resolves it against the directory the script ran in, which an import does not know, so when it is not in the descriptor's folder and exactly one owner of that name was found in the other folders of the run, it resolves to that owner: the owner must be selected (otherwise the pool is refused, naming it), the descriptor is rewritten when that owner is renamed, and a note says where the name was found. When several other folders hold an owner of that name, the pool is refused as ambiguous, naming the folders; the operator writes the reference as a relative path, or leaves the other folders out. The same resolution applies to every name inside `regWitness` (OUT-007).
- **SPO-Xmulti-PRE-009** The plain form (one folder, depth 0, and none of `--only`, `--all`, `--rename`; `--owner` is the old option and keeps it, including its row for every repetition of an owner: the second attempt meets what the first stored) imports every artefact, a pool descriptor included, exactly as before this extension: byte for byte, with no examination. Where a selective import would have refused or rewritten the descriptor (a path that resolves to nothing, an open `regWitness` whose names differ, a `poolName` that is not the file's), the descriptor row carries a note that it was stored as it is and not examined and what a selective import would do. In a selective import a leading UTF-8 byte order mark is accepted, kept, and does not prevent a rewrite; the other two cases are refused.
- **SPO-Xmulti-PRE-010** The verification-key comparison of PRE-004 and the note of PRE-005 are made against the workspace as it was before the import wrote anything (INV-003).
- **SPO-Xmulti-PRE-011** A pool is imported only if every owner its descriptor names (`ownerName`, `poolOwner`, `poolRewards`, and the names inside `regWitness`) is either imported in the same run or already in the workspace with the same keys. A pool that names a selected owner the plan refuses, for whatever reason (a rename onto a workspace owner, the case rule, a conflict with the workspace, a failed check of that owner, a password that does not open its keys), is itself refused, with a row that names the owner and its reason; this holds transitively. Two pools that name each other are both refused, and the row says it is a reference cycle. The one exception: an owner refused only because the workspace already holds an owner of the same stored name with byte-equal stake and payment verification keys is not imported, and the pool binds to the existing one, with a note saying so.
- **SPO-Xmulti-PRE-012** A reference binds to a selected owner only through the owner the source layout names (PRE-008, SEC-003). A name that no source owner has, but that this run stores another owner under (a rename target), is not satisfied by that owner: the pool is refused, saying that the name in the descriptor is not the renamed source owner, and that the operator must not rename onto it or must import the real owner. The note of PRE-005 describes the wallet as the workspace holds it after the run and is not printed for a name this run stores an owner under.
- **SPO-Xmulti-PRE-013** In the selective form a name in the descriptor (every field of OUT-005 and OUT-007) that no source owner has, that this run stores no owner under, and that the workspace holds no wallet of, is refused: the pool is never stored naming a wallet nobody has. A name that only the workspace has is accepted with the note of PRE-005, which names the field and the wallet by its stake key hash.
- **SPO-Xmulti-PRE-014** In the selective form a name in the descriptor (every field of OUT-005 and OUT-007) that matches an owner of the sources, or an owner of the workspace, only apart from case (no source owner has exactly that spelling) is refused as ambiguous, naming both spellings; it is never bound to the owner of the other spelling.
- **SPO-Xmulti-PRE-015** A name that no source owner has and that only the workspace holds is the note of PRE-005, and the note says that no wallet of that name was found within the given folders and depth: an owner of that name that lies below the depth cannot be known, and the operator raises `--depth` if it exists.
- **SPO-Xmulti-PRE-016** In the selective form a descriptor with a key that occurs twice in one object, or twice apart from case (`regPayName` and `REGPAYNAME`, `ownerName` and `OwnerName`, two slot keys `w.staking` and `W.staking`), at the top level or in any nested object (`poolOwner` entries, `regWitness`, its `witnesses`), is refused, naming the keys and the object. The programs that read a descriptor read exact keys, and the last of a repeated one, so such a descriptor names more than one thing and the import cannot say which it binds. The plain form stores it as it is and its row carries a note (PRE-009).

## Outputs

- **SPO-Xmulti-OUT-001** In the plain form an owner that passes is written in one atomic update of the workspace store of its own, whole or not at all, as in [Pfiles](../upstream/patterns/Pfiles.md); a failed owner leaves nothing. This is the atomicity the import always had (per owner, not per run). The selective form stores the whole run in one update (INV-008).
- **SPO-Xmulti-OUT-002** Two selected owners with one stored name are refused before anything is written, naming both with their folders, and nothing of the run is imported; an owner with an artefact the workspace already holds under its stored name is refused unless `--overwrite`, as before, and the others are still imported (the owners that were refused in the plan do not stop the run; the ones that pass are stored together, INV-008). Names that differ only by case are one name here (OUT-012).
- **SPO-Xmulti-OUT-003** The fields of a pool descriptor that hold a path or a name derived from one are each examined; none is stored unexamined. The decision per field is in the table below. Only the fields the table lists as rewritten are changed.
- **SPO-Xmulti-OUT-004** `poolName` is rewritten to the pool's stored name when it differs from it (it held a path prefix, another name, or the pool is renamed).
- **SPO-Xmulti-OUT-005** `poolOwner[].ownerName`, the legacy string `poolOwner` and `poolRewards` are resolved (SPO-Xmulti-SEC-003) and rewritten to the stored name of the owner they name; a rename of that owner reaches every selected pool that names it.
- **SPO-Xmulti-OUT-006** `regCertFile` and `deregCertFile` must name `<pool>.pool.cert` and `<pool>.pool.dereg-cert` of the pool as found, with or without a folder; they are rewritten to the stored name of the pool, and the certificate artefact is stored under it. Any other value refuses the pool, naming the field and the value. A certificate that is named and not in the source is not imported and the descriptor is stored as it is, with a note (the import has never checked this).
- **SPO-Xmulti-OUT-007** A descriptor with an open multi-witness registration (`regWitness`) is carried only when no name in it changes: the pool's name, the owners' names and the paying wallet's name are the same after import. Each name inside it is resolved as a bare name by the one resolver of the descriptor (INV-005), with the outcomes of PRE-004, PRE-005, PRE-008, PRE-011, PRE-012 and PRE-013, and must then map to the final name it already has. The names are `regPayName`; the slot keys `<pool>.node` (the cold-key slot), `<owner>.staking` (an owner's slot) and `<pay>` (the payer's slot, no suffix); and the pool name inside each file name of `metadataFilesList`. The other members (`id`, `type`, `ttl`, `regPayAmount`, `regPayReturn`, `txBody`, `hardwareWalletIncluded`) hold no name. Otherwise the pool is refused, naming the reason; a registration state that points at names the workspace does not have is never stored.
- **SPO-Xmulti-OUT-008** `regProtectionKey` is not a path and is left alone (it is secret, see [Pfiles](../upstream/patterns/Pfiles.md)); `poolMeta*`, `poolExtendedMetaUrl`, `poolRelays`, the pool id and hash fields and the registration and retirement state are left alone. Any other top-level string whose value looks like a path is left alone and noted.
- **SPO-Xmulti-OUT-009** The result table shows each owner's folder and stored name, and every descriptor rewrite as pool, field, old value and new value; the dry run, the JSON plan and the TUI summary list the same rewrites before anything is confirmed.
- **SPO-Xmulti-OUT-010** `--dry-run` reads and checks everything, writes nothing and prints the plan; the exit status is not zero when any selected owner would not be imported or the selection is invalid.
- **SPO-Xmulti-OUT-011** A `--rename` target that the workspace already holds as an owner of any kind is refused unless `--overwrite`. When an owner's stored name is an owner the workspace already holds, the consistency checks of [Pfiles](../upstream/patterns/Pfiles.md) (node counter against the cold verification key, KES counters, signing key against verification key, address against keys) run over the artefacts the workspace holds under that name together with the incoming ones, the incoming replacing those of the same reference; a failure refuses the owner. The coherence of the whole result is decided by OUT-016. With `--overwrite` the artefact rows say which existing artefacts are replaced (in the dry run, would be).
- **SPO-Xmulti-OUT-012** Owner names that differ only by case (`Owner`, `owner`) are a collision: two selected owners with such stored names are refused as in OUT-002 until one is renamed, and an owner whose stored name differs only by case from an owner the workspace holds is refused.
- **SPO-Xmulti-OUT-013** In the plain form with `--overwrite` the artefact rows say which existing artefacts are replaced (in the dry run, would be), as OUT-011 says for the selective form, and an incoming cold verification key or issue counter that replaces the artefacts of a workspace pool holding a different cold key carries a note naming both keys. These are notes only; the plain form refuses nothing it did not refuse before.
- **SPO-Xmulti-OUT-014** A selective import never deletes an artefact of the workspace. Into an owner of that name the workspace already holds, with or without `--overwrite` (OUT-016), the result is the existing artefacts together with the incoming ones, the incoming winning only with `--overwrite`, and the owner is imported only if that result is one coherent owner: every existing artefact the import does not replace (signing keys, verification keys, hardware signing files, keys kept encrypted, issue and KES counters, certificates, addresses, numbered KES keys and operational certificates) is shown to belong with the keys the owner would then have. A verification key belongs when byte-equal to the result's; a signing key or hardware signing file when its verification key equals the result's; an address when derivable from the result's keys; a counter when its cold key is the result's; a certificate or pool record when the key pair it depends on is not replaced by another one; a payment key pair when a base address of the result ties it to the result's stake key. Anything that cannot be shown (a key kept encrypted, a hardware signing file without a readable verification key, an unknown kind) counts as not belonging. A refused owner's row lists the artefacts that stay and says to import under a new name or to remove the old owner deliberately first; nothing of the workspace changes. The plain form is not changed by this (OUT-013).
- **SPO-Xmulti-OUT-015** An upstream-encrypted signing key file imported with `--defer-encrypted` is not imported: its row is `failed` with the reason "left in the source", its owner is not imported, and nothing of it is stored, in the plain and the selective form.
- **SPO-Xmulti-OUT-016** Whenever the stored name of a selected owner is a name the workspace already holds (an artefact of any kind under it), the resulting artefact set (the workspace's artefacts together with the incoming ones; the incoming one replaces an artefact of the same reference only with `--overwrite`, otherwise such a clash is the refusal of OUT-002) is checked as a whole by one function, with or without `--overwrite`, and the owner is stored only if the result is provably one coherent owner: it is of the same kind (a wallet is never merged into a pool, or the reverse); every key pair in it matches (signing key and hardware signing file against verification key), and a pair whose halves come one from the workspace and one from the import and cannot be matched refuses; every address and stake address is derivable from its keys; a payment key and a stake key belong together only when a base address of the result ties them, or they are the same on both sides, or both come from the workspace, or both from the import; every certificate names the key of the result it is about; the issue counter names the result's cold verification key; every operational certificate in it names the result's cold verification key and its hot key is the KES verification key of the same number; the KES counters agree with each other and are not behind the numbered KES keys. Anything that cannot be verified (a key kept encrypted, a hardware signing file without a stored verification key, an artefact of a kind the check does not know) refuses the owner unless it is the same on both sides. A refused owner's row names the artefacts and says to import under a new name; nothing of the workspace changes. A coherent addition (the next numbered KES key and operational certificate of the same cold key, the same owner again) is stored and its row notes what was added. The plain form is not changed by this (OUT-013).
- **SPO-Xmulti-OUT-017** A pool that has witness transfer files (`<pool>_<slot>_<id>.witness`, [Pfiles](../upstream/patterns/Pfiles.md) OUT-023) is refused when the pool, or an owner named in the slot, is stored in this run under another name: the files keep the old name in their file name and in their content, so they would name an owner that no longer exists under that name.
- **SPO-Xmulti-OUT-018** In the check of OUT-016, every pool record that carries or implies the pool id is compared with the pool id (the blake2b-224 hash) of the cold verification key of the result: the descriptor's `poolID` (hex) and `poolIDbech` (bech32, decoded), the `.pool.id` and `.pool.id-bech` files, and the pool id inside a registration or retirement certificate (the operator hash that follows the certificate type, decoded, not searched for). A record of another pool, or a record that names an id when the result has no cold key to compare it with, refuses the owner, naming the artefact. Calidus registration files are not decoded.
- **SPO-Xmulti-OUT-019** A merge into an existing owner (OUT-016: the result keeps an artefact of the workspace's owner and takes one from the import) needs an identity anchor in addition to OUT-014 and OUT-016: at least one verification key (or hardware public key, or a signing key that derives it) that both sides have and that is the same, or an artefact of one side that names a key of the other: an issue counter, operational certificate, registration or retirement certificate or id file for the other side's cold key, or a stake certificate, stake address or address for the other side's stake or payment key. With none the owner is refused: nothing shows that the source owner and the workspace owner of this name are the same; import it under a new name (`--rename`). A result that replaces every artefact of the workspace's owner, or adds nothing, is not a merge. The row's note says which anchor was verified.
- **SPO-Xmulti-INV-001** The sources are only read: nothing in them is created, changed, locked or deleted.
- **SPO-Xmulti-INV-002** A descriptor that needs no rewrite is stored byte for byte. One that does is stored with only the bytes of the changed string values replaced: the order of its fields, its spacing and every other value are exactly as in the source.
- **SPO-Xmulti-INV-003** The workspace is read once, before the first write of a run. Every resolution and check that depends on it (a wallet of that name, its keys, the artefacts that would be replaced, the owners of a name) uses that snapshot and the planned stored names, never the state the run has produced so far, and the dry run and the real run share one planning path: the dry run's plan is what the real run does. The pool descriptors of the workspace are read with the rest, so that INV-009 can be decided.
- **SPO-Xmulti-INV-004** Every selected owner's outcome is decided in the plan, before anything is written, in dependency order: an owner that a pool names is decided before the pool, whatever the order of the folders. Every check that can refuse an owner and needs no write runs in the plan (rename and case rules, conflicts with the snapshot, the union checks, the key pair, address and counter checks, the decryption of upstream-encrypted keys with the supplied password); only a failure of the write itself happens at execution. Execution follows the plan: owners that others name are written first, inside the one update of INV-008. A pool is never written while naming an owner of this run that was not stored.
- **SPO-Xmulti-INV-005** Every name in a descriptor that refers to an owner (`poolOwner[].ownerName`, the legacy string `poolOwner`, `poolRewards`, and each name inside `regWitness`, OUT-007) is resolved by one function, which returns the stored name, a note, a refusal and the selected owner depended on. No field has a resolution of its own. The values are read with the reader the consumers use (exact keys, in file order; for `regWitness` the domain's own parser of the names), never with a case-insensitive decoding.
- **SPO-Xmulti-INV-006** After any selective run, every name a stored pool descriptor carries refers to a wallet that (i) this run stored from the source owner the layout names, or (ii) the workspace already held with byte-equal stake and payment verification keys to that source owner, with a note, or (iii) exists only in the workspace, no source owner of that name being found, with a note naming it by its stake key hash; otherwise the pool is refused. And no owner ever holds another owner's key material or counters (OUT-014).
- **SPO-Xmulti-INV-007** INV-006 is checked on the planned end state, independently of the resolution that produced the descriptors. After the plan and before any write, for every pool the plan would store and every name its final descriptor carries (`poolOwner[].ownerName`, the legacy string `poolOwner`, `poolRewards`, and each name inside `regWitness`, read from the final descriptor bytes by the domain's own accessors, `Owners`, the text of `poolRewards` and the names of `regWitness`, not by the enumeration that rewrote them), the workspace as the plan would leave it must hold (1) an owner of exactly that name that is a wallet with a stake verification key, (2) where the source layout names a source owner for that reference, whether or not it was selected, a wallet whose stake verification key, and payment verification key where both have one, are byte-equal to that source owner's, and (3) where it names none, the workspace's own wallet of that name as it was, with the note of PRE-005; the payer of an open registration is bound on its payment key instead (see the limits below). By identity, over the same end state: the `poolID` the descriptor records is the hash of the pool's cold key; a witness slot that records a key hash records that of the stake key of the wallet it names; two owner names of one descriptor do not resolve to one stake key (a name two labels would claim; both are shown). A name that differs from another owner's only by case also fails it. A pool that fails is refused with a row naming the field, the name and the condition. This check does not use the resolution of INV-005 to decide; it recomputes from the plan's final artefact sets and the source files. It covers every pool of the end state that names an owner this run stores, those the run does not store included (INV-009).
- **SPO-Xmulti-INV-008** The selective form stores the whole run in one update of the workspace store: every owner the plan stores, or none. The snapshot and both gates are read before it (the store cannot list, or open a secret, from inside an update, and decrypting an upstream-encrypted key is slow work), so the update first re-reads what the decisions rested on and refuses the run with the workspace-changed error when it moved: an artefact the snapshot held that is gone or has other content, or an artefact of the plan, or of the probe set of a name the run looked at, that exists now although it did not. A failed write, or a moved workspace, stores nothing; every row of an owner that was planned then says that nothing of the run was imported and why, and the plan rows are still shown. The dry run stores nothing. The plain form is unchanged (OUT-001).
- **SPO-Xmulti-INV-009** When a run would change the stake or payment verification key of a wallet the workspace holds, or make it no longer a wallet, every pool of the end state whose descriptor names that wallet (`ownerName`, `poolOwner`, `poolRewards`, the names of `regWitness`, read as INV-007 reads them) and that this run does not replace must still find the wallet it named. If one does not, the wallet is refused, naming those pools and the field; the keys of a wallet that does not change are not a reason. The pools that the run does store are held to INV-006 and INV-007.

| Descriptor field | Decision |
| --- | --- |
| `poolName` | rewritten to the stored pool name (OUT-004) |
| `poolOwner[].ownerName`, `poolOwner` (legacy string) | resolved, rewritten to the owner's stored name; refused when unresolvable (OUT-005, PRE-004 to PRE-006, PRE-008) |
| `poolRewards` | as `ownerName`; an empty value is left |
| `regCertFile` | rewritten to `<stored pool>.pool.cert`; any other value refuses the pool (OUT-006) |
| `deregCertFile` | rewritten to `<stored pool>.pool.dereg-cert`; any other value refuses the pool (OUT-006) |
| `regWitness` (and the names inside it: `regPayName`, the slot keys, `metadataFilesList`) | each name resolved like an owner name (INV-005); carried untouched when no name changes; the pool is refused otherwise (OUT-007) |
| `regProtectionKey` | not a path; left alone, with the existing warning (OUT-008) |
| `poolMeta*`, `poolExtendedMetaUrl`, `poolRelays`, `poolID`, `poolIDbech`, `poolPledge`, `poolCost`, `poolMargin`, `regEpoch`, `regSubmitted`, `regCertCreated`, `deregCertCreated`, `deregEpoch`, `deregSubmitted` | not paths; left alone (OUT-008) |
| any other top-level string with `/` or `\` and no `://` | left alone, noted (OUT-008) |

## Limits

These are not requirements; they say what the checks above do not reach.

- Owners beyond the given folders and `--depth` are not known. A name a descriptor holds that no source owner has is bound to the workspace's wallet of that name with a note (PRE-005), and the note says that a wallet of that name below the depth cannot be known; such an owner is treated as workspace-only.
- Pool records and role keys are tied to an owner only through the checks above: signing keys, verification keys and hardware public keys by their key bytes, counters and operational certificates by the cold key they name, certificates, addresses and pool ids by the key hash they carry, descriptors by the names of OUT-005 and OUT-007 and the pool id of OUT-018. A record that carries none of these (`kes-expire.json`, metadata files, witness transfer files, Calidus registration files, a `regProtectionKey`) is tied only by its file name.
- The workspace is checked again at the write (INV-008) for the artefacts the run read, wrote or probed; an artefact of another kind added to an owner the run did not probe after the snapshot is not seen, and neither is a new pool that names a wallet the run replaces.
- A registration (`regWitness`) is read for its names, not validated as a transaction.
- The payer of an open registration is a payment key identity (ADR 0010): `regPayName` and its witness slot name `<wallet>.payment` (the payment account of a wallet) or a key-only address, and INV-007 binds them on the wallet's payment verification key, byte-equal to the source owner's (or, where the layout names none, the workspace's own wallet as it was); the wallet needs no stake key, so a selective import carries a pool paid from `<wallet>.payment` or from an enterprise wallet. A payer named by a wallet that has only a stake key is bound as an owner is. A rename of the payer wallet still refuses the registration (OUT-007).
- The checks guard against an operator's mistakes, not against a hostile source folder: the identity anchor of OUT-019 and the address ties are public data that a crafted folder can reproduce.
- A descriptor that starts with a byte-order mark is stored as it is in the selective form; the pool commands do not read it until the mark is removed.

## Security

- **SPO-Xmulti-SEC-001** A symbolic link is never followed: a linked folder is not entered, a linked file is listed as ignored and not read, at every depth.
- **SPO-Xmulti-SEC-002** The bounds of IN-002 apply before any file is opened for reading its content; a refused discovery reads no key.
- **SPO-Xmulti-SEC-003** A reference is resolved lexically and by what discovery found, never by reading the file system: `\` is a separator; a NUL, a line break, a leading `/` or a drive letter, `.` and `..` alone are refused; otherwise the value is joined to the descriptor's own folder and cleaned, the result must lie inside a source root, and only an owner discovered in that folder counts. A bare name is looked up as PRE-008 says.
- **SPO-Xmulti-SEC-004** Every name, folder and value taken from a source is printed through the text-safe writer; the JSON plan carries them in the same cleaned form.

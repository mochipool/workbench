# Xbackup: backup to a sink

This spec is not upstream behaviour. It specifies stages 1 and 2 of [ADR 0012](../../docs/explanation/adr/0012-server-backup-and-deployment.md): the sealed SQLite backup that `spo store backup` already makes is copied to a sink (a directory or an S3 bucket) and fetched back for the built `spo store restore`. No new cryptography is added: the file is sealed before it leaves the machine.

Stage 2 adds a **checkpoint**: a small object beside each backup, signed by a **checkpoint key** (a FIDO2 credential used as an OpenSSH security-key signing key, so the signature is a standard SSHSIG), that says what the backup is. The operator then keeps one long-lived pin (`<workspace id hex>:ck:<checkpoint key hash hex>`, optionally with `:<minimum sequence>`) and a restore takes the newest authentic backup of a sink nobody trusts. The key hash is SHA-256 of the SSH public key blob, the value `ssh-keygen -l` prints as the key's fingerprint. No real authenticator was used to write or test this stage.

Terms: a **sink** is the place the copy goes. An **object** is one stored file, named by a slash-separated relative **name**. The **head** of a backup is the sequence number and the MAC of the last row of its audit chain. A **pin** is `<workspace id hex>:<head sequence>:<head MAC hex>:<SHA-256 of the file, hex>`, printed after a backup and kept by the operator somewhere other than the sink. A **partial file** is the private, incomplete download of a pinned file.

## Interface

- **SPO-Xbackup-IF-001** `ports.ObjectWriter.Put(name, reader, size)` is create-if-absent. When the name exists with identical bytes it succeeds and changes nothing; when it exists with different bytes it fails with `ErrObjectExists`. There is no overwrite and no delete. The directory adapter links a synced temporary file into place with `link(2)`; the S3 adapter sends `PutObject` with `If-None-Match: *` on every write and, on a 412 or 409, reads the existing object and compares its SHA-256 with the body.
- **SPO-Xbackup-IF-002** `ports.ObjectReader` (`Get`, `Has`) and `ports.ObjectLister` (`List` by name prefix, giving name and size) are separate ports. `Get` of an absent name is `ErrObjectNotFound`.
- **SPO-Xbackup-IF-003** `ports.SinkProbe.Check` reports the kind (`dir` or `s3`), whether versioning is on, the default Object Lock mode and whether it has a default retention period, and whether the credentials are short-lived. An adapter only reports; the use case decides. Static credentials are reported as not short-lived without any request to the bucket.
- **SPO-Xbackup-IF-004** `ports.ObjectRangeReader.GetRange(name, offset)` reads from an offset to the end of the object and is its own port, not part of `ObjectReader`. An offset at or beyond the end is `ErrRangeNotSatisfiable`. The directory adapter seeks; the S3 adapter sends an HTTP `Range` request.

- **SPO-Xbackup-IF-005** `ports.SignatureFactor` (`EnrolSigner`, `SignAssert`) is a capability apart from `ports.FactorSource`: the unlock path never signs. `EnrolSigner` makes an ES256 credential for the relying-party id `ssh:spo-checkpoint` with user verification and returns the credential id and the 65-byte uncompressed P-256 point. `SignAssert` asks for an assertion over a 32-byte client data hash with user presence and user verification, and returns the flags, the counter and the ASN.1 DER signature; a source refuses an answer whose authenticator data is not the 37 fixed bytes for that relying party or lacks either flag.
- **SPO-Xbackup-IF-006** `InspectBackupFacts` reads, without a key and read-only, a file's workspace id, the end of its audit chain and the hash of its slot table (the policy and every slot row, as the audit rows of slot changes record it).

## External tools

- **SPO-Xbackup-EXT-001** Enrolling a checkpoint credential runs `fido2-cred -M [-v -q] -i /dev/fd/N <device> es256`: `-c 3` (credProtect level 3, confirmed in the answer, as for an unlock credential), no `-h` (no hmac-secret), user verification required, the PIN on stdin of a child with no controlling terminal, as for an unlock credential. The public key is read from the COSE key of the attested credential data (kty 2, alg -7, crv 1, two 32-byte coordinates); a credential made without the user-verification flag, or without such a key, is refused.
- **SPO-Xbackup-EXT-002** Signing runs `fido2-assert -G -p [-v | -t uv=true -t pin=false] -i /dev/fd/N -o /dev/fd/M <device>` with no `-h`, with the client data hash, the relying-party id and the credential id as input; the answer is four lines (client data hash, relying-party id, authenticator data, signature). The client data hash echoed must be the one sent, the authenticator data must be exactly 37 bytes with no attested-credential or extension data, and its flags must carry user presence and user verification. What the tools do for these options is read from their documentation and is unconfirmed on a device.

## Outputs

- **SPO-Xbackup-OUT-001** An object is named `backups/<workspace id hex>/<head sequence, 20 digits, zero-padded>-<SHA-256 of the file, hex>.spo`. A name is parsed strictly (lower-case hex, exactly 20 and 64 digits, no other characters); a name that does not parse is never trusted.
- **SPO-Xbackup-OUT-002** The pin is `<workspace id hex>:<head sequence>:<head MAC hex>:<SHA-256 hex>`. It is parsed strictly and has one spelling: lower-case hex, no leading zeros in the sequence (except 0 itself), and a head MAC of exactly the audit MAC length (32 bytes). It is not stored in the sink.
- **SPO-Xbackup-OUT-003** `store backup --sink URL` makes the backup with the existing code into a private scratch directory inside the workspace directory (through `ports.Scratch`), verifies it with the existing verification, checks that the file's own workspace id and head are those the backup reported, hashes it, puts it, reads it back and compares the SHA-256, and only then reports success. It prints the object name and a `Pin:` line followed by one sentence telling the operator to keep the pin somewhere other than the sink. The scratch directory is removed on every path.
- **SPO-Xbackup-OUT-004** `store backups --sink URL` lists the backups of this workspace id, newest first by head sequence. A name under the workspace's prefix that does not parse is listed as unrecognised and is never trusted. It asks for no passphrase and downloads nothing.
- **SPO-Xbackup-OUT-005** `store restore --sink URL --pin PIN` downloads the object the pin names, accepts it only when its SHA-256, workspace id and head are those of the pin, and then runs the existing restore on the file unchanged. Pushing and then fetching a backup into a fresh directory gives a workspace that opens and verifies, for the `standard` policy on a directory sink and for the `hardware` policy on a directory sink and on S3.
- **SPO-Xbackup-OUT-006** Every failure of a push or a fetch, including a cancelled context, ends with one sentence saying what state the sink and the workspace are left in and that the command can be run again (or, where it cannot succeed until something else is done, what that is). The sink and the workspace are left as they were, and the temporary directory is removed; the one thing kept is a partial download (OUT-009).
- **SPO-Xbackup-OUT-007** When the upload succeeded but the read-back failed or was interrupted, the push reports "uploaded but not verified" and fails, and says that running it again verifies the object without uploading it again. A re-run finds the object by its name, does not upload, reads it back and compares. When the response to an upload is lost after the store kept the object, a retry or a re-run ends in success through the `If-None-Match` and compare-hash path, and the sink holds exactly one object. When the object was not uploaded in this run and the sink says it exists but cannot return it (not found, or other bytes under a name that is their hash), the message says the sink is faulty or hostile and does not tell the operator to run again.
- **SPO-Xbackup-OUT-008** A push looks only at the object that its own file's hash names (`Has`, then the read-back). It never lists the sink, and never downloads, parses or verifies any other object, so a hostile listing costs nothing. Two backups of an unchanged workspace need not be byte-identical (they were in the test, which is not a guarantee); a second backup of the same head with other bytes is a second object, which is accepted and documented.
- **SPO-Xbackup-OUT-009** A fetch downloads to a private partial file in the workspace directory, named by the pinned SHA-256, made through `ports.Scratch`. A re-run with the same pin resumes it with a range request from the file's length (a stale partial longer than the object is discarded when the sink answers that the range cannot be satisfied). The result is accepted only when the whole file's SHA-256 equals the pin; otherwise the partial is deleted and the message says so. A partial file of another pin is removed (exact name pattern, regular file of this user only).

- **SPO-Xbackup-OUT-010** `store restore --sink` checks every flag combination that can be checked without the file before it downloads (an existing workspace needs `--force`; `--allow-weaker-policy` and `--allow-other-workspace` need `--force`; `--allow-older` is refused). After a hash-verified download, a restore refusal that is not about the file (a wrong passphrase or PIN, a cancelled prompt, a locked workspace, no terminal) keeps the verified file so that a re-run does not download again; a refusal about the content deletes it.
- **SPO-Xbackup-OUT-011** The checkpoint statement is canonical text: the first line `spo/checkpoint/v1`, then one `key value` line each, in this order, with no other line: `workspace` (hex), `sequence` (decimal), `head-mac` (64 hex), `slot-table` (64 hex), `sha256` (64 hex), `size` (decimal), `time` (UTC `YYYY-MM-DDTHH:MM:SSZ`; informational, used for no decision of a restore or a listing), `key-hash` (64 hex), and a line feed after every line. It is parsed strictly: lower-case hex, numbers without a sign, a leading zero or a fraction and within 64 bits, no duplicate or reordered key, no space, tab, carriage return or NUL in a value, no empty value, at most 4 KiB, and the text must re-encode to itself.
- **SPO-Xbackup-OUT-012** A checkpoint object is the statement, one blank line and the armored SSH signature (`-----BEGIN SSH SIGNATURE-----`, 70-column base64) of it in the namespace `spo/checkpoint/v1`, at most 16 KiB. The signature verifies against a key hash, not against a key the sink supplied: the public key travels in the SSHSIG and is accepted only when its hash is the pinned one; the statement must name that key hash too.
- **SPO-Xbackup-OUT-013** With a checkpoint key enrolled, `store backup --sink` signs after the object has been put and read back (nothing is asked of the authenticator before the sink's own checks and the read-back have passed), with one PIN and one touch, and puts the object as `<object name without .spo>.checkpoint` (create-if-absent; read back). It prints the exact pin of stage 1 and the long-lived pin `<workspace id>:ck:<key hash>` with the key hash and enrolment date beside it, the sentence that adding `:<sequence>` makes a restore refuse anything older, and the advice to record the pin from `checkpoint-key enroll` (or `show` at a trusted time), not from later backup output, because the sealed key record can be rewritten by whoever holds the daily factor and a modified build. With no key enrolled the behaviour is exactly that of stage 1. `store backup <dest>` with a key writes `<dest>.checkpoint` (mode 0600, never overwritten) and prints the long-lived pin.
- **SPO-Xbackup-OUT-014** A failure to sign after a verified upload is reported as "uploaded and verified, but NOT signed", with the exact pin, a non-zero status and the sentence that the command can be run again; the re-run finds the object, uploads nothing and signs. A valid checkpoint for exactly that file already in the sink is found and nothing is signed or put; a checkpoint under that name that is not valid is refused and never replaced. A signature from an authenticator that returned the wrong key, a missing flag or a bad signature is refused before anything is put. `--no-checkpoint` skips signing and says so.
- **SPO-Xbackup-OUT-015** `store restore --sink URL --pin <workspace id>:ck:<key hash>[:<minimum sequence>]` lists the workspace's objects, considers at most 16 candidates that have a checkpoint (and at most 256 names in all, with or without one) newest first by the sequence in the name, and for each reads its checkpoint (at most 16 KiB each, 256 KiB in all) and verifies it against the pinned key hash, the pinned workspace id, the minimum sequence and the object's own name (workspace, sequence and SHA-256 equal the statement's). Only then is the object downloaded, resumably, and its size, SHA-256, workspace id, head and slot-table hash checked against the statement before the built restore runs on it. The first candidate that passes is used; a candidate that fails is reported (the sink's text escaped) and skipped, and nothing is downloaded for a candidate whose checkpoint does not verify. Once a checkpoint has verified against the pinned key for sequence N (its signature, workspace, minimum sequence and name all check), N is a floor: if its object cannot be obtained or does not match the statement, the restore refuses, names N, and says an older backup can be restored only with an explicit `--below N`; a checkpoint that does not verify never sets a floor. `--below SEQ` (also on `store backups`) starts the search below a sequence. A failure of the transport or of the restore itself ends the search: an older backup is never restored because a newer one could not be fetched. No valid candidate is a refusal that says so and restores nothing.
- **SPO-Xbackup-OUT-016** `store backups --sink` shows, for each backup, whether a checkpoint sits beside it, and a checkpoint name is not listed as unrecognised unless no backup object sits beside it. With `--pin <workspace id>:ck:<key hash>` it also reads and verifies the checkpoints (at most 16) and says per backup whether each verifies. `store verify --backup FILE --checkpoint FILE.checkpoint --pin PIN` checks a local pair with no passphrase: the signature against the pinned key hash, the workspace and the minimum sequence, then the file's SHA-256 and size (the file is hashed first and nothing of it is parsed until both match), then its workspace id, head and slot-table hash against the statement.

## Preconditions and failures

- **SPO-Xbackup-PRE-001** An S3 sink is refused for a `standard` workspace, before any request to the bucket and before the passphrase is asked. The message names `spo workspace rotate --policy hardware` and the directory alternative (ADR 0012 owner question 8). A policy that is neither `hardware` nor `strict` is refused for S3 too.
- **SPO-Xbackup-PRE-002** An S3 sink is refused, before the workspace is unlocked (no passphrase, PIN or touch is asked), before the backup is made and before any byte is sent, unless versioning is on, Object Lock is on in COMPLIANCE mode with a default retention period, and the credentials are short-lived. Every unmet property is named.
- **SPO-Xbackup-PRE-003** A directory sink is allowed for every policy. For `standard` the warning of `store backup` about offline guessing is printed; for `hardware` and `strict` it is not.
- **SPO-Xbackup-PRE-004** A backup that fails the existing verification, whose file names another workspace than the one opened, or whose head is not the head the backup reported, is not sent.
- **SPO-Xbackup-PRE-005** A fetch is refused unless the file's SHA-256, workspace id and head sequence and MAC all equal the pin's, whichever name the object was fetched under: a tampered object, an older object under the pinned name, and a wrong field of the pin are each refused, and nothing is restored.
- **SPO-Xbackup-PRE-006** The file goes to the existing restore path unchanged, so every refusal that restore has (a weaker policy, opening through factors, an older or diverged backup, another workspace) still applies, and the temporary file is removed whatever the restore does.
- **SPO-Xbackup-PRE-007** `store restore --sink` accepts `--allow-older` under the counter rule of PRE-011 to PRE-014: the same restore runs, so an older backup from a sink never lowers a counter.
- **SPO-Xbackup-PRE-008** `store backup` takes exactly one of `<dest>` and `--sink`; `store restore` takes a `<backup>` file or `--sink` with `--pin`, never both, and `--sink` without `--pin` is refused.
- **SPO-Xbackup-PRE-010** A read-only `store verify` after a restore that died past the swap says that a matching `.head.next` is present and that opening the workspace completes the restore; it adopts nothing and changes no file.
- **SPO-Xbackup-PRE-011** A restore never lowers an operational-certificate counter or a KES counter of the workspace it replaces. It applies whenever the destination exists and can be opened, whatever its workspace id (a pool has the same anchor in every workspace that holds it) and whether or not the backup contains the destination's head: a chain that contains the head can still hold a lower counter (`pool opcert issue --counter N` writes N+1 whatever was stored; an import can replace a record). Per pool (keyed by the pool's cold key identity) the destination's `node.counter` (the issue counter, the number the next certificate takes) is carried into the restore's private copy when it is larger than the backup's or the backup has none, and `kes.counter-next` (the number the next KES key must have) when the destination's is larger; when the destination holds a KES key generated and not yet used for a certificate (current equal to next) that the backup does not hold (the same key: a hash of the key record must match, the same number with other key material is not held), next is carried as that number plus one, so the restored workspace does not generate the same number again; `kes.counter`, which names the newest key the restored file may not hold, is not carried. The writes are one ordinary audited write of the copy before the swap, with an event per counter (both values); the copy is verified again; the head file and the sidecar record the copy's new head. A counter that names another cold key in the backup is refused, naming the pool, and nothing is replaced. The values are printed only after the destination was opened. (The same pool in the destination and the backup is compared by anchor and cold key; a pool only in the destination has its counters carried.)
- **SPO-Xbackup-PRE-012** The destination's counters are read by opening it read-only with the credential presented for the backup; when that credential does not open it (its slots changed since the backup) the recovery material of the current workspace is used (the one `--allow-weaker-policy` also takes: `--recovery-key-in-fd` or a prompt, and under hardware `--current-recovery-device` and `--recovery-pin-fd`), asked for only then, and the command offers it without being asked to. Without it, or when it does not open the destination, the restore refuses, with or without `--allow-older` and also for a backup that contains the destination's head or for another workspace (`--allow-other-workspace`), with a message that names those flags, shows no counter value and never names `--accept-lower-counters`: a credential problem is not damage, and the flag is never honoured for it (if the credentials are lost, the operator moves the workspace file aside and restores into the empty directory, which compares nothing). A busy file, an I/O error and a factor that is refused are returned as they are and also never satisfy the flag. A read-only open can leave an empty `-wal` and `-shm` beside the destination until the swap or the next open.
- **SPO-Xbackup-PRE-013** Only a destination whose file is unusable counts as damaged: it does not parse as a workspace or fails its verification. The restore then compares nothing: it refuses, naming the risk and the flag, unless `--accept-lower-counters` is given; then it proceeds, prints a warning that names what to check on chain before issuing an operational certificate, and writes an audit event in the restored copy. A file that the credential unlocks but whose head file is ahead of it (older than its head file, or a head file that does not match; a genuine rollback, or a head file rewritten by someone who can write the directory) is not damaged: its counters are read and always carried as a floor, also under `--accept-lower-counters`. It refuses, saying that the true counters may be higher than the file's, unless the flag is given; with the flag the restore goes on with a warning (the head file is ahead of the file, the true counters may be higher still, check on chain) and an audit event. The flag never applies when the destination can be opened and shows no head-file problem. A file older than its head file that a matching restore sidecar explains (a restore that died past the swap; its carried counters are in the file) is read as it is and needs no flag. The refusal for a destination that is not a workspace at all names every flag the restore needs (`--allow-weaker-policy`, `--allow-other-workspace`, `--accept-lower-counters`) in one step.
- **SPO-Xbackup-PRE-014** The destination is not written before the swap: a crash after the counters were carried and before the swap leaves the destination and its head file as they were. The destination's head is recorded whenever its counters were read, and rechecked under the lock: if it moved on since (a certificate issued meanwhile), nothing is replaced, whether or not the backup contains the head.
- **SPO-Xbackup-PRE-009** A process that dies after the restore renamed the new file into place and before it wrote the head file leaves the restored file beside the old head file. The restore first writes `<file>.head.next` holding exactly the head record it is about to write, and removes it after the head file. An open whose head file disagrees with the file adopts `.head.next` (writes the head file, removes the sidecar, prints a notice) when it parses, names this workspace and names exactly the head the file itself verifies to; for an older or diverged backup this replaces the rollback error, for a newer one the open already succeeds. A sidecar that does not match is ignored, named in the rollback error, and never trusted. An attacker who can write the workspace directory gains nothing: they can already replace the head file.
- **SPO-Xbackup-PRE-015** A restore over a strict workspace that cannot be opened with the credential presented for the backup (its daily slot changed since) is refused with a message that says the workspace is strict, has no recovery path and can be opened only with one of its own enrolled authenticators, that none left means it cannot be compared, and that the route then is to move the file aside, restore into the empty directory and check every pool's counter on chain. It does not name the recovery key or its flags, and `--accept-lower-counters` is not honoured for it.
- **SPO-Xbackup-PRE-016** `workspace checkpoint-key enroll` refuses an authenticator that is the one the session unlocked the workspace with, and a credential that is a credential of a daily slot (the recovery composite's credentials do not count: the recovery authenticator may be the checkpoint authenticator, and the recovery token is then used at every backup). The device of the session and the checkpoint device are compared after the source resolved them (the token a missing `--fido2-device` auto-picks, a path with its symbolic links followed), not as typed. Before the credential is made the checkpoint token is probed with an assertion with user presence off for each daily slot's credential id and the daily relying-party id (`spo.<workspace id>`), and is refused if it recognises one: it is the daily token however it is named. Under `standard` there is no daily credential, so only the resolved-device rule applies. The probe has not been run on a real authenticator. The first key needs only the unlocked workspace. The record (public key, credential id, key hash, time) is one sealed record of the class Sensitive; `show` prints the key hash, the SSH fingerprint, the SSH public key line and the long-lived pin.
- **SPO-Xbackup-PRE-017** Replacing or removing an existing checkpoint key under `standard` or `hardware` needs the current recovery credential presented (the recovery key and, under hardware, the second authenticator) before any credential is made; without it nothing changes and no authenticator is asked.
- **SPO-Xbackup-PRE-018** Under `strict`, which has no recovery path, replacing or removing needs a signature by the EXISTING checkpoint key (namespace `spo/checkpoint-replace/v1`) over a canonical replacement statement (`workspace`, `old-key-hash`, `new-key-hash` or `none`, `time`), valid for that workspace, that old key and that new key (or removal) and recent (ten minutes); the signature must carry user presence and verification. A strict workspace is never asked for a recovery credential.
- **SPO-Xbackup-PRE-019** A workspace rotation keeps the checkpoint key record: it is a sealed record like any other and is re-sealed with them.
- **SPO-Xbackup-PRE-020** A restore does not drop the checkpoint key silently. When the destination opens (the counter rule's read-only open) and holds a checkpoint key record and the backup holds none, the record is carried into the private copy in the same audited write as the counters, with an audit event `checkpoint-key-carried` (key hash, "carried from the replaced workspace") and a printed line. When the backup holds a different key, the backup's is kept (it is what that file was sealed with), an audit event `checkpoint-key-differs` is written, and a warning names both key hashes and says that pins made with the replaced key no longer match new backups. The same key changes nothing. When the destination cannot be opened the existing refusals apply. The restored file's checkpoint key hash is always reported, and a restore with the long-lived pin says whether it equals the pin's key hash and warns if it does not (or if the file has no key), because new backups from it would not verify against that pin.
- **SPO-Xbackup-PRE-021** `store verify` reports that a checkpoint key record is present (it does not decrypt, so it does not fail on its content); `store verify --deep` parses the record strictly and fails, naming it, when it is malformed.
- **SPO-Xbackup-PRE-022** `init --policy hardware|strict` and `workspace migrate` print one line that no checkpoint key is enrolled and name `spo workspace checkpoint-key enroll`, for the policies that may use an S3 sink only; a `standard` workspace gets no such line.

## Security

- **SPO-Xbackup-SEC-001** The directory adapter refuses a name that is empty, absolute, has an empty, `.` or `..` component, a backslash or a control character, or that passes through a symbolic link, and writes nothing outside the sink directory.
- **SPO-Xbackup-SEC-002** The directory adapter writes files with mode 0600 and creates directories with mode 0700.
- **SPO-Xbackup-SEC-003** The directory adapter refuses a sink directory that is group- or world-writable, and a sink path that is not absolute.
- **SPO-Xbackup-SEC-004** The S3 adapter takes credentials only from the SDK's default chain and refuses credentials that are not short-lived: after retrieval it requires that they can expire, that they carry a session token and that they expire within 12 hours. Static access keys, environment credentials even with a session token, shared-file keys, a `credential_process` with no `Expiration` and one that asserts an expiry more than 12 hours ahead are refused. The message names SSO, IAM Roles Anywhere, IRSA and Workload Identity, says static access keys are not accepted and names the limit. No credential is printed or logged.
- **SPO-Xbackup-SEC-005** A download is bounded: an object larger than the cap (1 GiB by default) is refused, and the reader is limited, so a store that sends more than it listed is cut off.
- **SPO-Xbackup-SEC-006** Nothing is put that was not hashed from the verified local file: the name carries that hash, the S3 adapter sends the file's SHA-256 with `PutObject` so the store rejects a body corrupted in transit, and the object is read back and compared. Object Lock means a bad object cannot be deleted, so no upload happens before verification.
- **SPO-Xbackup-SEC-007** At the start of `Put` the directory adapter removes the temporary files of a previous crashed run in the object's directory: regular files of its own temporary-name pattern older than one hour, never a symbolic link or a directory. At the start of a push and of a fetch the use case sweeps the scratch directory: `.spo-backup-<digits>` directories and `.spo-fetch-<sha256>.partial` files older than one hour, only of the exact pattern, only regular files or directories of the right type owned by the current user, never a symbolic link.
- **SPO-Xbackup-SEC-008** The partial file has mode 0600 and holds only sealed bytes. It is refused when it is not a regular file, has more than one link or belongs to another user; a symbolic link planted at its name is removed (the link, never its target) and the download starts again. It is trusted for nothing: a wrong or stale partial can only cause a refusal.
- **SPO-Xbackup-SEC-009** Expired credentials, whether the provider says so or the store answers `ExpiredToken`, give a message that names re-authentication.
- **SPO-Xbackup-SEC-010** Waits are bounded: dial and TLS handshake have a timeout (also when a CA bundle makes the SDK supply its own HTTP client), a transfer that moves no data for the stall timeout (one minute by default) is abandoned, a transfer has a total deadline of a fixed allowance plus its size at a minimum rate (64 KiB/s) that is always armed and never derived from what the sink claims: it comes from the size the caller expects (the local file's size for a read-back, the 1 GiB cap for a fetch), and a response whose Content-Length exceeds it is refused at once, so a trickle, a huge claimed length or no length at all all end; other calls have a deadline, and the SDK's standard retryer makes at most three attempts.

- **SPO-Xbackup-SEC-011** The S3 adapter refuses an endpoint that is not https, whether it comes from the configuration or from `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3` or the shared configuration. There is no switch that allows plain http: tests run against a fake on 127.0.0.1 over TLS with a throw-away certificate that they trust (an HTTP client in an injected configuration, or `AWS_CA_BUNDLE` through the real chain), and the architecture test that forbids test-only switches in production code covers the rest. Versioning and Object Lock are reported by the endpoint itself: they guard against misconfiguration, not against a hostile store.
- **SPO-Xbackup-SEC-012** The scratch space refuses a workspace directory that is writable by its group or by others or that is not owned by the user running the program, so the partial file cannot be replaced by another user. An existing own file with a looser mode is made 0600 when opened.
- **SPO-Xbackup-SEC-013** `store restore --sink` passes the pinned SHA-256 to the restore, which checks it on its own private copy of the file before anything else is done with it, so the bytes installed are the bytes that were hashed; a mismatch installs nothing.
- **SPO-Xbackup-SEC-014** Every name or message a sink supplied (object names, listing entries, error text) reaches the terminal only after the control, format and non-printable characters are escaped; a name with an escape sequence or a carriage return is listed quoted and escaped.
- **SPO-Xbackup-SEC-015** An SSH signature is accepted only for the key type `sk-ecdsa-sha2-nistp256@openssh.com`, only when its signed flags carry both user presence (0x01) and user verification (0x04), and only when the ECDSA signature verifies (standard library, P-256) over `SHA-256(application) || flags || counter || SHA-256(signed data)`, where the signed data is `SSHSIG` || namespace || reserved || hash algorithm || H(message). Stock `ssh-keygen -Y verify` accepts a signature with either flag missing (confirmed against OpenSSH 10.6), so the flags are checked here and nowhere else.
- **SPO-Xbackup-SEC-016** The SSHSIG blob is parsed strictly: the preamble, version 1, a key blob of the expected type, curve and a point on the curve, the expected namespace (never empty), an empty reserved string, a hash algorithm of `sha256` or `sha512`, a signature blob of the expected type with its two integers, flags and counter, and no byte after any structure. The counter and the flags are signed: editing either breaks the signature.
- **SPO-Xbackup-SEC-017** Signatures made by this code verify with stock `ssh-keygen -Y verify -n spo/checkpoint/v1` for the key as an allowed_signers line, and not for another namespace or another message; the key hash is the SHA256 fingerprint `ssh-keygen -l` prints; a signature that `ssh-keygen -Y sign` made with a plain Ed25519 key is refused for its type. The test runs `ssh-keygen`; in the Nix check a missing `ssh-keygen` fails the test (`SPO_REQUIRE_SSH_KEYGEN`), elsewhere it skips.
- **SPO-Xbackup-SEC-018** A restore from the long-lived pin is bounded in what a sink can make it do: at most 16 candidates with a checkpoint examined (candidates without one are bounded by a separate cap of 256 names, so bare names cannot hide a valid backup), at most 16 KiB per checkpoint and 256 KiB of checkpoints in all, a stop at any limit says how many candidates were not examined and that a valid backup may exist below them, an object no larger than the statement's size (and the 1 GiB cap), and nothing downloaded for a candidate whose checkpoint does not verify.
- **SPO-Xbackup-SEC-019** Without a minimum sequence a long-lived pin proves authenticity, not freshness: a sink that hides the newer backups and replays an older checkpoint and object that were once valid is accepted. A pin with the newer sequence refuses it. The how-to says so.

## Invariants

- **SPO-Xbackup-INV-001** An interrupted upload (a connection broken before or in the middle of the body, a cancelled context) leaves no object and no partial object in the sink, and the directory adapter leaves no temporary file.
- **SPO-Xbackup-INV-002** The use case imports no adapter and no `os`, reaches a sink only through the object ports and scratch space only through `ports.Scratch`; the AWS modules are imported only by the S3 adapter.

## Not covered

What no test here can show: that the bucket is in a separate account, that its policy denies deletes and overwrites, and that an S3-compatible store other than AWS honours `If-None-Match`. Nothing was run against a real bucket.

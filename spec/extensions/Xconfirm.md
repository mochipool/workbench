# Xconfirm: transaction status and waiting for confirmation

This spec is not upstream behaviour: no upstream script reports whether a submitted transaction reached a block (they print the id and stop). It defines the status query `spo tx status`, the opt-in wait of the submitting commands, what each may claim, and the one place the port deliberately departs from upstream because of it: records that upstream writes when a transaction is *accepted* are written here when it is *confirmed* (hazard H9; the PR requirements). Providers are those of [ADR 0006](../../docs/explanation/adr/0006-chain-access-providers.md); the port is `ports.TxStatusReader`, narrow in the sense of [ADR 0008](../../docs/explanation/adr/0008-capability-typed-ports.md).

Terms: a **provider** is a configured chain source (Koios, Blockfrost, the node socket). **Seen** means a provider states the transaction is in a block or in its mempool. **Not seen** is a provider's positive statement that it has no such transaction. **Unknown** is the lack of a usable answer.

## Interface

- **SPO-Xconfirm-IF-001** `spo tx status <txid> [--confirmations N]` asks every configured provider once and prints one line per provider (its source name and its statement: in a block with the block height, slot and confirmations the provider gave, in the mempool, not seen, or unknown with the reason), then one verdict line. `--confirmations` is the depth that counts as confirmed, default 1.
- **SPO-Xconfirm-IF-002** The Koios reader is `POST /tx_status` with `{"_tx_hashes":[<id>]}`. A row for the asked hash with a number is in a block with that many confirmations; a row with an explicit null is not seen; every other answer (failure, empty array, another hash, two rows, no member, a non-integer, a count above 100,000,000) is unknown. The request asks intermediaries not to cache (`Cache-Control: no-cache, no-store`). Koios has no mempool view here.
- **SPO-Xconfirm-IF-003** The Blockfrost reader is `GET /txs/{hash}`. A 404 whose body is the documented Blockfrost error object (a JSON object with `status_code` 404) is not seen; a 404 with any other body (a proxy's page, another code) is unknown. A 200 for the asked hash with a block height is in a block, with confirmations counted from `GET /blocks/latest` (the latest height minus the block height plus one) when that is readable; every other status, a failure, an answer for another hash or a computed depth above 100,000,000 is unknown. Both requests carry `Cache-Control: no-cache`. Blockfrost has no mempool view here.
- **SPO-Xconfirm-IF-004** The node reader looks up the transaction's own outputs by reference (the first N, N from the transaction when known, else 8): an output in the UTxO set is in a block, with no height or depth. Otherwise the local tx monitor says whether the mempool holds it. Otherwise, when the caller gave the transaction's inputs (it has no collateral), an input that is still unspent proves the transaction is not in a block, and with the mempool not holding it the reading is not seen. Every other case is unknown, with the reason (SPO-Xconfirm-INV-006).
- **SPO-Xconfirm-IF-005** Every command that submits in light or online mode takes `--wait`, `--wait-confirmations N` (default 1) and `--wait-timeout DURATION` (default 5m, at most 24h). The flags are registered by one helper shared with the chain flags, and the wait runs after the command's own work has finished, on every transaction the command submitted (SPO-Xconfirm-INV-005).

- **SPO-Xconfirm-IF-006** A command that leaves a pending update (SPO-Xconfirm-PR-001: `asset mint`, `asset burn`, `pool register`, `pool retire`) waits by default in light and online mode, as with `--wait` at the default depth and timeout, and applies the update when the wait ends confirmed. `--no-wait` skips the wait and the command prints `spo tx settle` as the way to apply the update later; `--wait-confirmations` and `--wait-timeout` are accepted, `--wait` is accepted and redundant, and `--no-wait` with any of them is refused. Where no provider can say where a transaction is (online mode with no web provider and no node) the command does not wait and says so: it prints, for each pending record it created, the record, its transaction id and the exact command `spo tx settle`, and its exit status 0 then means "submitted or queued, the record is pending", not "confirmed". A transaction that was submitted always has a provider to wait on (every submitter is a configured provider and every configured provider can be asked where a transaction is), so "submitted and cannot be waited for" does not arise and has no exit code of its own. In offline mode nothing is submitted and nothing is waited for. A wait that ends in anything other than confirmed leaves the update pending, exits with the wait's exit code (SPO-Xconfirm-OUT-002) and prints the settle command.
- **SPO-Xconfirm-IF-007** `spo tx settle [--dry-run] [--confirmations N] [--transfer-file PATH]` settles every pending update of the workspace against the configured providers (SPO-Xconfirm-PR-011 to PR-015) and, when a transfer file is present, records the outcome of every transaction `offline execute` submitted that has none (SPO-Xconfirm-PR-022). It needs the `tx-status` capability and is refused before any prompt, naming it, where there is no provider (offline mode). Exit status: 0 when nothing is left waiting; 1 when an update could not be settled or a carried record of the transfer file was refused (SPO-Xconfirm-PR-016, PR-026); 21 when an update was discarded as expired; 20 when something waits; 22 when no provider answered; 23 when providers disagree; the worst of them when several.

## Invariants

- **SPO-Xconfirm-INV-001** A reading is not seen only from a positive answer of a provider that is fresh and, for a node, synced. A failed request, an answer that cannot be read, a web provider whose tip is older than ten minutes against this machine's clock (or unreadable), and a node that is not synced are unknown; none of them is ever reported as not seen.
- **SPO-Xconfirm-INV-002** Providers are combined, never trusted singly. Confirmed is stated only when every configured provider says the transaction is in a block at the depth asked. When one provider has seen it and another has not, the output says they disagree and names each provider's answer. When one has seen it and the rest gave no answer, the verdict is partial, not confirmed. Not seen is stated only when every provider answered not seen; one silent provider makes it unknown.
- **SPO-Xconfirm-INV-003** Confirmations count blocks from the one that holds the transaction to the provider's tip, the holding block being one; a provider that says in a block and not how deep counts as depth 1 and satisfies a wanted depth of 1 or less only. A confirmation is never called final: the message states the depth reached and that a rollback is possible at low depth.
- **SPO-Xconfirm-INV-004** A wait never submits, rebuilds or resubmits anything. It polls with a pause of 5 seconds that grows by half each time to at most 30 seconds, never sleeps past its timeout, and stops at once when the context is cancelled (Ctrl-C). The requests of each poll end by the time left of the timeout plus 5 seconds, so a wait ends within 5 seconds of its timeout however slow a provider is.
- **SPO-Xconfirm-INV-005** A wait changes no local state of its own. Whatever a command records on an accepted submission (the offline queue entry, the addresses marked used, the audit log, the pending update of SPO-Xconfirm-PR-001) is recorded before the wait starts and is not undone by a timeout, an expiry or a cancellation. The one thing a wait may do is apply a pending update, and only when it ends confirmed (SPO-Xconfirm-PR-001). Cancelling a wait does not cancel the transaction.
- **SPO-Xconfirm-INV-006** The node cannot prove absence from outputs: an output that was spent after the transaction was included is not in the UTxO set, so no unspent output looks the same as never included. The node reader therefore returns not seen only from an unspent input of the transaction (a transaction in a block has spent all its inputs) and never from outputs; a transaction with collateral is not judged this way, because one that failed phase 2 is in a block with its inputs unspent.

- **SPO-Xconfirm-INV-007** The id a wait asks about is computed from the bytes that were submitted, never taken from the provider's answer. A provider's answer that differs is an error naming both ids, and the submission is not waited for: no confirmed or expired statement is made about it. A submission whose id cannot be computed here is reported the same way. `offline execute` refuses the same mismatch as the other submitting commands, before it changes the queue.

## Outputs and exit codes

- **SPO-Xconfirm-OUT-001** `spo tx status` exits 0 when confirmed at the depth asked, 10 when seen but pending (in a mempool, or in a block not yet that deep), 11 when not seen by every provider, 12 when unknown or partial, 13 when the providers disagree, and 1 for any other failure (a bad id, no provider configured).
- **SPO-Xconfirm-OUT-002** A wait exits 0 when confirmed, 20 when the time ran out, 21 when the transaction expired, 22 when no provider answered for the whole wait, 23 when the providers disagreed at the end, and 130 when cancelled. The submission itself had succeeded in every case, and the output says so.
- **SPO-Xconfirm-OUT-003** A command that submitted several transactions waits for each in turn and prints every outcome. Its exit status is the worst, from mildest to worst: 0 confirmed, 21 expired, 20 timed out, 22 unknown, 23 disagree, 1 an id that could not be tied to the transaction, 130 cancelled. A cancellation ends the wait; the transactions not yet waited for are named with `spo tx status` as the way to check them.

## Pending records (hazard H9)

Upstream writes the asset record of a mint or burn, and the registration and retirement records of a pool descriptor, right after it submits or queues the transaction. A submission that is accepted can still never land. The port writes them when the transaction is confirmed.

- **SPO-Xconfirm-PR-001** The registration record of a pool (`regEpoch`, `regSubmitted`), the asset record of a mint or burn and (SPO-Xconfirm-PR-002) the retirement record of a pool (`deregSubmitted`) are not written when the transaction is accepted by the provider or queued. The command writes a **pending update** under the transaction's id before the transaction leaves, so a crash after the submission cannot lose it: the transaction id, the validity upper bound when it has one, whether it was only queued, the date, and the update to apply (kind `asset`, `pool-registration` or `pool-retirement`; a pending update without a kind is an asset update). Nothing else in the record changes until the update is applied. The consumption of working files stays as upstream and the port had it: the certificate file is deleted, and a registration's witness collection is removed, in one commit with the id of what was sent (`.multisig.submitted`). A definite refusal, or a failure before the transaction was sent, removes the pending update; one whose outcome is unknown (`ErrSubmitOutcomeUnknown`) keeps it, because the transaction may be in a block, and the error says so (SPO-Xconfirm-PR-008). The final record after settlement has the content the old path wrote (the stamp and, for a registration, the epoch are those of the submission).
- **SPO-Xconfirm-PR-002** The retirement record (`deregSubmitted`) follows SPO-Xconfirm-PR-001: the pending update is written through the delivery stage of the transaction pipeline (`txflow.Input.Stage`), right after the id of the assembled transaction is known and before it is queued or submitted, and the retirement certificate is deleted once the transaction was sent.
- **SPO-Xconfirm-PR-007** A registration submitted through a multi-party witness collection is the same `pool register` command and follows SPO-Xconfirm-PR-001. The coordinator's notice that a collection was closed because the registration was submitted (SPO-Xparty-INV-035) is unchanged: it takes a pending registration whose transaction id is the collection's body, or the `.multisig.submitted` id and a `regSubmitted` stamp after the first request, as proof that the transaction was sent. A registration that was sent and later discarded as expired is reported as discarded, not as submitted, because the pending record is gone and `regSubmitted` was never written.
- **SPO-Xconfirm-PR-008** The pending update is removed **only** on an error that proves the transaction did not leave: a definite refusal by the provider, or a failure before the transaction was sent. Every other end of a submission is an unknown outcome and keeps the update. The outcome is unknown after the request may have been sent and: a transport failure, a context cancellation or deadline, an answer that is not a transaction id, an HTTP status that is not a definite refusal, and **an accepted submission whose answered transaction id is not the id computed from the bytes sent** (`chain.IDMismatchError`, which matches `ErrSubmitOutcomeUnknown`; the provider took the transaction, so it may be in a block). Its message says the transaction may have been accepted and names `spo tx status <local id>`; the commands that keep a pending update add that `spo tx settle` settles it. The rule for the status of a web provider's submit endpoint is one function (`chain.SubmitStatusRefuses`): a 4xx is a definite refusal (400 carries the node's rejection; 401, 403, 404, 413 and the like stop the request before the transaction is looked at), except 408, 425 and 429, which do not say the transaction was not taken; a 5xx (a gateway can answer 502 after it forwarded the transaction), a 3xx and a 2xx other than the expected one are unknown. A node socket's rejection is definite; once the transaction was sent, every other error is unknown. A cancellation before the request was built is a plain error.
- **SPO-Xconfirm-PR-003** What the pool commands show for a pool with a pending registration or retirement says it is pending: `pool descriptor show` and `pool witness status` print a PENDING line naming the transaction, saying the descriptor does not record it yet and naming `spo tx settle`. They never present it as registered or retired.
- **SPO-Xconfirm-PR-004** The asset record of a mint or burn is written when its pending update is applied; the record's `lastUpdate` is the time of the submission or queueing, as before.
- **SPO-Xconfirm-PR-005** Pending updates are stored as `<txid>.pending` in the encrypted store, like every other record. `<txid>.asset-pending`, which the first version wrote for asset updates, is still read, as an asset update, by every settle path, and removed once settled.
- **SPO-Xconfirm-PR-006** A pending update holds no secret. It names the record, the pool or the policy, amounts and a stamp; it never holds a key, a passphrase or a witness. Strings in it that were chosen by a provider do not exist; strings printed from it (names, actions) go through the terminal-safe escaper.

## Settling

- **SPO-Xconfirm-PR-011** Settling asks, for each pending update, every configured provider where its transaction is and combines the answers by the rules of SPO-Xconfirm-INV-002 and INV-003 (the same `Assess`). It never submits, rebuilds or resubmits anything, and it never trusts a provider's answer as the id of the transaction (the id is the key of the pending record).
- **SPO-Xconfirm-PR-012** Per pending update: confirmed at the depth wanted on every provider is applied and the pending record removed; expired by the strict rule of SPO-Xconfirm-PRE-002 (it needs the validity bound the pending update stored; the condition must hold on two consecutive polls) is discarded with a notice and never applied; every other answer (in a mempool, not deep enough, not seen but not expired, partial, no usable answer, disagreement) keeps the update and reports waiting, unknown or disagree. A probe stops at the first poll that shows neither a confirmation nor a possible expiry, so settling costs one poll for a transaction that is simply waiting.
- **SPO-Xconfirm-PR-013** Settling is idempotent: an applied or discarded update is gone, so a second run finds only the rest and changes nothing.
- **SPO-Xconfirm-PR-014** Applying and removing the pending update are one store commit. A crash between the two leaves both or neither, so an update is never applied twice.
- **SPO-Xconfirm-PR-016** One pending update that cannot be applied or discarded (a damaged record, an unknown kind) does not stop the others: it is reported as a failed item, the remaining updates are still settled, the outcomes are still recorded in the transfer file, and the command exits non-zero (1) at the end. The failed update is kept.
- **SPO-Xconfirm-PR-015** `--dry-run` decides and prints what would be applied or discarded and changes nothing.

## Across the air gap

The offline machine has no provider. The machine that runs `offline execute` has one.

- **SPO-Xconfirm-PR-021** `offline execute` waits by default, as in SPO-Xconfirm-IF-006, when the entry it submitted carries a pending update (the entry's `spoAssetPending` field, which carries the update of any kind; the name is from the first version); `--no-wait` skips it, `--wait` waits for any entry. It applies nothing on the accepted submit. On a wait that ends confirmed it records the confirmation, and on a wait that ends expired (the strict rule, the outcome the wait already has) it records the expiry, in the transfer file's history (SPO-Xconfirm-PR-022) and applies the update where this workspace holds the pending record, or, for an asset update, a copy of the asset record. An accepted submit alone applies nothing anywhere. The existing records of the submit (the queue removal, the addresses marked used, the history line and `spoAssetSubmitted`) are unchanged.
- **SPO-Xconfirm-PR-022** Confirmation is recorded in the transfer file as an entry of the history of its own, after the entry of the submit: `{date, action, spoConfirmed: {txid, depth, sources}}` (`spoExpired: {txid}` for an expired transaction). The fields are the port's own, in the style of `spoAssetSubmitted`; upstream's scripts read the history by `date` and `action` and ignore them. Recording later, for entries submitted without waiting, is done by `spo tx settle` on the online machine (SPO-Xconfirm-IF-007): for every history entry that carries a submitted update and has no outcome it asks the providers (the probe of SPO-Xconfirm-PR-012) and records confirmed or expired, once; anything else is reported and left. `offline execute` is not re-run for this: its queue is empty after the submit.
- **SPO-Xconfirm-PR-023** `spo asset settle` (the settle from the transfer file, which serves every kind of pending update and needs no provider) applies a pending update only when the history records its transaction as confirmed. A transaction recorded as submitted and not as confirmed is reported as waiting and its update is kept. **What the offline machine trusts:** the transfer file is not authenticated (SPO-Ptransfer-SEC-002, concern E7 in `docs/development/go-reference-implementation-concerns.md`), so its confirmation or expiry entry is a claim. It can cause only the locally stored update of a transaction this workspace queued to be applied or discarded: never a different delta, never an unknown transaction. A recorded outcome counts only for a transaction the file records as submitted (a `spoAssetSubmitted` entry) and that is no longer in its queue; a `spoConfirmed` or `spoExpired` for an entry still queued or never recorded as submitted is reported as inconsistent, kept, not applied, and the command exits 1. A recorded confirmation applies the update stored here; the delta in the file is never used. The flag `--accept-submitted` applies it anyway; its help text says it trusts the submit alone, and the output says each such update was applied on the submit alone.
- **SPO-Xconfirm-PR-024** `--discard-unmatched` keeps its meaning: pending updates the transfer file knows nothing about (neither queued nor submitted) are reported and kept, and dropped, never applied, only with the flag.
- **SPO-Xconfirm-PR-025** A transaction the history records as expired has its update discarded with a notice, never applied, by `spo asset settle`, only when the validity bound stored with the local pending update is set, is not zero and equals the bound the queued entry carried; otherwise the outcome is reported as inconsistent and the update is kept. The notice says the discard rests on the online machine's report, which the offline machine cannot check.
- **SPO-Xconfirm-PR-026** The history entry `offline execute` writes for a submitted update also holds the signed transaction (`spoTxCbor`, hex). `spo tx settle` derives the transaction id (the transaction id calculator) and the validity bound (the transaction view's TTL) from those bytes, never from the carried JSON, and refuses a carried record whose id or bound disagrees or whose transaction is missing or unreadable: it is reported, nothing is recorded for it, and the command exits 1. An edited bound therefore cannot produce an early `spoExpired`.
- **SPO-Xconfirm-PR-027** When `offline execute` applies the update its queue entry carried to a copy of the asset record (the workspace holds the record and no pending update), it first checks the update against the confirmed transaction: the update's txid is the transaction's locally computed id, and the policy, name and amount are those of the transaction's own mint field (the record's asset name is that name); otherwise the update is refused with a message and the record is not changed. An update that fails the check is never applied.

## Preconditions and failures

- **SPO-Xconfirm-PRE-001** When the time runs out with the transaction not confirmed, the message says it may still be included and must not be built again from the same inputs until it has expired, and names `spo tx status <id>`.
- **SPO-Xconfirm-PRE-002** Expired is stated only when the transaction has a validity upper bound known to the command and the decision is made per provider: for every configured provider, in one poll, a tip read before that provider's status read is at or past the bound plus the slack (compared without overflow), and the same provider's status read after it is not seen. A provider without a tip, with an unreadable tip, with a tip short of the mark, or with any other answer means not expired. The slack is the freshness window of SPO-Xconfirm-INV-001 plus 5 minutes, in slots (900, counting 1 s per slot), so a provider that lags by as much as the window allows still cannot reach the mark early. The freshness check and the status read are separate requests, so behind a load-balanced address this assumes every server is within the slack of the chain; that is not checkable, and the message says so. A rollback deeper than the slack could also overturn the verdict. The condition must hold on two consecutive polls. The message says that "expired" rests on the providers' answers and on that assumption. It is the only outcome whose message says the transaction can no longer be included and that it is safe to build it again.
- **SPO-Xconfirm-PRE-003** When no provider gave a usable answer for the whole wait, the message says the status is unknown and does not say the transaction was or was not included.
- **SPO-Xconfirm-PRE-004** `--wait` is refused before any prompt, naming the missing capability (`tx-status`), when the mode has no provider: air-gap (offline) mode, where a transaction is queued and a later `offline execute` submits it.
- **SPO-Xconfirm-PRE-005** When a submission ends with an unknown outcome, the error also names `spo tx status <id>` when the id can be computed from the transaction, and says not to build it again from the same inputs first.

## Work modes

- **SPO-Xconfirm-MODE-001** Light and online mode: every configured provider is asked (in online mode the web providers named in `[provider] order` only, as for every other read). Offline mode has no provider, so neither the status command nor the wait exists there.

## Security

- **SPO-Xconfirm-SEC-001** Every string a provider chose (its reason text, its answer) is written through the terminal-safe escaper before it is printed. The confirmation text states only numbers this code computed and the provider's source name, escaped.

## Open questions

* Whether Koios' `num_confirmations` counts the block that holds the transaction. The Koios document says only "number of block confirmations"; the number is used as given, so a count that starts at zero makes the wait cautious by one block.
* Whether a recently submitted transaction gives a 404 from Blockfrost or a null from Koios while it is in the provider's mempool; both are read as not seen, which is true of the chain and says nothing of the mempool.

# Xparty: party enrollment and multi-party signing

This spec is not upstream behaviour. It defines the protocol that replaces upstream's witness-file passing ([05c](../upstream/scripts/05c_regStakepoolCert.md), [05d](../upstream/scripts/05d_poolWitness.md)) and the unauthenticated transfer file ([Ptransfer](../upstream/patterns/Ptransfer.md)). Design decisions are in [ADR 0005](../../docs/explanation/adr/0005-party-envelope-and-signing-policy.md) and [ADR 0008](../../docs/explanation/adr/0008-capability-typed-ports.md). Requirements have ids so tests cite them like upstream requirements; they have no source ranges.

Terms: a **party** is one enrolled machine with its own store. The **coordinator** is the party that builds a transaction and collects signatures. A **signer** is a party asked for a signature. One machine can be both. A **transport** moves envelope bytes: the file transport and the tailcat transport are specified at the end.

## Party identity

- **SPO-Xparty-INV-001** A party identity is an Ed25519 signing key pair and an X25519 encryption key pair, generated at `init` and stored as Secret records. Neither private key ever leaves the store.
- **SPO-Xparty-INV-002** The fingerprint of an identity is the first 20 bytes of BLAKE2b-256 over the domain string `spo/party/v1`, the Ed25519 public key and the X25519 public key, in that order. It is displayed as 8 groups of 4 lower-case base32 characters (32 characters, 160 bits).
- **SPO-Xparty-INV-003** A party's public identity document is canonical CBOR of `[content, signature]`. `content` is the canonical CBOR of `[version, label, ed25519 public key, x25519 public key, tailcat node public key or null, created]`, and `signature` is Ed25519 by that key over the domain string `spo/identity/v1` followed by `content`. The label is chosen by its owner and is not trusted.

## Enrollment

- **SPO-Xparty-IF-001** `party export` writes the local public identity document. It contains no secret and no tailcat address.
- **SPO-Xparty-IF-002** `party enroll <document> --as <local name> --role <role>... [--key-role <key role>]... [--pool <pool id>]... [--unscoped]` records another party. Roles: `coordinator` (may send signing requests), `signer` (may be sent signing requests), `machine` (the operator's own other machine: may exchange air-gap bundles). A coordinator or a signer is enrolled with a **scope** (SPO-Xparty-INV-010): the key roles, the pools (given as pool id, `pool1...` or 56 hexadecimal characters, stored in bech32 because it is compared with the pools a transaction body concerns) and whether it is unscoped. There is no default: an enrollment of a coordinator or signer with no key role, or with neither a pool nor `--unscoped`, is refused.
- **SPO-Xparty-PRE-001** Enrollment refuses a document whose signature does not verify under the Ed25519 key it contains.
- **SPO-Xparty-PR-001** Enrollment shows the label, the roles requested and only the last four groups of the computed fingerprint, and requires the operator to type its first four groups (80 bits), as read out by the other party over a separate channel; the program compares what was typed with the document. The groups that must be typed are never displayed, so they cannot be copied from the screen: the operator has to have heard them. Two groups would leave 40 bits, which an attacker who can generate keys freely can match. There is no default and no flag that skips it.
- **SPO-Xparty-OUT-001** An enrolled party is a Sensitive record: public keys, fingerprint, local name, roles, scope, tailcat node key, state (`active`, `revoked`), and the enrollment time. Enrollment is an audit event.
- **SPO-Xparty-INV-004** Enrollment is mutual but not automatic: each side enrolls the other. A party that has enrolled us and that we have not enrolled gets no response at all.
- **SPO-Xparty-IF-003** `party revoke <name>` sets the state to `revoked`.
- **SPO-Xparty-IF-008** `party rotate` generates a new local identity and exports a rotation statement signed by the old key; a peer that imports it must confirm the new fingerprint as in SPO-Xparty-PR-001. (Split from SPO-Xparty-IF-003.)
- **SPO-Xparty-INV-005** A revoked party's envelopes are refused from the moment of revocation, including envelopes created before it. Open collections keep the witnesses already verified; unfilled slots assigned to the party become unassigned.
- **SPO-Xparty-SEC-001** A coordinator's tailcat address is a Secret record. It is given to a signer only inside an envelope addressed to that signer (message `Invite`), never in an identity document, a QR code or a log.

## Envelope

- **SPO-Xparty-OUT-002** An envelope is `age`-encrypted to the recipient's X25519 key. The plaintext is canonical CBOR of `[payload, signature]`, where `signature` is Ed25519 over the domain string `spo/envelope/v1` followed by the payload bytes.
- **SPO-Xparty-OUT-003** The payload is canonical CBOR of `[version, type, sender fingerprint, recipient fingerprint, message id (16 random bytes), created (unix seconds), expires (unix seconds), body]`.
- **SPO-Xparty-PRE-002** A receiver refuses an envelope, in this order, when: it does not decrypt; the payload version is unknown; the sender fingerprint is not an active enrolled party; the signature does not verify under that party's Ed25519 key; the recipient fingerprint is not its own; `expires` has passed or `created` is more than 10 minutes in the future; the message id is in its replay log; the sender's role does not permit the message type (SPO-Xparty-INV-010).
- **SPO-Xparty-INV-006** Every refusal is an audit event that records the reason and, when the signature verified, the sender; a refusal before the signature step records no sender, because the fingerprint in the envelope is a claim. Over a network transport the sender receives nothing that distinguishes one refusal from another, and nothing at all before the signature has verified: a connection whose first frame fails (SPO-Xparty-INV-018) is closed with no bytes written. A signer refuses a request it can decide from the request alone with a `SigningRefusal` that names the reason: wrong network, body hash, body does not decode, a part that cannot be displayed (SPO-Xparty-PR-002), TTL passed, pool cold key over a network. A refusal that depends on the signer's private state, which keys it holds, what it owns, what scope it gave the coordinator, is recorded locally and never sent: no key with that hash and role, out of scope, no input of the body is the signer's, the inputs cannot be resolved, the signer cannot meet the demand. Declining a request is the operator's decision and is sent. The signer's own refusals are kept without the request's body (SPO-Xparty-INV-022).
- **SPO-Xparty-INV-007** The replay log holds every accepted message id, with its sender, until its `expires` has passed. It is written in the same store transaction as the effect of the message.
- **SPO-Xparty-INV-008** An envelope is at most 1 MiB. A transaction body is at most the protocol's `maxTxSize`, taken as 16384 bytes unless protocol parameters are wired; a signer refuses a larger one on receipt, before it stores anything.
- **SPO-Xparty-SEC-002** Envelope validity is independent of the transport: the same checks run on an envelope read from a file and on one received over tailcat. No check is skipped because a tunnel authenticated the peer.

## Messages

| Type | From → to | Body |
| --- | --- | --- |
| `SigningRequest` | coordinator → signer | `[collection id, slot id, key role, key hash (28 bytes), operation, transaction body CBOR, body hash (32 bytes), ttl slot, network magic, purpose text, auxiliary data (bytes; empty when the body names none)]` |
| `SigningResponse` | signer → coordinator | `[collection id, slot id, request message id, witness CBOR]` |
| `SigningRefusal` | signer → coordinator | `[collection id, slot id, request message id, reason code]` |
| `CollectionClosed` | coordinator → signer | `[collection id, outcome: submitted with tx id, discarded, or expired]` |
| `Invite` | coordinator → signer | `[tailcat address, coordinator tailcat node key]` |
| `Hello` | signer → coordinator | `[]`: opens a connection when the signer has nothing else to send, so that it can receive pending requests |
| `Bundle` | machine → machine | the air-gap bundle: chain snapshot, queued transactions, attachments |

- **SPO-Xparty-INV-009** `SigningRequest.expires` is no later than the wall-clock time of the body's TTL slot, and no later than 7 days after `created`. The coordinator sets it so, and the signer enforces it on receipt: a request that lives longer, or whose lifetime it cannot check, is refused before it is stored.
- **SPO-Xparty-INV-010** Authorisation by role and scope. `SigningRequest`, `CollectionClosed` and `Invite` need the sender to be a `coordinator`; `SigningResponse` and `SigningRefusal` need the sender to be the `signer` assigned to that slot; `Bundle` needs `machine`. What a coordinator may ask is its **scope**: `KeyRoles`, which of this machine's key roles it may ask for; `Pools`, the pools it may send bodies about; `Unscoped`, whether it may send a body that concerns no pool (a payment, a withdrawal). The default scope allows nothing, and a record enrolled before scopes existed is read as that default. A body **concerns** every pool that appears in it as the subject of a pool registration or retirement, the target of a stake delegation or of any combined delegation certificate, or a stake-pool voter. A signer decodes the body itself and refuses a request unless the requested key role is among the sender's `KeyRoles`, every pool the body concerns is among its `Pools`, and a body that concerns no pool is sent by an `Unscoped` sender. The coordinator applies the same rule to the scope enrolled for a signer before it sends a request. A `CollectionClosed` has effect only on requests the same sender made, and a submission names the body hash of those requests (SPO-Xparty-INV-015). An `Invite` names the node key the coordinator has enrolled.
- **SPO-Xparty-INV-020** The body hash is BLAKE2b-256 over the transaction body CBOR exactly as carried in the request, which is the transaction id. The body is the transaction body map, the first element of the transaction array: the witness set is not sent. The auxiliary data is carried in the request when the body has an auxiliary-data hash: a signer checks that its BLAKE2b-256 hash is the hash in the body and shows it; a body with the hash and no auxiliary data, a mismatch, or auxiliary data the body does not name is refused. A signer hashes the bytes it received; it does not re-encode them.
- **SPO-Xparty-INV-021** `Hello` needs the sender to be a `signer`. It has no effect other than authenticating the connection and is not recorded in the replay log beyond its expiry, which is at most 5 minutes after `created`.
- **SPO-Xparty-INV-011** The purpose text is for display only. Nothing a signer shows or decides is derived from it (SPO-Xparty-PR-002).

## Coordinator

A collection is the aggregate `WitnessCollection` of the [domain model](../domain/domain-model.md), with states `OpenIncomplete`, `OpenComplete`, `Expired`, `Submitted`, `Discarded`.

- **SPO-Xparty-PRE-003** A collection is opened only with a signing plan (`custody.Plan`): every slot has a key reference whose holder can produce the signature. A slot whose key is held by a remote party must name an active enrolled `signer` whose scope allows the slot's key role and the pools the body concerns (SPO-Xparty-INV-010).
- **SPO-Xparty-INV-012** The body stored in the collection is final when the collection opens. When any slot's holder is a hardware wallet, the body is in hardware-canonical form ([Ctx](../upstream/common/Ctx.md)) before its hash is taken, so every party hashes the same bytes.
- **SPO-Xparty-INV-013** Every slot goes through the same request flow: owner stake keys, the fee payer, the pool cold key and any other required signer (this lifts SPO-05d-INV-007). Slots whose key the coordinator's own machine holds are filled by its local signer through the same verification as a remote response.
- **SPO-Xparty-PRE-004** A request for a pool cold key is not sent over a network transport. The coordinator refuses to create it, and an envelope that was sealed for the file transport is not handed to a network transport later; the file transport is allowed (ADR 0005). A transport of unknown kind is a network (SPO-Xparty-INV-024).
- **SPO-Xparty-PRE-005** A response is accepted for a slot only when all hold: the collection is `OpenIncomplete`; the slot is empty; the sender is the slot's assigned signer; the request message id is the one last sent for that slot; the witness is a valid Ed25519 signature over the stored body hash; the BLAKE2b-224 hash of the witness's verification key equals the slot's key hash (this closes SPO-05d-INV-006 and SPO-05d-SEC-003).
- **SPO-Xparty-INV-014** Filling a slot is a compare-and-set on the collection version. Of two valid responses for one slot, one is stored and the other is acknowledged without effect, also when the stored one completed the collection (SPO-Xparty-PRE-005 asks for an incomplete collection and an empty slot; a duplicate is not a refusal).
- **SPO-Xparty-INV-015** A collection whose TTL slot has been reached by the chain tip (tip at or above the TTL slot, as a signer holds a request expired) is `Expired`. It accepts no response and cannot be submitted. Expiry is derived from the chain tip when one is available and from the clock otherwise. A `CollectionClosed` whose outcome is `submitted` carries the transaction id, which a signer accepts only when it is the body hash it was asked to sign; a notice about a collection the sender never asked about is refused.
- **SPO-Xparty-OUT-004** Opening, each request sent, each response accepted or refused, completion, submission, discard and expiry are audit events (this closes SPO-05d-INV-001).
- **SPO-Xparty-OUT-005** When the last slot is filled the collection is `OpenComplete`. Submission assembles the stored body with the stored witnesses and nothing else.

## Signer

- **SPO-Xparty-PRE-006** A signer refuses a request, with an audit event, when, in this order: the network magic is not its workspace's; the body hash is not the BLAKE2b-256 hash of the body it received; the body does not decode as a transaction of the current era (the TTL of the decoded body must equal the request's `ttl slot`: a request that states another is a body that does not decode); the body's own network id (key 15) when present, or the network of any output address, withdrawal account or reward account in it, is not the workspace's network; the body has a part that cannot be displayed or the auxiliary data does not match (SPO-Xparty-PR-002); its TTL slot has passed; the key is a pool cold key and the request arrived over a network transport; then, from its own private state: the requested key role is not among the sender's `KeyRoles`, or a pool the body concerns is not among its `Pools`, or the body concerns none and the sender is not `Unscoped` (SPO-Xparty-INV-010); it holds no key with the requested key hash and role; the key is a payment key and its inputs cannot be resolved, or none of them is its own (SPO-Xparty-PR-002); its signer for that key cannot meet the demand of the decoded body (`custody.Plan` on the signer's side). The refusals that precede the private checks are sent as a `SigningRefusal`; the private ones are not (SPO-Xparty-INV-006). On receipt, before any of this, it enforces SPO-Xparty-INV-008, SPO-Xparty-INV-009 and SPO-Xparty-INV-022.
- **SPO-Xparty-PR-002** Before signing, the signer shows what the body does, decoded locally from the body bytes, and first whose money leaves, worked out by the signer from its own addresses (`OwnedAddresses`) and its own chain provider or offline snapshot (`UtxoReader`), never from the coordinator. For every input it looks the input up in the UTxO sets of its own payment addresses: an own input is shown with its lovelace and assets; the others are only counted, because their value does not matter to this signer. Every output is marked as the signer's own or not by its address. It shows the net outflow, its own inputs minus its own outputs, in lovelace and per asset, with the fee, the withdrawals from and to its own reward accounts, and the deposits and refunds the certificates state (a pool registration, and the legacy stake certificates, state none: the deposit is a protocol parameter, and the view says so and shows no amount). When the requested key can authorise spending a payment UTxO (the payment role) the signer must be able to resolve its inputs, and at least one must be its own: if it has no UTxO reader, the lookup fails or the answer is unknown, the request is refused automatically; if no input is its own the request is refused, because the key is not needed for this body. When the key cannot spend funds (stake, pool cold, DRep, committee) resolution is attempted when a reader exists, and otherwise the review states: inputs not checked: this key cannot spend funds; it authorises only the certificates, withdrawals and votes shown. It also shows every input and output with its address and value, the TTL, every certificate with its fields (for a pool registration: pool id, pledge, cost, margin, reward account, owners, relays, metadata URL and hash), withdrawals, votes, required signers, the treasury value and donation, and the auxiliary data: its hash, the metadata labels with their values, and CIP-20 messages as text. A body with any part the decoder cannot show in full is refused: a key, a certificate tag or an output form it does not know, a duplicate key in any map or a duplicate member of any set, and, for remote signing, proposal procedures, a script data hash, collateral inputs, collateral return or total collateral, reference inputs, an output with an inline datum, a datum hash or a script reference, and a mint. The decision can only be made from this review: it asks for approval with default No (this closes SPO-05d-INV-008).
- **SPO-Xparty-INV-016** There is no option that approves without the display of SPO-Xparty-PR-002. A non-interactive signer does not exist in this version. An approval also needs the operator to authenticate again: the signer calls its approval gate with the key about to sign and the body hash, the wiring prompts for the store passphrase for the pool cold, payment and owner stake roles, and a signer with no gate does not approve.
- **SPO-Xparty-OUT-006** On approval the signer produces the witness with the signer that holds the key (vault or hardware), verifies it itself as in SPO-Xparty-PRE-005, and sends `SigningResponse`. Request, decision and response are audit events that record the body hash.
- **SPO-Xparty-INV-017** A request that was answered is answered again with the stored response when the same message id arrives, over any transport, so a lost reply can be regenerated. It never signs twice. A network send has no application acknowledgement: the coordinator keeps a request as sent and sends it again after a new connection until the answer arrives or the request expires, and the signer does the same with its response until the collection closes or the response expires.

## Transports

- **SPO-Xparty-IF-004** File transport: `export` writes one envelope per file, named `<type>-<collection id prefix>-<slot>.spo`; `import <file>...` reads them. A file is at most the envelope size limit. Import never writes outside the store.
- **SPO-Xparty-IF-005** Tailcat transport, coordinator side: a tailcat server with a persistent node key and pre-shared key, listening on one TCP port. Its allow-list is built only from the active parties that are a signer or a machine and have a node key, never from a revoked party or a party that is only a coordinator. It refuses to start when that list is empty, and it sets the allow-list before starting (concern T2). tailcat cannot remove a key from its allow-list: a revoked party's node key can still open a tunnel until the server restarts, but our listener refuses it and closes its live connections.
- **SPO-Xparty-IF-006** Tailcat transport, signer side: a client with a persistent node key dials the address it received in `Invite`, sends its pending responses, and receives its pending requests. The coordinator's node key from the same `Invite` is required: a client is not built without it, and not for an address that leads to another key.
- **SPO-Xparty-INV-018** The stream protocol is a sequence of frames, each a 4-byte big-endian length and one envelope. The first frame on a connection must be a `Hello` or a response (`SigningResponse`, `SigningRefusal`) that is a valid envelope from an active enrolled party whose enrolled node key is the node key tailcat authenticated for the connection, and whose message id is not in the replay log; otherwise the connection is closed with no bytes written and the refusal is audited. The envelope inside the tunnel is checked again in full when it is handled (SPO-Xparty-SEC-002). The binding is between the tunnel's peer and the first frame's sender: a frame later in the connection is bound to nothing but its own signature.
- **SPO-Xparty-INV-019** Per connection: at most 64 frames, at most 30 seconds idle, at most 16 concurrent connections, and at most 6 connections per node key per minute (concern T7).
- **SPO-Xparty-INV-022** One enrolled party cannot exhaust a peer: the replay log holds at most 512 live entries per sender and a signer at most 64 undecided requests per sender, and a sender over its quota is refused alone; a refused request is stored as its id, sender, reason and time, never with its body; a tailcat server holds at most 2 live connections per node key and closes every connection 10 minutes after it opened.
- **SPO-Xparty-INV-023** The audit log is two logs. Security events (enrollment, revocation, requests sent and received, reviews, approvals and refusals, responses accepted or refused from an authenticated sender, collection open, complete and close) are kept in a log with a large cap, evicted oldest first among themselves only. A refusal that failed before the signature step goes to a small ring and a counter, which can never evict a security event.
- **SPO-Xparty-INV-024** A transport of unknown kind is a network. The zero kind is unknown, in every cold-key check (on receipt, on send, in the outbox), and a kind must be stated where a transport sends: the file bag and the tailcat server and client carry their own kind, and a call site cannot set it.
- **SPO-Xparty-SEC-003** Coordinator state lives in the store, not in the connection. A signer that reconnects, or that answers by file after being asked over the network, completes the same slot.
- **SPO-Xparty-MODE-001** A coordinator in offline mode has no network transport. It exchanges envelopes by file only.

## Upstream compatibility

- **SPO-Xparty-IF-007** `05c` witness transfer files (SPO-Pfiles-OUT-023) can be imported into and exported from a collection, for a party that still uses the upstream scripts. A witness imported this way is verified as in SPO-Xparty-PRE-005, and the slot records that it arrived unauthenticated.

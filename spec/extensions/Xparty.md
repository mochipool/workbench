# Xparty: party enrollment and multi-party signing

This spec is not upstream behaviour. It defines the protocol that replaces upstream's witness-file passing ([05c](../upstream/scripts/05c_regStakepoolCert.md), [05d](../upstream/scripts/05d_poolWitness.md)) and the unauthenticated transfer file ([Ptransfer](../upstream/patterns/Ptransfer.md)). Design decisions are in [ADR 0005](../../docs/explanation/adr/0005-party-envelope-and-signing-policy.md) and [ADR 0008](../../docs/explanation/adr/0008-capability-typed-ports.md). Requirements have ids so tests cite them like upstream requirements; they have no source ranges.

Terms: a **party** is one enrolled machine with its own store. The **coordinator** is the party that builds a transaction and collects signatures. A **signer** is a party asked for a signature. One machine can be both. A **transport** moves envelope bytes: the file transport and the tailcat transport are specified at the end.

## Party identity

- **SPO-Xparty-INV-001** A party identity is an Ed25519 signing key pair and an X25519 encryption key pair, generated at `init` and stored as Secret records. Neither private key ever leaves the store.
- **SPO-Xparty-INV-002** The fingerprint of an identity is the first 20 bytes of BLAKE2b-256 over the domain string `spo/party/v1`, the Ed25519 public key and the X25519 public key, in that order. It is displayed as 8 groups of 4 lower-case base32 characters (32 characters, 160 bits).
- **SPO-Xparty-INV-003** A party's public identity document is canonical CBOR of `[content, signature]`. `content` is the canonical CBOR of `[version, label, ed25519 public key, x25519 public key, tailcat node public key or null, created]`, and `signature` is Ed25519 by that key over the domain string `spo/identity/v1` followed by `content`. The label is chosen by its owner and is not trusted.

## Enrollment

- **SPO-Xparty-IF-001** `party export` writes the local public identity document. It contains no secret and no tailcat address.
- **SPO-Xparty-IF-002** `party enroll <document> --as <local name> --role <role>... [--key-role <key role>]... [--pool <pool id>]... [--unscoped]` records another party. Roles: `coordinator` (may send signing requests), `signer` (may be sent signing requests), `machine` (the operator's own other machine: may exchange air-gap bundles). A coordinator is enrolled with a **scope** (SPO-Xparty-INV-010): the key roles, the pools (given as pool id, `pool1...` or 56 hexadecimal characters, stored in bech32 because it is compared with the pools a transaction body names) and whether it is unscoped. There is no default: an enrollment of a coordinator with no key role, or with neither a pool nor `--unscoped`, is refused. The scope is what a coordinator may ask of this machine; it is recorded for a signer too but never read, because what this machine asks of a signer is limited by the slot assignment and by the signer's own checks. Enrollment refuses an identity whose tailcat node key is already the node key of another enrolled party, active or revoked (SPO-Xparty-INV-018).
- **SPO-Xparty-PRE-001** Enrollment refuses a document whose signature does not verify under the Ed25519 key it contains.
- **SPO-Xparty-PR-001** Enrollment shows the label, the roles requested and only the last four groups of the computed fingerprint, and requires the operator to type its first four groups (80 bits), as read out by the other party over a separate channel; the program compares what was typed with the document. The groups that must be typed are never displayed, so they cannot be copied from the screen: the operator has to have heard them. Two groups would leave 40 bits, which an attacker who can generate keys freely can match. There is no default and no flag that skips it.
- **SPO-Xparty-OUT-001** An enrolled party is a Sensitive record: public keys, fingerprint, local name, roles, scope, tailcat node key, state (`active`, `revoked`), and the enrollment time. Enrollment is an audit event.
- **SPO-Xparty-INV-004** Enrollment is mutual but not automatic: each side enrolls the other. A party that has enrolled us and that we have not enrolled gets no response at all.
- **SPO-Xparty-IF-003** `party revoke <name>` sets the state to `revoked`.
- **SPO-Xparty-IF-008** `party rotate` generates a new local identity and exports a rotation statement signed by the old key; a peer that imports it must confirm the new fingerprint as in SPO-Xparty-PR-001. (Split from SPO-Xparty-IF-003.)
- **SPO-Xparty-INV-005** A revoked party's envelopes are refused from the moment of revocation, including envelopes created before it. Open collections keep the witnesses already verified; unfilled slots assigned to the party become unassigned.
- **SPO-Xparty-SEC-001** A coordinator's tailcat address is a Secret record. It is given to a signer only inside an envelope addressed to that signer (message `Invite`), never in an identity document, a QR code or a log.

## Envelope

- **SPO-Xparty-OUT-002** An envelope is `age`-encrypted to the recipient's X25519 key. The plaintext is canonical CBOR of `[payload, signature]`, where `signature` is Ed25519 over the domain string `spo/envelope/v1` followed by the payload bytes.
- **SPO-Xparty-OUT-003** The payload is canonical CBOR of `[version, type, sender fingerprint, recipient fingerprint, message id (16 random bytes), created (unix seconds), expires (unix seconds), body]`. The envelope format is **version 1**, defined by this text as of the change that made it so: nothing was deployed before, so there is no older format to read and a receiver refuses any other version (SPO-Xparty-PRE-002).
- **SPO-Xparty-PRE-002** A receiver refuses an envelope, in this order, when: it does not decrypt; the payload version is unknown; the sender fingerprint is not an active enrolled party; the signature does not verify under that party's Ed25519 key; the recipient fingerprint is not its own; `expires` has passed or `created` is more than 10 minutes in the future; the message id is in its replay log; the sender's role does not permit the message type (SPO-Xparty-INV-010).
- **SPO-Xparty-INV-006** Every refusal is an audit event that records the reason and, when the signature verified, the sender; a refusal before the signature step records no sender, because the fingerprint in the envelope is a claim. Over a network transport the sender receives nothing that distinguishes one refusal from another, and nothing at all before the signature has verified: a connection whose first frame fails (SPO-Xparty-INV-018) is closed with no bytes written. A signer refuses a request it can decide from the request alone with a `SigningRefusal` that names the reason: wrong network, body hash, body does not decode, a part that cannot be displayed (SPO-Xparty-PR-002), TTL passed, pool cold key over a network. A refusal that depends on the signer's private state, which keys it holds, what it owns, what scope it gave the coordinator, is recorded locally and never sent: no key with that hash and role, out of scope, no input of the body is the signer's, the inputs cannot be resolved, the signer cannot meet the demand. Declining a request is the operator's decision and is sent. The signer's own refusals are kept without the request's body (SPO-Xparty-INV-022).
- **SPO-Xparty-INV-007** The replay log holds every accepted message id, with its sender, until its `expires` has passed. It is written in the same store transaction as the effect of the message.
- **SPO-Xparty-INV-008** An envelope is at most 1 MiB. A transaction, its body and its auxiliary data together (`len(body) + len(auxiliary data)`), is at most the protocol's `maxTxSize`, taken as 16384 bytes unless protocol parameters are wired; a signer refuses a larger one on receipt, before it stores anything, and a coordinator does not seal one.
- **SPO-Xparty-SEC-002** Envelope validity is independent of the transport: the same checks run on an envelope read from a file and on one received over tailcat. No check is skipped because a tunnel authenticated the peer.

## Messages

| Type | From → to | Body |
| --- | --- | --- |
| `SigningRequest` | coordinator → signer | `[collection id, slot id, key role, key hash (28 bytes), operation, transaction body CBOR, body hash (32 bytes), ttl slot, network magic, purpose text, auxiliary data (bytes; empty when the body names none)]` |
| `SigningResponse` | signer → coordinator | `[collection id, slot id, request message id, witness CBOR]` |
| `SigningRefusal` | signer → coordinator | `[collection id, slot id, request message id, reason code]` |
| `CollectionClosed` | coordinator → signer | `[collection id, outcome: submitted with tx id, discarded, or expired]` |
| `Invite` | coordinator → signer | `[tailcat address, coordinator tailcat node key]` |
| `Hello` | signer → coordinator | `[]`: the first frame of every network connection, so that the coordinator knows the signer is connected and sends its pending requests |
| `Bundle` | machine → machine | the air-gap bundle: chain snapshot, queued transactions, attachments |

- **SPO-Xparty-INV-009** `SigningRequest.expires` is no later than the wall-clock time of the body's TTL slot, and no later than 7 days after `created`. The coordinator sets it so, and the signer enforces it on receipt: a request that lives longer, or whose lifetime it cannot check, is refused before it is stored.
- **SPO-Xparty-INV-010** Authorisation by role and scope. `SigningRequest`, `CollectionClosed` and `Invite` need the sender to be a `coordinator`; `SigningResponse` and `SigningRefusal` need the sender to be the `signer` assigned to that slot; `Bundle` needs `machine`. What a coordinator may ask of this machine is its **scope**: `KeyRoles`, which of this machine's key roles it may ask for; `Pools`, the pools a body may name; `Unscoped`, whether it may send the parts of a body that name no pool. The default scope allows nothing, and a record enrolled before scopes existed is read as that default. The scope is checked **per part** of the body, not per body. A part **names a pool** when it is a pool registration or retirement (the pool it is about), a stake delegation or any combined delegation certificate (the pool delegated to), or a vote of a stake pool. A combined certificate is split into its parts and each is checked on its own: its delegation names the pool, but its **registration part** (certificate tags 11 and 13, a deposit paid) and its **vote-delegation part** (tags 10 and 13, a DRep chosen) name none and each needs `Unscoped`, so a pool-only scope never lets a coordinator choose a DRep or pay a deposit through a combined certificate. Every other part names none: a withdrawal, a stake registration or deregistration, a vote delegation, a DRep or committee certificate, a vote that is not a stake pool's, and every request for a payment key, which can spend this machine's funds. A signer decodes the body itself and refuses a request unless the requested key role is among the sender's `KeyRoles`, every pool that any part names is among its `Pools`, and, when any part names no pool, or the body has no part that names one, the sender is `Unscoped`. A body that mixes a certificate for an in-scope pool with a withdrawal, or a stake-vote delegation whose DRep is the coordinator's choice, needs the pool and `Unscoped`. The rule is applied when the request is received and again when it is approved (SPO-Xparty-INV-025). It is a rule about what a coordinator may ask of this machine only: the coordinator does not read the scope recorded for a signer. A `CollectionClosed` has effect only on requests the same sender made, and a submission names the body hash of those requests (SPO-Xparty-INV-015). An `Invite` names the node key the coordinator has enrolled.
- **SPO-Xparty-INV-020** The body hash is BLAKE2b-256 over the transaction body CBOR exactly as carried in the request, which is the transaction id. The body is the transaction body map, the first element of the transaction array: the witness set is not sent. The auxiliary data is carried in the request when the body has an auxiliary-data hash: a signer checks that its BLAKE2b-256 hash is the hash in the body and shows it; a body with the hash and no auxiliary data, a mismatch, or auxiliary data the body does not name is refused. A signer hashes the bytes it received; it does not re-encode them.
- **SPO-Xparty-INV-021** `Hello` needs the sender to be a `signer`. It authenticates the connection, is not recorded in the replay log beyond its expiry, which is at most 5 minutes after `created`, and has one effect: the coordinator, on receiving it, sends again the requests of that signer that have no answer yet (SPO-Xparty-INV-017). Its message id is new each time. The sender's role and the 5-minute lifetime are checked at the first frame of a connection, before the connection gets a route (SPO-Xparty-INV-018, INV-027), not only when the Hello is handled.
- **SPO-Xparty-INV-011** The purpose text is for display only. Nothing a signer shows or decides is derived from it (SPO-Xparty-PR-002).

## Coordinator

A collection is the aggregate `WitnessCollection` of the [domain model](../domain/domain-model.md), with states `OpenIncomplete`, `OpenComplete`, `Expired`, `Submitted`, `Discarded`.

- **SPO-Xparty-PRE-003** A collection is opened only with a signing plan (`custody.Plan`): every slot has a key reference whose holder can produce the signature. A slot whose key is held by a remote party must name an active enrolled `signer`. The scope recorded for that party is not consulted (SPO-Xparty-INV-010): the signer applies its own checks.
- **SPO-Xparty-INV-012** The body stored in the collection is final when the collection opens. When any slot's holder is a hardware wallet, the body is in hardware-canonical form ([Ctx](../upstream/common/Ctx.md)) before its hash is taken, so every party hashes the same bytes.
- **SPO-Xparty-INV-013** Every slot goes through the same request flow: owner stake keys, the fee payer, the pool cold key and any other required signer (this lifts SPO-05d-INV-007). Slots whose key the coordinator's own machine holds are filled by its local signer through the same verification as a remote response.
- **SPO-Xparty-PRE-004** A request for a pool cold key is not sent over a network transport. The coordinator refuses to create it, and an envelope that was sealed for the file transport is not handed to a network transport later; the file transport is allowed (ADR 0005). A transport of unknown kind is a network (SPO-Xparty-INV-024).
- **SPO-Xparty-PRE-005** A response is accepted for a slot only when all hold: the collection is `OpenIncomplete`; the slot is empty; the sender is the slot's assigned signer; the request message id is the one last sent for that slot; the witness is a valid Ed25519 signature over the stored body hash; the BLAKE2b-224 hash of the witness's verification key equals the slot's key hash (this closes SPO-05d-INV-006 and SPO-05d-SEC-003).
- **SPO-Xparty-INV-014** Filling a slot is a compare-and-set on the collection version. Of two valid responses for one slot, one is stored and the other is acknowledged without effect, also when the stored one completed the collection (SPO-Xparty-PRE-005 asks for an incomplete collection and an empty slot; a duplicate is not a refusal).
- **SPO-Xparty-INV-015** A collection whose TTL slot has been reached by the chain tip (tip at or above the TTL slot, as a signer holds a request expired) is `Expired`. It accepts no response and cannot be submitted. Expiry is derived from the chain tip when one is available and from the clock otherwise. A `CollectionClosed` whose outcome is `submitted` carries the transaction id, which a signer accepts only when it is the body hash it was asked to sign; a notice about a collection the sender never asked about is refused.
- **SPO-Xparty-OUT-004** Opening, each request sent, each response accepted or refused, completion, submission, discard and expiry are audit events (this closes SPO-05d-INV-001).
- **SPO-Xparty-OUT-005** When the last slot is filled the collection is `OpenComplete`. Submission assembles the stored body with the stored witnesses and nothing else.

## Signer

- **SPO-Xparty-PRE-006** A signer refuses a request, with an audit event, when, in this order: the network magic is not its workspace's; the body hash is not the BLAKE2b-256 hash of the body it received; the body does not decode as a transaction of the current era (the TTL of the decoded body must equal the request's `ttl slot`: a request that states another is a body that does not decode); the body's own network id (key 15) when present, or the network of any output address, withdrawal account or reward account in it, is not the workspace's network; the body has a part that cannot be displayed or the auxiliary data does not match (SPO-Xparty-PR-002); its TTL slot has passed; the key is a pool cold key and the request arrived over a network transport; then, from its own private state: the requested key role is not among the sender's `KeyRoles`, or a pool that any part of the body names is not among its `Pools`, or a part names no pool and the sender is not `Unscoped` (SPO-Xparty-INV-010); it holds no key with the requested key hash and role; the key is a payment key and any one of its inputs cannot be resolved (it is unknown, spent, or the lookup failed), or none of them is its own (SPO-Xparty-PR-002); for any key role, the body spends a script input or has a withdrawal, certificate or vote on a script credential, or on a credential the signer cannot read as a key (`RefuseScriptInput`, SPO-Xparty-PR-004); the request arrived over a network or an unknown transport and any input is not resolved by the signer's own resolver or its address cannot be inspected, for every key role (`RefuseCannotResolveInputs`, SPO-Xparty-PRE-007); a sum of the review overflows (undisplayable, and sent); its signer for that key cannot meet the demand of the decoded body (`custody.Plan` on the signer's side). The refusals that precede the private checks are sent as a `SigningRefusal`; the private ones are not (SPO-Xparty-INV-006). On receipt, before any of this, it enforces SPO-Xparty-INV-008, SPO-Xparty-INV-009 and SPO-Xparty-INV-022.
- **SPO-Xparty-PRE-007** **Network rule.** A request that arrived over a network transport, or over a transport whose kind is unknown (an unknown kind is a network), is refused automatically and in silence (`RefuseCannotResolveInputs`, not sent) for **every key role**, unless the signer has a resolver of its own AND every input of the body resolves to a value AND the address of every resolved input can be inspected. An input that is unknown, spent or whose lookup failed, no resolver, a provider that fails, and an address that cannot be read all refuse. The rule is applied when the request is received and again at review and approval, from the transport kind stored with the request (SPO-Xparty-INV-025). **File-transport residual:** a request that arrived by file keeps the rule of SPO-Xparty-PR-002 for the roles that cannot spend a payment UTxO: unresolved inputs there are **warned** in the review (`inputs not checked`, SPO-Xparty-PR-004), not refused; the payment role stays strict on both transports. A file is delivered by the operator's own hand, a network peer is not; the residual is that a file-delivered stake, pool cold, DRep or committee request with no resolver can be signed without the signer seeing whether a script input rides along, and the operator accepts that by reading the warning.
- **SPO-Xparty-PR-002** Before signing, the signer shows what the body does, decoded locally from the body bytes, and first whose money leaves, worked out by the signer from its own credentials and its own chain provider or offline snapshot, never from the coordinator. **Ownership is by credential.** A payment key's witness authorises every input whose payment credential is that key, at any address form (enterprise, base with any stake credential, pointer), so the signer holds the **key hashes** of its own payment keys and stake keys (`OwnedKeys`, derived from its store by the wiring) and not address strings. It resolves every input of the body **by reference** through its own `UtxoResolver` (a provider that answers a transaction id and index with the output's address, lovelace and assets, or the offline snapshot) and classifies each resolved input by the payment credential of the address it is at: **own** when that key hash is one of its payment keys, otherwise foreign. An own input is shown with its lovelace and assets; the others are counted, because their value does not matter to this signer. **An output is own** when the payment credential of its address is one of the signer's payment key hashes **and** its stake credential is absent or one of the signer's stake key hashes. An output to the signer's payment key with another party's stake credential, a script stake credential or a pointer is **not** own: its rewards and delegation belong to someone else; it is shown as not own with that reason. The review shows each term of the net per lovelace, and the net: **net = own inputs + own withdrawals (from the reward accounts of its stake keys) + own refunds (deposit refunds of certificates on its stake credentials) - own outputs - own deposits paid (deposits of certificates on its stake credentials)**, positive leaving the signer, and the same per asset for inputs and outputs, with the fee, the value going to outputs that are not the signer's, the withdrawals from other accounts, and the deposits and refunds the certificates state in total (a pool registration, and the legacy stake certificates, state none: the deposit is a protocol parameter, and the view says so and shows no amount). Every sum is checked: an amount beyond any possible supply, or a sum that overflows, refuses the request as undisplayable. When the requested key can authorise spending a payment UTxO (the payment role) **every input must resolve** to a value; an input that is unknown to the provider, that it says is spent, or whose lookup failed, a provider that fails and no provider at all each refuse the request automatically (`RefuseCannotResolveInputs`, not sent), and if no input is own it is refused (`RefuseNotASignerInput`, not sent), because the key is not needed for this body. When the key cannot spend funds (stake, pool cold, DRep, committee) the inputs are resolved when a resolver exists and the own ones are shown; a body that spends the signer's own payment UTxOs under such a key is shown as such with a prominent note that this key's witness does not authorise that, and that the payment witness must come from elsewhere; only when there is no resolver does the review state that the inputs were not checked and why that matters: this key cannot spend funds from its own address, but a key witness also satisfies any native script that names this key and the signer cannot see the scripts (and when a resolver exists but could not answer, the review says it could not, with the provider's text kept out of the digest, SPO-Xparty-PR-003). An input at a script address is refused for every role (SPO-Xparty-PR-004). It also shows every input and output with its address and value, the TTL, every certificate with its fields (for a pool registration: pool id, pledge, cost, margin, reward account, owners, relays, metadata URL and hash), withdrawals, votes, required signers, the treasury value and donation, and the auxiliary data: its hash, the metadata labels with their values, and CIP-20 messages as text. Displayed text is refused when it holds a control or format character, or the line and paragraph separators U+2028 and U+2029. The refusals and the net of an unresolved body that follow from this are SPO-Xparty-PR-003 to SPO-Xparty-PR-005. A body with any part the decoder cannot show in full is refused: a key, a certificate tag or an output form it does not know, a duplicate key in any map or a duplicate member of any set, and, for remote signing, proposal procedures, a script data hash, collateral inputs, collateral return or total collateral, reference inputs, an output with an inline datum, a datum hash or a script reference, and a mint. The decision can only be made from this review: it asks for approval with default No (this closes SPO-05d-INV-008).
- **SPO-Xparty-PR-003** When the inputs were not resolved (no resolver, a provider that failed, an input it does not know), the review still works out and shows the net from what does not depend on them: own withdrawals, own refunds, own outputs and own deposits, and says that it **excludes the inputs** (`NetExcludesInputs`). A withdrawal of the signer's own rewards to someone else's output is therefore visible as value leaving, in a stake-role request as in any other. The provider's error text is shown but is kept out of the digest (SPO-Xparty-INV-026).
- **SPO-Xparty-PR-004** A key witness satisfies every native script that names the key, and the script is in the witness set, not the body, so the signer never sees it. A remote signer therefore refuses, for **every key role** and in silence (`RefuseScriptInput`, not sent: it depends on the signer's own chain view), a body that has a resolved input whose payment credential is a script, a withdrawal from a script reward account, a certificate on a script credential (the cold or the hot credential), or a vote by a script voter. **Everything fails closed.** The kind of a credential is read from the bytes in the view itself, with no inspector: the header nibble of an address (1, 3, 5 and 7, the script-key base, script-script base, pointer and enterprise forms with a script payment credential, are scripts; 0, 2, 4 and 6 are key payment forms; 8 is Byron; any other nibble is unknown), the key header 0xe of a reward account, the `key:` prefix of a certificate credential and the key voter kinds. Anything that is not plainly a key (an unreadable reward account, an unknown credential or voter kind, an unknown header) is a script and is refused; the inspector may add a script verdict but never remove one. An input at an address that fails inspection is treated as a script (`RefuseScriptInput`; over a network, SPO-Xparty-PRE-007). A signer built without an address inspector refuses every request with a configuration error (`ErrNoAddressInspector`), never a silent pass. A key payment credential with a script stake credential (header 0x2) is the signer's input, and an output to it is not the signer's output (SPO-Xparty-PR-002). A **mint**, reference inputs, collateral and a script data hash are refused as undisplayable (`RefuseUndisplayable`, sent) for every role, the `policy` role included: remote signing signs no body whose scripts it cannot see evaluated, and a mint has no scope rule of its own. When the inputs were not resolved for a key that cannot spend from its own address, the review says plainly that the inputs were **not checked**, that a key witness satisfies any native script that names this key, and that the signer cannot see the scripts, so that this witness may help spend a script address.
- **SPO-Xparty-PR-005** The signer's chain view (`UtxoResolver`) is **its own**: its own provider, or an offline snapshot the operator took on this machine. A snapshot is unauthenticated (whoever wrote it chose what each input is), so a transfer file that arrived from another party, a coordinator's bundle above all, is never a resolver source. The signer use case takes the resolver only as a `multisig.OwnResolver`, made by `OwnProvider` or `OwnSnapshot`; a plain provider or a loaded transfer file cannot be assigned, and the wiring that calls `OwnSnapshot` states that the file is the operator's own. No exported path of `multisig` or `party` turns a received `Bundle` into an `OwnResolver`: the only makers are `OwnProvider` and `OwnSnapshot`, each taking one `ports.UtxoResolver`, and a test reads the source to keep it so. What is passed to `OwnSnapshot` is the one convention left, an **operator and wiring obligation** that types cannot enforce: a CLI must build the snapshot resolver only from a file path the operator named for that purpose on the command line or in the workspace configuration, never from a path inside the party store, the inbox of a transport (`filebag`, `tailcat`), or any file that a received `Bundle` or transfer file wrote, and must refuse a snapshot path that is one of those.
- **SPO-Xparty-INV-016** There is no option that approves without the display of SPO-Xparty-PR-002. A non-interactive signer does not exist in this version. An approval also needs the operator to authenticate again: the signer calls its approval gate with the key about to sign and the body hash, the wiring prompts for the store passphrase for the pool cold, payment and owner stake roles, and a signer with no gate does not approve. What is approved is what was shown: the review's token carries the request id, the body hash and a digest of the flow, and approval re-checks them (SPO-Xparty-INV-025).
- **SPO-Xparty-INV-025** An approval is claimed against the current state, inside the store transaction that claims it, and not only against what was true at the review. The signer re-checks that the request's sender is still an active enrolled party with the `coordinator` role, that the request is inside the sender's scope **as it is now** (SPO-Xparty-INV-010), and it works the flow out again from its own provider and requires its digest to equal the digest of the flow that was reviewed, and the flow to meet the rule of the key role (SPO-Xparty-PR-002). The flow is worked out just before the claim, outside the store transaction (the provider may be a network call), and its digest is compared inside the claim; what the provider answers between the two is not seen. Provider error text is not part of the digest (SPO-Xparty-INV-026). **Not re-checked:** a revocation or scope change that happens while the operator is at the approval gate prompt, after the claim: the claim already passed, and the signature that follows is for a request that was in scope when it was claimed. Any difference refuses the approval as stale (`ErrReviewStale`) before the operator is asked to authenticate and before the key is touched; the request stays pending and can be reviewed again. An operator who narrows a coordinator's scope or revokes it after the review, or an own UTxO that is spent or changes between review and approval, thus signs nothing.
- **SPO-Xparty-OUT-006** On approval the signer produces the witness with the signer that holds the key (vault or hardware), verifies it itself as in SPO-Xparty-PRE-005, and sends `SigningResponse`. Request, decision and response are audit events that record the body hash.
- **SPO-Xparty-INV-026** The digest of the flow (SPO-Xparty-INV-016, INV-025) is stable across retries: provider error text and other detail that differs between two attempts is shown to the operator but is not part of the digest, so a provider that fails twice with different messages does not make the review stale.
- **SPO-Xparty-INV-027** The first-frame check of a network connection runs, before the connection gets a route, the same checks that handling the Hello would refuse: the sender holds the `signer` role (SPO-Xparty-INV-010) and the Hello's lifetime is at most 5 minutes (SPO-Xparty-INV-021). A refused Hello leaves no route and an audit event.
- **SPO-Xparty-INV-028** An approval claims a request only from the pending state and marks it signing with the time of the claim; a second approval while the first is at the gate is refused (one prompt, one response). A request left in the signing state by a crash is claimable again once it has been signing longer than the gate timeout (default 10 minutes), which is how a stale claim is recovered; the first approval's final write is refused if another took over, so at most one response is stored.
- **SPO-Xparty-INV-029** A signer's refused requests are bounded: a refused request is dropped when its envelope expires (a later duplicate is refused by the window check and the replay log), and each sender keeps at most `MaxReplayPerSender` (512) refused entries, the oldest dropped first.
- **SPO-Xparty-INV-017** A request that was answered is answered again with the stored response when the same message id arrives, over any transport, so a lost reply can be regenerated. It never signs twice and does not touch the key. A request whose id is already stored and not answered (waiting for the operator, or refused in silence) that arrives again has no effect and no security event. A **response, a refusal and every message that is not a request is sent once**: it is delivered when its write succeeds and is never sent again of its own accord. A **`SigningRequest` is re-sent** over a network, with the same message id, each time its signer connects again (the coordinator learns this from the signer's `Hello`, SPO-Xparty-INV-021), until the slot is answered, the collection closes or the request expires; a request whose answer was lost is thereby answered again from the signer's stored response. The coordinator keeps the id of the response or refusal it accepted for a slot, and that same envelope arriving again is acknowledged without effect and without a security event; any other replay is refused (SPO-Xparty-INV-007). Over a file a written envelope is delivered. Re-arming applies to requests only. A closed collection asks for nothing more: its requests are not re-sent.

## Transports

- **SPO-Xparty-IF-004** File transport: `export` writes one envelope per file, named `<type>-<collection id prefix>-<slot>.spo`; `import <file>...` reads them. A file is at most the envelope size limit. Import never writes outside the store.
- **SPO-Xparty-IF-005** Tailcat transport, coordinator side: a tailcat server with a persistent node key and pre-shared key, listening on one TCP port. Its allow-list is built only from the active parties that are a signer or a machine and have a node key, never from a revoked party or a party that is only a coordinator. It refuses to start when that list is empty, and it sets the allow-list before starting (concern T2). tailcat cannot remove a key from its allow-list: a revoked party's node key can still open a tunnel until the server restarts, but our listener refuses it and closes its live connections.
- **SPO-Xparty-IF-006** Tailcat transport, signer side: a client with a persistent node key dials the address it received in `Invite`, sends a fresh `Hello` as the first frame of every connection (SPO-Xparty-INV-018), sends its pending responses, and receives its pending requests. The coordinator's node key from the same `Invite` is required: a client is not built without it, and not for an address that leads to another key. The client is not built without a Hello builder either: the wiring supplies it, because the identity key stays out of the adapter, and no caller can send anything before the Hello.
- **SPO-Xparty-INV-018** The stream protocol is a sequence of frames, each a 4-byte big-endian length and one envelope. The first frame on a connection must be a `Hello`, and the client sends a fresh one (a new message id, a 5-minute expiry) first on every connection, a connection after a drop included; it must be a valid envelope from an active enrolled party whose enrolled node key is the node key tailcat authenticated for the connection, whose role is `signer` and whose lifetime is at most 5 minutes (SPO-Xparty-INV-021), and whose message id is not in the replay log; otherwise, a response or any other type included, the connection is closed with no bytes written and the refusal is audited. A node key belongs to one enrolled party: enrollment refuses a second party with the same node key (SPO-Xparty-IF-002), and the server checks the allow-list when it admits a connection under the lock that revocation takes, so a revoked key is not admitted after its live connections were closed. The envelope inside the tunnel is checked again in full when it is handled (SPO-Xparty-SEC-002). The binding is between the tunnel's peer and the first frame's sender: a frame later in the connection is bound to nothing but its own signature.
- **SPO-Xparty-INV-019** Per connection: at most 64 frames, at most 30 seconds idle, at most 16 concurrent connections, and at most 6 connections per node key per minute (concern T7).
- **SPO-Xparty-INV-022** One enrolled party cannot exhaust a peer: the replay log holds at most 512 live entries per sender and a signer at most 64 undecided requests per sender, and a sender over its quota is refused alone; a refused request is stored as its id, sender, reason and time, never with its body; a tailcat server holds at most 2 live connections per node key and closes every connection 10 minutes after it opened.
- **SPO-Xparty-INV-023** The audit log is two logs. Security events (enrollment, revocation, requests sent and received, reviews, approvals and refusals, responses accepted or refused from an authenticated sender, collection open, complete and close) are kept in a log with a large cap, evicted oldest first among themselves only. A refusal that failed before the signature step goes to a small ring and a counter, which can never evict a security event. Refusals of an authenticated sender are coalesced: the same event kind, sender and reason is one entry with a counter and the time it was last seen, and one sender has at most 16 distinct refusal entries, the rest counted in one further entry, so an enrolled party that sends refused envelopes in a loop cannot push the operator's history out of the log.
- **SPO-Xparty-INV-024** A transport of unknown kind is a network. The zero kind is unknown, in every cold-key check (on receipt, on send, in the outbox), and a kind must be stated where a transport sends. The kind is set only by the transport adapters: the constructors take no kind (`FileTransport(sender)`, `NetworkTransport(sender)`), the file bag and the tailcat server and client call them for themselves, and a test fails when code outside the adapters calls them. An incoming envelope reaches `Handle` as a value that the receiving adapter made and that carries how it arrived (`Received`, with an unexported kind): wiring cannot relabel a network delivery as a file, so the cold-key rule on receipt and the offline rule cannot be defeated by the caller.
- **SPO-Xparty-SEC-003** Coordinator state lives in the store, not in the connection. A signer that reconnects, or that answers by file after being asked over the network, completes the same slot.
- **SPO-Xparty-MODE-001** A coordinator in offline mode has no network transport. It exchanges envelopes by file only.

## Upstream compatibility

- **SPO-Xparty-IF-007** `05c` witness transfer files (SPO-Pfiles-OUT-023) can be imported into and exported from a collection, for a party that still uses the upstream scripts. A witness imported this way is verified as in SPO-Xparty-PRE-005, and the slot records that it arrived unauthenticated.

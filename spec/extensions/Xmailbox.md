# Xmailbox: the relay mailbox, pure rules

This spec is not upstream behaviour. It specifies work package 1 of [ADR 0013](../../docs/explanation/adr/0013-tailnet-relay-and-mailbox.md) (status: proposed): the pure domain of the relay mailbox. The package is `internal/domain/mailbox`. It does no I/O, holds no state and imports only the standard library, the canonical CBOR helper of `internal/domain/identity`, the party types and Blake2b. The relay session logic is specified in "The relay session (work package 3)" at the end of this file; the stores and the ports in "Ports, store, access list and stream"; the client is specified in "The mailbox client (work package 6)", and the tailcat stream adapter in "The tailcat stream adapter (work package 5)", both at the end.

Terms: a **header frame** is a 4-byte big-endian length and one canonical CBOR array. A **raw frame** is a 4-byte length and an envelope. The **mid** (mailbox id) is the Blake2b-256 of the envelope bytes. **Retention** is counted in whole unix seconds.

Where the ADR text is ambiguous this spec takes the stricter reading. The choices are listed in "Choices that go beyond the ADR text".

## Outputs

- **SPO-Xmailbox-OUT-001** The mid of an envelope is the Blake2b-256 of its bytes, written as 64 lower-case hex digits. `Hasher` computes it while the bytes stream past, so a caller never holds an envelope twice. A `Hasher` takes at most `MaxEnvelopeBytes` (1 MiB) and refuses a write that would pass that, whole, leaving itself unchanged. `ParseHash` accepts exactly 64 lower-case hex digits.
- **SPO-Xmailbox-OUT-002** A frame is a 4-byte big-endian length `n` and `n` bytes. A header frame has `n` from 1 to 4096 (`MaxHeaderFrame`). A raw frame has `n` equal to the size declared in the header just before it, from 1 to `MaxEnvelopeBytes`. The length is checked before the body is read and before any buffer is made for it.
- **SPO-Xmailbox-OUT-003** *Amended in ADR 0014 work package 7: version 1 is deleted; the shapes of 1 Auth, 2 AuthOK and 3 Put below are the retired ones, and OUT-049 has those of version 2. The other shapes, and 10 Revoke and 11 RevokeResult, are as OUT-049 says.* Every header is a canonical CBOR array whose first element is the message type, an unsigned integer. The shapes after the type are: 0 Challenge `[min, max, nonce (32), relay node key (32), relay time]`; 1 Auth `[version, fingerprint (20), signature (64)]`; 2 AuthOK `[version, max envelope, max entries, max bytes, retention seconds]`; 3 Put `[request id, to (20), mid (32), size]`; 4 PutResult `[request id, status]`; 5 Fetch `[request id, after (32 bytes or empty), max items, wait seconds]`; 6 Items `[request id, [[mid, size], ...], more]`; 7 Ack `[request id, [mid, ...]]`; 8 AckResult `[request id, deleted count]`; 9 Error `[code]`. Relay time is unix seconds, 0 to `MaxTime` (253402300799). A request id is an unsigned 32-bit integer.
- **SPO-Xmailbox-OUT-004** A Put header is followed by one raw frame of `size` bytes, and an Items header by one raw frame per listed item. The codec writes and reads the headers and the raw-frame prefix (`RawFramePrefix`), and `ReadRawFrame(r, declared, limit, want, w)` reads the whole raw frame: it checks `declared` (1 to `MaxEnvelopeBytes`), then `limit` (at most `MaxEnvelopeBytes`) and `declared <= limit`, before reading anything; then reads the 4-byte prefix and requires it to equal `declared`; then streams exactly `declared` bytes to `w` in chunks of at most 8 KiB, hashing them, and checks the hash against `want`. A body that ends early is `io.ErrUnexpectedEOF`, never a clean end. No byte beyond the frame is consumed. **Contract:** `w` receives bytes before the hash is known, so that a store can stream to a temporary file; on any error the caller must discard everything `w` received, and only a nil return means that the bytes are the envelope whose hash is `want`. A nil `w` verifies without keeping the bytes. There is no function that returns a bare length-limited reader.
- **SPO-Xmailbox-OUT-005** *Amended in ADR 0014 work package 7: statuses 0 to 8 and codes 0 to 7 are the only ones (OUT-055 adds 8 unbound, 6 not_allowed and 7 binding); `Valid` is the range of version 2.* Put statuses are 0 stored, 1 duplicate, 2 refused, 3 full, 4 too_large, 5 bad_hash, 6 busy and 7 unavailable. Error codes are 0 version, 1 auth, 2 protocol, 3 limit, 4 revoked and 5 shutting down. No other value is defined. No text travels with a code.
- **SPO-Xmailbox-OUT-006** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-OUT-050 (`Versions.Choose`; `ChooseVersion` is deleted with version 1). The version 1 text: Versions are unsigned integers from 1 to 65535. A Challenge carries `[min, max]` and an Auth the one chosen. `ChooseVersion` returns version 1 when the range holds it and refuses otherwise with `ErrVersion`. A range with `min` of 0, `min` above `max` or `max` above 65535 is malformed.
- **SPO-Xmailbox-OUT-007** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-OUT-053 (the version 2 auth bytes and `VerifyAuthV2`; `AuthBytes`, `VerifyAuth` and the label `spo/mailbox-auth/v1` are deleted with version 1). The version 1 text: The bytes a client signs to authenticate a connection are the canonical CBOR array `["spo/mailbox-auth/v1", version, relay node key, client node key, nonce, relay time, fingerprint]`. The label is the first element of the array, not a prefix of the bytes. `AuthBytes` takes only typed, fixed-length values: a version, two node keys, a 32-byte nonce, a relay time and a fingerprint. There is no argument for arbitrary bytes. `VerifyAuth(identity, tunnelPeer, signature, params)` authenticates a connection for the listed party's identity (`party.Identity`: its Ed25519 and X25519 keys and its node key) and the node key the tunnel authenticated for this connection. It enforces, each failure with its own error that also satisfies `errors.Is(err, ErrAuth)`: the identity lists a non-zero node key (`ErrAuthNoNodeKey`); the fingerprint recomputed from the identity's keys equals `params.Fingerprint` (`ErrAuthFingerprint`); `params.ClientNodeKey` equals `tunnelPeer` (`ErrAuthTunnelKey`) and equals the identity's node key (`ErrAuthIdentityNode`); the parameters are in range (`ErrRange`); and the Ed25519 signature of the identity's key verifies over `AuthBytes` (`ErrAuth` alone). No exported function verifies with a bare public key.
- **SPO-Xmailbox-OUT-008** Every bound of the ADR's table is a named constant: envelope 1 to 1 MiB; header frame 4 KiB; CBOR nesting 4, array 64, map 8 pairs; 256 entries and 64 MiB per mailbox; 64 entries and 8 MiB per pair; 64 MiB per sender; 1024 parties; 64 connections, 2 per node key, 6 new per node key per minute; 256 requests, 64 MiB received and 256 MiB sent (`MaxBytesSentPerConn`, four times the received bound) per connection; 120 puts per party per minute; 8 requests in flight; 64 hashes per ack; 16 items per fetch; a wait of at most 20 seconds; a connection lifetime of 10 minutes, an idle limit of 30 seconds and a handshake limit of 10 seconds; a clock skew warning at 5 minutes; a default total storage of 4 GiB; retention 7 days by default and 30 days at most. The decoders and encoders enforce those that concern a frame.
- **SPO-Xmailbox-OUT-009** `ValidQuota.Admit` decides one put from the usage before it: a size outside 1 to `MaxEnvelopeBytes` gives too_large, any bound that the put would pass (entries or bytes of the mailbox, entries or bytes of the sender-recipient pair, bytes of the sender, bytes of the relay) gives full, otherwise stored. `DefaultQuota` is the table; `Quota.Validate(parties)` is the configuration-load rule: 1 to 1024 parties, every bound set and no looser than the table, and the global quota at least the number of parties times the per-sender total. `Quota.Validated(parties)` runs it and returns a `ValidQuota`, the only type that has `Admit`; the zero `ValidQuota` (never validated) admits nothing, `Admit` answers `StatusFull` for it, and a store refuses a put that carries it with an error that wraps `ErrQuota`.
- **SPO-Xmailbox-OUT-010** `Expired(arrival, now, retention)` is a pure function of unix seconds: an entry is expired once `now - arrival` reaches the retention. The retention is clamped to 30 days. `ClampRetention` refuses zero and cuts a larger value to the maximum. `ExpiresAt` is `arrival` plus the clamped retention, for an arrival of 0 to `MaxTime` (253402300799, the end of year 9999) and is refused outside it, so it cannot overflow. An arrival outside 0 to `MaxTime` is expired. An arrival in the future is expired once it is more than `MaxRetentionSeconds` ahead of `now`, so that a far-future name cannot hold quota for ever; a nearer one (the clock went back) is not. For every arrival that is not in the future `Expired(a, now, r)` equals `now >= ExpiresAt(a, r)`. Retention never extends an envelope's life: a value above the maximum behaves as the maximum.
- **SPO-Xmailbox-OUT-011** *Amended in ADR 0014 work package 7: `vectors.json` holds the envelope hash and the frames that version 2 shares with the framing (the Challenge of `[2, 2]`, PutResult, Fetch, Items, Ack, AckResult, Error), ten frames; the version 1 auth bytes and the version 1 Auth, AuthOK and Put frames are gone, and `check_vectors.py` checks the rest as before. The auth bytes are in `vectors_v2.json` (OUT-057).* Test vectors are committed (`internal/domain/mailbox/testdata/vectors.json`) and regenerated and compared by a test: the envelope hash, the auth bytes with an Ed25519 signature of a fixed test key (the key is deterministic) and every frame. `testdata/check_vectors.py` recomputes the hash and the auth bytes with an independent implementation (Python standard library only), encodes every frame again from its `fields` with its own canonical CBOR encoder and compares the result with `cbor_hex`, and checks the framing. A Go test runs it when `python3` is on `PATH`; `SPO_REQUIRE_PYTHON=1` makes a missing interpreter a failure (as `SPO_REQUIRE_SSH_KEYGEN` does for `ssh-keygen`). The layout package runs its checker the same way, without the variable.
- **SPO-Xmailbox-OUT-018** *Amended in ADR 0014 work package 7: the decoders are `DecodeFromClientIn(stage, frame)` and `DecodeFromRelayIn(stage, frame)` (OUT-051); `DecodeFromClient` and `DecodeFromRelay` are deleted with version 1; the Revoke (10) is the client's and the RevokeResult (11) the relay's; the order of refusal is unknown type, wrong sender, wrong stage.* Each message type has one sender. Client to relay: Auth (1), Put (3), Fetch (5), Ack (7). Relay to client: Challenge (0), AuthOK (2), PutResult (4), Items (6), AckResult (8), Error (9). `DecodeFromClient` accepts only the first four and `DecodeFromRelay` only the other six; each refuses the others with `ErrDirection` by the type alone, before the fields are read, and an unknown type with `ErrUnknownType`. There is no exported decoder without a direction. The type, status and code values are `uint64`, so a decoded number is compared as it is and nothing is truncated on a 32-bit build.
- **SPO-Xmailbox-OUT-019** *Amended in ADR 0014 work package 7: the constructors are `NewPutV2Of(requestID, walletKey, to, envelope)` and `NewPutV2(requestID, walletKey, to, mid, size)` (OUT-049); `NewPut` and `NewPutOf` are deleted with version 1.* `NewPutOf(requestID, to, envelope)` builds the Put header of an envelope, computing its mid and size, so that they cannot disagree with it; `NewPut(requestID, to, mid, size)` checks the size and cannot check that `mid` is the hash of the envelope that will follow.

## Preconditions and failures

- **SPO-Xmailbox-PRE-001** A header frame whose length is 0 or above 4096 is refused after the 4-byte prefix, and nothing more is read.
- **SPO-Xmailbox-PRE-002** A raw frame whose length differs from the declared size is refused after the 4-byte prefix, and a declared size of 0 or above 1 MiB is refused before anything is read.
- **SPO-Xmailbox-PRE-003** A header that is not canonical CBOR is refused: an integer longer than needed, an indefinite length, a tag, a float or a simple value other than null and booleans, trailing bytes, a truncation, or anything that does not re-encode to the input. A truncation at every length and a single appended byte are refused for every message.
- **SPO-Xmailbox-PRE-004** A header that breaks a structural bound (nesting above 4, an array of more than 64 items, a map of more than 8 pairs) is refused as such before any value is built. A header with the wrong number of fields (an unknown field, a missing field), a field of the wrong kind, an unknown message type or a map where an array is required is refused.
- **SPO-Xmailbox-PRE-005** *Amended in ADR 0014 work package 7: a status above 8 and an error code above 7 are out of range, a version field is exactly 2 (PRE-028), and the AuthOK has six fields with an `until` of 1 to `MaxTime`.* A value out of range is refused, when decoding and when encoding: an envelope size of 0 or above 1 MiB; a version of 0 or above 65535; a min version above the max; a request id above 2^32 - 1; a status above 7; an error code above 5; a fetch of 0 or more than 16 items or a wait above 20 seconds; an Items header with more than 16 entries, an entry size outside 1 to 1 MiB, or `more` set with no entry; an Ack with no hash, more than 64 hashes or a repeated hash; a deleted count above 64; a relay time above `MaxTime` (253402300799), when decoding and when building the auth bytes; an Items header that lists one mid twice; AuthOK values of 0 or above the table (envelope 1 MiB, 256 entries, 64 MiB, 30 days).
- **SPO-Xmailbox-PRE-006** A byte string of the wrong length is refused: a nonce, relay key or mid of other than 32 bytes, a fingerprint of other than 20 bytes, a signature of other than 64 bytes, an `after` that is neither empty nor 32 bytes.
- **SPO-Xmailbox-PRE-007** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-PRE-058 and OUT-050 (a range that does not hold version 2 is `ErrVersion`). The version 1 text: A version range that does not hold a version this code speaks is refused with `ErrVersion`; the relay answers it with the error code 0 and closes.
- **SPO-Xmailbox-PRE-009** A streamed envelope whose size differs from the declared size, or whose hash differs from the declared mid, is refused (`Hasher.Check`, the size first), and a `Hasher` refuses bytes beyond 1 MiB.
- **SPO-Xmailbox-PRE-010** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-PRE-030 (`AuthBytesV2` and `VerifyAuthV2` refuse a relay time outside 0 to `MaxTime`; there is no version argument). The version 1 text: `AuthBytes` and `VerifyAuth` refuse a version of 0 or above 65535, a negative relay time and a relay time above `MaxTime`.
- **SPO-Xmailbox-PRE-015** An Items header, decoded or encoded, that lists one mid twice is refused with `ErrRange`.
- **SPO-Xmailbox-PRE-016** A relay time above `MaxTime` is refused with `ErrRange` in a Challenge, when decoding and when encoding, and in the auth bytes.

## Security

- **SPO-Xmailbox-SEC-001** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-SEC-038 and SEC-039 (domain separation and coverage of the version 2 array). The version 1 text: The label `spo/mailbox-auth/v1` is the first element of the signed array. The separation argument: the auth bytes are a CBOR array and start with the byte 0x87; every other message the party's Ed25519 key signs (`spo/envelope/v1`, `spo/identity/v1`, `spo/rotation/v1/old`, `spo/rotation/v1/new`) is an ASCII label followed by content and starts with a byte below 0x80. So a signature of another kind cannot be read as an auth signature, and an auth signature cannot be read as one of those. Every field of the array is covered: changing the version, either node key, the nonce, the relay time or the fingerprint, or swapping the two node keys, changes the signed bytes.
- **SPO-Xmailbox-SEC-002** *Amended in ADR 0014 work package 7: the verifier is `VerifyAuthV2` (OUT-053, SEC-037); `VerifyAuth` is deleted with version 1. A version 1 signature is no signature of version 2 (SEC-036).* `VerifyAuth` accepts only a signature made by the listed identity's key over exactly these values: another key, any flipped signature bit, a changed field and a signature under another label are refused with `ErrAuth` alone (the bindings of SEC-012 have their own errors).
- **SPO-Xmailbox-SEC-003** Every length, count or size read from the wire is checked against its bound before anything of that size is allocated or read for it. A header claiming an array or string of 2^32 or 2^64 - 1 items allocates less than 16 KiB when refused; a header frame or raw frame prefix claiming a larger size reads only its 4 bytes and allocates less than 8 KiB.
- **SPO-Xmailbox-SEC-004** The quota and retention arithmetic does not wrap: `used + size` is never computed (the test is `size <= max` and `used <= max - size`), usage near the top of uint64 is full, and a retention age is computed only when the arrival is not negative and not in the future.

- **SPO-Xmailbox-SEC-012** *Amended in ADR 0014 work package 7: the identity is built from the presented keys and checked by `VerifyAuthV2`; the relay's key, nonce and time and the tunnel peer are the relay's own (SEC-064, SEC-065); there is no access-list entry.* The identity the relay authenticates is bound to the connection, not only to a signature: a valid signature by a key that does not belong to the claimed fingerprint, or a claim of a node key that is not the one the tunnel authenticated, is refused. The relay takes `params.RelayKey` from its own key, `tunnelPeer` from the tunnel and the identity from its access list entry for `params.Fingerprint`, never from the client's message; `VerifyAuth` checks the rest (OUT-007).
- **SPO-Xmailbox-SEC-013** A relay time is bounded to 0 to `MaxTime` on decode and in the auth bytes. `Skew(relayTime, now)` is the distance in seconds, never negative, saturating at the largest int64 instead of wrapping, for any two int64 values. A client compares it with `ClockSkewWarningSeconds` and never does `time.Duration` arithmetic on a relay-supplied time.
- **SPO-Xmailbox-SEC-014** Only a `ValidQuota` decides a put (OUT-009). Nothing that arrives from a configuration, a test or a zero value reaches `Admit` without `Validate` having accepted it, and the zero value fails closed.
- **SPO-Xmailbox-SEC-015** An entry whose arrival time is beyond `MaxTime`, or more than `MaxRetentionSeconds` ahead of the store's clock, is expired by the retention rule and swept; it does not hold quota for ever. The store does not name a new entry by a clock outside 0 to `MaxTime`. At open, a name whose arrival is above `MaxTime` but fits an int64 (SEC-007) is accepted and counted, then swept; refusing it would let one wrong clock stop the relay from starting.

## Invariants

- **SPO-Xmailbox-INV-001** `internal/domain/mailbox` imports no adapter, platform, port or use-case package, and no `os`, `net`, process, unsafe or random-source package (a test parses the imports of its own source files).
- **SPO-Xmailbox-INV-002** *Amended in ADR 0014 work package 7: read `DecodeFromClientIn` and `DecodeFromRelayIn` at a stage for the decoders, and `Encode` (version 2) for the encoder (INV-029).* Whatever `DecodeFromClient` or `DecodeFromRelay` accepts, `Encode` reproduces byte for byte; for every vector and every sample, decoding `Encode(m)` from its sender's side gives `m`. A single flipped bit of a valid frame is refused or decodes to a message that re-encodes to exactly the flipped bytes.
- **SPO-Xmailbox-INV-003** *Amended in ADR 0014 work package 7: the stage decoders replace the two direction decoders (INV-030).* No input makes `DecodeFromClient`, `DecodeFromRelay`, `ReadHeaderFrame`, `ReadRawFrame` or `ParseHash` panic (fuzz targets seeded with the vectors; every seed is small and inputs over 512 bytes are skipped so the engine does not spend its time minimising a large input).

## Choices that go beyond the ADR text

- **The fingerprint is in the signed array.** ADR 0013 decision 3 lists the array with the fingerprint as the last element. The work package description lists the fields without it. The array of the ADR is used; a signature therefore also binds the claimed identity.
- **Empty and duplicate lists.** An Ack of no hash, an Ack with a repeated hash and an Items header with `more` set and no entry are refused. The ADR says "up to 64".
- **Maps.** No message holds a map. The structural bound of 8 pairs is enforced, and a map that passes it is then refused by type.
- **Zero values.** A request id of 0 is valid. A zero quota, a zero retention and a zero AuthOK limit are refused.
- **Expiry at the boundary.** An entry whose age equals the retention is expired. A zero retention, or a negative arrival time, is expired (fail closed); an arrival in the future is not.
- **Direction.** The decoders take the direction (OUT-018): a session cannot decode a frame without saying which peer sent it.
- **`identity.DecodeCanonical` in place of the envelope adapter's decode options.** The header decoder uses the canonical decoder of `internal/domain/identity`, after its own structural pre-scan, and not the decode options that `adapters/envelope` builds on, because that adapter links age and a pure package cannot import it. The decoded value must re-encode to the input, which is the canonical rule.
- **The numbering of the preconditions** skips PRE-008. The corpus never renumbers an id (see `spec/README.md`), so the gap stays.

### What a session must still do

The package checks what it can from one message. These obligations are the session code's. The relay half of each is discharged by `internal/app/relay` and the requirement named after it; the client half (work package 6) is discharged by `internal/adapters/mailbox` and the requirement named after it ("The mailbox client (work package 6)").

- Take `params.RelayKey` from the relay's own key, `tunnelPeer` from the tunnel, and the identity from the access list entry for the claimed fingerprint; never from the Auth frame (SEC-012). **Relay: OUT-025 and SEC-020.** The entry is found by the tunnel node key, and the claimed fingerprint must equal the entry's.
- Check that the number of items in an Items reply is at most the `max items` of the Fetch it answers, and that each item size is at most the `max envelope` of the AuthOK that announced it (pass it as `limit` to `ReadRawFrame`). **Relay (what it sends): OUT-027, INV-012.** The relay sends at most the smaller of the request's and the limit's items and none above the announced envelope limit. **Client (reading Items): OUT-039, SEC-027.** The client checks the count against the request's `max items`, each size against the envelope limit (its own, tightened by AuthOK) before the body is read, and reads each body with `ReadRawFrame`.
- Send, after a Put header, exactly the envelope whose hash and size are in it (`NewPutOf` makes the header right; the bytes are the sender's), and read one raw frame per Items entry with the entry's mid and size. **Relay: OUT-026 (reads the Put's raw frame with `ReadRawFrame`) and OUT-027 (sends one raw frame per entry, the header listing exactly those). Client: OUT-035 (sends a Put made by `NewPutOf` and exactly its bytes) and OUT-039 (reads one raw frame per Items entry against the entry's mid and size).**
- Check that `AckResult.Deleted` is at most the number of hashes in the Ack it answers. **Relay (what it sends): OUT-028. Client (checking the reply): OUT-037.**
- Keep the request-id rule: a reply carries the id of the request it answers, and an id in flight is not reused. The package gives every id the meaning of an unsigned 32-bit number and no more. **Relay: PRE-023** (ids unique on the connection, replies carry the id). **Client (the counter, at most 8 in flight): OUT-041** (a counter that starts at 1 on each connection; one request in flight; a reply with another id is a violation, OUT-039 and PRE-025).
- Compare `Skew` with `ClockSkewWarningSeconds`, and count the limits per connection (requests, bytes, in flight, lifetime, idle). **Relay: INV-012** (the limits it counts). **Client (the skew warning): OUT-040; the limits it counts: OUT-041.**
- On any error from `ReadRawFrame` discard what the writer received. **Relay: OUT-026 and SEC-023.**
- Check access again immediately next to the `Put`, not only at the start of the request: a put whose caller checked access, then saw an access-list reload and `RemoveMailbox` for that recipient or sender, and only then reserved, is stored (INV-009 cancels only puts that had reserved). The server work package chooses one of two ways and tests it: the re-check of the (sender, recipient) pair against the list in force at the moment of the call (with the reload and the removal ordered so that a removal is never followed by a put that passed a check made before it), or a short-lived tombstone of the removed recipient that `Put` consults. Recorded obligation: the re-check, next to the `Put`; the tombstone stays the fallback if the re-check cannot be ordered with the reload. **Chosen: the re-check next to the `Put`, plus the whole decision made again after a stored put, which takes the entry back with the sender's own retraction when access no longer allows it (SEC-021, OUT-031). Tested with a reload between the check and the call, one inside the store's `Put` and one on the last byte of the body. The tombstone is not needed, and cannot be: the session holds no `MailboxRevoker`.**
- Take `MailboxAcker` in the ack handler, for acks only, `MailboxRetractor` for undoing the session's own put, and `MailboxRevoker` only in the access-list reload; never the union. **Relay: IF-005 and SEC-024** (the `Config` has no field for the revoker, the expirer or the whole store; a test parses the sources). The reload (work package 7) takes `MailboxRevoker` and calls `Server.CloseParty`, on a removal and also on a change of the party's node key (SEC-025); the session does not depend on it.

## Ports, store, access list and stream (work packages 2 and 4)

These requirements specify the server-side ports of [ADR 0013](../../docs/explanation/adr/0013-tailnet-relay-and-mailbox.md) decision 7, the directory store `internal/adapters/mailboxstore`, the configuration reader `internal/adapters/relayconfig` and the in-process fake tunnel `test/fakenet`. The relay session logic (work package 3) is specified in the last section of this file; the tailcat adapter (work package 5) is not specified here.

### Interfaces

- **SPO-Xmailbox-IF-001** The mailbox store is seven narrow capabilities in `internal/ports/relayport`: `MailboxWriter` (`Put`), `MailboxReader` (`List`, `Open`), `MailboxAcker` (`Remove`, the entries of one recipient by id, every sender's copy), `MailboxRetractor` (`Retract`, one sender's own copy of one id and no other: OUT-031), `MailboxRevoker` (`RemoveMailbox`, a whole mailbox), `MailboxExpirer` (`Sweep`) and `MailboxUsageReader` (`Usage`). The ack capability, the retraction and the mailbox-wide deletion are separate types, so the ack handler, which takes `MailboxAcker` for acks only, cannot delete a mailbox, and the compensation, which takes `MailboxRetractor`, cannot delete another sender's copy; the access-list reload takes `MailboxRevoker`. `MailboxStore` is their union with `Close`, for the composition root only. A holder takes the narrow interface it needs. `relayporttest.RunMailboxStore` is the contract every implementation passes. The relay ports are in their own package, `relayport`, and not in `internal/ports`, so that the relay's code does not link what `internal/ports` links (SEC-009, SEC-016); `relayport.Clock` is the method set of `ports.Clock`. *Amended in ADR 0015 work package 5 (decision 2, m1):* the body of a `Put` is streamed, or held whole up to `mailbox.MaxEnvelopeBytes` by an adapter whose store cannot refuse wrong bytes; such an adapter holds at most `relayport.MaxHeldBodies` (64) bodies, `MaxHeldBodyBytes` (64 MiB) for the whole store, and a put that finds no room waits for one until its context ends and otherwise fails as a store failure does. Nothing is visible to a reader before the hash is checked. The directory store streams, as before.
- **SPO-Xmailbox-IF-002** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-IF-022 (`relayport.AccessList` and `AccessEntry` are deleted; the tunnel list is the configuration's `[[device]]` tables and admission is the registry's). The version 1 text: `relayport.AccessList` has `Lookup` by fingerprint, `LookupNode` by tunnel node key and `NodeKeys`. An `AccessEntry` carries the party's verified identity document, its fingerprint recomputed from the keys in it, its non-zero node key and its `send_to` list. `MaySendTo` is true only for a fingerprint in `send_to`.
- **SPO-Xmailbox-IF-003** `relayport.Stream` is an ordered byte stream with `Read`, `Write`, `Close` and the three deadline setters, as `net.Conn` without addresses. A deadline that passes ends a blocked or later `Read` or `Write` with an error for which `errors.Is(err, os.ErrDeadlineExceeded)` holds, and the stream stays usable once the deadline is cleared. `StreamListener.Accept` and `StreamDialer.Dial` return the peer's node key as the tunnel authenticated it; the dialer compares the key it is given with the one it pinned. Over tailcat the key a dialer returns is the pinned key: the dialer is made for one key and the binding between the key and the stream is the tunnel's handshake to it, which fails when the peer does not hold it; it is the listener that reports a key the peer proved. Both honour their context, and a closed listener refuses `Accept` at once. What a listener must provide beyond this, and the errors it reports, are IF-007. Nothing in the ports names a tunnel library. `relayporttest.RunStream` is the contract (IF-004).
- **SPO-Xmailbox-IF-004** The stream contract (`relayporttest.RunStream`) holds every tunnel to the allow-list and to its deadlines and cuts: a dialer whose node key is not listed is refused and nothing reaches the listener; an empty allow-list admits no one; a write against a peer whose buffer is full ends at the write deadline with `os.ErrDeadlineExceeded`, the bytes it took are delivered and the stream is usable once the deadline is cleared; a stream cut in the middle delivers the bytes before the cut and then fails on both sides with an error that is not `io.EOF`. A final message written just before `Close` reaches a peer that had pipelined unread data (`FinalMessageSurvivesCloseWithUnreadInbound`); a past deadline set from another goroutine unblocks a pending `Read` and a blocked `Write` (`PastDeadlineFromAnotherGoroutineUnblocksReadAndWrite`). A rig supplies the four extra rigs these cases need (`Stranger`, `Empty`, `Bounded`, `Cut`); a nil one fails the suite. `StreamRig.StallBytes` (zero: 64 KiB; at most `relayporttest.MaxStallBytes`, 16 MiB) sizes the `Bounded` stall for a tunnel whose buffers cannot be limited. `relayport.Aborter` (`Abort`, a reset at once) is optional; `relayport.Abort` uses it when a stream has it.

### Store

- **SPO-Xmailbox-OUT-012** The store is a directory: `<root>/.spo-relay.lock` and `<root>/mailbox/<recipient fingerprint, 40 hex>/<arrival, 20 decimal digits, zero-padded>-<mid, 64 hex>-<sender fingerprint, 40 hex>`. The arrival time is the store's clock in unix seconds. The sender is in the name so that the per-pair and per-sender counters are rebuilt from names alone. Directories have mode 0700 and files 0600. A temporary file is `.tmp-<16 hex>` in the recipient's directory. Name order is arrival order.
- **SPO-Xmailbox-OUT-013** `Put` decides, in this order and under the store's lock: a declared size outside 1 to 1 MiB is `too_large`; an entry with that recipient, that sender and that mid is `duplicate` and costs nothing; the same (recipient, sender, mid) being put right now is `busy` (OUT-021); the domain's `ValidQuota.Admit` over the usage including puts in flight gives `full` or `too_large`; otherwise the quota is reserved and the body is read. The decision is made before a byte of the body is read. The store takes a `mailbox.ValidQuota`, so a quota looser than the table cannot reach it; it refuses the zero `ValidQuota` with an error that wraps `mailbox.ErrQuota`. After a `stored` the entry is visible with its arrival time, size and sender.
- **SPO-Xmailbox-OUT-014** The body is streamed to a temporary file through a hasher, never held whole or twice. `List` returns entries in arrival order (OUT-022), starting after the entry with the id `after`, from the start when `after` is absent or no longer there, with `more` set when entries remain. `Open` returns a reader of exactly the recorded size. `Remove` deletes the entry of one recipient with that id and reports whether it was there (OUT-021); `Retract` deletes only one sender's copy of it (OUT-031). `RemoveMailbox` deletes every entry of one recipient. `Sweep` deletes the entries for which the domain's `Expired(arrival, now, retention)` holds. An emptied mailbox directory with no put in flight is removed.
- **SPO-Xmailbox-OUT-015** The counters (entries and bytes of a recipient, of a sender-recipient pair, bytes of a sender and of the store) are recomputed at open from the directory, by name and `fstatat` size, reading no file, and are kept in step by every put, remove and sweep. A reservation made by a put counts until the put ends. `Usage` reports them.
- **SPO-Xmailbox-OUT-020** `Put` reads exactly the declared size from the reader: never the byte after it, so a reader that is a stream with another frame behind the body keeps the frame, and the put never waits for a byte it does not need. Framing (a body longer than declared) is the caller's, not the store's. The reader carries the deadline: the store has no reservation timeout, so a reader that blocks holds its reservation until it returns an error, and that error releases the reservation. The context is checked between reads, not during one.
- **SPO-Xmailbox-OUT-021** The `stored`, `duplicate` and `busy` decision is keyed by (recipient, sender, mid). The same bytes from another sender are another entry: the name already carries the sender, the quota is charged to that sender, and the answer tells a sender nothing about what other senders put (no probe of what is in a mailbox, no squatting of an id). Counters and the name stay unique per (recipient, sender, mid). An id names the recipient's message: `Remove` deletes every copy of it, `Open` returns the first stored copy (the bytes are the same), and `List` returns one entry for each id: the first stored copy, at that copy's place in the order, and no later copy. A page never repeats an id, so it always encodes as an `Items` message, and a listing resumes after the place of the first copy of `after`. Counters and quotas still charge each copy to its sender. There is no tombstone after an ack: a re-put of the same bytes, or a mailbox directory restored from a backup, can deliver a message again. The client is the one that tolerates repeats (ADR 0013: the application already handles repeated requests).
- **SPO-Xmailbox-OUT-022** A new entry's arrival is strictly later than every arrival already in that recipient's mailbox: the store's clock, or one second after the newest arrival when the clock is not later than it, decided under the store's lock. An existing arrival more than `MaxRetentionSeconds` ahead of the clock, or above `MaxTime`, is not counted as the newest (the rule of `Expired`, SEC-015), so one bad clock reading is not copied onto later puts and the next sweep does not remove them unread. A put that would need an arrival above `MaxTime` is refused with an error and stores nothing. Arrivals are therefore distinct in a mailbox, the names are totally ordered, and the listing order is the same while the store runs and after a reopen: a client that resumes after an entry, across a restart, never misses one that arrived later. The cost is a drift of an entry's arrival ahead of the clock: one second for each put committed while the newest arrival is not behind the clock. A burst of puts into one mailbox drifts by at most the number of entries it adds, and a mailbox holds at most `MaxMailboxEntries` (256), so a burst is bounded by that many seconds, and the drift ends when the clock passes the newest arrival. It is not bounded by the entry bound alone: a mailbox whose newest entry is kept while older ones are acked and new ones put can run further ahead, by a second for each such put, up to the `MaxRetentionSeconds` beyond which an arrival is no longer counted. An entry with a drifted arrival is kept that much longer than the retention.
- **SPO-Xmailbox-OUT-023** At open the store repairs what it can: a mailbox directory with no entry (a temporary file does not count) is removed, with one note counting them; two entries with one recipient, sender and mid keep the earlier arrival (the lower name on a tie) and the later is removed, with one note per removal naming it. `Open` returns the notes and logs nothing (the project has no logging port); the caller logs them. The counters are built from what remains. Mailbox names are read in chunks and refused past 8192, and past 1024 that hold an entry.
- **SPO-Xmailbox-PRE-011** A body whose length differs from the declared size, or whose hash differs from the declared mid, stores nothing: no visible entry, no temporary file left, no usage kept. The error wraps `mailbox.ErrSize` or `mailbox.ErrHash` (PRE-017 for a short body). A cancelled context stores nothing.
- **SPO-Xmailbox-PRE-017** A body that ends before the declared size is refused with an error that wraps both `mailbox.ErrSize` and `io.ErrUnexpectedEOF`, and stores nothing. A reader that returns a deadline error mid-body ends the put with that error and releases the reservation.
- **SPO-Xmailbox-PRE-018** A put that fails after its entry was linked removes the entry again. When that removal fails too, the error reports both failures, and the entry that stays on the disk is the store's: it is listed, counted and answered `duplicate` to a retry, so that memory and disk agree.

### Safety of the directory

- **SPO-Xmailbox-SEC-005** `Open` refuses, with an error that wraps `ports.ErrMailboxCorrupt`, a directory that holds anything a mailbox does not: a symbolic link, FIFO, directory or other non-regular entry where a file belongs; a stray name in the root or in `mailbox/`; a badly named mailbox or entry; more than 1024 mailboxes that hold an entry, more than 8192 names in `mailbox/`, more than 256 entries or 512 names in a mailbox; an entry file of size 0 or over 1 MiB; a file or directory that is not owned by the effective user (SEC-017) or that has any group or other permission bit. A root that is writable by its group or others, or owned by another user, is refused. A temporary file left by a crash is removed at open; one that is not a regular file is refused and left alone. What a crash or a failed rollback can leave is repaired and not refused (OUT-023). Opening reads no FIFO and blocks on none.
- **SPO-Xmailbox-SEC-006** Every size is checked against the domain bounds before anything is read or allocated for it: a declared size before the body, a file size at open and again by fstat on the descriptor that `Open` reads, a directory listing in chunks against its count bound. An entry that has changed size since it was indexed is refused, and the reader yields no more than the recorded size.
- **SPO-Xmailbox-SEC-007** Names are validated strictly before use: a mailbox name is exactly 40 lower-case hex digits, an entry name exactly the shape of OUT-012 with an arrival that fits an int64, a temporary name exactly `.tmp-` and 16 lower-case hex digits. A trailing newline, upper case, a path separator or any other deviation is refused.
- **SPO-Xmailbox-SEC-008** Every operation is relative to a directory descriptor opened once at `Open` with `O_NOFOLLOW`, and every file is opened without following links and required to be a regular file by fstat on the descriptor. Replacing a directory or a file by a link after `Open` cannot redirect an operation.
- **SPO-Xmailbox-SEC-009** The sealed envelopes are opaque to the relay's code, and what links into it cannot open one. The relay side is `app/relay`, `adapters/mailboxstore`, `adapters/relayconfig`, `ports/relayport`, `domain/mailbox` and the tunnel adapter `adapters/tailcat/stream` (and, since ADR 0014 work package 10, `domain/relayconf`, `app/relayhost` and the relay main `cmd/spo-relay`). The rule has four parts, each a pure function over the import graph that `go list -deps` gives (non-test), and each shown to bite by a test on synthetic graphs:

1. **Hard bans over the full closure** of every relay-side package, the tunnel adapter included: no `filippo.io/age` (nor a subpackage), no `adapters/envelope`, no `adapters/sqlitestore`, no sqlite driver (`modernc.org/sqlite`), no `internal/platform/secret`, no memguard, no `domain/unlock`.
2. **Primitive bans over the import walk** from the relay-side roots that does not descend into `adapters/tailcat/stream`: none of `crypto/ecdh`, `crypto/hpke`, `crypto/mlkem`, `crypto/hkdf`, `golang.org/x/crypto/hkdf`, `golang.org/x/crypto/curve25519`, `golang.org/x/crypto/chacha20poly1305` and everything below `golang.org/x/crypto/nacl` is reached. Tunnel transport crypto (WireGuard, TLS to DERP) is allowed only below the tunnel adapter's own import path, and nothing else in the relay may use it. The walk follows the import lists; it is not the difference of two closures, because a difference hides a relay package that imports a primitive directly when the tunnel adapter reaches the same one. A test shows that exact case: the walk reports it and the difference does not. The property this part states is about envelopes, and envelope crypto is `age`, which part 1 bans in the whole closure. The pre-existing check of the four packages `adapters/mailboxstore`, `adapters/relayconfig`, `ports/relayport` and `app/relay` stays: their full closure contains none of the hard-banned or primitive packages.
3. **An explicit allow-list of the tunnel adapter's direct imports**: the standard library packages it uses (`context`, `crypto/rand`, `errors`, `fmt`, `io`, `net`, `os`, `reflect`, `strings`, `sync`, `sync/atomic`, `time`, `unsafe`), `github.com/tailscale/tailcat`, `go4.org/mem`, `gvisor.dev/gvisor/pkg/tcpip`, `gvisor.dev/gvisor/pkg/tcpip/adapters/gonet`, `tailscale.com/tailcfg`, `tailscale.com/types/key`, `tailscale.com/wgengine/filter`, and, of this module, `domain/party` and `ports/relayport`. A new direct import fails the test until it is added on purpose; so does a listed entry that nothing imports.
4. **A confined list of importers** of `github.com/tailscale/tailcat`, `tailscale.com/...`, `gvisor.dev/...`, `github.com/tailscale/wireguard-go/...` and `golang.zx2c4.com/wireguard...`: `adapters/tailcat`, `adapters/tailcat/stream`, and, as an existing gap that is not moved, `cmd/spo`, which may import only `tailscale.com/tailcfg` (`cmd/spo/party.go` types its test hook `derpRegion *tailcfg.DERPRegion` with it). Any other importer, a lookalike prefix included, fails.

The self-tests show that each name of parts 1 and 2 bites, in a relay package, below one and through the tunnel adapter, and that `crypto/ed25519`, `crypto/rand`, `crypto/sha256` and `blake2b` do not. What the closure does contain: `domain/party` imports `domain/custody`, `domain/identity`, `domain/cose` and `domain/chain`, which are pure data and rules (key roles, signing capability profiles, canonical encodings, chain types), hold no key material, open nothing and do no I/O, so they are accepted. The crypto that is linked, and why: `crypto/ed25519` to verify a party's self-signature and the AuthOK signature, `golang.org/x/crypto/blake2b` for fingerprints and envelope ids, and `crypto/rand` for the names of temporary files. The Go standard library's own FIPS module is linked under `crypto/rand` and `crypto/ed25519` (AES, HMAC, SHA-2 and SHA-3 internals); none of it is reachable from the relay's code to seal or open an envelope. The test is skipped only when the go tool is absent. `Remove` is a method of the mailbox store only: the store implements no object port, and the directory sink and layout directory have no method named Remove, Delete or Unlink.
- **SPO-Xmailbox-SEC-016** The relay ports (`ports/relayport`, and its suites in `relayport/relayporttest`) import the standard library, `domain/mailbox` and `domain/party` and nothing else of this module (a test lists the imports). `internal/archtest` treats both as ports packages, so the layering rule applies to them as to `internal/ports`. The tunnel adapter is held by the same discipline from the other side: its direct imports are an explicit allow-list and the tunnel libraries have a confined list of importers (parts 3 and 4 of SEC-009).
- **SPO-Xmailbox-SEC-017** Every owner check of the store compares with one effective uid that a test can change (`geteuid`): the root directory, the lock file, `mailbox/`, each mailbox directory, each entry file and each temporary file. A test makes each check fail in turn and expects a refusal, and expects the exact number of checks for a fixed directory.

### Access list

- **SPO-Xmailbox-OUT-016** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-IF-022 and PRE-060 to PRE-064 (the version 2 file). The version 1 text: The relay configuration is a file of `[relay]` (retention and the six quota bounds, all optional, default the ADR table, retention 7 days) and `[[party]]` tables (`label`, `document` as base64 of the signed identity document, `send_to` as a list of 40-hex fingerprints). The label defaults to the document's. The access list is the parties in file order, and the tunnel allow-list is exactly their node keys. The file is read only after its size has been checked against 4 MiB; a line is at most 64 KiB; a document at most 4 KiB decoded, checked on the base64 length before decoding. A label is non-empty (not only spaces) and differs from every other party's (PRE-019). The file is read by the shared subset parser (OUT-024).
- **SPO-Xmailbox-OUT-024** The relay's file and the workspace file are read by one parser, `internal/platform/tomlsubset`, a pure package of the platform layer that both adapters may import. The relay turns on arrays of tables, lists of strings and unsigned integers; the workspace file keeps booleans, signed integers and the escapes `\n` and `\t`. What is off is an error. Bounds (line length, count of `[[party]]` tables, items of a list) are checked as the file is read, so a file that claims more than the bound is refused at the bound.
- **SPO-Xmailbox-SEC-010** ~~withdrawn~~ in ADR 0014 work package 10: the relay reads no identity document (ADR 0014 decision 5). The version 1 text: Each document's self-signature is verified (`party.Document.Verify`). A document that does not verify is refused, and so is one with no node key or a zero node key. The fingerprint is recomputed from the keys in the document and is not a field of the file. Two parties with one fingerprint, or one node key, are refused. The document parser is injected (`DocumentParser`), because the real one is in `adapters/envelope`, which links age.
- **SPO-Xmailbox-SEC-011** (Amended in ADR 0014 work package 10: `send_to` and `AccessEntry` are deleted with the version 1 access list; what holds is the last sentence.) The tunnel allow-list fails closed: a tunnel whose allow-list is empty admits no node (fakenet implements it so, as the relay must).
- **SPO-Xmailbox-SEC-018** (Amended in ADR 0014 work package 10 for the version 2 file of IF-022.) The configuration file must be owned by the effective user or by root, checked by fstat on the opened descriptor: another owner could add a device to the tunnel list or change the admission. A file of a user is refused when the relay runs as root. The effective uid is a variable of the package, so that a test can change it.
- **SPO-Xmailbox-SEC-019** Every control character other than tab, and every bidirectional control, isolate and line or paragraph separator (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, U+2028, U+2029), is refused anywhere in a line of either file, comments included. The set is one function, `tomlsubset.ActiveRune`, which the parser, the writer and the workspace configuration's own checks all use. The writer cannot produce what the reader refuses: `tomlsubset.Quote` refuses text that is not UTF-8 and any such character but tab and newline, which it escapes, and `config.Marshal` (so `Create` and `Save`) refuses the value with an error that names the field. A carriage return is accepted only as the CR of a CRLF line ending (a final CR with no line feed after it is not). A bare CR hides the text after it from a reader on a terminal while the parser reads it as a line of its own: `# old` then CR then `retention_seconds = 60` shows one comment and sets a value. Tab is whitespace outside a string and refused inside one. The error names the line.
- **SPO-Xmailbox-PRE-012** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-PRE-060 to PRE-062. The version 1 text: Loading refuses, with an error that names the party or the line: an empty list or more than 1024 parties (counted at the 1025th header, before any document is decoded); an unknown key or table, a repeated key or `[relay]`, a key outside a table, a value of the wrong kind, an unclosed or non-UTF-8 string, an escape other than `\"` and `\\`, a sign, hexadecimal, underscore or leading zero in an integer, a multi-line array; a file larger than the bound, a line larger than its bound; a file that is not a regular file or that is writable by its group or others.
- **SPO-Xmailbox-PRE-013** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-PRE-064 (the open quota's rule). The version 1 text: Retention is 1 to 30 days and is refused beyond. Each quota bound is set and no looser than the table, and the global quota covers the number of parties times the per-sender total (`Quota.Validate`); otherwise loading fails with the domain's message.
- **SPO-Xmailbox-PRE-014** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-OUT-102 (the reload of the device list). The version 1 text: A reload that fails (any refusal above) keeps the list that was in force, and the first load must succeed. A successful reload replaces the list as a whole.
- **SPO-Xmailbox-PRE-019** ~~withdrawn~~ in ADR 0014 work package 10; superseded by SPO-Xmailbox-PRE-060 (labels of `[[device]]` and `[[wallet]]`). The version 1 text: A label is not empty (a label of only spaces counts as empty) and is not the label of another party, whether it is given or taken from the document. Loading refuses a list that breaks either rule, naming the party.

### Locks and crashes

- **SPO-Xmailbox-INV-004** One process owns the directory: `Open` takes an exclusive `flock` on the lock file without waiting and fails with `ErrLocked` while another holder has it, in this or another process. `Close` releases it.
- **SPO-Xmailbox-INV-005** An entry is visible only whole. A put writes a temporary file, `fsync`s it, links it to its final name, removes the temporary name and `fsync`s the directory. A crash at any of those points leaves either no entry or a whole entry, never a partial one, and the next `Open` removes the temporary file; a failure at any step stores nothing, leaves no temporary file and releases the reserved quota. A remove unlinks and `fsync`s; a crash between leaves the entry present or absent, with counters that match the directory.
- **SPO-Xmailbox-INV-008** Under concurrent puts, removes, sweeps and listings the counters equal what the directory holds. Concurrent puts of one entry store it exactly once. Concurrent puts never pass a bound of the quota. A slow body does not hold the store's lock: the lock is held for the decision and for the final link only.
- **SPO-Xmailbox-INV-009** `RemoveMailbox` cancels the puts to that mailbox that have reserved and not committed: they store nothing, release their reservation, leave no directory behind and fail with an error that wraps `ErrMailboxRevoked`. A put that starts after the removal is a new put. The marker that does this exists only while such a put exists.
- **SPO-Xmailbox-INV-010** After `Close`, and while it runs, every operation either completes on descriptors it owns or fails with `ErrMailboxClosed`. None uses the store's directory descriptors outside the lock: a put or a read takes a duplicate under the lock, so a descriptor number that the process reuses after `Close` cannot be the one an operation writes through. Tests run `Close` against puts, reads, listings and sweeps under the race detector, and make a closed store's descriptor number reused before a put continues.
- **SPO-Xmailbox-INV-011** `RemoveMailbox` unlinks every entry of the mailbox and then syncs its directory once; `Sweep` does the same for one mailbox at a time and releases the lock between mailboxes, so a sweep of many entries does not hold the lock for one `fsync` per entry. An emptied directory costs one more sync, of its parent, for its removal. The counters follow each unlink.

### The fake tunnel

- **SPO-Xmailbox-OUT-017** `test/fakenet` has named nodes with deterministic node keys, a listener per node with an allow-list, dial and accept, and these faults, each deterministic: refuse a dial; cut a stream after N bytes in a direction (the bytes before the cut are delivered, then both ends fail with `ErrCut`; a write of exactly N bytes succeeds and the next fails); stall a direction after N bytes (the reader blocks until its deadline or its own `Close`); deliver one byte per read; report another node key to the dialer or to the listener; and make the next accepts of a listener fail with given errors (`Listener.FailAccept`, `fakenet.ErrTemporary` for a retryable one, IF-007), waking an `Accept` that is already waiting.
- **SPO-Xmailbox-INV-006** Fakenet buffers are bounded (64 KiB per direction by default, settable): a writer blocks when the buffer is full and ends at its write deadline. The listener's backlog is bounded (8). Deadlines end blocked operations, also when set while the operation is blocked. Fakenet starts no goroutine; a test that runs it leaves none behind (`fakenet.CheckLeaks`). Nothing opens a socket.

### Choices that go beyond the ADR text (work packages 2 and 4)

- **The put reserves, then streams.** The ADR says the store checks existence under the lock. The store checks, decides the quota and reserves under the lock, streams the body outside it and links under it. A slow uploader would otherwise stop every other put.
- **The store decides the quota.** `MailboxPut` carries the `ValidQuota` and the store runs `ValidQuota.Admit` under its lock; asking `Usage` and then putting would be a race between connections.
- **The sender is in the entry name**, beyond the ADR's `<arrival>-<mid>`. Without it the per-pair counters could not be rebuilt without reading envelopes. It is also in the duplicate key (OUT-021): the ADR keys a duplicate by (recipient, mid), which lets a second sender probe or squat an id.
- **Arrival is 20 digits, zero-padded**, so that name order is arrival order.
- **`List`'s `after` that is gone restarts from the beginning.** An acked entry is deleted, so a position cannot be remembered by name. The ADR has the client fetch again from the start after an ack.
- **A mailbox directory is removed when it is empty** and nothing is being put, so that revoked parties do not accumulate towards the 1024 bound that `Open` enforces; `Open` also removes the empty ones it finds (OUT-023).
- **`Dial` returns the peer's node key.** The ADR's `StreamDialer.Dial` returns a stream only. The caller needs the key to compare with its pin, and fakenet needs it to model a mismatch.
- **Stricter than the ADR:** `send_to` must name parties of the list; retention above 30 days is refused, not clamped; a group-writable or world-writable configuration file is refused.
- **One subset parser for two files.** `adapters/config` and `adapters/relayconfig` read their files with `internal/platform/tomlsubset` (OUT-024). The relay's copy that this work package first had is gone: the two had the same flaw (SEC-019) and would have kept diverging.

## The relay session (work package 3)

These requirements specify `internal/app/relay`: the session logic of the relay (the `Server`, one session on each connection) and the retention `Sweeper`. The package imports the standard library, `domain/mailbox`, `domain/party` and `ports/relayport` and nothing else of this module (SEC-009). It holds no store, no key and no file. The relay's main (work package 7) wires it; the client (work package 6) is the other end of the protocol.

Time: the relay's `Clock` is the wall clock of the Challenge, of the rate windows and of the log. Stream deadlines are real time, taken from the process clock, because a stream's deadline is a `time.Time` of the tunnel. Every limit of the ADR's bounds table is a field of `Limits` with the table's value as its ceiling: a server may only tighten it.

### Interfaces

- **SPO-Xmailbox-IF-005** ~~withdrawn~~ in ADR 0014 work package 6; superseded by SPO-Xmailbox-IF-015 (the session takes the registry and no access list; the revoker is the revoke path's). The version 1 text: `relay.New(Config)` takes narrow capabilities only: `relayport.MailboxWriter`, `MailboxReader`, `MailboxAcker` (acks only), `MailboxRetractor` (the compensation of the session's own put), `MailboxUsageReader`, `AccessList`, `Clock`, a random source for nonces, the relay's own node key, a `mailbox.ValidQuota` and a `ValidLimits`. There is no field for `MailboxRevoker`, `MailboxExpirer` or the whole store, and no non-test source of the package outside the sweeper names them (a test parses the sources). `New` refuses a missing capability, a zero relay key, a quota or limits that were not validated (`Quota.Validated`, `Limits.Validated`) and an empty access list: the tunnel allow-list is exactly the list, and an empty one admits no one (concern T2). `Limits` has a ceiling for each bound of the ADR's table and refuses zero and anything looser; the fetch wait may be tightened to 0 (long-poll off). `Server.Serve(ctx, listener)` accepts connections, runs one session on each and returns after every session has ended; `Server.CloseParty(fingerprint)` ends a party's live sessions (SEC-024). `NewSweeper` takes only a `relayport.MailboxExpirer`, a `relayport.Clock`, a retention and an optional sink (OUT-030).
- **SPO-Xmailbox-IF-006** The session reports to an `EventSink` (a func type; nil drops the events). An `Event` holds a kind (`connect`, `rejected`, `auth_fail`, `auth_ok`, `put`, `fetch`, `ack`, `close`, `sweep`, `sweep_error`), the relay's time, the tunnel node key, the authenticated party's fingerprint (zero before authentication), and for a put the recipient fingerprint, the mid, the declared size, the status and the recipient's usage after it; for a fetch the number of items, their bytes and how long the oldest had been stored; for an ack the hashes asked and entries deleted; for a close the reason and the error code sent. That is the metadata of ADR 0013 decision 2 ("what the relay unavoidably learns") and nothing more. An event never holds an envelope byte or text that a peer chose, and the reason is one of a fixed set of classes, never the text of an error (a path or a library message does not reach the log). The sink is called on the goroutine that has the event and must not block.
- **SPO-Xmailbox-IF-007** What a `relayport.StreamListener` provides, and what `Serve` does with its errors. A tunnel adapter must: (1) never let `Accept` wait on a peer, so that a peer that is slow or silent in the tunnel's own handshake costs the accept loop nothing (one loop serves every listed party); (2) make the first small write on a fresh stream (an Error frame of a few bytes) end at the write deadline set on it, and `Close` never block; (3) return an error wrapping `relayport.ErrListenerClosed` after `Close`, one wrapping `relayport.ErrAcceptRetry` for a failure it knows to be transient (a descriptor limit, one peer's failed handshake), and the context's error when the context ends. `Serve` returns nil for the context's end and for a closed listener; waits out a retryable error for a delay that starts at 5 ms, doubles with each failure in a row and never passes 1 s, then accepts again (the delay ends with the context); and returns any other error. Every return cancels the live sessions first (each is told shutting down) and then waits for them, so a failed listener does not leave connections running until their lifetimes end. An adapter marks only what it knows to be transient: a wrongly marked permanent error makes `Serve` retry for ever.

### Outputs

- **SPO-Xmailbox-OUT-025** ~~withdrawn~~ in ADR 0014 work package 6; superseded by SPO-Xmailbox-OUT-082, PRE-053, SEC-064 and SEC-065 (version 2 only, no access list, the party is no longer found by the tunnel node key). The version 1 text: A session is: Challenge, Auth, AuthOK, then requests until it ends. The relay draws a fresh 32-byte nonce for the connection (`io.ReadFull` of the random source; a source that fails ends the session before any Challenge is sent) and sends `Challenge{min 1, max 1, nonce, the relay's own node key, the relay's time}` (the time clamped to 0 to `MaxTime`). It reads one Auth with `DecodeFromClient` only. An Auth version other than 1 is the error code 0 (version). It finds the party by the **tunnel node key** (`AccessList.LookupNode`), and requires that the fingerprint in Auth is the entry's and that the entry's identity has that fingerprint (SEC-020); it then calls `mailbox.VerifyAuth` with the identity of the entry, the tunnel peer, the signature and `AuthParams{version, the relay's own key, the tunnel peer as client node key, this connection's nonce, the Challenge's relay time, the entry's fingerprint}`. Any failure is the error code 1 (auth) and a close. `AuthOK` carries the version, the envelope limit of `Limits`, the mailbox entry and byte bounds of the quota and the retention.
- **SPO-Xmailbox-OUT-026** **Version 2:** the header is `PutV2`, the sender the store is given is the authenticated DEVICE, and "access no longer allows" means the sender's own binding is not served any more or the recipient device is no longer bound to the wallet key the put names (OUT-084, SEC-021). A Put header is followed by one raw frame that is read with `mailbox.ReadRawFrame` and streamed into `MailboxWriter.Put` through a pipe: the bytes reach the store as they arrive, the envelope is never held whole or twice, and when the frame fails (short, wrong size prefix, wrong hash, a deadline) the pipe is closed with that error, so a store that reads to the end of its input does not take a bad body for a whole one, and a put that the store kept anyway is removed again (`MailboxRetractor.Retract`, the sender's own copy and no other sender's, SEC-023, OUT-031). The sender the store is given is the authenticated party and never anything the peer sent. A store that decides without reading the body (duplicate, full, too large, busy, an error) leaves the frame in the stream; the session reads it to its end and drops it, so the stream stays in step. The store outcome is mapped to the status of the ADR's table: stored 0, duplicate 1, full 3, too_large 4, busy 6; a store error is unavailable 7, except `ErrMailboxRevoked`, which is refused 2; a body whose hash differs from the mid is bad_hash 5; a put that access no longer allows once the store has committed it (the recipient left, the sender left or has another node key, `send_to` withdrawn) is retracted and refused (SEC-021). A stored put wakes the long-polls of the recipient on this server (INV-014). The reply carries the request id.
- **SPO-Xmailbox-OUT-027** A Fetch reads the authenticated party's own mailbox and no other: the recipient is the session's party and there is no field of the request that names one (SEC-022). It returns at most the request's `max items` and at most the limit's, in arrival order, after the entry `after` when it is there. Entries larger than the envelope limit announced in AuthOK are left out, not deleted, and do not hide the entries after them. The first entry is opened before the Items header is sent, and the others when their frame is due (OUT-032); an entry at the front of the page that has been removed since it was listed is left out of the header. With a wait above zero (clamped to the limit's and to the end of the connection's lifetime) and nothing to return, the session waits for a put to that mailbox or the end of the wait and answers with what it finds, or an empty Items (INV-014). A store failure is the error code 5, the only code the protocol has for "not now", and no text.
- **SPO-Xmailbox-OUT-028** An Ack removes the named entries from the authenticated party's own mailbox only (`MailboxAcker.Remove` with the session's fingerprint), and `AckResult.Deleted` is the number removed: at most the number of hashes sent, 0 for a hash that is absent or belongs to another mailbox. An Ack of more hashes than the limit's bound is the error code 3 (limit). A store failure is the error code 5.
- **SPO-Xmailbox-OUT-029** **Version 2:** the codes are those of OUT-055; a session ended by a revoke or by the end of a binding is told 7 `binding`, a login with a key off the allow-list 6 `not_allowed`; the session sends 4 `revoked` no more. Everything the relay tells a peer about a failure is an `Error` frame with a code from OUT-005 and no text, followed by the close: 0 version, 1 auth, 2 protocol (malformed, out of order or from the wrong side, a request id used twice), 3 limit (a connection bound, a deadline), 4 revoked (the party or its node key left the access list), 5 shutting down (the server is stopping, or the store cannot serve). A peer that is gone, or whose stream failed, gets no frame. A shutdown or a revocation is reported as such whatever error the deadline it set caused.
- **SPO-Xmailbox-OUT-030** The `Sweeper` deletes the entries older than the retention through `MailboxExpirer.Sweep`, with the retention clamped by `ClampRetention` (zero is refused when it is made, anything above 30 days is cut to 30 days) before it reaches the expirer. `Sweep` runs one pass and logs one event with the number removed; a failed pass is returned and logged as a class (`sweep_error`) without the error's text. `Run` sweeps on an interval until its context ends, logs and goes on after a failed pass, and stops its ticker. The sweeper is separate from the `Server`: the caller runs it. The entries are deleted by the store with the domain's rule (OUT-010).
- **SPO-Xmailbox-OUT-031** `MailboxRetractor.Retract(ctx, recipient, sender, mid)` deletes the entry that `sender` put to `recipient` with id `mid` and no other, reports whether it was there, and leaves the counters of every other entry as they were (the recipient's, the pair's and the sender's go down by that entry alone; the pair and sender of another copy of the id are untouched). Another sender's copy of the same bytes stays listed and readable, and the first stored copy listed afterwards is that one. It does not consult `ctx`, so a compensation is not refused for a context a revocation has cancelled; a closed store returns `ErrMailboxClosed`. The session compensates with it and only with it, on a context that is not cancelled with the session's, bounded by 5 seconds: for a stored put that access no longer allows (SEC-021) and for a stored put whose bytes did not match (SEC-023). `MailboxAcker.Remove`, which deletes every sender's copy, is for acks (OUT-028). The contract suite has the case (`RetractIsSenderScoped`).
- **SPO-Xmailbox-OUT-032** A Fetch reply opens its entries lazily and counts what it sends. The first entry of the page is opened before the header, so that a head that is gone is left out of it; the others are opened when their frame is due, one at a time, each closed after its frame, so a reader that does not read pins one descriptor and not one for each of up to 16 entries. An entry that is gone or shorter than listed when its frame is due cannot be left out (the header listed it, and an Error frame would be read as the raw frame): the session ends without another frame, with the reason `vanished`, and the client fetches again. When every entry of a page has gone, the page is read again from the same place, which no longer lists them: `more` is never dropped because entries vanished, and a reply is empty only when nothing follows; after 16 pages in a row gone, the answer is the error code 5. The relay counts every byte it sends on a connection (headers and raw frames) against `Limits.MaxBytesSent` (default and ceiling `MaxBytesSentPerConn`, 256 MiB, four times the received bound; a server may only tighten it). Before the header, the reply is cut to the entries whose header and frames fit exactly under what is left, with `more` set when entries were cut; a header that cannot be sent at all, or a first entry that does not fit, closes with the limit code and the reason `bytes_sent`. A reply that fits exactly is sent whole, and one byte less cuts it.
- **SPO-Xmailbox-OUT-033** **Version 2:** the tables are the node keys of new connections and of replies to refused connections, and the wallet keys of puts. The rate tables hold only keys active in the last minute. The window of a node key (new connections) and of a sender (puts) is dropped when it is empty on a read, and all windows whose minute has passed are swept, at most every 5 seconds of the relay's clock (at once when the clock has stepped back), on each accept, release, put and reject. A key that has left the access list, or one that was only seen once, does not stay in a table: the tables are bounded by the keys active in the minute, not by every key ever seen.
- **SPO-Xmailbox-OUT-034** The accept path never writes to a peer. A refused connection (PRE-021) is answered by a goroutine of its own, under a write deadline of at most 2 seconds that the shutdown cuts short, and only when all three bounds allow it: the key has had fewer than `MaxNewConnsPerMinute` replies in the last minute; the table of keys that have had a reply (fixed at 64 keys, swept as in OUT-033) has room for a new key; fewer than 8 reply writers are running. Otherwise the connection is closed without a reply and nothing is kept for it. A flood of refused connections whose peers do not read therefore costs at most 8 goroutines and 64 table rows, and does not delay the accept of a listed party. The bounds are the relay's, not configuration.

### Preconditions and failures

- **SPO-Xmailbox-PRE-020** **Version 2:** before login nothing but an Auth of version 2 and up to eight Revoke frames are accepted (PRE-054); a version 1 Auth is the `version` code; the handshake deadline is the unauthenticated budget. Before authentication nothing but an Auth is accepted: a Put, Fetch or Ack, a frame that only the relay sends and a malformed frame are the error code 2 and a close, and nothing is stored or listed for them. Only a header frame is read (bounded by `MaxHeaderFrame`, with its length checked before its body is read), so a frame that claims 4 GiB costs its 4-byte prefix and a bounded allocation. One failed Auth closes the connection: there is no second attempt. The handshake has its own deadline (`HandshakeTimeout`) from the accept to the AuthOK.
- **SPO-Xmailbox-PRE-021** **Version 2:** the order is the total bound, the unauthenticated slots (PRE-054), the live connections of the tunnel node key, the new connections of the node key in the last minute; there is no access list, so no connection is refused as unlisted and no `revoked` reply is sent at accept. A connection is admitted in this order: the total bound; the access list (a tunnel node key that is not listed, such as a revoked key that the tunnel still admits, is refused before any counter is kept for it, no nonce is drawn and no Challenge is made); the live connections of the key; the new connections of the key in the last minute. A refused connection gets one Error frame (revoked for an unlisted key, limit for a bound) under a write deadline of at most 2 seconds, written off the accept path and bounded (OUT-034), and is closed; when the key is over its bound for replies, the table of keys is full or every writer is busy it is closed without a reply. **Decision (ADR 0013 left it open):** an unlisted key gets the error code 4 (revoked) and no more, which tells a tunnel peer nothing it does not know, and costs the relay no random draw, no signature work and no state.
- **SPO-Xmailbox-PRE-022** **Version 2:** the order is that of OUT-084 (too large; the sender's binding; `unbound`; rate; admission; store). A Put is decided in this order, and the body is consumed whatever the decision (except the first): an envelope above the announced limit is too_large and the connection is closed, without reading the body; a sender that has left the access list, or whose entry has another node key, is refused and the connection is closed with the revoked code; a recipient that is not listed, or that the sender's `send_to` does not contain, is refused, with the same bytes for both causes so the answer does not tell who is on the list; a sender over the rate or concurrency bound is busy; then the store. A refused or busy put reads the body to its end and drops it, and the hash of that body is not an answer (SEC-023). The client's next request goes on.
- **SPO-Xmailbox-PRE-023** Requests are numbered by the client. A request id used twice on a connection is the error code 2: ids are unique on the connection (ADR 0013 decision 6), at most `MaxRequestsPerConn` of them, so the relay's memory for them is bounded. A reply carries the id of the request it answers. The relay handles one request at a time, so the client's bound on requests in flight is a bound on what it may have written ahead, which the relay reads in order.

### Security

- **SPO-Xmailbox-SEC-020** ~~withdrawn~~ in ADR 0014 work package 6; superseded by SPO-Xmailbox-SEC-064 and SEC-065 (there is no access list entry to find: the identity is built from the presented keys, and the relay's own key, nonce and time and the tunnel's node key are never read from the frame). The version 1 text: The party is found by the tunnel node key, never by the fingerprint the client claims, and the claim must equal the found entry's fingerprint: a listed peer that claims another party's fingerprint, with that party's own valid signature, is refused. The relay's own key, the tunnel peer and the identity of the entry are the relay's, never read from the Auth frame (SEC-012). The nonce is fresh for each connection, so an Auth frame captured on one connection fails on another; a signature over another relay's key or another client node key fails. The entry is looked up again when the Auth arrives, so a party removed since the accept is refused as revoked.
- **SPO-Xmailbox-SEC-021** **Version 2:** the "access" decision is the registry's: the sender's own binding is served and the recipient device is bound to the key the put names (OUT-084); the check next to the `Put`, the check after a stored put and the compensation by the sender's own retraction are as below, with the stranger accounting released by the retraction (OUT-086). The session now holds `MailboxRevoker` for the revoke path only (IF-015). Access is checked again immediately next to the `Put`: the sender's entry, the recipient's presence and the sender's `send_to` are looked up in the list in force at that moment, after the rate and concurrency bounds and just before the store is called. A reload between the first check and this one is seen. A reload that falls after this check, up to the store's commit, is caught by the whole decision made again once the put is stored: the sender still listed with the node key of this connection, the recipient listed and `MaySendTo` (the same function as the check before the put). When any clause fails the entry is taken back with `MailboxRetractor.Retract` (the sender's own copy; another sender's copy of the same bytes stays, OUT-031), on a context that no revocation cancels, and the sender is told refused; when it is the sender that is gone or has another node key the revoked code follows and the connection closes (with `CloseParty` the reply cannot be written and only the revoked code arrives). A retraction that fails still refuses the sender, and the event reason is `store`, not `compensated`. This does not rest on the order of the reload for the sender's clauses; for the recipient it relies on the order the reload follows (the list is replaced before the mailbox is removed, `Server.CloseParty` between them). The session holds no `MailboxRevoker`, so it cannot use the tombstone alternative of "What a session must still do"; the re-check with the compensation is the choice, and it is tested with a reload between the check and the put, with one inside the store's `Put` and with each clause changed on the last byte of the body (while the store commits), and with another sender's copy of the same id kept. The earlier text of this requirement said only that the recipient was looked up again after the put; a sender revoked in the commit phase kept its entry in the recipient's mailbox.
- **SPO-Xmailbox-SEC-022** A party reads and acknowledges its own mailbox only, by construction: the Fetch and Ack messages carry no recipient, and the session passes its own authenticated fingerprint to the store. A test shows a party's fetch returns nothing of another mailbox, and that an ack of a hash held only in another mailbox deletes nothing there; when both mailboxes hold the same bytes, only the caller's copy goes.
- **SPO-Xmailbox-SEC-023** A body that is short, whose size prefix differs from the header, or whose hash differs from the mid stores nothing and leaves nothing: the pipe to the store ends with the error, a store that kept the bytes is told to retract this sender's copy (`MailboxRetractor`, OUT-031), and the connection is closed for a framing failure and kept for a hash failure (all of the frame was read). On a path that is refused or busy the hash of the body is not looked at as an answer: a refused put whose bytes are also wrong is refused, so the hash check cannot be used to find out which recipients exist.
- **SPO-Xmailbox-SEC-024** **Version 2:** every request looks the device's binding up again in the registry (OUT-085) and an end is the `binding` code; `Server.CloseParty` is `CloseDevice` (and `CloseKey`), and it is also what a verified revoke calls (SEC-067); the session holds `MailboxRevoker` for the revoke path alone. Every request of an authenticated session looks the party up again: a party that has left the access list, or whose entry has another node key, is answered with the revoked code (a put: refused, then the revoked code) and the connection is closed, and nothing is stored, listed or acknowledged for it. `Server.CloseParty` ends the live sessions of a party at once, also in a long-poll or a blocked read, with the revoked code; the reload calls it after it has replaced the list and before it removes the mailbox. The session holds `MailboxAcker` (acks only) and `MailboxRetractor`, never `MailboxRevoker`: the reload takes the last. That a session ends on `CloseParty` is a promptness, not the guarantee: SEC-025 says what holds when the reload does not call it. `CloseParty` sets both deadlines of the stream in the past (not only the read deadline), so a session blocked in a write to a peer that does not read ends at once and not after the write timeout of each frame it has left.
- **SPO-Xmailbox-SEC-025** **Version 2:** "the party" is the device's binding in the registry; the re-check is at the start of every Fetch, Put and Ack, after every wake, before items are sent and before an empty reply (OUT-085); there is no reload of an access list. The session does not depend on the reload for revocation. The party is looked up again (its entry exists, with the node key of the connection) at the start of a fetch, after every wake of a long-poll, immediately before items are sent and before an empty reply at the end of a wait. A party that was removed, or whose entry has another node key, is answered with the revoked code and the connection closes, and the mailbox is not read again after the wake. A put checks the same after the store has committed (SEC-021). **Obligation of the reload (work package 7, not built):** it replaces the list, calls `Server.CloseParty` for every party it removes **and for every party whose node key changed**, then removes the mailboxes of the removed ones. `CloseParty` ends the connections at once; without it a connection ends at its next request or wake, or when its wait ends, and no item is sent to it in between.

### Invariants

- **SPO-Xmailbox-INV-012** **Version 2:** the handshake time is `UnauthBudget`; the unauthenticated slots (16), the revokes before login (8) and the puts a minute of a wallet key are bounds of the table too (PRE-054, OUT-084), each tested one under, at and one over. Each bound of the ADR's table that is the session's job is enforced here, at the figure of `Limits`, and each has a test one under, at and one over: requests per connection (the limit is served, the next closes with the limit code); bytes received per connection (counted over every frame read, a raw frame refused before its body is read when it would pass the bound); bytes sent per connection (OUT-032: exactly at the bound is sent whole, one under is cut short with `more`, and a reply that cannot be sent closes with the limit code); connection lifetime; idle time between frames; the handshake time; the envelope limit announced in AuthOK; items per fetch; the fetch wait; hashes per ack; live connections in total and per node key; new connections per node key per minute; puts per party per minute; concurrent puts per sender over all its connections. The rate windows are a minute of the relay's clock; an event exactly a minute old is out of the window; a time in the future (the clock stepped back) is dropped so that it cannot lock a key out for the length of the step. A refused put does not use a put slot until the access decision passes. The windows are swept so that the tables stay bounded (OUT-033), and so is the reject path (OUT-034).
- **SPO-Xmailbox-INV-013** A stalled or cut peer cannot hold a goroutine, a connection slot or a store reservation past a deadline. A read deadline is set on the stream before every read (the idle bound for a header, the body bound for a raw frame, the handshake bound before AuthOK) and a write deadline before every write (each header and each raw frame), each the earlier of its bound and the end of the connection's lifetime. A deadline is set again after a revocation or a shutdown could have set one in the past, so a blocked operation is never left to run on. A put that stalls releases its reservation when the body deadline passes; a cut at any byte of the handshake or of a put stores nothing and frees the accounting; a session that ends logs its close after its accounting is released. `Serve` returns after every session has ended, whichever way it ends (the context, a closed listener or an accept error: IF-007), and cancels them before it waits; a cancelled context ends every session promptly, in every state, with the shutting-down code. A revocation ends a session blocked in a write (SEC-024). Tests run with `fakenet.CheckLeaks`.
- **SPO-Xmailbox-INV-014** The long-poll holds no goroutine and no timer past the request: the session's own goroutine waits on a slot of an in-process notifier, a timer that is stopped when the request ends, and its context. The slot is made before the mailbox is read, so a put between the read and the wait is not missed; it is keyed by the recipient, so only a put to that mailbox on this server wakes it; the notifier is bounded by the number of connections, and a session that cannot get a slot answers at once. A wake that arrives while another is pending adds nothing. The wait ends at the end of the connection's lifetime, at a shutdown and at a revocation. A put by another server process, or a mailbox changed any other way, is seen at the next fetch or the end of the wait, not before.
- **SPO-Xmailbox-INV-015** Fuzz targets (`FuzzSessionBeforeAuth`, `FuzzSessionAfterAuth`) give a version 2 session arbitrary client bytes, before and after an honest login with a real binding (the seeds are version 2 frames: Auth, both Revokes, Put with a raw frame, Fetch, Ack), with short deadlines. A session never panics, never sends more than its own egress bound (`MaxBytesSent`, set small in the rig, and one Error frame), always ends, `Serve` always returns, no goroutine is left, and the store's counters stay within the quota. The store is emptied after each input and found empty before the next, so that no input fills the quota for the others and a leaked counter shows. The rig's timers are a few milliseconds and the inputs at most 512 bytes. The throughput that the engine reports drops to 0 for seconds while it minimises a new interesting input (it counts no execs then, for up to `-fuzzminimizetime`, a minute by default); it is not a wait of the target. The seeds are small frames of every kind.

### Choices that go beyond the ADR text (work package 3)

- **Request ids are unique on the connection** (PRE-023). The spec of work package 1 says only "an id in flight is not reused"; the ADR says "unique on the connection". The ADR is taken, and the relay keeps at most 256 ids.
- **Unlisted node key at accept:** error code 4 and no more (PRE-021); no code of the protocol says "not listed" otherwise.
- **A store failure on a fetch or an ack is the error code 5.** The protocol has a status for a put (unavailable) but no code for a fetch or ack that the store cannot serve.
- **The access re-check is paired with a compensation after the put** (SEC-021). The store's `RemoveMailbox` cancels only puts that had reserved; the re-check alone leaves a window, so the whole decision is made again after a stored put and the entry is retracted (OUT-031) when it fails. The compensation is the sender's own retraction, a capability of its own, and not the ack: `Remove` deletes every sender's copy of an id and would delete another sender's legitimate copy of the same bytes.
- **Bytes sent have a bound of their own** (OUT-032), four times the bytes received, which the ADR's table did not have. Without it a client could read the same mailbox for ever within the received bound, which counts the requests and not the replies.
- **A fetch reply is cut short, not stalled, when it does not fit**; a vanished entry after the header ends the session (OUT-032). The wire format has no way to announce fewer items after the header, no filler frame (a raw frame must hash to its id) and no code for it, so the choice is between a stream out of step and a close; the close is the only one that does not corrupt the next frame, and the client fetches again. The cost is a dropped connection in a rare race (an ack on another connection, a sweep) and it is logged as `vanished`.
- **The reject path is bounded by constants** (OUT-034): 64 keys, 8 writers, 6 replies a key a minute. They are not configuration: a bound that an operator can loosen is one more thing to get wrong, and the replies carry no information beyond what the tunnel allow-list already tells a peer.

### What the protocol tells a sender (metadata; not requirements)

A listed sender learns two things from the statuses, which the design accepts (ADR 0013 decision 2 lists what the relay learns; this is what a sender learns about a recipient). They are noted here so that nothing later relies on their absence.

- `full` tells a sender that the recipient's mailbox, or the pair's or its own quota, is at a bound. A sender allowed to put to a recipient can therefore tell that the recipient's mailbox is near its cap. It cannot tell whose entries fill it.
- `duplicate` against `stored` on a re-put of the same bytes tells a sender whether the recipient has acknowledged that sender's own earlier message (the entry is gone after the ack, so the re-put is stored). The answer depends on the sender's own entry only (OUT-021): it says nothing of other senders' messages.
- **The server refuses an empty access list in `New`** (IF-005), beside the configuration loader's refusal.
- **Entries above the announced envelope limit are skipped by fetch,** not deleted (OUT-027), so lowering the limit does not wedge a mailbox.
- **Usage in the log only.** `MailboxUsageReader` is held to put the recipient's usage after a put in the log (IF-006). It is not used to decide a put: the store decides from the usage under its lock (OUT-013), and a decision made here would answer `full` for a duplicate that the store answers `duplicate`.
- **Deadlines are real time, the rate windows use the `Clock`.**

## The mailbox client (work package 6)

These requirements specify `internal/adapters/mailbox`: the client that lets a party's device exchange sealed envelopes through the relay. It implements `ports.EnvelopeSender`, `ports.EnvelopeReceiver` and `ports.EnvelopeAcker` as the tailcat adapter and the file bag do, and treats an envelope as opaque bytes. The relay is not trusted: every reply is checked before anything is read for it or delivered from it. Time: stream deadlines and the pacing of fetches are real time (the process clock); the injected `Clock` is read for the skew warning, for the client's own limit on new connections and for the window of stale-connection retries (OUT-044), and for nothing else. The real implementation of the auth signer on the local identity, the `--transport mailbox` wiring and the use in `party rotate` are work package 8.

### Interfaces

- **SPO-Xmailbox-IF-008** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-IF-017 (the signer has the version 2 form, without a version and with the binding and senders hashes). The version 1 text: The auth signer is `relayport.AuthSigner`, one typed method: `SignMailboxAuth(relayKey, clientNodeKey party.NodeKey, nonce [32]byte, relayTime int64, version uint) ([64]byte, error)`. It is in `ports/relayport`, which imports only the standard library, `domain/mailbox` and `domain/party`, so the relay's import closure is unchanged (SEC-009). There is no `Sign(bytes)` form: an implementation builds the signed array itself with `mailbox.AuthBytes` and its own fingerprint, so no wiring can obtain a signature over bytes it chose. The client takes this port and holds no identity key. Tests use a signer that holds an Ed25519 key; the implementation on the real local identity is work package 8.
- **SPO-Xmailbox-IF-009** *Amended in ADR 0014 work package 7: the configuration of version 2 is IF-016; the wallet-key fields, the resolver, the binding and the version 2 signer are in it, and the file `ports/porttest` suite runs against the real version 2 relay with the real store and a registry.* `mailbox.New(Config)` makes a `Client` from a `relayport.StreamDialer`, the pinned relay node key, the client's own node key, the party fingerprint, a `relayport.AuthSigner`, a `relayport.Clock`, `Limits` and an optional `EventSink`. It refuses a missing dialer, signer or clock and a zero key or fingerprint, and does not dial. `Limits` has a ceiling for each bound of the ADR's table (envelope 1 MiB, 16 items, a wait of 20 seconds, 256 requests, 64 MiB written, 256 MiB read, a lifetime of 10 minutes); a zero field takes the table and a value above a ceiling or below zero is refused with `ErrLimits`: a client may only tighten the table (OUT-040 for what AuthOK adds). The `Client` is a `ports.EnvelopeSender`, `ports.EnvelopeReceiver` and `ports.EnvelopeAcker` (compile-time assertions); `Transport()` is `ports.NetworkTransport(client)` and a delivery is `ports.NetworkReceived`, so the kind is a network for the cold-key rule (SEC-026). The client passes the file `ports/porttest` suite (delivery, size rule, copying, cancellation) against the real relay.

### Outputs

- **SPO-Xmailbox-OUT-035** *Amended in ADR 0014 work package 7: the Put header is `NewPutV2Of` (request id, the recipient's wallet key and device from the resolver, mid and size computed from the bytes); OUT-091 has the addressing and the statuses.* `Send(ctx, to, envelope)` refuses an envelope that is empty or above 1 MiB with `ports.ErrEnvelopeSize` before any dial. Otherwise it puts the envelope: the Put header is `NewPutOf` (id, size and mid computed from the bytes), then the raw-frame prefix, then the bytes, each write under a deadline. An envelope above the envelope limit (the client's own, tightened by AuthOK, OUT-040) is not sent and is `ports.ErrRefusedByTransport`. The client does no duplicate suppression: the same bytes sent twice are put twice, and the relay answers `duplicate` while the first is unacked and stores them again after an ack (INV-017). A caller's context that ends is returned as the context's error, not as no route. A relay's `too_large` answer ends the connection's use (OUT-046). A nil return means the relay stored the envelope, not that the party has it (INV-020).
- **SPO-Xmailbox-OUT-036** `Receive(ctx)` returns the next envelope for the party, as `ports.NetworkReceived`, blocking until one is available or `ctx` ends (then the context's error). It sends a Fetch for at most `MaxItems` items with a long-poll wait that is a whole number of seconds, at most the limit's, and never beyond the caller's deadline less half a second (a request still waiting at the relay when the context ends would abandon its connection, and the relay lets a key open only six a minute); with under a second and a half left the fetch is a plain look (wait 0). A page is queued whole and handed up one envelope at a time, each only after its hash was verified (OUT-039, SEC-028). When a page says `more`, the next fetch resumes after its last id; otherwise from the start. An empty reply that came early is followed by a pause of at least `MinPoll`, so a relay with the long-poll off cannot make a spin. A page that carries only mids delivered within the last two minutes is still delivered, never held back (INV-017), and is paced like an empty one (OUT-043). A transient failure (relay unreachable, a deadline, a cut stream, an Error frame `limit` or `shutting down`) is waited out with the backoff (OUT-041) until `ctx` ends; a protocol violation, the wrong relay key, a signer failure and any other Error code are returned (PRE-024, PRE-025). An envelope delivered and not acked is delivered again by a later fetch, in the same session: delivery is at least once, as `ports.EnvelopeReceiver` says.
- **SPO-Xmailbox-OUT-037** `Ack()` acknowledges the envelope the last `Receive` returned and the envelopes whose earlier `Ack` failed: one Ack with their mids and no other (at most 64, the newest; a list of delivered-but-unacked mids is kept for this, bounded, and an envelope is put on it only when its own `Ack` failed, never because it was received and not yet handled). It does nothing, without a dial, when nothing is waiting. The `AckResult` must carry the Ack's request id and a `Deleted` count of at most the number of hashes sent; more is a protocol violation and the connection is closed. On any failure every one of them stays waiting, so a later `Ack` names them again together with the next one. This discharges the client half of the obligation in "What a session must still do" (the ack count).
- **SPO-Xmailbox-OUT-038** *Amended in ADR 0014 work package 7: status 8 `unbound` is `ports.ErrNoRoute` with the reason `unbound` (OUT-091); the login codes `binding` and `not_allowed` are `ports.ErrNoRoute` with their own sentinels (OUT-092); the reason classes are those of OUT-042 and the new ones.* The put status maps to the error as the ADR's table says: `stored` and `duplicate` give nil; `full`, `busy` and `unavailable` give `ports.ErrNoRoute` with a fixed reason text ("the mailbox is full", "the relay is busy", "the relay's storage failed"); `refused`, `too_large` and `bad_hash` give the new `ports.ErrRefusedByTransport`. Neither sentinel satisfies `errors.Is` for the other. An unreachable relay, a timeout, a failed handshake, a relay that broke the protocol and an Error frame all give `ports.ErrNoRoute`, with a fixed reason and wrapping the failure's own sentinel (`ErrUnreachable`, `ErrProtocol`, `ErrRelayKey`, `ErrSigner`, `ErrRelayError`), so the item stays queued and nothing is lost. A refused item does not end the session: the next put goes on the same connection, except after `too_large` (OUT-046). `ports.ErrRefusedByTransport` is documented in `ports/party.go`; `Outbox.Flush` records it as an event, marks the item and goes on with the others without returning it (SPO-Xparty-INV-040).
- **SPO-Xmailbox-OUT-039** The reply to a Fetch is checked, in this order, before any body is read, and any failure closes the connection and returns `ErrProtocol` with nothing delivered from the page: the frame is a header from the relay's side (`DecodeFromRelay`: a client-only type is refused); it is an Items with the request's id; it lists at most the request's `max items`; each size is 1 to the envelope limit (the client's own, tightened by AuthOK); no mid repeats (the decoder refuses a repeat first; the client's own check is defence in depth). The bytes the page would add are counted from the announced sizes against the client's read bound before any body is read, and a page that would pass it is cut, not refused (OUT-045). Then each body is read with `ReadRawFrame` against its announced mid and size into memory of exactly that size (at most 1 MiB), under its own deadline; a prefix that differs from the header, a short body, a stall and a hash mismatch are failures (a hash mismatch also satisfies `wire.ErrHash`, class `hash`). A page with any failure is dropped whole, the relay still holds the entries, and the next connection fetches them again. The reply to a Put must be a PutResult with the Put's id and the reply to an Ack an AckResult with the Ack's id. This discharges the client halves of the obligations in "What a session must still do" for reading Items and for the request-id rule.
- **SPO-Xmailbox-OUT-040** ~~withdrawn~~ in ADR 0014 work package 7; superseded by SPO-Xmailbox-OUT-089 (the version 2 handshake). The version 1 text: The handshake runs in this order and closes the connection at the first failure: the key the dialer reports for the peer equals the pinned relay key; the Challenge is read with `DecodeFromRelay` and names the pinned relay key; the version range holds version 1 (`ChooseVersion`); the skew is measured; the signer is called with the pinned relay key, the client's own node key, the Challenge's nonce and relay time and the chosen version; the Auth is sent; the AuthOK must carry the chosen version. Nothing is signed before the second check. The relay's time is used only for the skew warning: more than five minutes (`ClockSkewWarningSeconds`) in either direction emits `EventSkew` with the difference, exactly five minutes does not, an absurd value (up to `MaxTime`) warns and the handshake still completes, and the value is signed as given. The limits in AuthOK are honoured and can only tighten the client's own: the envelope limit is the smaller of the client's and the relay's; the other announced values (entries, bytes, retention) are not used. The whole handshake is bounded by `HandshakeTimeout`.
- **SPO-Xmailbox-OUT-041** One connection is reused for many requests, one at a time, with request ids that are a counter and unique on the connection (the client has one request in flight, at most 8 allowed). A new connection is opened before a request that would pass the connection's request bound, bytes-written bound, lifetime (less a margin) or an idle time of half the idle timeout, and the `reconnect` event says which. A connection that was reused and fails as a connection (the relay closed it) is replaced once, at once, without counting a failure, and only twice in a minute of the injected clock (OUT-044), after which it is a failure with a backoff; a timeout is not retried. After a failure the next dial waits `BackoffMin`, doubling with each consecutive failure up to `BackoffMax`, and a success resets it: a `Send` inside the wait fails at once with no route and no dial, a `Receive` or `Ack` sleeps it out (ends with its context). Every blocking read and write has a deadline set first, the earlier of its bound and the end of the connection's lifetime: the handshake, a reply (a long-poll adds its wait), a body, a write; a deadline is set again after a cancellation or `Close` could have set one in the past, so a blocked operation is never left to run on. `Send` and `Ack` are bounded as a whole by `OpTimeout`.
- **SPO-Xmailbox-OUT-042** *Amended in ADR 0014 work package 7: the event kinds `renew`, `senders` and `revoke` and the reasons `binding`, `binding_expired`, `not_allowed`, `unbound`, `no_wallet_key` and `senders` are added (OUT-089 to OUT-095); an event still carries no text of a peer.* Events go to an `EventSink` (nil drops them): `reconnect` (with why the earlier connection ended), `skew` (the difference in seconds), `refused` and `no_route` (the status, the recipient and the mid, which are the client's own), and `failed` (the class, the relay's Error code when it sent one, and the backoff). Every reason is one of a fixed set of classes (`dial`, `relay_key`, `version`, `protocol`, `limit`, `hash`, `timeout`, `peer`, `relay_error`, `signer`, `backoff`, `dial_limit`, `lifetime`, `requests`, `bytes`, `idle`, `full`, `busy`, `storage`, `refused`, `too_large`, `bad_hash`, `clock_skew`); an event never carries text from the relay, from an error or from a path, and never an envelope byte.
- **SPO-Xmailbox-OUT-043** **Repeated pages are paced, never suppressed.** The client keeps a bounded set (64) of the mids it delivered in the last two minutes, and uses it for one thing: when a fetch returns a page that is not empty and carries only such mids, the page is queued and delivered as usual (the recovery of SPO-Xparty-INV-017 needs the same mid delivered again), and the next fetch waits first: `MinPoll`, doubling with each repeated page in a row, up to 64 times `MinPoll` and at most 30 seconds. A page with a mid not in the set, or an empty page, ends the streak. The wait is interrupted by the caller's context and by `Close`, so a pump with a short idle time goes idle while a relay repeats one envelope. Without this a relay that answers every Fetch at once with one envelope and every Ack with `deleted 1` made the client deliver it a hundred thousand times a second and redial every 256 requests.
- **SPO-Xmailbox-OUT-044** **The client limits its own connections.** At most `DialsPerMinute` new connections (a dial that returned a stream) in any minute of the injected clock: default five, ceiling six, the relay's limit for a key (`MaxNewConnsPerKeyPerMinute`). Each connection signs one challenge, so this also bounds the handshake signatures to the same number a minute. A dial beyond it waits for the oldest to leave the window when the caller may wait (`Receive`, `Ack`; ended by the context and `Close`) and is `ports.ErrNoRoute` with the reason `dial_limit` ("too many connections to the relay in the last minute"), wrapping `ErrUnreachable`, for `Send`, with no dial. A clock that steps back counts as no time passing. Dials that fail before they have a stream are not connections; the backoff paces them. A connection that was reused and fails as a connection is replaced at once, without counting a failure, at most twice in a minute of the same clock; the third is a failure with a backoff.
- **SPO-Xmailbox-OUT-045** **A read bound tighter than the relay's is not a violation.** A connection is replaced, by the dial limit's rules, before its read bound could pass: when the bytes read plus 1 KiB for the next reply's header would exceed `MaxBytesRead`. A page whose announced sizes would pass the bound is cut at the last whole envelope that fits: those envelopes are read, verified and delivered, `more` is taken as set, the connection is dropped after the page (it holds bodies that were not read), and the next fetch resumes after the last one. When not even the first fits and the connection served earlier requests, the connection is replaced and the fetch asked again, once; on a new connection it is a limit failure (the bound is below one envelope). Bytes are never read past the bound on one connection, and a hostile relay that sends endless valid pages costs one dial a page at most, which the limit of OUT-044 paces.
- **SPO-Xmailbox-OUT-046** **A connection is not reused after `too_large`.** After the relay answers a put `too_large` (it closes the connection) the client drops the connection once the put's result is delivered, whatever the connection does next: the next `Send` dials a new one and writes nothing on the old one, and a relay that stalls instead of closing costs no failure. An envelope above the limit that the client itself refuses writes nothing and does not drop the connection.
- **SPO-Xmailbox-OUT-047** **`Ack` honours the caller's context.** The port's `Ack()` has none, so the client has `AckContext(ctx)` (`ports.EnvelopeContextAcker`), which is `Ack` bounded by the caller's context and `OpTimeout`; `Ack()` is `AckContext(context.Background())`. A relay that does not answer costs the caller's deadline, which is returned as the context's error, and the mids stay waiting (OUT-037). `Pump` uses `AckContext` with the run's context when the receiver has it.

### Preconditions and failures

- **SPO-Xmailbox-PRE-024** *Amended in ADR 0014 work package 7: read OUT-089 for OUT-040 and PRE-058 for the version 2 failures; a Challenge that offers only version 1 is `ErrProtocol` wrapping the domain's `ErrVersion`.* A handshake that breaks a rule of OUT-040 fails the connection and signs nothing further: a dialer that reports a key other than the pinned one, or a Challenge that names another, is `ErrRelayKey` (the signer is never called, the relay sees the client close and never an Auth); a version range the client cannot speak, a first frame that is not a Challenge, an AuthOK that is not an AuthOK or has another version, a header the relay's direction does not allow, a malformed or oversized header and an unexpected Error frame are `ErrProtocol` or `ErrRelayError`; a signer that fails is `ErrSigner` and no Auth is sent. `Send` returns `ports.ErrNoRoute` wrapping the sentinel; `Receive` returns the sentinel, not a retry.
- **SPO-Xmailbox-PRE-025** *Amended in ADR 0014 work package 7: a status above 8 (not 7) is the violation, and the same holds for the RevokeResult of a Revoke (a wrong id, another type, a status other than 0 and 2).* A reply that is not the reply to the request is a protocol violation, closes the connection and is `ErrProtocol`: for a Put, a wrong request id, any type but PutResult, a status above 7 or a non-canonical frame; for an Ack, a wrong id, a wrong type, or a `Deleted` count above the number of hashes sent; for a Fetch, see OUT-039. An Error frame as a reply ends the connection and is `ErrRelayError` (also `ErrUnreachable` for `limit` and `shutting down`).

### Security

- **SPO-Xmailbox-SEC-026** Cold-key and isolation obligations of the ADR, stated and tested: the client never writes a fetched envelope to a file inbox or a bag, and there is no path that puts an arbitrary file into the mailbox: its only inputs are the bytes the application hands to `Send`, and its non-test sources import no file or process package (`os`, `os/exec`, `io/fs`, `path/filepath`, `net`, `syscall`, `unsafe`), no file transport (`adapters/filebag`, `adapters/transferfile`), no envelope adapter, no age, no secret buffer, no store, no tailcat and no `app/multisig` (checked transitively and by source: SEC-031). It calls only `ports.NetworkTransport` and `ports.NetworkReceived`, so its `Transport` and its deliveries are of kind network, and `ports/transport_callers_test.go` lists `internal/adapters/mailbox/` among the places that may call them (and still fails for a call from any other package, a lookalike prefix included). It opens no envelope: it carries opaque bytes and the mid. The structural enforcement of the cold-key rule stays where it is: `Outbox.Flush` skips cold-key items unless the transport is a file, and the signer refuses on `Via()`; this client cannot change either.
- **SPO-Xmailbox-SEC-027** A hostile relay cannot make the client allocate beyond a bound, block for ever or loop. Every length, count and size read from the relay is checked against a bound before anything is allocated or read for it: a header frame by `ReadHeaderFrame` (4 KiB), a claimed item size against the envelope limit before the body is read (a claim of 1 MiB above a limit allocates less than 900 KiB in total), the page's bytes against the read bound before the first body, and the bytes read on a connection against `MaxBytesRead`, headers included. Every blocking read and write has a deadline (OUT-041): a relay that stalls at any state (before the Challenge, in a header, before AuthOK, before a PutResult, before an AckResult, before Items, in the middle of a body) costs one timeout and the client closes; a relay that never answers a long-poll costs one reply timeout and the client reconnects. Nothing loops without the caller's context or a bound: transient retries sleep, empty replies are spaced by `MinPoll`, repeated pages are paced with a growing pause (OUT-043), a stale-connection retry happens once a request and twice a minute, and new connections, and with them handshake signatures, are limited to five a minute (OUT-044, SEC-030).
- **SPO-Xmailbox-SEC-028** The client never hands up an envelope whose hash was not verified. A body is delivered only after `ReadRawFrame` returned nil for the mid and size the header announced; a hash mismatch, a short body or a wrong prefix closes the connection and delivers nothing from the page, including the items of the page that were good. The relay can announce any mid; what the client checks is that the bytes are those of the announced mid, and the application checks the envelope as ADR 0005 says (SPO-Xparty-SEC-002).
- **SPO-Xmailbox-SEC-029** *Amended in ADR 0014 work package 7: the signature verifies over the version 2 array (OUT-053), with the full hash of the binding presented and the hash of the sender list presented (SEC-071); there is no chosen version.* The signer is given the pinned relay key and the client's own node key, never a value read from the Challenge; only the nonce and the relay's time come from it. The signature it returns verifies, at the relay, over exactly the pinned key, the client's node key, that Challenge's nonce and relay time, the chosen version and the client's fingerprint. A Challenge that names another relay key is closed on before the signer is called.
- **SPO-Xmailbox-SEC-030** **A hostile relay cannot make the client spin, dial or sign.** Whatever the relay answers and however fast (the same envelope for every Fetch and `deleted 1` for every Ack, a connection closed after the handshake, a connection closed after each reply, pages that would pass the read bound), the client delivers a repeated envelope a bounded number of times a second (OUT-043), opens at most `DialsPerMinute` connections and signs at most that many challenges in a minute (OUT-044), and a pump over it can go idle. Tested with a scripted relay that answers at once: deliveries, fetches, dials and signatures are counted over a run.
- **SPO-Xmailbox-SEC-031** *Amended in ADR 0014 work package 7: the explicit allow-list of the client's own sources gains `domain/relaybind` (the pure statement format, which the client uses to check the binding and the revokes it sends; it reaches no file, process, age or store package), and `sync/atomic` and `time` as before.* **The isolation of SEC-026 is checked transitively and by source.** The client's import closure, listed by `go list -deps`, reaches no file bag, no transfer file, no envelope adapter, no age, no store adapter (sqlite, the relay's mailbox store, the object stores), no tailcat and no multisig; a direct-import parse would miss a package reached through a port. `os`, `platform/secret` and memguard arrive through `ports` and cannot be banned from the closure, so in addition the client's own non-test sources import nothing outside an explicit allow-list (`bytes`, `context`, `errors`, `fmt`, `io`, `slices`, `sync`, `sync/atomic`, `time`, `domain/mailbox`, `domain/party`, `ports`, `ports/relayport`) and use no file-writing function (a scan of the syntax tree). Each check is shown to bite on the closure of a package that must be refused and on crafted sources.

### Invariants

- **SPO-Xmailbox-INV-016** Every blocking operation honours its context and `Close`: a context that ends interrupts a read, a write, a dial and a sleep at once and is returned as the context's error; `Close` ends a blocked `Receive` with `ports.ErrClosed` and later calls return it (`Ack` of nothing returns nil). After an interrupt the connection is dropped, never reused. The client starts no goroutine of its own: a test run with `fakenet.CheckLeaks` leaves none behind.
- **SPO-Xmailbox-INV-017** There is no duplicate suppression in the client: no recent-hash set and no filter before the application. A repeated put is the application's business (SPO-Xparty-INV-017): the outbox re-puts the same bytes of an unanswered request on each pump run, the relay answers `duplicate` while the entry is unacked and stores it again after the recipient's ack, the client delivers the repeated envelope, and the signer answers it from its stored response without using the key. Tested with the real relay and store, and with the multi-party outbox, coordinator and signer over the mailbox (`test/multiparty`).
- **SPO-Xmailbox-INV-018** A fuzz target (`FuzzClientAgainstArbitraryRelayBytes`) gives the client arbitrary bytes as the relay's stream (from the first byte, after an honest Challenge, after an honest handshake), for a receive and for a send. The client never panics, always returns within its context, returns only the errors it documents, and never delivers an envelope that the relay's bytes do not announce and carry (the envelope and its hash both appear in the input). Seeds are small and inputs over 600 bytes are skipped; limits are tens of milliseconds.
- **SPO-Xmailbox-INV-019** *Amended in ADR 0014 work package 7: the full logout recipe of ADR 0014 decision 8 is INV-038.* **`Close` interrupts every wait, the dial included.** `Close` cancels the context of a dial in progress (the client keeps its cancel function under its own lock), sets a deadline in the past on the stream of a handshake, a long-poll or a put, and ends a backoff wait, a dial-limit wait and a pacing wait: each returns `ports.ErrClosed` within 100 ms of the call. A dial that returns after `Close` has its stream closed. `Close` drops the envelopes that were fetched and not yet delivered (zeroing them), the list of unacked mids and the position of the next fetch. Logout without closing the application means: close this client, close the stream dialer given to it, and destroy the identity the auth signer signs with; the client holds no key.
- **SPO-Xmailbox-INV-020** **`stored` is not delivery.** `Send` returning nil means the relay stored the envelope (`stored` or `duplicate`). It does not mean the party has it, and no transport reports delivery. A response the relay loses is recovered only while the coordinator keeps re-running its pump and the request is unexpired: the request is put again (OUT-035), and the signer answers it again from its stored response (SPO-Xparty-INV-017). This is the direct tailcat transport's "the write succeeded and the peer lost it". An envelope fetched and not acknowledged stays at the relay and is delivered again by a later fetch or session.

### Choices that go beyond the ADR text (work package 6)

- **The auth signer is in `relayport`,** not in `ports`: it sits with the other mailbox ports, and the relay's import closure does not change. Its signature returns `[64]byte` (the ADR text says `[]byte`), so a wrong length cannot be returned.
- **The Challenge has no client key.** The work package text asks the client to check "its client key" in the Challenge; the wire shape (OUT-003) has none, so the checks are the dialer's reported key and the Challenge's relay key. The client's own node key is only ever an input to the signer.
- **`Ack` acknowledges one envelope,** the last one received, as the port says; a page of 16 is acked one request each.
- **A repeated mid in a page is refused by the decoder first** (PRE-015); the client's own check is defence in depth and cannot be reached by a test through the wire.
- **A Receive on a connection to a relay that sends `limit` or `shutting down` retries; any other Error code is returned.** The ADR does not say; a revoked or unauthenticated party must be told, a busy relay must be waited out.
- **The long-poll is clamped to the caller's deadline** (OUT-036), which the ADR does not say. Without it a `Pump` with a short idle time abandons a connection at each idle expiry and passes the relay's six new connections a minute per key within a minute.
- **A Receive that hits a transient failure retries until its context ends** instead of returning at once, so a `Pump` over a relay that is briefly down ends at its idle time rather than failing the run. The reason is in the events.
- **One request at a time.** A `Send` that arrives during a long-poll waits for it (bounded by its context and `OpTimeout`); a daemon that sends and receives concurrently should use the idle time of the pump, not a second connection (a key may hold two).
- **`porttest` needs an acking receiver.** The suite's "nothing is delivered twice" holds when the receiver acks what it delivered, as `Pump` does for an `EnvelopeAcker`; a receiver that never acks is delivered the same envelope again by design (INV-017). The wrapper in the contract test is required, not a convenience, and the suite's doc says so; the file bag and tailcat pass without one. The port documents delivery as at least once.
- **A client's dial limit is below the relay's.** The relay lets a key open six connections a minute; the client's default is five, so a restart or a second process of the same key does not meet the relay's limit at once. Dials are counted when they return a stream; the limit uses the injected clock and a sliding window, not a token bucket, which would allow a burst of six and a refill of six more inside one minute.
- **The reason of a blocked dial is `dial_limit`,** a new class beside `backoff`; the ADR text says only that excess dials wait or fail.

## The tailcat stream adapter (work package 5)

The package is `internal/adapters/tailcat/stream`. It implements `relayport.Stream`, `relayport.StreamListener` and `relayport.StreamDialer` over a tailcat tunnel (WireGuard with a pre-shared key in the address, relayed through DERP). It is its own package: `adapters/tailcat` frames whole envelopes and links the secret buffers, and the relay must not link `platform/secret` (SEC-009). The two share no code and no state. Keys reach the package as `SecretReader` functions. The closure rule that confines the tunnel libraries to the two tunnel adapters is SEC-009 and SEC-016.

### Interfaces

- **SPO-Xmailbox-IF-010** `stream.Listener` implements `relayport.StreamListener` over one tailcat server. The node key `Accept` returns for a stream is the key tailcat's `Server.PeerEnv` names for that connection (`TAILCAT_PEER_KEY`), which the WireGuard handshake bound to the connection's address. A connection for which tailcat names no key is closed unserved, with a reset, and counted (`Stats.Unidentified`). The key is exact for every connection when several dialers connect at once.
- **SPO-Xmailbox-IF-011** `stream.Dialer` implements `relayport.StreamDialer` for one relay. `NewDialer` refuses, before any packet is sent, a zero pinned key, a missing or malformed address and an address whose server key differs from the pinned one (`ErrPinnedKeyMismatch`). `Dial` returns the pinned key itself; the tunnel's handshake to that key is the binding. There is no inbound listener on the client side.
- **SPO-Xmailbox-IF-012** A timeout of the underlying connection is reported as an error for which `errors.Is(err, os.ErrDeadlineExceeded)` holds and which is a `net.Error` with `Timeout()` true (gVisor's own timeout error is neither); a clean end of stream from the peer is `io.EOF`. A deadline in the past, set from another goroutine, unblocks a pending `Read` and a blocked `Write` with that error (contract case `PastDeadlineFromAnotherGoroutineUnblocksReadAndWrite`).
- **SPO-Xmailbox-IF-013** An error of tailcat's accept that is `net.ErrClosed`, or any error after `Close`, is `relayport.ErrListenerClosed`; any other error is wrapped with `relayport.ErrAcceptRetry`, reported once to the next `Accept`, and the pump goes on after a delay that doubles from 5 ms to 1 s. A context that has ended is its own error. `Accept` never returns a stream with a nil error once the listener is closed (the closed state is checked again after a stream was taken; the stream is reset) and never returns a stream that was revoked while it waited.

### Outputs

- **SPO-Xmailbox-OUT-048** The relay's real session logic (`app/relay.Server`) over the real mailbox store behind the tailcat listener serves a scripted client over the tailcat dialer through handshake, put, duplicate put, fetch, ack and an empty fetch; a node key outside the access list cannot connect; after the access list drops a party, `SetAllowed` rebuilds the tunnel without his key, `CloseParty` closes his live session and he can no longer form a tunnel, while a party that stays reconnects.

### Preconditions and failures

- **SPO-Xmailbox-PRE-026** Configuration is checked before any network is touched: the node key and the pre-shared key are required and 32 bytes, the pre-shared key is not all zero, no zero key is in the allow-list; a dialer needs its address, its node key and a non-zero pinned key. Keys reach the package as `SecretReader` (a `platform/secret` Buffer's `Use` fits), so the package does not import the secret buffers; the listener keeps the readers, not the bytes, to rebuild its tunnel. The package has no state directory: tailcat keeps its state in memory.

### Security

- **SPO-Xmailbox-SEC-032** The allow-list is enforced twice. The tunnel admits only the listed node keys plus one key that nobody holds (so that an empty list admits no one: tailcat admits everyone when its list is empty). The listener's own accept closes, with a reset and before any byte is read, a connection whose key is not in the current list (`Stats.Refused`). A node key that is not listed never reaches the listener's accept unless the tunnel still admits a key that was removed (SEC-033, SEC-035).
- **SPO-Xmailbox-SEC-033** `Listener.SetAllowed(keys)` replaces the list. It adds to the tunnel only keys not added before. tailcat's allow-list has no removal (`Server.AddAllowedClient` only inserts into a map; `onMeow` only reads it; the server's `clients` map is only ever added to), so when a key that the tunnel admits is removed the listener rebuilds the tunnel server with the same node key, pre-shared key and region (so the same address) and the keys listed now (`Stats.Rebuilds`), at most once per `RebuildGap` (default 5 s), requests during a rebuild merged into one more. Every stream of every party ends with the old server; the other parties reconnect through the dialer's tunnel replacement (INV-026). If the old server's teardown has not finished within `TeardownTimeout`, the new server is started beside it and `OnTeardownStuck` is called. Until the new server is up, and always when `KeepTunnelOnRemoval` is set, the removed key can still form a tunnel: every live stream of it (handed out or waiting) is reset at once and each later connection is reset at its own accept. Listing the key again admits it again (adding a key needs no rebuild). A zero key is refused and nothing changes. An empty list admits no one. A rebuild that cannot start a server three times in a row, or that starts one with another address, reports an `Accept` error that does not wrap `ErrAcceptRetry` (fail closed).
- **SPO-Xmailbox-SEC-034** No TCP socket is opened by either side; the served port is virtual (gVisor netstack in the process), and the packet filter admits only that port (`ServedTCPPorts` is empty and non-nil; another port is dropped, not reset). Each tailcat engine, on either side, does bind UDP sockets on operating-system ports (wildcard addresses, one per address family, ports chosen by the system: magicsock with `ListenPort` 0) for direct paths and STUN. Those are reachable from outside the tunnel. Streams open no further socket. The package reaches the netstack endpoint behind a `*gonet.TCPConn` by reflection (unexported field `ep`, as tailcat does) to set its linger option for a reset.
- **SPO-Xmailbox-SEC-035** Refusals leave nothing. A connection that is refused (key not listed), unidentified, or shed (backlog or stream cap) is reset at once (linger 0), so that a peer that keeps its end open leaves no endpoint behind: a flood of 300 connections from a removed key, three rounds, leaves the relay's netstack at its baseline and the heap flat. A stream that is revoked or aborted ends with a reset: the peer reads a connection error, not a clean end.

### Invariants

- **SPO-Xmailbox-INV-021** `Accept` never waits on a peer. A pump goroutine takes each connection from tailcat as soon as the tunnel has established it and queues it in a bounded backlog (default 16); a connection that finds the backlog full is reset (`Stats.Shed`). A peer that connects and says nothing does not delay the next accept.
- **SPO-Xmailbox-INV-022** `Close` of a listener, a dialer or a stream never blocks. Listener `Close` makes `Accept` return an error wrapping `relayport.ErrListenerClosed`, resets every stream that is not already closing, and starts the tunnel teardown on its own goroutine; `Done()` closes when it is finished. Dialer `Close` does the same for its streams and cancels its dials in flight. Stream `Close` is an orderly close: it unblocks a pending `Read` and `Write` at once; off the caller's goroutine the stream shuts the write side (a FIN after the bytes already written), discards what the peer still sends until its end or `LingerTimeout` (default 2 s), then closes the connection, so that a final frame written before `Close` is not lost behind a reset when unread data is pending. At most `MaxLingering` (default 64) streams linger at once per listener or dialer; beyond that a stream is reset. `Abort` (optional interface `relayport.Aborter`, helper `relayport.Abort`) resets at once, also a stream that is lingering. After `Close` or `Abort`, `Read` and `Write` fail with `net.ErrClosed` and a deadline is refused with `net.ErrClosed` (it cannot undo the deadline that unblocked a pending operation). There is no half-close.
- **SPO-Xmailbox-INV-023** Streams leave no record behind: a closed stream is removed from the listener's and the dialer's tables when it has finished closing, and 40 sequential connections leave the process's goroutines and descriptors where they were. Starting and closing listeners leaves nothing. The node key and pre-shared key copies this package makes are cleared (the temporaries of `read32`, the pre-shared key array, the dialer's private key at the end of `Close`); the copies inside tailcat, the WireGuard device and `key.NodePrivate` values handed to the library cannot be wiped from here.
- **SPO-Xmailbox-INV-024** Lifecycle. An idle stream carries data after a quiet period (4 s in process). A relay that restarts with the same node key and pre-shared key has the same address. tailcat registers a client with the relay only at its first dial, so a tunnel that worked before cannot reach a restarted relay: a `Dial` through a tunnel that worked before gives it at most 6 s; if it fails and the dialer has no live stream, the tunnel is replaced (INV-026, subject to its rate limit) and the `Dial` tries once more on the new tunnel within the same `DialTimeout`. One node key is one live endpoint: of two dialers with the same node key the newer one works and the older one's streams stop.
- **SPO-Xmailbox-INV-025** Dialer close. `Dialer.Close` cancels every `Dial` in flight (they return `ErrDialerClosed` within 200 ms) and a `Dial` after `Close` fails with `ErrDialerClosed`. The teardown waits for the dials that took a tunnel and only then closes it, so that an engine that a dial started after `Close` ran is closed too: after `Done` there is no new UDP socket, no goroutine of the engine, and the relay's DERP server sees the device as not connected (logout leaves nothing). A stream that a dial opened after `Close` is reset and not handed out. `CloseWithin(d)` reports a teardown that did not finish as `ErrTeardownStuck`.
- **SPO-Xmailbox-INV-026** Tunnel replacement. After any `Dial` that fails, except one the caller cancelled (`context.Canceled`), while the dialer has no live stream, the tunnel is replaced by a new one for the next `Dial`: tailcat believes any "meowed" acknowledgment whoever sent it (a forged one makes a client think it is registered with a relay that does not know it) and it registers only once, so a relay restart between the acknowledgment and the first successful dial wedges the client for ever. At most one replacement per failed `Dial`, and no two closer than `MinRebuildInterval` (default 5 s; injected clock). A stream that a dial opened on a tunnel that was replaced meanwhile is reset and not handed out; the `Dial` retries once on the new tunnel. A forgery that continues cannot be recovered by this: each new tunnel registers again and meets the next forged acknowledgment (it needs an upstream fix).
- **SPO-Xmailbox-INV-027** Bounded endpoints and bounded teardown. tailcat's `Close` deadlocks when the netstack holds more than about 512 endpoints. The listener holds at most `MaxStreams` streams (default 256, waiting, handed out and closing; a connection over it is reset and counted as shed) and the dialer at most `MaxStreams` (default 64; `Dial` returns `ErrTooManyStreams`). Before a tunnel is closed every stream is reset (those that are closing get `DrainTimeout`, default 2 s, to finish first), the resets get up to 200 ms to leave the engine and the stack drain is bounded by `DrainTimeout`. `Done` can still fail to close: `CloseWithin(d)` returns `ErrTeardownStuck` after `d`, and `OnTeardownStuck(ErrTeardownStuck)` is called when a teardown (a close, or the old server of a rebuild) runs longer than `TeardownTimeout` (default 10 s), with a log line. The relay process must exit when either happens; a client that is logging out must report "tunnel did not stop" and never claim success.

### Choices that go beyond the ADR text (work package 5)

- **Removal is a rebuild.** ADR 0013 says tailcat cannot remove a key; that stays true of the library. The adapter works around it by replacing the tunnel server (SEC-033), at the price of ending every party's streams once per `RebuildGap`.
- **The relay address stays the same across a rebuild** because the node key, pre-shared key and region do not change; a rebuild that would change it fails closed.
- **The stream contract gained cases and an optional interface.** `relayporttest.StreamRig.StallBytes` (zero means 64 KiB, capped at `relayporttest.MaxStallBytes`, 16 MiB) lets a real tunnel, whose buffers cannot be limited, take part in the `Bounded` case; the cases `FinalMessageSurvivesCloseWithUnreadInbound` and `PastDeadlineFromAnotherGoroutineUnblocksReadAndWrite` were added; `relayport.Aborter` is optional (`app/relay` does not call it).
- **Open mode is not built here.** The tunnel keeps its never-held key in every mode; see the tunnel-library limits in ADR 0013.

## Protocol version 2 (ADR 0014, work package 2)

This section specifies version 2 of the wire protocol in the same pure package, `internal/domain/mailbox`, as [ADR 0014](../../docs/explanation/adr/0014-wallet-key-identity-for-the-relay.md) decides it (decision 7 and the bounds in decisions 3 and 5). The binding and revoke statements are specified in [Xrelaybind](./Xrelaybind.md).

**Version 1 is deleted (ADR 0014 work package 7); there is one version.** The relay session (`internal/app/relay`, work package 6) and the client (`internal/adapters/mailbox`, work package 7) speak version 2 only, and nothing is deployed, so version 1 is gone from this package: the frames `Auth`, `AuthOK` and `Put`, their codecs, `AuthLabel`, `AuthParams`, `AuthBytes`, `VerifyAuth`, the errors `ErrAuthNoNodeKey` and `ErrAuthIdentityNode`, `NewPut`, `NewPutOf`, `ChooseVersion`, `DecodeFromClient`, `DecodeFromRelay`, the stages `StageV1` and `StageUnversioned`, the versions `V1` and `BothVersions` and the constant `Version1`. `Encode` writes version 2 (it is `EncodeV(Version2, ...)`, and `EncodeV` refuses every other number), `Status.Valid` and `Code.Valid` are the ranges of version 2, and `Message.fields` is the version 2 shape of each type. The requirements that were version 1 only are withdrawn above (IF-008, OUT-006, OUT-007, OUT-040, PRE-007, PRE-010, SEC-001), and the ones that still hold carry a note that says what changed. **Names that were left:** the version 2 types and functions keep their suffix (`AuthV2`, `AuthOKV2`, `PutV2`, `AuthV2Params`, `AuthBytesV2`, `VerifyAuthV2`, `NewPutV2`, `NewPutV2Of`, `DecodeFromClientIn`, `DecodeFromRelayIn`, `EncodeV`): renaming them would touch every user and every test of the relay and the client for no gain, and a rename later is mechanical. `Quota`, `ValidQuota`, `Quota.Validate(parties)` and `MaxAccessListParties` stay: the session and the store still use `ValidQuota` (the ADR 0013 part of the open quota), and the store and the operator configuration use the party bound (the configuration is replaced in work package 10). The frames that are the same in all of the protocol's shapes (Challenge, Fetch, Items, Ack, AckResult) are one shared type each. The committed vectors of the version 1 frames and of the version 1 auth bytes are deleted, and the version 1 functions are no longer pinned by a test: their pins went with them. A test (`TestTheFramesOfTheRetiredVersionAreRefused`, `TestThereIsNoDowngrade`) shows that the retired frames are refused by every decoder and that a signature over the retired array is no signature of version 2.

**The mailbox domain does not import the binding domain.** The version 2 frames carry the binding and the wallet revoke as bounded byte strings (a `COSE_Sign1` and a `COSE_Key`) and the fixed-length hashes; verifying them is the caller's pure glue (`relaybind.ParseStatement`, `ParseCOSEKey`, `VerifyBinding`, `Admit`), which the session already links. `domain/relaybind` and `domain/mailbox` are both pure and each pins the constants it shares with the other in a test (`MaxTime`, `MaxSign1Bytes`, `MaxCOSEKeyBytes`, `KeyHashSize`); a test in this package imports `relaybind` to run the whole path with a real binding. The reverse arrangement (mailbox imports relaybind) is allowed by the layering rule, which lets a domain package import another, but it would put the strict COSE parser and `domain/cose` in the closure of every user of the frames, the client included, for no gain.

### Outputs (version 2)

- **SPO-Xmailbox-OUT-049** The version 2 shapes, after the type, are: 0 Challenge as before (a range `[min, max]`; a relay that offers both versions announces `[1, 2]`, one that offers only version 2 `[2, 2]`); 1 Auth `[2, fingerprint (20), signature (64), binding, senders]` with `binding = [ed25519 (32), x25519 (32), sign1, cose key]` and `senders` an array of at most 64 byte strings of 28 bytes; 2 AuthOK `[2, max envelope, max entries, max bytes, retention seconds, until]` (the limits as in version 1 and the `until` of the binding as the relay recorded it, unix seconds 1 to `MaxTime`: 0 is `ErrRange`, when encoding and decoding); 3 Put `[request id, wallet key (28), to device (20), mid (32), size]`, followed by one raw frame as in version 1; 4 PutResult `[request id, status]`; 5, 6, 7 and 8 as in version 1; 9 Error `[code]`; 10 Revoke, signed by the device `[request id, 0, ed25519 (32), x25519 (32), not-before, signature (64)]` or signed by the wallet key `[request id, 1, sign1, cose key]` (the kind is the third element; a kind other than 0 and 1 is `ErrRange`); 11 RevokeResult `[request id, status]`. `sign1` and the cose key are byte strings of 1 to 512 and 1 to 128 bytes. The version field of an Auth and of an AuthOK is exactly 2. The fingerprint travels in the Auth, and the relay recomputes it from the two keys (OUT-053). `not-before` is a unix time 0 to `MaxTime`; that it is not beyond relay time plus the skew is the session's (`relaybind.VerifyRevoke`, `VerifyDeviceRevoke`). The Put carries the **recipient's** wallet key; the sender's wallet key is the session's, bound at Auth, and is never a frame field. There is no Lookup and no Directory (ADR 0014 decision 6): types 12 and up are unknown in every stage. The largest Auth (512, 128, 64 senders) is 2726 bytes, under the 3 KiB of the ADR and the 4096 of `MaxHeaderFrame`, which does not change. `NewPutV2` and `NewPutV2Of` are the constructors of the Put, as `NewPut` and `NewPutOf`.
- **SPO-Xmailbox-OUT-050** *Rewritten in ADR 0014 work package 7, when version 1 was deleted (`V1`, `BothVersions` and `ChooseVersion` are gone).* `Versions` is the set of versions an endpoint speaks. There is one valid set, `V2`: `Valid()` is true for it alone (the empty set, the bit of the retired version 1, the two together and every other bit are not valid), and `Has(v)` is true for version 2 alone and only in `V2`. `Range()` of `V2` is `[2, 2]`, the range a relay announces in its Challenge; a set that is not valid gives `[0, 0]`. `Choose(min, max)` is the client's rule: a malformed range (a min of 0, a min above the max, or a max above 65535) is `ErrMalformed`; a range that holds 2 gives version 2; every other range is `ErrVersion`. So `V2.Choose(1, 1)`, the Challenge of a relay that offers only version 1, is `ErrVersion`, as is a range above 2. There is no floor, no `ErrDowngrade` and nothing persisted per relay (SEC-036): with one version there is nothing to downgrade to.
- **SPO-Xmailbox-OUT-051** *Rewritten in ADR 0014 work package 7, when version 1 was deleted (`StageUnversioned` and `StageV1` are gone).* The decoders take the **stage** of the connection: `DecodeFromClientIn(stage, frame)` (the relay's side) and `DecodeFromRelayIn(stage, frame)` (the client's). There are two stages: `StageV2PreAuth` (the connection is open and the Auth is not yet accepted; the Challenge is its first frame) and `StageV2Authed`; the zero value and any other number is invalid and refuses every frame with `ErrStage`. A frame is refused in this order: a header body outside 1 to `MaxHeaderFrame` bytes (`ErrFrameSize`), structure over the bounds, CBOR that is not canonical (`ErrNotCanonical`); then by its type alone, before any field is read: a type that does not exist is `ErrUnknownType` (types 12 and up), the wrong sender is `ErrDirection`, the right sender at the wrong stage is `ErrStage`; then the wrong number of fields (`ErrMalformed`, which is what a frame of the retired shape is), a field of the wrong kind or length, and a value out of range. The version field of an Auth or an AuthOK that is not 2 is `ErrVersion`; at `StageV2Authed` an Auth is already `ErrStage` by its type. Who may send which frame, at which stage:

  | Stage | Client to relay (the relay decodes) | Relay to client (the client decodes) |
  | --- | --- | --- |
  | `StageV2PreAuth` | Auth, Revoke | Challenge, AuthOK, RevokeResult, Error with a code 0 to 7 |
  | `StageV2Authed` | Put, Fetch, Ack | PutResult with a status 0 to 8, Items, AckResult, Error with a code 0 to 7 |

  A Revoke is allowed only **before** Auth (ADR 0014 decision 7); a Revoke after Auth is `ErrStage`. The Challenge is allowed at `StageV2PreAuth` because it is the first frame; a client that reads a second one stops, because at that point it expects a RevokeResult or the AuthOK. A relay takes its first stage from `StageForOffer(V2)` and a client from `StageAfterChoice(2)`, both `StageV2PreAuth`; every other argument is `ErrVersion`. A stage is moved only by functions that take the message the session has accepted, and each refuses (`ErrStage`, no stage) a message that does not belong: `Stage.AfterAuth(message)`, the relay's, gives `StageV2Authed` for an `AuthV2` at `StageV2PreAuth`; `Stage.AfterRevoke(message)`, the relay's, keeps `StageV2PreAuth` for a `RevokeByDevice` or `RevokeByWallet` at `StageV2PreAuth`; `Stage.AfterAuthOK(message)`, the client's, gives `StageV2Authed` for an `AuthOKV2` at `StageV2PreAuth`. The stage constants name stages for comparison and tests; a session moves its stage only by these. The full relay sequence: Revoke or Revokes, an `AuthV2`, then a second Auth and a Revoke are `ErrStage` and a Put, Fetch and Ack are accepted. Moving is the session's (see "What a session must still do in version 2").
- **SPO-Xmailbox-OUT-052** *Rewritten in ADR 0014 work package 7, when version 1 was deleted.* There is one encoding, version 2's. `EncodeV(version, message)` writes version 2 and refuses every other version number, the retired 1 included, with `ErrVersion`; `Encode(message)` is `EncodeV(2, message)`; a nil message is `ErrMalformed`. Every message of the protocol (Challenge, `AuthV2`, `AuthOKV2`, `PutV2`, PutResult, Fetch, Items, Ack, AckResult, Error, `RevokeByDevice`, `RevokeByWallet`, RevokeResult) encodes in version 2, with the status and code ranges of version 2 (OUT-055), and none encodes in any other. Whatever a decoder accepts, `EncodeV(2, ...)` writes back byte for byte (INV-029).
- **SPO-Xmailbox-OUT-053** The bytes a device signs to authenticate a version 2 connection are the canonical CBOR array `["spo/mailbox-auth/v2", 2, relay node key, client node key, nonce, relay time, fingerprint, binding hash, senders hash]`: 9 elements, the label first. `binding hash` is `relaybind.VerifiedBinding.FullHash()` (Blake2b-256 of the canonical `COSE_Sign1`, signature included), and `senders hash` is `SendersHash` of the list (OUT-054). `AuthBytesV2(AuthV2Params)` takes only typed, fixed-length values and no version (it is 2). `VerifyAuthV2(keys, tunnelPeer, signature, params)` takes the two device keys **as presented** (there is no identity document at the relay) and enforces, in this order and each with its own error that also satisfies `errors.Is(err, ErrAuth)`: the Ed25519 key is not a small-order point and is canonical (`ErrAuthWeakKey`, SEC-041); the fingerprint recomputed from the presented keys equals `params.Fingerprint` (`ErrAuthFingerprint`); `params.ClientNodeKey` equals `tunnelPeer` (`ErrAuthTunnelKey`); the parameters are in range, a relay time 0 to `MaxTime` (`ErrRange`, not an `ErrAuth`); and the signature of the presented key verifies (`ErrAuth` alone). The version 1 check "the client node key is the identity's" does not exist in version 2: there is no identity document at the relay (ADR 0014 decision 7).
- **SPO-Xmailbox-OUT-054** The expected-sender list is strictly ascending by bytes (sorted, so with no repeat), at most 64 keys of 28 bytes. The ADR names no order; ascending makes one set one encoding and one hash. A frame that carries a list that is not strictly ascending is refused (`ErrRange`), when decoding and when encoding. `CanonicalSenders(keys)` sorts a copy and drops repeats and is `ErrRange` if more than 64 distinct keys are left. `SendersHash(list)` is Blake2b-256 of the canonical CBOR array of the byte strings, in list order (the empty list is the hash of the empty array `0x80`); it refuses a list that is not canonical.
- **SPO-Xmailbox-OUT-055** Version 2 adds the put status 8 `unbound` (the device has no valid binding to that key, expired or revoked included), the error codes 6 `not_allowed` (key not on the allow-list; sent only to the presenter) and 7 `binding` (the binding is invalid, expired or revoked, and the client must sign a new one), and the revoke statuses 0 recorded and 2 refused (1 is not used). `Status.ValidIn(version)` and `Code.ValidIn(version)` give the range of a version: statuses 0 to 7 in version 1 and 0 to 8 in version 2, codes 0 to 5 and 0 to 7. `Valid` is the version 1 range, as before. The decoders use the range of their stage; before a version is chosen a code is 0 to 5. Every other authentication failure stays `1 auth`, and a registry that cannot take a new binding answers `3 limit`.
- **SPO-Xmailbox-OUT-056** Open mode quota (ADR 0014 decision 5). `OpenQuota` is the quota of ADR 0013, `MaxBoundDevices`, and the stranger allowance (`StrangerEntries`, `StrangerBytes`); `Validated()` returns the `ValidOpenQuota`, the only type that has `Admit(usage, size, listed)`. A sender whose wallet key is on the recipient's expected-sender list (`listed`) is held to the bounds of ADR 0013 (`ValidQuota.Admit`). Any other sender is also held to the stranger allowance of its recipient, shared by all strangers: **16 entries and 1 MiB**, strictly inside the queue bound (PRE-031). The strangers' pool is a sub-budget of the queue: strangers never hold more than the allowance, and a listed sender may use all the rest, which is never less than one envelope of the largest size. A stranger therefore cannot fill a victim's queue. `Admit` answers too_large for a size outside 1 to `MaxEnvelopeBytes`, full for any bound the put would pass, otherwise stored; the zero `ValidOpenQuota` answers full. The `sender bytes` figure of the usage is counted per wallet key (the sum of its devices); the 120 puts a minute per wallet key are the session's (`MaxPutsPerPartyPerMinute`). `ReservedBytes(perDevice, devices)` is the product and reports when it does not fit a `uint64`. `DefaultOpenQuota()` is exactly the default of ADR 0014 decision 5, and a test pins each figure and validates it: **1024 bound devices** (`DefaultBoundDevices`; `MaxBoundDevices` is the ceiling of 4096); per device a queue of **256 entries and 4 MiB** (`OpenMailboxBytes`); per pair **64 entries and 2 MiB** (`OpenPairBytes`); strangers **16 entries and 1 MiB**; **64 MiB** per wallet key as a sender; a global quota of **4 GiB**, which is exactly 1024 queues of 4 MiB (a constant assertion fails the build if the default registry reserved more than the default global quota). The queue and pair bounds of ADR 0013 (64 MiB, 8 MiB) are ceilings. The earlier default of 4096 devices at 64 MiB needs 256 GiB (PRE-031); an operator who wants 4096 devices at the default queue bound sets 16 GiB.
- **SPO-Xmailbox-OUT-057** Test vectors of version 2 are committed (`testdata/vectors_v2.json`) and regenerated and compared by a test: the version 2 auth bytes with an Ed25519 signature of the fixed test key, five expected-sender lists with their hashes, and every frame that version 2 adds or changes (the Challenge for both offers, the Auth with three senders, with none and the largest, the AuthOK, the Put, the `unbound` PutResult, the two new error codes, both Revokes and both RevokeResults), each with its stage and sender. `testdata/check_vectors.py` recomputes the auth bytes and the sender hashes and encodes each frame again from its fields with its own encoder. For each Auth frame it also checks that the sender list is canonical (strictly ascending, each key 28 bytes, at most 64) and is one of the sender-list vectors, and recomputes the fingerprint from the frame's two device keys with its own code (the first 20 bytes of Blake2b-256 over `spo/party/v1`, the Ed25519 key and the X25519 key, as `party.FingerprintOf`); each auth-bytes vector names the sender-list vector (`senders_list`) whose hash is its senders hash. A corrupted fingerprint, an unsorted list or a senders hash of another list fails it. The Go test that runs it fails if it does not agree, and `SPO_REQUIRE_PYTHON=1` makes a missing interpreter a failure. The frames that are identical in both versions are in `vectors.json`.

### Preconditions and failures (version 2)

- **SPO-Xmailbox-PRE-027** The bounds of an Auth and of a wallet Revoke: `sign1` 1 to 512 bytes, the cose key 1 to 128, at most 64 senders of exactly 28 bytes, fingerprint 20, signature 64, each device key 32. Under, at and over each is tested; a value over the bound is `ErrRange`, except that an array of more than 64 items is `ErrShape` (the structural bound of the pre-scan, `MaxCBORArray`, which equals `MaxSenders`), and the encoder holds the same bounds. A constants test pins them to `relaybind` (512, 128, 28, `MaxTime`). The header bound stays 4096.
- **SPO-Xmailbox-PRE-028** A version 2 field of the wrong kind or length is `ErrMalformed`; a value out of range is `ErrRange`: a request id above 2^32 - 1, an envelope size outside 1 to 1 MiB, a status above 8, a code above 7 (above 5 before a version is chosen), an AuthOK value as in version 1, an `until` of 0 or above `MaxTime` or a `not-before` above `MaxTime` (a negative one is a wrong kind when decoding), a revoke kind above 1, a revoke status of 1 or above 2, senders that repeat or are not ascending, a binding that is not four items. A Revoke with a kind and the arity of the other kind is `ErrMalformed`.
- **SPO-Xmailbox-PRE-029** *Amended in ADR 0014 work package 7: only the retired version 1 is a wrong version now: its Auth is `ErrVersion` (or `ErrMalformed` by its arity), its Put and AuthOK are `ErrMalformed`, at both stages; the stage cells are the four of OUT-051.* A frame of the wrong version is refused. At `StageV1` a version 2 frame is `ErrUnknownType` (Revoke, RevokeResult) or the wrong shape, `ErrMalformed` (Auth, Put, AuthOK of version 2); at a version 2 stage a version 1 frame is `ErrVersion` (an Auth of version 1) or `ErrMalformed` (Put, AuthOK). A status 8 and the codes 6 and 7 are out of range at `StageV1`. A frame at a stage that does not allow it is `ErrStage`. A test lists every cell of the table of OUT-051 and every refusal's reason.
- **SPO-Xmailbox-PRE-030** `AuthBytesV2` and `VerifyAuthV2` refuse a negative relay time and a relay time above `MaxTime` with `ErrRange`.
- **SPO-Xmailbox-PRE-031** The configuration-load rule of open mode: every bound of ADR 0013 is set and no looser than the table; `MaxBoundDevices` is 1 to 4096; the stranger allowance is 1 to 16 entries and 1 to 1 MiB and **strictly inside the queue bound**: `StrangerEntries < MailboxEntries` and `MailboxBytes - StrangerBytes >= MaxEnvelopeBytes`, so that once the strangers hold all they may, a listed sender still has room for one envelope of the largest size (an allowance equal to the queue bound would let strangers fill the whole queue and is refused; so is a queue with one byte less room, and one smaller than the allowance); and **the global quota is at least the per-device queue bound times `MaxBoundDevices`** (the quota reserves room per bound device, not per sender); otherwise `ErrQuota`. A global quota one byte short is refused and exactly enough is accepted. The defaults meet the rule on its edge: 1024 devices times the 4 MiB queue bound is the 4 GiB global quota (OUT-056). The ceilings of ADR 0013 do not: 4096 devices at 64 MiB need a global quota of 256 GiB, and 1024 need 64 GiB; the configuration sets the queue bound or the quota to match (the `relayconfig` work package keeps the rule).

### Security (version 2)

- **SPO-Xmailbox-SEC-036** *Amended in ADR 0014 work package 7: **there is one version.** Version 1 is deleted from the tree, so there is nothing to downgrade to: a version 1 Auth is refused by every decoder, a signature over the retired array is no signature of version 2, and a client that speaks `V2` refuses a Challenge that offers only version 1 (`ErrVersion`, no signature made, no frame sent: client PRE-058). The text below is the argument that held while both existed.* Downgrade. The version is inside the signed bytes in both versions, with a different label and a different array length, so a signature made for one is no signature for the other: a version 2 signature does not verify as a version 1 auth, nor the reverse, and a version 1 array that says version 2 is not the version 2 array. An attacker who rewrites the Auth frame into the other version's shape gets a frame that does not decode, or one whose signature does not verify. What is **not** signed, in either version, is the Challenge's range `[min, max]`. **Only the relay can rewrite its own Challenge**: the tunnel is authenticated to the relay key the client pinned, and nobody else holds it. A client that accepts the rewritten range `[1, 1]` and chooses version 1 signs version 1 bytes itself, but that signature binds that relay's key (the signed array holds the relay key the client pinned) and verifies at no other relay, so the harm is confined to a relay the client already trusts with its mailbox. **The protection is that clients speak version 2 only** (`V2.Choose(1, 1)` is `ErrVersion`), and **version 1 is deleted from the tree in the same series of changes as the session and client migration**; there is no client floor and nothing is kept per relay. `BothVersions` exists only for the interim relay that still speaks version 1. A relay configured for version 2 only offers `[2, 2]` and refuses a version 1 Auth at the decoder (`StageV2PreAuth`: `ErrVersion`).
- **SPO-Xmailbox-SEC-037** `VerifyAuthV2` accepts only a signature made by the presented key over exactly these values. Another key, any flipped signature bit, a changed relay key, nonce, relay time or hash, and a signature under another label are `ErrAuth` alone; a fingerprint that is not that of the presented keys (either key changed), a claimed node key that is not the tunnel's, and a weak key each have their own error, in the order of OUT-053. Each comparison is the only thing that refuses in its test, because the signature in that test is genuine.
- **SPO-Xmailbox-SEC-038** Domain separation. The version 1 array has 7 elements and the label `spo/mailbox-auth/v1`; the version 2 array has 9 and the label `spo/mailbox-auth/v2`; the device revoke array of `relaybind` has 3 and the label `spo/relay-revoke-device/v1`; the other messages a device key signs (`spo/envelope/v1`, `spo/identity/v1`, `spo/rotation/v1/old`, `spo/rotation/v1/new`) start with an ASCII label, and every statement payload starts with `spo-`. The three arrays start with three different bytes (0x87, 0x89, 0x83), each carries its own label and no other, and none starts with another's label.
- **SPO-Xmailbox-SEC-039** Every field of the version 2 array is covered: changing the relay key, client key, nonce, relay time, fingerprint, binding hash or senders hash, swapping the two node keys or the two hashes, or zeroing a hash, changes the signed bytes. With a real binding and a real list, the device signature fails if the binding is replaced by another encoding of the same statement (another valid signature of the wallet key: another full hash), or the senders are changed in any way (one added, one dropped, one changed, all dropped).
- **SPO-Xmailbox-SEC-040** Every length, count or size in a version 2 frame is checked against its bound before anything of that size is built. A frame that claims a `sign1`, key, senders array, sender, binding or revoke field of 2^32 or 2^64 - 1 bytes or items allocates less than 16 KiB when refused; a real `sign1` of 513 bytes is refused for its size with less than 16 KiB; the largest legitimate Auth costs less than 64 KiB; a header frame over 4096 bytes is refused on its length.
- **SPO-Xmailbox-SEC-041** A device Ed25519 key that is a small-order point (y of 0, 1, p - 1 or one of the two order-8 values, with either sign bit) or not a canonical encoding (y of p or more) is refused by `VerifyAuthV2` (`ErrAuthWeakKey`). With the identity point as the key, R = identity and S = 0 verify for every message, so a signature by such a key would prove nothing (the test shows that the standard library accepts it). The rule is the one `relaybind` applies to wallet keys and to the device-signed revoke; this package carries its own copy, and a test runs both on the same keys. **The X25519 key is not checked**: the relay only hashes it into the fingerprint and never hands it out in version 2, so an all-zero or small-order X25519 key is accepted. Any future directory or lookup work (ADR 0014 decision 6) must refuse such keys before serving them to anyone.
- **SPO-Xmailbox-SEC-042** The open-mode arithmetic does not wrap: `used + size` is never computed (`size <= max` and `used <= max - size`), a stranger usage near the top of a `uint64` is full, `ReservedBytes` reports an overflow instead of wrapping, and a stored answer is only given when every bound still holds after the put (fuzzed).

### Invariants (version 2)

- **SPO-Xmailbox-INV-028** `internal/domain/mailbox` still imports neither `relaybind` nor `domain/cose` (a test parses its imports, in addition to INV-001).
- **SPO-Xmailbox-INV-029** Whatever the version 2 decoders accept, at any stage and from either side, is written back byte for byte; for every version 2 sample and vector, decoding the encoding at its stage gives the message; a single flipped bit, a byte replaced, removed or doubled in any frame, including the largest Auth, is refused or decodes to a message that is written back to exactly the changed bytes. Truncations and extensions are refused.
- **SPO-Xmailbox-INV-030** No input makes a version 2 decoder, `CanonicalSenders` or `ValidOpenQuota.Admit` panic or break its rule (fuzz targets `FuzzDecodeIn`, `FuzzCanonicalSenders` and `FuzzOpenAdmit`, with small seeds, inputs over 512 bytes skipped).

### What a session must still do in version 2

The package checks what it can from one frame. These remain the session's, in addition to the version 1 list above (whose relay halves that name the access list are superseded by the section "The relay session, version 2"). The unnumbered items are the first draft of the section; the numbered items 1 to 18 are the obligations the session package implements and cites one by one (the discharge table follows item 18).

- **Count and time.** At most 8 Revoke frames a connection (`MaxRevokesPerConn`), the 5 second budget for the whole connection before Auth (`UnauthBudget`), 16 unauthenticated slots, 60 new bindings an hour with a burst of 10, 8 devices per key, 4096 bindings: the package names the numbers and pins them; nothing here counts.
- **Verify the binding.** Parse `sign1` and the cose key with `relaybind.ParseStatement` and `ParseCOSEKey`; call `relaybind.VerifyBinding` with the fingerprint **computed** from the presented keys (`DeviceKeys.Fingerprint()`), the relay's time and its policy; call `Admit` with the three merged tombstones before registering anything. Display only the key hash, never the address bytes.
- **Compute the commitments.** `AuthV2Params.BindingHash` is `VerifiedBinding.FullHash()` of what was presented and `SendersHash` is `SendersHash` of the list in the frame: never a value the client states (a client states none). `RelayKey` is the relay's own key and `tunnelPeer` is the tunnel's. This package does the recomputation of the fingerprint from the presented keys and the comparison of the claimed node key with the tunnel's; it does not know whether the binding is valid or the list is the one the registry should store.
- **Revokes.** Verify with `relaybind.VerifyRevoke` or `VerifyDeviceRevoke` (they check `not-before` against relay time plus the skew), record the tombstone always (maximum wins, three scopes), and delete the binding, sessions and mail only if `relaybind.Invalidated`. Answer `RevokeResult` with 0 or 2.
- **Put.** The sender's wallet key is the one bound at Auth, never a frame field. The recipient's key and device in the Put are checked against the registry (`unbound` for no valid binding, expired or revoked included); the quota is `ValidOpenQuota.Admit` with `listed` decided from the recipient's stored expected-sender list.
- **Versions.** The relay decodes at the stage of its offer, so an Auth of a version it did not offer is refused by the decoder. The client is configured for version 2 only and closes on `ErrVersion` when the Challenge does not offer it (SEC-036). `AuthOKV2.Until` is the recorded binding's `until`, a time of 1 or more.

1. **Stage transitions.** The relay starts at `StageForOffer(offered versions)`. For every Revoke that decodes, accepted or refused, it takes the stage from `AfterRevoke(message)`; once the Auth is verified and accepted it takes it from `AfterAuth(message)`. A relay that offers both versions is therefore at `StageV2Authed` after a version 2 Auth, and its decoder refuses a second Auth and any later Revoke with `ErrStage`; a Revoke before the Auth keeps a version 1 Auth from following it. A version 1 Auth accepted at `StageUnversioned` or `StageV1` gives `StageV1`, which does not track authentication (version 1 allows every frame of the client): the version 1 session keeps its own record of it, as before. The client takes `StageAfterChoice(version)` and `AfterAuthOK(message)`. No session assigns a stage constant; an error from a transition, like a frame the stage refuses, ends the connection.
2. **Failure to code.** Binding failures (`ParseStatement`, `ParseCOSEKey`, `VerifyBinding`, `Admit`: invalid, expired, not yet valid, revoked by a tombstone, a fingerprint in the payload that is not the device's) are the `binding` code (7). A key that is not on the operator's allow-list is `not_allowed` (6), **decided after `Admit`**, so that a presenter of an invalid binding learns nothing about the list and the code names only the presenter's own key. A weak device key (`ErrAuthWeakKey`), a fingerprint that is not that of the presented keys (`ErrAuthFingerprint`), a claimed node key that is not the tunnel peer's (`ErrAuthTunnelKey`) and a signature that does not verify (`ErrAuth`) are the `auth` code (1), with no text. A registry that is full with nothing evictable, and the new-binding rate cap, are the `limit` code (3). A Revoke that the relay refuses after it decoded (a signature or a statement that does not verify, a `not-before` beyond relay time plus the skew) is answered `RevokeResult` with status `refused` (2) and the connection stays open; **a refused Revoke counts toward the 8 per connection** exactly as a recorded one does, and the ninth ends the connection. A frame that does not decode ends the connection and is not a refused Revoke.
3. **A binding can expire mid-connection.** The session either re-checks the sender's own binding (not past its `until`, not invalidated by a tombstone) on each Put, ending the connection with the `binding` code when it fails, or closes the session at the binding's `until`, which `AuthOKV2.Until` has told the client. No Put is stored from a binding that has expired.
4. **Stranger accounting.** The relay keeps, per recipient device, counters of the entries and bytes held for strangers. A Put is classified when it is made (listed or stranger) and the class is kept with the stored entry, so that an ack, or the retention sweep, releases exactly what the put took even when the list has changed since. "Listed" is decided from the **session's bound wallet key**, the one the verified binding named, being on the recipient's stored expected-sender list, **never from a frame field**. The expected-sender list is stored only after an Auth has succeeded in full (binding verified and admitted, `VerifyAuthV2`) and is replaced by the list of the device's latest successful Auth; a failed Auth stores and replaces nothing.
5. **Registry rules.** A new binding for a device replaces its old one (one wallet key per device). At most `MaxDevicesPerKey` (8) devices per wallet key. The new-binding rate cap (60 an hour, burst 10, relay-wide) does not count the re-authentication of a (wallet key, device) pair that is already registered **with the same statement**, matched by `StatementID` (which leaves the signature out); a different statement for the pair is a new binding and counts.
6. **Fetch and Ack only for the session's device.** Neither frame names a device: the relay serves the device bound at Auth, and no other.
7. **The relay's own nonce and time.** `AuthV2Params.Nonce` and `RelayTime` are the values the relay sent in this connection's Challenge and `RelayKey` is its own key, never anything a client states (the frame has no such field).
8. **A binding that is not yet valid** (its `from` is after relay time) **is refused with the `binding` code and never stored**: `Admit` decides before any write to the registry.
9. **The client reconnects when the list changes.** The expected-sender list is fixed for the connection that presented it (item 4). When the set of expected senders in the client's party registry changes, the client reconnects, which authenticates again and presents the new list. **Discharged by the client (work package 7): OUT-093.**

The registry of work package 5 ([The binding registry](#the-binding-registry-adr-0014-work-package-5)) adds these obligations to the session. They are the registry review's: each one closes something the registry cannot close by itself. **Items 1 to 18 are discharged by the version 2 session (work package 6), table below, and item 9 by the client (work package 7: OUT-093).**

10. **One fingerprint for both checks.** The session computes the device fingerprint ONCE, from the two keys that the version 2 login signature authenticated (`DeviceKeys.Fingerprint()`), and passes that one value to `relaybind.VerifyBinding` and to `VerifyAuthV2`. It never takes a fingerprint from a frame field or from the payload of the statement.
11. **Commit to the presented statement.** The login's signed bytes must carry the full hash of the statement the client PRESENTED in this Auth (`VerifiedBinding.FullHash()` of what it verified), not the hash of the entry the registry stores for the device: after a renewal by re-signature the two differ (a re-presentation of the same statement keeps the stored one, SPO-Xmailbox-PRE-038).
12. **Policy.** The session verifies with the registry's own `Policy` (`Core.Config().Policy`, tightened by the operator), and the registry checks the lifetime against it again (SPO-Xmailbox-PRE-046).
13. **The expected-sender list on every login.** After a successful login the session calls `SetExpectedSenders` with the list of that Auth, on EVERY successful login and also with an empty list, so the stored list is always the latest login's (a list left from an earlier login would otherwise stay).
14. **A revoke that errors.** On any error from `Revoke` the session acts on the partial `RevokeResult` it returns (it closes the sessions and drops the queued mail of `Invalidated`) and re-checks `Lookup` for the device, **but only for a device that was served before the revoke and is the revoke's own** (revised after the session review, finding H1: the first build purged any device the revoke named that was not served, which let anyone purge the queue of a lapsed device; the rule is SPO-Xmailbox-SEC-069). `ErrTombstoneUnrecorded` is not a refusal: the binding was deleted; the session logs it. (SPO-Xmailbox-OUT-077, PRE-049.)
15. **Re-check on every operation.** A long-lived session re-checks `Lookup` for its device on every Fetch, Put and Ack, and ends with the `binding` code when the device is no longer served (revoked, expired, or invalidated by a tombstone whose file is still there), so a revoked device's open session cannot continue. This extends item 3, which re-checked on Put only.
16. **The eviction guard.** The session supplies `Config.Evictable`: "queue empty and not connected". It must be cheap, and it never calls a writer of the registry (it may read it).
17. **Sweep.** The session runs `Sweep` periodically (expired bindings, invalidated leftovers, idle bindings, expired tombstones). Tombstones are dropped nowhere else (SPO-Xmailbox-OUT-079).
18. **Error mapping.** A `relaybind` verification error (including `relaybind.ErrLifetimePolicy` from the registry and `relayregistry.ErrOlderBinding`) is `binding` (7); `ErrNotAllowed` is `not_allowed` (6); `ErrLimit` and every error wrapping it from `Register` (`ErrKeyDeviceLimit`, `ErrRegistryFull`, `ErrNewBindingRate`, `ErrKeyChangeRate`) is `limit` (3); from `Revoke`, `ErrTombstoneFull` and `ErrRevokeRate` (a revoke that invalidates nothing, refused) are a `RevokeResult` with status `refused` (2). A `Lookup` miss is `unbound` (8) for a put.

### Choices that go beyond the ADR text (work package 2)

- **Stages, not a bare version, decide the decoder.** A connection has three moments with different rules (before a version is chosen, before Auth, after Auth) and the ADR's "Revoke before Auth" cannot be stated by a version alone.
- **Revoke only before Auth.** The ADR says a Revoke is allowed before Auth and says nothing of after. After Auth it is `ErrStage`: a client sends its pending revokes first on every connection (ADR 0014 decision 8).
- **Revoke kind in the frame.** The two Revoke shapes are told apart by an explicit kind (0 device-signed, 1 wallet-signed) after the request id, as the ADR's table has it.
- **The sender list is strictly ascending.** The ADR gives no order.
- **Non-empty statements.** `sign1` and the cose key are 1 to their bound, not 0 to it.
- **A weak device key is refused** in `VerifyAuthV2`, which the ADR states for the wallet key and the device-signed revoke only.
- **AuthOK keeps its version field** (always 2) and gains `until`: "as ADR 0013, plus `until`".
- **`DefaultOpenQuota` has 1024 devices, a 4 MiB queue and a 2 MiB pair bound**, not 4096 devices at 64 MiB (OUT-056, PRE-031).
- **The stranger allowance is strictly inside the queue bound** (PRE-031); the ADR said only "inside".
- **The downgrade defence is that clients speak version 2 only.** The signed array of the ADR cannot also cover the offered range without a tenth element, and a client floor would need state per relay; see SEC-036.
- **`AuthOK.until` is 1 or more.** A recorded binding never has an `until` of 0.

## The binding registry (ADR 0014 work package 5)

[ADR 0014](../../docs/explanation/adr/0014-wallet-key-identity-for-the-relay.md) decisions 5, 7 and 8 describe the relay's durable registry of wallet-key bindings and revocation tombstones. It is built in three parts: the pure rules `internal/domain/relayregistry` (a `Core` that decides and changes nothing: `Plan*` returns ordered storage operations, `Apply` changes one), the ports `internal/ports/relayport/registry.go` with a contract suite and an in-memory reference in `relayporttest`, and the durable adapter `internal/adapters/bindingstore` (a directory, crash-safe, with the hardening of "Safety of the directory"). The binding statements are [Xrelaybind](./Xrelaybind.md). The rules were revised after the security review of the registry; the requirements below are the revised ones and the review's findings are stated where they change a rule.

Terms. A binding is **held** when it has not expired and no stored tombstone invalidates it (`relaybind.Invalidated`); it is **served** when it is held and valid yet by the clock (`from - skew <= now`). A revoke is **invalidating** when it invalidates at least one held binding that no stored tombstone already invalidated; any other revoke is **non-invalidating**. The **bound** of the tombstone table is `MaxTombstones` (default 16 times `max_bound_devices`, ceiling 65536); its **limited share** is half of it; its **headroom** is `max_bound_devices` entries above it.

### Interfaces (registry)

- **SPO-Xmailbox-IF-014** The relay registry ports (`relayport`): `RegistryReader`, `Registrar`, `Revoker`, `ExpectedSenderReader`, `ExpectedSenderWriter`, `RegistryExpirer`, `RegistryStats`, joined as `Registry` for the composition root. Values crossing: `relayregistry.Presented` (a `relaybind.VerifiedBinding` plus the strict COSE_Sign1 and COSE_Key, built only by `NewPresented`, which refuses bytes that are not those verified), `relayregistry.RevokeRecord` (from a `VerifiedRevoke`, or from the `relaybind.VerifiedDeviceRevoke` that `VerifyDeviceRevoke` returned: SPO-Xmailbox-SEC-062), `relaybind.KeyHash`, `party.Fingerprint`, `mailbox.WalletKey`. No secret crosses. A writer returns what it did together with its error (SPO-Xmailbox-OUT-077).

### Outputs (registry)

- **SPO-Xmailbox-OUT-058** Register admits a valid binding; Lookup, Devices, Tombstones and ExpectedSenders read it, as of the registry clock.
- **SPO-Xmailbox-OUT-059** There is one binding per device. A binding for a device that has one replaces it, also under another wallet key (the old key loses the device, the new key counts it). What a replacement costs is SPO-Xmailbox-PRE-044 and PRE-045.
- **SPO-Xmailbox-OUT-060** A revoke deletes only the stored bindings `relaybind.Invalidated` names, and only those of its scope (pair: that key and device; all: that key; device: that device, under any key). A replayed or older revoke changes nothing but the tombstone.
- **SPO-Xmailbox-OUT-061** A revoke for a device that is not bound is recorded (device scope) and blocks that device's older bindings under any key.
- **SPO-Xmailbox-OUT-062** Scope all: every binding of the key whose `from` is not later than the not-before, and no binding of another key.
- **SPO-Xmailbox-OUT-063** A tombstone keeps the maximum not-before ever seen and is never lowered, also across restarts. *Amended in ADR 0015 work package 4:* in a store that keeps versions the maximum is taken across every version of the scope key (`LoadTombstoneVersion`, SPO-Xmailbox-PRE-070), and across the tombstones learnt while running (SPO-Xmailbox-OUT-126).
- **SPO-Xmailbox-OUT-064** Expiry agrees with `relaybind`: a binding is live at `now == until` and not after. A tombstone is kept through not-before plus the maximum lifetime (and by a margin of the skew, SPO-Xmailbox-OUT-079) and dropped after.
- **SPO-Xmailbox-OUT-065** The expected-sender list: set or replaced for a served device (`ErrNotBound` otherwise), canonical only (`ErrBadSenders`: strictly ascending, at most 64), kept with the device across a replacement under the same key (cleared under another key: SPO-Xmailbox-OUT-078), gone with the binding, returned as copies. The session sets it on every successful login, an empty list included.
- **SPO-Xmailbox-OUT-066** Sweep drops the bindings past their `until` (whatever their queue holds), the bindings a stored tombstone invalidates (SPO-Xmailbox-OUT-081), the bindings idle for 30 days that the guard allows, and the expired tombstones (SPO-Xmailbox-OUT-079).
- **SPO-Xmailbox-OUT-067** The idle boundary: a binding is idle when `now - last >= IdleDrop`.
- **SPO-Xmailbox-OUT-068** Stats and counters name no wallet key.
- **SPO-Xmailbox-OUT-069** Bindings survive a restart.
- **SPO-Xmailbox-OUT-070** Tombstones survive a restart, and the maximum still wins across it. *Amended in ADR 0015 work package 4:* in the object store the maximum is taken across versions, whichever version is current (SPO-Xmailbox-PRE-070).
- **SPO-Xmailbox-OUT-071** Expected-sender lists survive a restart (they are as of the last login); a list that is not strictly ascending is dropped at load with a note, and its senders are strangers until the device logs in.
- **SPO-Xmailbox-OUT-072** A restart drops the bindings that expired. It does not drop tombstones (SPO-Xmailbox-OUT-079).
- **SPO-Xmailbox-OUT-073** A binding that a revoke invalidated is not served again after a restart.
- **SPO-Xmailbox-OUT-074** The last authentication is persisted at the granularity of 3600 seconds: a re-authentication younger than that writes nothing and a crash loses at most that much of the time; the time in memory is exact.
- **SPO-Xmailbox-OUT-075** Every stored binding is verified again at load with `relaybind` (strict parse, signature, key hash, device named by the file, the window, the tombstones, the allow-list). One that fails for a reason other than a time or the policy is quarantined with a note, and Open still succeeds.
- **SPO-Xmailbox-OUT-076** Every reader (`Lookup`, `Devices`, `ExpectedSenders`, the set operations and the counts of a key's devices) serves a binding only when it is served: not expired, valid yet by the clock (`from - skew <= now`) and not invalidated by a stored tombstone (`relaybind.Invalidated`). A binding whose delete failed (the tombstone was written, the file is still there) is therefore never served, and one stored under a clock that is behind is absent until the clock reaches it (review finding F8, F4).
- **SPO-Xmailbox-OUT-077** A writer returns what it did together with its error. A revoke whose operations do not all succeed returns the `RevokeResult` of what was applied: when its tombstone is stored (written, already there, or none was needed) every binding it names is invalidated, so the result lists them all, deleted or not; when the tombstone was not written, none. A revoke that could not record its tombstone lists only the bindings actually deleted. A registration that evicted bindings and then failed lists the evictions. The session acts on it (PRE-049, session obligation 14).
- **SPO-Xmailbox-OUT-078** When a device is bound under another wallet key its expected-sender list is cleared; a replacement under the same key keeps it.
- **SPO-Xmailbox-OUT-079** Tombstones are dropped only by `Sweep` and to make room at a limit, never at load, and only when expired by a margin of the skew: after not-before plus the maximum lifetime plus the skew. A start-up clock that is ahead therefore drops nothing, and a running clock a little ahead drops no live tombstone. The scan of the table is skipped when the least not-before in it (kept by day) says that nothing can have expired. *Amended in ADR 0015 work package 4:* a drop that storage refuses (`relayport.ErrDeleteRefused`, a retention not yet over on the store's clock) or that fails while making room is not made and is no failure: the tombstone stays loaded and enforced and is held back for `relayregistry.HoldSeconds` (one hour, `Core.Hold`), and neither a revoke nor a sweep plans it again before then (SPO-Xmailbox-OUT-124).
- **SPO-Xmailbox-OUT-080** At load a binding over this relay's maximum lifetime (the operator tightened it) is dropped with a note, like an expiry, and not quarantined; so is an expired one. A binding that is not valid yet by the clock is kept on disk and loaded, not served until valid, and counted in one summary note. A time is never a reason to quarantine.
- **SPO-Xmailbox-OUT-081** A binding still stored that a stored tombstone invalidates (a delete that failed earlier) is removed by `Sweep` and at load, and a replay of the revoke removes it too.

### Preconditions and failures (registry)

- **SPO-Xmailbox-PRE-032** Admission uses the three tombstone scopes: `relaybind.Admit` with the pair, the key's all and the device's own tombstone. A binding that is not yet valid, expired or at or before a tombstone is refused with `relaybind`'s error and nothing is stored.
- **SPO-Xmailbox-PRE-033** At most 8 live devices per wallet key, not counting the device being replaced (`ErrKeyDeviceLimit`, which wraps `ErrLimit`).
- **SPO-Xmailbox-PRE-034** The registry holds at most `max_bound_devices`. A new device evicts, in this order: expired and invalidated bindings (oldest `until` first, whatever the guard says), then the least recently authenticated binding the guard allows, equal times by device bytes. The registering device is never a victim.
- **SPO-Xmailbox-PRE-035** When nothing is evictable the newcomer is refused (`ErrRegistryFull`, wrapping `ErrLimit`) and nothing changes, no token is used; a nil guard evicts nothing; the registering device is not a victim; an expired binding goes before any live one.
- **SPO-Xmailbox-PRE-036** The relay-wide cap on new bindings is a token bucket of 60 an hour with a burst of 10, in integer arithmetic on relay time; a clock that steps back gives nothing; an operator may tighten both, never raise.
- **SPO-Xmailbox-PRE-037** A re-presentation of the same statement (same `StatementID`) is `Renewed`: only the last authentication moves; no token, no cap, no eviction.
- **SPO-Xmailbox-PRE-038** De-duplication is by `StatementID`, never by the full hash, which holds the signature: two signatures over one statement are one binding, and the stored statement is the first.
- **SPO-Xmailbox-PRE-039** The allow-list is decided after `Admit` (`ErrNotAllowed`, distinct from `ErrLimit`); a restricted relay with an empty list admits nobody.
- **SPO-Xmailbox-PRE-040** The tombstone table is bounded: `MaxTombstones` (default 16 times `max_bound_devices`: a registry slot can have caused at most three tombstones, one per pair, one per key for all, one per device; 16 is more than five times that worst case; ceiling 65536). Which revoke may use how much of it is SPO-Xmailbox-PRE-048 and PRE-049. A live tombstone is never dropped to make room; expired ones are dropped first. *Amended in ADR 0015 work package 4:* the drops that make room are a plan of their own (`Core.PlanRoom`), carried out before the revoke, and a drop that storage refuses or that fails is not made, is held back and is no failure of the revoke; the revoke is then planned with the room that is really there (SPO-Xmailbox-OUT-124, SEC-087). A tombstone learnt from storage while running is kept whatever the bound (SPO-Xmailbox-OUT-126).
- **SPO-Xmailbox-PRE-041** The configuration is refused outside its bounds (`ErrConfig` or `relaybind.ErrRange`): devices 1 to 4096, per key 1 to 8, tombstones 2 to 65536, new bindings 1 to 60 an hour and burst 1 to 10, revokes 1 to 60 an hour and burst 1 to 10, idle drop 1 hour to 30 days, and a `relaybind.Policy` that only tightens.
- **SPO-Xmailbox-PRE-042** `Open` refuses a relative directory, a nil clock, an invalid configuration and a clock outside 1970 to 9999.
- **SPO-Xmailbox-PRE-043** A binding file is at most 2452 bytes (`7 + 8 + 1 + 64*28 + 2 + 512 + 2 + 128` plus the lengths), a tombstone file 15, and a record outside those bounds is refused when it is decoded.
- **SPO-Xmailbox-PRE-044** A token of the new-binding cap is used only by a device that has NO held binding. A new statement for a device that has one, under the same wallet key (the renewal every 90 days, a longer `until`), is free, also when the bucket is empty (review finding F2: a drained bucket used to refuse every renewal). A binding that expired and is still stored does not count as held.
- **SPO-Xmailbox-PRE-045** A device bound again under ANOTHER wallet key draws on its own budget of 4 key changes in any 24 hours (`ErrKeyChangeRate`, wrapping `ErrLimit`), so that cycling keys is not free; it uses no token. The count is kept with the binding in memory only: a restart starts it again, and a device whose binding is gone starts afresh by paying a token.
- **SPO-Xmailbox-PRE-046** The registry checks the lifetime (`until - from`) against its own `Policy.MaxLifetime` and refuses a longer one with `relaybind.ErrLifetimePolicy` (also `ErrLifetime`), using no token, so a statement verified under the default policy cannot be registered in a relay limited to 30 days and then be dropped at the next start (finding F6). This is the one place the registry checks it.
- **SPO-Xmailbox-PRE-047** A presented binding whose `from` is earlier than the stored binding's for the same wallet key and device is refused (`ErrOlderBinding`); an equal `from` with another `until` is a replacement, and the same statement again is a renewal (finding L1).
- **SPO-Xmailbox-PRE-048** Where a new tombstone goes depends on whether the revoke is invalidating. A non-invalidating revoke (of a device not bound here, of a key with nothing bound, with a not-before below every held `from`) uses only the limited share of the table and is refused with `ErrTombstoneFull` when that is full; an invalidating revoke is never refused for room (SPO-Xmailbox-PRE-049). Raising a tombstone that is stored needs no room. This closes finding F1: a revoke that named something bound used to take a slot of the protected half whether or not it deleted anything, so an attacker with one binding and three revokes per token below its own `from` could fill the table and make every later revoke of a live device refused.
- **SPO-Xmailbox-PRE-049** Fail toward revocation. A revoke that invalidates held bindings deletes them whatever the table holds. Its tombstone is recorded up to the bound, then in the headroom above it (`max_bound_devices` entries: one tombstone per binding slot is enough to revoke every binding stored now, and growth into it needs a binding that a rate-capped registration made). Only when the headroom is spent too, the bindings are still deleted and no tombstone is recorded: the writer returns the result with `ErrTombstoneUnrecorded` (not a refusal; the session logs it). That is weaker, because the old binding could be presented again, and strictly better than leaving a revoked binding live. *Amended in ADR 0015 work package 4:* the same path is taken when the drops the room needed were refused or failed (held back, SPO-Xmailbox-OUT-124): the bindings are deleted and the result carries `ErrTombstoneUnrecorded`; a revoke that invalidates nothing then gets `ErrTombstoneFull` (PRE-048).
- **SPO-Xmailbox-PRE-050** The relay-wide cap on RECORDED non-invalidating revokes is a token bucket of 60 an hour with a burst of 10 on relay time (`ErrRevokeRate`, wrapping `ErrLimit`; an operator may tighten, never raise). A replay that records nothing and an invalidating revoke use no token. This is the rate limit the session would otherwise have to invent: throwaway-key revokes need no authentication and used to fill the limited share in seconds.
- **SPO-Xmailbox-PRE-051** The eviction guard is asked at most `EvictionProbes` (64) times besides one ask per binding that must go, for one registration, so a refused registration costs a bounded number of calls however many bindings there are. The consequence: when the oldest 64 bindings are all busy a registration is refused though a younger one is idle. A sweep asks once per idle binding.
- **SPO-Xmailbox-PRE-052** `Open` bounds the number of names it will read in each directory by the hard ceilings (`mailbox.MaxBoundDevices` for bindings; the tombstone ceiling plus the largest headroom for tombstones), never by the configured values. An operator who lowers `max_bound_devices` or the tombstone bound below what is stored can still start: everything valid is loaded, a note says so, and the normal eviction rules apply at later registrations (a registration evicts as many bindings as stand above the cap, within the guard's answers). *Amended in ADR 0015 work package 4:* a store that keeps versions bounds tombstone versions, not names: at most `relayregistry.MaxTombstoneVersions` (1 048 576), SPO-Xmailbox-PRE-070; the directory store has one version per name and keeps this bound of names.

### Security (registry)

- **SPO-Xmailbox-SEC-043** A binding is never stored before it is valid: the `Admit` window is checked at registration, and a value that no verification made (the zero `Presented`, the zero `RevokeRecord`, the zero `VerifiedRevoke`) is refused.
- **SPO-Xmailbox-SEC-044** Unverified values are refused by construction: `NewPresented` refuses a statement that is not the one the binding was verified from and a COSE key that is not the wallet key's.
- **SPO-Xmailbox-SEC-045** A closed registry answers every call with `ErrRegistryClosed`, and `Close` waits for a write in progress.
- **SPO-Xmailbox-SEC-046** A cancelled context stores nothing.
- **SPO-Xmailbox-SEC-047** Racing operations are safe under `-race`: writers are serialised, readers take a read lock only for the instant they read memory, and the guard is called with no reader lock held (SPO-Xmailbox-INV-035).
- **SPO-Xmailbox-SEC-048** The directory layout and modes: directories 0700, files 0600, nothing else in the root but the lock file and the three directories.
- **SPO-Xmailbox-SEC-049** One process owns the directory by an exclusive `flock` held from `Open` to `Close` (`ErrLocked`).
- **SPO-Xmailbox-SEC-050** No secret is ever at rest: a binding and a tombstone are public statements.
- **SPO-Xmailbox-SEC-051** Names are strict: lower-case hex of the exact length, one of three tombstone shapes, a temporary name, or a quarantine name.
- **SPO-Xmailbox-SEC-052** A hostile or foreign directory is refused at `Open` with an error wrapping `ErrRegistryCorrupt`: a link, a FIFO, a directory or a file of another type where a record belongs, a wrong owner, a mode that lets the group or others in, a junk name, a size over its bound, too many names. An `Open` that is refused leaves the directory byte-identical to what it found (SPO-Xmailbox-SEC-061).
- **SPO-Xmailbox-SEC-053** A binding that fails verification at load is quarantined (not deleted, not loaded, with a note) and the registry still opens; at most 256 files are kept there, and at the bound `Open` refuses and the file stays. A tombstone that cannot be read is not quarantined: `Open` refuses.
- **SPO-Xmailbox-SEC-054** Load drops what the rules drop (expired, over the lifetime policy, revoked by a tombstone, key not on the allow-list), clamps a last authentication in the future to the clock, and removes the leftovers of a crash, each with a note.
- **SPO-Xmailbox-SEC-055** Every write is crash-safe at every step (a temporary file, fsync, rename over the name, fsync of the directory; an unlink and an fsync of the directory): a crash leaves the old state or the new one, never a mix, and no temporary file after `Open`.
- **SPO-Xmailbox-SEC-056** A crash between a tombstone and the deletion of the binding it invalidates leaves a binding that the next load drops: the registry never serves a binding that a stored tombstone invalidates.
- **SPO-Xmailbox-SEC-057** A failure before the rename leaves the old state, a failure after it leaves the memory following the directory with the error returned; the registry is usable afterwards.
- **SPO-Xmailbox-SEC-058** The syncs are where durability needs them: the file before the rename, the directory after it, the directory after an unlink.
- **SPO-Xmailbox-SEC-059** The size of a file is read from the descriptor that was opened and checked against its bound before the file is read, so refusing an oversize file allocates nothing proportional to the size it claims. A test makes a small file claim a terabyte through an injected `fstat`; no test creates a large or sparse file.
- **SPO-Xmailbox-SEC-060** A clock stepped back at start by more than the skew (a board with no battery clock) does not quarantine bindings as not yet valid: they are kept and not served until valid. `Open` reports a prominent note, "the clock appears to be behind", when now is earlier than the newest stored last authentication minus the skew, and does not refuse to start (finding F4).
- **SPO-Xmailbox-SEC-061** An `Open` that is refused changes nothing it found. Every check runs first and only collects the cleanups (temporary files, drops, quarantine moves, rewrites), which run after the last check has passed. `Open` may still create the lock file and the three subdirectories of a directory that lacks them.
- **SPO-Xmailbox-SEC-062** A device-signed revoke reaches the registry only as a `relaybind.VerifiedDeviceRevoke`, which has unexported fields and is returned only by `VerifyDeviceRevoke`; `relayregistry.DeviceRevoke` takes nothing else, so a fingerprint nobody proved cannot become a tombstone (finding F7). It is held at compile level (a function taking another type does not build) and by an archtest: no other function of `relaybind` returns the type, no code outside `VerifyDeviceRevoke` fills one, its fields are unexported, and the only constructors of a `RevokeRecord` are `WalletRevoke` and `DeviceRevoke`.
- **SPO-Xmailbox-SEC-063** Nothing in the registry protects against a FULL rollback of the directory (a restored backup, an older snapshot): it brings back older bindings and forgets newer tombstones, and cannot be told from a restart. The only defence is the client's, which re-sends its pending revokes on every connection until the revoked binding's `until` (ADR 0014 decision 8). A PARTIAL rollback is handled: tombstones are loaded first and every binding is checked against them.

### Invariants (registry)

- **SPO-Xmailbox-INV-031** A plan changes nothing: only `Apply` changes the state, and the rate caps are used by `Apply`, not by the plan.
- **SPO-Xmailbox-INV-032** The operations of a plan are in the order of durability: a tombstone before the deletion of the bindings it invalidates; the deletion of victims before the write of the newcomer.
- **SPO-Xmailbox-INV-033** Load refuses two records of one device.
- **SPO-Xmailbox-INV-034** The table never holds more than `MaxTombstones` plus the headroom (`max_bound_devices`), at most 65536 plus 4096, except what a lowered configuration found stored (SPO-Xmailbox-PRE-052). Only an invalidating revoke goes above `MaxTombstones`.
- **SPO-Xmailbox-INV-035** The eviction guard is called with no reader lock of the registry held, by the durable adapter and by the in-memory reference alike: it may call a reader and must not call a writer. The contract suite has a guard that calls readers and would deadlock otherwise.

### Choices that go beyond the ADR text (work package 5)

- **Expected-sender lists are durable** (embedded in the binding record): after a restart they are as of the last login. The ADR said the relay "stores the latest list with the binding".
- **The last authentication is durable at an hour's granularity**; the rate buckets, the key-change counts and the counters are not (a restart starts them full or empty).
- **A replacement under another key frees the old key's count**, draws on the device's key-change budget and clears the list.
- **The tombstone table has a protected share and a headroom** (PRE-048, PRE-049); the ADR said only that a tombstone is always recorded and that the table is bounded. The first build gave the protected half to every revoke that named something bound; the review showed that this let a flood fill it (F1).
- **ADR gap closed:** the ADR has no relay-wide cap on unauthenticated revokes; PRE-050 is one, in the pure core, so the session does not invent it. `relaybind` had no verified device-revoke type; SEC-062 adds it.
- **Quarantine versus drop.** A stored binding that fails verification is quarantined (the registry still opens); a hostile directory or an unreadable tombstone refuses `Open`; an expiry, a lifetime over the policy, and a revoke are dropped; a time is never a reason to move a file (OUT-080).
- **The relay ports' closure** is held by an archtest: the direct imports of the ports are within mailbox, party, relaybind, relayregistry and cose, and the transitive closure holds nothing of this module but those, the ports, and the pure domain packages they import (identity, chain and custody are reached through party, mailbox and relaybind).

## The relay session, version 2 (ADR 0014 work package 6)

[ADR 0014](../../docs/explanation/adr/0014-wallet-key-identity-for-the-relay.md) decisions 5, 7 and 8 and the version 2 obligations above are built in `internal/app/relay`. The session offers **version 2 only** (a Challenge of `[2, 2]`); version 1 handling is gone from the session (the frames stay in `domain/mailbox` until the client has moved, work package 7). The operator's access list of signed identity documents is **removed from the session**: who may reach the relay is the tunnel's job (ADR 0014 decision 5, owner decision of 2026-11-18: restricted by default, the operator lists the device node keys), and the session admits a device only with a valid binding. The session still receives the tunnel peer's node key and requires the node key in the login to be that key. A per-relay allow-list of wallet key hashes is the registry's `ErrNotAllowed` (PRE-039). The package imports the standard library, `domain/mailbox`, `domain/party`, `domain/relaybind`, `domain/relayregistry` and `ports/relayport`, and nothing else of this module (SEC-009, `archtest`).

The version 1 session requirements that name the access list (IF-005, OUT-025, PRE-021, SEC-020, SEC-021, SEC-024, SEC-025, OUT-026, PRE-020, PRE-022, OUT-029, OUT-033, INV-012) are withdrawn or amended where they stand; this section is what holds. The requirements of the version 1 session that do not depend on the access list (OUT-027, OUT-028, OUT-030 to OUT-032, OUT-034, PRE-023, SEC-022, SEC-023, INV-013, INV-014) hold unchanged for the version 2 session, with "device" for "party" (the mailbox is the device's, ADR 0014 decision 10).

### Interfaces (session)

- **SPO-Xmailbox-IF-015** `relay.New(Config)` takes narrow capabilities only: `relayport.MailboxWriter`, `MailboxReader`, `MailboxAcker` (acks only), `MailboxRetractor` (the compensation of the session's own put), `MailboxUsageReader`, a `Registry` (the union of `RegistryReader`, `Registrar`, `Revoker`, `ExpectedSenderReader` and `ExpectedSenderWriter`; the sweep is the sweeper's), a `*Guard`, `Clock`, a random source for nonces, the relay's own node key, a `mailbox.ValidOpenQuota`, a `ValidLimits` and a `relaybind.Policy` (which must be the registry's own: obligation 12), and **`MailboxRevoker` for exactly one use**: the purge of a revoked device's queue in the revoke path (`revoke.go`). The fetch and ack handlers hold no revoker and a test parses the sources: only `revoke.go` and the server's constructor name `MailboxRevoker` or the field `purge`; no non-test source outside `sweeper.go` names `MailboxExpirer` or `RegistryExpirer`, and none names the whole store or the whole registry. `New` refuses a missing capability, a zero relay key, a quota or limits that were not validated and a policy outside the ADR's (`relaybind.Policy.Validate`). The store is given the ADR 0013 part of the open quota as a `mailbox.ValidQuota` (validated for one party: the open-mode rule, devices times the queue bound, was checked by `OpenQuota.Validated`). `Limits` gains `UnauthBudget` (the whole unauthenticated phase; ceiling 5 s, `HandshakeTimeout` is gone), `MaxUnauthConns` (16), `MaxRevokes` (8), `MaxConnsPerDevice` (2) and `MaxConnsPerWalletKey` (16: PRE-056), each a ceiling that a server may only tighten (`MaxConnsPerKey` stays the bound of the tunnel node key); `MaxPutsPerMinute` counts a **wallet key** summed over its devices; `MaxConcurrentPuts` counts a device. `Server.CloseDevice(fp)` and `Server.CloseKey(key)` end the live sessions of a device or of a wallet key with the `binding` code; they are what a future reload calls and what a verified revoke calls (SEC-067). `NewSweeper(...).WithRegistry(reg)` adds the registry's sweep (OUT-087).

### Outputs (session)

- **SPO-Xmailbox-OUT-082** A session is: Challenge, then before login at most 8 Revoke frames and one Auth, all within `UnauthBudget`, then AuthOK, then requests. The relay draws a fresh nonce for the connection (a source that fails ends the session before a Challenge) and sends `Challenge{2, 2, nonce, own node key, time}`; it starts at `StageForOffer(V2)` and moves its stage only with `Stage.AfterRevoke` (for every Revoke that decoded, verified or not) and `Stage.AfterAuth` (once the login succeeded), so a second Auth, a Revoke after login, a version 1 frame and every frame before login are refused by the decoder of the stage (the codes of PRE-053). A login: the device fingerprint is computed once from the presented keys (SEC-064); the signed bytes must commit to the full hash of the statement presented and to the hash of the list received (SEC-065); the binding is verified with `relaybind.VerifyBinding` with the registry's policy and the relay's time; it is registered (`Register`: the registry admits it against its tombstones, its lifetime policy and caps, and decides the allow-list after that); the expected-sender list of the Auth is stored with `SetExpectedSenders` on EVERY successful login, an empty list included; the `AuthOKV2` carries the limits and the `until` of the binding **as the registry recorded it** (a re-presentation of an older statement answers with the stored one). The session then lives no longer than that `until` (OUT-085). The device is counted connected for the eviction guard from before it is registered until its last session ends (INV-036).
- **SPO-Xmailbox-OUT-083** A Revoke is verified with `relaybind.VerifyRevoke` (wallet-signed) or `VerifyDeviceRevoke` with the keys of the frame (device-signed), recorded through `Revoker.Revoke`, and answered with `RevokeResult`: `recorded` when the tombstone is recorded, when it is recorded although a later step failed (the result says so), and when the binding was deleted but the tombstone could not be recorded (`ErrTombstoneUnrecorded`, which the log notes as the reason `unrecorded`); `refused` when verification fails (a signature, a statement that does not parse, a not-before beyond relay time plus the skew), when the registry refuses a revoke that invalidates nothing (`ErrTombstoneFull`, `ErrRevokeRate`: the limited share and the relay-wide rate), and when the registry fails without storing the tombstone. A revoke whose stored binding is not invalidated (older than the binding, a replay) records the tombstone and changes nothing else: no session ends and no mail goes. Request ids of Revokes are unique on the connection like every other id (PRE-023). The operator log gets an `EventRevoke` with the key hash, the device the revoke names, the status, the number of devices it invalidated and a fixed reason class.
- **SPO-Xmailbox-OUT-084** The Put frame is `PutV2`: the recipient is the pair (wallet key, device) of the header and the sender's wallet key is the one bound at login, never a frame field. A put is decided in this order, and the body is consumed whatever the decision except the first: an envelope above the announced limit is too_large and the connection closes without reading the body; the sender's own binding is looked up again, and a sender whose binding is gone (expired, revoked, replaced under another key) is refused and the connection closes with the `binding` code; the attempt is then counted against the puts a minute of the sender's wallet key (SEC-070), and a sender over that budget, or over the puts in flight of its device, is busy whatever the recipient; a recipient device that has no served binding, or one under another wallet key than the put names, is `unbound` (status 8, and no more: the answer is the same for a device never bound, expired, revoked and bound elsewhere), and a registry that cannot answer about it is `unavailable`; then the open-mode admission (OUT-086), then the store. After a stored put the whole decision is made again (sender still served, recipient still bound to that key); when a clause fails the entry is taken back with the sender's own retraction, the stranger accounting with it, and the sender is told refused (or, if its own binding ended, the `binding` code follows). The store keeps the entry by the recipient's **device** fingerprint and the sender's device fingerprint, as before (ADR 0014 decision 10); the wallet key is an admission and quota index.
- **SPO-Xmailbox-OUT-085** Fetch and Ack serve the device bound at login and no other (SEC-022). The session looks the device up again, with the registry, on every Fetch, every Put and every Ack, after every wake of a long-poll, immediately before items are sent and before an empty reply at the end of a wait, and ends with the `binding` code when the device is no longer served under the wallet key it logged in with (revoked, expired, invalidated by a tombstone whose file is still there, replaced under another key); nothing is read, listed or acknowledged for it after that. A renewal of the binding under the same key extends the session (the `until` is read again). Every deadline of the session ends no later than the binding's `until` (mapped to the process clock at login and when it is renewed): a session that is idle at the binding's end closes with the `binding` code and the reason `expired`.
- **SPO-Xmailbox-OUT-086** Open-mode admission and the stranger book. A put is admitted with `ValidOpenQuota.Admit` from the store's usage, the wallet key's total as a sender (the sum of the `SenderBytes` of all its devices, read from the store, plus the bytes of the key's puts that were admitted and have not ended: they are reserved under the book's lock before the store is called and released when the call ends, so two puts of one key at once cannot both pass the bound, and a put that has committed but not yet ended is counted twice, which errs toward refusing) and the recipient's stranger counters; the store then decides the bounds of ADR 0013 again under its lock. "Listed" is decided by the caller (SEC-066). **Where the counters live** (a choice the ADR left open): in the session layer, in memory, not in the store. The ADR's table keeps the mailbox store keyed by device and says the counters per wallet key are not the store's, so the class of an entry is not stored with it. The server keeps, per recipient device, one record for each entry its queue holds (sender device, mid, size, and whether the sender was a stranger when the put was made). It releases them on the events that remove entries: an ack (every copy of the id), a retraction of the session's own put, a purge on revoke, and the retention sweep, which the session does not see: at each admission for a recipient the book is compared with the store's own pair counters, and the oldest records of a sender above what the store still counts for that pair are dropped. After a restart the book is empty and is rebuilt at the first admission for each recipient from a listing of its queue, and every entry it rebuilds counts as a stranger's, because the class an entry was put under is not stored. That is an approximation for entries put before the restart, and it errs toward stranger only: a stranger may be answered `full` until the recipient acks, and strangers never hold more than the allowance because the relay forgot (a listed sender is not limited by the stranger counters). The rebuild reads the store only. A sender whose every entry is a second copy of an id is not seen by the rebuild (the listing shows the first copy of an id only); the store's own bounds still apply to those copies. A retry of a put the book holds is not counted again, so it is answered `duplicate` and not `full`. A stranger's put reserves its entry and bytes before the store is called and releases the reservation when the call ends, so two concurrent strangers cannot both pass the allowance. The lock that guards the book is held across the store reads of an admission; what bounds that wait is INV-037, and the residual is stated under "Accepted residuals of the session".
- **SPO-Xmailbox-OUT-087** The `Sweeper` runs `RegistryExpirer.Sweep` on every pass beside the mailbox sweep (`WithRegistry`): bindings past their `until`, bindings a stored tombstone invalidates, idle bindings the guard allows and expired tombstones (OUT-066, OUT-079). The two sweeps are independent: a failure of one does not stop the other, and the first error is returned. Each pass logs `EventSweep` (entries removed) and `EventRegistrySweep` (bindings and tombstones dropped); a failure is `EventSweepErr` with the reason class `store` or `registry` and no text. Live sessions need no call: they look their binding up on every request.
- **SPO-Xmailbox-OUT-088** With the durable registry (`adapters/bindingstore`) a restart of the relay keeps the bindings, the tombstones and the expected-sender lists (OUT-069 to OUT-071): a put to a bound device that is offline after the restart is stored; a revoked binding is refused after the restart.

### Preconditions and failures (session)

- **SPO-Xmailbox-PRE-053** Login failure to code, each with a fixed reason class in the log and a close: the Auth fails with `auth` (1, no text) for a claimed fingerprint that is not that of the presented keys, a weak device key, a node key that is not the tunnel's, and a signature that does not verify (which covers a changed relay key, nonce, time, client node key, binding hash or sender-list hash); with `binding` (7) for a statement or key that does not parse, a key that is not the statement's, a device in the payload that is not the device of the presented keys, an expired binding, one not valid yet, a lifetime over the relay's policy, a binding at or before a tombstone, and one older than the stored one for the key and device; with `not_allowed` (6) for a wallet key that the operator's allow-list does not hold, **decided after the binding was admitted** so that an invalid binding is `binding`; with `limit` (3) for `ErrLimit` and every error wrapping it from `Register` (devices per key, a full registry with nothing evictable, the new-binding rate, the key-change rate); and with the "not now" code (5, `shutting down`) when the registry cannot answer (a closed registry, a failing disk). A failed login replaces no list and leaves no binding. A put to a device with no valid binding to the key is the status `unbound` (OUT-084). Before login a Put, Fetch, Ack, a relay-only frame, an unknown type and a malformed frame are `protocol` (2); a version 1 Auth is `version` (0).
- **SPO-Xmailbox-PRE-054** Unauthenticated limits: the whole connection before the AuthOK has `UnauthBudget` (5 s by default and at most), revokes included: slow revokes do not renew it, and the connection closes with `limit` (3) when it ends, reason `handshake`. At most `MaxRevokes` (8) Revoke frames are accepted, **the refused ones counting**; the ninth ends the connection with `limit`, reason `revokes`. At most `MaxUnauthConns` (16) connections hold an unauthenticated slot at once, relay-wide; the next is refused at accept with `limit` and no Challenge; a login (or the end of the connection) frees its slot at once. The per-node-key limits (2 live, 6 a minute) stay and are no abuse bound: a node key costs nothing.
- **SPO-Xmailbox-PRE-055** A Revoke that decoded and does not verify is answered `RevokeResult` with `refused` and the connection stays open until the count of PRE-054 is spent; a frame that does not decode ends the connection and is not a refused Revoke. A refused revoke records nothing and ends no session.
- **SPO-Xmailbox-PRE-056** Connections follow the identity (finding L1 of the session review). A logged-in session counts against the live connections of its device (`MaxConnsPerDevice`, 2) and against those of its wallet key summed over its devices (`MaxConnsPerWalletKey`, 16: 8 devices of 2); both are ceilings that a server may only tighten, and both are in the bounds table of ADR 0013 and ADR 0014 decision 5. The check is made at login, after the signature, the binding and the fingerprint verified and before anything is registered, and a login over either bound is answered `limit` (3) with the reason `limit`, and registers nothing and replaces no list. The place is held from that point to the end of the session and is given back on every exit: a failed login, a closed stream, a revoke, a shutdown. A connection that has not logged in counts against neither (it holds an unauthenticated slot, PRE-054). The per-node-key bounds of PRE-054 stay and are no abuse bound, because a node key costs a peer nothing; these follow the identity the peer had to prove. The field of the key bound is `MaxConnsPerWalletKey` because `MaxConnsPerKey` is the bound of the tunnel node key.

### Security (session)

- **SPO-Xmailbox-SEC-064** One fingerprint for both checks (obligation 10): the session computes the device fingerprint once, from the two keys the login signature authenticated, and that one value is what `VerifyAuthV2` and `relaybind.VerifyBinding` take. A fingerprint field that differs from it is the `auth` code and nothing of the claimed device is read. The theft scenario: a valid binding for device D, signed by D's wallet key, presented on a connection that the device keys of E authenticated, is refused with `binding` (the statement names D, not E), registers nothing for E and leaves D's binding and list untouched; presenting D's keys with E's signature is `auth`.
- **SPO-Xmailbox-SEC-065** The relay's own values (obligations 7 and 11): the relay's key, the nonce (fresh for each connection, drawn from the random source) and the time sent in this connection's Challenge, and the tunnel's node key, are what the signature is checked against, never anything the frame says (it has no such field); an Auth captured on one connection fails on another. The signed bytes commit to the full hash (`FullHash`, signature included) of the statement **presented in this Auth**, not of the one the registry stores: after a renewal by re-signature the client signs the hash of what it presents and is admitted, the stored statement stays, and a client that signs the stored statement's hash while presenting another encoding is refused. They commit to `SendersHash` recomputed by the relay from the list it received: a list changed after signing is refused.
- **SPO-Xmailbox-SEC-066** "Listed" (obligation 4) is decided from the wallet key the session's verified binding names against the recipient's stored expected-sender list, read from the registry at the put: never from a field of a frame. Every device of a listed wallet key is listed; a device is not a stranger because its own fingerprint is on no list; a list replaced at the recipient's next login classifies later puts, and puts already admitted keep the class they were admitted under (OUT-086).
- **SPO-Xmailbox-SEC-067** A verified revoke acts on the invalidated devices (obligations 2 and 14): for every binding the registry's result lists, **a partial result returned with an error included**, the session ends the device's live sessions with the `binding` code at once (also in a long-poll or a blocked write) and then deletes its queue through the narrow `MailboxRevoker` and drops its stranger accounting; on any error from `Revoke` other than `ErrTombstoneUnrecorded` (which is not a refusal) it asks the registry again about the devices the revoke could have taken away, so a binding that is gone is not left with a session and a queue; **which devices that may be, and which errors exclude it, is SEC-069**. A revoke that invalidates nothing ends nothing. Sessions are closed first, so nothing reads the queue while it is deleted; a put that began before the revoke and commits after the purge is taken back by its own check after the commit (OUT-084). The session does not depend on this call for revocation: SEC-025's re-check holds on every operation (OUT-085).
- **SPO-Xmailbox-SEC-068** The operator log names the wallet key hash and the device fingerprint, which are public, and never a statement byte beyond them, an envelope byte, a COSE key or text a peer or an error chose. The `Event` type has no byte slice, map, pointer or free string; every reason is one of a fixed set of classes (IF-006).
- **SPO-Xmailbox-SEC-069** What a revoke may purge (finding H1 of the session review, proved before the fix). A queue is deleted only for a device the revoke really took away: (1) every device the registry returns as invalidated, a partial result returned with an error included (SEC-067); (2) in the error fallback only, a device that the registry **served before the revoke ran** (the session looks up the device the revoke names, or for scope `all` the devices of its key, before it calls `Revoke`), that is **not served after it**, and that is the revoke's own: its scope is `device` (signed by that device's own keys) or the wallet key it was served under **equals the revoke's key**; (3) nothing at all on an error that touched no storage (`ErrRevokeRate`, `ErrTombstoneFull`, `relaybind.ErrUnverified`, `relaybind.ErrRange`) or on the end of a context (`context.Canceled`, `context.DeadlineExceeded`), nothing for a registry that could not answer before the call, and nothing for a device that is served again. The attack this closes: an unauthenticated peer with a throwaway wallet key spends the relay-wide cap on non-invalidating revokes (PRE-050) or fills the limited share of the tombstone table, then sends a pair revoke naming a victim's device whose binding has lapsed (expired, swept or evicted); the registry refuses it, and the first fallback, which purged any named device that was not served, deleted the victim's queue. A lapsed pair's stored mail stays until retention and is served again when a fresh binding arrives (ADR 0014 decision 5), and an expiry, a sweep or an eviction never purges (the session ignores the registry's evictions). A device-signed revoke names the fingerprint recomputed from the keys in its frame, so an attacker's device-signed revoke names the attacker's own device and leaves the victim's alone.
- **SPO-Xmailbox-SEC-070** Every put attempt that reaches a decision counts against the sender's per-minute put budget (finding L2 of the session review): stored, duplicate, full, busy (also the busy of the puts in flight), refused, unbound, unavailable, too_large and bad_hash alike. The count is made before the answer about the recipient is given, so a sender over its budget is told `busy` whatever the pair, and the question "is this (wallet key, device) bound here?" cannot be asked faster than the budget allows (120 a minute for a wallet key by default), not only as fast as the request and connection rates allow. An attempt that finds the window full adds nothing, so the window stays at its bound. A peer that wants more probes needs more wallet keys, and a new wallet key needs a binding, which is capped (PRE-036).

### Invariants (session)

- **SPO-Xmailbox-INV-036** The eviction guard of the registry is `Guard.Evictable`: "queue empty and not connected". It is cheap (a map read and a listing of at most one entry), reads only the mailbox store, never calls a writer of the registry (the registry calls it with its writers serialised: a call back into one would wait for itself) and answers `false` for a store that cannot answer, and for a nil guard. The server marks a device connected from before it is registered until its last session ends. A full registry therefore evicts the least recently authenticated idle binding with an empty queue, never a connected device or one that holds mail, and refuses a new device with `limit` when nothing is evictable (PRE-034, PRE-035, PRE-051).
- **SPO-Xmailbox-INV-037** The store and registry reads of an admission, which run under the stranger book's lock (OUT-086), honour the session's own deadline (finding L3 of the session review). An admission runs under a context with the deadline of the put: the earliest of `BodyTimeout`, the end of the connection's lifetime and the end of the device's binding, and the session's own cancellation. The wait for the lock gives up at that deadline, and so does every read under it; an admission that does not finish is answered `unavailable`. What bounds the hold of the lock, stated exactly: a store or registry that honours its context returns at the deadline and the lock is released then; one that ignores its context (a stalled disk) is bounded only by its own I/O, and until it returns the lock stays held, but no other session waits for it past its own deadline. The bookkeeping releases that read no store (the forgetting of an entry after an ack, a retraction or a purge) give up at their own deadline and are repaired by the book's comparison with the store at the next admission; only the release of a reservation at the end of a put, which must run, waits for the lock without a deadline, for at most the holder's. The residual is stated under "Accepted residuals of the session".

### What the session does not do, and what the client must

- The expected-sender list is fixed for the connection that presented it (obligation 9): the session reads the stored list at each put and the list changes only at a login; **the client reconnects when its registry's set of expected senders changes** (work package 7). The client halves of the version 2 protocol (the auth signer with the binding, `unbound` to `ErrNoRoute`, pending revokes re-sent on every connection) are built by work package 7, "The mailbox client, version 2" below; its end-to-end tests run against the real relay.
- The session has no `Lookup` and no `Directory` frame (ADR 0014 decision 6).
- The operator configuration and the relay binary that wires `Server`, `Guard`, the registry and the `Sweeper` are built by work package 10: "The relay configuration, the relay binary and several relays" below (the version 1 file with the access list is deleted).

### What the relay binary and configuration must do

The session is pure over ports and cannot check these; the binary and the configuration (work packages 10 and after) must. Each is a rule the session relies on.

- **Quota and registry agree on the number of devices.** `OpenQuota.MaxBoundDevices` must equal the registry's `MaxBoundDevices`. The global quota reserves room per bound device (OUT-056, PRE-031); a registry that holds more devices than the quota reserves for breaks the rule the quota was validated for.
- **Retention is one number.** The session's `Limits.RetentionSeconds` (announced in AuthOK) must equal the `Sweeper`'s retention.
- **The policy is the registry's.** `Config.Policy` must be the `Policy` of the registry's own configuration (obligation 12).
- **The eviction guard is built over the same mailbox store, before the registry opens.** `relay.NewGuard(store)` over the store the server writes to, its `Evictable` set in the registry's configuration before the registry is opened, and the same `*Guard` given to `relay.Config.Guard`. A guard over another store, or one set after `Open`, evicts bindings whose queue is not empty or whose device is connected (INV-036).
- **The sweeper runs with the registry.** `NewSweeper(...).WithRegistry(reg)` runs for as long as the server does: expired bindings, bindings a stored tombstone invalidates, idle bindings and expired tombstones are dropped only by it (OUT-079, OUT-087).

What the client must do (built in work package 7, "The mailbox client, version 2" below: OUT-090, OUT-089, OUT-093):

- **Pending revokes go out on every connection**, before the Auth, until the revoked binding's `until` (ADR 0014 decision 8). A `refused` that the relay-wide cap on non-invalidating revokes caused (PRE-050) is **retryable, not final**: the client keeps the revoke pending and sends it again on its next connection. Only a verification failure of its own statement is final.
- **The client signs over its own tunnel node key.** The login commits to the node key of the tunnel peer; a client that signs another key sees an authentication failure (`auth`, no text), not a distinct "tunnel key" error, because the relay says nothing more (PRE-053).
- **Obligation 9:** the client reconnects when the set of expected senders in its party registry changes. **Discharged: OUT-093.**

Before any open mode (ADR 0014 decision 5, `admission = "open"`):

- The per-device and per-wallet-key connection bounds (PRE-056) are built and held; the connection and request rates alone were no bound on the identity.
- The accepted residual below, that any peer can keep the relay-wide cap for non-invalidating revokes empty, must be weighed.

### Accepted residuals of the session

- **A peer can keep the relay-wide cap for non-invalidating revokes empty.** The cap (PRE-050: 60 an hour, burst 10) is spent by unauthenticated throwaway-key revokes that bind nothing, so a legitimate revoke that invalidates nothing (a device-signed revoke of a device that is not bound here, a wallet revoke of a lost device that never bound at this relay) is answered `refused` while it is empty. Invalidating revokes are never rate-limited (PRE-049), so the revoke that matters, of a bound device, always lands. The client keeps such a revoke pending and sends it again (above). SEC-069 makes sure the refusal costs nobody a queue.
- **A slow disk can serialise admission.** The stranger book's lock is held across the store reads of an admission (OUT-086), and a store read can wait behind the store's fsyncs. With a store that honours its context, the wait ends at the session's deadline (INV-037); with one that ignores it the lock is held until the store returns, bounded only by the store's own I/O, and every put that needs admission answers `unavailable` at its own deadline meanwhile; an ack gives up its release of the stranger accounting at its deadline too (the book repairs itself at the next admission, `reconcile`). What still waits for the lock without a deadline is the release of a reservation at the end of a put (`finish`, which must run) and the test hook that reads the counters: a put that has been admitted is held at its end for as long as the holder of the lock is in the store. Fetches do not take the lock. The design is kept: the book is in memory, small and rebuilt from the store, and a per-recipient lock would not help a disk that is slow for every recipient. A slow store is an operator's fault to fix.
- **A wallet key can reset its total as a sender.** The total of a wallet key as a sender is the sum of the `SenderBytes` of the devices it has bound now (the registry's `Devices`), read from the store at each put (OUT-086). A device that the key revokes (a device-signed revoke by that device, or the key's wallet revoke) leaves that sum although the entries it put into other devices' queues are still there. A key can therefore put up to its bound with one device, revoke it, bind another device and put up to the bound again before the first entries are acknowledged or swept. This is bounded by what a binding costs (the new-binding cap of 60 an hour for the whole relay, and the 4 key changes a day of a device) and by the per-recipient bounds (queue, pair, stranger allowance), which do not depend on the sender's device or key. It is no way past the bounds of a recipient.

### Choices that go beyond the ADR text (work package 6)

- **The put addresses the recipient by the pair (wallet key, device)** and the store by the device (ADR 0014 decision 2 and 10): `unbound` for a device that is not bound to that key. The sender's key is never in a frame.
- **The stranger counters are in the session layer** (OUT-086), not in the store: the ADR's table keeps the store essentially unchanged and puts the per-key counters elsewhere; a durable marker in the entry name would have changed the store's names, its recovery and its contract suite for a figure that the book rebuilds approximately at a restart. The price is the approximation after a restart.
- **The wallet key's total as a sender is read from the store at admission** (the sum over its devices, at most 8) and the bytes of the key's puts in flight are reserved in the book with the stranger counters (OUT-086), so the bound has no overshoot. A put that has committed and not yet ended is in both figures; the error is toward refusing.
- **The policy is a field of `Config`**, taken by the composition root from the registry's own configuration, because the registry port has no accessor for it; the registry checks the lifetime again (PRE-046).
- **A session closed by a revoke is told `binding` (7), not `revoked` (4)**: the code that tells the client to sign a new binding. The code 4 is no longer sent by the session.
- **The binding's `until` closes the session** through every deadline, in addition to the re-check on each request (obligation 3 allows either).
- **Registry errors that are not the peer's fault are the "not now" code** (5), the only code the protocol has for it.

## The mailbox client, version 2 (ADR 0014 work package 7)

These requirements amend "The mailbox client (work package 6)" for protocol version 2 (the only version, "Protocol version 2" above). `internal/adapters/mailbox` keeps everything of work package 6 that does not name the login: hash-verified delivery, the checks of an Items reply, pacing of repeated pages, the dial limiter, the backoff, the stale-connection rule, rotation at the read bound, `Close` interrupting every wait and dropping the queued ciphertext, and the unacked list. What changes is the login, the addressing of a put and what the caller can set. The client holds no key of any kind: the device key is behind `relayport.AuthSigner`, and the wallet key signed the binding and the revokes elsewhere (`app/relaybinding`); the client holds their bytes. Its non-test sources gain one import, `domain/relaybind` (SEC-031). Time: the injected clock is also read for the window of the binding, the window of a pending revoke and the renewal margin.

### Interfaces (client, version 2)

- **SPO-Xmailbox-IF-016** `mailbox.New(Config)` for version 2 takes, besides the dialer, the pinned relay key, the client's own node key, the `Clock`, the `Limits` and the optional `EventSink` of IF-009: the device's public keys (`Device`, `wire.DeviceKeys`) and its fingerprint (`Self`, which must be their fingerprint, or `New` refuses); the `Binding` to present (`Statement` and `Key`, the COSE_Sign1 and the COSE_Key as `app/relaybinding` returns them); the expected-sender list (`Senders`, wallet key hashes); a `Resolver` from the party fingerprint an item is addressed by to the recipient's `Route` (the wallet key and the device, with a boolean that is false for a party that has no wallet key); an optional `RevokeBook` of pending revokes (IF-018); a `relaybind.Policy` (the zero value is the ADR's default) and a `RenewMargin` (zero is 14 days; negative is refused); and a `relayport.AuthSigner` of the version 2 form (IF-017). It refuses a missing dialer, signer, clock or resolver, a zero key or fingerprint, a fingerprint that is not that of the device keys, a negative margin and a policy outside the ADR's. It does not dial. **The binding is checked at construction as the relay would check it (PRE-057), so a client never dials with a binding the relay would refuse.** `BindingUntil()` is the end of the binding the next connection presents, so that the caller can renew. The client is a `ports.EnvelopeSender`, `ports.EnvelopeReceiver` and `ports.EnvelopeAcker`, and passes the `ports/porttest` suite against the real version 2 relay with the real store and a registry (the world of `internal/adapters/mailbox` and of `test/multiparty`).
- **SPO-Xmailbox-IF-017** The auth signer is `relayport.AuthSigner`, one typed method: `SignMailboxAuth(relayKey, clientNodeKey party.NodeKey, nonce [32]byte, relayTime int64, bindingHash, sendersHash [32]byte) ([64]byte, error)`. It has no version and no fingerprint argument: the implementation builds the labelled array of OUT-053 with `mailbox.AuthBytesV2` from these values and **its own fingerprint** and signs nothing else (it refuses a relay time outside 0 to `MaxTime`, and a destroyed identity signs nothing). The real implementation is `envelope.Local.SignMailboxAuth`, next to the device-revoke signer; a test shows that the signature is the Ed25519 signature of those bytes by the device key, that it verifies with `VerifyAuthV2` as the relay checks it, and that it fails for any other value of any field of the array.
- **SPO-Xmailbox-IF-018** The client's setters and the revoke port. `SetBinding(Binding)` takes a renewed binding, checked as `New` checks the first (PRE-057) and refused with `ErrBindingInvalid` when its `from` is earlier than the one held; `SetSenders([]WalletKey)` takes a changed expected-sender set (OUT-093); both are safe to call from another goroutine. `RevokeBook` is the caller's list of pending revokes: `Pending() []Revoke` (oldest first) and `Result(Revoke, RevokeOutcome)`; the client persists nothing and calls them **only on the goroutine that holds its operation slot**, `SendRevokes` included, so one client never makes two calls at once and a book used by one client needs no lock for them. A `Revoke` is a device-signed one (`Keys`, `NotBefore`, `Signature`) or a wallet-signed one (`Sign1`, `Key`), with the `Until` of the binding it revokes. `SendRevokes(ctx) (RevokeReport, error)` (OUT-090) is the revoke-only exchange.
- **SPO-Xmailbox-IF-019** **The revoke-only sender.** `NewRevokeSender(RevokeConfig)` takes the dialer, the pinned relay key, the `Clock`, the `RevokeBook` (all four required), an optional `relaybind.Policy` (checked as `New` checks it), the `Limits` and the optional `EventSink`, and **no binding, no auth signer, no expected senders and no resolver**. It does not dial. Its only operations are `SendRevokes(ctx) (RevokeReport, error)`, the client's revoke-only exchange of OUT-090 with every check of the handshake (the dialer's key and the Challenge's relay key are the pinned key, version 2 only, bounded reads, the dial limit, the backoff, `Close` interrupting a dial, a stall or a wait), and `Close`. Its connections end after the last answer: it has nothing to present, the signer it holds inside refuses, and the connection is marked so that the handshake stops before the signature, so it cannot send an Auth or sign anything. It is how a new device with no binding sends the wallet-signed revoke of a lost device (`spo party relay forget --lost`, ADR 0014 decision 8): against the real relay the revoke is recorded and the lost device's next login is refused with `binding`.

### Outputs (client, version 2)

- **SPO-Xmailbox-OUT-089** The handshake of version 2 runs in this order and closes the connection at the first failure: the binding the client holds is inside its window on the injected clock (else no dial, OUT-094); the key the dialer reports for the peer equals the pinned relay key; the Challenge is read at `StageV2PreAuth` and names the pinned relay key (the signer is never called and no revoke is sent otherwise); the range holds version 2 (`Versions.Choose`: **version 2 only**, a Challenge that offers only version 1 is `ErrVersion`); the skew is measured (as OUT-040); the pending revokes are sent (OUT-090); the signer is called with the pinned relay key, the client's own node key, the Challenge's nonce and relay time, the full hash of the canonical binding presented and the hash of the canonical sender list presented, never a value of the Challenge but the nonce and the time; the `AuthV2` is sent (the fingerprint, the signature, the device keys, the binding bytes as given and the canonical list); the answer must be an `AuthOKV2`. In its limits the AuthOK can only **tighten**: the envelope limit is the smaller of the client's and the relay's, and the other announced values are not used. Its `until` is **recorded**: it must be at most the `until` of the binding presented (a relay records the statement it was given, or one that ends earlier) and not already past by the client's clock, else the connection is closed as a protocol violation; and the connection is not used past it (the relay closes the session then): a connection that ends sooner than its lifetime is replaced by the lifetime rule. A binding within the renewal margin of its end is reported (OUT-094). The whole handshake, the revokes included, is bounded by `HandshakeTimeout`.
- **SPO-Xmailbox-OUT-090** **Pending revokes** (ADR 0014 decision 8). At every connection the client asks the book for its list and, before the Auth, sends the revokes in the frame of their kind, each with its own request id (the connection's counter), and reads each `RevokeResult`, which must carry the revoke's id. A revoke that the client's own check refuses is not sent and is reported `invalid` (final): its statement does not parse or verify (`relaybind.VerifyRevoke`, `VerifyDeviceRevoke` with the client's clock and policy), its kind is unknown, or its `Until` is not set; one whose `Until` has passed is `expired` (final; the end is inclusive, so a revoke is still sent at its `until`); one whose not-before the relay would still call future is `deferred` (not final). At most `MaxRevokesPerConn` (8) are sent on a connection, **the least recently sent first**: the client remembers, in memory, the exchange at which it last sent each pending revoke (a revoke counts as sent when its frame goes out, whatever the relay then does); one never sent goes before every one that was, and equal ones go in the book's order (oldest first). What the relay answered does not change the order, so no answer can hold a revoke back. Those beyond the bound are reported `deferred`. **What is guaranteed:** with a fixed list of N pending revokes, every one of them is sent at least once in every ceil(N/8) consecutive exchanges that reach the revokes (with N of 8 or fewer, on every connection), whether the relay records them all, refuses them all, mixes, or always answers the same revokes the same way; an exchange that fails in the middle counts the revokes it sent and not the others. A book that adds new revokes faster than eight a connection can delay the older ones, since a never-sent revoke goes first. The memory holds only the revokes pending at the last exchange, so it is no larger than the book's list. A `recorded` answer and a `refused` answer both leave the revoke pending (`recorded`, `refused`: not final): **a relay may lose its state, so the revoke is sent again, as above, until the revoked binding's `until`**, and a refusal can be the relay-wide cap on revokes that invalidate nothing or a full table (ACCEPTED RESIDUALS of the session), which pass; only the client's own check ends a revoke. The signer is called only after the last answer. A frame that is not the answer (a wrong id, another type, a status of 1 or above 2, garbage, a stall, an Error) fails the connection and drops no revoke. `SendRevokes(ctx)` does the same on a connection of its own and ends it after the last answer **without a login: no signature is made and no Auth is sent**. It asks the book for its list only once it holds the operation slot (IF-018), and does nothing and dials nothing when the list is empty. It presents no binding, so a binding that has lapsed does not stop it, and it does not serve the wait that a refused binding or key set (OUT-092); it waits out the dial limit and the backoff of every other failure like `Receive`, and returns `ports.ErrClosed` after `Close` and the context's error when it ends. It returns a `RevokeReport` with one result per revoke the book listed (the revoke and the outcome the book was told, in that order; `Count(outcome)`), so a relay that refused them all is a nil error and a report that counts them `refused`; with an error the report holds what was learnt before it. It is the last step of "forget this device"; a device that has no binding it may present sends with a `RevokeSender` (IF-019).
- **SPO-Xmailbox-OUT-091** **A put of version 2** is `NewPutV2Of` with the recipient's route: `Send(ctx, to, envelope)` asks the resolver for the wallet key and device of `to` (an unset device is `to` itself) **before anything else is done for the put**; a party with no wallet key, or a zero wallet key, is `ports.ErrNoRoute` with the reason `no_wallet_key` ("it is reachable by file or direct connection only") and an event, with no dial: the cold-key rule and the registry's wallet-key field are the caller's (work package 8). The put statuses map as OUT-038 says, and `unbound` (the device has no valid binding to that key, expired or revoked included) is `ports.ErrNoRoute` (not `ErrRefusedByTransport`: the recipient may bind later, so the item stays queued) with the reason `unbound` and the status in the event; the session goes on. A status above 8 is a violation (PRE-025). The wire answer for a device bound under another key is `unbound` too, so the client cannot tell the two apart and does not try.
- **SPO-Xmailbox-OUT-092** **The login codes `binding` and `not_allowed`.** An Error frame with the code 7 `binding` (the binding is invalid, expired or revoked: a new one must be signed), at login or in the middle of a session (the relay ends a session whose binding was revoked or has ended with it), is `ErrBindingRefused` (also `ErrRelayError`, never `ErrUnreachable`), with the reason `binding`; the code 6 `not_allowed` (the operator's allow-list does not hold this wallet key) is `ErrNotAllowed` (also `ErrRelayError`), with the reason `not_allowed`. `Send` returns `ports.ErrNoRoute` wrapping the sentinel with a fixed text that says what to do; `Receive` returns the sentinel and does not retry it (it is not transient); an event `failed` names the reason and the code and carries the **longest backoff** (`BackoffMax`), because only a new binding or the operator can change the answer; nothing is dialled inside the backoff (a `Send` fails at once, a `Receive` sleeps it out), so a refused binding is never retried in a tight loop. **A `Send` inside that backoff still says why:** the client remembers the refusal that set the wait (until `SetBinding`, a login, or a later failure replaces it), and such a `Send` is `ports.ErrNoRoute` wrapping the same sentinel with its reason (`binding`, `not_allowed`, or `binding_expired` for OUT-094), never `ErrUnreachable` with the reason `backoff`; it emits no new event. A `Receive` sleeps the wait out and then tries, so it returns the sentinel again rather than an unreachable relay. `SetBinding` ends the wait (OUT-094). Every other Error code keeps its class (OUT-038).
- **SPO-Xmailbox-OUT-093** **The expected senders (obligation 9).** The relay fixes the expected-sender list for the connection that presented it. When the caller changes the set (`SetSenders`), and the canonical set differs from the one the open connection logged in with (a change that was reversed before the next operation is no change; the same set in another order or with repeats is none), the client **authenticates again at the next safe point**: the start of its next operation, or the next fetch of a `Receive` that is waiting (a request in flight is never interrupted); the connection is replaced, an event `reconnect` says why (the reason `senders`), the new login presents the new list and signs over its hash, and the relay stores it (`SetExpectedSenders` at every login). The reconnection is a connection like every other: it counts against the dial limiter (OUT-044), so a caller that changes the set at every call cannot make the client dial or sign more than `DialsPerMinute` times a minute, and a `Send` beyond it is `ports.ErrNoRoute` with the reason `dial_limit` and no dial. Against the real relay the effect is the stranger allowance: a sender that was a stranger (16 entries) is a listed sender (the pair bound) after the reconnection.
- **SPO-Xmailbox-OUT-094** **The binding, its renewal and its end.** `SetBinding` replaces the binding the next connection presents; the open connection is left alone, the signer is not asked, and the client signs nothing with a wallet key itself. When the binding in use is within `RenewMargin` of its end (at the margin itself too) and no newer one was set, an event `renew` with its end is emitted at each connection; a newer binding silences it. **A binding that has expired by the client's own clock, or is not valid yet by it, is never presented:** the client does not dial; `Send` is `ports.ErrNoRoute` wrapping `ErrBindingRefused` (not `ErrUnreachable`), also inside the backoff that follows (OUT-092), and `Receive` returns it, with the reasons `binding_expired` and `binding` and the longest backoff; `SetBinding` with a binding that is valid now ends the wait and the next operation dials. The client's check of the binding and the relay's are the same pure function, so the relay's `binding` code remains only for what the client cannot see: a tombstone, the relay's own tightened policy and the relay's clock (the sentinel is the same).
- **SPO-Xmailbox-OUT-095** **The sender list is canonicalised by the client**: sorted, unique and at most 64 (`wire.MaxSenders`), so that one set has one encoding and one hash. A caller with more than 64 distinct keys gets a documented, deterministic cut: **the first 64 distinct keys in the caller's own order are kept** (so the caller puts the keys that matter most first), the others are dropped, and an event `senders` says how many were dropped (at `New` and at each `SetSenders`). The hash given to the signer is that of the list sent.

### Preconditions and failures (client, version 2)

- **SPO-Xmailbox-PRE-057** The binding given to `New` and to `SetBinding` is checked with `relaybind` as the relay checks it: the statement and the key are not empty and parse (`ParseStatement`, `ParseCOSEKey`), `VerifyBinding` accepts it for the device fingerprint of the client (the payload's device is the client's own, the signature and the key are one wallet key's, the lifetime is inside the policy, the window `from - skew <= now <= until` holds on the injected clock) and, for `SetBinding`, its `from` is not earlier than the held one. A failure is `ErrBindingInvalid` wrapping the reason, and nothing changes. **What `SetBinding` takes besides a renewal:** the wallet key is not compared, so a binding of this device under another wallet key is taken when its `from` is not earlier than the held one's (the relay moves the device to that key, within its budget of key changes) and refused when it is, which is stricter than the registry (it refuses an earlier `from` only under the same key); a binding with the same `from` and an earlier `until` is taken (the relay takes it too, it is not older), `BindingUntil` moves back to it and the next login presents it. What it refuses is only the above: a binding that fails the checks of `New`, or one with an earlier `from`. A key that is not the statement's, a binding of another device, an expired binding, one not valid yet and a lifetime above the policy each have a test in which that check is the only thing that refuses.
- **SPO-Xmailbox-PRE-058** The version 2 handshake failures: a Challenge that offers only version 1 (or any range without 2) is `ErrProtocol` wrapping `wire.ErrVersion`, with the reason `version`, and nothing is signed or sent; an Error frame, a frame of the relay's side the stage does not allow, a version 1 shape (an AuthOK without an `until`, an AuthOK of version 1), an AuthOK whose `until` is 0 (refused by the decoder), beyond the binding's or already past, a RevokeResult for a request that was not made, and every malformed or oversized header are `ErrProtocol` (an Error frame is `ErrRelayError`); the connection is closed and, for `Send`, the item stays queued (`ports.ErrNoRoute`).

### Security (client, version 2)

- **SPO-Xmailbox-SEC-071** The client's signing surface is one typed call and it signs nothing with a wallet key. The signer gets the pinned relay key and the client's own node key (never the Challenge's), the Challenge's nonce and relay time, the full hash of the binding bytes it presents (`relaybind`'s `FullHash`, computed from the bytes it holds) and the hash of the canonical list it presents; a signature over any other binding or list does not verify at the relay (SEC-039). The wallet-signed bytes it holds (the binding, the revokes) were made by `app/relaybinding` and are only sent. The implementation on the local identity (`envelope.Local`) signs only the array of OUT-053 with its own fingerprint (IF-017).
- **SPO-Xmailbox-SEC-072** There is no downgrade at the client: it speaks version 2 only, so a Challenge that offers version 1 is refused before anything is signed (PRE-058), and a relay that sends frames of the retired version 1 (an Auth-shaped frame, a version 1 AuthOK, a Put) is refused by the stage decoder as a protocol violation. The hostile cases of the version 1 suite each have a version 2 counterpart (handoff, table).

### Invariants (client, version 2)

- **SPO-Xmailbox-INV-038** **Logout under ADR 0014** (the package documentation says it in full): cancel the contexts of the receive loop and of the sends; acknowledge what was handled (`AckContext`); `Close` the client, which interrupts every blocking operation (INV-019), drops the queue and returns `ports.ErrClosed` afterwards, `SetBinding` included; close the stream dialer given to the client (it stops the tunnel engine that holds the node key); destroy the local identity the signer signs with. The client persists nothing, so the binding and the pending revokes stay with the caller, untouched. **Forget this device:** fetch and handle the queue (a revoke deletes it), put the device's own revokes in the `RevokeBook` and call `SendRevokes` (a revoke is allowed before the Auth only, so it goes on a connection of its own and is not followed by a login that the revoke would make fail), then close as above, then delete the stored bindings; against the real relay the device's next login with the same binding is refused with `binding`. A device that has no binding it may present revokes another one with a `RevokeSender` (IF-019). A relogin needs no wallet: the client presents the same binding bytes at every connection and signs only through the typed signer, once per connection; the nonce and the signature differ per connection.

## Wallet-key identity on the client side (ADR 0014 work package 8)

What a workspace keeps and decides so that its mailbox client can be built: the routes from its party registry (`app/relayroutes`), its own binding, revokes and their times (`app/relayself`), and the commands of `spo party relay` (`adapters/cli`). The relay itself is not touched. The party's relay identity and the evidence check are [Xparty](./Xparty.md) OUT-007 and PRE-008.

### Interfaces (client side)

- **SPO-Xmailbox-IF-020** **The resolver comes from the registry.** The route of a put to a party is the pair (the party's recorded wallet key, the party's fingerprint as the device). It is a miss, and the put is `ports.ErrNoRoute` with nothing dialled, for: an unknown fingerprint; a party that is not active; a party with no relay identity; a wallet key whose role history in this store is cold, holds a role other than payment and stake, or cannot be read; a wallet key that is the id of a pool named in any party's scope or one of this workspace's own pool ids (SEC-075; without a source of them nothing routes); and a party whose stored relay identity no longer verifies (Xparty OUT-007), which the table names for the command to report. The key hash of a signing slot is never a route: the routes are built from the party records alone. The table is built by `Refresh` (one store read, under the caller's context) and read by `Resolve` without I/O, so the resolver the client calls never blocks on the store and never calls the client. Of two refreshes that run at once, the one that began later is the table installed: a refresh that read the registry earlier never replaces a newer table.
- **SPO-Xmailbox-IF-021** **Commands.** `spo party relay bind --key NAME [--role payment|stake] [--lifetime-days N]` binds this device with a payment or stake key of the vault (`relaywallet.FromRef`, default-deny on role and on role history, ADR 0014 decision 4); `bind --print --wallet HEX [--lifetime-days N]` prints, for an external wallet, the exact one-line payload to sign, its hex, the address to sign for, the device (its full fingerprint and its last groups), the dates in UTC and `K`, and stores the prepared request; `bind --import --sign1 HEX --cose-key HEX` verifies the wallet's answer against the stored request (Xrelaybind IF-004, SEC-023) and stores the binding. `status` shows the binding (wallet key, from, until, days left, a renewal warning 14 days before `until`), each pending revoke (an id of 16 hex characters, what it revokes, its not-before and until it is sent), a prepared request, and a notice for a stored binding of another device (OUT-097). `revoke (--device FINGERPRINT | --all) (--key NAME | --print --wallet HEX | --import --sign1 HEX --cose-key HEX)` makes a wallet-signed revoke and stores it as pending. `forget` makes a device-signed revoke of this device, stores it, and deletes this device's binding (asks first; `--yes` answers). `forget --lost DEVICE` is the wallet-signed revoke of another device, by the same three ways as `revoke`, stored and sent by the revoke-only sender when a relay is wired; with `--import` the prepared request must be a revoke of exactly DEVICE (not of every device of the key, not of this device), or nothing is imported, and a state that cannot be read refuses it. `drop-revoke ID` drops one pending revoke after a yes or no question with no flag that answers it (OUT-098). `peer NAME --binding FILE | --clear` updates an enrolled party's relay identity (Xparty PR-007): `--binding` asks for the typed groups, `--clear` asks a yes or no question (`--yes` answers it), because clearing grants nothing and only stops delivery over a relay. `spo party outbox status` lists the items waiting, refused ones with when, by which kind of transport and why; `spo party outbox retry` clears the refusal marks. Every failure exits 1, as every other `spo` command does, and a refused command changes nothing.

### Outputs (client side)

- **SPO-Xmailbox-OUT-096** **The expected-sender list comes from the registry**: the wallet keys of the active parties whose route IF-020 accepts, in the order of their local names, given to the client's `SetSenders`. `Refresh` reports whether the set changed, so a caller calls `SetSenders` only then (the client logs in again for a changed set, SEC-071 and OUT-093).
- **SPO-Xmailbox-OUT-097** **This device's relay state is one record in the encrypted store** (kind `relay.own`): the current binding (statement and key, with `K`, from, until), at most one prepared request of an external wallet, the pending revokes (at most 64) and the latest revoke not-before per device (at most 64 devices). The decoder is strict: the record is at most 64 KiB (checked before it is parsed, which bounds every count and allocation); an unknown or duplicate key, another version, hex that is not canonical, a count over its bound (checked before any entry is verified), a binding that verifies neither for this device's fingerprint nor for the device it names, at its own `from`, or a revoke that does not parse, refuses the record and nothing is decided from it. Keys are compared byte for byte with the field names, at every level (a key that differs from a name only in case or by Unicode folding is unknown). A binding that verifies for **another** device than this one (a record from before a rotation) does not refuse the record: it is no binding of this device, `status` shows it with the remedy (revoke that device with the wallet key), and it is dropped at the next write; a prepared binding request for another device is dropped the same way. The pending revokes stay readable. The record survives a restart; nothing secret is in it.
- **SPO-Xmailbox-OUT-098** **The revoke book.** Every revoke this device makes (device-signed, or wallet-signed for itself or another device) is stored before it is reported and kept until the revoked binding's `until`: for a revoke of this device alone, the end of this device's binding when it holds one; for every other revoke (another device, **every device of the key** (`--all`), or this device without a binding) the 180-day maximum after the not-before, capped at the largest time, because another device's binding may end that late. It is handed to every mailbox client as its `RevokeBook`, which reports outcomes in memory; a final outcome (`invalid`, `expired`) drops it, and the book is saved by the caller after the exchange. A revoke already pending (the same statement) is not added twice. A new revoke **supersedes** a pending one of the same scope at the relay (the device alone; a wallet key and one device; a wallet key and all its devices) whose not-before and `until` are not later than the new one's, which then replaces it. **The bound is 64, and 16 places are reserved**: a revoke made with `revoke` (and one stored with `AddRevoke`) is refused when 48 are pending; this device's `forget`, `forget --lost` (every way) and the revoke of the old device at a rotation (SEC-076) may use all 64. A revoke that finds no place is refused before anything is signed, and the message names the way out: `status` lists the pending revokes with their ids, and `drop-revoke ID` drops one after the operator confirms (a yes or no question; no flag answers it; with no terminal nothing is dropped), because a dropped revoke is not sent again. Making a revoke raises the stored not-before of its device and **never lowers it**; when the table of not-befores (64) is full the oldest entry goes, **never this device's own**, which is the only one read: the `lastNotBefore` of its next binding (`relaybind.PlanFrom`).
- **SPO-Xmailbox-OUT-099** **A refused identity stops the run and tells the operator.** When the transport says this device's identity is refused (`ports.ErrIdentityRefused`: the relay's `binding` or `not_allowed` code, or a binding the client itself holds expired), `Outbox.Flush` tries no further item in that run and returns the error, and the command says the remedy: for `binding`, sign a new binding with `spo party relay bind`; for `not_allowed`, ask the relay's operator to allow the wallet key or bind another key. The client's own backoff holds until `SetBinding` (OUT-094), so nothing asks the wallet or dials again in a loop. The commands that loop over the outbox (`serve`, `connect`) tell the remedy **once per command**, not at every run; `outbox export` returns it with the error. Nothing asks a wallet for a signature because of it.

### Preconditions and failures (client side)

- **SPO-Xmailbox-PRE-059** **Setting this device's binding** follows the client's `SetBinding` rule (OUT-094): the binding must verify for this device's own fingerprint on the clock, inside the relay policy; one whose `from` is earlier than the binding held is refused; the same statement again changes nothing; a newer one replaces the old and is the one presented at the next connection. A binding is made only after the plan of `relaybinding` (the wait rule with the stored not-before: a `*WaitError` signs nothing and stores nothing). A prepared request for an external wallet is kept at most ten minutes and is cleared by a successful import or a new print.

### Security (client side)

- **SPO-Xmailbox-SEC-073** **Forget.** `forget` revokes this device with its own key (a device-signed revoke, not-before now), stores the revoke before the binding is deleted, and deletes the binding, so a new login needs a new binding. `forget --lost DEVICE` revokes another device with the wallet key and sends it with a sender that holds no binding and no signer (IF-019); the use case returns the outcome of each revoke and keeps them pending (a `recorded` or a `refused` answer is not final). Revoking a device that is this one with `--lost` is refused (use `forget`).
- **SPO-Xmailbox-SEC-074** **The relay statement signer is reached only through the closed wallet key.** The relay commands make the wallet key with `relaywallet.FromRef` from the key the operator names, so only a payment or a stake key reference can be one; the pass-through for a key of no known history is an unexported field of `relaybinding.Service`, set only by its method `AllowingUnknownHistory`, which no production code calls (an architecture test scans the module for the call and for any other write of the field in its package); and the peer path never signs anything.
- **SPO-Xmailbox-SEC-075** **A pool id never signs a relay statement.** Every path of this device that names a wallet key (`bind` with a vault key, `--print` and `--import`; `revoke` the three ways; `forget --lost` the three ways) refuses, before anything is signed or printed and again at an import, a key hash equal to a pool id this workspace knows: its own pools (a pool id record, in hex or bech32, or the hash of the pool's cold verification key; a pool kept here only by its id has no role history of the cold key) and every pool named in the scope of an enrolled party. Without a source of these ids nothing is signed. The peer path (enrollment, rotation acceptance, `peer`, and the routes of IF-020) refuses the workspace's own pool ids too. For an external key this workspace has no history of, `--print` asks the operator to type its role, `payment` or `stake`, after saying that it must never be a pool cold key; any other answer and no terminal print nothing and prepare nothing; no flag answers it and `--yes` does not.
- **SPO-Xmailbox-SEC-076** **A rotation revokes the old device.** `party rotate`, when this device holds a binding, signs a device revoke of the old device with the OLD identity, not-before now, before the rotation (a revoke that cannot be signed refuses the rotation, with nothing changed), and in the rotation's own store transaction stores it as pending (it may use the reserved places, OUT-098), raises the old device's not-before, and drops the old binding and any prepared request; the pending revokes are kept and the new device has no binding and no not-before of its own. A book with no place at all does not stop the rotation: the revoke is not stored and the command says so, with the old binding's end and how to revoke the old device with the wallet key. After the rotation `status`, `bind`, `revoke` and `forget --lost` work for the new device, and the stored revoke sent to a relay ends the old device's binding there.

### Choices that go beyond the ADR text (work package 8)

- A peer's wallet key that this store has no record of is accepted at enrollment (it lives in the peer's wallet); a known cold or other history refuses it, and so does a pool id named in any scope.
- Several enrolled parties may share one wallet key (the same person's laptop and server), at most 8 active, as at the relay; the evidence shows which.
- Revokes are not kept per relay: a revoke names no relay, so the same pending list is given to every relay client.
- An expired binding of a peer still routes: the peer renews at the relay without a new enrollment, and the relay answers `unbound` when it has no binding.

## The relay configuration, the relay binary and several relays (ADR 0014 work package 10)

What runs a relay and what lets a device use several. The relay side is `internal/domain/relayconf` (the configuration as checked values, pure), `internal/adapters/relayconfig` (the operator's file, version 2, and the relay's key file: it replaces the version 1 access list, which is deleted with `relayport.AccessList` and `AccessEntry`), `internal/app/relayhost` (the assembly of a relay process, its run and teardown, and the logic of its command line, over adapters it is given) and `cmd/spo-relay` (a main that only gives `relayhost.Main` the adapters and the signals). The layering rule of the module (an adapter imports no use case; a use case imports no adapter and no `os`) is why the configuration's model is a domain package and the assembly takes its adapters as functions. The device side is the composite `mailbox.Multi` in `internal/adapters/mailbox`, the relay list of the workspace, and the wiring of `spo party serve`, `spo party connect` and `spo party relay forget`. Owner decisions that hold here: anyone can run a relay, and relays are independent (each has its own key, address and store; ADR 0013 "Owner decisions"); the tunnel is **restricted by default** (ADR 0014 decision 5, note of 2026-11-18); the relay cannot open an envelope and holds no party secret.

### Interfaces (relay process and several relays)

- **SPO-Xmailbox-IF-022** **The configuration file.** `relayconfig.Load(path)` reads the file and `relayconfig.Parse(data)` its text; both return a `*relayconf.Config` whose parts are already validated: the admission (`open` or `allow-list`) and the wallet keys of the allow-list, the relay's key file and its two store directories, the tunnel port, the DERP map address, the device node keys the tunnel admits, the registry's configuration (`relayregistry.Config` with the policy and the allow-list set and no `Evictable`, which the assembly sets), the open quota (`mailbox.ValidOpenQuota`), the operator's overrides of the session limits (by the keys of `[limits]`), the retention and the sweep interval. The session limits belong to `app/relay`, so they are applied to the protocol table and validated by `relayhost.Prepare`, which `check-config` and `Start` both call: "at load" means the configuration is refused before anything starts. The file is the subset of TOML of `platform/tomlsubset` with tables `[relay]`, `[registry]`, `[quota]`, `[limits]`, `[derp_region]` and the array tables `[[device]]`, `[[wallet]]` and `[[derp_node]]` (the region pin, IF-030); the keys are listed in the reference page (`docs/reference/relay-config.md`). The package parses no identity document and imports nothing that can open an envelope (SEC-009).
- **SPO-Xmailbox-IF-023** **The relay process.** `relayhost.Start(ctx, cfg, Deps)` is the one assembly of a relay, used by the binary and by the end-to-end test: it returns a `*Relay` with `Serve(ctx)`, `Reload(cfg)`, `NodeKey()`, `Address()` and `Shutdown(bound)`. `Deps` holds the adapters as functions (the configuration and key files, the two stores, the public key of a relay key, and the tunnel: a function that opens a `relayhost.Tunnel`, which is a `relayport.StreamListener` with `NodeKey`, `Address`, `SetAllowed` and `CloseWithin`; the binary gives the tailcat listener of `adapters/tailcat/stream`, a test a fake one), the clock, the random source, the operator log and the teardown bound. `relayhost.Main(args, stdout, stderr, signals, deps) int` is the command line (the binary maps SIGINT and SIGTERM to `SignalStop` and SIGHUP to `SignalReload`): `spo-relay serve --config FILE [--print-address]`, `spo-relay check-config --config FILE`, `spo-relay init-key --config FILE`; it returns the exit status (OUT-101). *Amended in ADR 0015 work package 5:* the two stores and the lease are given as described in SPO-Xmailbox-IF-034 (`StoreSpec`, `StoreEnv`, `OpenLease`).
- **SPO-Xmailbox-IF-024** **Several relays on a device.** `mailbox.NewMulti(MultiConfig)` takes 1 to 8 named members, each a `*mailbox.Client` of one relay, and is a `ports.EnvelopeSender`, `ports.EnvelopeReceiver` and `ports.EnvelopeContextAcker` whose `Transport()` is a network transport, so the application cannot tell several relays from one (ADR 0013, "Owner decisions"). It also has `SetBinding`, `SetSenders` and `SendRevokes`, which act on every member, and `Close`. `mailbox.LockedBook` wraps a `RevokeBook` so that several clients may share it. Names are 1 to 32 characters of `a` to `z`, `0` to `9` and `-`, starting with a letter or digit, and unique; a client given twice is refused.
- **SPO-Xmailbox-IF-025** **The relay list of a workspace.** `spo party relay add NAME --node-key HEX --address-file FILE [--port N]`, `spo party relay list` and `spo party relay remove NAME [--yes]` keep the relays this device uses: the name, the pinned relay node key and the port in one public record (kind `relay.list`, strict JSON, at most 8 relays), and the relay's address, which holds the pre-shared key, as a secret record per relay (kind `relay.addr`, sealed like the coordinator's tailcat address). `add` refuses an address that does not lead to the pinned key, before anything is stored. `spo party serve --transport mailbox` and `spo party connect --transport mailbox` exchange over every listed relay at once; `--transport tailcat` (the default) is unchanged. `spo party relay send-revokes` sends the pending revokes to every listed relay on revoke-only connections (OUT-111).
- **SPO-Xmailbox-IF-026** **A revoke book that learns which relay recorded what.** (Added in the security review of work package 10.) `relayport.RelayRevokeBook` is a `RevokeBook` with `ResultAt(relay, revoke, outcome)`. `mailbox.ForRelay(book, name)` is the book as the client of one relay sees it: `Pending` is the book's, and every outcome goes to `ResultAt` with the relay's name when the book takes it (to `Result` otherwise). `mailbox.Connect` and `mailbox.SendRevokesTo` give each relay's client the shared book this way, and `LockedBook` passes `ResultAt` on. `Multi.SendRevokes` and `SendRevokesTo` put each relay's own error in its report (`RevokeReport.Err`). `relayself.Book` implements it (OUT-111).

### Outputs (relay process and several relays)

- **SPO-Xmailbox-OUT-100** **Assembly, in this order** (the obligations of "What the relay binary and configuration must do"): the configuration's parts are checked to agree (PRE-064); the relay key is loaded (SEC-077); the mailbox store is opened; the eviction guard is made over that store and set as the registry configuration's `Evictable` **before the registry is opened**; the registry (`adapters/bindingstore`) is opened; the server gets the same guard, the registry's own policy, the open quota, the limits and the relay node key the tunnel reports; the sweeper gets the same retention and the registry (`WithRegistry`) and runs every sweep interval for as long as the server does; the tunnel listener is opened with exactly the configured device node keys; the relay node key is printed. A failure at any step closes what the steps before it opened, in reverse order, and nothing is served. The notes the stores return at open are written to the operator log.
- **SPO-Xmailbox-OUT-101** **Shutdown and exit status.** SIGINT and SIGTERM end serving: the server's context ends (every session gets the "shutting down" code), the sweeper stops, the tunnel is closed with `CloseWithin`, and the stores are closed; the whole teardown has one bound (default 20 s). The exit status is 0 after a clean stop, 1 for a configuration, key, store or tunnel failure, 2 for a usage error, and **3 when the teardown is stuck**: the server did not return within the bound, `CloseWithin` returned `ErrTeardownStuck`, or the tunnel's `OnTeardownStuck` was called. On 3 the process says "tunnel did not stop" and exits; it never reports a clean stop, because a stuck engine cannot be recovered in process and a supervisor restart is the recovery (ADR 0013, "Limits of the tunnel library"). (Amended in the security review of work package 10.) The same holds for a start that fails after the tunnel opened: when the close of that tunnel in the undo is stuck, or the tunnel called `OnTeardownStuck` during the start, `Start` returns an error that satisfies `ErrTeardownStuck` (with the cause) and `serve` exits 3. *Amended in ADR 0015 work package 5:* **4 when the authority is lost** (`ExitAuthority`): the lease was lost, or a store call returned `relayport.ErrAuthorityLost`, at the start or while serving (SPO-Xmailbox-OUT-127). The teardown is the same, the lease is not released, and the process says "no longer the writer of its store". 4 is distinct from 1 because a restart is the remedy (the new process waits for the lease), and from 3 because the tunnel did stop; when both happen, 3 wins, as ADR 0015 decision 5 says. A planned stop releases the lease after the stores are closed.
- **SPO-Xmailbox-OUT-102** **Reload of the device list.** SIGHUP reads the file again. A file that does not load, or that differs from the running configuration in anything but the `[[device]]` tables, is refused: the relay says why and keeps the list in force; a configuration with the same devices changes nothing. Otherwise the new list is given to the tunnel with `SetAllowed` (tailcat cannot remove a key: the adapter rebuilds the tunnel with the same identity, so the address stays, and resets the live streams of a removed key). (Amended in the security review of work package 10.) The relay then ends, itself, the logged-in sessions that came from a removed node key (`relay.Server.CloseNode`, the "shutting down" code, logged as `close reason=delisted`), so that a removed device keeps no live session whatever the tunnel does with its streams (SEC-079). Everything else, the admission and the allow-list of wallet keys included, takes a restart.
- **SPO-Xmailbox-OUT-103** **check-config** loads and checks the file (every rule of PRE-060 to PRE-064) and, when the key file exists, the key file (SEC-077), without opening a store or the tunnel, and prints the relay node key when there is a key; the status is 0 or 1. **init-key** creates the key file (SEC-077) and prints the relay node key; it refuses a key file that exists. **serve** refuses a missing key file and names `init-key`. The relay's address holds the pre-shared key, so it is printed only by `serve --print-address`, on standard output, with a warning on standard error that it is a secret to pass only to the devices that may use the relay. The how-to says it is never part of a unit file or a container command (its output would land in a journal or a container log) and how to get the address once.
- **SPO-Xmailbox-OUT-104** **A send to several relays.** `Multi.Send` puts the envelope to every member at once. It returns nil when **at least one member stored it** (stored or duplicate: "delivered" means stored by at least one relay). After the first member stored it, the others have `SendGrace` (default 3 s) to answer and are then cancelled, so a relay that stalls or is slow cannot hold a send back. When no member stored it, the result is `ports.ErrRefusedByTransport` if every member answered with a refusal of the envelope (`refused`, `too_large`, `bad_hash`), an error that satisfies `ports.ErrIdentityRefused` only if every member refused this device's identity, and otherwise `ports.ErrNoRoute` (the item stays queued). The outcome of each member (stored, no route, refused, identity refused, abandoned, closed, context) is reported as an event that names the member and carries no text a relay chose.
- **SPO-Xmailbox-OUT-105** **A receive from several relays.** `Multi.Receive` fetches from every member at once, each on its own goroutine, so a member that is down, stalls or floods does not delay the others: each member has at most one fetched envelope held at a time, and the held envelopes are delivered in turn, member after member. An envelope is identified by its hash (`mailbox.HashOf` of its bytes). (Amended in the security review of work package 10.) A copy that is the **second copy of a put already delivered** is acknowledged at the member it came from and not delivered; every other envelope is delivered, a re-put of the same bytes included (OUT-110). The copies of the envelope being delivered that other members hold are acknowledged together with it. A member's receive that fails (anything but the end of the context) pauses that member alone, for a backoff that doubles from `BackoffMin` (1 s) to `BackoffMax` (2 min) and is reset by a success. `Receive` returns an error only when every member has failed and no envelope is held: the identity refusal when every member refused this device's identity, else the first member's error; it returns it **after the shortest pause of the failed members has passed** (or at the caller's deadline, whichever is first; the caller's cancel and `Close` end the wait with their own errors), so a loop over `Receive` does not spin. With every relay unreachable it waits until its context ends, as one client does. The member receives run until the caller's deadline (a caller with no deadline cancels them when `Receive` returns), so a long-poll is not cut short by the return of another member's envelope.
- **SPO-Xmailbox-OUT-106** **Acknowledgement over several relays.** `Multi.AckContext` acknowledges the envelope of the last `Receive` at every member it was fetched from and at every member that holds a copy of it, and counts it (OUT-110): one delivery of its hash, and one copy acknowledged at each member whose acknowledgement succeeded. It returns nil when at least one member's acknowledgement succeeded; a member whose acknowledgement failed is not counted and keeps the hash waiting to send with its next acknowledgement (OUT-037), and if that relay delivers the envelope again it is a second copy of the delivered put: acknowledged and not delivered. A `Receive` without an `Ack` in between leaves the envelope unacknowledged everywhere: it comes again, as from one client.
- **SPO-Xmailbox-OUT-107** **Identity and revokes on every relay.** `Multi.SetBinding` and `Multi.SetSenders` give the binding and the expected-sender set to every member (a binding one member refuses is refused for all: the members check it the same way). `Multi.SendRevokes` runs the revoke-only exchange on every member at once and returns each member's report, with the member's own error in it (IF-026); it returns an error only when every member failed. A revoke names no relay, so one book (wrapped with `LockedBook`) is given to every member (work package 8), each member reporting to it with its name (`ForRelay`), so that the book knows which relay recorded which revoke (OUT-111). The revoke-only sender of a device with no binding (`RelayOps.SendRevokes`, `forget --lost`, `spo party relay send-revokes`) dials every listed relay with a `RevokeSender` the same way and returns each relay's own error by name.
- **SPO-Xmailbox-OUT-108** **The commands that exchange over the relays.** `serve --transport mailbox` (coordinator) and `connect --transport mailbox` (signer) build one client per listed relay from this device's state: the tailcat node key of the identity (`spo party init --tailcat`), the binding of `relay.own` (a device with no binding is told to bind first), the routes and the expected senders of `relayroutes.Table`, and the revoke book of `relayself`. The loop flushes the outbox to the relays, receives and hands each envelope to the coordinator or the signer, acknowledges it, and **saves the revoke book after each exchange**. Every sync interval it calls `Table.Refresh` and, when the expected-sender set changed, `SetSenders`; when `relay.own` holds a binding newer than the one in use (a `party relay bind` in another process), it calls `SetBinding`. A refused identity is told with its remedy **at most once per binding statement per process**; a new binding that is refused again is told once more. (Amended in the security review of work package 10.) A failure of the send or the receive that persists is told once, and again only when its text changes or after a success. The error output and the binding in use are shared by the loop and the composite's member goroutines (its event callback), so they are one guarded value (`app/relayloop.Teller`), tested under the race detector. Every `relayRearmEvery` (10 minutes) the loop re-arms the outbox (`Outbox.Rearm`): no `Hello` arrives over a relay, so the unanswered requests are put again on a timer and a lost response is recovered while the command runs (SPO-Xparty-INV-017). A device with no binding is refused, but first, when a listed relay still owes a pending revoke, the revokes are sent on revoke-only connections and reported per relay (OUT-111). Logout is the end of the process (SIGINT or SIGTERM): the clients are closed, then every tunnel dialer with `CloseWithin`; a teardown that is stuck says "tunnel did not stop" and the command fails, never "Disconnected".
- **SPO-Xmailbox-OUT-109** **Forget over the relays.** `spo party relay forget` on a device that has relays listed and holds a binding runs the order of ADR 0014 decision 8: (1) log in to every relay, fetch and hand the queue to this device's coordinator or signer (`--as` when it is both), acknowledging what was handled; (2) sign and store the device-signed revoke of this device, keeping the binding; (3) send the pending revokes to every relay on revoke-only connections; (4) close the clients and the dialers; (5) only then delete the binding. A failure of step 1 or 3 is reported and the order goes on (the revoke stays pending); a stuck teardown in step 4 fails the command before step 5. Without relays, or without a binding, `forget` stores the revoke and deletes the binding as before (SEC-073) and sends it on revoke-only connections when relays are listed. (Amended in the security review of work package 10.) In step 1 an envelope whose handling fails is tried once: when the relay serves it again it is acknowledged without being handled, and the failures are counted in the output, so the drain never spins on one envelope until its time bound. After step 5 (and after the send of the path without a binding) the command says, per listed relay, whether it recorded this revoke, naming the cause of each that did not (its own error, or "it did not record it": refused or deferred); it says the device was revoked at the relays **only when every listed relay recorded it**. Otherwise it says which relays still owe it, until when, that a binding stays valid at such a relay, and how it is completed (OUT-111), and exits non-zero. The binding is deleted in either case: the revoke is device-signed and goes on revoke-only connections that need no binding, so keeping the binding would only leave a device that can still log in.

- **SPO-Xmailbox-OUT-110** **Each put is delivered once; a re-put is delivered.** (Added in the security review of work package 10, replacing the de-duplication window, which dropped the outbox's recovery re-put: a relay that answers `stored` and drops could then stall a collection.) The composite keeps, per hash, the number of deliveries `D` and, per member, the number of copies acknowledged there `c[m]` (never more than `D`); both are counted only on an acknowledgement that succeeded. A copy of hash `h` served by member `m` is **held back** (acknowledged at `m`, not delivered, reported as `duplicate`) exactly when `c[m] < D`: another member served more copies of `h` than `m`, so this is `m`'s copy of a put already delivered. Otherwise it is delivered, and its acknowledgement raises `D` and the `c` of every member it was acknowledged at. What is guaranteed: in the honest case (every relay stores each put once and every acknowledgement succeeds), **each put of the same bytes is delivered exactly once**, however many relays carry it and in whatever order their copies arrive; a put that reached only a relay that missed an earlier put of the same bytes is taken for that relay's copy of the earlier one and held back, and the next re-put is delivered. A relay that replays an envelope it served (or that answers every fetch with it) has each replay delivered, because it cannot be told from a re-put; the client paces a page of envelopes delivered a moment ago (OUT-043: the pause doubles from `MinPoll` to at most 30 s), so a hostile relay causes at most one page of repeats per pause, which the application absorbs: an answered request is answered from the stored response and never signed again (SPO-Xparty-INV-017), an accepted response arriving again changes nothing and counts nothing (SPO-Xparty-INV-041), any other repeat is a replay of the replay log (SPO-Xparty-INV-007). Its replays also raise `D`, so the honest members' copies of that hash are held back while its count leads, but the bytes it delivers are the same, so nothing the honest relays carry is lost. The memory is bounded: at most `AckedMemory` hashes (default 4096, the oldest forgotten first), each forgotten `AckedWindow` (default 10 minutes) after its last acknowledgement; a copy past either is delivered once more (a repeat the application tolerates).
- **SPO-Xmailbox-OUT-111** **A revoke is owed to each relay until that relay recorded it.** (Added in the security review of work package 10.) The record of `relay.own` keeps, per pending revoke, the relays that recorded it (`recorded_at`: at most 8 valid relay names, none twice, checked when the record is read; a ninth pushes the oldest out, which only makes that relay owe the revoke again). `relayself.Book` learns it from `ResultAt` (an outcome `recorded` at a named relay) and `Save` adds it to the record. A revoke is **owed** to every listed relay not named there until it ends; a relay added later owes it too. A revoke recorded by every relay stays pending, and is still sent on every connection until it ends (a relay may lose its state), but is owed to nobody. `spo party relay status` shows, per pending revoke, the relays that recorded it and those that have not. `spo party relay send-revokes` sends every pending revoke to every listed relay on revoke-only connections, which need no binding and sign nothing, reports per relay which revokes it has not recorded (with the relay's own error when it was not reached) and fails while any is owed; `serve` and `connect --transport mailbox` on a device with no binding do the same before they refuse, when a relay owes a revoke. `forget` and `forget --lost` report per relay in the same way (OUT-109).
- **SPO-Xmailbox-OUT-112** **Junk is paced.** (Added in the security review of work package 10.) An envelope refused before its sender is known (one that does not open, or whose signature does not verify: anything a relay can make up) costs the device one opening and one write of the noise ring of the event log (SPO-Xparty-INV-023), which bound the log but not the rate. The exchange loop of `serve` and `connect` paces them with `relayloop.Pacer`: 64 pass at once, and each one beyond waits for a token that comes back at one per second, so a relay that serves unique junk without end costs at most one handling per second once the burst is spent.
- **SPO-Xmailbox-OUT-113** **The tunnel adapter's lines reach the operator log, safely.** (Added in the security review of work package 10.) `relayhost` gives the tunnel a `Logf` (`TunnelSpec.Logf`, passed to `stream.ListenerConfig.Logf` by `cmd/spo-relay`): a line whose format starts with `tailcat stream:` (the adapter's own: a rebuild that failed, a teardown that is stuck) is written to the operator log as one line, every control or unprintable character replaced by `?` and cut at 512 bytes, so the error it carries cannot forge a line or drive a terminal; every other line (the tunnel library's own chatter, which may carry what a peer sent) is dropped.

### Preconditions and failures (relay configuration)

- **SPO-Xmailbox-PRE-060** **The file.** It is read only if it is a regular file (a FIFO is refused without being waited on), owned by the effective user or by root, not writable by its group or by others, and at most 1 MiB (room for the 4096 array tables), checked on the descriptor before a byte is read. The text is refused for: a table other than the eight (the six and, since ADR 0015 work package 1, `[derp_region]` and `[[derp_node]]`, PRE-068), a key not of its table, a key outside a table, a value of the wrong kind, a key or a plain table that occurs twice, more than 4096 `[[device]]` and `[[wallet]]` tables in all, more than 8 `[[derp_node]]` tables, a line over 4 KiB, and everything `tomlsubset` refuses (SEC-019). A label is 1 to 64 bytes with no `tomlsubset.ActiveRune`, not only spaces, and unique among its kind.
- **SPO-Xmailbox-PRE-061** **Admission is required.** `[relay] admission` must be `"open"` (any device with a valid binding) or `"allow-list"` (only the wallet keys of the `[[wallet]]` tables, the registry's `not_allowed`); a missing key refuses to start, and so does any other value. `allow-list` needs at least one `[[wallet]]`; `open` with a `[[wallet]]` table is refused, because the operator would believe the list applies. A wallet key is 56 lower-case hex digits and unique.
- **SPO-Xmailbox-PRE-062** **The tunnel is restricted by default.** The tunnel admits exactly the node keys of the `[[device]]` tables (`node_key`, 64 lower-case hex digits, not zero, unique); at least one is required, because an empty list would admit no one and a relay that serves nobody is a mistake. The open tunnel is the key `[relay] unsafe_open_tunnel`; absent or `false` is the restricted tunnel, and `true` is refused by this build with the reason (tailcat v0.7.0 registers any client that knows the relay's public key and region, permanently, at a cost that grows as the square of their number; ADR 0013, "Limits of the tunnel library"). Nothing else switches the tunnel open.
- **SPO-Xmailbox-PRE-063** **Paths.** `key_file`, `mailbox_dir` and `registry_dir` are required, absolute and clean; the three are distinct and none is inside another. At load: a store directory that exists must be a directory owned by the effective user with no group or other permission bit; one that does not exist must have a parent owned by the effective user or by root that its group and others cannot write (the store creates it with mode 0700). The key file's directory must be owned by the effective user or by root and not writable by its group or others; a key file that exists is checked as SEC-077 says.
- **SPO-Xmailbox-PRE-064** **The parts agree.** One `[registry] max_bound_devices` (1 to 4096, default 1024) is both the registry's `MaxBoundDevices` and the open quota's, and the quota is `OpenQuota.Validated` (the global quota covers that many queues; the stranger allowance is strictly inside the queue bound: PRE-031). One `[registry] max_binding_days` (1 to 180) and `skew_seconds` (0 to 300) are the policy of the registry and of the session. One `[relay] retention_seconds` (1 to 30 days, default 7) is the session's `Limits.RetentionSeconds` and the sweeper's. The limits are within the protocol tables (`relay.Limits.Validated`) and the registry within its bounds (`relayregistry.Config.Validate`). `Config.Check` refuses a configuration whose parts differ in any of these, and `relayhost.Start` calls it again, so a configuration changed after its load cannot start a relay whose quota, registry, policy or retention disagree.

### Security (relay process and several relays)

- **SPO-Xmailbox-SEC-077** **The relay key at rest.** The relay's node private key and pre-shared key are one file of three lines (`spo-relay-key-v1`, `node` and 64 hex digits, `psk` and 64 hex digits; 156 bytes). It is not a party secret, and the relay links no secret buffer and no store encryption (SEC-009), so it is protected by the file system, as ADR 0013 puts the relay keys in a secret store: `init-key` creates it with `O_EXCL` and mode 0600 from `crypto/rand`; a key file is used only if it is a regular file owned by the effective user with no group or other permission bit, exactly 156 bytes (checked on the descriptor before it is read) and in exactly that form, and neither key is all zero. The key is never written to the log; the relay's public node key is.
- **SPO-Xmailbox-SEC-078** **What the relay binary links.** The import closure of `cmd/spo-relay` and of `app/relayhost` holds the hard bans of SEC-009 and also nothing that signs or holds a wallet or reads the workspace: no `adapters/native`, `adapters/hwcli`, `adapters/fido2cli`, `app/relaybinding`, `domain/relaywallet`, `adapters/sqlitestore`, `adapters/envelope`, `platform/seal`, `platform/secret`, `domain/unlock`, `adapters/cli`, `adapters/tui`, `adapters/mailbox` (the client), `adapters/partystore`, `app/relayself`, `app/multisig`, the workspace ports (`internal/ports`, which carry secret buffers; `ports/relayport` is the relay's) and no command-line framework. Both are relay-side roots of the tunnel rule (SEC-009); `app/relayhost` is also a root of the full-closure rule, and `cmd/spo-relay`, which links the tunnel adapter, is not (its transport crypto is allowed below the adapter only).
- **SPO-Xmailbox-SEC-079** **A device off the list never reaches the session.** A dial from a node key that is not in `[[device]]` is refused by the tunnel: the server accepts no stream for it and logs no connection, and after a reload that removes a key its next dial is refused the same way and its live session is ended by the relay (OUT-102). The session's own checks (the binding, the login signature) come after the tunnel and are not what keeps an unlisted device out.
- **SPO-Xmailbox-SEC-080** **One hostile relay among several.** A member relay that stalls, lies (answers that break the protocol), floods (answers every fetch at once), serves another relay's items or replays envelopes already acknowledged cannot stop the other members' mail: the honest member's envelopes are delivered, a put is delivered once however many members serve it while its hash is remembered, a hostile member's replays are delivered paced and absorbed by the application (OUT-110), and the hostile member is paused alone. A relay cannot make the device sign anything but its own login (the client's signing surface, SEC-071), and the envelopes it serves are checked by the application as from any transport. Pool cold keys never sign over this transport: the outbox offers a cold-key item only to the file transport (SPO-Xparty-PRE-004) and the composite is a network transport.

- **SPO-Xmailbox-SEC-081** **The relay address file is a secret file.** (Added in the security review of work package 10.) `spo party relay add --address-file FILE` opens the file without following a symbolic link and without waiting (`O_NOFOLLOW`, `O_NONBLOCK`, as the import of a signing key file does), so a FIFO is refused at once by the regular-file check on the descriptor; the file must be a regular file of at most 1 KiB (and a line end), checked before it is read, with no group or other permission bit (refused, with the `chmod 600` that fixes it). The bytes are read into guarded memory (`secret.TryRead`), trimmed and checked there, and copied once into the guarded buffer that is stored; they never reach the Go heap.

### Invariants (several relays)

- **SPO-Xmailbox-INV-039** **Bounded and closed.** A `Multi` holds at most one fetched envelope per member, at most `AckedMemory` hashes (the oldest is forgotten first) and the copies waiting for the delivered envelope; it starts one receiving goroutine per member at a time and none after `Close` (the check that the composite is open and the count of its goroutines are one step under one lock, and so is the setting of closed, so `Send`, `Receive` or the acknowledgement of a copy racing `Close` add no goroutine once `Close` waits for them; tested under the race detector). `Close` closes every member, interrupts every receive and send, and returns only after its goroutines have ended; later calls return `ports.ErrClosed`. Logout of a device over several relays is: close the `Multi`, close each member's tunnel dialer with `CloseWithin` (a stuck one says "tunnel did not stop"), destroy the local identity the members sign with.

### Choices that go beyond the ADR text (work package 10)

- **The open tunnel is not built.** The owner decided "restricted by default" and the handoff says `ListenerConfig.Open` must not be built while tailcat v0.7.0 has unbounded, permanent registrations. The configuration names the switch loudly (`unsafe_open_tunnel`) so that it cannot be set by accident, and refuses `true`. The measurement of the cost of an unknown peer (ADR 0014 work package 10) therefore waits too.
- **Admission is `[relay] admission`**, required, as decision 5 says; the allow-list is `[[wallet]]` tables with a label, and `open` with a list is refused.
- **An empty device list refuses to start**, like ADR 0013's empty access list (T2): a relay that admits nobody is a mistake.
- **Reload is for the device list only.** It is what tailcat can change at runtime (by a rebuild); every other key takes a restart, so a reload never leaves a server, a registry and a quota that disagree.
- **The relay key is a file, not a sealed record.** The relay links no store encryption by design (SEC-009); its keys are not party secrets, so file permissions protect them and the operator backs them up like the configuration.
- **Delivered means stored by at least one relay**, with a grace of 3 s for the others after the first stored, and the outbox re-puts what is not settled at its next run, so a relay that missed an envelope gets it again while the request is live.
- **De-duplication holds back copies, never puts** (OUT-110, which replaces the text of package 10: "a repeat inside the 2-minute window is not delivered"). The security review showed that the window acknowledged and dropped the outbox's recovery re-put: send, receive and acknowledge an envelope, put the same bytes again inside the window, and nothing was ever delivered while both relays ended empty; with "delivered means stored by one relay" and "responses are sent once", one fast relay that answers `stored` and drops could stall a collection. Counting deliveries per hash and copies per relay tells the second copy of one put (held back) from a new put of the same bytes (delivered), so the window delays nothing and was lengthened to 10 minutes, to recognise the copy of a slow relay; the price is that a relay's own replays are delivered, paced (OUT-043) and absorbed by the application.
- **The outbox is re-armed on a timer over the relays.** A `SigningRequest` is re-sent when the signer's `Hello` arrives (SPO-Xparty-INV-021), which never happens over a relay; re-arming only at the start of an exchange left a lost response unrecovered until the command was run again. Every 10 minutes is the simplest safe rate: a re-put that a relay still holds is answered `duplicate` and stores nothing, one the signer fetched is answered from its stored response.
- **A revoke is owed per relay; `forget` deletes the binding anyway** (OUT-109, OUT-111). Keeping the binding until every relay recorded the revoke would buy nothing: the revoke is device-signed and needs no binding to be sent, and a kept binding would let the device log in again, which the operator asked to end.
- **The address file is refused when its group or others have a permission bit** (SEC-081), as the relay's own key file is (SEC-077), and unlike the signing key files of an import, which are only warned about: the address file is written for `spo party relay add`, so the operator can fix it, and its pre-shared key admits anyone who reads it to the relay's tunnel.
- **The relay list is per device, in the encrypted store**, with the address sealed (ADR 0013 decision 7, "handled as Secrets like the coordinator address") and the node key pinned in a public record.
- **Forget keeps the binding until the revokes are sent.** Decision 8 says to delete the bindings last; `relayself.Forget` deleted it with the revoke in one transaction, so the command now stores the revoke first (`ForgetRevoke`), sends it, closes, and deletes the binding (`DropBinding`).

## The relay session of the TUI, login and logout (ADR 0014 work package 9)

What lets an operator log in to the relays, keep receiving while doing other work, and log out without closing the application (owner, 2026-11-18: "ensure that a client can logout without having to close the application"). The exchange loop of `serve`, `connect` and the new `spo party relay login` is one piece of code, `app/relayloop` (`Exchange` and `Serve`), so the plain command line and the TUI's background session run the same steps. The TUI (`adapters/tui`) runs the command `spo party relay login` of the command tree as its background session and is the session's host: an executor that runs the session's store steps between foreground commands, a status line and screen, and a bounded logout. ADR 9 is amended for this one component (ADR 0014 decision 9). The terms: a **store step** is a part of the loop that reads or writes the workspace (flush the outbox, handle one envelope, follow the store, re-arm the outbox, save the revoke book); the **host** is what runs the loop's store steps and receives its state (`relayloop.Host`); a **foreground command** is a command the operator runs from the menu.

### Interfaces (relay session)

- **SPO-Xmailbox-IF-027** **One exchange loop.** `relayloop.Exchange` is the loop of every exchange over the relays: flush the outbox, receive (with a window), hand the envelope to the handler, acknowledge, pace junk (OUT-112), follow the store every sync interval, re-arm the outbox every re-arm interval, until its context ends or it ends itself (OUT-118). Its store steps are run through `Host.Post(ctx, job)`; the network steps (receive, acknowledge) run on the loop's own goroutine. `relayloop.Inline` is the host of the plain command line (a job runs at once on the caller's goroutine; a panic in it is returned as `relayloop.ErrInternal`). `relayloop.Serve(ctx, status, open)` is a whole session, the host being the status's: it reports `connecting`, opens the session (`open` returns the exchange and its close), reports `logged-in`, runs the exchange, reports `logging-out`, closes, and reports `logged-out` only when the close returned nil, `stuck` otherwise; an opening that fails with an error carrying `relayloop.ErrTunnelDidNotStop` (a revoke-only send whose tunnel did not stop, OUT-111) is `stuck` too. A panic in `open`, in the loop or in a step is recovered by `Serve`: the close runs when `open` had returned it and it has not run, the session reports `logged-out` with the error (or `stuck` when the close failed, panicked, or the opening panicked, since what it made is not known), and `Serve` returns `EndFault` with `ErrInternal`. `Flush` returns the number of envelopes it sent. `Between` (optional) runs on the loop's goroutine after every store sync, for network work the sync found due (OUT-121). `relayloop.Status` is the session's state, shared by the loop and the composite's callbacks under one lock; every change is given to `Host.Report` as a copy (`relayloop.State`). A host may also be a `relayloop.Lender`: the logged-in session lends it its `relayloop.Revokes` (OUT-120) and takes it back before it closes. `serve --transport mailbox`, `connect --transport mailbox` and `party relay login` all run through `Serve`.
- **SPO-Xmailbox-IF-028** **The login command.** `spo party relay login [--as coordinator|signer]` logs this device in to every listed relay and exchanges until it is stopped: it hands each envelope to this device's coordinator or signer (`--as` when it is both, as `inbox import`), never asks the operator anything after the workspace is open, and on the plain command line logs out when SIGINT or SIGTERM ends it (ADR 0014 decision 8, "Plain CLI": logout is the end of the process; there is no `logout` command). It ends itself at `relay_login_max`, when the binding in use expires and when the store handle can no longer be used (OUT-118). The limit is the key `relay_login_max` of the `[party]` table of `spo.toml`: a duration of Go's form (`"12h"`, `"90m"`), 1 minute to 168 hours, default 12 hours (PRE-066).
- **SPO-Xmailbox-IF-029** **The TUI's relay session.** The TUI finds the login command by its annotation (`uihint.RelaySession` = `login`) and runs it as the session: its run asks for the passphrase like any command, and when the command reports `logged-in` the run leaves the screen and goes on in the background. The command finds the host on its terminal (`SessionHost() relayloop.Host`); a terminal without one is the plain command line. The root menu gains **Log out of relays** while a session runs or is stuck: while it is logged in (or logging in) it logs out; while it is logging out or stuck it opens the session's screen, which says where the logout stands and what to do, and starts nothing. **Relay session** shows the state (OUT-115) and the session's last lines. **Forget this device** is the command `spo party relay forget` (annotation `forget`), run after a logout (OUT-119); `forget --lost` is not, since it goes through the logged-in session. The commands that only queue mail (annotation `outbox`: `party request queue`, `party approve`, `party refuse`, `party outbox status`, `party outbox retry`) are told whether a session will send it (OUT-120). A foreground command's terminal says whether a session is logged in (`RelaySessionLive() bool`), whether one is in any phase but logged out (`RelaySessionBusy() bool`), gives the logged-in session's revoke sending (`RelaySessionRevokes() relayloop.Revokes`), and takes word of a tunnel of the command's own that did not stop (`RelayTunnelStuck(string)`, OUT-117). The session's own command answers false, false and nil: it is not a foreground command.

### Outputs (relay session)

- **SPO-Xmailbox-OUT-114** **Store steps run between foreground commands.** The TUI's executor runs one job at a time and runs a session job only while no foreground command runs; a foreground command started while a job runs waits for it, says so, and starts when it ended. A job is a message to the UI's own goroutine: the background session never touches the UI's state; every change of what the UI shows happens in the UI's update. A job that has not started when its poster's context ends is never run (`Post` returns the context's error); a job that has started is waited for, so the session never closes its store while one of its jobs uses it. When the host is closed (the program ends), `Post` refuses (`relayloop.ErrHostClosed`).
- **SPO-Xmailbox-OUT-115** **What the session shows.** The phase (logged out, logging in, logged in, logging out, stuck); per relay, its state: `waiting` (no exchange with it yet since login: the composite dials nothing at its making), `connected` (an exchange with it succeeded, a put stored or a fetch acknowledged, and no failure since), `backing off` with the pause, `identity refused` (`binding` or `not_allowed`), `pinned key mismatch` (the tunnel or the client found another key than the pinned one); the end of the binding in use, and at login the reminder when it ends within 14 days ("renew it with spo party relay bind"); the number of revokes still owed to a relay (OUT-111); the envelopes received and handled, the last one handled and the envelopes the outbox's flushes sent (a count of sends, not of flushes); the remedy of a refused identity, told at most once per binding statement in the process (OUT-108: the session's `Teller` holds the binding in use, renewed by the store sync); junk paced as in OUT-112. For a signer's login, the requests waiting for the operator's review, counted from the store at every sync as their ids: the header says "requests waiting for review: N" on every screen while a session runs, and the session screen lists each as `spo party review ID` (approval stays a foreground command, ADR 0014 decision 9). Text a relay chose is never shown (the composite's events carry classes only); every string that reaches the TUI's view or the session's line buffer from a command or the network (error text, relay names, the line of the last envelope, the remedy, a recovered panic's text, the review ids) passes the TUI's sanitiser (`tui.Clean`), so a terminal escape, a control character or a bidirectional control is never drawn.
- **SPO-Xmailbox-OUT-116** **Logout without closing the application.** Logout cancels the loop's context and waits for the loop: a receive, a send or an acknowledgement in flight ends with the context, an envelope fetched and not acknowledged comes back at the next login, a store step queued and not started is dropped, a started one is waited for. Then, in this order: the revoke book is saved when it learnt something (a store step, given at most 2 s; when it cannot run, the book's news is lost and the revokes stay owed, which errs toward sending again); the clients are closed and every tunnel dialer is closed with `CloseWithin` (10 s, `RelayClient.Logout`); the local identity is destroyed; the command returns, which closes the store handle and destroys its passphrase. Only when every step succeeded does the operator read "Logged out of the relays."; afterwards no goroutine, connection or secret of the session remains, and a new login in the same process works (it opens the workspace again: the passphrase is asked again and no wallet is touched). A logout with no session, or a second logout while one runs, changes nothing.
- **SPO-Xmailbox-OUT-117** **A teardown that fails is said, never hidden.** When the close fails (a tunnel did not stop) or the session has not ended within the logout bound of the TUI (15 s), the operator reads "tunnel did not stop" and what to do ("the device may still be online at the relays: quit spo and start it again"), never "logged out". The session is then **stuck**: a new login is refused while it is stuck. If the session ends later and its close succeeded, the TUI says that the teardown completed and allows a login again; if it ends with a failed close, the session stays stuck until the application is restarted (a stuck engine cannot be recovered in process: ADR 0013, "Limits of the tunnel library"). The same holds when the session ends itself (OUT-118) and its close then hangs: its `logging-out` report starts the bound, and a `stuck` report is stuck until the restart even before the command returns. Past the bound the TUI says what is slow: when the session had reported `logged-out` (the clients and tunnels are closed) only the command's return is late, which it says without "tunnel did not stop"; otherwise the close or the loop did not end. `RelayClient.Logout` is bounded itself: when the composite's goroutines have not ended within the bound, the dialers are closed all the same and it returns `ErrTunnelDidNotStop`, so the plain command line's logout says "tunnel did not stop", never logged out. A foreground command of the TUI whose own tunnel did not stop (a revoke-only send, the close of `forget`) tells the TUI (`RelayTunnelStuck`): the TUI is stuck until it restarts. At the end of the program the TUI says on standard error what it waits for ("waiting up to … for the relay session to log out"), waits only for what is left of the bound of a logout under way, and not at all for a session already stuck.
- **SPO-Xmailbox-OUT-118** **The session ends itself, with the full logout.** At `relay_login_max` after login, at the earlier of the deadline on the monotonic clock and the deadline on the wall clock (Go's monotonic clock does not count a suspend on Linux, so a suspended machine ends at the wall-clock deadline; a wall clock set back does not extend the session past the monotonic one; no idle logout: it would defeat receiving); when the binding in use has ended by the device's clock (the binding is renewed by the store sync, OUT-108, so a renewal before the end keeps the session); when a store step fails with an error that says the store handle can no longer be used (the workspace was rekeyed elsewhere, or the handle lost its lock); when a step or the loop fails with an internal error (a recovered panic, `EndFault`). The limit and the binding's end are watched on a goroutine of their own (every second, on the exchange's injected clocks), which cancels the context the steps run under: a store step that waits for the TUI's executor (a foreground command holds it, at a prompt say) is given up, so a foreground command cannot keep the device online past the limit. Each is followed by the logout of OUT-116 and named in the output ("the login limit of 12h0m0s was reached", "the binding ended", "the workspace can no longer be used"). Quitting the TUI while a session runs runs the same bounded logout first; `spo tui` then exits non-zero and says "tunnel did not stop" when the session was stuck or did not end within the bound, as the plain commands do.
- **SPO-Xmailbox-OUT-119** **Forget this device from the TUI.** Running `spo party relay forget` while a session runs first logs the session out (OUT-116) and then runs the command, which is OUT-109 unchanged: it logs in again (the passphrase is asked again), fetches and hands the queue, stores and sends the device revoke, logs out and deletes the binding, and reports per relay (OUT-111: it says revoked only when every listed relay recorded it). A stuck logout refuses to run it. `forget --lost DEVICE` (another device) does not log the session out: its revoke goes over the logged-in session's connections (OUT-120).
- **SPO-Xmailbox-OUT-120** **Foreground mailbox commands use the session.** The session flushes the outbox at every turn of its loop, so what a foreground command queues (a signing request with `request queue`, an answer with `approve` or `refuse`, an envelope offered again with `outbox retry`) is sent through the session's transport and no foreground command dials a relay: after such a command (and after `party outbox status`) the TUI speaks of what waits in the outbox: "the relay session sends it" while logged in; "sent once the relay session has logged in" while it logs in; "stays there: the relay session is logging out or stuck … sent at the next login once the session has ended" while it logs out or is stuck (never "log in" then); "sent when you log in to the relays (party relay login)" when logged out. In the TUI `party request queue` does not print the command line's own "Deliver them with: spo party serve", so the two do not disagree. "Live" (logged in) is distinct from "busy" (any phase but logged out): `serve --transport mailbox`, `connect --transport mailbox`, `forget` (the TUI logs a logged-in session out first, OUT-119), `send-revokes`, and the revoke sending of `forget --lost` and `revoke --import` refuse while the session is busy and not logged in ("logging in, logging out or stuck"), before they store or dial anything. While it is logged in, `serve` and `connect` refuse ("the relay session already exchanges over the relays"), and every revoke send of a foreground command (`send-revokes`, `forget --lost`, `revoke --import` of a lost device) goes over the session's own connections (`RelaySessionRevokes`: the book the command loaded becomes the session's, its revokes go on revoke-only connections of the session's tunnels, the command saves the book) instead of a second dial with the same node key. So the device never holds two logins of its own in one process (and PRE-067 across processes). A command that needs the workspace alone (a rekey, a restore) refused because this TUI's own session holds it open is told to "log out of the relays first", not that another process holds it.

- **SPO-Xmailbox-OUT-121** **A revoke stored while a session runs is sent by it.** At every store sync the session saves its revoke book, loads it again and compares the pending revokes: when another command stored a revoke (`party relay revoke --device X`, say, for a stolen device) or dropped one, the session's clients use the new book at once, and a new revoke is sent at once on revoke-only connections of the session's tunnels, on the loop's goroutine after the sync (`Exchange.Between`), not only at the next connection; what the relays answer is saved at the next sync. The revoke command says so: under a logged-in TUI session "the relay session sends it within seconds"; otherwise "a relay login or serve running for this workspace sends it within seconds; otherwise it goes at the next relay connection, or now with spo party relay send-revokes".

### Preconditions and failures (relay session)

- **SPO-Xmailbox-PRE-065** **What a login needs.** The sealed workspace, opened by the command's own passphrase prompt; a binding of this device (without one the owed revokes are sent first and the command says to bind, OUT-111); at least one listed relay; the tailcat node key of the identity. The TUI runs at most one session; a login is refused while one runs ("already logged in") or while one is stuck (OUT-117). A login cancelled before it connected (the operator cancels the passphrase prompt, or chooses "Log out of relays" while it is open) leaves nothing to tear down and says so ("Not logged in to the relays", or "The login was cancelled before it connected: nothing was logged in"), never "Logged out of the relays".
- **SPO-Xmailbox-PRE-066** **The login limit.** `relay_login_max` is a string that Go's `time.ParseDuration` reads, from 1 minute to 168 hours; anything else (a number, a negative or zero duration, more than 168 hours, unparsable text) refuses the configuration when it is loaded, naming the key.
- **SPO-Xmailbox-PRE-067** **One relay login per workspace, across processes.** Every command that logs in to the relays or dials them (`serve` and `connect --transport mailbox`, `party relay login`, `forget`, `send-revokes`, and the revoke sending of `forget --lost` and `revoke --import`) holds the workspace's relay-login lock for as long as it is logged in or dialling: an exclusive advisory lock (flock, taken without waiting) on `workspace.spo.relay.lock` beside the workspace file (`adapters/relaylock`, `cli.Deps.RelayLock`). A second process is refused at once, before it dials, with "another spo process holds the relay login of this workspace: end it first (Ctrl-C in that process, or Log out of relays in its TUI)". The store's own lock is shared and cannot say this; relays admit two connections per device, and two logins would each keep a revoke book of their own and both flush the one outbox. A command that uses the lock already (a login sending its owed revokes) does not take it twice. It is released at every clean end; when the teardown is stuck (a tunnel did not stop) it stays held until the process ends, kept reachable so no finalizer closes it. The kernel drops it when the process ends however it ends, so a file left by a crash refuses nothing; the file is never followed through a symbolic link and must be a regular file. On a platform without flock (not unix) there is no lock: two processes are not kept apart there.

### Security (relay session)

- **SPO-Xmailbox-SEC-082** **No pool cold key request goes over the session.** The session sends only by `Outbox.Flush` with the composite's network transport, so the outbox's cold-key rule (SPO-Xparty-PRE-004) applies to everything it sends, foreground commands' mail included. The TUI cannot bypass it: it imports no use case but `app/relayloop` and no adapter; `app/relayloop` imports no use case and never names a transport or a sender (an architecture test). In the command tree the session holds the composite as `sessionClient`, an interface with no `Send`, and takes its transport once at the opening; the loop's steps are built by `sessionExchange`, which hands the transport only to the outbox's flush. An architecture test parses `adapters/cli/party_relaynet.go` and refuses a `Send` on `sessionClient`, an embedded interface in it, a `relaySession.client` of another type, a type assertion on the client, a call of `.Send(` and a second `Transport()`. It cannot prove what another file of the package does with `RelayClient` (which has `Send`), nor what the flush function does with the transport (it is `Outbox.Flush`, whose rule has its own tests), and a reflective call or an unsafe cast would pass it.
- **SPO-Xmailbox-SEC-083** **After logout, what of the session's secrets this code holds is wiped; what the tunnel library holds is not.** The local identity the clients signed with is destroyed by the logout; the guarded buffers of the node key and the relay addresses are destroyed once the clients are made; the store handle and its passphrase are closed with the command. The count of live guarded buffers (`secret.Budget().Live`) is back to what it was before the login. The tunnel dialer (`adapters/tailcat/stream`) holds the node private key as a `key.NodePrivate` value, which it clears when its teardown ends, and hands the tunnel library a copy in each `tc.Client`, which it clears after the engine is closed; the relay address (which holds the relay's pre-shared key) is a Go string, as the library's API takes it, so it is dropped (the dialer's and the client's references are set empty) but cannot be wiped. What the library copied from either inside its engine (WireGuard and DERP state) stays in memory until the engine is closed and the garbage collector takes it, and is not wiped; a teardown that is stuck clears nothing of the engine (the concerns file records this residual). The background session never asks the operator anything: a question from it is refused at once, so no secret is typed into a session that runs in the background.
- **SPO-Xmailbox-SEC-084** **The outbox's cold-key flag is the creation rule.** A request the coordinator puts into the outbox carries `ColdKey` from the same rule that refuses to create it for a network (`Coordinator.coldKey`: a pool cold or committee cold role named by the slot, or a key identity whose role history was ever cold), decided for every transport: an item sealed for a file whose flush failed is never flushed into a network later, by a relay session or anything else.

### Invariants (relay session)

- **SPO-Xmailbox-INV-040** **The session is bounded and leaves nothing.** The loop runs on the session command's own goroutine and has ended before the close starts; the composite's goroutines have ended when `Logout` returns (INV-039); after the TUI has shown the end of a session, no goroutine of it is running. The UI's update never waits on the network or on a job: a hostile relay that stalls a fetch or a send, serves junk without end, or refuses this device's identity on every login cannot freeze the UI, and cannot hold a logout beyond the bound of OUT-117 (every network step honours the loop's context; past the bound the session is reported stuck). A handler error that persists (the envelope is not acknowledged, as `serve` does not acknowledge an envelope it could not handle, so the composite serves it again at once) is told once while it persists, through the teller, and the next fetch waits one receive window; an envelope refused by the handler is handled (with a refusal) and acknowledged as before. A panic in a store step does not end the process: the TUI's executor recovers it in the job's goroutine and returns it as the step's error (`relayloop.ErrInternal`), the loop ends (`EndFault`) and the full logout runs, the terminal stays in the state the TUI keeps, and the UI says the session ended with an internal error, its text cleaned (OUT-115). Foreground commands run under the same recovery (`execute`).

### Choices that go beyond the ADR text (work package 9)

- **The session is the login command, run in the background.** ADR 9 has the TUI run commands of the tree and nothing else; the session is the tree's own `party relay login`, so its refusals, output and logout are the command line's. The TUI adds a host (executor, status, bounded logout) and two menu entries, which is the amendment of decision 9.
- **The session keeps its own handle of the workspace for its lifetime.** Each foreground command opens the workspace with its own handle, as before (the store's shared lock allows it). A command that needs the workspace alone (a rekey, a restore) is refused by the store with "open elsewhere" while a session runs: log out first.
- **"Store lock" is the end of the handle.** The TUI has no lock action and no idle timeout (ADR 0014 decision 9: "There is no in-process lock action today"). The session ends itself when its store handle says it can no longer be used, which is what a lock of the workspace from elsewhere looks like to it.
- **Foreground mail goes out through the session's flush.** The outbox commands never dialled; they queue. Sending is the session's flush, which runs at every turn of the loop (at most the receive window apart), so "use the session's transport" needs no new path. The commands that do dial (revoke sending) go through the logged-in session's connections (OUT-120), so no foreground command opens a second connection with the same node key.
- **Forget logs out and logs in again.** Decision 8 says "log in if needed" before forget; running the command after a logout reuses `relayForget` unchanged (one more login, no wallet touch) instead of a second forget path inside the session.
- **"Connected" means an exchange succeeded.** The composite reports failures, stores and acknowledgements, not a long-poll that is waiting, and its making dials nothing; a relay is shown `waiting` until its first exchange and `connected` after one, until a failure. A relay that stays quiet (no mail, nothing sent) stays `waiting`: that is what the session knows of it.
- **Approvals are a header indicator and a list, not a pop-up.** ADR 0014 decision 9 says approvals are "surfaced as notifications"; the TUI shows "requests waiting for review: N" in the header on every screen while a session runs, counted from the store by the session's sync (never from a peer's text), and lists their review ids on the session screen. The review and the approval stay foreground commands. After logout the count is not shown: nothing reads the store for it then.
- **Outbox commands queue; they do not fail without a login.** Decision 9 says foreground mailbox commands "with no login fail and say log in first". They queue instead and say how what is queued gets sent (the session's flush, or a login), because queueing loses nothing and a request prepared before the login is the common case; a command that would dial (send-revokes and the revoke sending of forget --lost and revoke --import) goes through the logged-in session, or refuses while it is busy.
- **One relay login per workspace is a lock file, not the store's lock.** The store's lock is shared by design (foreground commands open the workspace beside the session); the relay login takes its own exclusive lock (PRE-067).
- **The logout bound of the TUI is 15 s**: the 10 s of `CloseWithin`, the 2 s of the book's save and a margin. Past it the session is stuck even if the tunnel would have stopped later (OUT-117 then allows a login again once it did).

## The DERP region pin (ADR 0015 work package 1)

What keeps a relay's address the same when its process restarts or moves. tailcat's address is `"tc"` and base64url of a CBOR `ConnInfo`: the server's node public key, its disco public key (derived from the node key by `discoPrivateForNode`), the pre-shared key, and a **full DERP region**, with no region id: `ConnInfo.Addr` zeroes `RegionID`, `RegionCode`, `RegionName` and a node's `Name` next to its `HostName` (`tailcat.go`, `Server.TailcatAddr`, `locoBackend.tailcatAddr`, `ConnInfo.Addr`; `wire.go`, `wireRegionOf`). `Server.startLocked` takes `Region` as given, or, with `RegionID` set and `Region` nil, fetches the map and embeds that region's description from it; with neither it picks the nearest region by latency at every start. So the address is fixed only when the region's description is. The packages are `domain/relayconf` (the pin as checked values), `adapters/relayconfig` (its keys), `app/relayhost` (`TunnelSpec`), `cmd/spo-relay` (`listenerConfig`) and `adapters/tailcat/stream` (`ListenerConfig.Pin` and `RegionID`, `region.go`).

### Interfaces (region pin)

- **SPO-Xmailbox-IF-030** **The pin, from the file to the listener.** Two forms, at most one: `[relay] derp_region_id` (1 to 65535, a region of the DERP map) and the table `[derp_region]` (`region_id` 1 to 65535, required; `region_code` optional) with 1 to 8 `[[derp_node]]` tables (`name`, `host_name`, `cert_name`, `ipv4`, `ipv6`, `stun_port`, `derp_port`). They become `relayconf.Config.DERPRegionID` and `DERPRegion` (`relayconf.DERPRegion`, `DERPNode`), `relayhost.TunnelSpec.RegionID` and `Region` (the tunnel's own copy), and `stream.ListenerConfig.RegionID` and `Pin` (`stream.RegionPin`, `RegionNode`; copied field by field by `cmd/spo-relay`'s `regionPin`). The listener's `Region` (a raw `tailcfg.DERPRegion`) is the in-process test rig's form; `cmd/spo-relay` never sets it.

### Outputs (region pin)

- **SPO-Xmailbox-OUT-122** **One region for every build, and the address checked against it.** `stream.Listen` resolves the region once: the `Pin` as configured, or the region of `RegionID` taken from the map fetched once at `Listen` (as a client fetches it), or `Region` as given; two forms are refused before the network is touched. Every build and every rebuild after `SetAllowed` gets a copy of that region as `tailcat.Server.Region`, so tailcat fetches no map and picks nothing. After each build the engine's address must be byte-equal to the encoding of the node key, the pre-shared key and that region (`pinnedAddr`, the same `ConnInfo.Addr` that `Server.TailcatAddr` uses); otherwise the start fails with `ErrRegionMismatch`, and a rebuild fails closed as before (SEC-033). With a full region the address is therefore byte-equal at every start and rebuild with the same key, pre-shared key and region, and changes when any encoded field of a node changes (host name, certificate name, IPv4, IPv6, STUN port, DERP port, the nodes and their order); the region id, the region code and a node's name next to a host name are not in the address. With a region id the region is fixed but the address is the map's current description of it: a change of that region's nodes in the map changes the address at the next start (tailcat caches the map in the process for up to an hour). `serve --print-address` prints the address of the pinned region; `check-config` and `serve` say in their summary which form is in force.
- **SPO-Xmailbox-OUT-123** **Unpinned, the relay behaves as before and says so once.** Without a pin the listener lets tailcat pick a region at every build, as before this package, and `relayhost.Start` writes one line to the operator log, `derp_region=unpinned`, that the address may change at the next start and names `[derp_region]` and `derp_region_id`. With a region id it writes one line, `derp_region=map`, that the address follows the map. No mode refuses a missing pin yet: `relayconf.Config.RegionPinRequired` is the hook, false in this build, which the object-store mode of ADR 0015 is to make true, and then only the full region satisfies it.

### Preconditions and failures (region pin)

- **SPO-Xmailbox-PRE-068** **The pin's rules.** The two forms are refused together; `derp_map_url` is refused with `[derp_region]` (no map is fetched); a `[[derp_node]]` without `[derp_region]`, a `[derp_region]` without a node or without `region_id`, a ninth node, a key not listed, a value of the wrong kind and a port of 0 or above 65535 are refused at load. A node's `name` is 1 to 64 of letters, digits, `.`, `_` and `-`, unique in the region; `host_name` is a lower-case DNS name (labels of 1 to 63, at most 253 bytes, a last label that is not all digits) or an IP literal without a zone; `cert_name` is such a DNS name or `sha256-raw:` and 64 lower-case hex digits; `ipv4` and `ipv6` are empty, `none` or an address of their family, not both `none`. `region_code` is 1 to 32 of `a` to `z`, `0` to `9` and `-`. `Config.Check` applies these again, so a configuration changed after its load cannot start with a bad pin, and `SameExceptDevices` compares the pin, so a reload refuses another pin. The region a `derp_region_id` takes from a fetched map is held to the same node rules (`relayconf.DERPNode.Check` on each node, at most eight nodes, names unique, ports 0 to 65535): a map's node that a `[[derp_node]]` could not be refuses the start with `ErrRegionBadNode`, and no other region is used. Only the full `[derp_region]` form pins the DERP server itself: with `derp_region_id` the map's operator decides the nodes, their host names and their certificate names.
- **SPO-Xmailbox-PRE-069** **A pinned region that is absent, silent or not the configured server refuses the start.** A region id the fetched map lacks, or whose region has no DERP node, fails `Listen` with `ErrRegionNotInMap` naming the id and the map. A pinned region (either form) is then probed by an authenticated contact: a DERP connection (`derphttp` region client with a throwaway node key) to its DERP nodes in order, over TLS verified by each node's rules (`cert_name`: the name the certificate carries, or `sha256-raw:` and its hash; a probed region is a pin or a map's region copied without its test-only fields, SEC-085), followed by the DERP handshake, in which the server names its key. A STUN answer does not count: it proves neither the DERP port nor the certificate, and anyone on the path can give one. When no node completes the contact before the start's context ends (a wrong certificate name or hash, the DERP port down while STUN answers, an impostor), the start fails with `ErrRegionUnreachable`, which names the region and says to check `host_name`, `cert_name` and `derp_port`; `serve --print-address` then prints nothing. Both are bounded by `relayhost`'s start timeout (60 s by default; the DERP client gives up after 10 s) and no other region is ever used. The relay then exits with status 1, as every tunnel failure does (OUT-101). The probe proves the DERP server is reachable and the configured one at the start; it does not prove that the engine's own DERP connection, made after it, succeeds.

### Security (region pin)

- **SPO-Xmailbox-SEC-085** **TLS to a pinned region is always verified.** Nothing in the configuration can turn DERP's TLS verification off: no key of `[[derp_node]]` maps to tailcat's test-only flag, `regionPin` sets only the listed fields, and a region taken from a fetched map is copied field by field without its test-only fields. A self-signed DERP certificate is pinned by its hash (`cert_name = "sha256-raw:…"`), which tailcat's TLS dialer checks (`tlsdial.SetConfigExpectedCertHash`, with the host name and the validity dates). The end-to-end test of `cmd/spo-relay` reaches the in-process DERP server this way, with no test-only path. **The tunnel library's debug knobs are refused.** tailcat and tailscale read environment variables named `TS_DEBUG_*`: `TS_DEBUG_ADDR` makes the library print the tunnel address, which holds the pre-shared key, to the standard error through Go's global `log` package (past the relay's filtered logger), and `TS_DEBUG_USE_DERP_HTTP` turns TLS to DERP off for the whole process. Every tunnel start (`stream.Listen` of `spo-relay`, `stream.NewDialer` of `party relay login` and the TUI's relay session, `tailcat.NewServer` of `party serve`, `tailcat.NewClient` of `party connect`) first runs `platform/tunnelenv.Prepare`: when any variable of the prefix `TS_DEBUG_` is set (the whole prefix, not a list, so a knob added to the library later is refused too), the start is refused before a key is read or the network is touched, with an error that names the variables (never their values) and says to unset them; `spo-relay serve` then exits with status 1. Then the global `log` output of the process is discarded, so a line the library writes there, now or in a later version, reaches no stream. **What the operator of the DERP server can do.** The DERP server, which the relay's configuration names and the address embeds, sees which node keys connect and when, and the size and timing of every packet between them; it can send a "meow" ping in the name of any node key it has seen and learn from the reply (a reply comes only to a listed key) whether the key is on the relay's list (a membership oracle); it relays disco messages and sees each device's disco key; and because the relay keeps the first disco key a "meow" names for a node key until its tunnel is next rebuilt, a forged "meow" sent before the device's own binds that listed node key to a disco key of the operator's choosing until then (the device's disco messages, and so a direct path, then fail; the WireGuard session does not open to the operator); it can drop, delay or replay packets, and so deny service. It cannot read or change what the tunnel carries (WireGuard with the pre-shared key) and cannot impersonate the relay or a device to the other (node keys). No mitigation on this side is cheap and safe; the pin chooses which operator is trusted.
- **SPO-Xmailbox-SEC-086** **A connection reset before it is admitted does not crash the relay.** (Found by the race run of this package.) gonet's `TCPConn.RemoteAddr` returns nil once the endpoint is gone, and tailcat's `Server.PeerEnv` calls `remote.String()` on it, so a peer that resets its connection between tailcat's accept and the listener's peer lookup panicked the relay process. The listener's peer lookup (`peerFunc`) treats a connection without a local or a remote address as unidentified (`Stats.Unidentified`, closed with a reset) and never passes it to `PeerEnv`; a panic inside the library's lookup is recovered, the connection is closed with a reset unserved, and it is counted on its own (`Stats.PeerPanics`, not `Unidentified`: it is a library bug, not a peer without an address); the first such panic of the process is logged once, and later ones are only counted. The envelope transport's server (`adapters/tailcat/server.go`) has the same rule (SPO-Xparty-SEC-004). The DERP server's operator, who relays the disco messages, is not trusted beyond what SEC-085 lists.

### Choices that go beyond the ADR text (region pin)

- **The full region is the recommended form, the region id is kept with its honest meaning.** The ADR offered both as equal; the encoding shows only the full region fixes the address. `derp_region_id` stays because it fixes which region a host relay uses without copying host names, and the log and the summary say that its address follows the map.
- **The region is probed at the start.** The ADR says the pinned start needs no region probe; a probe of the one pinned region is what makes "cannot be reached at start fails the start" testable, and costs one STUN exchange when the region answers.
- **The map is fetched in client mode**, the whole map, so the pinned region is not looked up in a map the server may have narrowed by the caller's address (tailcat's comment on `Expand`: "Assume the server filtered the map based on our IP when the Tailcat-Mode header was server"). What the public map server does with the header is not checked.

## The registry core and the ports for a store that is not a directory (ADR 0015 work packages 4 and 5)

What lets a store that can refuse a deletion, lose an answer or lose its writer stand behind the relay's ports, without naming the store. The packages are `domain/relayregistry` (the plans), `ports/relayport` (the lease, the store errors, the refresher, the held-body bound), `ports/relayport/relayporttest` (the contract suites, the in-memory lease and registry), `adapters/bindingstore` (the directory store, which follows the same order), `app/relay` (the session's answer to a lost authority) and `app/relayhost` (the start order and the exit). The object-store adapters are later packages.

### Interfaces (store ports)

- **SPO-Xmailbox-IF-031** **The lease.** `relayport.Lease` has `Acquire(ctx)`, `Renew(ctx)`, `Release(ctx)`, `Until() (time.Time, bool)` and `Lost() <-chan struct{}`; a value is used once. `Acquire` waits while another holder has the lease and takes a released one at once, a lapsed one only after seeing it unchanged for the duration plus the margin, and then waits the drain before it returns. A confirmed renewal holds the lease from the time it was sent for the term (duration minus margin); a renewal refused, sent after the end, or answered after the end returns an error wrapping `ErrAuthorityLost` and closes `Lost`; any other error leaves the lease as it was. `Until` is the end on the lease's monotonic clock (zero with ok: no end). `relayport.RequestContext(ctx, lease, now, max)` gives a request's context, bounded by the earlier of `max` and the lease end, or `ErrAuthorityLost` when the lease is not held, lost or past its end. `relayporttest.RunLease` is the contract (with optional hooks: a second holder, a theft, late answers); `relayporttest.LeaseStand` and `FakeLease` are the in-memory lease that passes it with every hook; `relayhost.SingleHostLease` passes it without them. *Amended in the review of work packages 4 and 5:* `Release` is called only when no request may still land (SPO-Xmailbox-OUT-129); how the relay keeps the lease is SPO-Xmailbox-INV-045.
- **SPO-Xmailbox-IF-032** **The store errors.** `relayport.ErrAuthorityLost` (the process is no longer the writer: lease lost, or a conditional write met a change a read-back does not explain), `ErrOutcomeUnknown` (storage did not confirm and a read-back could not settle it; the caller claims no success) and `ErrDeleteRefused` (a deletion refused because a retention has not ended on the store's clock; never a failure of the call that needed it). They are distinct; the directory adapters return none of them. *Amended in the review of work packages 4 and 5:* the directory registry returns `ErrOutcomeUnknown` (wrapped with the cause) for a file renamed or unlinked whose directory sync then failed, and `ErrAuthorityLost` when such a write stays unconfirmed past its bound (SPO-Xmailbox-INV-044); the directory mailbox store still returns none.
- **SPO-Xmailbox-IF-033** **The tombstone refresher.** `relayport.TombstoneRefresher.RefreshTombstones(ctx) (relayregistry.MergeResult, error)` is part of `Registry`: it merges what storage holds and this process did not write (`Core.MergeTombstones`) and names the served bindings that became invalid. The directory store and the in-memory registry find nothing (the in-memory one finds what `Learn` put there); a closed registry answers `ErrRegistryClosed`. `relayport.TombstoneRefreshEvery` is 60 s. *Amended in the review of work packages 4 and 5:* the refresh, and the sweep, first settle the operations whose outcome storage did not confirm (SPO-Xmailbox-INV-044); the directory store's refresh does that and finds nothing else, and fails only on a closed registry or a directory sync that keeps failing.
- **SPO-Xmailbox-IF-034** **The stores and the lease in the assembly.** `relayhost.Deps.OpenMailbox(spec StoreSpec, env StoreEnv)` and `OpenRegistry(spec, cfg, env)` take a `StoreSpec` (a `StoreKind`, `StoreDirectory` the only one built, and its directory) and a `StoreEnv` (the clock and the lease). `Deps.OpenLease(relayKey, clock)` makes the lease; nil is `SingleHostLease`, which has no end, so the binary with directory stores starts and stops as before. `Start` runs in this order: the lease (acquired), then the stores (the load), the server, the sweeper, then the tunnel; it refuses with `ErrAuthorityLost` and starts no tunnel when the lease is lost before the tunnel would start, and a failed start releases the lease unless it was lost. The lease is renewed every `DefaultRenewEvery` (10 s; `Deps.RenewEvery`), each renewal bounded by `RequestContext` with `DefaultRequestTimeout` (10 s). *Amended in the review of work packages 4 and 5:* the lease is renewed at a quarter of its term (SPO-Xmailbox-INV-045; `DefaultRenewEvery`, now 5 s, is the interval of a lease without an end); `Deps.RequestTimeout` replaces `DefaultRequestTimeout` (a test's); SIGTERM during `Start` ends it as a planned stop (SPO-Xmailbox-OUT-132).
- **SPO-Xmailbox-IF-035** **The rate state port.** `relayport.RateSaver.SaveRates(ctx) error` is part of `Registry`: the adapter stores `Core.Rates(now)` (the two buckets, `relayregistry.RateSnapshot` of two `RateState{Units, At}`, `RateUnitsPerToken` units a token) and loads them at open with `Core.RestoreRates` (SPO-Xmailbox-OUT-130). The relay calls it after every successful tombstone refresh and once at a planned stop, before the stores close, through `Server.SaveRates` (under the server's authority: nothing after a loss). The directory store and the in-memory registry keep no rate state and return nil (`ErrRegistryClosed` once closed); the buckets of a directory relay start full at a restart, as before.

### Outputs (registry core and store ports)

- **SPO-Xmailbox-OUT-124** **Room is planned on its own, and a refused drop is held back.** `PlanRevoke` holds no drop. `Core.PlanRoom(rec, now)` plans the drops of expired tombstones that make room for the tombstone `rec` adds, in a stable order, only when they would make room (an invalidating revoke at the bound, while the drops leave room under the hard size; a revoke of nothing at the limited share, while the drops leave room in it and the revoke cap has a token), and none for a raise. An adapter carries each out before the revoke; one that storage refuses (`ErrDeleteRefused`) or that fails is not made and is held: `Core.Hold(tomb, now + HoldSeconds)`, so neither `PlanRoom` nor `PlanSweep` plans it until then, and it stays loaded and enforced. The revoke is then planned with the room there is. A sweep skips a refused drop, counts it in `SweepResult.Held` (and not in `Tombstones`) and goes on. `Stats.HeldDrops` counts the holds. With every drop refused at a table full to its hard size, an invalidating revoke deletes its bindings and returns `ErrTombstoneUnrecorded`, and one that invalidates nothing returns `ErrTombstoneFull`. *Amended in the review of work packages 4 and 5:* a drop that failed for another reason than a refusal (an I/O error, a request without an answer) is held for `HoldErrorSeconds` (60 s), not an hour; a refusal (`ErrDeleteRefused`) keeps `HoldSeconds` (3600 s).
- **SPO-Xmailbox-OUT-125** **A raise names the tombstone it replaces.** An `OpPutTombstone` over a stored tombstone of the same scope key has `Replaces` and `Prev` (the stored not-before), so that a store keeps one object per scope key and overwrites it (a new version, conditional on the one it holds); without `Replaces` the store creates the name. *Amended in the review of work packages 4 and 5:* an operation on a scope key (or a device) whose last write is unconfirmed has `Retry` set: the write planned again by a replay, or a raise whose `Prev` storage may not hold; an adapter that keeps versions or ETags reads the object back before it writes.
- **SPO-Xmailbox-OUT-126** **Tombstones learnt while running.** `Core.MergeTombstones(values, now)` merges tombstones that storage holds: the maximum wins, nothing is lowered, a value with no scope or a not-before outside 0 to `relaybind.MaxTime` is ignored and counted, and a merged tombstone is kept whatever the table's bound. The result counts the raised ones and lists, by device, the bindings that were served and are invalidated now; it changes no binding on storage (a sweep removes them, OUT-081). The relay runs `Server.RefreshTombstones` every 60 s while it serves, which ends the sessions of those devices with the binding code and keeps their queues. *Amended in the review of work packages 4 and 5:* a value at least as high as an unconfirmed write of the same key confirms it (SPO-Xmailbox-INV-044); each refresh is bounded by the request timeout (SPO-Xmailbox-OUT-131); a refresh whose context was cancelled (a tick that raced the stop) logs nothing, and after a lost authority it calls nothing.
- **SPO-Xmailbox-OUT-127** **A lost authority claims no success and ends the relay.** Every store call of the server is watched for `ErrAuthorityLost`. The call is answered as a store failure is: a put `unavailable`, a revoke `refused` (whatever its partial result says), a request the "shutting down" code. The session that made the call then ends with the "shutting down" code (reason `authority`), every other session ends with it too, the event `authority_lost` is logged once, and `Serve` returns `relay.ErrAuthorityLost`. The host calls `Server.LoseAuthority` when its lease is lost, and the sweeper (`WithAuthority`) and the tombstone refresh when they see the error. `Run` then tears down as for a stop, closes the stores, does not release the lease and returns `relayhost.ErrAuthorityLost`; `serve` exits 4 (OUT-101). *Amended in the review of work packages 4 and 5:* what happens between the call that reported the loss and `LoseAuthority` is SPO-Xmailbox-SEC-088; the reporting session's answer is written under the short bound of a closing session's last frame (2 s at most), not the write timeout; `Sweeper.WithAuthority` takes the `*Server` (not a function), and the sweep is gated and ends the relay the same way.
- **SPO-Xmailbox-OUT-128** **A tombstone whose outcome is unknown is enforced and not recorded.** When storage does not confirm a tombstone's write (`ErrOutcomeUnknown`; in the directory store a sync that failed after the rename), the registry applies it with `Core.ApplyUnknown`: every reader enforces it, the bindings it invalidates are not served and are named in the result (the session ends their sessions and purges their queues), and the result has `Recorded` false and `Unconfirmed` true (`PartialRevoke(plan, applied, unknown)`). The session answers `refused`, never `recorded`, so the client sends the revoke again; the replay's plan holds the same write (`Op.Retry`, charged nothing), whose success records it. An unknown outcome is not a lost authority: the relay goes on serving.
- **SPO-Xmailbox-OUT-129** **A planned stop lets the lease lapse while a request may land.** The server counts the store calls that may have reached storage without an answer (`Server.Unanswered`): a write (put, ack, retract, purge, register, revoke, expected senders, sweep, refresh, rate save) whose error wraps `ErrOutcomeUnknown`, `context.Canceled` or `context.DeadlineExceeded` and whose context was live when it started; a read is not counted, nor an answered failure. At a planned stop `Run` saves the rate buckets, then reads `Unanswered` and the registry's `Stats.Unconfirmed` before the stores close: when either is above zero, or the statistics cannot be read, the lease is not released (`stopped lease=lapses reason=unanswered|unconfirmed|registry`), so the taker waits out its drain; otherwise it is released as before. The exit status is that of a planned stop (0).
- **SPO-Xmailbox-OUT-130** **The rate buckets across a restart.** `Core.Rates(now)` exports the two buckets (new bindings, revokes of nothing) as their level at `now`; `Core.RestoreRates(snapshot, now)` loads them. Each value is checked first: `Units` 0 to the largest burst any configuration may have (10 tokens of `RateUnitsPerToken` = 3600 units each) and `At` 0 to `relaybind.MaxTime`; one outside is refused with `ErrRateState` and nothing changes. A restore can only take tokens away: each bucket becomes the lower of what it holds and the stored level refilled at this configuration's rate from `At` to `now`, capped at this configuration's burst; a stored `At` in the future gains no refill and freezes none.
- **SPO-Xmailbox-OUT-131** **Stale tombstones lose the authority.** Each tombstone refresh is bounded by the request timeout (`DefaultRequestTimeout`, 10 s), so a store that does not answer cannot stall it or the teardown. `relayhost.StaleRefreshes` (3) refreshes in a row that fail (three minutes at the default period) log `tombstone_refresh_stale` and call `Server.LoseAuthority`: the relay stops as for a lost lease (exit 4). A refresh that succeeds resets the count.
- **SPO-Xmailbox-OUT-132** **SIGTERM during the start is a planned stop.** `serve` watches the signals while `Start` runs (the lease may be another process's for a while): `SignalStop` cancels the start's context, and a start that fails for it exits 0 with "stopped before serving", having started no tunnel; a reload during the start is ignored with a line on standard error. A start that finished as the stop came is stopped at once as a planned stop; a stuck teardown (3) and a lost authority (4) keep their status.

### Preconditions and failures (registry core)

- **SPO-Xmailbox-PRE-070** **The load reads versions, up to a ceiling.** `Core.LoadTombstoneVersion(key, notBefore)` loads one version of a tombstone; several versions of one scope key give the highest, whatever their order. It counts them and refuses the one past `relayregistry.MaxTombstoneVersions` (1 048 576: twice the about 530 thousand versions both rate caps allow over a tombstone's life) with `ErrTombstoneVersions`, changing nothing, so the load fails closed. *Amended in the review of work packages 4 and 5:* `LoadTombstone` and `LoadTombstoneVersion` range-check the value as `MergeTombstones` does: a key with no scope or a not-before outside 0 to `relaybind.MaxTime` is refused with an error wrapping `relaybind.ErrRange`, nothing changes and the version is not counted; the directory store's load then refuses to open (fail closed).

### Security (registry core)

- **SPO-Xmailbox-SEC-087** **A failed drop never leaves a revoked binding live.** In both the directory store and the in-memory registry the drops that make room run first and none of them can stop the revoke: the revoke's own plan, the tombstone then the binding deletes, runs whatever the drops did. Before this package, `bindingstore.execute` stopped at a failed drop, before the tombstone and before the deletes. *Amended in the review of work packages 4 and 5:* a tombstone renamed into place whose directory sync then failed is no longer `recorded` (SPO-Xmailbox-OUT-128).
- **SPO-Xmailbox-SEC-088** **Nothing reaches the store after a lost authority.** Every store capability the server holds is the authority wrapper (`watched`): the writer, the reader, the acker, the retractor, the usage reader, the registry, and also the purge of the revoke path (`MailboxRevoker`) and the eviction guard's read (`relay.New` points the `Guard` at it). The moment one call returns an error wrapping `ErrAuthorityLost` the server is marked, and from then on: every wrapped call returns `relay.ErrAuthorityLost` without reaching the store (a body being read stops too); `admit` refuses a new connection with the "shutting down" code (reason `authority`); `login` registers and replaces nothing; a revoke's result is acted on only in memory (the invalidated devices' sessions end; no purge, no fallback lookup, no stranger release); no put is compensated (`retractOwn`); the guard answers "not evictable"; `Server.RefreshTombstones`, `Server.SaveRates` and a sweep under `WithAuthority` call nothing and end the relay. The marking is immediate; `LoseAuthority` follows when the reporting session ends, or at once from the sweep and the refresh.
- **SPO-Xmailbox-SEC-089** **A put waits for the store no longer than its body may take.** The context of `MailboxWriter.Put` ends at the session's body deadline (the earliest of `BodyTimeout`, the connection's lifetime and the binding's end), so a put that waits for a slot to hold its body (an adapter of ADR 0015 decision 2) is answered `unavailable` at that deadline, not at the end of the session.
- **SPO-Xmailbox-SEC-090** **A store cannot hand out rate tokens.** A restored rate bucket is never fuller than the bucket was before the restore, nor than the stored level refilled since its time, capped at the burst (SPO-Xmailbox-OUT-130). A bucket starts full, so a hostile store, a rolled-back snapshot or a missing one gives at most what a restart without stored state gives: one burst. A future-dated snapshot cannot freeze the refill.

### Invariants (registry core and lease)

- **SPO-Xmailbox-INV-041** **An unknown outcome keeps the stricter state.** `relayregistry.ApplyWhenUnknown(op)` is true only for a tombstone written and a binding deleted: an adapter whose storage could not confirm an operation applies it to memory only then, so memory never serves more than storage may hold. *Amended in the review of work packages 4 and 5:* the rule is `Core.ApplyUnknown(op)`, which applies the operation only in those two cases, reports whether it did, and keeps it unconfirmed (SPO-Xmailbox-INV-044); the exported `ApplyWhenUnknown`, which had no production caller, is gone.
- **SPO-Xmailbox-INV-042** **Two holders never both hold the lease.** A taker takes a lapsed lease only after its holder's end (the holder's end is at most the term after its last write, the taker waits the duration plus the margin after first seeing that write); a renewed lease is never taken; a theft or a late answer is a loss for the old holder. The defaults are a duration of 30 s, a margin of 10 s (a term of 20 s, a wait of 40 s) and a drain of 15 s.
- **SPO-Xmailbox-INV-043** **Serve leaves no goroutine.** `Server.Serve` starts no goroutine of its own besides its sessions and its bounded reject writers, and waits for all of them before it returns, whichever way it returns (the context ends, the listener closes, an accept fails, the authority is lost): the lost authority cancels it through a callback registered on the server's lost context (`context.AfterFunc`), unregistered when Serve returns. An idle Serve is one goroutine.
- **SPO-Xmailbox-INV-044** **An unconfirmed operation is settled or ends the relay.** `Core.ApplyUnknown` keeps every operation it applied as unconfirmed, with the relay time it was first applied (sending it again does not move that time); `Stats.Unconfirmed` counts them. One is confirmed by a later confirmed write of the same thing (`Apply`: the scope key written or dropped; the device written with `Persist`, or deleted), by a stored value at least as high (`LoadTombstone`, `MergeTombstones`; never by memory's own merged value), or by a read-back: the adapter's `Sweep` and `RefreshTombstones` list them (`Core.Unconfirmed`) and give each read-back to `Core.Settle(u, ReadBack, now)`: `ReadBackApplied` confirms it, `ReadBackNotYet` returns the same operation to send again (`Retry`), `ReadBackCannotTell` keeps it. One unconfirmed for `UnconfirmedSeconds` (180 s, three refresh periods) makes `Settle` and `Core.Overdue` return `ErrUnconfirmed`, which the adapter wraps with `ErrAuthorityLost`: a read-back that does not show a write is a conflict (ADR 0015), and the relay stops; it never writes other content in its place. The directory store maps a sync that now succeeds to `ReadBackApplied` and one that fails to `ReadBackCannotTell`; an object store maps its client's read-back (package 8).
- **SPO-Xmailbox-INV-045** **How the lease is kept.** The relay renews a lease that has an end at a quarter of its term (read from the lease when it is taken: 5 s at the defaults). A renewal that fails without saying the lease is lost is tried again after 250 ms, doubling to at most 2 s (`RetryMin`, `RetryMax`), while the time left exceeds the request timeout (10 s), and at the regular interval after that. The loss is declared when the time left falls below an eighth of the term (2.5 s at the defaults) without a confirmed renewal, so the relay stops serving before its lease ends. The renewal runs on its own goroutine, so a `Renew` that ignores its context cannot hide the lease end (its late answer is dropped); the end timer is a real timer set from the relay clock's reading, and each wake checks the lease on that clock again (`relayport.Clock` has no timer). One and two failed renewals are survived at the defaults.

### Choices that go beyond the ADR text (work packages 4 and 5)

- **The drops run before the revoke, as the ADR says, and any failure of one is held.** The ADR names a store's refusal; the directory store's own I/O error on a drop is treated the same way in a revoke (held, not made, no failure of the revoke), so the fix holds for both stores. In a sweep only a refusal is skipped; another error still fails the sweep, as before.
- **The single-host lease, not the `flock`, is the directory default.** The stores keep their own lock from `Open`; the lease has no end and nothing to renew, so a host relay behaves exactly as before.
- **The refresh ends sessions and does not purge queues.** The revoke that recorded the tombstone purges where it ran; a learnt tombstone may come from a stale writer whose purge is lost, and that gap is the one ADR 0015 records (m2).
- **A revoke answered after a lost authority is `refused`, even with a tombstone recorded.** The client keeps it pending either way (ADR 0014 decision 8), and nothing this process did may be claimed after the loss.
- **The exit status of a lost authority is 4**, with 3 winning when the tunnel is stuck too (OUT-101).
- **Not built here:** a lease of the object store (package 6). The rate buckets' export and load are built (SPO-Xmailbox-OUT-130, IF-035); the directory store does not persist them (one host, restarted by its operator), and what an object store does with a missing or invalid stored state is package 8's to decide (starting full is today's behaviour and the bound of SEC-090).
- **The window after a lost authority is closed by marking, not by an early LoseAuthority.** Calling `LoseAuthority` from the failing call would cancel the reporting session before its answer, so the client would not learn that its put was not stored; the mark stops every store call at once instead, and the answer is written under a short bound.
- **The unconfirmed bound is three refresh periods (180 s),** not the 15 minutes a lost request may stay valid at the store: memory enforces the operation the whole time, so the bound limits how long this writer runs ahead of storage, and the successor of a writer that stops for it waits out the drain.
- **The loss is declared an eighth of the term before the lease end,** so the relay has stopped serving when its lease ends; every request is bounded by the lease end anyway (`RequestContext`).

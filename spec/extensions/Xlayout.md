# Xlayout: the object layout

This spec is not upstream behaviour. It specifies the format that [ADR 0012](../../docs/explanation/adr/0012-server-backup-and-deployment.md) stage 3 freezes (decision 3, "Staged freeze", and decision 4): the stored object, its envelope, the body of a record, an audit row, a manifest page and root, the slots object and the provisional head note. The first part (OUT-001 to OUT-013, PRE, SEC-001 to SEC-005, INV-001 to INV-006) is a pure format: no store, adapter, file or network is involved. The package is `internal/domain/layout`; the envelope is `internal/platform/seal` (`SealObject`, `OpenObject`). The last part, "The exporter", specifies work package 3, `spo store convert --to-layout DIR` (use case `internal/app/layoutexport`, adapters `internal/adapters/layoutdir` and `sqlitestore.TakeExport`): it writes a workspace into a directory in this format, and nothing else. The part after that, "The verifier and the importer", specifies work packages 4 and 5: `spo store verify --layout DIR` and `spo store convert --from-layout DIR` (use case `internal/app/layoutread`). Opening a layout read-only (`spo -C DIR`) is a later work package.

Terms: a **stored object** is the bytes a bucket holds. A **sealed object** is a stored object with format byte `0x01`. A **bucket** is an allowed stored size. The **body** is what the AEAD seals. The **epoch** is the 16-byte key epoch of ADR 0003. **W** is the width of the wrapped-key field of a record body.

What is not frozen here: heads, roots, devices documents, location statements and the `parent` field of the manifest root carry a provisional format and may change at stage 5 (ADR 0012 decision 3). Signing a head is not done here; this spec names only the note and the SSHSIG namespace.

Several choices below differ from or go beyond the ADR text (the 16-byte epoch, the sealed kind and class, zero padding checked on open, W, the 4 MiB largest bucket, a separate envelope key, the manifest pages, the contents of `meta`, the head note and the format byte `0x02`). They are listed in the implementation notes of the ADR as proposed amendments, awaiting the owner.

## Outputs

- **SPO-Xlayout-OUT-001** The name of an object is the lower-case hex Blake2b-256 of its stored bytes, 64 digits. Its path is `objects/<first two hex digits>/<name>`, which satisfies `ports.ValidObjectName`. A name that is not exactly 64 lower-case hex digits has no path.
- **SPO-Xlayout-OUT-002** A stored object starts with a plaintext header of 17 bytes: a format byte and the 16-byte key epoch. Format `0x01` is a sealed object, `0x02` the slots object, `0x03` is reserved for chunked objects and refused in this version. Any other byte is refused. (The ADR text says an 8-byte epoch; the store's epoch is 16 bytes and 16 is used.)
- **SPO-Xlayout-OUT-003** The stored length of every object is exactly one of 4 KiB times 2^i for i = 0 to 10; the largest is 4 MiB (4194304 bytes). A body that does not fit the largest bucket is refused with an error that names the size; it is never chunked and never moved to a larger bucket. The body is placed in the smallest bucket that holds it.
- **SPO-Xlayout-OUT-004** A sealed object is `header (17) || nonce (24) || XChaCha20-Poly1305(K_obj, nonce, body, AD)`. The associated data is the canonical CBOR of `["spo/object/1", 1, key epoch, genesis nonce]`. `K_obj` is HKDF-Expand (HMAC-SHA256) with the **index key** as the pseudorandom key, the info label `spo/object-envelope/1` and 32 bytes of output; `K_nonce` is the same with the label `spo/object-nonce/1`. The index key is used for nothing but `IndexKey.Tag`, an HMAC-SHA256 whose message is `lp(namespace) || lp(part)...` and so starts with an 8-byte big-endian length (first byte `0x00`, namespaces being far shorter than 2^56 bytes), while the expand input `label || 0x01` starts with `s`; the inputs are prefix-disjoint and plain HMAC-PRF security suffices. (The record-wrapping key is also an XChaCha20 key and was not used.) `Keys` does not hold either key: an `ObjectSealer` derives both once (`Keys.ObjectSealer`), seals and opens any number of objects, and destroys them on `Close`; `SealObject` and `OpenObject` do the same for one object, with `defer`. **The nonce is synthetic:** `HMAC-SHA256(K_nonce, AD || body)[:24]`. Sealing the same body under the same keys, epoch and genesis nonce gives byte-identical stored bytes and so the same object name (idempotent export: an unchanged record keeps its name, full audit pages are reused byte for byte); two different bodies share a nonce only by a collision of the truncated HMAC; an observer learns equality of whole bodies, which are unique per (record id, version, updated-at). `OpenObject` accepts any nonce and does not recompute it: the nonce rule binds writers, not readers.
- **SPO-Xlayout-OUT-005** A sealed object's body is `u32 big-endian length || canonical CBOR || zero bytes`, filling the bucket less the 57 bytes of the header, nonce and tag. After opening, the decoder checks that the body size is a bucket less 57 and the smallest that holds the CBOR, that the length is non-zero and inside the body, that the CBOR is canonical, and that every padding byte is zero.
- **SPO-Xlayout-OUT-006** The CBOR of a record is the array `[objectKind, class, recordID, anchor, num, version, recordFormat, updatedAt, inner]`. `objectKind` is the record's kind; `class` is `secret` or `sensitive` as the store's kind-to-class rule gives it (a cold-role record has class `secret`; the cold form is a property of its wrapped key); `recordID` is 16 bytes; `anchor` the binary anchor identity and `num` the number from the owner blob; `version` and `updatedAt` are the row's `version` and `updated_at`; `recordFormat` is the record encoding of the store and must be 2 (`layout.RecordFormat`, compared with `seal.RecordFormat` by a test); `version` is at least 1; both are checked when encoding and when decoding. `inner` is `[nonce, wrapped key field, owner, ciphertext]`, the four sealed fields byte for byte. Of the columns of the `records` row the body holds `id`, `kind`, `version`, `updated_at` and the four sealed fields; `lookup_tag` is not stored, because it is the index-key hash of the anchor, kind and number and is recomputed by a holder of the keys.
- **SPO-Xlayout-OUT-007** The wrapped-key field is a byte string of exactly W + 2 bytes: a 2-byte big-endian true length, the wrapped key, and zero bytes. W is 1536. It is measured from the largest cold-role wrapped-key blob the code can produce (a FIDO2 header with a 1024-byte credential id, a previous wrap, the left mark, the outer wrap, the HPKE recovery wrap and the largest fallback counter: 1431 bytes) rounded up to a multiple of 256. A hot record's 72 bytes and every cold form therefore give a body of the same length. The codec never parses, rebuilds or re-seals the cold form.
- **SPO-Xlayout-OUT-008** The CBOR of an audit row is `["audit", seq, at, kind, event, touched, slotset, mac, prev_mac]`, the columns of the `audit` row as `verify.go` reads them. `kind` is `update`, `slots` or `rollover`; `slotset` is empty for `update` and 32 bytes otherwise; both MACs are 32 bytes.
- **SPO-Xlayout-OUT-009** The manifest is made of objects of the same envelope. A record page is `["manifest-page", "records", [[record id, version, object hash]...]]`, sorted by record id, at most 512 entries, all pages but the last full. An audit page is `["manifest-page", "audit", [[seq, object hash]...]]`, 1000 entries each, consecutive from sequence number 1, so appending rows leaves every full page byte for byte unchanged. The root is `["manifest-root", record page hashes, audit page hashes, slots object hash, audit head seq, audit head MAC, record count, audit count, parent]` with `parent` = `[parentFormat, seq, previous head hash]`, `parentFormat` being the constant `provisional-1`. Stage 5 may change `parent`; nothing else in the root may change without a new format. `VerifyManifest` checks the record count, the audit row count and head sequence number (the number of rows, the last sequence number and the root's two fields must all agree), the order across pages, that every page but the last is full, and that audit rows run on from 1 without a gap or overlap across page boundaries.
- **SPO-Xlayout-OUT-010** The slots object is `0x02 || epoch (16) || u32 length || canonical CBOR || zeros` in the smallest bucket. It is plaintext and is referenced by hash from the root and the head. Its CBOR is `["spo/slots/1", meta, slots]`. `meta` is the workspace id (the genesis nonce), the store format (3), the policy, the key epoch (equal to the header's), the epoch MAC, the creation time, the recovery public key or null and its SHA-256 hash or null. Of the `meta` row, `cleanup_pending` is not kept (local state of an unfinished VACUUM). `slots` holds every one of the twelve `keyslots` columns of each slot, sorted by id, with SQL NULL kept apart from an empty value.
- **SPO-Xlayout-OUT-011** `SlotSetHash` recomputes the store's slot-set hash from the parsed slots: SHA-256 of the canonical CBOR of `["spo/slotset/3", policy, rows]`. Tests make real workspaces with the store (standard, and hardware and strict with the fake authenticator), read their rows with SQL, and require the same value that the store records.
- **SPO-Xlayout-OUT-012** The provisional head note is canonical text: the first line `spo/head-provisional/1`, then one `key value` line each, in this order: `workspace` (32 hex), `sequence` (decimal from 1), `previous` (hash of the previous head note, 64 hex, all zeros exactly for the first head), `manifest` (64 hex), `slots` (64 hex), `audit-seq` (decimal), `audit-mac` (64 hex), `recovery-key` (64 hex or `none`), `checkpoint-key` (the checkpoint key hash, 64 hex, or `none`), `epoch` (the key epoch, 32 hex), `object-format` (the literal `spo/object/1`, the envelope the head's objects are in), `time` (UTC `YYYY-MM-DDTHH:MM:SSZ`), a line feed after every line. Its hash is Blake2b-256 of the note. It is stored as `heads/<sequence, 20 digits>`. The SSHSIG namespace for signing it is `spo/head-provisional/v1`; signing is not part of this format.
- **SPO-Xlayout-OUT-013** Test vectors are committed (`internal/domain/layout/testdata`, `internal/platform/seal/testdata`) and regenerated and compared by tests: the bucket edges, the sealed records (a hot Sensitive, a hot Secret, a cold-role passphrase record and a cold-role FIDO2 record with a previous wrap and the left mark, made with the real seal functions), an audit row, a manifest page and root, a slots object for each policy and a head note. Sealing is deterministic (OUT-004), so the stored bytes and names are pinned without an injected nonce. A cold-role FIDO2 record **with an HPKE recovery wrap** is committed as an open-only vector with its test recovery private key: the ephemeral key is drawn through the standard library (made deterministic with `testing/cryptotest.SetGlobalRandom` when the file is written), and how the library uses randomness may change with the Go version, so the test never compares the committed bytes with a regeneration; it opens the outer layer with the master-derived keys, the recovery wrap with the private key, and the payload with the data key that yields. `testdata/check_vectors.py` recomputes the envelope with an independent implementation (Python standard library only, XChaCha20-Poly1305 and HKDF written from the RFCs) after checking that implementation against published known answers (RFC 5869 test cases 1 and 3, the HChaCha20 example and the AEAD example of draft-irtf-cfrg-xchacha), and reproduces every vector byte for byte.

## Preconditions and failures

- **SPO-Xlayout-PRE-001** A stored object whose format byte is `0x03` (chunked) or not `0x01` or `0x02` is refused, and `OpenObject` refuses a format byte other than `0x01`.
- **SPO-Xlayout-PRE-002** A stored object whose length is not a bucket is refused, at every truncation length and with a trailing byte.
- **SPO-Xlayout-PRE-003** A body that does not fit the largest bucket is refused naming its size, by the framing; `SealObject` refuses a body whose length plus 57 is not a bucket.
- **SPO-Xlayout-PRE-004** A header epoch that is not the expected epoch is refused, and because the epoch is in the associated data a rewritten header epoch does not authenticate either.
- **SPO-Xlayout-PRE-005** Non-zero padding, a length field of zero or past the body, a body in a larger bucket than its content needs and a body that is not a bucket less 57 are refused. For a body the framing checks the size, the length field, the smallest bucket and the zero padding; for the slots object the re-encode comparison is the check of the padding and of the smallest bucket (the encoder writes zeros and picks the smallest bucket), and likewise the fill after a wrapped key is checked by the re-encode comparison of `DecodeObject` and not by a separate loop.
- **SPO-Xlayout-PRE-006** CBOR that is not canonical (a longer head than needed, an indefinite length, trailing bytes, a map where an array is required, a wrong number of items) is refused.
- **SPO-Xlayout-PRE-007** An unknown object kind, and a class that the store's kind-to-class rule does not give for the kind, are refused. The rule is an argument of the decoder; a missing rule refuses every record.
- **SPO-Xlayout-PRE-008** A wrapped key longer than W is refused when encoding and, in a decoded body, a field that is not W + 2 bytes, a length of zero or above W, or a non-zero fill (the last by the re-encode comparison).
- **SPO-Xlayout-PRE-009** A root whose `parentFormat` is not `provisional-1` is refused, as is a previous head hash that is all zeros for any head but the first or not for the first; a manifest whose root and pages disagree is refused (counts, order, a page that is not full and not last, a gap in the audit rows).
- **SPO-Xlayout-PRE-010** A head note is parsed strictly: exact tag and keys in order, canonical decimals within 64 bits, lower-case hex of the right lengths, a UTC time with no fraction or offset, no empty value and none with a space, tab, carriage return or NUL, a final line feed, at most 4 KiB, and what is accepted re-encodes to itself (every field is compared with its exact spelling, and the fuzz target requires the round trip).
- **SPO-Xlayout-PRE-012** A record body whose record format is not 2 or whose version is 0 is refused, when encoding and when decoding.
- **SPO-Xlayout-PRE-011** A slots object with a format byte other than `0x02`, a length that is not the smallest bucket, non-zero padding, a meta key epoch that is not the header's, a recovery key hash that is not the hash of the key, an unknown policy or slot kind, slots that are not sorted by id or repeat, an empty slot table or non-canonical CBOR is refused.

## Security

- **SPO-Xlayout-SEC-001** The whole sealed object is authenticated: every single-bit flip of the stored bytes makes `OpenObject` or the decoder fail (all bits of a 4 KiB object; the header, nonce, tag and a bounded sample of a 1 MiB object).
- **SPO-Xlayout-SEC-002** `K_obj` and `K_nonce` are separate keys: each equals an independent HKDF-Expand of the index key under its pinned label, and neither equals the index key, the record-wrapping key or the other. The prefix-disjointness argument of OUT-004 is tested (every index-key message starts with a zero byte, no label does).
- **SPO-Xlayout-SEC-003** Opening the envelope yields the inner fields of a cold-role record, and the master-derived keys alone do not open its payload: opening the inner record without the cold sub-key fails. This guards the guarantee of ADR 0011 against a later simplification of the exporter.
- **SPO-Xlayout-SEC-005** An ordinary unlock holds no key that only the layout needs: `DeriveKeys` locks three buffers (as before the envelope), an open workspace holds the same number of locked buffers as at the commit before stage 3, so `secret.MinimumBudget` and the locked-memory floor are unchanged. An `ObjectSealer` holds two locked buffers (`K_obj` and `K_nonce`) from `ObjectSealer()` to `Close()`, however many objects it seals; `Close` is idempotent; the one-shot methods and every error path leave the count where it was.
- **SPO-Xlayout-SEC-004** A stored object shows no kind, class, record id, anchor, owner blob, nonce or wrapped key in the clear: only a bucket size, the epoch and the format byte.

## Invariants

- **SPO-Xlayout-INV-001** `internal/domain/layout` imports no adapter, platform, port or use-case package, no `os`, no `net`, no process or random source.
- **SPO-Xlayout-INV-002** For every vector, encode(decode(x)) equals x, for bodies, slots objects and head notes.
- **SPO-Xlayout-INV-003** The `inner` bytes of a decoded record equal the bytes that were encoded.
- **SPO-Xlayout-INV-004** A hot Secret record and a cold-role record of equal payload size are stored in objects of the same size, at every payload size.
- **SPO-Xlayout-INV-005** No input makes the body decoder, the object decoder under the framing, the slots object parser or the head parser panic, and whatever they accept re-encodes to itself (four fuzz targets seeded with the vectors). The two targets over framed 4 KiB inputs, the body decoder and the slots parser, take the CBOR and a mode and three small numbers and build the framing themselves, in the shapes the decoder must refuse (a wrong length field, a flipped byte, a bucket larger than needed, a truncation): with a 4 KiB argument the Go fuzzing engine's minimiser works on each input it finds interesting for up to its default 60 seconds and reports nothing meanwhile, which gave about 560 executions in 15 seconds against millions for the unframed target. An ordinary test keeps arbitrary edits of the whole 4 KiB.
- **SPO-Xlayout-INV-006** Sealing is deterministic: the same body under the same keys, epoch and genesis nonce gives byte-identical stored bytes and the same name, and different bodies, or the same body under another epoch, give different nonces (OUT-004).

## Requirements on what the exporter writes and the verifier reads

These were stated for two later work packages. The exporter (work package 3, below) writes objects that satisfy them, and tests open what it wrote with the workspace keys and check each one, with the real store for every policy. The verifier and the importer (work packages 4 and 5, below) check them again on what they read (INV-015 and INV-016).

- **SPO-Xlayout-INV-007** The `recordID` and `version` of a record object equal the entry for its object hash in the manifest record page that lists it.
- **SPO-Xlayout-INV-008** The `seq` of an audit object equals the sequence number of its entry in the manifest audit page.
- **SPO-Xlayout-INV-009** The MAC of the last audit object equals the root's audit head MAC, and its sequence number equals the root's audit head sequence number.
- **SPO-Xlayout-INV-010** The anchor and number in a record body equal those inside the record's sealed owner blob (`OpenOwnerRef`, authenticated against the workspace id, the record id and the kind), and the lookup tag recomputed from them (the index-key tag of the anchor, kind and number) equals the `lookup_tag` of the row the object was made from. The exporter checks both before it seals anything and refuses the export otherwise.
- **SPO-Xlayout-INV-011** The slot-set hash of the slots object equals the slot-set hash of the newest audit row of kind `slots` or `rollover`. The exporter refuses a snapshot where it does not. A workspace always has a genesis slot-table row (`init` and every slot change write one); a snapshot with no `slots` or `rollover` row at all is inconsistent and is refused, not waved through.
- **SPO-Xlayout-INV-017** The epoch MAC of the slots object's `meta` verifies under the audit key of the key epoch. The snapshot is taken only from a file that passes the full verification, which checks it; a file with an edited epoch MAC is not exported.
- **SPO-Xlayout-INV-015** The lookup tag that import writes for a record is recomputed, with the keys of the workspace, from the anchor and number of the record's body, and the anchor and number are first checked equal to those of the record's sealed owner blob (INV-010). The tag is never read from the object. The store's verification of the scratch file then checks it against the audit chain, which recorded each record's hash with its tag. Tests read back a real layout of every fixture family and compare the rebuilt rows with the workspace's (INV-026).
- **SPO-Xlayout-INV-016** The verifier checks INV-007 to INV-011 and INV-017 on the objects it reads, in the unlocked pass (OUT-021): each is a refusal that names the object, and each is tested by changing exactly that fact in a layout that is otherwise valid. INV-007 and INV-008 are checked against the manifest page entry, INV-009 against the manifest root, INV-010 against the owner blob, INV-011 against the newest audit row of kind `slots` or `rollover`, and INV-017 under the keys the credential opened.

## The exporter

The command is `spo store convert --to-layout DIR [--no-checkpoint] [--checkpoint-device DEV --checkpoint-pin-fd N]`. The use case reaches the directory, the lock, the pin and the keys only through ports (`ports.ObjectWriter`, `ObjectReader`, `ObjectLister`, `LayoutLocker`, `LayoutPins`, `ObjectSealer`) and imports no adapter and no `os`. It never sees a key byte. The record references (anchor and number) come from the store adapter, which opens each owner blob with the workspace keys; no record payload and no cold-role record is opened. Nothing in this part changes a frozen byte of the format above.

- **SPO-Xlayout-IF-001** `store convert --to-layout DIR` writes the workspace into the local directory DIR as objects of this format and changes nothing in the workspace. DIR is an absolute path, a relative path or `dir:/absolute/path`. An `s3://` URL is refused with a message that says this version writes to a local directory only. The workspace is unlocked the normal way for its policy: a standard workspace with its passphrase, a hardware or strict workspace through its daily authenticator. `--unlock recovery-composite` is refused. `--adopt-layout` is the operator's statement that an existing layout this machine has no pin for is trusted (PRE-019). The verified raw snapshot of the workspace file is taken through that one presentation of the credential (`sqlitestore.TakeExport`, which is `ReadSnapshot` that also returns the object sealer, the record references and the checkpoint key record from the same verified private copy); a workspace that does not verify is not exported and the verification notices are printed.
- **SPO-Xlayout-OUT-014** A run puts, in this order: the slots object, every record object, every audit object, the record pages, the audit pages and the manifest root, and last the head note. Every put is create-if-absent and is read back (the stored bytes are fetched and their Blake2b-256 compared with the name) before the next step. The slots object is first because it is plaintext and names the workspace, so a directory that holds objects can always be recognised as this workspace's. The head is `heads/<sequence, 20 digits>` with every field of the head note as OUT-012 defines it: `previous` is the hash of the newest valid head already there (all zeros for the first), `sequence` is that head's plus one, `manifest` and `slots` are the object hashes, `audit-seq` and `audit-mac` those of the last audit row, `recovery-key` the hash of the recovery public key (or `none`), `checkpoint-key` the key hash when the head is signed (else `none`), `epoch` the key epoch and `time` the time of the run. The root's `parent` is `[provisional-1, sequence, previous head hash]`.
- **SPO-Xlayout-OUT-015** The export is incremental by construction. Because the nonce is synthetic (OUT-004), an unchanged record, audit row or full page has the same name as before. The run lists the directory once, and an object whose name and size are already there is counted as reused and is not put (the writer is not called); an object that is there with the same name and another size is put, and the writer refuses it. A run after nothing changed since the newest head puts no object and writes no head and says "already up to date". Because the root names its own head's sequence number and the hash of the head before it, "nothing changed" is decided by building the root as it would be for the newest head and comparing its hash and the slots object's hash with that head's. After one record changed the new objects are the record, the audit rows it added, the record page that lists it, the last audit page, the root and the head. After a rotation (a new key epoch) every object is new and the old objects stay, unreferenced by the new head. After a cold-role record's salt rotation exactly that record's object is new.
- **SPO-Xlayout-OUT-016** When a checkpoint key is enrolled and `--no-checkpoint` is not given, the head note is signed with it as an SSH signature under the namespace `spo/head-provisional/v1` (the signing code path of the stage 2 checkpoint): one PIN and one touch, asked only after every object and the manifest are in the directory and read back, and before the head is put. The armored signature is put as `heads/<sequence>.sig` after the head, create-if-absent and read back. A signing failure leaves no head: the run reports "objects written, no head written", exits non-zero, and a re-run puts no object again. When the newest head is unchanged but has no signature and a signature is asked for, the run signs that head and puts only the signature. A signature file that is found in the directory counts as a signature only after it verifies (INV-019). With no key enrolled the head is unsigned and the output says plainly that the head is then protected against accidents (a damaged or half-written directory) and not against forgery. With `--no-checkpoint` and a key enrolled the head is unsigned, names no key, and the output says so.
- **SPO-Xlayout-OUT-019** An export interrupted between putting a head and putting its signature is completed by the re-run, under exactly these conditions: a checkpoint key is enrolled and this run signs; there is a pin; the unsigned head is the only head above the pin, the newest, at the pin's sequence plus one; there is no `.sig` file for it at all; the run would otherwise be "already up to date"; the unsigned note equals the note this run encodes from the verified workspace in every field but `time`; its `checkpoint-key` field is the enrolled key's hash; and its `time` is not before the pinned head's and not more than 5 minutes in the future. The run then puts only the signature and records the pin. If any condition fails it refuses as for any unverified head. If the workspace changed since the crash, it refuses, saying a head that was never signed cannot be built on, and to use a fresh directory.
- **SPO-Xlayout-OUT-017** After a head is written, or found as the newest when nothing changed, the run records `(sequence, head hash)` in a pin file beside the workspace file (`<workspace file>.layout-<16 hex of the SHA-256 of the real directory path>.pin`, so each layout directory has its own), mode 0600, never in the layout directory. The file is written atomically (a temporary file in the same directory, synced, renamed over the pin, the directory synced) and only moves forward: the same pin is not written again, and a pin that is behind, or has the same sequence number and another hash, is refused. The run prints `<workspace id hex>:layout:<sequence>:<head hash hex>` and, when the head is signed, the long-lived pin `<workspace id>:ck:<key hash>` of stage 2.
- **SPO-Xlayout-OUT-018** The output gives the counts of objects written and reused, the head sequence number and hash, the pins, and one paragraph of what someone who can read the directory sees: the number of objects and how many there are of each bucket size, the plaintext slots object (its size and what it holds), the plaintext head notes, and when each file was written; and what they do not see. The paragraph is the same for every directory. Nothing in the output is secret, and every name or error text that came from the directory goes through the terminal-safe quoting of stage 1.

- **SPO-Xlayout-PRE-013** Every check that needs no secret is made before the workspace is unlocked: no passphrase, PIN or touch is asked for, no authenticator is called and the terminal is not read. They are: DIR is a local directory (not an `s3://` URL); `--unlock` is not `recovery-composite`; DIR is not the workspace directory and not inside it or above it (links resolved); DIR is owned by the user and not writable by its group or by others (checked by path and again with fstat on the opened descriptor); DIR is empty or absent, or holds only a layout (`objects`, `heads` and the lock file) of this workspace, which is the workspace id of its newest valid head (a directory with objects and no head is accepted only when its plaintext slots objects all name this workspace and there is one, which is an export that was stopped); a head that is not valid is never replaced or deleted and blocks the directory. Anything else in DIR is refused (PRE-018), and the scan is capped. A refusal creates nothing in DIR.
- **SPO-Xlayout-PRE-014** A single writer: the run holds an exclusive lock on `<DIR>/.spo-export.lock`, taken without waiting, for the whole run; a second exporter is refused (`ports.ErrLayoutLocked`) before it unlocks anything. The directory adapter opens DIR once (`O_DIRECTORY|O_NOFOLLOW`) and does every open, link, listing and lock-file open relative to that descriptor (`openat`, `linkat`, `fstatat`), so replacing DIR afterwards cannot redirect a read or a write. Before every put the run also checks that DIR is still the directory that was locked (not replaced, not a link, and the lock file still the held one, compared by device and inode with `fstatat` without following links, so a lock file that was unlinked and made again by a second exporter is detected); a directory replaced mid-run stops the run before another object is put and no head is written.
- **SPO-Xlayout-PRE-015** A record whose body does not fit the largest bucket is refused with an error that names its kind, its class and the sizes, and never its content or id; the run writes no head. Nothing is chunked.
- **SPO-Xlayout-PRE-016** A directory with a head that has a larger audit sequence number than the workspace's last audit row is refused, in different words when every head verified against the key (the workspace file is older than what was exported) and when not (a head this machine cannot vouch for); every head of the chain is also checked against the workspace (INV-023); a directory whose newest valid head is behind the pin file, or has the pin's sequence number and another hash, is refused before anything is asked (the directory was rolled back or replaced).
- **SPO-Xlayout-PRE-017** A pin file that does not parse (or is not a small regular file: it is opened with `O_NOFOLLOW|O_NONBLOCK` and checked with fstat, so a link or a FIFO is reported and never waited on) is reported with its path and is never replaced by the tool; no export runs until the operator has dealt with it.

- **SPO-Xlayout-PRE-018** An entry under `objects/` or `heads/` that is not a regular file of the right name (a symbolic link, a FIFO, a socket, a device, a directory where a file belongs, a name that is not a layout's) is refused by name at open, before the lock file is made and before anything is asked, and the scan reads each directory in chunks of 1,024 names and stops at a cap on entries (1,000,000) and on depth (3), saying so, without having read the rest (a scan of 100,000 entries takes about 0.16 s warm, so the cap costs a few seconds). The tool's own stale temporary files (`.tmp-<16 hex>` in the layout, older than an hour, regular files of this user, never through a link) are removed once for each directory, and so are `.spo-pin-<16 hex>` files beside the workspace file. Every open of a file by the directory adapters (the layout's and the backup sink's) uses `O_NOFOLLOW|O_NONBLOCK` and requires a regular file by fstat on the descriptor, so a FIFO under an object name is refused at once and never waited on; a cancelled context is honoured.
- **SPO-Xlayout-PRE-019** An existing layout that this machine has no pin for is not trusted silently. With no checkpoint key enrolled the run is refused, after unlock (the key is not known before), unless `--adopt-layout` is given; the refusal and the notice print what is trusted (the newest head's sequence, hash and time). With a key enrolled the layout is trusted only when every head in it carries a signature that verifies against the key, and the run says so; a head that does not verify is refused by name and **`--adopt-layout` never overrides it** (INV-022): the flag is for a workspace with no key. In both cases the pin is recorded. What the run trusts (the newest head's sequence, audit sequence, hash and time) is said before the pin is recorded.

- **SPO-Xlayout-SEC-006** Nothing leaves the machine in plaintext except what the format defines as plaintext: the 17-byte headers, the slots object, head notes and signatures. Tests scan every byte written for the test passphrases, recovery keys and authenticator secrets, and for record kinds, classes, labels, record ids, anchors, owner blobs and payload bytes outside a seal.
- **SPO-Xlayout-SEC-007** Records are carried byte for byte: the inner fields of every exported object equal the snapshot's fields. The exporter holds an object sealer (which only seals) and the record references; a cold-role payload is not opened by it and cannot be opened with the workspace keys alone, while a hot record opens from the fields of its object with them.

- **SPO-Xlayout-INV-012** Crash safety. A run puts objects, then the manifest, then the head. After a failure at any step (a put that fails, a read back that differs, a full disk, a cancelled context, a failure to sign, a lock that is lost, a directory replaced mid-run) the newest valid head of the directory, if there is one, has every object it names in the directory and its manifest verifies against its pages; no head is ever put that names an object that is missing; and a re-run completes and does not put again an object that is already there.
- **SPO-Xlayout-INV-013** An unchanged object is never put again: on a re-export the writer's `Put` is called only for objects that are new (and for the head and its signature).
- **SPO-Xlayout-INV-018** Every object a head will reference is verified in the run that writes the head: an object that is already in the directory is fetched, its size is checked and its Blake2b-256 must equal its name, one at a time. A mismatch (flipped bytes of the same size, a truncated or longer file under a valid name, a replaced manifest root or slots object) refuses the export naming the object, says that the directory holds wrong content under that name and that the tool never overwrites or deletes it, and says to export to a fresh directory. "Already up to date" is said only after every object has been verified this way. Before anything is asked, the newest head's manifest root and slots object are also read and hashed. Cost on the 50,000-audit-row fixture (50,253 objects, 199 MiB): about 1.0 s with the in-memory fake, one object in memory at a time.
- **SPO-Xlayout-INV-019** A signature file is believed only when it verifies: `heads/<sequence>.sig` is checked with `domain/sshsig` against the workspace's enrolled checkpoint key, namespace `spo/head-provisional/v1`, over the exact bytes of the head note, with user presence and user verification set. Only a signature that verified in this run is reported as "signed"; one that does not verify is reported as such and never counted, and with no key enrolled none can be counted. A signature file with no head note (it would block the next head's name for ever) refuses the run with advice that works (move it away yourself or use a fresh directory).
- **SPO-Xlayout-INV-020** The run chains a new head only onto heads this machine can vouch for. With a pin, `heads/<pin sequence>` must still hash to the pin and every head from it to the newest must name this workspace, be consecutive without a gap, link by `previous` to the hash of the one before it, and, when a checkpoint key is enrolled, carry a signature that verifies. Without a pin the chain runs from the first head (PRE-019). The first head that fails is named and the run refuses, saying the directory holds heads this machine did not write or cannot verify and to use a fresh directory; the message does not claim a rollback. A head sequence number above 2^32 is refused as out of range, never wrapped.
- **SPO-Xlayout-INV-021** The checkpoint key signs only a note this run encoded itself from the verified snapshot. For an existing unsigned head the note is rebuilt from the workspace and must be byte for byte the existing one in every field but the time (`checkpoint-key` may be `none` or the key's hash); otherwise the run refuses and says the existing head differs from the workspace, and nothing is signed.
- **SPO-Xlayout-INV-022** The checkpoint key is never overridden. When a key is enrolled, every head the new head would build on (those above the pin, or all when there is no pin) must carry a signature that verifies against it in this run; `--adopt-layout` does not override a head that fails, the refusal does not suggest it, and its only remedy is a fresh directory. The key never signs a head whose chain holds a head that did not verify in this run, except the pinned head, which the pin vouches for, and the one exception of OUT-019. (`--adopt-layout` is for a workspace with no key.)
- **SPO-Xlayout-INV-023** Every head of the chain is this workspace's history: it names this workspace; audit sequences do not go down along the chain and none is above the workspace's audit head; the head's audit MAC is the workspace's audit-row MAC at that sequence (zeros for sequence 0); and, for a head at or after the newest `rollover` audit row, its `epoch` and `recovery-key` are the current ones. Before the newest rollover the snapshot does not say what the epoch and recovery key were, so those two fields are not checked for older heads. A head that fails is refused by name, saying that the layout and the workspace are not the same workspace history (it diverged, or the workspace was restored from a diverged backup). This holds with a pin without a key, with `--adopt-layout`, and for a chain verified by the key.
- **SPO-Xlayout-INV-014** The export does not hold the workspace twice. The snapshot is held once and each row is cleared when its object is put; the manifest keeps one hash per object. Measured with 50,000 audit rows and 200 records (50,253 objects) under a collector set to 10 percent: the heap in use rose by 26.7 MiB over its start, of which 17.0 MiB is the snapshot, so the export itself held about 10 MiB (the chain checks and the object verification added a little to the 6 MiB of the first version); with the default collector the peak is higher by the garbage it has not yet collected.

## The verifier and the importer

Two commands read a layout back. `spo store verify --layout DIR --pin PIN [--at SEQ] [--locked]` checks it and changes nothing, neither the directory nor any workspace. `spo store convert --from-layout DIR --pin PIN [--at SEQ]` with the flags of `store restore` checks it the same way and installs it as the workspace by the existing restore path. Both use one reader, `internal/app/layoutread`, which reaches the directory, the keys, the slot-table check, the store file writer and scratch space only through ports (`ports.ObjectReader`, `SlotTableChecker`, `LayoutKeyOpener`, `ObjectOpener`, `SnapshotFileWriter`, `Scratch`) and imports no adapter and no `os`. It never lists `objects/`: it starts from the heads and fetches every object by hash. The reader holds no key byte and opens no record payload. The directory is opened by the same adapter as the exporter's (`layoutdir`: one descriptor, every operation relative to it, regular files only, the preflight scan and its caps).

A check has two passes. The **locked pass** needs no credential and asks for none. The **unlocked pass** presents the credential of the workspace and opens the objects. Nothing the directory says is believed on its own authority: a pin brought by the operator is the only root of trust.

- **SPO-Xlayout-IF-002** `store verify --layout DIR --pin PIN [--at SEQ] [--locked]` runs the locked pass and, unless `--locked`, the unlocked pass, then removes its scratch file. It prints the head used (sequence, hash, time, audit sequence), whether it is signed and by which key hash, the number of heads examined, the counts of what the unlocked pass opened (objects, bytes, records, audit rows), every notice, what the locked pass established and what it cannot, and the exact pin of the head used. It exits non-zero on any failure. It changes nothing in DIR and nothing in any workspace: its scratch file is made in a private temporary directory of its own and removed. `--at` and `--locked` without `--layout`, and `--layout` with `--backup`, `--checkpoint`, `--deep` or `--with-cold-factor`, are refused. DIR is a local directory (an `s3://` URL is refused, as for the exporter) and must exist.
- **SPO-Xlayout-IF-003** `store convert --from-layout DIR --pin PIN [--at SEQ]` takes the flags of `store restore` (`--force`, `--allow-older`, `--allow-weaker-policy` with the recovery-material flags, `--allow-other-workspace`, `--accept-lower-counters`, `--network`). It runs both passes, writes the verified scratch file, and installs it with the restore path (OUT-023). `--to-layout` and `--from-layout` together are refused, and the flags of one direction are refused with the other. Into an empty directory it installs the workspace and writes `spo.toml` as a restore does (`--network` is needed when there is none). It does not retire anything, writes no location statement, and does not widen the scope of the recovery composite.
- **SPO-Xlayout-PRE-020** A pin is required. With none, both commands refuse before anything is read or asked, and the message says how to get one; no option trusts the directory. Three forms are accepted. The **exact pin** `<workspace id>:layout:<sequence>:<head hash>` is what the exporter prints: it names one head and proves that head and, through the `previous` hashes, the chain below it. The **key pin** `<workspace id>:ck:<checkpoint key hash>[:<minimum sequence>]` is the long-lived pin of stage 2: it authenticates every head that carries a signature of that key. The **local pin**, `--pin local`, is the pin this machine keeps beside the workspace file for a layout it exported (OUT-017): it is read as an exact pin of the workspace on this machine. A pin is parsed strictly (lower-case hex, canonical decimals, a sequence number from 1 to 2^32) and a malformed one is refused before the directory is read.
- **SPO-Xlayout-PRE-021** With an exact pin the walk starts at `heads/<pinned sequence>`, which must hash to the pin (otherwise ErrPinHash; absent is a rolled-back directory). The head used is that head or a later one that chains from it: every head must name the pinned workspace, be consecutive, and link by its `previous` hash to the hash of the head before it. An exact pin does not authenticate a later head; so when the pinned head names a checkpoint key, every later head must carry a signature that verifies against that same key, and one that does not stops the check. When the pinned head names none, later heads are accepted as chained by hash only and the output says that nothing authenticates them and that `--at <pinned sequence>` uses only the pinned head. `--at` below the pinned sequence is refused.
- **SPO-Xlayout-PRE-022** With a key pin the walk starts at `heads/1` and every head up to and including the one used must carry `heads/<seq>.sig` that verifies with `domain/sshsig` in the namespace `spo/head-provisional/v1`, over the exact note bytes, with the user-presence and user-verification flags, against a public key whose hash is the pin's, and the head's `checkpoint-key` field must equal it. A head that is not signed, signed by another key, or with a signature over other bytes stops the check. With a minimum sequence, a directory whose newest verified head is below it is refused as behind the pin; without one the output says that the pin proves the head authentic and not that it is the newest. An older head (by `--at`) is accepted only at or above the minimum.
- **SPO-Xlayout-PRE-023** `--at` naming a head that is not in the directory is refused, naming that sequence and the last head the chain reaches; it never falls back to another head. A head that fails (it does not parse, is stored under another sequence number, names another workspace, does not link, has a bad or missing signature the pin requires) is never skipped. The check stops, names the head and why, says that the heads below it may still be valid, names the newest head below it that verified, and says to run it again with `--at THAT` only if that state is acceptable; the pin still has to accept it. Junk at the next sequence number (a squatted head) is such a head. Heads are found by number (`heads/N`, then `heads/N+1`), never by listing; with `--at` the check never reads a head above it, and without it says that a newer head could exist beyond a gap. At most 100,000 heads are examined (`MaxHeads`): a longer chain is refused with that number.
- **SPO-Xlayout-PRE-024** For the head used, the slots object and the manifest root are fetched by hash, at most 4 MiB each (a longer file is refused after 4 MiB + 1 bytes are read), and checked: the bytes hash to the name, the stored size is a bucket; the slots object parses strictly (PRE-011), its header epoch is the head's `epoch`, its workspace id is the pin's, the hash of its recovery public key is the head's `recovery-key`, and its slot table passes the store's unlock-policy check (`unlock.Check`, through the store adapter, on the same table parse the store's open uses) before any credential is asked; the manifest root is a sealed object (format `0x01`) of the head's key epoch.
- **SPO-Xlayout-PRE-027** The slots object is plaintext and is decoded from the directory before anything is known about it, so its stored size is bounded by `layout.MaxSlotsObject`, 256 KiB: a store holds at most 64 slots (`ports.SnapshotMaxSlots`) of at most 4 KiB each, and the largest legal table fits (tested). The reader reads at most that size plus one byte and refuses a longer file before decoding (a 4 MiB object of CBOR nulls costs under 1 MiB, asserted); `ParseSlotsObject` refuses a longer object, and the exporter (`EncodeSlotsObject`) refuses to write one.
- **SPO-Xlayout-PRE-028** The slot table that decides which credential is asked for and what the authenticator is asked (its credential id, RP id and salt) is one the pin vouches for, and this is decided in the locked pass, before any prompt. With a key pin the head is signed, so the hash of its slots object is signed and the table is fetched and matched to it. With an exact pin (and so with `--pin local`) the pinned head's slots object is fetched and checked too (its hash is in the pinned head, which hashes to the pin). A later head whose slots object differs from the pinned one is accepted only if all hold: its policy is not weaker than the pinned table's (`unlock.Weakens`), its recovery public key hash equals the pinned table's, and its table passes the store's own check, which refuses a FIDO2 factor whose RP id is not `spo.` and the workspace id in hex (the only RP id a store writes; `sqlitestore.CheckLayoutSlotTable`). Otherwise the check refuses, names the head, and says to pin a head that carries the table (a newer exact pin), use a key pin, or use `--at <pinned sequence>`. A legitimate rotation that changes the recovery key or lowers the policy therefore needs a newer pin. Independently, the credential kind comes from the policy of the vouched table, and a hardware or strict table never leads to a passphrase prompt (a guard in the command, tested apart from the check above it).
- **SPO-Xlayout-PRE-029** A key cannot appear after the pin without the pin vouching for it. A signature counts as "signed" only when it verifies against a key the pin vouches for: the key of a key pin, or the key the pinned head of an exact pin names. A signature by any other key is reported as such and the head is treated as unsigned for every rule. With an exact pin whose pinned head names no key, a later head that names a key is refused (its note's key and time are not bound by the manifest, so such a head is one anyone who can write the directory could make); with one that names a key, a later head must name the same key and carry its signature.
- **SPO-Xlayout-OUT-020** The locked pass reports what it established (the head and the chain by hash, the signatures, the objects fetched by hash and the slot table's policy) and what it cannot: it cannot open a sealed object, cannot check the manifest, the records or the audit chain, the record hashes the chain recorded or the epoch MAC, and cannot tell that the records are those the operator expects. `--locked` stops here, asks for no credential, touches no authenticator, and says so. An unsigned head is reported as protected against accidents and not against forgery. With an exact pin the output says the head used is the newest the directory offers, not necessarily the newest that exists (a deleted head above the pin cannot be detected); only a key pin with a minimum sequence, or a newer exact pin, says what the newest is. The sizes printed are those of the slots object and of the manifest root.
- **SPO-Xlayout-OUT-021** The unlocked pass unlocks the slot table of the slots object through the store's own unlock path and opens, in this order: it checks the epoch MAC (INV-017) before any object is fetched; opens the manifest root and checks it against the head (its `parent` is the head's sequence number and `previous`, so a manifest of another export of the same workspace is refused; its slots object hash, audit sequence and audit MAC are the head's); refuses a root that names more than 100,000 records, 500,000 audit rows or the pages they need, before any page is fetched (INV-024); fetches and opens every page and runs `layout.VerifyManifest`; fetches every record and audit object named by the pages, at most eight at a time, each checked (hash equals name, a bucket size, opened under the workspace key epoch, decoded strictly: padding zero and canonical, class by the store's rule); and checks INV-007, INV-008, INV-009, INV-010 and INV-011 as INV-016 says. Every failure names the object and the fact (a refusal for an object that is missing, of the wrong content, of the wrong size, that does not open, whose entry names another record, version or sequence number, whose owner blob says another anchor or number, a last audit row that is not the root's, a slot table that is not the newest recorded one). The rows are rebuilt into a `ports.Snapshot` carried byte for byte, with the lookup tag recomputed (INV-015), and a snapshot of a file with no record has no record slice, as the store's does.
- **SPO-Xlayout-OUT-022** The rebuilt snapshot is written with `WriteSnapshotFile` (through `sqlitestore.WriteLayoutFile`, which sets the schema version) into a private scratch directory made through `ports.Scratch`; that call runs the store's full verification (the audit chain from the first row, every record hash the chain recorded, the slot table and its policy, the epoch MAC) and a read-back equal to the snapshot, and it is the audit-chain check of the reader: the reader does not re-implement it. A forged manifest whose pages and counts agree but which omits a record or holds a record object changed after sealing passes the layout checks and is refused here. The verifier removes the scratch directory; the importer keeps it for OUT-023 and removes it afterwards, on every path. The scratch file is never written onto the destination.
- **SPO-Xlayout-OUT-023** The importer hands the scratch file to the existing restore (`RestoreWithFactors`, or the passphrase restore for a standard workspace) with `ExpectedSHA256` set to the file's hash, so every rule of a restore applies unchanged: an existing workspace needs `--force`; an older or diverged layout needs `--allow-older`; a weaker policy is refused without `--allow-weaker-policy` and the current recovery credential; another workspace needs `--allow-other-workspace`; the operational certificate and KES counters of the replaced workspace are carried forward and never lowered; the checkpoint key is carried; the `.head.next` sidecar and the head file are written as a restore writes them. When no workspace is replaced (an empty directory) there is nothing to compare the counters with, and the output says so and names the on-chain check (`spo pool opcert counter POOL`); the same line is printed by `store restore` of a file and of a sink into an empty directory. A crash at any point leaves the destination untouched until the restore's own atomic swap. A destination that holds another workspace is refused before anything is asked.
- **SPO-Xlayout-OUT-024** After a successful import the pin of the head used is recorded beside the new workspace file, in the same file the exporter keeps (OUT-017), so that an export that follows continues the chain: the exporter accepts the directory (the pinned head is there and hashes to the pin; the head's audit position is the workspace's) and writes the next head, or says that nothing changed. The pin is recorded only when the head's note equals, in every field but its time, the note the importer would encode for the installed workspace (`layoutread.NoteMatchesSnapshot`: workspace, epoch, recovery key, audit position, and a checkpoint key that is none or the installed workspace's own): the manifest binds the sequence, previous head, slots object and audit head, not the note's key or time. Otherwise no pin is recorded and the output says the next export needs a fresh directory or `--adopt-layout`. A pin already recorded for the directory that is not behind the head is left as it is and said so; the import is complete either way.
- **SPO-Xlayout-PRE-025** Both commands refuse before any prompt whatever can be refused then: a missing or malformed pin, an `s3://` URL, a directory that is not a layout or whose mode or owner is refused, a head chain that does not verify, a slot table that breaks its policy, a pin the directory is behind, `--unlock recovery-composite`, a hardware or strict workspace in a binary with no factor source, flags that do not belong to the chosen direction (`--pin`, `--at` and the restore flags with `--to-layout`; the checkpoint flags with `--from-layout`), and, for the import, an existing workspace without `--force`, `--allow-other-workspace` without `--force`, `--allow-weaker-policy` without `--force`, a workspace of another id without `--allow-other-workspace`, and a missing `spo.toml` without `--network`.
- **SPO-Xlayout-PRE-026** The credential is the one the policy of the slots object takes: the passphrase of a standard workspace; the daily authenticator of a hardware or strict workspace, through the factor path (PIN once, a touch for each presentation). A passphrase never opens a hardware or strict workspace, `--unlock passphrase` with one and `--unlock fido2` with a standard one are refused, and `--unlock recovery-composite` is refused. A wrong credential is the ordinary wrong-passphrase or wrong-authenticator error and nothing is left behind. The credential is presented to open the slot table, again for the store's verification of the scratch file and, for an import, again by the restore (a standard workspace holds the passphrase it read once; a hardware workspace costs the authenticator one touch for each presentation, which the output of the factor path announces).
- **SPO-Xlayout-INV-024** The reader is bounded, and no length, count or size from the directory is used to allocate before it is checked against a bound. At most 100,000 heads; a head at most 4 KiB and a signature file at most 16 KiB; an object at most 4 MiB, read up to that size plus one byte (an endless file costs that much and no more); a root that claims more than 100,000 records, 500,000 audit rows or 196 + 500 pages (the limits of a snapshot, `ports.Snapshot.Validate`) is refused before any page is fetched, so a manifest that claims a billion entries costs nothing; a page or root whose CBOR claims a billion entries is refused by the decoder without allocating for the claim (under 32 MiB allocated, asserted); at most four gibibytes of objects read in one pass (`MaxStoredBytes`; the claims above already bound the objects the root can name to 2.4 GiB); the bytes of the fields of the rows are counted as each row is read and refused past 256 MiB (`MaxFieldBytes`, the snapshot limit), before the row is copied, not only when the snapshot is validated; at most eight objects in flight (`Workers`), each released after it is decoded and its fields copied. **Worst-case resident size at the snapshot limits:** the snapshot (at most 256 MiB of fields and the row structures, about 80 MiB for 600,000 rows) is held once by the reader and a second time while the store writes the scratch file and reads it back to compare, plus about eight objects of 4 MiB each and their decoded forms: under 1 GiB. The measurement on a layout with 50,000 audit rows and 200 records is `TestMeasureLargeLayout` (skipped unless `SPO_MEASURE=1`); the figures are in the handoff. Every read honours the context.
- **SPO-Xlayout-INV-025** A directory that changes while it is read fails closed. Every object is hashed against its name when it is read, so a file replaced between the checks and the read, or between two reads, does not match; the directory is held as one descriptor and every read is relative to it, so replacing the directory cannot redirect a read; and at the end of the unlocked pass the head used is read again and must be the bytes the locked pass saw, or the check fails (ErrChanged).
- **SPO-Xlayout-INV-026** An import is the workspace row for row. The rows read back from the imported file equal the rows of the exported workspace in every column of every table except `meta.cleanup_pending`, the transient column of Xsnapshot OUT-002, for every fixture family of the snapshot tests (standard with records of every class, cold-role records under all three policies, a previous wrap, a healed record, a workspace rotated to hardware and to strict, a slot added and removed, a passphrase changed and rekeyed, one migrated from format 2 and from the legacy format, with a checkpoint key record and with counter records). The imported workspace passes `store verify --deep`. An export after an import continues the chain (OUT-024).
- **SPO-Xlayout-INV-027** The use case `internal/app/layoutread` imports no adapter, no platform package, no other use case, no `os`, `net`, `syscall` or random source: an architecture test fails otherwise. It reads a directory only through `ports.ObjectReader`, unlocks only through `ports.LayoutKeyOpener`, and gets scratch space only through `ports.Scratch`.
- **SPO-Xlayout-SEC-008** The reader and the importer never open a record payload. `ports.ObjectOpener` has no operation that returns one (the envelope of an object, the owner blob's anchor and number, the lookup tag and the epoch MAC are all it offers), and a cold-role record is carried through the import byte for byte: its four sealed fields in the rebuilt snapshot equal the workspace's, and the keys the reader holds do not open its payload (the master-derived keys open only its outer layer, ADR 0011).
- **SPO-Xlayout-SEC-009** Everything the directory supplies that reaches the terminal (a path, an object name, an error text, a notice) goes through the terminal-safe quoting of stage 1. The output contains no passphrase, PIN, recovery key or authenticator secret.

## Not covered

That the byte `0x03` will later mean chunked objects: it is only refused here. That a real bucket accepts objects of 4 MiB. The bytes of the recovery wrap, which are an open-only vector (OUT-013).

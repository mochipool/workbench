# Xobjstore: the narrow S3 client and the S3 stand-in

This spec is not upstream behaviour. It specifies work packages 2 and 3 of [ADR 0015](../../docs/explanation/adr/0015-stateless-relay.md): an S3 client that the relay binary may link (`spo/internal/adapters/objstore/s3client`), the Signature Version 4 it shares with the unlock backends (`spo/internal/platform/sigv4`), and an in-process S3 stand-in for tests (`spo/test/s3stand`), honest and hostile. The lease, the mailbox adapter and the registry adapter that use the client are later packages. No real object store was contacted to write or test it.

Terms: a **conditional put** carries `If-None-Match: *` (create only) or `If-Match: <ETag>` (overwrite of exactly that ETag). A **typed outcome** is an error that `errors.Is` matches against one sentinel per status. The **stand-in** is the test server; its **honest mode** is what S3 is documented to do, its **hostile modes** are faults switched on per test.

## Interface

- **SPO-Xobjstore-IF-001** `Client.Put` makes only conditional puts: exactly one of `IfNoneMatch` and `IfMatch` is set, otherwise `ErrUnconditional` before any request. There is no unconditional put, because both buckets' policies deny one (ADR 0015 decision 3) and every write of decisions 2 and 5 is conditional. A key is 1 to 1024 bytes of letters, digits, `.`, `_`, `-` and `/` with no empty, `.` or `..` segment (`ErrInvalidKey`); the body is held whole, at most 4 MiB.
- **SPO-Xobjstore-IF-002** A refused request is a `*StatusError` with the operation, the key, the status, the S3 error code, the number of attempts, the delete-marker flag and `Uncertain`. `errors.Is` matches 412 to `ErrPreconditionFailed`, 409 to `ErrConflict`; a 404 to `ErrNotFound` only for the codes `NoSuchKey` and `NoSuchVersion` and for a 404 without a code to a GET or a HEAD of an object; a 404 `NoSuchBucket` to `ErrBucketNotFound`; 403 `RequestTimeTooSkewed` to `ErrClockSkew`, any other 403 to `ErrAccessDenied` (a policy deny or a delete that retention refuses), 400 `BadDigest` and its kin to `ErrBadDigest`, a 3xx to `ErrRedirect`, every refusal to `ErrStatus`, and a refusal with `Uncertain` also to `ErrOutcomeUnknown`; no status matches another's sentinel. Any other 404 (a code-less 404 to a put or a delete, a bucket configuration not found) is `ErrStatus` only. A HEAD answer has no body and so no code: a HEAD 403 is `ErrAccessDenied` even for a skewed clock, and a HEAD 404 is `ErrNotFound` even for a missing bucket.
- **SPO-Xobjstore-IF-003** `ReadBack(key, body)` reads the current version back, bounded by the length of `body`, and reports one of three states: `ReadBackApplied` (the bytes are `body`), `ReadBackNotYet` (as of this read the key is absent, `NoSuchKey`, or holds other bytes) or `ReadBackCannotTell` (with the error: a 403, which a store without `s3:ListBucket` gives for a missing key, a missing bucket, a deadline, a bad answer). `Applied` means the writer's own write or one with the same bytes. Its precondition is the caller's: equal bytes must mean "my write or an equivalent one" (the lease carries the holder id and the renewal counter; a mailbox entry's name holds its hash; a tombstone or a binding with the same bytes is the same record).
- **SPO-Xobjstore-IF-004** `Get` reads an object (or one version) whole, with a bound of 1 byte to 16 MiB that the caller states; `Head` reports size, ETag, version id, retention mode and date (see IF-002 for what its refusals cannot say); `Delete` removes by name (in a versioned bucket it adds a delete marker and reports it); `DeleteVersion` removes one version by id. A delete's visible effect is idempotent: after one attempt or several the key or version reads as absent. In a versioned bucket a simple delete is not idempotent in its versions: each attempt that landed adds one more delete marker, so a retry after a lost answer can leave two. For ADR 0015 that is harmless: the registry role may make a simple delete only on `registry/bindings/*`, a stacked marker reads as absent, a create with `If-None-Match: *` over it succeeds, and the lifecycle rule of decision 3 removes noncurrent markers there.
- **SPO-Xobjstore-IF-005** `List` reads one ListObjectsV2 page under a prefix with keys, sizes, ETags and the continuation token; `ListAll` reads every page within a stated bound on the number of objects (`ErrListLimit` above it).
- **SPO-Xobjstore-IF-006** `ListVersions` reads one ListObjectVersions page with object versions and delete markers told apart (`DeleteMarker`), with their version ids, newest first per key, and the key and version-id markers; `ListAllVersions` reads every page within a stated bound.
- **SPO-Xobjstore-IF-007** A put may carry an Object Lock retention (`COMPLIANCE` or `GOVERNANCE`, a retain-until date in whole seconds) and a SHA-256 checksum (`x-amz-checksum-sha256` with `x-amz-sdk-checksum-algorithm: SHA256`); a retention always carries the checksum. A put whose answer echoes another checksum fails with `ErrChecksumMismatch` joined with `ErrOutcomeUnknown` (the store committed something). A get with `Checksum` checks a checksum the store reports against the bytes and passes when it reports none; a get with `ExpectSHA256` hashes the bytes received and compares, whatever the store reports. Either mismatch is `ErrChecksumMismatch`.
- **SPO-Xobjstore-IF-008** `Versioning` and `ObjectLockEnabled` read the bucket's state (a missing Object Lock configuration is "not enabled"). `SelfTest` runs the checks of ADR 0015 decision 2 one request at a time. In every bucket: the bucket exists (its versioning status is read; a missing bucket is `ErrBucketNotFound`), a create over an existing object is 412, an overwrite with a wrong `If-Match` is 412, two writes of different bytes give different ETags, a written object is read back and listed at once, and the test object is deleted (by name in the working bucket, each version by its id in the registry bucket, so no delete marker is left). The working bucket must report versioning never enabled (PRE-005). The registry bucket must report versioning on and Object Lock enabled, and a simple delete of `registry/tombstones/selftest-<16 hex>` must be refused by the policy (without the deny, the marker it made is removed by version id and the test fails). With `Retention` (registry only, at `init-store` and `store verify`, not at every start): a create with a one-day retention read back by a GET with its mode and date, a delete of that version by id refused, the version listed; that one object stays locked and is left for the sweep. A run that fails part-way removes what it wrote where the store lets it; the removal runs on a context of its own, bounded by 5 s, so a run whose context ended (a stop during the start) cleans up too. So a start-up run, and a crash loop of them, leaves nothing behind. *This changes ADR 0015 decision 2, which had a locked object at every start.*
- **SPO-Xobjstore-IF-009** Credentials come from a `Provider` the caller supplies (`Retrieve(ctx) (Credentials, error)`): an access key id, a secret, a session token and an expiry. One `Retrieve` runs at a time for every request that needs a set, in its own goroutine, bounded by `CredentialFetchTimeout` (30 s), with the values of the request that started it; no lock is held across it, and each waiting request gives up at its own deadline. The package has no fixed-set provider: tests write their own. Web identity is a later package. *Amended after the security review of work package 10:* a set with more than five minutes left is used as it is; inside those five minutes a set that outlives the request's deadline by a minute is used at once and the refresh runs in the background (one at a time; a caller's cancellation does not end it; bounded by `CredentialFetchTimeout` and ended by `Close`, which waits for it at most 2 s), so a provider that fails for a while does not fail a request while the set is valid. A background refresh that fails is tried again after 1 s, doubling to 30 s, not at every request; one that succeeds resets the back-off. A request blocks on a fetch only when there is no set or the set is nearly expired (less left than its deadline and a minute), and an expired set is never used. After `Close` no fetch runs.
- **SPO-Xobjstore-IF-010** Signature Version 4 is `platform/sigv4.Sign`, which takes the secret through a lending function and imports no secret buffer type. The unlock backends (`adapters/vaultkms`) lend it their guarded buffer; the S3 client lends a copy it wipes. The published vectors hold for it: get-vanilla, IAM ListUsers, the signing-key derivation, and the S3 GET Object, PUT Object, GET Bucket Lifecycle (`?lifecycle`, an empty value) and ListObjects examples (the S3 figures recalled from memory; the page could not be fetched). Vectors with no published figure (a session token with reserved characters; a create-only put with the checksum and retention headers; an overwrite with `If-Match`) were derived with the stand-in's independent implementation (`s3stand.RefSign`) and both implementations must give them.

## Modes

- **SPO-Xobjstore-MODE-001** Path-style addressing puts the bucket in the path (`https://host/bucket/key`); virtual-host addressing puts it in the first label of the host (`https://bucket.host/key`), and a bucket name with a dot needs path style over TLS. Both are signed with the host they are sent to.

## Outputs

- **SPO-Xobjstore-OUT-001** A store that fails the self-test is refused with a `*SelfTestError` whose `Property` is the property's sentence and whose message names it.

## Preconditions and failures

- **SPO-Xobjstore-PRE-001** Every request needs a context deadline (`ErrNoDeadline` otherwise). Retries are made only for requests that are idempotent (get, head, delete, listings, bucket reads) or conditional (every put), only after a transport failure or a 500, 502, 503, 504 or 429, at most `MaxAttempts` (3 by default) with a doubling wait, and never when the wait would leave less than the wait again before the deadline. A 4xx and a 3xx are never retried.
- **SPO-Xobjstore-PRE-002** A write (a put or a delete) matches `ErrOutcomeUnknown` when any of its attempts may have been applied: an attempt that got no answer (a lost response, a reset, the deadline or a cancel while it was in flight), any 5xx (a proxy may answer one after the backend committed), or a 2xx whose body fails the bounds or whose ETag, version id or checksum fails the checks. It is matched by whatever error ends the write: a later credential or signing failure, a final 5xx, a bad body, and a definite refusal (412, 404, 409, 403 or any other) after such an attempt, which keeps its own sentinel and carries `Uncertain`. A 429 is a rate limit answered before the request is processed and, with every other 4xx and 3xx, is a definite refusal that does not set it; neither does an attempt never sent (the context done before it, credentials refused). A read never matches it.
- **SPO-Xobjstore-PRE-003** After a write that matches `ErrOutcomeUnknown`, the caller reads back (IF-003): `ReadBackApplied` is success; `ReadBackNotYet` is a conflict (the exit rule of ADR 0015 decision 5), never "absent, so write again with different content", because the store may still apply the first write for as long as its signature is valid (15 minutes); `ReadBackCannotTell` is a store error, not success. A `PutResult` returned with such an error after a 2xx holds the ETag and version id that passed the checks, to compare with the read-back's `Info`.
- **SPO-Xobjstore-PRE-004** `Head` alone must not decide that an object or a bucket exists or not where it matters: its 404 cannot tell the two apart. A missing bucket is found with a request whose 404 carries a code: the self-test reads the bucket's versioning status first and fails with `ErrBucketNotFound`.
- **SPO-Xobjstore-PRE-005** The working bucket must report versioning never enabled (an empty status): `Enabled` and `Suspended` both fail the self-test, because ADR 0015 decision 3 depends on "a delete removes the bytes". Reading it needs `s3:GetBucketVersioning` on the working bucket, which ADR 0015 decision 2 grants on the registry bucket only; the working bucket's role needs it too.

## Security

- **SPO-Xobjstore-SEC-001** Only short-lived credentials are used: a set without a session token or an expiry is `ErrStaticCredentials`, one past its expiry `ErrCredentialsExpired`, one that expires more than 12 hours ahead `ErrCredentialsTooLong`, all before any request. A set is cached until five minutes before its expiry. No credential appears in an error, and the `Credentials` type prints as redacted under every verb.
- **SPO-Xobjstore-SEC-002** The endpoint must be `https`; plain `http` is accepted only to a loopback IP literal with the explicit test opt-in. TLS 1.2 is the minimum, no proxy is used, and no redirect is followed, so no credential goes to another host.
- **SPO-Xobjstore-SEC-003** Every response is read within a stated bound: a success body within the request's bound (a get's, 4 MiB for a listing page by default, 8 KiB for an error document), checked against `Content-Length` before any byte is read and against the bytes read after; a body shorter than its length is `ErrTruncated`; the header block is at most 32 KiB; transparent decompression is off. Header values that are used (ETag, version id, retention, checksum) are checked before use.
- **SPO-Xobjstore-SEC-004** XML is decoded strictly, token by token, with no entity map (only the predefined entities and character references decode, nothing expands), no charset reader, no document type or other directive, no processing instruction other than the declaration, one root of the expected name, nesting at most 6, element text at most 2048 bytes, and at most 16 elements per entry asked for. Sizes are decimal without a sign or a leading zero; a delete marker has no size; an entry lacks no required field and repeats none.
- **SPO-Xobjstore-SEC-005** A listing is checked: every key is in the alphabet and under the prefix, keys strictly increase within and across pages (versions: keys do not go back and no key and version id repeats, and `IsLatest` is set on exactly the newest entry of each key, which a page that continues a key from the markers does not repeat), no page has more entries than asked, a truncated page has a continuation and at least one entry, and the continuation advances. A listing that fails is `ErrBadListing`.
- **SPO-Xobjstore-SEC-006** An answer to a get or a head by version id must name that version (`ErrBadResponse` otherwise); an answer to a delete by version id that names another is `ErrBadResponse` joined with `ErrOutcomeUnknown`. A version id a store invents in a put's answer cannot be seen on the put; a head or a get by that id finds nothing.

## Invariants

- **SPO-Xobjstore-INV-001** The client and `platform/sigv4` link nothing the relay binary may not (SPO-Xmailbox-SEC-078: no `internal/ports`, no `platform/secret`, no AWS SDK) and nothing relay-banned (SPO-Xmailbox-SEC-009). The key agreement, key derivation and AEAD packages are reached only below the standard library's TLS stack (`crypto/tls`, `crypto/x509`), the store connection's transport, as the tunnel's are below the tunnel adapter. Their direct imports are exact allow-lists.
- **SPO-Xobjstore-INV-002** The stand-in is never in a release binary: `cmd/spo` and `cmd/spo-relay` do not contain it, and no non-test file outside `spo/test/` imports any package under `spo/test/`, checked over every `.go` file whatever its build constraints, with one exception: `cmd/spo/wiring_plain.go` (built only with `-tags plainlayout`) imports `test/plainstore`, as the custody architecture tests allow. The S3 client declares no fixed-credential provider outside its tests.
- **SPO-Xobjstore-INV-003** The stand-in's honest mode does what S3 is documented to do for what ADR 0015 relies on: strong read-after-write and listing; 412 for `If-None-Match: *` over a live object and for `If-Match` with another ETag; 404 for `If-Match` on a missing object or a current delete marker; versioned buckets (a put adds a version, a simple delete adds a marker, a delete by version id removes that version), suspended ones (the `null` version replaced) and unversioned ones; Object Lock in compliance and governance mode (a delete by version id refused until the date, governance bypass only with the right and the header, a simple delete still adds a marker), and never without versioning enabled; the bucket-policy denies of a simple delete on the tombstones and the marker and of a put without a condition, and a principal limited to its prefix, optionally without `s3:ListBucket` (a missing key is 403) or `s3:GetObjectRetention` (no retention headers); ETag = MD5 of the body, or with `OpaqueETag` an ETag that is not the MD5 and differs per write (SSE-KMS), under which the client's contract tests pass too; SHA-256 checksum refusal; Signature Version 4 verified by a second implementation that shares no code with `platform/sigv4` (exported as `RefSign`), with a 15-minute skew limit and the session token required to be the principal's exactly; paged listings and version listings, a version-id marker that names no version refused. Each property states its source (documentation or memory) where it is implemented, and the package comment has a table of where the stand-in is laxer than S3 or its fidelity unknown (racing conditional writes never answer 409 unless injected; the status of a wrong region or token).
- **SPO-Xobjstore-INV-004** The stand-in's hostile modes, each switchable per test by operation, key prefix and count: a lost response after a commit, a commit answered with a 5xx, a write applied after the client's deadline or twice, 412, 404, 409 or any status at will, a stale listing (which panics without an earlier snapshot rather than serve live data), a listing that omits or repeats keys, a version listing whose `IsLatest` lies, truncated, falsely sized and oversized bodies, hostile XML, a wrong ETag, version id or checksum in a success answer, a damaged body accepted with the client's checksum, a body damaged on the way, a stall before the headers or in the body, a slow body, a redirect, a clock that disagrees; and, as a foreign principal or the store's operator, a write of any bytes (the same bytes as another writer's among them), a delete marker over a locked version, a lower version on top, an older version restored as current and a rollback (refused for a compliance-locked version). A recorder keeps every request with its conditions, retention and checksum headers, principal and status, and lists the unconditional puts.

## The object-store lease (ADR 0015 work package 6)

The lease of ADR 0015 decision 5 over the client, `spo/internal/adapters/objlease`, implementing `relayport.Lease` (SPO-Xmailbox-IF-031). Its ids are numbered from 101 so they cannot meet the ids of the mailbox and registry adapters, written at the same time. "The lease clock" is the clock the lease is given: `time.Now`'s monotonic reading in production. The term is the duration minus the margin; the take-after time is the duration plus the margin.

- **SPO-Xobjstore-IF-101** The lease object is a record of eight lines, each `name value` and a newline, in this order: `spo-lease 1` (the version), `node` (the relay's node public key, 64 lower-case hex), `holder` (32 lower-case hex), `generation` and `counter` (decimals from 1, no sign, no leading zero), `duration-ms` and `margin-ms` (whole milliseconds; the duration from 1 s to 1 h, the margin below it) and `state` (`held` or `released`). A body over 256 bytes is refused before it is read; a missing, repeated, reordered, renamed or extra line, another version, a carriage return or any other byte is refused (`ErrUnreadable`). Decoding accepts only the canonical encoding of what it returns, and encoding refuses what decoding would. *Amended in the review of work package 6, 2026-11-20:* the duration is from 1 s to 5 minutes (`MaxDuration`, the longest a waiter honours) and the margin from a third of the duration to below it; a record outside these is unreadable (PRE-102), not foreign.
- **SPO-Xobjstore-IF-102** `objlease.New(Config{Store, NodeKey, Clock, Wall, Times, Tick})` makes a lease of `relays/<node key>/lease` in the working bucket with a holder id of 16 random bytes, new for each lease value, so for each process. It makes no request. `Times` are `DefaultTimes()` when zero: a duration of 30 s, a margin of 10 s, a drain of 15 s, a poll every 5 s and requests of at most 10 s. `Wall` defaults to the lease clock's reading without its monotonic part; `Tick`, the real time between two looks at the lease clock while waiting, to 250 ms. *Amended in the review of work package 6, 2026-11-20:* the lease implements `relayport.LeaseTerm` (`Term()`, the duration minus the margin) and `relayport.LeaseLoser` (`Lose()`: the lease is lost from then on without a request, and a renewal in flight cannot extend it); `Config.Logf` takes its notes for the operator log (a record whose duration or margin exceed the waiter's own, an absent object).
- **SPO-Xobjstore-IF-103** `Acquire` reads the object every poll interval of the lease clock, each read bounded by the request timeout. An absent object is created with `If-None-Match: *`; a released one is taken at once with `If-Match` on the ETag read; a held one is taken with `If-Match` on the ETag read only after the waiter saw the same ETag and the same bytes (so the same holder, generation and counter) for the take-after time, the larger of its own and the record's duration plus the larger margin, on its own lease clock, counted from the answer of the first read that showed them, never from a store timestamp or another host's clock. A take writes this holder's id, the generation raised by one, the counter raised by one and `held`. After the take of a held lease (a lapsed one) `Acquire` waits the drain period on the lease clock, sends nothing during it, then renews once, so the lease end counts from after the drain; the take of an absent or released lease has no drain. `Acquire` returns the context's error, wrapped, as soon as its context ends; cancelled during the drain, the lease is lost. *Amended in the review of work package 6, 2026-11-20:* an absent object is lapsed, not free: it is created with `If-None-Match: *` only after the waiter saw it absent, read after read, for the take-after time (its own duration and margin, or the larger of a record it saw earlier in the same `Acquire`), and the create is followed by the drain as the take of a lapsed lease is; on a healthy store an ordinary start never meets an absent object, because `init-store` writes a released record (IF-106). During the drain the taker sends no state write and no read; it renews the lease every quarter of the term, counted from the sending of the renewal before (a take answered after 6 s is still held after the drain), and renews once more at its end; a renewal during the drain that fails without a loss is survived while the lease lasts. *Amended after the review of work package 10 (2026-11-20):* a take whose outcome is unknown and whose read-back does not show it is pending: the waiter holds nothing and goes on reading at the poll interval; while a read shows the record the take is conditional on it sends only the same take again (the same bytes, the same condition); a read that shows the take's bytes confirms it from its first copy's sending (then the drain, for a lapsed lease), unless the term it began has passed, when the record is waited out like any held one; any other record ends the pending take. Cancelled while a take is pending, `Acquire` returns the context's error and the lease is lost.
- **SPO-Xobjstore-IF-104** `Renew` is an `If-Match` on the holder's own last ETag with the counter raised by one. A confirmed renewal holds the lease from the moment it was sent, on the lease clock, for the term. The renewal is not sent, and the lease is lost, when the lease end has passed on the lease clock or on the wall clock (a paused process whose monotonic clock stopped). Its request deadline is the earlier of the request timeout and the lease end; an answer that arrives at or after the end it was meant to extend is a loss. `Until` reports the lease as not held, and closes `Lost`, once its end has passed on either clock. *Amended in the review of work package 6, 2026-11-20:* after `Lose` a renewal is a loss and sends nothing, and one that was in flight is not confirmed even when the store applied it.
- **SPO-Xobjstore-IF-105** `Release` writes the record with `released` and the counter raised, with `If-Match` on the holder's last ETag, only while the lease is held and before its end; from the moment it starts the process holds nothing and sends nothing more. That `released` state is how a waiter knows it need not wait or drain. A release after the end, or of a lease already lost, sends nothing and is no error; one answered 412, 404 or 409 is no error (another holder has it); one whose outcome is unknown, or that was refused otherwise, returns an error and the lease lapses. *Amended after the review of work package 10 (2026-11-20):* a release whose outcome is unknown is read back once (a read, not a write) before the lease end: the released bytes are success. A release while a renewal is pending is conditional on the last confirmed ETag, as the pending renewal is, so at most one of them lands; a 412, 404 or 409 to it then returns an error and the lease lapses, as the renewal may be what moved the ETag.
- **SPO-Xobjstore-IF-106** `objlease.Init(ctx, store, nodeKey)` writes the first lease record of an identity create-only (`If-None-Match: *`): released, holder `InitHolder` (32 zeros), generation and counter 1, the default duration and margin (`InitRecord`). `init-store` (work package 9) calls it, so the first start takes the lease at once while an absent object is lapsed for every later one. An object already there that is a record of this node key is left as it is and is no error; one that is not a readable record is `ErrUnreadable`, one of another node key `ErrForeignLease`, both left as they are; a create whose outcome is unknown is read back. A context without a deadline gets the default request timeout. *Added in the review of work package 6, 2026-11-20.*
- **SPO-Xobjstore-PRE-101** Every write of the lease follows the client's rule (PRE-003). Success: the ETag the store answered is the holder's. An error that matches `ErrOutcomeUnknown`: the lease reads the object back before its end; equal bytes are success with the ETag the store reports for them; a read-back that does not show the write, or cannot tell, is a loss, after which this lease never writes again and never writes other content in its place. A 412, 404 or 409 without an unknown outcome: for a renewal a loss; for a take, the waiter goes on waiting and reads again. Any other refusal (a 429, a 403, a request never sent) leaves the lease as it was; it still ends at its end. A storm of 5xx is an unknown outcome and so a loss. *Amended in the review of work package 6, 2026-11-20:* a renewal whose outcome is unknown and whose read-back shows this holder's own previous record with its ETag (the write has not landed) is sent again with the same bytes and the same `If-Match`, at most `MaxResends` (2) times and while the lease lasts; the rule forbids other content, not the same write. A resent renewal answered 412, 404 or 409 is read back: its own bytes are success (the first copy landed), anything else a loss. A copy that lands later finds the ETag changed and is refused. A renewal holds the lease from its first sending. *Amended after the review of work package 10 (2026-11-20):* a write whose outcome is unknown and whose read-back cannot tell (5xx, no answer, 403) or shows the record it is conditional on is pending, not a loss: a pending renewal returns an error without a loss, the lease keeps the end of the last confirmed renewal, and the next renewal sends the same bytes with the same `If-Match` (no renewal with other content is built until one copy is confirmed; the rule and why it is safe are in `adapters/objlease`, "Pending writes"). A copy answered 412, 404 or 409 after an earlier copy was sent is read back: the pending bytes are success, another record (another holder, another generation, no object) a loss at once; a read that cannot tell leaves it pending. A copy answered 200 holds the lease from its own sending; a renewal settled by a read-back from its first copy's sending. A definite refusal of a first copy (429, 403, not sent) drops it: nothing of it was applied. "A storm of 5xx is an unknown outcome and so a loss" no longer holds: such a storm is ridden out until the lease end. A pending take does not end `Acquire` (IF-103).
- **SPO-Xobjstore-PRE-102** An object the waiter cannot read as a record of version 1 (over 256 bytes, malformed, another version) refuses the start with `ErrUnreadable`, and one that names another node key with `ErrForeignLease`; neither is taken over and nothing is written. Treating it as held and taking it after the take-after time would overwrite a record whose duration and holder are unknown (a newer relay's, during a rollout), so the refusal names the object and asks the operator to check that no relay of the identity runs before removing it. *Amended in the review of work package 6, 2026-11-20:* the remedy is to overwrite the object with a released record with the store tool (`spo-relay store`, work package 9), never to remove it: a removed object is lapsed (IF-103), and the bucket policy denies its delete (ADR 0015 decision 3). A record whose duration exceeds 5 minutes (`MaxDuration`, ten times the default) or whose margin is under a third of its duration is unreadable too.
- **SPO-Xobjstore-PRE-103** `New` refuses (`ErrInvalidConfig`) a configuration without a store or a clock, a node key that is not 64 lower-case hex, a duration outside 1 s to 1 h or not whole milliseconds, a negative margin or one not below the duration, a request timeout that is not positive or exceeds the term, a drain not longer than the request timeout or not shorter than the term, a negative poll or one not shorter than the take-after time, and a tick that is negative or over a second. *Amended in the review of work package 6, 2026-11-20:* the duration is at most 5 minutes; the margin is at least a third of the duration (so the take-after time is at least twice the term, INV-102); the request timeout is at most half the term (a take answered at its timeout leaves half the term for the first renewal of the drain); the drain is longer than the request timeout and at most the take-after time (it no longer needs to be shorter than the term, because the lease is renewed during it); a configuration without `Wall` whose clock's reading carries no monotonic part is refused.
- **SPO-Xobjstore-SEC-101** A store whose reads lag cannot make a waiter take a live lease: a take is an `If-Match` on exactly the ETag the waiter read, so a take from a stale view is refused (412) and the waiter reads again; the live holder's renewals are not disturbed.
- **SPO-Xobjstore-INV-101** The lease sends no unconditional write: its only create is `If-None-Match: *` on an absent object, every other write is an `If-Match`; after a loss it sends nothing.
- **SPO-Xobjstore-INV-102** Two leases never both hold at one moment, under these assumptions: the store's conditional writes are atomic (of two writes conditional on one ETag or on absence at most one is applied) and an applied write changes the ETag; the two processes' monotonic clock rates differ by less than a factor of two (the holder's authority lasts the term, 20 s, on its clock; a taker waits the take-after time, 40 s, on its own, from a moment after the holder's last write was sent; at equal rates that leaves 20 s); no principal writes or deletes the object outside these rules; a process's clocks run while it runs, or at least its wall clock does. A process whose two clocks both stopped (ADR 0015 decision 5, "A paused process") wakes believing it holds; its first renewal is an `If-Match` on its own old ETag and is refused, so it is lost without writing. A request the old holder sent before its end and that the store applies more than the drain period after the take is the residual of ADR 0015 decision 5 ("The lease does not fence"). *Amended in the review of work package 6, 2026-11-20:* the clock assumption is that the rates of the two processes' monotonic clocks differ by less than the ratio (D+M)/(D−M) of the record's duration D and margin M (the holder's authority lasts D−M on its clock, a taker waits at least D+M on its own); every configuration and record has M ≥ D/3, so the ratio is at least 2 (40 s against 20 s at the defaults). The object is not removed (the bucket policy denies `s3:DeleteObject` on `relays/*/lease` to every principal); one removed anyway is lapsed (IF-103), except that a removal, a create and a second removal between two reads of one waiter are not seen. A process whose two clocks both stopped wakes believing it holds: until its next renewal is refused it may send state writes (at most one keeper period plus the request's latency), and bytes it handed to the kernel before the pause may leave after its end; both are residuals of "The lease does not fence". No check of its own clocks narrows this: the wall clock is already compared with the last confirmed renewal's wall time in `Until`, which `RequestContext` calls first. The tests sample "both hold" at every step of the lease clock; that the store's conditional writes are atomic is assumed, not shown (the stand-in applies them one at a time).
- **SPO-Xobjstore-INV-103** Every write of the lease raises the counter, so every write changes the bytes and the ETag, with ETags that are the MD5 of the body and with opaque ETags alike; "unchanged" compares the ETag and the bytes, so the lease does not depend on ETag = MD5.
- **SPO-Xobjstore-INV-104** The lease package is linkable by the relay under the client's rules (INV-001): no `internal/ports` (only `relayport`), no `platform/secret`, no AWS SDK, no package under `spo/test/`; its direct imports are an exact allow-list.

## The registry adapter over the object store (work package 8)

The relay's registry of bindings and tombstones over the two buckets (`spo/internal/adapters/objregistry`), on the rules of `domain/relayregistry` as the directory store (`adapters/bindingstore`, SPO-Xmailbox-IF-014) has them. The ids are numbered from 801 so that they never meet the ids of the lease and the mailbox adapter.

- **SPO-Xobjstore-IF-801** `objregistry.Open(ctx, Config, ...Option)` implements `relayport.Registry` over two clients (`Config.Registry`, the versioned bucket with Object Lock; `Config.Working`, the unversioned bucket), the writer's `relayport.Lease`, the relay's clock, the node public key (the prefix `relays/<64 hex>/` in both buckets), the core's configuration, the retention mode (compliance by default, governance for a test deployment) and a request bound (10 s by default). It loads only under a held lease. It passes the registry contract (`relayporttest.RunRegistry`) unchanged over the S3 stand-in, with restarts, refused drops, learnt tombstones and unknown outcomes made by the stand-in's own faults.
- **SPO-Xobjstore-IF-802** The layout under the prefix: in the registry bucket `marker`, `registry/bindings/<device 40 hex>`, `registry/tombstones/p-<K 56 hex>-<device 40 hex>`, `a-<K 56 hex>`, `d-<device 40 hex>`; in the working bucket `marker` and `registry/rates`. Bindings and tombstones are encoded byte for byte as the directory store encodes them (`SPORB1`, `SPORT1` and 8 bytes of not-before); the marker is `SPORM1\n` and the node key (39 bytes); the rate object `SPORR1\n` and four 8-byte values (units and time of the new-binding bucket, then of the revoke bucket; 39 bytes). Every decoder is strict and bounded by its object's size. A load costs six requests plus one per tombstone version and one per binding (each name's current version is read without a version id and stands for its latest version); a registration one put; an invalidating revoke one put and one delete per binding; a refresh one listing page per thousand entries and one get per version not seen before; a sweep with nothing to do none; `SaveRates` one put. *Amended after the review of work package 8:* a load also costs one get per tombstone name of a stored binding that the listing did not show (PRE-803), a registration of a device not bound in memory under the presented key one get per such name it does not know (at most three), a renewal nothing more; a refresh at most `RefreshPages` (8) listing pages (IF-804); a sweep one delete per superseded version or marker entry it prunes (OUT-805, OUT-806).
- **SPO-Xobjstore-IF-803** `InitIdentity()` is the option of `init-store`: it writes the registry marker (create-only, locked for a year) only when neither bucket holds a marker or state of the identity, then the working marker when the working bucket holds no state; and, when it wrote the registry marker and finds no rate object, full rate buckets. An ordinary start writes no marker.
- **SPO-Xobjstore-OUT-801** Every difference from the directory store: the rate buckets are durable (OUT-802); a binding that fails verification at load is left in place, not loaded and replaced by the device's next registration, instead of moved to a quarantine; the load bounds tombstone versions, not names (PRE-802); a binding delete is a simple delete (the client has no conditional delete); the markers (PRE-801); unknown outcomes come from the store, not from a directory sync (PRE-804); a refused drop comes from the store's retention (PRE-805); `RefreshTombstones` finds what other writers left (OUT-804).
- **SPO-Xobjstore-OUT-802** `SaveRates` writes `registry/rates` with `If-Match` on the ETag the writer holds (create-only when there is none). The load restores it with `Core.RestoreRates`; a missing, damaged, oversized or out-of-range object restores empty buckets, never full ones, so a rolled-back or deleted rate object gives at most the burst a restart without stored state gives, and a deleted or damaged one gives none.
- **SPO-Xobjstore-OUT-803** Bindings are loaded after the tombstones from a listing and one get each, verified again with `relaybind` against every tombstone version loaded: an expired one, one over the relay's lifetime, a revoked one (a binding restored after its revoke among them) and one not on the allow-list are dropped and deleted from the store after every check has passed; an older version restored as current is loaded as the older binding it is, and the device's current one replaces it.
- **SPO-Xobjstore-OUT-804** `RefreshTombstones` lists the versions of `registry/tombstones/`, reads only the version ids it has not seen and merges them with `Core.MergeTombstones`; a listing that shows fewer or lower values lowers nothing. A latest version it has not seen (a write of another writer, a stale writer's late request) becomes the version the next raise is conditional on; a latest version it has seen (a stale listing) changes nothing. A failure of the listing or of a read is an error and leaves memory as it was. *Amended after the review of work package 8:* the listing is read in passes of at most `RefreshPages` pages a refresh (IF-804); a version it cannot read is merged at the strictest reading and counted in `MergeResult.Unreadable`, an object that is not a tombstone counted in `MergeResult.Foreign` and ignored (PRE-809); neither is an error.
- **SPO-Xobjstore-OUT-805** `Sweep` writes a new marker version, locked for a year and conditional on the current one, when the newest of the identity's marker versions is locked for less than eleven months (every 30 days). *Amended after the review of work package 8:* a new version is written when the newest has less than `MarkerRenewBefore` (30 days) left, so about every 335 days, and `Sweep` deletes by version id every object version of the marker but the identity's newest once its lock has ended on the relay's clock by a margin of the skew, and every delete marker but the current entry; a refused delete holds the marker's pruning back an hour. The store then holds at most two object versions of the marker (seven years of sweeps, measured), and delete markers, which whoever may delete there can add when the policy lacks the deny, are bounded apart (`MaxMarkerEntries`, 4096 entries a load reads) from the 64 object versions.
- **SPO-Xobjstore-PRE-801** A start refuses a store whose marker is missing in either bucket: `ErrStoreNew` when neither bucket holds anything of the identity ("run init-store only for a new relay"), `ErrStoreEmptied` when one bucket lacks the marker while the identity has state or a marker in the other (a prefix emptied, rolled back or wrong), or when a marker names another identity. The registry marker is found by a version listing, so a delete marker over it hides nothing. A registry bucket emptied under a working bucket that still names the identity is refused even with `InitIdentity`. *Amended after the review of work package 8:* the marker is present when any object version names this identity; a version that is not a marker, or names another identity, over it is noted and does not refuse the start (a holder of the role can write one, locked), and the renewal is conditional on it. Without this identity's marker, one naming another identity is `ErrStoreEmptied`.
- **SPO-Xobjstore-PRE-802** Tombstones are loaded from a version listing of `registry/tombstones/`: delete markers are ignored, every object version that exists counts whether or not it is current, and per scope key the highest not-before wins (`Core.LoadTombstoneVersion`). The start is refused (fail closed) for a version whose body is not a tombstone, a name that is not one (the self-test's probe name excepted), more object versions than `relayregistry.MaxTombstoneVersions` (1 048 576; `ErrTombstoneVersions`), as many delete markers, and a listing that goes back or repeats. A version the relay cannot read is never skipped: it may be the highest value of its name. *Amended after the review of work package 8:* a version whose body is not a tombstone, and an object whose name is not one, no longer refuse the start (PRE-809); the ceiling counts every object version listed, foreign ones too. The worst case the relay's own writes reach is 667 660 versions (`relayregistry.MaxTombstoneVersions`; OUT-806, PRE-806), so the ceiling is met only by versions someone else wrote.
- **SPO-Xobjstore-PRE-803** At load each name's current version is read without a version id; when the listing does not show it as the name's latest (or shows a version where the store serves a delete marker), the start is refused with `ErrStaleListing` and a later start lists again, so a listing that missed a raise never loads the lower value. A listing that omits a whole name cannot be told at load (Not covered). *Amended after the review of work package 8:* a listing that omits a whole name is caught where it matters. At load, for every stored binding that verifies, and at a registration of a device not bound in memory under the presented key (a fresh device or a key change), each of the three names that apply (`p-K-d`, `a-K`, `d-d`) that the writer does not know is read directly (one get); one that exists, or whose current version is a delete marker, was hidden: its versions are listed and read (or its current version stands for it when that listing hides it too) and it is enforced before the binding is admitted. The cost is at most three gets per stored binding at load and per such registration; a renewal and a replacement under the same key cost nothing, because their names were read then and later writes land on top, where the refresh finds them. A name hidden from the listing and from a read of its current version (a delete marker on top and the name's own listing hidden) is still not seen.
- **SPO-Xobjstore-PRE-804** A write whose outcome is unknown is read back at once: the same bytes is success. Otherwise a tombstone written or a binding deleted is applied to memory as the stricter state and kept unconfirmed (`Core.ApplyUnknown`): the revoke answers `Recorded` false and `Unconfirmed` true with an error wrapping `relayport.ErrOutcomeUnknown`, and the next `Sweep` or `RefreshTombstones` reads it back and settles it (`Core.Settle`: confirmed, sent again with the same bytes, or kept; past `relayregistry.UnconfirmedSeconds` the writer ends). A binding write with an unknown outcome is not applied, and the next write of that device reads the object first and adopts the late bytes. A 412, 404 or 409 that the read-back does not explain ends the writer: that write and every later one return an error wrapping `relayport.ErrAuthorityLost`; readers still answer. A revoke that stops after its tombstone is stored still names every binding it invalidates, and the next load drops them.
- **SPO-Xobjstore-PRE-805** A tombstone is dropped by deleting each of its versions by version id, the lowest not-before first, so what is left holds the highest value; a delete the store refuses (403, its retention) is `relayport.ErrDeleteRefused` and the drop is held (`Core.Hold`). Under retention a revoke at a full table therefore takes the unrecorded path (SPO-Xmailbox-PRE-049) and still deletes its binding.
- **SPO-Xobjstore-SEC-801** No unconditional put and no simple delete of a tombstone or of the marker is ever sent. Every tombstone version is written with an Object Lock retention in the configured mode until its not-before plus `relaybind.MaxLifetimeSeconds` plus `relaybind.SkewSeconds` and one second (and never less than an hour from now), and with a SHA-256 checksum; the registry marker is locked for a year. *Amended after the review of work package 8:* and never longer than PRE-808 allows.
- **SPO-Xobjstore-SEC-802** Every request is made under `relayport.RequestContext` with the writer's lease: a writer whose lease has ended sends nothing more, and its writes return an error wrapping `relayport.ErrAuthorityLost`. A request of a lost writer that the store applies after a successor loaded is merged by the successor's `RefreshTombstones`, which ends the bindings it revokes.
- **SPO-Xobjstore-SEC-803** Every get is bounded by its object's size (15 bytes for a tombstone version, 39 for a marker or a rate object, the record bound for a binding); the listings are read page by page with the counts checked before anything is kept. A listing far past the ceiling and a body of 64 MiB or one claiming a terabyte for a tombstone are refused within 16 MiB of allocation (measured: about 5 MiB for a page of 1000 versions, under 0.4 MiB for the bodies). *Amended after the review of work package 8:* such a body is no longer a refused start but a version read at the strictest reading (PRE-809), with a head for its lock; measured under 0.6 MiB.
- **SPO-Xobjstore-INV-801** The adapter links nothing the relay binary may not, under the rule of INV-001 (the TLS stack excepted for the primitives), and its direct imports are an exact allow-list (`internal/archtest`, `TestObjectRegistryIsLinkableByTheRelay`).

Added after the review of work package 8 (ADR 0015, "Changes after the review of work package 8"):

- **SPO-Xobjstore-IF-804** `RefreshTombstones` reads at most `RefreshPages` (8) pages of the version listing (each at most 1000 entries) and resumes, at the next refresh, where it stopped; a pass over the listing takes one refresh per 8000 entries. A pass resumed from a version the store no longer has resumes after its key (the rest of that key is seen in the next pass), and the prune never deletes that version. A refresh therefore sends at most 8 listing requests and one get per version it has not seen; a late write (on top of its name) is merged within one pass: one refresh up to 8000 entries, 84 refreshes (84 minutes) at the worst case of 667 660 versions.
- **SPO-Xobjstore-IF-805** The reads of a load and of a refresh run with at most `LoadConcurrency` (32) in flight, each under its own request context (so under the lease: a lease that ends or is lost stops every read not yet sent, `ErrAuthorityLost`), and the first failure stops the rest. The load reads the listing page by page and loads each name once all its versions are listed, so it holds one page and one name's entries, not the whole listing. At the worst case of 667 660 versions a load is 668 listing pages and as many gets: about 11 minutes at 30 ms a request (not measured); the lease is renewed meanwhile by the host's keeper, which starts before the store opens. Memory: 81 bytes per tracked version id (measured at 50 000, ids of 32 characters; the test bounds it at 200), so about 52 MiB at the worst case.
- **SPO-Xobjstore-OUT-806** `Sweep` deletes, by version id, the superseded versions of each live tombstone name whose lock has ended on the relay's clock by a margin of the skew (the date the store reported or the writer wrote, else the date the writer would write for its not-before): every object version but the name's highest (of equal ones the current, else the greatest id) and its current one. The highest is locked at least as long as any lower one the relay wrote, so the name's value never drops; a highest version written by someone else with a shorter lock is kept too. A name with an unconfirmed write is left; a refused delete holds that name back an hour; another failure ends the sweep's pruning, which the next sweep resumes; at most `PrunePerSweep` (4096) deletes a sweep. A version's lock ends at most its write time plus 180 days, twice the skew and a second (PRE-808), so the store holds the versions written within that and `relayregistry.VersionLagSeconds` (two days) and at most two older ones per name: 667 660 at most from the caps (`TestTheWorstCaseVersionCountFitsTheCeiling`). Retention is set once, at the write; a superseded version is never extended (the client has no `PutObjectRetention`).
- **SPO-Xobjstore-OUT-807** A tombstone write that meets a conflict the read-back does not explain is applied to memory as unconfirmed before the writer ends (`Core.ApplyUnknown`): the readers, which still answer, enforce it; the revoke's result is `Recorded` false, `Unconfirmed` true, and names the bindings it invalidates. In the core, `PartialRevoke` reports `Recorded` false whenever the tombstone write the revoke needed did not take, a raise over a stored lower value included (it was true for a raise).
- **SPO-Xobjstore-OUT-808** A conflict on `registry/rates` (a stale writer's late save, an operator's copy) does not end the writer: the object is read again, restored with `Core.RestoreRates`, which can only take tokens away (an unreadable, oversized or out-of-range one restores empty buckets), and its ETag adopted; the next period saves again. A save whose last outcome was unknown and that finds other bytes does the same.
- **SPO-Xobjstore-PRE-806** (the core, for every store) A raise of a stored tombstone that invalidates no binding is refused with `relayregistry.ErrNameRaiseRate`, which wraps `ErrRevokeRate` (the `limit` outcome), when the name has had `MaxRaisesPerName` (4) such raises in `RaiseWindowSeconds` (24 hours); the refusal changes nothing and takes no token. A revoke that invalidates a binding is never refused for it. The times are in memory (a restart starts the budget again; the durable revoke cap still bounds the relay-wide total), and a clock that steps back gains nothing. One name gains at most 733 versions from revokes of nothing in a lock's life.
- **SPO-Xobjstore-PRE-807** (the core) While a binding delete of a device is unconfirmed (`Core.ApplyUnknown`), a registration of that device is refused with `relayregistry.ErrDeletePending` (a `limit`, so the client tries again): the delete may still land and would remove the new binding (PRE-003). It ends when the delete is confirmed (a read-back, a later confirmed delete) or the bound of `UnconfirmedSeconds` ends the writer. The directory store is held the same way while its unlink's sync is unconfirmed.
- **SPO-Xobjstore-PRE-808** No tombstone version is written with a lock that would end more than the maximum lifetime, twice the skew, a second and `RetentionMargin` (one hour) after now (`ErrLockTooLong`): a compliance lock cannot be shortened, and a verified revoke's not-before is at most now plus the skew. The write fails as a store refusal: nothing is sent, the revoke is not recorded and its bindings are not deleted (the tombstone goes first), and the writer goes on. Only a bug, or a looser verifier, reaches it. A relay clock far ahead cannot write at all: the store refuses a request signed more than 15 minutes from its own clock (memory). At load a version whose not-before is ahead of the clock (written by someone else) is enforced as it is and noted: lowering it could re-open what it revokes, and its lock cannot be shortened; its scope stays revoked until the not-before plus 180 days, and the operator's only remedy in compliance mode is to wait or to start a new identity.
- **SPO-Xobjstore-PRE-809** A tombstone version the relay cannot read (a body that is not a tombstone, one larger than a tombstone, a listed size that is not a tombstone's) does not refuse the start or stop the refresh: it is enforced at the strictest reading, its scope (named by its key) revoked until the end of the lock the store reports for it, or for ever when it reports none (`relaybind.MaxTime`). That only adds to what is enforced, because the maximum of a name's versions is taken: it costs that scope, not the relay. A listed size that is not a tombstone's is read with a head only. A listed version that the store answers 404 for is never skipped: the name is listed again; no longer listed, it is gone (counted); still listed, it is read again, and a second 404 is enforced at the strictest reading with no lock (`MaxTime`). An object under `registry/tombstones/` whose name is not a tombstone names no scope: it is counted, noted and ignored. The load notes each kind, and a current version lower than an older one; the refresh counts them (`MergeResult.Unreadable`, `Foreign`), which the host should log.
- **SPO-Xobjstore-PRE-810** A read-back that shows the writer's bytes counts as its write only when, for a write with a retention, the version read back is locked in the configured mode or compliance until no earlier than the write asked; otherwise a locked version is written on top of it, conditional on it, once. The same holds for the read before a write sent again and for the settle, which sends the write again for an unlocked copy.

Added after the review of work package 9 (the store tools; ADR 0015, "Changes after the review of work package 9"):

- **SPO-Xobjstore-PRE-811** A tombstone version counts as storing its value only when it is readable and locked in the configured mode or compliance until its not-before plus the maximum lifetime, the skew and a second (`objregistry.LocksFor`, `TombstoneLockNeed`); a version with a shorter lock, a governance lock in a compliance deployment or none is enforced while it exists but does not count, because the relay's role can write one and delete it by its id once the lock ends. A revoke whose not-before memory already holds (no raise) but that no counting version holds at that value or higher writes the relay's own version first, before any binding is deleted: the value enforced, with its retention, or the revoke's own not-before when that value's lock would be refused as too long (PRE-808); memory is not changed. A second such revoke finds the relay's version and writes nothing. The write is an ordinary conditional put; its failure is returned with the revoke's result, a conflict the read-back does not explain ends the writer.
- **SPO-Xobjstore-OUT-809** `Sweep` deletes, by version id, the registry bucket's object versions under the identity's `selftest/` whose lock has ended on the relay's clock by a margin of the skew (the retention self-test leaves one locked for a day; ADR 0015 decision 2). It runs once every `SelftestEvery` (24 hours), the first an hour after `Open`, reads one listing page of at most `SelftestPerSweep` (64) entries and one head per object version on it; it never deletes a version without a lock (a self-test in progress, or a failed run's, which `store repair --action selftest` removes), a delete marker, or a key outside `selftest/`. A failure leaves the rest to the next pass; only a lost authority is returned. *This amends IF-802:* a sweep with nothing to do sends nothing, except this pass once a day (one listing).
- **SPO-Xobjstore-IF-806** For the store tools, `objregistry` exports its own layout and encodings, not copies: the paths (`MarkerPath`, `BindingsPath`, `TombstonesPath`, `RatesPath`, `SelftestPath`), the sizes, `TombName`, `ParseTombName`, `IsProbeName`, `EncodeTomb`, `DecodeTomb`, `EncodeMarker`, `DecodeMarker`, `EncodeRates`, `DecodeRates`, `DecodeRecord`, `MarkerLock`, `TombstoneLockNeed`, `TombstoneRetention` (the retention the registry itself writes), `LockedAsWanted`, `LocksFor`, `MaxLockAhead`; `objmailbox` exports `MailboxPrefix`, `EntryKey` and `ParseEntryKey`. `InitIdentity` still writes markers only over a store that holds nothing of the identity.

Not covered by the registry adapter: a listing that omits a whole name (at load nothing tells; the client's re-sent revoke is the defence, as for a full rollback of the directory store; *amended after the review of work package 8:* now caught for the names of stored bindings and fresh registrations, PRE-803); a version deleted by its id early (governance mode with the bypass); the extension of a marker's retention in place (the client has no PutObjectRetention; a new version is written instead); the shared operator tombstone set (stage 3); and every property only a real store can show (ADR 0015, "What only real infrastructure can show").

## The mailbox over the object store (ADR 0015 work package 7)

The package `spo/internal/adapters/objmailbox` implements every mailbox port of `relayport` (`MailboxStore`) over the client, in the working bucket, under the relay's lease. Its ids are numbered from 701 so that the other packages of ADR 0015 can number theirs without a clash. Where it does what the directory store does (`adapters/mailboxstore`, SPO-Xmailbox-OUT-012 to OUT-032, SEC-005, SEC-007), the Xmailbox requirement holds and is not repeated; what differs is said here.

- **SPO-Xobjstore-IF-701** `objmailbox.Open(ctx, Config{Client, NodeKey, Lease, Clock, LeaseClock, RequestTimeout})` opens the store of the relay whose node public key is `NodeKey` (64 lower-case hex digits) under the held `Lease`; `Clock` is the store's clock (arrivals, sweeps), `LeaseClock` the lease's (the `now` of `relayport.RequestContext`; nil is `Clock`), `RequestTimeout` the bound of one request (0 is 10 s, more is refused). `LeaseClock` (or `Clock` when it is nil) must give readings with a monotonic reading, as `time.Now` does, because the lease end is judged on the monotonic clock; Open refuses one that does not. One object per entry, at `relays/<node key>/mailbox/<recipient, 40 hex>/<arrival, 20 digits>-<mid, 64 hex>-<sender, 40 hex>-<nonce, 16 hex>`: up to the sender it is the directory store's entry name (SPO-Xmailbox-OUT-012); the nonce is 64 random bits drawn once per put (OUT-707). Every character is in the client's key alphabet, and the key order of a listing is arrival order within a recipient. The sender, the id and the arrival are in the key and the size is in the listing, so nothing of an entry is read to index it; no header is inside the object, which is the sealed envelope's bytes. The nonce plays no part in what an entry is: the recipient, the sender and the id are.
- **SPO-Xobjstore-OUT-701** Open rebuilds the index, the quota counters and the per-pair and per-sender accounting from one listing of the prefix, page by page (1000 keys a page), with no GET: a second store loads what the first stored with the same order, counters and duplicate answers. Of two objects with one sender and id the earlier is the entry and the later is **doomed**; the directory store deletes the later file at open, the object store sends no write while it loads and leaves it to the sweep. An entry past the 256 entries of its mailbox (a late write of an earlier holder can leave one) is doomed too, with a note, and the start is not refused. A listing that omits keys or is stale (a store that lies) loses those entries from memory until the next load: they are not listed and not counted, and a put of the same bytes is a new entry under a new name; a listed object that is gone is found by the first Open (OUT-703).
- **SPO-Xobjstore-PRE-701** Open refuses, with an error that wraps `relayport.ErrMailboxCorrupt`, a prefix that holds anything a mailbox does not, as the directory store refuses a directory (SPO-Xmailbox-SEC-005, SEC-007): a key below `mailbox/` that is not exactly an entry name (a stray name, a key at the recipient level, upper-case hex, an arrival that is not 20 digits or does not fit an int64, a trailing segment, another separator, a temporary name), an object listed with a size of 0 or over 1 MiB, more than 512 objects in one mailbox, more than 524 288 objects in all. These two counts are the bounds of what the index allocates, and only they refuse the start. The count of mailboxes does not: each mailbox holds at least one object, so the objects bound covers its index, and recipients come and go (a mailbox stays until its entries expire, and an earlier holder's late write can add one), so a count of mailboxes past 1024 is not a sign that the prefix is not a mailbox. The entry bound of a mailbox does not either (OUT-701). A listing that repeats or reorders keys across pages, or whose continuation does not advance, is refused with `s3client.ErrBadListing`. Keys outside the mailbox prefix (the lease, the rate object, another relay's prefix) are not listed. A lease that is not held refuses the load before any request (`ErrAuthorityLost`).
- **SPO-Xobjstore-SEC-701** The key decoder is strict and total: exactly the shape of IF-701, each field checked before it is decoded, and a key it accepts is the key it would write (fuzzed). Every bound of PRE-701 is checked at the entry that passes it, before anything more is read or kept; only the index of what was read and one listing page (at most 4 MiB, the client's bound) are held, and a load of 1025 mailboxes allocates under 32 MiB.
- **SPO-Xobjstore-PRE-702** A put holds its body whole in memory (ADR 0015 decision 2, m1): after the directory store's decision and reservation it waits for one of `relayport.MaxHeldBodies` (64, equal to `mailbox.MaxConnections`, asserted at compile time: one put at a time per connection) slots until its context ends, and otherwise fails as a store failure, having read nothing and keeping no reservation. It reads exactly the declared size, each read asking for at most 32 KiB, with the context checked before every read (a read that blocks is ended by the reader's own deadline, not by the context), and checks the size and the id before any request. A put that its context ends before it sent anything (in the wait for a slot, in the body, in the wait for the recipient's exclusion, or at the check after it) returns an error that wraps `objmailbox.ErrNotSent` and not the context's error, so the relay's watcher does not count it as unanswered (SPO-Xmailbox-OUT-129). An Open holds the body it reads in one of `MaxOpenBodies` (64) other slots until the reader is closed, waiting for one within its request deadline: so at most 128 MiB of bodies are held in all. The directory store streams both.
- **SPO-Xobjstore-OUT-702** A checked put waits for the recipient's exclusion until its context ends, checks the context once more, stamps the arrival (OUT-707) and sends a PUT with `If-None-Match: *` and the body's SHA-256 checksum, which the store verifies, under its own key. Its PUTs and their read-backs share one deadline of `RequestTimeout` and are bounded by the lease end, not by the put's context, as the directory store's link is not: a PUT cut at the context would be an unknown outcome. The true bound: a put answers at most 2 × `RequestTimeout` (20 s at the default) after its context ended, one for the PUTs and read-backs and one for the deletion of a revoked put; everything before the first PUT ends with the context (SPO-Xmailbox-SEC-089). Memory changes only after the store confirmed the write. A refusal that is not a conflict (a body damaged on the way, `BadDigest`; a deny) is a store failure and nothing is stored. An answer that matches `s3client.ErrOutcomeUnknown`, and a conflict (412, 404, 409), are read back with a GET bounded by one byte more than the body (SPO-Xobjstore-PRE-003): the body under the key is the entry (no other put uses the key), and the put is stored. **Other bytes under the key end the writer** (`relayport.ErrAuthorityLost`, with `ErrOutcomeUnknown` too when one of its PUTs may still land): that, and the lease's own end, are the only stale-writer signals of a put. Nothing under the key, or a read-back that cannot tell, sends the **identical** PUT again (the same key and bytes, at most 6 in all, after 20 ms doubling to 320 ms) while the deadline lasts; a later answer, or a later conflict that reads back as the body, is success. A put that stays unconfirmed is a store failure when none of its PUTs may have been applied (conflicts or refusals only), and otherwise is held (OUT-706). A mailbox removal while the PUT is in flight (the put reserved before it) answers the put `ErrMailboxRevoked`; the put deletes its own object, under the exclusion, before it answers, so a put answered revoked has nothing listed and, once the deletion is confirmed, nothing stored; a deletion that is not confirmed makes the object doomed (counted, not listed, swept) and the answer wraps the deletion's error too (`ErrOutcomeUnknown` when it may still be there). A put whose PUT is confirmed after `Close` is stored and answers so. Duplicate and busy answers are the directory store's.
- **SPO-Xobjstore-OUT-703** Open (fetch) reads the object whole with a bound of its recorded size and checks its length and its id (the Blake2b-256 that names it, SPO-Xmailbox-OUT-001) before a byte is served, so a checksum or ETag header the store reports is not relied on. An object that is longer, shorter or other than the entry is refused with `ErrMailboxCorrupt` and stays listed, as the directory store keeps a damaged file. An object the store answers 404 for is `ErrMailboxNotFound`, as the directory store answers for a vanished file (SPO-Xmailbox-OUT-032), and unlike the directory store it is then doomed: no longer listed, so a fetch that resumes does not meet it again. A transfer cut short or a 5xx is a store failure.
- **SPO-Xobjstore-OUT-704** An ack, a retract, a mailbox removal and a sweep delete by name, one DELETE per object. Each deletion takes the recipient's exclusion and gives it up after, so a put of the recipient waits for one deletion and not for a whole removal, and looks the object up again under it (one gone or changed meanwhile is skipped). The wait for the exclusion ends with the caller's context, with an error that wraps `objmailbox.ErrNotSent` and sends nothing; an exclusion that is free is taken whatever the context, so a retract on a cancelled context still runs (SPO-Xmailbox-OUT-031), and a DELETE once sent is not cut by the context: it and the read after a lost answer share one deadline of `RequestTimeout`. Within a mailbox a removal or a sweep stops at the first error, as the directory store stops at its first failed unlink, and when its context ends between two deletions; the entries not reached stay listed and counted. A sweep that fails on one mailbox goes on with the others and returns the errors joined; it stops once the store is closed or its authority is lost. A deletion confirmed by its answer, by a 404, or after an answer that was lost by a read (`GET` with a bound of one byte) that finds no such key, frees the entry and its quota, unless a PUT of its key may still land (the put needed a retry or was held, OUT-706): then the object is doomed until a deletion is confirmed after its window. A read that finds no key settles a lost DELETE because no other object ever takes the key (OUT-707). One whose outcome stays unknown makes the entry doomed and returns an error that wraps `relayport.ErrOutcomeUnknown`. A refusal leaves the entry listed and counted. A deletion of an object someone else removed is a success; a second ack of an id reports false.
- **SPO-Xobjstore-INV-704** Doomed objects (held keys among them) are counted in every quota and listed by nothing, because their bytes may be stored or may still land; every sweep deletes them again first, and a mailbox removal deletes them with its entries; one is freed only by a deletion confirmed after its window, if it has one. So the quota never undercounts what this process may have stored. The consequence is at least once: an entry whose ack could not be confirmed is listed again by the next load if the store still holds it, and its recipient may receive it twice (the replay log of ADR 0005 drops the copy).
- **SPO-Xobjstore-INV-701** No write is unconditional: every PUT the store makes is create-only with the SHA-256 checksum (asserted with the stand-in's recorder over every test, the contract suite included). The listing and the counters agree after any mix of concurrent puts, fetches, acks, retracts and sweeps, every listed entry opens to its bytes, and a restart loads the same.
- **SPO-Xobjstore-INV-702** Once a store call learned that the authority is lost (other bytes under a put's key, a lease that ended), every later call of the store answers `ErrAuthorityLost` and sends nothing, and so does every request a call already running would send next (the loss and `Close` are checked under the store's lock before every request, inside loops and read-backs too). A put that stays unconfirmed (OUT-706) does not lose the authority. `Close` sends nothing more and returns once every request in flight has ended, each within its own bound (`RequestTimeout` and the lease end); the host calls it before it releases the lease (work package 10), and releases the lease only when the relay counted no unanswered write (SPO-Xmailbox-OUT-129), which a held put is. The directory store has no such state.
- **SPO-Xobjstore-INV-703** Every request goes through `relayport.RequestContext`: a lease that has ended, is not held or whose loss was seen sends no request (no PUT while a put read its body, no DELETE for an ack), and a request in flight is cut at the lease end. A crash at any step leaves what the directory store would: an entry is in the next load exactly when its PUT reached the store, and a removal cut short leaves the entries it had not deleted. A PUT the store applies after the client gave up is in the next load, not in the index (ADR 0015 decision 5, "A mailbox entry created"); this process counts it as held until its window ends (OUT-706).
- **SPO-Xobjstore-OUT-705** Requests per operation: a put is one PUT; an answer that matches `ErrOutcomeUnknown`, and a conflict, add one GET to read it back, and the identical PUT is sent again after a read that does not show it, at most 6 PUTs and 6 GETs in all for one put; a revoked put adds its DELETE (and its read). A duplicate, busy, full or too-large answer, a listing and a usage read make none; a fetch is one GET; an ack is one DELETE per copy of the id, a retract one DELETE, a mailbox removal and a sweep one DELETE per entry and per doomed object, held keys included, at every sweep until each is freed (and one GET for each deletion whose answer was lost); a load is one LIST per page of 1000 keys.
- **SPO-Xobjstore-OUT-706** A **held** key is a put that stayed unconfirmed when one of its PUTs may have been applied (a 5xx, a lost answer). The object store may apply such a PUT for as long as its signature is valid (15 minutes) on the object store's own clock, and an object store more than 15 minutes behind the relay refuses every request, so the key's window ends 30 minutes (`objmailbox.LandingWindow`) after its last PUT returned, on the relay's clock (`Clock`). Until a deletion confirmed after that end it is a doomed object: counted in every quota and in the arrival mark, listed nowhere, deleted again by every sweep and mailbox removal (a deletion confirmed earlier may be followed by the late landing). The put is answered with an error that wraps `relayport.ErrOutcomeUnknown` and not `ErrAuthorityLost`, so the session answers `unavailable` and the relay counts it as unanswered (SPO-Xmailbox-OUT-129) and lets the lease lapse at a planned stop; the writer goes on. A storm of 5xx answers on many puts never ends the writer. At most 32 held keys a mailbox and 256 in the store (each reached bound answers a new put `busy`, before it reads a byte; puts that already hold a body may each add one more, so at most 256 + 64); none of them ends the writer. A retry by the sender is a new put under a new key; when the held one lands too, a restart's load lists the earlier as the entry and dooms the later, and a restart during the window lists a landed held key as an ordinary entry: at least once, which the replay log of ADR 0005 absorbs. A put confirmed only after a retry (of the client or of the store) gets the same window: its entry, deleted within it, stays doomed until it ends.
- **SPO-Xobjstore-OUT-707** No key is used twice. Every put draws a 64-bit random nonce for its key, and every PUT it re-sends carries the same key, so a request the store applies late (a DELETE whose answer was lost, a PUT of a held key) can only reach the object it was sent for, in this process and after a restart: another process draws its own nonces. Arrivals are kept apart too: each mailbox has an arrival mark, the newest arrival stamped or loaded, which no deletion, removal or pruning lowers and which is kept at least 30 minutes after the last stamp (and to the end of every held key's window); a new arrival is the clock raised to the load's time and to one second after the mark, so it is strictly increasing in a mailbox (SPO-Xmailbox-OUT-022) and a clock stepped back stamps above the mark, not below it. A load sets the mark from the listed arrivals (one more than the retention ahead of the clock ignored) and stamps nothing below its own time. The clock assumption: the store's clock (`Clock`) does not step back by more than 30 minutes while a mailbox is empty and its mark has been forgotten; if it does, arrivals may repeat, which changes the order of a listing and nothing else, because keys still differ by their nonce. A restart does not rely on the clocks: a pre-restart late request carries the old process's nonce.
- **SPO-Xobjstore-INV-705** The package links nothing the relay binary may not and nothing relay-banned, by the rule of INV-001 over its closure; its direct imports are an exact allow-list (the client, the mailbox and party domains, the relay ports and the standard library).

Not covered by the mailbox package: the request-cost guard and the metrics (work packages 11 and 12; OUT-705 gives the counts), its wiring into `relayhost` (work package 10: pass `time.Now` as the lease clock, call `Close` before `Release`, release only when nothing is unanswered), a batch delete (the client has no `DeleteObjects`), and anything that only a real store can show (ADR 0015, "What only real infrastructure can show").

## The relay binary on the object store (ADR 0015 work package 10)

The assembly and the configuration: the `[store]` table (`domain/relayconf` `ObjectStore`, read by `adapters/relayconfig`), the web identity provider (`adapters/webidentity`, sharing `platform/stsweb` with the unlock backends), the reading of a kubelet-mounted file (`platform/mountfile`, for the token and the Secret-shaped key), the start and stop of `app/relayhost` with `Deps.OpenObjectStore`, and its wiring in `cmd/spo-relay` (`store.go`). The ids are numbered from 301 so that they never meet those of the store tools (work package 9). No real store, STS or cluster was contacted.

- **SPO-Xobjstore-IF-301** `webidentity.New(Config{Region, RoleARN, TokenFile, Endpoint, AllowLoopbackHTTP, RootCAs, SessionName, Duration, Timeout, Now, Jitter})` is an `s3client.Provider`. Each `Retrieve` reads the token file again (kubelet rotates it; one trailing newline dropped, at most 16 KiB, printable ASCII), sends one unsigned `POST` of `AssumeRoleWithWebIdentity` (`platform/stsweb.Request`: the role, the session name `spo-relay`, `DurationSeconds` 900 by default and 900 to 3600, the token last) and returns the answer's key id, secret, session token and expiry. The expiry it gives is moved earlier by a jitter of 0 to the lesser of two minutes and a tenth of the credentials' life (uniform from `crypto/rand`), so the client's refresh, five minutes before the expiry it is given, comes at different times on different relays. The endpoint is the public STS endpoint of the region (`https://sts.<region>.amazonaws.com`, `.amazonaws.com.cn` for a `cn-` region); another only from the configuration's `sts_endpoint`.
- **SPO-Xobjstore-IF-302** The `[store]` table of the relay configuration. Absent, or `kind = "directory"` and no other key: the directory store of `[relay] mailbox_dir` and `registry_dir`, unchanged. `kind = "s3"`: `region` (an AWS region name), `registry_bucket` (versioned with Object Lock) and `working_bucket` (unversioned), both required and distinct; `endpoint` (scheme and host of an allow-listed compatible product, default the public S3 endpoint of the region) and `path_style`; `object_lock_mode` (`compliance`, the default, or `governance` with `test_deployment = true`); `role_arn` and `web_identity_token_file` (required: the only credentials); `sts_endpoint` (a private STS endpoint); `request_timeout_seconds` (1 to 10, default 10); `unsafe_loopback_http_for_tests` (plain http to a loopback IP literal, for the test rig). The values become `relayconf.Config.Store` (`StoreS3`) and `Object` (`relayconf.ObjectStore`); `Config.FileHash` is the Blake2b-256 of the file and `HashTag` its first 8 bytes in hex.
- **SPO-Xobjstore-IF-303** The assembly: `relayhost.StoreObject` and `StoreSpec.Object`; `Deps.OpenObjectStore(ctx, spec, relayKey, clock)` returns a `relayhost.ObjectStore` (the lease, the openers of the mailbox and the registry, `Close`, notes), which `Start` uses instead of `OpenLease`, `OpenMailbox` and `OpenRegistry`; a configuration of kind `s3` with no `OpenObjectStore` is refused. The configured request timeout bounds every renewal and every tombstone refresh of the host (`Deps.RequestTimeout` overrides it for a test). `cmd/spo-relay` gives `OpenObjectStore`: the provider of IF-301, one `s3client.Client` per bucket, `objlease.New` with `objlease.DefaultTimes` and the configured request timeout, `objmailbox.Open` and `objregistry.Open` with the lease, the relay clock (`time.Now`, which carries a monotonic reading) and the configured mode and request timeout.
- **SPO-Xobjstore-OUT-301** `check-config` (and `serve`'s summary) prints the store's kind, the two buckets, the endpoint, the Object Lock mode, that the credentials are a web identity and where they are exchanged, and `configuration hash <16 hex>`; with a key file, also `store prefix relays/<node key>/ in both buckets`. It prints no secret (there is none in the file) and not the token file's path. A start logs `start config=<16 hex> store=s3 registry_bucket=… working_bucket=… prefix=relays/<node key>/` first (`store=directory` for a host). `SameExceptDevices` compares the store kind and every `[store]` value: a change of the store is never a reload.
- **SPO-Xobjstore-OUT-302** The start order for an object store: the provider and the two clients; the start-up self-test of the working bucket (versioning never enabled) and then of the registry bucket (versioning on, Object Lock enabled, the deny of a simple delete in the tombstone namespace; the retention part is not run, ADR 0015 "Changes after the review of the store client"), each within 16 request timeouts; the check of PRE-303; the lease, acquired (a taker of a lapsed lease waits out the drain inside it) and kept by the keeper while the stores load; the mailbox, then the registry, both given the lease; the server; the tunnel. Any failure before the lease (a self-test property, a refused web identity, an uninitialised store) starts nothing and exits 1 with the cause. A planned stop: the tunnel closed, the sessions ended, the rate buckets saved, the registry and the mailbox closed (the mailbox's `Close` waits for its requests in flight), then the lease released unless a request went unanswered or an operation is unconfirmed (SPO-Xmailbox-OUT-129), then the clients' connections dropped. A lost authority (4) and a stuck teardown (3) keep their statuses. SIGTERM during the self-test, the wait for the lease or the load is a planned stop (SPO-Xmailbox-OUT-132); during the load the lease is left to lapse (`start_failed lease=lapses reason=load`).
- **SPO-Xobjstore-OUT-303** Two processes on one identity: the second reads the lease every poll and writes nothing while the first renews it; when the first stops (a release), the second takes the released lease at once and loads with no drain; when a holder is gone without a release (killed, cut off), the next takes the lease only after it saw it unchanged for the duration plus the margin, and loads only after the drain. A holder cut off from the store loses its authority at the end of its term and exits 4 without a release.
- **SPO-Xobjstore-OUT-304** A store outage, by how the store fails (the figures are `relayhost.OutageBounds` of the default term of 20 s, renewed every 5 s from the sending, the loss declared 2.5 s before the end; a test pins them). (a) Every request failing at once: refused without being applied (429, 403), not sent (no credentials), or answered 5xx (the renewal's outcome unknown, its read-back failing too: it is pending and sent again with the same bytes, PRE-101): a put is answered `unavailable` (the object mailbox holds the key, OUT-706), renewals are retried (SPO-Xmailbox-INV-045), and an outage of up to 10 s (term − interval − guard − the least renewal time − the longest retry gap) is ridden out wherever it starts: the relay keeps serving, and once the store answers a put is stored and fetched. From 12.5 s (term − interval − guard) such an outage can end the lease, and from 17.5 s (term − guard) it always does. (b) A store that does not answer at all: the renewal sent into the outage waits for its deadline (the request timeout, 10 s, or the guard) before it fails, and the next try follows the least back-off (250 ms) after it. Such an outage of up to 10.25 s (request timeout + least back-off) is ridden out, a longer one can end the lease when it starts just before a renewal, and one of 15.25 s (interval + request timeout + least back-off) always does. In both, a renewal that is not confirmed never extends the lease, and a loss exits 4 without a release. (c) An STS outage while the store credentials are valid does not end the relay (IF-009). *Amended after the security review of work package 10:* this said an outage shorter than the term was ridden out, which (a) and (b) contradict. *Amended after the review of work package 10 (2026-11-20):* (b) said that a store answering 5xx or not at all ends the relay at the first renewal sent into the outage (5 s or more always did), because the lease was given up when a renewal's read-back failed; a 5xx is now (a), and a hung store has the figures of (b).
- **SPO-Xobjstore-OUT-305** A lease record of another holder written over the relay's (the lease taken from it): its next renewal meets the change (412), it stops serving and exits 4, writes nothing over the other record, and sends no request after the end of its last confirmed renewal (its sending plus the term).
- **SPO-Xobjstore-PRE-301** The rules of `[store]`, applied at load and again by `Config.Check`: a known kind; for `directory` no other key; for `s3` every required key; a region name; bucket names by S3's rule (3 to 63 of `a-z`, `0-9`, `.` and `-`, no `..`, not an IP address), a dotted one only with `path_style`; https endpoints with scheme and host only; `unsafe_loopback_http_for_tests` refused unless `endpoint` is `http://<loopback IP>[:port]`, and plain http to `sts_endpoint` only with it and only to a loopback IP; `governance` only with `test_deployment = true`, and `unsafe_loopback_http_for_tests` only with `test_deployment = true`; `test_deployment` only with one of the two; without `sts_endpoint`, `role_arn`'s partition must be the region's (`cn-` regions `aws-cn`, `us-gov-` regions `aws-us-gov`, a region with `-iso` refused, every other `aws`; from memory of AWS's region names), since the region's STS assumes no role of another partition; with `sts_endpoint` the pair is not checked (a private or non-AWS STS); a request timeout of 1 to 10 s (the lease needs at most half its term, the object mailbox at most 10 s); every unknown key refused (there is no key for a static credential). With `s3`: `[relay] mailbox_dir` and `registry_dir` are refused, the full `[derp_region]` is required (`RegionPinRequired` is true) and `derp_region_id` is refused (ADR 0015 decision 7). `Load` checks no store directory for an object store and reads no token file; the key file's checks are unchanged.
- **SPO-Xobjstore-PRE-302** A configuration whose mailbox can hold more objects than the object mailbox lists at a start is refused at load and by `check-config`: `max_bound_devices × mailbox_entries + 320` (the 256 held keys and one per body slot) must be at most 524 288 (`objmailbox.MaxObjects`), and the message gives the arithmetic and the largest values that fit (2046 bound devices at 256 entries a queue). A test checks the constants against the adapter's. The directory store is not bounded by it.
- **SPO-Xobjstore-PRE-303** A store that holds neither the identity's lease record nor its working-bucket marker was never initialised: the start is refused before the lease with a message that names `spo-relay init-store` and says it is for a new relay only, and nothing of the identity is written. The binary never initialises an identity: it never passes `objregistry.InitIdentity` and never calls `objlease.Init`. A lease record alone missing is lapsed (IF-103); a marker alone missing is the registry's refusal (PRE-801).
- **SPO-Xobjstore-SEC-301** The STS exchange: TLS 1.2 at least, the system roots (or the caller's), no proxy, no redirect followed (a 3xx is an error), every exchange bounded by its context and by 10 s, the answer's header block at most 32 KiB and its body at most 64 KiB (a declared length over it is refused before a byte is read), a status other than 200 an error by class (`ErrRefused` for a 4xx, `ErrUnavailable` for a 5xx, a 429 or no answer, `ErrBadAnswer` otherwise), the answer read by `stsweb.Parse` (the secret and the token each one element of plain printable text, found as spans of the answer's bytes, the structure checked by the strict decoder on a copy with both blanked; a key id of `ASIA` and 12 to 124 upper-case letters and digits; an expiry more than a minute away), and credentials living more than 12 hours refused. No error carries the token, the secret, the session token or what STS sent. The unlock backends' KMS client reads its STS answers with the same `stsweb.Parse` and keeps its own guarded copies (SPO-Xunlock-IF-011 unchanged).
- **SPO-Xobjstore-SEC-302** A kubelet-mounted file is read by `platform/mountfile` without refusing kubelet's real layout (the modes are from memory, unverified on a cluster): the directory of the path is first resolved component by component, a link above it followed (`/var/run -> /run` on Debian and Alpine images, under which IRSA mounts its token), every directory an entry is looked up in on the way (each ancestor, and each a link leads through) passing the directory rule below and every link on the way owned by root or the relay's user, at most 40 links; the rest is checked against the resolved directory; the directory owned by root or the relay's user, and writable by its group or others only when it is root's with the sticky bit (a projected or Secret volume is a 1777 tmpfs); the final component a regular file opened with `O_NOFOLLOW` and `O_NONBLOCK`, or a link owned by root or the relay's user that resolves to the same name in a `..<date>` directory directly inside that directory (kubelet's `<name> -> ..data/<name>`, `..data -> ..<date>`), which is root's or the relay's user's and not writable by its group or others; any other link refused; the file root's or the relay's user's, not writable by its group or others, its size checked by `fstat` before it is read (at most the bound, or exactly the size of a key). A token may be readable by others (kubelet's default 0644). A key of root (the Secret volume of ADR 0015 decision 6, source 1) is accepted only when it was reached through kubelet's link (a plain root-owned file, on a host or from a `subPath` mount, is refused with the remedy: the relay user's file, mode 0400), and may carry only the read bits of its owner and group (0400, 0440), the group read bit only when the file's group is the process's effective group (a supplementary group, such as `fsGroup` alone, does not count; *amended after the security review of work package 10*, which found any supplementary group accepted); a token of root may be a plain file. A key of the relay's user keeps SPO-Xmailbox-SEC-077 (no group or other bit, a link followed). A rotation between the resolution and the open is retried twice. Errors name the path and the rule, never the content.
- **SPO-Xobjstore-SEC-303** Over the whole run of the binary (the self-tests, the loads, serving, a revoke, the stops, a take-over), the stand-in's recorder shows no unconditional put and no simple delete of a tombstone, of a marker or of the lease (the self-test's own probe of the deny, `registry/tombstones/selftest-<16 hex>`, is not a tombstone's name and is excepted), no delete by version id of the lease, and none of a tombstone or a marker whose lock (the latest retain-until its puts asked for) has not ended by the test's clock; and a relay whose lease was taken sends no request after its lease's end, counted strictly: a request must arrive before the arrival of the lease request before the last confirmed put plus the term, which is at most that put's sending plus the term.
- **SPO-Xobjstore-INV-301** `adapters/webidentity`, `platform/stsweb` and `platform/mountfile` link nothing the relay binary may not and nothing relay-banned, by the rule of INV-001 (the TLS stack excepted for the primitives); the two platform packages reach no network and no TLS; the three direct import lists are exact allow-lists. The relay binary reaches `crypto/tls` through the store client and the provider; the relay side's primitive rule lets the TLS stack's own primitives through and nothing else (SPO-Xmailbox-SEC-009, part 2, amended).

Not covered by work package 10: `spo-relay init-store`, `migrate-store` and `store` (work package 9), health and metrics (11), the request-cost guard (12), the manifests and their checks (13), the KMS-wrapped key (14); `check-config` does not run the self-test (it needs the role's credentials and writes test objects; ADR 0015 work package 10 had it run there); a private CA for `endpoint` or `sts_endpoint` (the system roots only); anything a real store, a real STS or a real cluster must show (ADR 0015, "What only real infrastructure can show"), among them kubelet's exact modes for a Secret and a projected token with and without `fsGroup`.

## The store tools (ADR 0015 work package 9)

`spo/internal/adapters/relaystore` (an adapter: it works on the object adapters' layout, which no package under `internal/app` may import): `init-store`, `store verify`, `store inspect`, `store repair` and `migrate-store` over the two buckets of one relay identity, each a function with explicit dependencies (`relaystore.Deps`: the two clients, the node key, the Object Lock mode, the clock, the lease's times and wait, the request timeout, the registry configuration, a random source) and a typed report; and `spo/internal/adapters/relaydir`, which reads a stopped directory relay for the migration. The ids are numbered from 901. No real store was contacted.

- **SPO-Xobjstore-IF-901** `InitStore(ctx, Deps) (InitReport, error)` initialises a new identity: it reads the markers, the state and the lease (`StoreState`); runs the self-test of both buckets with the retention part (`s3client.SelfTest` with `Retention`, this being where it runs) and a probe for a default retention (an object written without a retention in `selftest/` whose read shows a lock); writes the released lease record (`objlease.Init`) when the identity holds no state and no lease object; takes the lease (`objlease.Acquire`) and opens the registry with `objregistry.InitIdentity`, which writes the registry marker (locked for a year), the working marker and full rate buckets; releases the lease. It is never run by `serve` (PRE-303).
- **SPO-Xobjstore-OUT-901** What `init-store` leaves, and nothing else: in the registry bucket `marker` (one version, locked) and `selftest/<16 hex>-r` (the retention self-test's object, locked for a day; *amended after the review of work package 9:* the relay's sweep deletes it once the lock has ended, OUT-809, and `store repair --action selftest` does too); in the working bucket `marker`, `lease` (a released record; after the tool's own take and release its generation is 2) and `registry/rates`. The report lists every object written and what the prefix holds. A second run on an initialised identity writes nothing but the self-test's objects (`AlreadyInitialised`); a run stopped at any step (after the lease record, after the markers, before the release) is completed by the next. An initialised store whose lease object is absent is not given one (it is lapsed, and may be in use).
- **SPO-Xobjstore-PRE-901** `init-store` refuses, before it writes a marker, the lease or the rate object: a marker of another identity in either bucket, an object at the working marker's name that is not a marker, an unreadable lease object or one of another node key (the remedy is `store repair --action lease`), a registry bucket with no marker of the identity while the store holds its state or its working marker, a working bucket with no marker that holds state while the registry marker is there (`ErrForeign`, `ErrEmptied`, `ErrLeaseUnreadable`), and a bucket that fails the self-test (`ErrSelfTest`).
- **SPO-Xobjstore-IF-902** `Verify(ctx, Deps, VerifyOptions{Probe, Operator, MaxVersions, MaxObjects}) (VerifyReport, error)` checks one identity and does not take the lease. Without `Probe` it only reads. The report has a verdict per check (ok, warning, failure, not verifiable), the store state, the version-aware tombstone view (per name: every version or delete marker, newest first, its not-before, whether it is unreadable or gone, its lock mode and end; the enforced maximum), the bindings (each with what a load does with it), the mailbox (objects, bytes, per recipient the objects, entries, senders, bytes, later duplicates and objects past the 256 entries), and the reference block of the bucket policy statements, the lifecycle rule and the bucket settings ADR 0015 decision 3 requires (`PolicyStatements`). `Failed` is true when a check failed; `store verify` then exits 1.
- **SPO-Xobjstore-OUT-902** The checks and when each fails. Failure: the registry bucket not versioned or without Object Lock; the working bucket's versioning ever enabled; a marker missing while the identity holds state, one of another identity, an object at the working marker's name that is not one; the identity's newest marker version unlocked or locked in governance mode in a compliance deployment; the lease object unreadable or of another node key; a tombstone object version without a lock, or locked in governance mode in a compliance deployment; a tombstone listing whose latest entry is not what the store serves, or past `relayregistry.MaxTombstoneVersions`; a binding name that is not a device's, more than 1024 bindings; a mailbox key that is not an entry key or a size outside 1 B to 1 MiB, a mailbox of more than 512 objects or more than 524 288 in all (each of these refuses a relay's start); the rate object unreadable for a reason other than its content. Warning (the relay starts and enforces): delete markers over tombstones or the marker, an unreadable tombstone version (enforced at the strictest reading), an object under `registry/tombstones/` that is not a tombstone, a current version lower than an older one, a lock shorter than its tombstone's life or longer than a verified revoke needs, a binding below a tombstone or failing verification, mailbox objects a load dooms, a missing or unreadable rate object, an absent lease object, the marker's lock ending within 30 days. *Amended after the review of work package 9:* a lock shorter than its tombstone's life, a migration record, and a delete marker or foreign version newer than the marker are failures (OUT-908, OUT-909, OUT-911).
- **SPO-Xobjstore-OUT-903** What the relay's role can and cannot show. With `Probe`: the self-tests of both buckets with the retention part (one object stays locked for a day); the default-retention probe; the deny of a simple delete in the tombstone namespace (the self-test's probe); a simple delete of `selftest/<16 hex>/marker` in the registry bucket, a name `relays/*/marker` matches (in a policy `*` spans `/`), refused for the role (the delete marker it makes when not refused is removed by its version id); a simple delete of `selftest/<16 hex>/lease` in the working bucket, where the role may delete, refused only by a deny matching `relays/*/lease` (an applied one leaves nothing). Not verifiable from the role, and so reported, with the statements to compare: the governance-bypass deny (the client sends no bypass header), the 182-day and 366-day retention denies (a probe would leave an object locked for half a year if the deny were missing), the legal-hold deny (the client cannot set one), the TLS and conditional-put denies (the client sends neither kind of request), that the simple-delete denies hold for every principal and not only for the role, and the lifecycle rule. `Operator` asks for the reads that need the operator's own credentials; the client has no `GetBucketPolicy`, `GetBucketLifecycleConfiguration` or `GetBucketEncryption`, and its `GetObjectLockConfiguration` reads `ObjectLockEnabled` only, not the default retention rule, so the check is not verifiable and names the missing calls (they are not added here).
- **SPO-Xobjstore-IF-903** `Inspect(ctx, Deps, InspectOptions{Bucket, Path, Versions, Locks, Limit, After}) (InspectPage, error)` lists one page (1 to 1000 entries, 100 by default) of one prefix below the identity's: a listing, or in the registry bucket a version listing (`Locks` adds one head per version for its lock); names decoded (a tombstone's scope, wallet key hash and device; a binding's device; a mailbox key's recipient, arrival, id, sender and nonce; the marker, the lease, the rate object, the self-test's objects), sizes, version ids, delete markers, lock ends; `Next` is where the next page starts. It reads no body and writes nothing. A path that is absolute or outside the key alphabet, a page over 1000 and a version listing of the working bucket are refused.
- **SPO-Xobjstore-IF-904** `Repair(ctx, Deps, RepairOptions{Actions, DryRun}) (RepairReport, error)` makes only the named actions, each off unless named: `delete-markers` (each delete marker under `registry/tombstones/` and over the marker, by its version id), `lease` (OUT-905), `mailbox-duplicates` and `mailbox-over-bound` (the objects a load dooms), `mailbox-unparsable` (keys that are not entry keys and sizes outside 1 B to 1 MiB, which refuse a load), `selftest` (the self-test's objects: in the registry bucket each version whose lock has ended, by its version id, and delete markers; in the working bucket every object under `selftest/`). It lists every step first; `DryRun` stops there, writes nothing and takes no lease. An unknown action, or none, is refused. *Amended after the review of work package 9:* `migration-record` (OUT-909); only the confirmed plan is made, against a fresh scan under the lease, at most 10 000 steps a run (OUT-910).
- **SPO-Xobjstore-OUT-904** Repair takes the lease through `objlease` for every action but `lease` (PRE-902), checks each step's precondition again before it is made (a delete marker by a head of its version; a self-test version's lock by a head), makes it, and lists it as done, skipped (with why) or failed; versions it saw and left (locked self-test objects) are listed as untouched. A second run after a repair has nothing to do. It never touches a binding, a tombstone object version, the marker's object versions, or an entry a load serves.
- **SPO-Xobjstore-OUT-905** `repair --action lease` overwrites a lease object that is unreadable or names another node key with a released record of this identity (`objlease.InitRecord`), with `If-Match` on its ETag, only after it saw the object unchanged (the same ETag and bytes) for the take-after time and the drain on the lease clock, as a waiter sees a lapsed lease before it takes it; a change while it watches starts the watch again, and a conflict writes nothing more. It never deletes the object. A relay then takes the released record at once.
- **SPO-Xobjstore-SEC-901** The store tools never send an unconditional put, a simple delete in the registry bucket other than the policy probes under `selftest/` (OUT-903), a delete of the lease object, a delete by version id of a version whose lock has not ended (by a margin of the skew), a write of a tombstone lower than the one enforced, or a delete of any tombstone, binding or marker version; and never write, rename or delete in a directory relay (the lock files excepted, which a store creates too). The stand-in's recorder checks it over every test.
- **SPO-Xobjstore-PRE-902** The lease is taken with `objlease.Acquire` within `Deps.LeaseWait` (by default the take-after time, the drain, two polls and a request: 75 s): a released lease at once; a held one only once seen unchanged for the take-after time, then drained; an absent one as lapsed. A relay that renews it is never displaced: the wait ends and the operation is refused with `ErrLeaseHeld`, having written nothing. Repair and a migration into an initialised identity hold it for their whole run, renewing it every quarter of the term between requests, every request bounded by its end (`relayport.RequestContext`), and release it at the end.
- **SPO-Xobjstore-IF-905** `Migrate(ctx, Deps, DirSource, MigrateOptions{NoMailbox}) (MigrateReport, error)` copies a stopped directory relay. `relaydir.Open(mailboxDir, registryDir)` is the source: it takes both directory stores' exclusive locks without waiting (`relaydir.ErrLocked` while a relay runs), refuses a directory that is not the user's or is writable by its group or others, and reads, read only, what the stores would load: every tombstone file (exactly 15 bytes, a not-before in range), every binding file (at most the record bound), every mailbox entry in the directory store's order (arrival, id, sender) with its size (1 B to 1 MiB), the earlier of two entries with one sender and id; temporary files are skipped and noted, quarantined bindings not read, any other name, a link or a wrong size refused. `NoMailbox` leaves the queues in the directory.
- **SPO-Xobjstore-OUT-906** The migration's order (ADR 0015 work package 9): every tombstone checked for a lock objregistry would write (one too long or a not-before out of range stops the run before any write); into a new identity a migration record (`relays/<key>/migration` in the working bucket, `SPORMG1\n` and the node key) written first; every tombstone written, unless the store enforces it at an equal or higher not-before, as a locked version (until its not-before plus the maximum lifetime plus the skew and a second, never under an hour from now) with a checksum, `If-Match` on the current version or `If-None-Match: *`; a version-aware read of `registry/tombstones/` that must show every tombstone of the directory enforced, readable and locked; the bindings, each verified and admitted against that view as a load does (one below a tombstone, expired, over the lifetime or failing verification is skipped and reported; one the store holds with other bytes is left), copied byte for byte create-only; the mailbox entries, keys `<recipient>/<arrival>-<id>-<sender>-<nonce>` with the directory's arrival and a fresh random nonce, each body read and checked against its size and id, an entry the store holds (same recipient, sender and id) not written again; a rate object with empty buckets when there is none; then the registry marker (locked for a year, in the configured mode), the working marker, the released lease record, and the deletion of the migration record. The markers are written by the tool with objregistry's bytes (`objregistry.InitIdentity` refuses a store that holds tombstones), and `objregistry.Open` and `objmailbox.Open` load the result: every binding served or refused, every tombstone enforced, every queue in the same order with the same bytes, as the directory stores do. *Amended after the review of work package 9:* "enforces it" is now "holds a version locked for its life" and the value written is the higher one (OUT-908); the self-tests run first into a new identity (PRE-904); the record's delete is sent again and its failure is an error (OUT-909); the markers' bytes and lock are objregistry's exported own (IF-806).
- **SPO-Xobjstore-OUT-907** A migration stopped at any step leaves a store the relay refuses (`ErrStoreNew` or `ErrStoreEmptied`) until both markers are written; after them it holds the whole state. A second run completes it without a duplicate: tombstones already enforced, bindings and entries already there are not written again. A state without markers is the tool's own only when its migration record is there; without it the store looks emptied and the run is refused. *Amended after the review of work package 9:* the record alone is not enough (PRE-904).
- **SPO-Xobjstore-PRE-903** The migration refuses a target with a marker or lease of another identity, an unreadable lease, or the state of an emptied store (PRE-901, without its migration record), and a tombstone whose lock would be refused. Anything that should be carried and is not (a tombstone write refused or of unknown outcome that the read-back does not settle, a listing that does not show a tombstone enforced, a binding or an entry whose write is not confirmed) is listed in `NotCarried`, stops the run before the rate object and the markers, and returns `ErrNotCarried`; `migrate-store` exits 1. A lost answer and a 5xx after a commit are read back and are no loss.
- **SPO-Xobjstore-IF-906** The commands (`relaystore.Main`, dispatched by `spo-relay` before its other commands): `init-store --config FILE`; `store verify --config FILE [--probe] [--operator]`; `store inspect --config FILE --bucket registry|working [--path P] [--versions [--locks]] [--limit N] [--after T]`; `store repair --config FILE --action A ... [--dry-run] [--yes]`; `migrate-store --config FILE --from-mailbox DIR --from-registry DIR [--no-mailbox] [--yes]`. Exit statuses as spo-relay's (SPO-Xmailbox-OUT-101): 0 success, 1 a failure (a refusal, a failed check, a failed repair step, a migration that did not carry everything, a declined confirmation), 2 a usage error. The configuration's `[store]` table and key give the clients and the node key.
- **SPO-Xobjstore-PR-901** `store repair` (after printing its plan) and `migrate-store` ask a yes-or-no question on the terminal before they write, never on standard input; without a terminal they refuse unless `--yes` is given; a declined question writes nothing. A dry run asks nothing.
- **SPO-Xobjstore-SEC-902** Every listing the tools read is bounded before anything is kept for an entry past the bound: tombstone versions and delete markers (`relayregistry.MaxTombstoneVersions` each), bindings (1024), mailbox objects (`objmailbox.MaxObjects`), the marker's entries (4096), self-test versions (4096); a bound passed is a failed check, not a crash. A mailbox scan keeps an index, not the listing (measured: about 16 MiB of allocation for 3002 objects, most of it the client's page buffers; the test bounds it at 24 MiB). A report names at most 32 keys of a class. The renderings print names, counts, sizes, version ids, dates and fingerprints, never a credential, a binding statement's bytes or an envelope body.

Changed after the security review of work package 9 (each amends the requirement it names; ADR 0015, "Changes after the review of work package 9"):

- **SPO-Xobjstore-OUT-908** (amends OUT-906, OUT-902, SEC-901) A tombstone version counts as carried only when it is readable and locked in the deployment's mode or compliance until its own not-before plus the maximum lifetime, the skew and a second (`objregistry.LocksFor`): a short lock, a governance lock in a compliance deployment, an unreadable version (enforced only to the end of its lock) and an unlocked one do not, and the migration writes its own version, before the markers, and the read-back requires one that counts. The value it writes is the higher of the directory's and the highest the store enforces, with the lock for that value, so a lower value is never written on top of a higher weak one; only when that value's lock would be refused as too long does it write the directory's own (lower on top; the higher stays enforced while it exists). `store verify` fails (it warned) a lock shorter than its tombstone's life while that life has not ended; a lock longer than a revoke needs stays a warning. SEC-901's "a write of a tombstone lower than the one enforced" holds but for that refused-lock case.
- **SPO-Xobjstore-PRE-904** (amends OUT-907, PRE-903) The migration record is never evidence on its own (its bytes are public; anyone who may write the working bucket can plant one). It lifts `ErrEmptied` only in the two shapes an interrupted migration into a new identity leaves: no marker in either bucket and no lease object; or the identity's registry marker, locked in the deployment's mode until after now, with no working marker and no lease object. A working marker without the registry marker, or a lease object without both markers, is refused, record or not. A store with the lease record and not both markers (and no record) is what an interrupted `init-store` leaves: the migration refuses it (`ErrInitIncomplete`) and names `init-store`. The record's absence lifts nothing. Into a new identity, before its first write, the migration runs the self-test of both buckets with the retention part and the default-retention probe; a failure writes nothing of the identity (`ErrSelfTest`).
- **SPO-Xobjstore-OUT-909** (amends OUT-906, PRE-901, OUT-902, IF-904) The migration sends the record's delete up to three times; if it still fails the run returns `ErrMigrationRecord` (exit 1) with the message that the migration is complete and the repair to run. `init-store` refuses a store that holds a migration record (`ErrMigrationRecord`: with both markers and the lease record, "store repair --action migration-record"; otherwise "run migrate-store again"); `store verify` fails one, with the same remedies. `store repair --action migration-record` deletes it only when both markers and the lease record are there, and lists it as left otherwise.
- **SPO-Xobjstore-OUT-910** (amends IF-904, OUT-904, PR-901) Repair makes only the confirmed plan: `RepairOptions.Confirmed` (the command line passes the plan it printed and asked about; nil confirms the plan Repair lists first). Under the lease it plans again from a fresh scan and makes a confirmed step only when the fresh plan holds the same step (action, bucket, key, version id); one that left its class (a duplicate whose earlier copy went, so a load serves it) is skipped with the reason and nothing is sent; a step only the fresh plan holds is not made and is reported. A version step is still checked by a head just before its delete. One run plans at most `MaxRepairSteps` (10 000) steps and says to run it again; `selftest` handles at most 1000 entries of `selftest/` a run in each bucket and says so instead of failing on the listing's bound.
- **SPO-Xobjstore-SEC-903** (amends SEC-902) No tool holds a listing: the tombstone scan holds one page and one name's sums, keeping the first 64 names (each with its first 32 entries) for the report, counts for the rest, and the sums only of the names it is asked for (the directory's tombstones and the names of the bindings, read first); repair keeps at most `MaxRepairSteps` steps and streams the delete-marker listing; the mailbox scan keeps counts, the first 32 keys of each class and the first 1024 mailboxes. A verify of 6002 tombstone names retains about 90 KiB in its report (measured; the test bounds it at 512 KiB; it was 2.2 MiB when every name was kept). No store content makes a tool panic: every lock is read through a nil check, and a verdict out of range prints as a number.
- **SPO-Xobjstore-OUT-911** (amends OUT-901, OUT-902) `init-store` over an initialised store skips the retention part of the self-test (it leaves an object locked for a day) and says so; what it reports as left names at most 32 self-test objects, counts up to 1000 and says when that bound was hit. `store verify` fails a delete marker, or an object version that is not the identity's marker, newer than the identity's newest marker version (the relay's load still finds its marker by versions); older ones stay a warning.

Not covered by the store tools: the reads with the operator's credentials (OUT-903: the client lacks the calls); a probe of the retention-day and legal-hold denies; whether the policy statements hold on any real store (none was checked against AWS; in particular whether `s3:object-lock-remaining-retention-days` governs a `PutObject` with lock headers); the shared operator tombstone set (stage 3); an allow-list check of migrated bindings (configuration: the relay's load drops them); and anything only a real store can show. *Changed after the review of work package 9:* the relay's sweep deletes the retention self-test's object (OUT-809).

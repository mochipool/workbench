# 04d_genNodeOpCert: Issue the operational certificate

Signs the newest KES verification key (generated by [04c](./04c_genKESKeys.md)) with the pool's cold key and the cold issue counter, producing `<pool>.node-<NNN>.opcert`. It is the second half of the KES rotation state machine: it requires the two KES counters to be equal (a key waits to be used) and moves `kes.counter-next` to N+1 (the next key may now be generated). Every run increments the cold issue counter, so the script is not repeatable. In online and light mode it then checks the issued counter against the chain and, on a mismatch, offers to re-issue with the right counter. In offline mode it cannot check and prints a reminder to run [04e](./04e_checkNodeOpCert.md) on an online machine.

```
          04c (generate)                     04d (issue opcert)
current < next  ───────────▶  current == next  ───────────▶  current < next+1
```

## Interface

- **SPO-04d-IF-001** Takes the pool name as the first, required argument. Without it (or with an empty one) prints a usage line on stdout and exits 2. (src: L19)
- **SPO-04d-IF-002** Takes an optional second argument, the opcert counter value to use, only when exactly two arguments are given. It must be a string of decimal digits; an empty or non-numeric value exits 2. With three or more arguments the extra values are ignored without error. (src: L20)

## Inputs

- **SPO-04d-IN-001** Reads `<pool>.node.vkey` and one of `<pool>.node.skey` / `<pool>.node.hwsfile`. (src: L30-L31, L142, L157)
- **SPO-04d-IN-002** Reads `<pool>.kes.counter` and `<pool>.kes.counter-next`, each as a base-10 integer (leading zeros allowed), compared as three-digit zero-padded numbers. (src: L36-L37)
- **SPO-04d-IN-003** Reads `<pool>.kes-<NNN>.vkey` where `<NNN>` is the (equal) KES counter. (src: L44)
- **SPO-04d-IN-004** Reads the Shelley genesis file (`genesisfile`): `slotLength`, `slotsPerKESPeriod`, `maxKESEvolutions`. (src: L122-L123)
- **SPO-04d-IN-005** Reads `<pool>.node.counter`, the cold issue counter (see SPO-Pfiles-OUT-011). (src: L83, L152)

## Behaviour

1. **Pre-flight.**
   - **SPO-04d-PRE-001** In online and light mode, exits 2 when the node or Koios is not synced (`get_currentSync`, SPO-Cchain-OUT-004). Offline mode skips this. (src: L23-L26)
   - **SPO-04d-PRE-002** Exits 2 when neither `<pool>.node.skey` nor `<pool>.node.hwsfile` exists, and exits 2 when `<pool>.node.vkey` is missing. (src: L30-L31)
   - **SPO-04d-PRE-003** Exits 2 when `<pool>.kes.counter` or `<pool>.kes.counter-next` is missing. (src: L35, L39-L41)
   - **SPO-04d-PRE-004** Exits 2 when the two KES counters differ. With the state machine of [04c](./04c_genKESKeys.md): a key generated by 04c exists (`current == next`) and has not yet been consumed. (src: L38)
   - **SPO-04d-PRE-005** Exits 2 when `<pool>.kes-<NNN>.vkey` does not exist for the equal counter. (src: L44-L45)
2. **Set or repair the cold counter.** (runs at the top of every loop pass, see step 5)
   - **SPO-04d-PR-001** When a counter value was supplied (second argument, or the corrected value of SPO-04d-INV-007), asks "use the given OpCertCounter '<n>' as the next one?" with default Yes. On Yes the cold counter is rewritten (SPO-04d-EXT-001). On No in the first pass (given on the command line) the existing counter file is used unchanged and the script continues; on No in a correction pass (SPO-04d-INV-007) it exits 2. (src: L58-L60, L75)
   - **SPO-04d-EXT-001** Rewrites the counter with `cardano-cli <era> node new-counter --cold-verification-key-file <pool>.node.vkey --counter-value <n> --operational-certificate-issue-counter-file <pool>.node.counter` (after unlocking it), then sets the file's `description` to `Next certificate issue number: <n>` and locks it again. A cardano-cli or `jq` failure ends the script with that code. (src: L62-L71)
   - **SPO-04d-OUT-005** After SPO-04d-EXT-001 the counter file holds the supplied value `<n>` as the next issue number, so the opcert issued next carries counter `<n>`. (src: L62-L73)
   - **SPO-04d-PR-002** When `<pool>.node.counter` does not exist, asks "Cannot find ..., do you wanna create a new one?" with default No. On Yes it creates the counter with value 0 the same way as SPO-04d-EXT-001, tells the operator to run the script again, and exits **1** without issuing anything. On No it exits 2. (src: L83-L103)
3. **Compute the KES period and expiry.**
   - **SPO-04d-EXT-002** The current slot comes from `get_currentTip` in the active work mode (SPO-Cchain-OUT-003; offline mode derives it from the local clock, SPO-Cchain-INV-008). A failure ends the script (SPO-Cchain-INV-001). (src: L119)
   - **SPO-04d-PRE-006** Exits 1 when the Shelley genesis file is missing. (src: L122)
   - **SPO-04d-INV-001** `currentKESperiod = floor(currentSlot / (slotsPerKESPeriod * slotLength))`, and negative results become 0. The multiplication by `slotLength` is upstream behaviour: it is the identity on every network with one-second slots, and wrong for a genesis with another slot length. (src: L123-L126)
   - **SPO-04d-INV-002** `expireKESperiod = currentKESperiod + maxKESEvolutions`, and `expireKESdate` is the local-time date of `now + slotLength * maxKESEvolutions * slotsPerKESPeriod` seconds, taken from the wall clock rather than from the start of the current period (so it overestimates by the time elapsed in the current period). (src: L130-L133)
   - **SPO-04d-OUT-004** Writes `<pool>.kes-expire.json` (unlock, write, lock) with the four members `latestKESfileindex` (the three-digit KES number), `currentKESperiod`, `expireKESperiod`, `expireKESdate`, all as strings. It is written before the opcert is issued and again on every loop pass, so it survives a later failure or abort. (src: L135-L137)
4. **Issue the certificate.**
   - **SPO-04d-INV-003** The opcert file is `<pool>.node-<NNN>.opcert` with `<NNN>` the KES counter. (src: L139)
   - **SPO-04d-INV-004** When both `<pool>.node.skey` and `<pool>.node.hwsfile` exist, the software key is used and the hardware file is ignored. This is the opposite of the hardware-first rule of SPO-Pfiles-INV-002. (src: L142, L157)
   - **SPO-04d-EXT-003** Software key: reads the cold signing key with `read_skeyFILE` (decrypting an `enc` key per SPO-Ckey-PR-001, or with `ENV_DECRYPT_PASSWORD`, SPO-Ckey-IN-002); a failure exits 1. The key is read once per run and held in memory. It runs `cardano-cli <era> node issue-op-cert --hot-kes-verification-key-file <kes vkey> --cold-signing-key-file <process substitution of the in-memory key> --operational-certificate-issue-counter-file <pool>.node.counter --kes-period <currentKESperiod> --out-file <opcert>` after unlocking the opcert and counter files, then locks both. A cardano-cli failure ends the script with its code. (src: L145-L147, L150-L155)
   - **SPO-04d-PR-003** Hardware key: asks "Generating the new opcert from a local Hardware-Wallet keyfile ..., continue?" with default Yes; No exits 2. (src: L157-L159)
   - **SPO-04d-EXT-004** Hardware key: opens a session restricted to Ledger or Keystone (`start_HwWallet "Ledger|Keystone"`, SPO-Chw-IF-001) and runs `cardano-hw-cli node issue-op-cert --kes-verification-key-file <kes vkey> --kes-period <currentKESperiod> --operational-certificate-issue-counter-file <pool>.node.counter --hw-signing-file <pool>.node.hwsfile --out-file <opcert>`, stderr merged into the captured text. Output containing `ERROR` or `DISCONNECT` (case-insensitive) exits 1. The opcert and counter files are unlocked before and locked after. (src: L161-L168)
   - **SPO-04d-OUT-002** The cold issue counter is advanced by the issuing tool (cardano-cli or cardano-hw-cli), not by the script: after a successful issue the file holds `<counter used> + 1`. This happens on **every** run that reaches this step, so the script is not repeatable: running it twice consumes two counter values, even when the first opcert is discarded. (src: L150-L155, L162-L167)
   - **SPO-04d-INV-005** The plaintext cold signing key is never written to a file; it is passed through a process substitution and dropped (`unset`) when the loop ends. (src: L145, L152, L280)
5. **Verify against the chain and correct** (online and light mode only; one pass of the loop; the loop ends on success).
   - **SPO-04d-INV-006** The check passes when the counter embedded in the opcert (`onDisk`) equals `onChain + 1`, where `onChain` is the last counter the chain has seen for the pool, or -1 when the chain has none. On a pass the loop ends. (src: L240, L244-L250)
   - **SPO-04d-INV-007** On a mismatch the script deletes the issued opcert (unlocking it first), sets the supplied value to `onChain + 1`, switches the prompt to "use the correct OpCertCounter", and runs the loop again from step 2: the counter is rewritten to the correct value and a new opcert is issued. The cold counter has by then advanced at least twice (SPO-04d-OUT-002). (src: L259-L265)
   - **SPO-04d-PRE-007** Exits 2 when, in a correction pass, the operator answers No to the corrected counter (SPO-04d-PR-001). The wrong opcert is already deleted, `kes.counter-next` is unchanged, and the cold counter file is left as last written. (src: L75, L260-L261)
6. **Advance the KES state machine.**
   - **SPO-04d-OUT-003** After the loop ends, sets `<pool>.kes.counter-next` to the KES number N used for the opcert plus one (three-digit zero-padded; unlock, write, lock). `<pool>.kes.counter` is unchanged, so afterwards `current < next` and [04c](./04c_genKESKeys.md) may generate key N+1. (src: L299-L302)
   - **SPO-04d-INV-008** `kes.counter-next` is advanced only on this path, after a passing check or in offline mode. Every earlier refusal, abort, failure or interrupt leaves it at N, so the same KES key stays "unconsumed". (src: L299-L302)
7. **Report.** Prints the opcert file, the updated counter file, the expiry JSON and the new `kes.counter-next` for the operator; in offline mode also the command for [04e](./04e_checkNodeOpCert.md) `next`. Display only. (src: L285-L312)

## Work modes

- **SPO-04d-MODE-001** Online (full node): before the query the sync check is repeated (exit 2 when not synced, L185). The script runs `cardano-cli <era> query kes-period-info --op-cert-file <opcert> --out-file <tempDir>/opcert.query`; a non-zero exit prints cardano-cli's text and exits 2. `onChain` is `qKesNodeStateOperationalCertificateNumber` (null or absent means -1) and `onDisk` is `qKesOnDiskOperationalCertificateNumber`. The query file is deleted. (src: L180-L195)
- **SPO-04d-MODE-002** Light: sends `POST <koiosAPI>/pool_info` with body `{"_pool_bech32_ids":["<poolID>"]}`, headers `authorization` (`koiosAuthorizationHeader`), `Accept` and `Content-Type` JSON, `-L`, 30-second timeout, **one attempt, no retry and no HTTP-status check**. `<poolID>` is the bech32 pool id of SPO-04d-EXT-005. (src: L202-L206)
- **SPO-04d-MODE-003** Light: a response that `jq` cannot parse exits 2. A response that is a JSON array of exactly one element yields `onChain = .[0].op_cert_counter // -1`. Any other parseable response (an empty array, an error object, **and an empty body from a failed request**) is treated as "pool has made no block yet" and sets `onChain = -1`. (src: L208-L224)
- **SPO-04d-MODE-004** Light: `onDisk` is decoded from the opcert file's `cborHex`: the unsigned integer starting at hex offset 72 (after the array headers and the 32-byte KES key), via `int_from_cbor` (SPO-Cconv-IF-001). A read or decode failure exits 2. (src: L227-L230)
- **SPO-04d-MODE-005** Offline: no chain check, no sync check and no loop; the current slot comes from the local clock (SPO-04d-EXT-002). The opcert is issued with the counter in the file as it stands, then SPO-04d-OUT-003 runs. (src: L119, L271-L273, L312)
- **SPO-04d-EXT-005** Prints the KES verification key as bech32 (`kes_vk`) and the pool id from `cardano-cli <era> stake-pool id --cold-verification-key-file <pool>.node.vkey --output-bech32`, stderr discarded and failure unchecked. The pool id is used for the Koios request in light mode; if cardano-cli fails there it is empty. (src: L110-L115)

> **Upstream quirk:** in light mode a network failure or Koios error is indistinguishable from a pool with no blocks (SPO-04d-MODE-003). The script then computes `onChain = -1`, expects counter 0, and, if the opcert does not carry 0, offers (default Yes) to re-issue with counter 0, which can move the cold counter below the on-chain value. [04e](./04e_checkNodeOpCert.md) in pool-id mode refuses instead (it exits 1 unless exactly one element is returned).

## Outputs

- **SPO-04d-OUT-001** Creates `<pool>.node-<NNN>.opcert` and locks it. On a counter mismatch (SPO-04d-INV-007) it is deleted and a replacement with the same name is created. (src: L139, L154, L260-L261)
- **SPO-04d-OUT-006** If cardano-cli fails at SPO-04d-EXT-003, the script exits before relocking: the opcert (if created) and counter files stay unlocked (mode `0600`). (src: L150-L153)

## Security

- **SPO-04d-SEC-001** The script never prints a signing key. It prints the opcert, the counter file and the expiry file, none of which is secret. (src: L285-L296)
- **SPO-04d-SEC-002** The decrypted cold signing key lives in a shell variable and a process substitution; a software-key run needs the cold key online on the issuing machine. A hardware run keeps it on the device. (src: L145, L152, L164)
- **SPO-04d-SEC-003** In light mode the opcert counter decision depends on an unauthenticated, unretried HTTP response (SPO-04d-MODE-003). (src: L206-L224)

## Domain mapping

Use case `IssueOperationalCertificate(pool, counterOverride?)` on aggregate `StakePool`, touching its `KesState` (`current`, `next`), its `OpCertIssueCounter` and the `OperationalCertificate` it produces. State machine: requires `current == next`, ends with `next = current + 1`.

| Port | Operation | Purpose |
| --- | --- | --- |
| `Store` | `get(KesCounter, KesCounterNext, OpCertIssueCounter, KesVerificationKey[n])`, `put(KesCounterNext, OpCertIssueCounter, OperationalCertificate, KesExpiry)`, `delete(OperationalCertificate)`, `lock` | Artefacts |
| `Vault` / `Signer` | `signOpCert(coldKeyRef, kesVkey, period, counter)` *(new)* | Software key via unseal, hardware key via device; counter advanced by the signer |
| `Ledger` | `newCounter(coldVkey, value)` *(new)*, `poolId(coldVkey)` *(new)* | Counter reset and pool id |
| `ChainQuery` | `tip()`, `opCertCounter(poolId)` *(new)* | KES period input and on-chain counter; online uses `kes-period-info`, light uses Koios |
| `Clock` | `kesPeriod(slot)`, `kesExpiry(period)` *(new)* | KES period and expiry from genesis |
| `UI` | `confirm`, `askPassword` | Prompts |

## Port notes

* Treat counter issuance as one transaction: reserve counter N, sign, verify against the chain, and only then commit N+1 and `kes.counter-next`. The script commits the counter before it verifies (SPO-04d-OUT-002) and deletes the wrong opcert afterwards.
* Distinguish "Koios unreachable" from "pool has no blocks" (SPO-04d-MODE-003); refuse to auto-correct on an unreachable chain.
* Drop the multiplication by `slotLength` in SPO-04d-INV-001 only when parity tests pin the networks to one-second slots; otherwise keep it and test both.
* Compute `expireKESdate` from the period start, not from now (SPO-04d-INV-002).
* Delegate the cold key to a remote or multi-party signer: the opcert signing is one `signOpCert` call whose inputs are public (KES vkey, period, counter), which is a natural remote-signing request.

## Open questions

* Whether cardano-cli also rewrites the counter file's `description` on `issue-op-cert`, or only the `cborHex` counter: settle by diffing the file before and after on the pinned release. The script itself patches the description only after `new-counter` (SPO-04d-EXT-001).
* An empty `qKesOnDiskOperationalCertificateNumber` or non-numeric genesis values (`null`) would give a shell arithmetic error; the resulting exit code depends on bash and is not specified here.
